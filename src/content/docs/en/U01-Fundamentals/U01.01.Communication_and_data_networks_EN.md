# U01.01 — Communication and Data Networks

## 1. Starting point

A network should not initially be understood as a collection of cables, icons, or commands. Before configuring anything, it is useful to understand the problem it solves: it allows systems and applications to exchange information.

When someone sends a photo, opens a website, or downloads a file, the user perceives a simple action. However, for that action to work, several elements must be involved: participants, information, transmission media, signal representation, and shared rules.

What the user sees may look like this:

```text
person A
→ photo
→ person B
```

But real communication requires more structure than that simplified representation.

---

## 2. Basic elements of communication

In general, communication involves at least the following elements.

| Element | Function | Example |
|---|---|---|
| **Sender** | Originates the information | A phone sending a photo |
| **Receiver** | Receives the information | The destination phone |
| **Message** | Information being exchanged | Text, image, audio, video, or application data |
| **Channel or medium** | Carries the signal | Copper, optical fiber, or radio |
| **Encoding** | Physically represents the information | Electrical, optical, or radio signal |
| **Protocol** | Defines rules so participants can understand each other | Ethernet, IP, TCP, HTTPS |

These elements are not always visible to the user. The user may only see an application, a button, or a page, but underneath there is organized communication.

### 2.1. Sender and receiver

> The **sender** is the participant that originates information in a specific communication. The **receiver** is the participant that receives it.

They should not necessarily be understood as people. In networking, the sender and receiver may be applications, services, devices, or interfaces, depending on the level of detail used to analyze the communication.

For example:

```text
web browser
→ requests a page
→ web server
```

In that interaction, the browser initiates a request and the web server replies. In another communication, the same computer may play a different role.

### 2.2. Message

> The **message** is the information being exchanged. It may be something the user directly recognizes, such as a PDF file, an image, or a text message, but it may also be technical information required for the service to work.

In this first session, we do not need to analyze all internal messages yet. It is enough to understand that communication carries information and that this information must be represented somehow in order to travel through the medium.

### 2.3. Channel or medium

> The **medium** or **channel** is what carries the signal between devices or interfaces.

Initial examples:

| Medium | Typical signal type |
|---|---|
| Copper | Electrical |
| Optical fiber | Optical |
| Air | Radio |

A complete communication may cross several media. For example, a laptop may connect to an access point over Wi‑Fi, and from that point onward the infrastructure may continue over copper or optical fiber.

### 2.4. Encoding

For information to travel through a medium, it must be physically represented. That representation may be electrical, optical, or radio-based, among other possibilities.

In U01, the general idea is enough:

```text
information
→ physical representation
→ signal traveling through a medium
```

The detailed study of technologies, connectors, fiber, radio, speeds, interference, and channel quality will be developed in U03.

### 2.5. Protocol

> A **protocol** is a set of rules that allows communication participants to exchange and interpret information in a compatible way.

A protocol is not just the name of a technology. It defines aspects such as:

- what information is exchanged;
- how it is organized;
- when it is sent;
- how it is interpreted;
- what should happen in certain situations.

Examples of protocols that will appear throughout the module:

```text
Ethernet
IP
TCP
UDP
DNS
DHCP
HTTP/HTTPS
SSH
```

In U01, we only need to recognize that compatible rules exist. Layered operation, encapsulation, PDUs, headers, and formal traffic analysis will be developed in U02.

## 3. Medium is not protocol

A common early mistake in networking is mixing up the physical channel with the communication rules.

```text
medium
→ carries or allows signal propagation

protocol
→ defines rules for exchanging and interpreting information
```

A copper cable is not a protocol. A radio signal is not a protocol. Likewise, IP or TCP are not cables or radio waves: they are logical rules and mechanisms that help organize communication.

Example:

```text
copper Ethernet cable
→ physical medium

Ethernet as a link technology
→ communication rules on that link
```

In professional practice both aspects are related, but they should be distinguished from the beginning because they answer different questions.

---

## 4. What is a data network?

> A **data network** is an organized system of devices, interfaces, media, protocols, and services that allows applications and systems to exchange information.

Therefore, a network is not simply:

```text
several computers + cables
```

A network may include:

- desktop computers;
- laptops;
- mobile phones;
- servers;
- printers;
- IP phones;
- cameras;
- sensors;
- virtual machines;
- switches;
- routers;
- access points;
- firewalls;
- physical and virtual interfaces;
- copper, fiber, or radio links;
- services such as DNS, DHCP, authentication, storage, or monitoring.

A professional network should not only connect devices. It should also be manageable, scalable, protected, monitored, and maintained with an appropriate level of service.

---

## 5. A network and the Internet are not the same thing

A network can exist without Internet access.

Example:

```text
PC ── switch ── local server
```

If the PC can access the local server, there is a functional local network even if there is no Internet access.

The Internet is a worldwide interconnection of networks managed by different organizations. It may be an external destination or a set of external networks we want to reach, but it is not the definition of a network.

Simplified Internet access model:

```text
PC
 │
switch
 │
router
 │
provider
 │
Internet
```

Therefore:

```text
network ≠ Internet
```

This difference matters when troubleshooting problems. If someone says “I have no network,” they may mean many different things:

- there is no physical link;
- Wi‑Fi is not working;
- the device is not getting an IP address;
- the device cannot reach its gateway;
- name resolution is failing;
- a specific application does not open;
- there is no Internet access.

Each of these situations requires different observations.

---

## 6. Network expansion and dependencies

Networks have expanded because more and more functions depend on digital communication:

- web;
- email;
- messaging;
- videoconferencing;
- databases;
- business applications;
- storage;
- cloud services;
- remote administration;
- IoT;
- virtualization;
- remote work.

But more services also mean more **dependencies**.

An apparently simple application may depend on several elements:

```text
client
→ local network
→ gateway
→ provider
→ DNS
→ server
→ database
```

This diagram should not be interpreted as a universal path or a complete explanation of all the protocols involved. It is an initial map of possible dependencies.

If an application is not working, we cannot automatically state the cause. The failure may be in the user device, the local network, a name service, an external link, the server, the database, or an access policy.

That is why, from the beginning of the module, it is important to distinguish:

```text
observed symptom
≠
proven cause
```

---

## 7. First professional criterion: observe before concluding

A common mistake is jumping directly from a symptom to a cause.

Example:

```text
"The PDF does not download"
→ "The server is down"
```

That conclusion may be true, but it is not proven by the symptom alone.

A more careful line of reasoning would be:

```text
symptom: the PDF does not download
fact: the file has not been obtained yet
possible hypothesis: there may be a server problem
other hypotheses: DNS, connectivity, authentication, permissions, browser, local network...
next step: obtain more specific evidence
```

Throughout the module, we will learn how to turn symptoms into ordered investigations. In this first session, one idea is enough:

> A technical conclusion can only be as strong as the evidence that supports it.

---

## 8. Summary

By the end of this section, you should be able to explain that:

- communication requires participants, information, a channel or medium, representation, and compatible rules;
- a protocol defines communication rules, while a medium carries a signal;
- a data network is an organized system, not just a set of cables or devices;
- a network can exist without Internet access;
- service growth increases dependencies;
- a symptom alone does not prove a specific cause.

Final map:

```text
communication
│
├── sender
├── receiver
├── message
├── channel/medium
├── encoding
└── protocol

data network
│
├── devices
├── interfaces
├── media
├── protocols
└── services

initial operation
│
├── observe
├── distinguish what works and what fails
├── avoid premature conclusions
└── look for evidence
```
