> **Guiding question:** How do we segment a local network, and how do the segments then communicate?

## Introduction

A local network may use many switches and still behave as a single Layer 2 domain. This can be convenient in a small network, but it creates problems as the network grows: certain broadcasts reach the entire logical network, different functions share the same logical space, and the infrastructure becomes harder to organize.

A **VLAN — Virtual LAN** divides one physical switching infrastructure into multiple logical Layer 2 domains.

The central idea of this unit is:

```text
same physical infrastructure
+
logical segmentation
=
multiple independent Layer 2 networks
```

A VLAN is not simply a number configured on a switch. Several elements must remain consistent:

```text
function
→ VLAN
→ port
→ trunk
→ subnet
→ gateway
→ routing
→ documentation
```

Throughout this unit, keep three ideas separate:

```text
VLAN ≠ subnet ≠ security policy
```

- a **VLAN** provides Layer 2 logical separation;
- an **IP subnet** defines a Layer 3 addressing domain;
- a **security policy** decides which communications are allowed or blocked.

A user VLAN is commonly associated with one IP subnet, but these concepts belong to different layers and must not be treated as identical.

The unit is organized in three blocks:

| Block | Sections | Question it answers |
|---|---|---|
| **Segmentation** (*segmentar*) | 1–3 | Why divide the network, and how do I place each device in its VLAN? |
| **VLAN transport** (*transportar*) | 4–8 | How do several VLANs travel between switches, and how is consistency maintained? |
| **Inter-VLAN routing and operations** (*comunicar y operar*) | 9–13 | How do VLANs communicate, how is the deployment documented, and how is it troubleshot? |

Sections 14–18 are for reference: commands, common mistakes, summary, glossary, and troubleshooting map.

# 1. From a flat network to a segmented network

This section explains **why** VLANs exist before looking at any command. We start from a "flat" network, where every device shares the same Layer 2 domain, and see what problems it causes as it grows. Then we introduce the VLAN as the solution and place it next to two concepts it is often confused with: the IP subnet and security.

| Concept | Question it answers | Example |
|---|---|---|
| **Flat network** | What happens if every device shares one Layer 2 domain? | Administration, students, and servers all receive the same broadcasts |
| **VLAN** (*Virtual LAN*) | How do I logically separate devices connected to the same infrastructure? | VLAN 10 ADMIN, VLAN 20 USERS |
| **Broadcast domain** (*dominio de difusión*) | How far does a broadcast travel? | A VLAN 20 broadcast does not reach VLAN 10 |
| **Subnet** (*subred*) | Which IP addressing does each VLAN use? | VLAN 20 ↔ `10.10.20.0/24` |
| **Segmentation vs. authorization** | Is separating devices enough to decide which traffic is allowed? | No: ACLs or a firewall are needed (U08) |
| **Benefits and limitations** | What do I gain, and not gain, by using VLANs? | Less broadcast, grouping by function |
| **VLAN types** | What roles can a VLAN play in a design? | Data, voice, management, native, default |
| **VLAN matrix** | How do I document the design before configuring? | VLAN–name–subnet–gateway table |

Do not confuse **separating** (VLAN, Layer 2), **addressing** (subnet, Layer 3), and **authorizing** (security policy): they are designed together, but they are different decisions.

## 1.1. What happens in a flat network

Consider an organization with:

- Administration;
- users;
- servers;
- IP telephony;
- management devices.

If every device belongs to the same Layer 2 domain, certain Ethernet broadcasts may propagate through that whole logical network.

The design also expresses no logical separation between functions.

```text
Admin PC ───────────┐
User PC ────────────┼── switching LAN ── Servers
IP Phone ───────────┤
Management ─────────┘
```

The important question is not only "does it work?" but:

> Is it reasonable for all these systems to belong to the same logical domain?

## 1.2. A VLAN creates a logical Layer 2 domain

With VLANs, one physical switch can participate in several separate broadcast domains.

Example:

```text
VLAN 10 → ADMIN
VLAN 20 → USERS
VLAN 30 → SERVERS
VLAN 40 → VOICE
VLAN 99 → MGMT
```

Devices in VLAN 10 do not share the same Layer 2 broadcast domain as devices in VLAN 20.

This allows the network to be organized according to function and requirements.

## 1.3. VLAN and broadcast domain

A VLAN defines a Layer 2 **broadcast domain**.

If a host in VLAN 20 sends an Ethernet broadcast, the switch forwards it within ports that belong to VLAN 20 and through trunks that carry VLAN 20.

It should not automatically appear in VLAN 10, 30, or 40.

The same applies to unknown unicast frames that the switch floods: flooding is limited to the ports of that VLAN.

## 1.4. VLAN and subnet

A typical design uses a different IP subnet for each VLAN.

Example:

| VLAN | Function | Subnet | Gateway |
|---:|---|---|---|
| 10 | ADMIN | `10.10.10.0/24` | `10.10.10.1` |
| 20 | USERS | `10.10.20.0/24` | `10.10.20.1` |
| 30 | SERVERS | `10.10.30.0/24` | `10.10.30.1` |
| 40 | VOICE | `10.10.40.0/24` | `10.10.40.1` |
| 99 | MGMT | `10.10.99.0/24` | `10.10.99.1` |

This association simplifies design, routing, documentation, and troubleshooting.

However, avoid the inaccurate statement:

> "A VLAN is a subnet."

It is not.

A VLAN is Layer 2; a subnet is Layer 3.

## 1.5. VLAN and security

Placing devices in different VLANs **does not by itself define a complete security policy**.

Segmentation can reduce exposure and organize control points, but deciding which traffic is allowed between networks requires Layer 3 or higher mechanisms such as ACLs or firewalls (U08).

Therefore:

```text
segmentation ≠ authorization
```

## 1.6. Benefits and limitations of VLANs

VLANs are used in almost every professional network because they provide several benefits at once:

| Benefit | What it means | Example |
|---|---|---|
| **Smaller broadcast domains** | Each broadcast only reaches devices in its VLAN | An ARP from USERS does not disturb SERVERS |
| **Logical grouping** | Devices are grouped by function, not by physical location | Teachers on three floors in the same VLAN |
| **Security foundation** | Creates boundaries where controls can be applied | ACL between USERS and SERVERS at the gateway (U08) |
| **Cost reduction** | Several logical networks on the same switches and cables | No need for one switch per department |
| **Easier management** | Moving a user means changing a port's VLAN | Office move without recabling |
| **Per-group policies** | Different treatment for each traffic type | Voice VLAN separated from data |

They also have **limitations** you should know from the start:

- different VLANs **do not communicate** without a Layer 3 device (section 9);
- they add **complexity**: more elements must stay consistent (ports, trunks, gateways);
- a configuration error can take down a whole VLAN;
- if misconfigured, they can be attacked (for example, *VLAN hopping*, section 6.7): a VLAN **does not replace** a security policy.

## 1.7. VLAN types by function

Designs refer to VLANs with different roles. They are not technically different "classes" but different **uses** in the design:

| Type | Function | Usual recommendation |
|---|---|---|
| **Default VLAN** | VLAN 1 on Cisco: initially every port belongs to it | Do not use it for users or management; it cannot be deleted or renamed |
| **Data VLAN** (*user VLAN*) | User and server traffic | One per function: ADMIN, USERS, SERVERS… |
| **Voice VLAN** | IP telephony traffic | Separate from data (section 3) |
| **Management VLAN** | Administrative access to network devices | Dedicated VLAN, e.g., 99 (section 11) |
| **Native VLAN** | Untagged traffic on an 802.1Q trunk | VLAN with no users, e.g., 999 (section 6) |
| **Parking / black-hole VLAN** | Destination for unused ports | VLAN with no gateway and ports `shutdown` (section 6.7) |

## 1.8. Design before configuration

Before typing commands, create a VLAN matrix.

| VLAN | Name | Function | Subnet | Gateway |
|---:|---|---|---|---|
| 10 | ADMIN | Administration | `10.10.10.0/24` | `10.10.10.1` |
| 20 | USERS | Users | `10.10.20.0/24` | `10.10.20.1` |
| 30 | SERVERS | Servers | `10.10.30.0/24` | `10.10.30.1` |

Configuration should be the result of a design decision, not the other way around.

### Key idea

> A VLAN is a Layer 2 architecture decision, not just a numeric identifier.

# 2. Creating VLANs and configuring access ports

Once the matrix is designed, it has to be applied to the switch. This section covers the two basic steps—**creating** the VLAN and **assigning** ports to it—and, above all, how to **verify** that the switch state matches the design. We also see where the switch stores VLANs and what happens if a VLAN that still has ports is deleted.

| Concept | Question it answers | Command / example |
|---|---|---|
| **VLAN creation** | Does the VLAN exist on this switch? | `vlan 20` · `name USERS` |
| **Access port** (*puerto de acceso*) | Which VLAN does the connected device belong to? | `switchport mode access` · `switchport access vlan 20` |
| **Untagged frames** | Does the PC need to know its VLAN? | No: the switch classifies by ingress port |
| **Per-VLAN MAC table** | Where is each MAC, and in which VLAN? | `show mac address-table` |
| **Verification** | Does the observed state match the design? | `show vlan brief` · `show interfaces switchport` |
| **VLAN ranges and database** (*vlan.dat*) | Which numbers can I use, and where are they stored? | 1–1005 normal, 1006–4094 extended; `flash:vlan.dat` |

A typical mistake is to think that **creating** the VLAN already **puts** ports into it: they are two separate steps, and each one is verified separately.

## 2.1. Create and name a VLAN

In Cisco IOS, a VLAN can be created with:

```text
Switch(config)# vlan 20
Switch(config-vlan)# name USERS
Switch(config-vlan)# exit
```

The name does not change technical behavior, but it greatly improves readability and documentation.

An identifier such as `20` is less informative than:

```text
20 USERS
```

To delete a VLAN, use `no vlan 20` (read 2.8 before doing so).

## 2.2. Verification

A common verification command is:

```text
show vlan brief
```

Representative output:

```text
VLAN Name                             Status    Ports
---- -------------------------------- --------- -------------------------------
1    default                          active    Gi0/3, Gi0/4, Gi0/5, Gi0/6
10   ADMIN                            active    Gi0/1
20   USERS                            active    Gi0/2, Gi0/8
30   SERVERS                          active
1002 fddi-default                     act/unsup
1003 token-ring-default               act/unsup
1004 fddinet-default                  act/unsup
1005 trnet-default                    act/unsup
```

The output can show:

- existing VLANs;
- names;
- status;
- associated access ports.

Two important details when reading it:

- **trunk ports do not appear** in the `Ports` column: if a port is not listed here, it is not "lost"; check it with `show interfaces trunk` (section 5);
- a VLAN can exist without any ports (VLAN 30 in the example).

The professional question is not "did I type the command?" but:

> Does the observed state match the design?

## 2.3. Access port

An access port is normally used to connect an endpoint that belongs to one data VLAN.

Example:

```text
interface GigabitEthernet0/8
 switchport mode access
 switchport access vlan 20
```

These are two different decisions:

```text
port mode = access
assigned VLAN = 20
```

Confusing them can lead to incorrect troubleshooting.

If several ports share the same configuration, use `interface range`:

```text
Switch(config)# interface range GigabitEthernet0/1 - 6
Switch(config-if-range)# switchport mode access
Switch(config-if-range)# switchport access vlan 20
```

Two Cisco IOS behaviors worth knowing:

- if you assign a port to a VLAN that **does not exist**, the switch creates it automatically (message `% Access VLAN does not exist. Creating vlan 30`), but **without a name**: the design is left incomplete;
- `no switchport access vlan` returns the port to VLAN 1.

To check the mode and VLAN of a specific port:

```text
Switch# show interfaces GigabitEthernet0/8 switchport
Name: Gi0/8
Switchport: Enabled
Administrative Mode: static access
Operational Mode: static access
Administrative Trunking Encapsulation: dot1q
Negotiation of Trunking: Off
Access Mode VLAN: 20 (USERS)
Trunking Native Mode VLAN: 1 (default)
Voice VLAN: none
```

`Administrative Mode` is what was configured; `Operational Mode` is what the port is actually doing.

## 2.4. What happens to host frames?

A PC connected to a normal access port does not need to add an 802.1Q tag to every frame.

The switch knows the VLAN associated with the ingress port and classifies the traffic in that logical context.

Simplified:

```text
untagged frame from PC
→ enters Gi0/8
→ Gi0/8 belongs to VLAN20
→ switch treats frame as VLAN20 traffic
```

## 2.5. Port–VLAN–MAC relationship

The MAC address table must be interpreted in a VLAN context.

Conceptually, the switch needs more than:

```text
MAC → port
```

It needs:

```text
VLAN + MAC → port
```

This allows one physical infrastructure to maintain separate Layer 2 domains.

Observation commands:

```text
show mac address-table
show mac address-table vlan 20
```

Representative output:

```text
          Mac Address Table
-------------------------------------------
Vlan    Mac Address       Type        Ports
----    -----------       --------    -----
  20    0050.7966.6801    DYNAMIC     Gi0/8
  20    0060.2f3a.1b02    DYNAMIC     Gi0/24
```

The MAC learned on `Gi0/24` (a trunk) belongs to a VLAN 20 device connected to another switch.

## 2.6. Moving a host to another VLAN

If a host is connected to a port assigned to another VLAN, its Layer 2 membership changes.

If its IP configuration still belongs to the previous subnet, an inconsistency can appear:

```text
port → VLAN 20
host IP → VLAN 10 subnet
```

The physical link may be `up` while connectivity is still wrong.

### Common mistake

> Seeing `up/up` and concluding that the host belongs to the correct VLAN.

Physical status does not prove logical membership.

## 2.7. VLAN ranges and database

The VLAN identifier (VID) uses 12 bits in the 802.1Q tag (section 4): there are 4096 values, of which 0 and 4095 are reserved. That is why usable VLANs range from **1 to 4094**.

| Range | VLANs | Notes |
|---|---|---|
| **Normal range** | 1–1005 | 1 = default VLAN; 1002–1005 reserved (legacy FDDI/Token Ring), cannot be deleted |
| **Extended range** | 1006–4094 | Used in large networks; with VTP v1/v2 they require transparent mode (section 8) |

Normal-range VLANs are stored in the **`vlan.dat`** file in flash memory, **not** in the `startup-config`. Practical consequence in the lab:

```text
erase startup-config   → erases the configuration, but NOT the VLANs
delete flash:vlan.dat  → erases the VLAN database
reload                 → restart to begin from scratch
```

## 2.8. Deleting a VLAN that still has ports

If you run `no vlan 20` while ports are assigned to VLAN 20:

- the ports **remain configured** with `switchport access vlan 20`;
- but the VLAN no longer exists, so they become **inactive** and their devices lose connectivity;
- those ports **disappear** from `show vlan brief`, which can be misleading.

Before deleting a VLAN, reassign its ports. If it has already happened, recreate the VLAN (or reassign the ports) and verify.

### Key idea

> An access port classifies an endpoint's traffic into a specific VLAN.

# 3. Voice and data on the same physical port

In many offices there is a single network outlet per desk, and an IP phone is connected to it with the PC connected through the phone. This section explains how one switch port can serve both devices while keeping them in different VLANs, and what this means for other configurations such as Port Security (U06).

| Concept | Question it answers | Example |
|---|---|---|
| **Data VLAN** (*access VLAN*) | Which VLAN does PC traffic enter? | `switchport access vlan 20` |
| **Voice VLAN** | Which VLAN does phone traffic enter? | `switchport voice vlan 40` |
| **Tagged voice traffic** | How does the switch tell both traffic types apart? | Voice tagged with 802.1Q; data untagged |
| **Multiple legitimate MACs** | How many MAC addresses appear on the port? | Two: phone + PC |

A voice VLAN is **not** a lesson on QoS or telephony: here we only care about two VLANs coexisting on the same physical access link.

## 3.1. Common scenario

In some networks, an IP phone connects to the switch and a PC connects through the phone.

```text
Switch ── IP Phone ── PC
```

One physical switch port can carry:

- PC data traffic;
- phone voice traffic.

## 3.2. Conceptual configuration

Cisco example:

```text
interface GigabitEthernet0/10
 switchport mode access
 switchport access vlan 20
 switchport voice vlan 40
```

Interpretation:

```text
VLAN 20 → data
VLAN 40 → voice
```

Verification: `show interfaces GigabitEthernet0/10 switchport` shows `Access Mode VLAN: 20 (USERS)` and `Voice VLAN: 40 (VOICE)`.

## 3.3. Tagged and untagged traffic in this scenario

In the Cisco scenario studied here, PC data traffic normally reaches the switch untagged, while the phone tags voice traffic with 802.1Q.

A Cisco phone **learns which voice VLAN to use** through CDP (in multivendor environments, LLDP-MED), so it does not have to be configured by hand on the phone.

This allows two traffic types to share one physical link while remaining logically separated. Although it carries two VLANs, the port is still an **access port** with an added voice VLAN, not a trunk.

## 3.4. Multiple legitimate MAC addresses

Several legitimate MAC addresses may appear on this port:

- phone MAC;
- PC MAC.

This matters when recovering Port Security from U06. An overly restrictive policy (for example, `maximum 1`) could block a valid design.

## 3.5. What is outside this unit

A voice VLAN is not a complete lesson on:

- QoS;
- VoIP signaling;
- codecs;
- call management systems.

The goal here is to understand voice/data coexistence on one access link.

### Key idea

> Sharing one physical port does not require sharing one VLAN.

# 4. IEEE 802.1Q

As long as each port belongs to a single VLAN, the switch knows each frame's VLAN from the ingress port. The problem appears when **one link** must carry frames from several VLANs, for example between two switches: the receiver needs a mark on each frame. This section presents that mark, the **802.1Q tag**, and how to observe it.

| Concept | Question it answers | Example |
|---|---|---|
| **802.1Q tag** (*etiqueta 802.1Q*) | How is a frame's VLAN marked on a shared link? | 4 bytes inserted into the Ethernet header |
| **TPID** (*Tag Protocol Identifier*) | How does the receiver know the frame is tagged? | Value `0x8100` |
| **VID** (*VLAN Identifier*) | Which VLAN does the frame belong to? | VID = 20 |
| **Tagged / untagged** | Does the frame carry a tag at this point? | Untagged on access; tagged on trunk |
| **Capture point** | Why does a capture show the tag or not? | Capture on the PC ≠ capture on the trunk |

You do not need to memorize every bit of the tag: it is enough to know where it goes, what it is for, and which field identifies the VLAN.

## 4.1. The problem

Between switches, we may need to carry frames from several VLANs over one physical link.

The receiving switch needs to know which VLAN each frame belongs to.

The common solution is **IEEE 802.1Q**, the open VLAN tagging standard. (Cisco had its own protocol, ISL, which is now obsolete.)

## 4.2. The 802.1Q tag

802.1Q inserts a **4-byte** tag into the Ethernet frame, between the **source MAC address** and the **EtherType** field. Because the frame changes, the switch **recalculates the FCS**.

```text
Untagged:  | Dest MAC | Source MAC |              | EtherType | Data | FCS |
Tagged:    | Dest MAC | Source MAC | 802.1Q tag   | EtherType | Data | FCS |
                                    (4 bytes)
```

Tag fields:

| Field | Size | Function |
|---|---:|---|
| **TPID** | 16 bits | Indicates an 802.1Q tag (`0x8100`) |
| **PCP** (*Priority Code Point*) | 3 bits | Frame priority (802.1p); used, for example, by voice |
| **DEI** (*Drop Eligible Indicator*) | 1 bit | Marks frames that may be dropped during congestion |
| **VID** (*VLAN Identifier*) | 12 bits | Identifies the VLAN (1–4094) |

At this level, recognize especially:

- **TPID**: identifies the presence of the 802.1Q tag;
- **VID — VLAN Identifier**: identifies the VLAN.

## 4.3. VLAN ID

The VID identifies the VLAN context of a tagged frame.

Conceptually:

```text
Ethernet frame
+
VID 20
→ belongs to VLAN20 while being transported as tagged traffic
```

With 12 bits there are 4096 values; 0 and 4095 are reserved, hence the 1–4094 range in section 2.7.

## 4.4. Access versus trunk

### Access

Normally connects an endpoint and carries one data VLAN. Frames leave and enter **untagged**.

### Trunk

Carries multiple VLANs between devices that need to preserve VLAN identity. Frames travel **tagged**, except those of the native VLAN (section 6).

```text
access → local endpoint classification
trunk  → multiple-VLAN transport
```

The complete path of a VLAN 20 frame between two switches:

```text
PC (untagged) → SW1 access Gi0/8 (VLAN 20)
→ SW1 adds tag VID 20 when sending out the trunk
→ SW2 receives, reads VID 20, removes the tag
→ SW2 delivers untagged out a VLAN 20 access port
```

## 4.5. Capture point

Whether a tag is visible depends on where traffic is captured.

A capture at a host connected to an access port does not necessarily show the same frame format as a capture on a trunk link.

Therefore:

> Always interpret a capture in the context of its capture point.

## 4.6. Observing 802.1Q in Packet Tracer and Wireshark

- **Packet Tracer (Simulation mode):** when you open the PDU on the trunk link, the frame details show the 802.1Q header with the VID; on the access link, they do not.
- **Wireshark:** in a capture taken on a trunk (usually a prepared capture or one taken with a mirror port), the frame shows a line `802.1Q Virtual LAN, PRI: 0, DEI: 0, ID: 20`. Useful filters:

```text
vlan
vlan.id == 20
```

Many network cards remove the tag before passing the frame to the operating system; that is why a capture on a normal PC almost never shows it.

### Key idea

> 802.1Q preserves VLAN identity when multiple VLANs share one link.

# 5. Trunk links and allowed VLANs

With 802.1Q we know **how** each frame's VLAN is marked; now we must configure **the links** that carry those tagged frames. This section covers the static trunk, its verification, and control over which VLANs cross it. The most important idea is that "operational trunk" does not mean "every VLAN works."

| Concept | Question it answers | Command / example |
|---|---|---|
| **Trunk link** (*enlace troncal*) | Which link carries several VLANs? | `switchport mode trunk` |
| **Trunk encapsulation** | Do I need to select 802.1Q explicitly? | `switchport trunk encapsulation dot1q` (on switches that support ISL) |
| **Allowed VLANs** | Which VLANs may the trunk carry? | `switchport trunk allowed vlan 10,20,30,99` |
| **Add / remove** | How do I change the list without replacing it? | `switchport trunk allowed vlan add 40` |
| **Allowed and active** | Does the allowed VLAN really exist on the switch? | `show interfaces trunk` + `show vlan brief` |

Do not confuse **allowed** (what the trunk configuration authorizes) with **active** (what exists and works on the switch).

## 5.1. What is a trunk?

A **trunk** is a link that can carry traffic from multiple VLANs.

It is commonly used between:

- switches;
- a switch and a router in router-on-a-stick;
- a switch and another 802.1Q-aware device (for example, virtualization servers or access points with several SSIDs).

## 5.2. Static configuration

Example:

```text
interface GigabitEthernet0/24
 switchport mode trunk
```

On switches that support two encapsulations (ISL and 802.1Q), such as the Catalyst 3560 multilayer switch in Packet Tracer, you must **select the encapsulation first**; otherwise IOS rejects trunk mode:

```text
interface GigabitEthernet0/1
 switchport trunk encapsulation dot1q
 switchport mode trunk
```

On a Catalyst 2960, which only supports 802.1Q, the first command does not exist and is not needed.

## 5.3. Verification

A particularly useful command is:

```text
show interfaces trunk
```

Representative output:

```text
Port        Mode         Encapsulation  Status        Native vlan
Gi0/24      on           802.1q         trunking      999

Port        Vlans allowed on trunk
Gi0/24      10,20,30,99

Port        Vlans allowed and active in management domain
Gi0/24      10,20,99

Port        Vlans in spanning tree forwarding state and not pruned
Gi0/24      10,20,99
```

It can provide evidence about:

- trunk interfaces (`Status: trunking`);
- mode (`on` = static trunk; `auto` or `desirable` = negotiated by DTP);
- encapsulation;
- native VLAN;
- allowed VLANs;
- VLANs that are allowed **and active** (in the example, VLAN 30 is allowed but does not exist on this switch);
- VLANs in the STP forwarding state.

If a port does not appear in `show interfaces trunk`, it is **not** working as a trunk.

## 5.4. A trunk being `up` does not prove service for every VLAN

This reasoning is essential.

You may observe:

```text
trunk operational
VLAN10 works
VLAN20 fails
```

That reduces the hypothesis space.

If VLAN10 uses the same physical link successfully, the physical medium and part of the trunk configuration have already demonstrated that they work.

Look for a VLAN20-specific difference.

## 5.5. Allowed VLAN

By default, a trunk allows **all** VLANs (1–4094). You can restrict which VLANs it is authorized to carry.

Example:

```text
switchport trunk allowed vlan 10,20,30,99
```

The list should follow the design.

There is no benefit in carrying a VLAN over a link that does not need it: it only adds unnecessary broadcasts and room for error.

## 5.6. Replacing versus adding

In Cisco IOS, `switchport trunk allowed vlan <list>` **replaces** the whole list. This is one of the most common mistakes: trying to add one VLAN and leaving out all the others.

| Command | Effect |
|---|---|
| `switchport trunk allowed vlan 10,20` | The list becomes **exactly** 10 and 20 |
| `switchport trunk allowed vlan add 30` | **Adds** 30 to the existing list |
| `switchport trunk allowed vlan remove 20` | **Removes** 20 from the existing list |
| `switchport trunk allowed vlan except 30` | Allows all **except** 30 |
| `switchport trunk allowed vlan all` | Allows all again |
| `switchport trunk allowed vlan none` | Allows none |

Example of the mistake:

```text
State: allowed 10,20,99
Typed: switchport trunk allowed vlan 30
Result: allowed 30   → VLANs 10, 20, and 99 stop passing
Correct: switchport trunk allowed vlan add 30
```

Before making a change, verify the current state.

Professional sequence:

```text
read current state
→ compare with design
→ decide change
→ apply minimum change
→ verify
```

## 5.7. `allowed` versus `allowed and active`

A VLAN can be allowed on the trunk but not exist locally or not be active.

Therefore distinguish:

```text
allowed by trunk policy
≠
existing and active
```

The combination of:

```text
show interfaces trunk
show vlan brief
```

can provide complementary evidence.

Remember: the VLAN must exist on **every** switch it passes through, including intermediate switches that only carry it over trunks and have no access ports in it.

### Key idea

> An operational trunk does not prove that every required VLAN is being carried correctly.

# 6. Native VLAN and DTP

A trunk has two configuration details that cause many problems if left to chance: the **native VLAN**, which decides what happens to untagged frames, and **DTP**, the Cisco protocol that can turn a port into a trunk without our having decided it. This section explains both, how to detect inconsistencies between the two ends, and which good practices protect the design.

| Concept | Question it answers | Command / example |
|---|---|---|
| **Native VLAN** (*VLAN nativa*) | Which VLAN receives the trunk's untagged frames? | `switchport trunk native vlan 999` |
| **Native VLAN mismatch** | Does the native VLAN match on both ends? | SW1 = 999, SW2 = 1 → inconsistency |
| **DTP** (*Dynamic Trunking Protocol*) | Can a port negotiate on its own whether it is a trunk? | `dynamic auto`, `dynamic desirable` |
| **Static mode, nonegotiate** | How do I stop negotiation from deciding for me? | `switchport mode trunk` + `switchport nonegotiate` |
| **VLAN hardening** | How do I reduce attacks such as *VLAN hopping*? | Native VLAN with no users, DTP disabled, unused ports parked |

DTP decides **whether** a link is a trunk; it never decides **which** VLANs should cross it or **what** the native VLAN should be: that is design.

## 6.1. Native VLAN

An 802.1Q trunk includes the concept of a **native VLAN**.

In common Cisco configurations, traffic belonging to the native VLAN is carried **untagged**, and any untagged frame arriving on the trunk is assigned to the native VLAN. By default, the native VLAN is **VLAN 1**.

It is changed on the trunk interface:

```text
interface GigabitEthernet0/24
 switchport mode trunk
 switchport trunk native vlan 999
```

For this course, the most important point is consistency between both ends: **both sides of the trunk must use the same native VLAN**.

## 6.2. Native VLAN mismatch

Suppose:

```text
SW1 Gi0/24 native VLAN = 99
SW2 Gi0/24 native VLAN = 1
```

The design is inconsistent. Untagged traffic that SW1 sends as VLAN 99 is received by SW2 as VLAN 1: two different VLANs get "mixed."

Typical evidence on Cisco devices:

- CDP console messages such as `%CDP-4-NATIVE_VLAN_MISMATCH: Native VLAN mismatch discovered on GigabitEthernet0/24 (99), with SW2 GigabitEthernet0/24 (1)`;
- a different `Native vlan` column in `show interfaces trunk` on each end;
- STP may block the port for those VLANs as a protective measure.

Do not "fix" it by changing one side at random.

First determine the intended design.

Then:

```text
expected state
→ observed state on both ends
→ discrepancy
→ minimum change
→ verification
```

## 6.3. DTP

**DTP — Dynamic Trunking Protocol** is a Cisco proprietary protocol that can participate in trunk negotiation.

Switch port modes:

| Mode | Command | Behavior |
|---|---|---|
| **Access** | `switchport mode access` | Always access; never forms a trunk |
| **Trunk** | `switchport mode trunk` | Always trunk; also sends DTP messages |
| **Dynamic auto** | `switchport mode dynamic auto` | Waits: forms a trunk only if the other side asks |
| **Dynamic desirable** | `switchport mode dynamic desirable` | Actively asks to form a trunk |

Negotiation result (overview, not for memorizing):

| SW1 \ SW2 | access | trunk | dynamic auto | dynamic desirable |
|---|---|---|---|---|
| **access** | access | inconsistent (avoid) | access | access |
| **trunk** | inconsistent (avoid) | trunk | trunk | trunk |
| **dynamic auto** | access | trunk | **access** | trunk |
| **dynamic desirable** | access | trunk | trunk | trunk |

The most important cell is **auto + auto = access**: two switches with the default configuration of many models (for example, the 2960 uses `dynamic auto`) do **not** form a trunk even if the student expects them to.

The important idea is that negotiation-based configuration may produce a state different from what a beginner expected. `show interfaces <int> switchport` shows the difference between `Administrative Mode` (configured) and `Operational Mode` (actual result).

## 6.4. Explicit configuration

Many professional designs prefer to configure explicitly whether a link must be access or trunk.

This improves:

- predictability;
- readability;
- operational security;
- troubleshooting.

When DTP negotiation is not needed, use:

```text
interface GigabitEthernet0/24
 switchport mode trunk
 switchport nonegotiate
```

`switchport nonegotiate` stops sending DTP messages. It is accepted only if the port is in static `access` or `trunk` mode; with a `dynamic` mode, IOS rejects it. On an access port, `switchport mode access` already disables trunk negotiation.

## 6.5. DTP does not replace design

Successful trunk negotiation does not answer:

- which VLANs should cross the link?;
- what should the native VLAN be?;
- should that trunk exist at all?;
- is the result consistent with the topology?

## 6.6. An explicit trunk template

Combining sections 5 and 6, a well-defined trunk between two switches looks like this (and **must be the same on both ends**):

```text
interface GigabitEthernet0/24
 description TRUNK to SW2 Gi0/24
 switchport mode trunk
 switchport trunk native vlan 999
 switchport trunk allowed vlan 10,20,40,99
 switchport nonegotiate
```

## 6.7. VLAN security good practices

A misconfigured VLAN can let an attacker send traffic into another VLAN (**VLAN hopping**). The two classic techniques are:

- **switch spoofing**: the attacking device negotiates a trunk through DTP with a port in `dynamic` mode;
- **double tagging**: the attacker, in the native VLAN, sends frames with two tags; the first switch removes the outer tag and the inner tag carries the frame into another VLAN.

Good practices that prevent them:

| Practice | What it prevents |
|---|---|
| User ports in `switchport mode access` | Negotiating trunks from a PC |
| `switchport nonegotiate` on trunks | Unnecessary DTP messages |
| Dedicated native VLAN with no users (e.g., 999), different from VLAN 1 | Double tagging |
| Do not use VLAN 1 for users or management | Exposing the default VLAN |
| Unused ports in a parking VLAN and `shutdown` | Unauthorized connections |
| `allowed` list limited to the design | Carrying unnecessary VLANs |

Example for unused ports:

```text
interface range GigabitEthernet0/15 - 22
 switchport mode access
 switchport access vlan 666
 shutdown
```

These measures complement the Layer 2 security features seen in U06 (Port Security, BPDU Guard, DHCP Snooping).

### Key idea

> Automatic negotiation never replaces an architecture decision.

# 7. VLANs with STP and EtherChannel

In U06 we studied STP (loop prevention) and EtherChannel (link aggregation). When those same links become trunks carrying several VLANs, new questions appear: does STP decide the same way for every VLAN? Where is the trunk configured on a Port-channel? This section does **not** reteach STP or LACP; it only connects them with VLANs.

| Concept | Question it answers | Command / example |
|---|---|---|
| **Per-VLAN STP** (*PVST+ / Rapid PVST+*) | Which path does STP use for each VLAN? | `show spanning-tree vlan 20` |
| **Per-VLAN root** | Can I balance load by choosing a different root per VLAN? | `spanning-tree vlan 10 root primary` |
| **VLAN-specific failure** | What specific difference does the failing VLAN have? | allowed, existence, STP, gateway |
| **Port-channel trunk** | Where is a bundle's trunk configured? | On `interface Port-channel1` |
| **Verification order** | What do I check first if a Po trunk fails? | `show etherchannel summary` → `show interfaces trunk` |

A failure can be in the VLAN, the trunk, STP, or the bundle: evidence must separate those decision layers.

## 7.1. Recovering U06 knowledge

In U06 we learned that:

- STP/RSTP prevents Layer 2 loops;
- EtherChannel combines several links into one logical interface;
- LACP can negotiate aggregation.

U07 reuses those concepts when links carry VLAN traffic.

## 7.2. STP and VLANs

Cisco switches run **one STP instance per VLAN** by default (PVST+ or Rapid PVST+). That is why the Bridge ID includes the VLAN number (*extended system ID*), as we saw in U06.

In Cisco environments, STP information can be observed for a specific VLAN.

Example:

```text
show spanning-tree vlan 20
```

This can help answer:

- which switch is root for that VLAN?;
- which ports are forwarding?;
- which path is blocked?

Because each VLAN has its own tree, you can **balance load** by choosing a different root for each group of VLANs:

```text
SW1(config)# spanning-tree vlan 10,99 root primary
SW2(config)# spanning-tree vlan 20,40 root primary
```

This way, a link that is blocked for VLAN 10 can be forwarding for VLAN 20.

We do not relearn STP from scratch.

## 7.3. One VLAN fails while another works

This pattern provides useful evidence.

If two VLANs use similar links but only one fails, look for VLAN-specific differences:

- allowed VLAN list;
- VLAN existence;
- STP state for that VLAN;
- gateway for that VLAN.

## 7.4. EtherChannel as a trunk

A Port-channel can carry multiple VLANs.

Conceptually:

```text
physical members
→ LACP
→ Port-channel
→ trunk on the logical interface
```

Switching configuration must be applied consistently to the proper logical interface:

```text
interface range GigabitEthernet0/1 - 2
 channel-group 1 mode active
!
interface Port-channel1
 switchport mode trunk
 switchport trunk native vlan 999
 switchport trunk allowed vlan 10,20,30,40,99
```

Members must have compatible parameters (mode, native, allowed, speed). A mismatch on one member can leave it out of the bundle (in U06, suspended state).

## 7.5. Verification order

If the design uses `Po1` as a trunk and a problem appears, a high-value first check is:

```text
show etherchannel summary
```

Then:

```text
show interfaces trunk
```

The `show interfaces trunk` output should list `Po1`, not the physical members.

Do not troubleshoot one physical member in isolation while ignoring the bundle state.

### Key idea

> VLAN, STP, and EtherChannel are related decision layers; evidence must separate which one explains the symptom.

# 8. Centralized VLAN administration with VTP

Creating the same VLANs by hand on twenty switches is slow and error-prone. Cisco offers **VTP** to distribute the VLAN list from a central point. This section explains what VTP does, what it does not do, its modes, and above all its **operational risk**: one badly introduced switch can erase the VLANs of the whole network.

| Concept | Question it answers | Command / example |
|---|---|---|
| **VTP** (*VLAN Trunking Protocol*) | How do I distribute the VLAN list to several switches? | VTP advertisements over trunks |
| **VTP domain** | Which switches share the same information? | `vtp domain COMPANY` |
| **Modes** (*server / client / transparent*) | Who creates VLANs and who receives them? | `vtp mode client` |
| **Configuration revision** | Which version of the VLAN database is the newest? | Revision 12 > revision 8 |
| **Verification** | Which domain, mode, and revision does the switch have? | `show vtp status` |
| **VTPv3** | How is risk reduced in modern versions? | *Primary server* |

VTP only distributes **the VLAN list** (number and name). It does not configure access ports, trunks, gateways, or routing.

## 8.1. What problem does it address?

In a network with many switches, manually creating the same VLAN information everywhere can introduce inconsistencies.

**VTP — VLAN Trunking Protocol** is a Cisco technology that can distribute certain VLAN information inside a VTP domain. VTP advertisements travel **only over trunk links**.

## 8.2. What VTP does NOT do

VTP does not replace:

- trunks;
- access ports;
- gateways;
- routing;
- ACLs;
- documentation.

Its role is narrower.

## 8.3. VTP domain

Participating devices must use the expected administrative domain: the same **domain name** (case-sensitive), the same **version**, and, if used, the same **password**.

A domain mismatch can prevent the expected behavior.

A new switch has an empty (*null*) domain and adopts the domain of the first VTP advertisement it receives on a trunk.

## 8.4. Classic modes

| Mode | Creates / modifies / deletes VLANs? | Applies advertisements? | Forwards advertisements? | Where VLANs are stored |
|---|---|---|---|---|
| **Server** (default) | Yes | Yes | Yes | `vlan.dat` |
| **Client** | No (VTP v1/v2) | Yes | Yes | `vlan.dat` |
| **Transparent** | Yes, locally only | No | Yes (without applying them) | `vlan.dat` and `running-config` |

### Server

Can create/modify VLAN information and participate in distribution. It is the default mode.

### Client

Receives information inside the domain and applies it. In VTP v1/v2 it cannot create, modify, or delete VLANs locally.

### Transparent

Does not apply the distributed VLAN database: it keeps its own local VLANs and simply forwards advertisements over its trunks. It is the mode required to use extended-range VLANs with VTP v1/v2.

Exact behavior varies by version and platform, so verify the real state instead of relying on a memorized description.

Basic configuration:

```text
Switch(config)# vtp domain COMPANY
Switch(config)# vtp mode server
Switch(config)# vtp password VTP-Key
Switch(config)# vtp version 2
```

On the other switches in the domain: `vtp domain COMPANY`, `vtp mode client`, and the same password.

## 8.5. Configuration revision

In classic VTP, the **configuration revision** reflects the state of the distributed database. Each VLAN change on a server increases the number by 1.

A switch in the domain accepts the advertised database if its revision is **higher** than its own, **even if it comes from a client**.

Historically, connecting a switch with unexpected VTP information could produce unwanted changes in a domain: for example, a switch reused from a lab, with the same domain and a higher revision, can **overwrite** the VLAN list of the whole network and leave ports without a VLAN.

Before adding a used switch, reset its revision to 0, for example by setting it to transparent mode (or changing the domain name) and then returning it to the intended mode.

VTP therefore requires disciplined operational handling.

## 8.6. Verification

Typical command:

```text
show vtp status
```

It can provide information about:

- version (`VTP Version`);
- domain (`VTP Domain Name`);
- mode (`VTP Operating Mode`);
- revision (`Configuration Revision`);
- VLAN count (`Number of existing VLANs`).

Another useful option is `show vtp password` to check the configured password.

## 8.7. VTPv3 and VTP pruning

VTPv3 adds control improvements and the concept of a **primary server**: only that server can modify the VLAN database, which reduces the risk of accidental overwrites. It also supports extended-range VLANs.

**VTP pruning** (`vtp pruning` on the server) avoids sending flooded traffic over a trunk for VLANs that have no active ports on the other side.

In this course both are treated as a professional evolution, not as an exhaustive configuration block.

## 8.8. Why VTP has limited weight here

Understanding VTP helps interpret Cisco networks and some curriculum scenarios.

However, a professional VLAN design must not depend on making VTP the center of the architecture. Many organizations use **transparent mode** (or disable VTP) and create VLANs by hand or with automation tools.

### Key idea

> Centralizing information can reduce repetitive work, but it can also amplify the impact of an incorrect configuration.

# 9. Why inter-VLAN routing is required

So far we have separated the network into VLANs. But separation has a price: a USERS device can no longer talk to a SERVERS server through the switches alone. This section explains **why** a Layer 3 device is needed and what role the **default gateway** plays, before configuring any solution.

| Concept | Question it answers | Example |
|---|---|---|
| **Layer 2 / Layer 3 boundary** | Why can't two VLANs talk through the switch? | Different VLANs = different subnets |
| **Per-VLAN default gateway** | Where does the host send remote traffic? | VLAN 20 → `10.10.20.1` |
| **Switching vs. routing** | Does a trunk connect VLANs? | No: it only carries them |
| **Inter-VLAN routing** (*routing entre VLAN*) | Which devices can do it? | Router (ROAS) or multilayer switch (SVI) |

This section recovers the **local/remote** decision from U04: the host compares the destination IP with its prefix and, if it is remote, sends the frame to its gateway.

## 9.1. Layer 2 versus Layer 3

Suppose:

```text
PC-A → VLAN10 → 10.10.10.25/24
PC-B → VLAN20 → 10.10.20.30/24
```

These hosts are in different VLANs and different IP subnets.

PC-A uses its subnet mask to determine that `10.10.20.30` is not local.

It therefore does not try to deliver the traffic directly to the destination through local switching.

It needs its **default gateway**.

## 9.2. Gateway per VLAN

Each subnet needs an appropriate gateway if it must communicate with other networks.

Example:

```text
VLAN10 / 10.10.10.0/24 → gateway 10.10.10.1
VLAN20 / 10.10.20.0/24 → gateway 10.10.20.1
```

The gateway must be **in the same VLAN and subnet** as the hosts; otherwise the host cannot reach it through ARP.

## 9.3. Switching does not replace routing

A trunk can carry VLAN10 and VLAN20 between switches, but that does not automatically allow communication between them.

```text
trunk = transports Layer 2 domains
routing = connects different Layer 3 networks
```

## 9.4. Simplified flow

When PC-A communicates with PC-B:

```text
PC-A identifies a remote destination
→ sends to VLAN10 gateway (ARP for the gateway MAC)
→ Layer 3 device receives
→ selects VLAN20 network
→ forwards toward VLAN20 (ARP for PC-B's MAC)
→ PC-B receives
```

## 9.5. Three ways to route between VLANs

| Solution | How it works | Current use |
|---|---|---|
| **Legacy inter-VLAN routing** | One physical router interface per VLAN, each to an access port | Obsolete: does not scale (one interface and one cable per VLAN) |
| **Router-on-a-stick** (*ROAS*) | One physical router interface with subinterfaces, over a trunk | Small networks and labs (section 10) |
| **Multilayer switch with SVIs** (*Layer 3 switch*) | Virtual interfaces per VLAN inside the switch itself | Campus networks (section 11) |

### Key idea

> A VLAN separates Layer 2 domains; communication between different IP subnets requires a Layer 3 routing decision.

# 10. Router-on-a-stick

The first practical inter-VLAN routing solution uses **one router and a single cable**. The trick is to combine what we saw in the previous block (an 802.1Q trunk) with a new idea on the router side: **subinterfaces**, one per VLAN, each with the IP address that will act as the gateway.

| Concept | Question it answers | Command / example |
|---|---|---|
| **Router-on-a-stick** (*ROAS*) | How does a router route several VLANs with one interface? | Trunk + subinterfaces |
| **Switch-side trunk** | How does each VLAN reach the router? | Port toward the router in `switchport mode trunk` |
| **Subinterface** (*subinterfaz*) | Which logical interface represents each VLAN on the router? | `interface GigabitEthernet0/0.10` |
| **dot1Q encapsulation** | Which VLAN does each subinterface serve? | `encapsulation dot1Q 10` |
| **Gateway address** | Which IP do hosts use as their default gateway? | `10.10.10.1` |
| **Verification** | Does each piece work: switch, router, and host? | `show interfaces trunk`, `show ip interface brief`, `show ip route` |

The subinterface number (`.10`) is only a name; what binds it to the VLAN is `encapsulation dot1Q 10`. For clarity, they are made to match.

## 10.1. Concept

**Router-on-a-stick — ROAS** allows one physical router interface to route for multiple VLANs by using subinterfaces.

```text
Switch ===== trunk ===== Router
                         ├─ .10 → VLAN10
                         ├─ .20 → VLAN20
                         └─ .30 → VLAN30
```

## 10.2. Switch side

The link toward the router must carry the required VLANs.

Conceptually:

```text
port toward router
→ trunk
→ correct allowed VLANs
```

Example:

```text
interface GigabitEthernet0/1
 description TRUNK to R1 Gi0/0
 switchport mode trunk
 switchport trunk allowed vlan 10,20,30,99
```

Routers do not negotiate DTP: the switch port must be in static `switchport mode trunk`.

## 10.3. Subinterfaces

Representative example:

```text
interface GigabitEthernet0/0
 no ip address
 no shutdown
!
interface GigabitEthernet0/0.10
 encapsulation dot1Q 10
 ip address 10.10.10.1 255.255.255.0
!
interface GigabitEthernet0/0.20
 encapsulation dot1Q 20
 ip address 10.10.20.1 255.255.255.0
```

Each subinterface is associated with a VLAN through `encapsulation dot1Q`. You must enter `encapsulation` **before** `ip address`; otherwise IOS does not accept the address.

Important details:

- the **physical interface** has no IP address, but it **does** need `no shutdown`: if it is shut down, all its subinterfaces are down too;
- if the trunk's native VLAN carries traffic the router must handle, its subinterface is marked as native: `encapsulation dot1Q 999 native` (it must match the switch's native VLAN).

## 10.4. Gateway address

The address configured on the subinterface normally acts as the gateway for hosts in that VLAN.

For example:

```text
VLAN20
network 10.10.20.0/24
gateway 10.10.20.1
```

When the subinterfaces are up, the router has a **connected route** for each VLAN, so it can already route between them without additional routes (static routing is studied in U08).

If hosts get their IP through DHCP and the server is in another VLAN, the gateway will need a relay agent (`ip helper-address`), which is covered in U08.

## 10.5. Verification

### On the switch

```text
show vlan brief
show interfaces trunk
```

### On the router

```text
show ip interface brief
show running-config interface GigabitEthernet0/0.20
show ip route
show vlans
```

`show ip route` should show a `C` (connected) route for each subinterface: `C 10.10.10.0/24 is directly connected, GigabitEthernet0/0.10`. `show vlans` (on the router) shows which VLAN each subinterface serves.

### On the host

- IP address;
- subnet mask/prefix;
- gateway;
- reachability to gateway;
- reachability to another VLAN.

## 10.6. Common mistake: blaming routing too early

If a host cannot even reach its gateway, first consider:

- access port;
- wrong VLAN;
- trunk;
- missing allowed VLAN;
- incorrect subinterface (for example, `encapsulation dot1Q 20` on the VLAN 10 subinterface);
- router physical interface in `shutdown`;
- host addressing.

## 10.7. Limitations of ROAS

- **A single link** carries all inter-VLAN traffic, which goes up to the router and back down the same cable: it can become a bottleneck.
- **Single point of failure:** if the link or the router fails, all inter-VLAN communication is lost.

That is why ROAS suits small networks and labs, while larger networks prefer a multilayer switch.

### Key idea

> ROAS combines a Layer 2 trunk with multiple logical Layer 3 interfaces.

# 11. SVI, multilayer switching, and management VLAN

The second inter-VLAN routing solution places the gateway **inside the switch itself**: a multilayer switch has one virtual interface (SVI) per VLAN and routes between them with no extra cable. The same tool, the SVI, has a second use on Layer 2 switches: giving the switch a **management IP address**. This section distinguishes both uses, because they are easily confused.

| Concept | Question it answers | Command / example |
|---|---|---|
| **SVI** (*Switch Virtual Interface*) | Which Layer 3 interface represents a VLAN inside the switch? | `interface vlan 20` |
| **Multilayer / Layer 3 switch** (*switch multicapa*) | Can a switch route between VLANs? | `ip routing` + one SVI per VLAN |
| **Routed port** (*puerto enrutado*) | How do I connect the Layer 3 switch to a router as if it were a router interface? | `no switchport` + `ip address` |
| **Management SVI** | How do I manage a Layer 2 switch over IP? | `interface vlan 99` + `ip default-gateway` |
| **SVI status** | Why is an SVI `down`? | VLAN does not exist or has no active ports |
| **ROAS vs. Layer 3 switch** | Which solution do I choose? | Size, performance, equipment |

Having an SVI does **not** mean the switch routes: on a Layer 2 switch, the SVI is only for managing it.

## 11.1. What is an SVI?

An **SVI — Switch Virtual Interface** is a logical interface associated with a VLAN.

Example:

```text
interface vlan 20
 ip address 10.10.20.1 255.255.255.0
 no shutdown
```

Its exact role depends on the device type and design.

## 11.2. SVI as a gateway

On a **multilayer switch**, an SVI can act as the gateway for a VLAN when the device performs routing.

With several SVIs:

```text
VLAN10 → SVI 10 → 10.10.10.1
VLAN20 → SVI 20 → 10.10.20.1
VLAN30 → SVI 30 → 10.10.30.1
```

With routing enabled, the multilayer switch can route between these networks.

In Cisco IOS, routing is enabled with:

```text
ip routing
```

Complete minimal configuration on a multilayer switch (for example, a Catalyst 3560 in Packet Tracer):

```text
MLS(config)# ip routing
MLS(config)# vlan 10
MLS(config-vlan)# name ADMIN
MLS(config-vlan)# vlan 20
MLS(config-vlan)# name USERS
MLS(config-vlan)# exit
MLS(config)# interface vlan 10
MLS(config-if)# ip address 10.10.10.1 255.255.255.0
MLS(config-if)# no shutdown
MLS(config-if)# interface vlan 20
MLS(config-if)# ip address 10.10.20.1 255.255.255.0
MLS(config-if)# no shutdown
```

Without `ip routing`, the switch has an IP address in each VLAN (you can ping each SVI from its own VLAN) but it does **not** forward between them. `show ip route` then shows `Default gateway is not set` or similar instead of the connected routes.

To connect the multilayer switch to a router (for example, toward the Internet), a port can be turned into a **routed port**:

```text
interface GigabitEthernet0/1
 no switchport
 ip address 10.10.255.1 255.255.255.252
```

Routing toward other networks from that point is studied in U08 (static) and U09 (dynamic).

## 11.3. Management SVI

On a Layer 2 switch, an SVI can be used to provide an IP management address for the switch itself.

Conceptual example:

```text
VLAN99 → MGMT
SVI VLAN99 → switch management address
```

Configuration on a Layer 2 access switch (SW1):

```text
SW1(config)# vlan 99
SW1(config-vlan)# name MGMT
SW1(config-vlan)# exit
SW1(config)# interface vlan 99
SW1(config-if)# ip address 10.10.99.11 255.255.255.0
SW1(config-if)# no shutdown
SW1(config-if)# exit
SW1(config)# ip default-gateway 10.10.99.1
```

- `ip default-gateway` is essential to manage the switch **from another subnet**: a Layer 2 switch does not route and needs to know where to send its replies.
- The management VLAN must be allowed on the trunks leading to the administration station.
- Good practice: use a dedicated VLAN (not VLAN 1).
- Secure remote access (SSH, VTY lines) over this IP address is covered in U08.

This does not automatically mean that the switch is routing between all VLANs.

## 11.4. Operational state of an SVI

Do not interpret an SVI only by reading the configured lines.

Check its real operational state.

Useful commands:

```text
show ip interface brief
show vlan brief
```

An SVI is `up/up` only if **all three** conditions are met:

1. the VLAN **exists** in the switch's VLAN database;
2. there is **at least one active port** in that VLAN (a connected access port or a trunk carrying it in forwarding state);
3. the SVI is **not** `shutdown`.

Troubleshooting example: `Vlan30 10.10.30.1 YES manual up down` means the SVI is enabled but there is no active port in VLAN 30 (or the VLAN does not exist).

## 11.5. ROAS versus multilayer switch

| Aspect | Router-on-a-stick | Multilayer switch |
|---|---|---|
| Gateway | router subinterfaces | SVIs |
| Path to gateway | trunk to router | internal Layer 3 switching |
| Performance | limited by a single link | hardware Layer 3 switching, much higher |
| Scalability | suitable for small/lab scenarios | better for campus designs |
| Dependency | physical router link | Layer 3 switch capability |
| Key command | `encapsulation dot1Q` | `ip routing` + `interface vlan` |

There is no single universal solution; the choice depends on size, requirements, and available equipment.

## 11.6. IPv6

The same VLAN/gateway separation idea can apply to IPv6, although IPv6 addressing and neighbor discovery mechanisms were studied in U05.

At this point, recognize that a VLAN can carry IPv4, IPv6, or both, and that a subinterface or an SVI can also have an IPv6 address (`ipv6 address`), with `ipv6 unicast-routing` enabled if the device must route IPv6.

### Key idea

> An SVI is a logical interface associated with a VLAN; it can support management or routing depending on the device and design.

# 12. Integrated design and deployment

So far we have seen each piece separately. In a real network they must all fit together and also be **documented** so that someone else can understand and change them without breaking anything. This section brings the pieces together in four design documents and a change procedure.

| Document / practice | Question it answers | Content |
|---|---|---|
| **VLAN matrix** | Which VLANs exist and what for? | VLAN, name, subnet, gateway, use |
| **Port map** | What is connected to each port, and in which mode? | Switch, port, mode, VLAN, use |
| **Trunk table** | Which VLANs cross each link? | Native, allowed, resilience |
| **Change plan** | How do I apply a change safely? | Pre-check → change → verification → rollback |
| **Minimal change** | How do I know which modification fixed or broke something? | Previous state → specific change → resulting state |

Documentation is **not** a final add-on: it is part of the deployment.

## 12.1. Designing a maintainable system

A professional VLAN deployment should be understandable from its documentation.

It is not enough that it "works right now."

The design should make clear:

- which VLANs exist;
- what each VLAN is for;
- which subnet each uses;
- its gateway;
- which ports are access;
- which links are trunks;
- which VLANs cross each trunk;
- which native VLAN is used;
- where routing occurs;
- which redundancy mechanisms exist.

## 12.2. VLAN matrix

Example:

| VLAN | Name | Subnet | Gateway | Use |
|---:|---|---|---|---|
| 10 | ADMIN | `10.10.10.0/24` | `10.10.10.1` | Administration |
| 20 | USERS | `10.10.20.0/24` | `10.10.20.1` | Users |
| 30 | SERVERS | `10.10.30.0/24` | `10.10.30.1` | Servers |
| 40 | VOICE | `10.10.40.0/24` | `10.10.40.1` | Telephony |
| 99 | MGMT | `10.10.99.0/24` | `10.10.99.1` | Management |
| 666 | PARKING | — | — | Unused ports |
| 999 | NATIVE | — | — | Trunk native VLAN (no users) |

## 12.3. Port table

| Switch | Port | Mode | VLAN/Allowed | Use |
|---|---|---|---|---|
| SW1 | Gi0/1 | access | 10 | Admin PC |
| SW1 | Gi0/2 | access + voice | data 20 / voice 40 | Phone + PC |
| SW1 | Gi0/15–22 | access, `shutdown` | 666 | Unused ports |
| SW1 | Gi0/23 | trunk | 10,20,40,99 | SW2 |
| SW1 | Po1 | trunk | 10,20,30,40,99 | SW3 |

## 12.4. Trunk table

| Link | Native | Allowed | Resilience | Note |
|---|---:|---|---|---|
| SW1–SW2 | 999 | 10,20,40,99 | STP | VLAN30 not required |
| SW1–SW3 | 999 | 10,20,30,40,99 | Po1/LACP | Port-channel |

These values are design examples, not universal rules. Native VLAN 999 has no users; it does not need to be in the `allowed` list because it must not carry user traffic.

## 12.5. Change plan

A simple professional sequence is:

```text
pre-check
→ change
→ verification
→ rollback if required
```

### Pre-check

Before changing anything:

- read current configuration;
- verify VLANs;
- verify trunks;
- verify STP/EtherChannel;
- verify gateways;
- have a backup or rollback approach (for example, `copy running-config startup-config` before starting and saving the `show` outputs).

### Change

Apply only the planned modifications.

### Verification

Check:

- VLANs;
- ports;
- MAC learning;
- trunks;
- allowed/native;
- STP/EtherChannel;
- gateway;
- intra-VLAN connectivity;
- inter-VLAN connectivity.

### Rollback

Know what to revert if validation fails (for example, the inverse command of each change: `switchport trunk allowed vlan remove 30` to undo an `add 30`).

## 12.6. Minimum and traceable change

Avoid:

> "Reconfigure everything until it works."

Prefer:

```text
previous state
→ specific change
→ resulting state
```

### Key idea

> A maintainable network is one whose design can be explained, verified, and modified without depending on informal memory.

# 13. Integrated VLAN troubleshooting

When something fails in a VLAN network, the number of possible causes is large: port, VLAN, trunk, native VLAN, STP, bundle, gateway, routing… This section proposes a method to **avoid trying commands at random**: first define the scope of the failure, then choose the test that rules out the most hypotheses, and only then make the minimum change and verify.

| Step | Question it answers | Example |
|---|---|---|
| **Scope** (*alcance*) | Does one host, one VLAN, one link, or only inter-VLAN traffic fail? | Only VLAN 20 fails |
| **Hypothesis** | Which decision layer could explain it? | VLAN 20 not allowed on the trunk |
| **Test** | Which command provides the evidence? | `show interfaces trunk` |
| **Fact vs. hypothesis** | What have I seen, and what am I assuming? | "20 is not listed" is a fact |
| **Minimal change** | What is the least I must change? | `allowed vlan add 20` |
| **Verification** | Does what failed now work, and does everything else still work? | Intra- and inter-VLAN ping |
| **Incident report** | How do I record it? | Incident template |

Comparing **what works** with **what fails** is the fastest tool to rule out hypotheses.

## 13.1. Do not start with random commands

Troubleshooting is not about executing every command you know.

The goal is to identify the likely **failure domain**.

A useful mental sequence is:

```text
symptom
→ scope
→ endpoint/port
→ VLAN
→ MAC
→ trunk
→ allowed/active
→ native
→ STP/EtherChannel
→ VTP if used
→ IP/gateway
→ inter-VLAN routing
```

You do not always need every step.

## 13.2. Determine the scope

| Scope | Likely hypotheses |
|---|---|
| Only one host fails | Wrong access port, endpoint, IP, Port Security, cabling |
| One whole VLAN fails | VLAN does not exist, trunk/allowed list, STP for that VLAN, gateway, VTP if used |
| All VLANs fail between two switches | Link, trunk (mode/DTP), Port-channel, STP, shared configuration |
| Intra-VLAN works, inter-VLAN fails | Gateway, trunk toward router, subinterface, SVI, `ip routing` |

### Only one host fails

Likely areas:

- incorrect access port;
- endpoint;
- IP configuration;
- Port Security;
- cabling.

### One whole VLAN fails

Likely areas:

- VLAN does not exist;
- trunk/allowed list;
- STP for that VLAN;
- gateway;
- VTP if used.

### All VLANs fail between two switches

Likely areas:

- link;
- trunk (for example, both ends in `dynamic auto`, section 6.3);
- Port-channel;
- STP;
- shared configuration.

### Intra-VLAN works, inter-VLAN fails

Likely areas:

- gateway;
- trunk toward router;
- subinterface;
- SVI;
- routing (for example, `ip routing` missing on the multilayer switch).

## 13.3. Case: port in the wrong VLAN

Expected:

```text
Gi0/8 → VLAN20
```

Observed:

```text
Gi0/8 → VLAN10
```

Even if the host has an address from the VLAN20 subnet, its traffic is entering the wrong Layer 2 domain.

Evidence: `show vlan brief` or `show interfaces Gi0/8 switchport` (`Access Mode VLAN: 10`).

## 13.4. Case: incomplete allowed list

Symptom:

```text
VLAN10 works
VLAN20 fails
```

Same inter-switch link.

A high-value test is:

```text
show interfaces trunk
```

If VLAN20 is missing from the allowed list, that is concrete evidence.

## 13.5. Case: VLAN allowed but not active

The VLAN may be in the allowed list but absent from the local VLAN database (for example, on an intermediate switch where nobody created it).

Also check:

```text
show vlan brief
```

## 13.6. Case: native VLAN mismatch

Check **both ends** of the trunk (`show interfaces trunk` on each one, CDP console messages).

Do not change one side randomly.

## 13.7. Case: Port-channel

If the design uses `Po1`:

```text
show etherchannel summary
```

is a priority check before analyzing individual members in isolation.

## 13.8. Case: inter-VLAN routing

Observation:

```text
host VLAN20 ↔ host VLAN20 = works
host VLAN20 ↔ host VLAN10 = fails
```

This proves that a significant part of VLAN20 Layer 2 switching works.

The investigation can move toward:

```text
gateway
→ trunk toward Layer 3 device
→ subinterface/SVI
→ routing
```

Useful tests: ping from the host to **its own** gateway; ping to the gateway of **the other** VLAN; `show ip interface brief` and `show ip route` on the router or multilayer switch.

## 13.9. Fact versus hypothesis

### Fact

> `show interfaces trunk` does not list VLAN20 as allowed on Gi0/24.

### Hypothesis

> VLAN20 fails because it is not allowed on the trunk.

The hypothesis is supported by observable evidence, but it still needs verification after the change.

## 13.10. Minimum change

If the evidence identifies an incorrect allowed list, you do not need to rebuild the entire configuration.

Correct only the required discrepancy and test again:

```text
interface GigabitEthernet0/24
 switchport trunk allowed vlan add 20
```

(And not `switchport trunk allowed vlan 20`, which would replace the list: section 5.6.)

## 13.11. Verification

A correction is not complete until you verify:

- the corrected state;
- expected connectivity;
- traffic that worked before still works.

## 13.12. Incident documentation

Useful format:

```text
Symptom:
Scope:
Expected state:
Observed facts:
Hypothesis:
Selected test:
Evidence:
Change made:
Verification:
Conclusion:
```

### Key idea

> Comparing what works with what fails usually reduces hypotheses faster than running commands without a specific question.

# 14. Essential observation commands

This section gathers the unit's verification commands in one place. It is not a recipe to run from top to bottom: each command answers **one specific question**, and the professional approach is to choose the one that provides the evidence you need.

| Command | Question it answers | Where it runs |
|---|---|---|
| `show vlan brief` | Which VLANs exist and which access ports do they have? | Switch |
| `show interfaces <int> switchport` | What mode (administrative and operational), access VLAN, voice VLAN, and native VLAN does a port have? | Switch |
| `show mac address-table [vlan N]` | Where was each MAC learned, and in which VLAN? | Switch |
| `show interfaces trunk` | Which ports are trunks, with which native VLAN, and which VLANs are allowed/active? | Switch |
| `show spanning-tree vlan N` | Who is root and which ports forward for that VLAN? | Switch |
| `show etherchannel summary` | Is the Port-channel formed, and with which members? | Switch |
| `show vtp status` | Which VTP domain, mode, and revision does the switch have? | Switch |
| `show ip interface brief` | Which subinterfaces or SVIs have an IP address and are `up/up`? | Router / switch |
| `show ip route` | Does the Layer 3 device have a connected route per VLAN? | Router / multilayer switch |
| `show vlans` | Which VLAN does each subinterface serve? | Router (ROAS) |

## VLAN and access

```text
show vlan brief
show interfaces switchport
show interfaces GigabitEthernet0/8 switchport
show mac address-table
```

## Trunks

```text
show interfaces trunk
```

## STP and EtherChannel

```text
show spanning-tree vlan 20

```

```text
show vtp status
```

```text
show ip interface brief

```

# 15. Common mistakes

The mistakes in this section are not syntax errors but **reasoning** errors: conclusions that seem logical but are not. Recognizing them saves a lot of troubleshooting time.

| Mistake | Correct idea |
|---|---|
| "A VLAN and a subnet are the same thing" | They are associated, but they are Layer 2 and Layer 3 |
| "Creating the VLAN places ports in it" | Creating and assigning are separate steps |
| "The trunk is `up`, so every VLAN works" | Check allowed, active, and native |
| "If DTP negotiates, the design is correct" | Negotiating does not validate the design |
| "Two VLANs communicate because they are on the same switch" | Layer 3 routing is required |
| "An SVI always performs routing" | On a Layer 2 switch, it is only for management |
| "VTP configures the entire VLAN system" | It only distributes the VLAN list |
| "`allowed vlan 30` adds VLAN 30" | It replaces the list; use `add` |
| Changing several things at once | One minimal change at a time, then verify |

## Mistake 1. "A VLAN and a subnet are the same thing"

No. They are commonly associated, but they belong to different layers.

## Mistake 2. "Creating the VLAN automatically places ports in it"

No. Verify each access port assignment.

## Mistake 3. "The trunk is `up`, so every VLAN works"

False. Check allowed, active, native, and VLAN-specific state.

## Mistake 4. "If DTP negotiates successfully, the design is correct"

No. Successful negotiation does not prove that the trunk should exist or that it carries the correct VLANs.

## Mistake 5. "Two VLANs can communicate because they are on the same switch"

Not when they represent different IP subnets and no routing is available between them.

## Mistake 6. "An SVI always performs routing"

No. It may exist only for management on a Layer 2 switch. Even on a multilayer switch, without `ip routing` it does not route.

## Mistake 7. "VTP configures the entire VLAN system"

No. It does not replace access ports, trunks, gateways, or routing.

## Mistake 8. "`switchport trunk allowed vlan 30` adds VLAN 30"

No. It replaces the whole list with "30." To add, use `switchport trunk allowed vlan add 30`.

## Mistake 9. Changing several things at once

This makes it harder to identify which change fixed or worsened the problem.

# 16. Unit summary

This section summarizes the unit as one sequence and twelve ideas. Use it to review before the exam or to check, at the end of your study, that the pieces fit together.

| Block | Key question | Typical evidence |
|---|---|---|
| Segment (1–3) | Is each device in the VLAN of its design? | `show vlan brief` |
| Transport (4–8) | Does each link carry the correct VLANs with the correct native VLAN? | `show interfaces trunk` |
| Connect (9–11) | Does each VLAN have a gateway, and is there routing between them? | `show ip interface brief`, `show ip route` |
| Operate (12–13) | Is it documented, and is it troubleshot with evidence? | VLAN matrix, incident report |

A VLAN creates multiple logical Layer 2 domains over a shared physical infrastructure.

The overall process can be represented as:

```text
organizational need
→ VLAN design
→ access ports
→ 802.1Q
→ trunks
→ allowed/native
→ STP/EtherChannel integration
→ gateway per VLAN
→ inter-VLAN routing
→ documentation
→ troubleshooting
```

Keep these ideas:

1. **VLAN, subnet, and security policy are different concepts.**
2. **Configuration should begin with a design.**
3. **An access port classifies an endpoint into a VLAN.**
4. **802.1Q carries VLAN identity across shared links.**
5. **An operational trunk does not prove every VLAN works.**
6. **Allowed and native settings must match the design.**
7. **DTP and VTP are Cisco technologies worth recognizing, but they do not replace architecture decisions.**
8. **STP and EtherChannel from U06 remain relevant when VLAN traffic crosses redundant or aggregated links.**
9. **Different VLAN/subnet pairs require Layer 3 routing to communicate.**
10. **ROAS and multilayer switching are two ways to provide inter-VLAN routing.**
11. **Documentation is part of deployment.**
12. **Troubleshooting must be based on questions, tests, and evidence.**

# 17. Essential glossary

The professional vocabulary of this unit is used in English in documentation, commands, and daily work. The glossary gives the English term you will find in the CLI and manuals and, in italics, the Spanish term used in class when there is one.

| Term | Meaning |
|---|---|
| **VLAN** (*Virtual LAN*) | virtual local area network; logical Layer 2 domain |

| **Trunk** (*enlace troncal*) | link carrying multiple VLANs |

| **Native VLAN** (*VLAN nativa*) | VLAN assigned to untagged traffic on an 802.1Q trunk |
| **DTP** (*Dynamic Trunking Protocol*) | Cisco trunk negotiation protocol |
| **VLAN hopping** (*salto de VLAN*) | attack that sends traffic into a VLAN the attacker does not belong to |
| **Port-channel** | logical EtherChannel interface |
| **VTP** (*VLAN Trunking Protocol*) | Cisco VLAN information distribution protocol |
| **Configuration revision** (*número de revisión*) | version/change indicator in classic VTP |
| **Inter-VLAN routing** (*routing entre VLAN*) | routing between networks associated with different VLANs |
| **Router-on-a-stick** (*ROAS*) | routing using subinterfaces over a trunk |
| **Subinterface** (*subinterfaz*) | logical interface derived from a physical interface |
| **SVI** (*Switch Virtual Interface*) | virtual interface associated with a VLAN |
| **Multilayer switch / Layer 3 switch** (*switch multicapa*) | switch capable of Layer 3 functions |
| **Routed port** (*puerto enrutado*) | multilayer switch port that works as a router interface (`no switchport`) |
| **Management VLAN** (*VLAN de gestión*) | VLAN used for infrastructure management |

# 18. Final troubleshooting map

This map summarizes section 13 as a chain of questions. Each question has a command that answers it; you do not need to go through all of them, but rather choose, at each moment, the one that provides the most information.

| Question | Command that provides the evidence |
|---|---|
| Is the port in the correct VLAN? | `show interfaces <int> switchport`, `show vlan brief` |
| Does the VLAN exist? | `show vlan brief` |
| Is the MAC learned where expected? | `show mac address-table vlan N` |
| Does the trunk carry the VLAN (allowed/active)? | `show interfaces trunk` |
| Is the native VLAN consistent on both ends? | `show interfaces trunk` on both switches |
| Do STP/EtherChannel allow the path? | `show spanning-tree vlan N`, `show etherchannel summary` |
| Does VTP play a role? | `show vtp status` |
| Are ROAS/SVIs operational? | `show ip interface brief`, `show vlans` |
| Does routing work? | `show ip route`, ping between gateways |

When a VLAN problem appears, a useful mental map is:

```text
what should work?
→ what actually works?
→ what is the scope?
→ is the port in the correct VLAN?
→ does the VLAN exist?
→ is the MAC learned where expected?
→ does the trunk carry the VLAN?
→ do allowed and active states match?
→ is native VLAN consistent?
→ do STP/EtherChannel allow the path?
→ does VTP matter in this design?
→ are IP and gateway correct?
→ are ROAS/SVIs operational?
→ does routing work?
→ what evidence proves the cause?
```

You do not need every step every time.

The professional goal is to select **the next test that provides the most useful information**.
