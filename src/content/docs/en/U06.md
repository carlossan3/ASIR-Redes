> **Guiding question:** How does a LAN switch frames, survive failures, and protect itself, and what evidence proves it?

## Introduction

A local network may have every cable connected correctly and still behave poorly. A port may be physically up while accumulating errors. A switch may learn a MAC address on an unexpected interface. Redundant links may create a loop. An aggregated link may look configured while not actually operating. A security feature may disable a port that is physically healthy.

In this unit we will study how a Layer 2 switch **observes, learns, and makes forwarding decisions**, how a switched LAN remains available when redundancy exists, and how basic security controls can be applied without losing sight of one fundamental idea:

> A configuration is not correct simply because a command was accepted. It is correct when the observed behavior matches the expected behavior and evidence proves it.

The goal is not to memorize a collection of Cisco commands. The goal is to build a mental model that lets us answer questions such as:

- What does the switch know right now?
- Why did it forward a frame through that port?
- Why is a physically healthy link not forwarding user traffic?
- Which mechanism is preventing a loop?
- What evidence proves that an EtherChannel is actually formed?
- Why did a port enter `err-disabled`?
- Which test should we run before changing the configuration?

The unit is organized in five blocks. Each one builds on the previous one: you cannot understand STP without knowing how a switch learns, and you cannot troubleshoot a blocked port without telling a failure apart from a protection.

| Block | Sections | Question it answers |
|---|---|---|
| **Switch management** (*administración del switch*) | §1–§3 | How do I access the switch, secure it, save its configuration, and read the state of its ports? |
| **MAC learning and forwarding** (*aprendizaje y reenvío*) | §4–§6 | How does the switch know where each device is and where to send each frame? |
| **Resilience** (*resiliencia*) | §7–§13 | How do we use redundant links without creating loops (STP/RSTP), and how do we combine links (EtherChannel/LACP)? |
| **Layer 2 security** (*seguridad L2*) | §14–§15 | How do I limit who can use a port and how do I protect DHCP and ARP? |
| **Troubleshooting** (*diagnóstico*) | §16–§23 | How do I locate a Layer 2 fault with evidence and without blind changes? |

# 1. The switch as an observable device

Before configuring a switch, it is worth learning how to **look at it**. A switch keeps a lot of information about what is happening in the network (which ports have a link, which devices it has seen, which paths it blocks) and shows it in two ways: on its front panel, through LEDs, and in its operating system, through commands. This section introduces that idea and separates two functions that are often confused: forwarding user traffic and being manageable.

| Concept | Question it answers | Example |
|---|---|---|
| **Internal state** (*estado interno*) | What does the switch know and remember right now? | MAC table, STP state, counters |
| **Data plane** (*plano de datos*) | Is it forwarding user frames? | PC-A sends a file to PC-B |
| **Management plane** (*plano de gestión*) | Can I log in to inspect and configure it? | Console or SSH session |
| **Switch LEDs** (*LED del switch*) | What does the front panel tell me before I connect? | Green SYST; amber port |

We should not mix up “I can log in to the switch” with “the network works”: they are different planes and can fail independently.

## 1.1. A switch is not a transparent box

A Layer 2 Ethernet switch receives frames on its interfaces and decides where to forward them. It mainly uses information from the Ethernet header, especially **MAC addresses**.

It also maintains internal state, including:

- active and inactive interfaces;
- negotiated speed and duplex;
- traffic and error counters;
- the MAC address table;
- Spanning Tree information;
- EtherChannel information;
- security feature states.

Therefore, when a LAN fails, the switch provides valuable evidence. We should observe that evidence before making changes.

## 1.2. Data plane and management plane

It is useful to distinguish two ideas:

- **data plane**: forwarding user frames;
- **management plane**: accessing the device to inspect and configure it.

A switch may continue forwarding traffic even if management access is broken. Likewise, a switch may be manageable while user traffic is failing.

This distinction prevents us from confusing:

> “I can log in to the switch”

with

> “the network is working correctly.”

## 1.3. Switch LEDs

A switch's first evidence is on its front panel. Cisco Catalyst access switches typically have:

| LED | What it indicates |
|---|---|
| **SYST** | Off: no power. Blinking green: booting and running self-test (*POST*). Solid green: system booted and running. Amber: powered on but faulty |
| **RPS** / power | Redundant power status |
| **STAT / SPEED / DUPLEX / PoE** | Port LED mode; changed with the **MODE** button |
| Per-port LED | In STAT mode: off = no link; green = link; blinking green = activity; amber = port blocked (for example, by STP) or in error; alternating green and amber = link fault |

The exact meaning depends on the model and is found in its documentation. As in U03, an LED is starting evidence, not a diagnosis: a green port doesn't prove it's in the right VLAN or that STP lets it forward.

In **Packet Tracer**, the visible equivalent is the link lights at each end of a link in the logical view: green (forwarding), amber (the port is not forwarding yet: STP is blocking it or it is in transition), and red (no link or shut down). It is a quick clue that you then confirm with commands.

# 2. IOS access and configuration persistence

To manage a switch you have to solve three problems: **how to get in** (console or other methods), **how to move around its operating system** (IOS modes and help), and **how to make sure changes persist and nobody else gets in** (saving the configuration, maintaining the system image, and securing access). This section follows those problems in the order they come up when you take a switch out of the box.

| Concept | Question it answers | Example |
|---|---|---|
| **Console access** (*acceso por consola*) | How do I get in when there is no IP network yet? | Console cable + terminal emulator |
| **IOS modes** (*modos de IOS*) | Which context am I in and what can I do there? | `Switch>`, `Switch#`, `Switch(config)#` |
| **Context-sensitive help** (*ayuda contextual*) | Which options does this command accept? | `show ?`, Tab key |
| **running-config / startup-config** (*configuración activa / de arranque*) | What is running now and what will load after a reboot? | `copy running-config startup-config` |
| **IOS image** (*imagen del sistema*) | Which operating system is running and how is it upgraded? | `show version`, `copy tftp: flash:` |
| **Access security** (*protección del acceso*) | Who can log in and with which privileges? | `enable secret`, console password |
| **Management access methods** (*métodos de acceso*) | From where can I manage it? | Console, Telnet, SSH, web |

We should not confuse **saving the configuration** (copying running-config to startup-config) with **upgrading the operating system** (changing the image in flash): they are different operations with different risks.

## 2.1. Console access

Console access lets us manage the switch without depending on a working IP network. It is especially useful for:

- initial deployment;
- device recovery;
- loss of management connectivity;
- troubleshooting before IP connectivity is available.

The console is an **out-of-band** management channel relative to normal LAN traffic.

## 2.2. Basic IOS modes

Cisco IOS uses different operating modes. Common examples include:

| Mode | Typical prompt | Purpose | How to enter / leave |
|---|---|---|---|
| User EXEC | `Switch>` | Limited inspection | On connecting |
| Privileged EXEC | `Switch#` | Administrative inspection and operations | `enable` / `disable` |
| Global configuration | `Switch(config)#` | Global configuration | `configure terminal` / `exit` or `end` |
| Interface configuration | `Switch(config-if)#` | Interface configuration | `interface Fa0/1` / `exit` |
| Line configuration | `Switch(config-line)#` | Console or VTY configuration | `line console 0` / `exit` |

The prompt itself provides context. Before entering a command, check where you are. `end` (or Ctrl+Z) returns directly to privileged mode from any configuration mode.

## 2.3. Context-sensitive help

IOS provides `?` help and Tab completion. Using these tools is normal professional practice. Engineers do not need to memorize every command and parameter in isolation.

Example:

```text
Switch# show ?
```

shows which options are available after `show` in that context.

## 2.4. Running-config and startup-config

Always distinguish between:

- **running-config**: the active configuration in RAM;
- **startup-config**: the stored configuration used at the next boot.

A change may work now but disappear after a reboot if it is not saved.

Representative commands:

```text
show running-config
show startup-config
copy running-config startup-config
```

The professional question is not only:

> Does it work now?

but also:

> Will it still work after a reboot?

### Where each file lives

| Memory | What it holds | Lost at power-off? |
|---|---|---|
| **RAM** | running-config, MAC table, STP state | Yes |
| **NVRAM** | startup-config | No |
| **Flash** | IOS image (operating system); on switches, also `vlan.dat` | No |

### Common operations with configuration files

| Goal | Command |
|---|---|
| View the active configuration | `show running-config` |
| View the saved configuration | `show startup-config` |
| Save changes | `copy running-config startup-config` (legacy shortcut: `write memory`) |
| Return to factory settings at the next boot | `erase startup-config`, then `reload` |
| Back up to a server | `copy running-config tftp:` (practiced in U08) |

In U07 we will see that a switch's VLANs are stored separately, in `flash:vlan.dat`; that is why erasing the startup-config does not remove them.

## 2.5. System software and image files

The switch operating system is normally stored in flash memory. A safe software upgrade requires checks such as:

- hardware model and platform;
- release compatibility;
- available storage;
- file integrity;
- transfer method;
- boot settings;
- recovery plan.

Upgrading only because “a newer version exists” without checking need and compatibility creates unnecessary risk.

## 2.6. Image upgrade procedure

A careful procedure for upgrading the switch's operating system:

```text
Switch# show version                       ! current version, boot file, memory
Switch# show flash:                        ! free space and files present
Switch# copy running-config startup-config ! save before touching anything
Switch# copy tftp: flash:                  ! copy the new image from a TFTP server
Switch# verify /md5 flash:NEW_IMAGE.bin    ! check integrity (if the platform supports it)
Switch(config)# boot system flash:NEW_IMAGE.bin
Switch# copy running-config startup-config
Switch# reload
Switch# show version                       ! verify it booted the new image
```

Keep the previous image while there's space, so you can roll back. In Packet Tracer the procedure can be practiced with a TFTP server that holds images.

Before `copy tftp: flash:` the switch needs **IP connectivity to the TFTP server** (a management address; see §2.7). The command interactively asks for the server address and the file name.

## 2.7. Securing access and management methods

A switch fresh out of the box doesn't ask for a password. Before connecting it to the production network, access is secured:

```text
Switch(config)# hostname SW1
SW1(config)# enable secret Cl4ve-Privilegiada
SW1(config)# service password-encryption
SW1(config)# banner motd #Authorized access only#
SW1(config)# line console 0
SW1(config-line)# password Cl4ve-Consola
SW1(config-line)# login
SW1(config-line)# exec-timeout 5 0
```

| Command | Effect |
|---|---|
| `enable secret` | Protects privileged mode with a password stored as a *hash* (it shows in the configuration as `secret 5 …` or `secret 9 …`, depending on the release) |
| `enable password` | Legacy command: stores the password in clear text. If it coexists with `enable secret`, `enable secret` wins; its use is not recommended |
| `password` + `login` on console | Requires a password when connecting via console. Without `login`, the password is not requested |
| `service password-encryption` | Hides clear-text passwords in the configuration (they show as `password 7 …`; weak, reversible encryption) |
| `banner motd` | Displays a legal notice on connection |
| `exec-timeout` | Closes idle sessions (minutes seconds) |

After securing access, check twice: log out and log back in (it must ask for the passwords) and review `show running-config` (no clear-text passwords should be visible).

**Methods for accessing the configuration:**

| Method | Requirement | Where it's covered |
|---|---|---|
| Console | Console cable (U03) | This unit |
| Telnet / SSH | Management IP address on the switch (SVI) and VTY lines | Management IP in U07 (management VLAN); full SSH in U08 |
| Web / API | Device web server or API | Awareness |

A Layer 2 switch doesn't need an IP address to switch frames; it only needs one to be **managed remotely**. Telnet sends everything in clear text: the professional method is SSH.

# 3. Interfaces: status, speed, duplex, and counters

Many LAN problems are located on one specific port. This section teaches you to read what the switch says about each interface: whether it is enabled, whether it has a link, what speed and duplex it uses, and whether the traffic crossing it is healthy. All of this comes from U03, but now from the switch's point of view and with the aim of deciding whether the fault is **in the port** or **in the switch's behavior**.

| Concept | Question it answers | Example evidence |
|---|---|---|
| **Administrative status** (*estado administrativo*) | Has someone shut the port down by configuration? | `administratively down`, `disabled` |
| **Operational status / line protocol** (*estado operacional*) | Is there really a working link? | `up, line protocol is up (connected)` |
| **Speed and duplex** (*velocidad y dúplex*) | Have both ends agreed on the same settings? | `a-full`, `a-100` |
| **Counters** (*contadores*) | Is the traffic crossing it healthy? | CRC errors increasing during a test |

An `up/up` port only proves that the link exists: it does not prove that applications work.

## 3.1. Administrative and operational state

An interface may report different states. The goal is not to memorize combinations but to interpret them.

The first line of `show interfaces` has two parts:

```text
FastEthernet0/1 is up, line protocol is up (connected)
```

The first part (“is up”) summarizes the physical and administrative state; the second (“line protocol is up”) indicates whether the link is operational for exchanging frames.

Conceptual examples:

| Observed state | Initial interpretation |
|---|---|
| administratively down / down | The interface was disabled by configuration (`shutdown`) |
| down/down | No operational link; investigate the physical layer or remote endpoint |
| down/down (err-disabled) | A protection mechanism disabled the port (§11, §14) |
| up/down | There is a physical signal but the link is not operational; uncommon on access ports, investigate the remote end or a link problem |
| up/up | The physical/data-link path is operational, but this does not prove end-to-end connectivity |

`up/up` does not prove that the application works. It only narrows the likely fault domain.

`show interfaces status` summarizes every port on one line each:

```text
Port      Name   Status       Vlan  Duplex  Speed Type
Fa0/1            connected    1     a-full  a-100 10/100BaseTX
Fa0/2            notconnect   1     auto    auto  10/100BaseTX
Fa0/3            disabled     1     auto    auto  10/100BaseTX
Fa0/4            err-disabled 1     auto    auto  10/100BaseTX
```

| *Status* value | Meaning |
|---|---|
| `connected` | Link operational |
| `notconnect` | No link (unplugged cable, remote end off, damaged cable) |
| `disabled` | Shut down by configuration |
| `err-disabled` | Shut down by a protection mechanism |

The `a-` prefix in *Duplex* and *Speed* means the value was **autonegotiated**.

## 3.2. Speed and duplex

Modern Ethernet normally uses autonegotiation. Both ends try to agree on compatible settings such as:

- speed;
- duplex.

Manually forcing one side without understanding the other may create abnormal behavior.

A **duplex mismatch** may cause:

- very poor performance;
- upper-layer retransmissions;
- errors or collisions depending on platform;
- poor user experience even though the link appears up.

A typical clue: the side running *half duplex* accumulates **late collisions**, and the side running *full duplex* accumulates **CRC/FCS** errors and undersized frames (*runts*).

The general rule is to keep settings consistent and avoid forcing values without a reason.

## 3.3. Counters as evidence

Counters help distinguish “traffic exists” from “traffic is healthy.” Depending on platform, you may observe:

- packets received and sent;
- input errors;
- CRC/FCS errors;
- drops;
- overruns;
- collisions;
- resets;
- output errors.

A single counter value says little. Its **trend** matters.

Example:

1. record the current value;
2. generate controlled traffic;
3. inspect the counter again;
4. compare the increase.

If errors increase during the test, the evidence is much stronger than simply seeing a nonzero value that may have accumulated for months. To start from zero before a test you can use `clear counters` (it affects only the counters, not the traffic).

## 3.4. Observation commands

Common commands include:

```text
show interfaces status
show interfaces
show interfaces counters errors
```

Exact output varies by model and IOS release, but the stable question is:

> What evidence shows the real interface state, and how does it change when traffic is generated?

# 4. MAC address learning

A switch starts out without knowing where each device is. It finds out by **observing the traffic it receives** and stores what it learns in a table. That table is the basis of all its forwarding decisions (§5) and also one of the best pieces of evidence for troubleshooting (§6). This section explains how the table is filled, how it is viewed, how a technician manages it, and why its entries expire.

| Concept | Question it answers | Example |
|---|---|---|
| **Source MAC learning** (*aprendizaje por MAC de origen*) | How does the switch know which port leads to a device? | Frame from PC-A enters Fa0/1 → `PC-A MAC → Fa0/1` |
| **MAC address table / CAM table** (*tabla MAC*) | Which MAC–port associations does it know right now? | `show mac address-table` |
| **Dynamic / static entry** (*entrada dinámica / estática*) | Did the switch learn it or did the administrator set it? | `DYNAMIC` / `STATIC` |
| **Aging** (*envejecimiento*) | When does the switch forget an entry? | 300 s without traffic, by default |

We should not confuse “the switch knows the MAC” with “the device is connected right now”: the table reflects what was seen recently, not the real inventory.

## 4.1. What the switch learns

When a frame enters a port, the switch reads the **source MAC address** and associates that address with the incoming interface.

Example:

```text
PC-A --- Fa0/1  SW1  Fa0/2 --- PC-B
```

If SW1 receives a frame from PC-A with source MAC `AAAA.AAAA.AAAA` on `Fa0/1`, it can learn:

```text
AAAA.AAAA.AAAA -> Fa0/1
```

This is **source MAC learning**.

A switch does not learn where a host is located by looking at the destination MAC. Location is learned from frames that **arrive from** that host.

## 4.2. MAC address table

The MAC address table—also called a forwarding table or CAM table in some contexts—maintains associations between:

- MAC address;
- interface;
- and, when applicable, a logical context such as a VLAN.

Representative command:

```text
show mac address-table
```

Typical output:

```text
          Mac Address Table
-------------------------------------------

Vlan    Mac Address       Type        Ports
----    -----------       --------    -----
   1    0001.4321.a1b2    DYNAMIC     Fa0/1
   1    0060.2f84.3c11    DYNAMIC     Fa0/2
   1    0050.7966.6800    STATIC      Fa0/5
```

We are not developing VLANs yet (all ports are in VLAN 1, the default VLAN). In U07 we will see that MAC learning occurs within a VLAN context.

### Managing the MAC table

Besides viewing it, the administrator can act on the table:

```text
Switch# show mac address-table dynamic
Switch# show mac address-table interface FastEthernet0/5
Switch# show mac address-table count                        ! how many entries there are
Switch# clear mac address-table dynamic                     ! clears learned entries
Switch(config)# mac address-table static 0050.7966.6800 vlan 1 interface FastEthernet0/5
Switch(config)# mac address-table aging-time 600            ! 600 s instead of 300 s
```

- Clearing dynamic entries forces the switch to relearn: useful to check that a moved device shows up on its new port.
- A **static** entry pins a MAC to a port (for example, a critical server); it doesn't age out and doesn't move even if the MAC appears on another port.
- Changing the *aging time* affects how long an entry takes to be forgotten if the device stops transmitting.

In older IOS releases the same commands are written with a hyphen: `show mac-address-table`, `clear mac-address-table dynamic`. The `?` help shows which form each device accepts.

## 4.3. Aging

Dynamic entries do not remain forever. If traffic from an address is not observed for a period of time (on Cisco, **300 seconds** by default), the entry expires.

This lets the switch adapt when:

- a device disconnects;
- a laptop moves to another port;
- topology changes occur.

Therefore, the MAC table is a **temporary snapshot of what the switch currently knows**, not a permanent inventory database.

# 5. How the switch makes forwarding decisions

Once it has learned the source MAC, the switch looks at the **destination MAC** and checks its table. There are only a few possible cases, and each has a fixed response. Mastering these cases lets you **predict** where each frame will go before running any test, which is the basis of all later troubleshooting.

| Case | Destination MAC situation | What the switch does |
|---|---|---|
| **Known unicast** (*unicast conocido*) | In the table, associated with another port | Forwards only through that port (*forwarding*) |
| **Destination on the incoming port** (*filtrado*) | In the table, associated with the same port it arrived on | Drops it (*filtering*) |
| **Unknown unicast** (*unicast desconocido*) | Not in the table | Floods it through every port except the incoming one (*flooding*) |
| **Broadcast** (*difusión*) | `FFFF.FFFF.FFFF` | Floods it through every port except the incoming one |

Flooding is not an error: it is the normal response when the switch doesn't yet know where the destination is.

After learning the source MAC, the switch examines the destination MAC.

## 5.1. Known unicast

If the destination MAC is in the table and points to another port, the frame is forwarded only through that port.

Example:

```text
Destination BBBB.BBBB.BBBB -> Fa0/2
```

The frame does not need to leave through every interface.

## 5.2. Destination known on the incoming port

If the table says the destination is reachable through the same port where the frame arrived, forwarding it back to that segment is unnecessary.

The switch can filter it.

## 5.3. Unknown unicast

If the destination MAC is not yet in the table, the switch does not know where that device is located.

The normal response is **flooding** within the appropriate domain: the frame is forwarded through relevant ports except the incoming port.

When the destination responds, the switch learns the source MAC from that reply, and later traffic can become known unicast.

## 5.4. Broadcast

A frame sent to the broadcast MAC:

```text
FF:FF:FF:FF:FF:FF   (Cisco notation: FFFF.FFFF.FFFF)
```

is flooded through the corresponding broadcast domain.

IPv4 ARP uses broadcast for certain requests, so concepts from U02 become useful again here.

**Multicast** frames, unless the switch has additional mechanisms (such as *IGMP snooping*, outside this unit), are handled the same way as broadcasts.

## 5.5. Predict before observing

A useful professional exercise is to:

1. draw the topology;
2. write the initial MAC table;
3. identify frame source and destination;
4. predict what the switch will learn;
5. predict where it will forward the frame;
6. generate traffic;
7. inspect the table;
8. compare prediction and evidence.

This makes misunderstandings visible.

### Worked example

Topology: one switch SW1 with PC-A on `Fa0/1`, PC-B on `Fa0/2`, and PC-C on `Fa0/3`. The MAC table is empty.

| # | Frame | What SW1 learns | Case | Leaves through |
|---:|---|---|---|---|
| 1 | PC-A → PC-B | PC-A MAC → Fa0/1 | Unknown unicast (PC-B is not in the table) | Fa0/2 and Fa0/3 |
| 2 | PC-B → PC-A (reply) | PC-B MAC → Fa0/2 | Known unicast | Fa0/1 only |
| 3 | PC-C → broadcast (ARP) | PC-C MAC → Fa0/3 | Broadcast | Fa0/1 and Fa0/2 |
| 4 | PC-A → PC-B | Nothing new (refreshes PC-A's timer) | Known unicast | Fa0/2 only |

After the four frames, `show mac address-table` should show three dynamic entries. If one is missing or appears on another port, the prediction or the assumed topology doesn't match reality.

# 6. Abnormal MAC table evidence

The MAC table is not only used for forwarding: it is also a **record of what has happened** in the network. When a MAC shows up where we don't expect it, or keeps jumping from one port to another, the table is warning us that something doesn't match the topology we think we have. This section teaches you to interpret those signals without jumping to conclusions.

| Anomaly | Question it raises | Possible explanations |
|---|---|---|
| **MAC on an unexpected port** (*MAC en un puerto inesperado*) | Why does the switch see this device here? | Device moved, intermediate switch, outdated documentation |
| **Multiple MACs on one access port** (*muchas MAC en un puerto de acceso*) | What is really connected to this port? | Undocumented switch or access point, server running virtual machines |
| **MAC flapping** (*oscilación de MAC*) | Why does the same MAC keep changing ports? | Layer 2 loop, incorrect topology |

The MAC table is **evidence**, not an explanation: it shows what the switch has seen, but not why.

## 6.1. A MAC address on an unexpected port

If an address appears on a different port than expected, several explanations are possible:

- the device moved;
- another switch or intermediate device exists;
- documentation is outdated;
- a legitimate change occurred;
- the topology is not fully understood;
- a loop or instability exists.

A similar case is finding **several MACs on a port that should have a single device**: it usually means there is another switch, an access point, or a server with virtual machines behind it. Whether that is legitimate depends on the organization's policy (§14 shows how to limit it).

The MAC table is evidence, but it does not explain the cause by itself.

## 6.2. MAC flapping

**MAC flapping** occurs when the same MAC appears to move repeatedly between ports.

It can indicate:

- a Layer 2 loop;
- an incorrect topology;
- special designs or technologies;
- other unexpected behavior that requires investigation.

Many Cisco switches log it with a message such as:

```text
%SW_MATM-4-MACFLAP_NOTIF: Host 0050.7966.6800 in vlan 1 is flapping between port Gi0/1 and port Gi0/2
```

Do not automatically conclude “there is a loop” without checking additional evidence.

# 7. Why Layer 2 loops are dangerous

Professional networks connect switches through **more than one path** so that a broken cable doesn't leave anyone without service. But Ethernet was not designed for closed paths: if two switches are joined by two active links, the same frame can loop indefinitely. This section explains exactly what happens in that case and why, unlike with IP, the frame doesn't “expire” by itself. It is the problem that STP will solve in the following sections.

| Concept | What happens | Observable symptom |
|---|---|---|
| **Physical redundancy** (*redundancia física*) | There is more than one path between two switches | Better availability… if it is controlled |
| **Broadcast storm** (*tormenta de broadcast*) | A broadcast is replicated endlessly | Saturated links, high CPU, a “frozen” network |
| **Duplicate frames** (*tramas duplicadas*) | A device receives several copies of the same frame | Errors or odd behavior in applications |
| **MAC table instability** (*inestabilidad de la tabla MAC*) | The same MAC enters on different ports | MAC flapping |
| **No hop limit in Ethernet** (*sin TTL en la trama*) | Nothing in the frame limits how many times it loops | The loop never stops by itself |

Redundancy is good; what is dangerous is redundancy **without a protocol that controls it**.

## 7.1. Physical redundancy: useful but potentially dangerous

Redundancy improves availability. Two switches connected by multiple paths may continue communicating if one path fails.

However, Layer 2 Ethernet needs a control mechanism to prevent those paths from creating an active logical loop.

Consider:

```text
       link 1
SW1 ------------- SW2
 |                 |
 +-----------------+
       link 2
```

If both links freely forward the same broadcast traffic, frames can circulate repeatedly.

## 7.2. Broadcast storm

A broadcast frame can be replicated again and again by the switches. The amount of traffic may grow rapidly and consume a large portion of available capacity.

Possible symptoms include:

- extreme utilization;
- high CPU use;
- traffic loss;
- latency;
- difficult or impossible management access;
- a network that appears frozen.

## 7.3. Duplicate frames

An endpoint may receive multiple copies of the same frame through redundant paths.

## 7.4. MAC table instability

The same source may arrive alternately on different ports. The switch keeps changing its table, causing MAC flapping and unstable forwarding.

## 7.5. Unlike IP, Ethernet frames do not have an equivalent hop limit

IPv4 uses TTL and IPv6 uses Hop Limit. These fields prevent a Layer 3 packet from circulating forever.

A switched Ethernet frame does not contain an equivalent mechanism that independently solves a Layer 2 loop.

That is why we need a topology-control protocol.

# 8. Spanning Tree Protocol: building a loop-free topology

STP (*Spanning Tree Protocol*, IEEE 802.1D) is the answer to the problem in the previous section: it lets us **keep the redundant cables** and, at the same time, **stop forwarding** on just enough ports so that no closed path exists. To decide which ports forward, the switches agree on a reference point—the *root bridge*—and calculate the paths toward it. This section explains how they communicate (BPDUs), how they compare themselves (Bridge ID), and how the root is elected and **set by design**.

| Concept | Question it answers | Example |
|---|---|---|
| **Spanning Tree Protocol, STP** (*árbol de expansión*) | How can we have physical redundancy without a logical loop? | One link stops forwarding |
| **BPDU** (*Bridge Protocol Data Unit*) | How do switches exchange information? | Message every 2 s |
| **Bridge ID, BID** (*identificador de bridge*) | How are switches compared with each other? | `32769.0001.c7a1.1111` |
| **Root bridge** (*puente raíz*) | Which switch is the reference of the tree? | The one with the lowest BID |
| **Bridge priority** (*prioridad*) and **`root primary`** | How do I decide which switch will be root? | `spanning-tree vlan 1 priority 4096` |

STP leaving a port without forwarding **is not a failure**: that is exactly its job.

## 8.1. Core idea

STP allows physical redundancy while building a **loop-free logical topology**.

It does not necessarily remove a physical link. Instead, it decides which paths should forward traffic and which should temporarily stop forwarding to prevent a cycle.

If the topology changes, a new solution can be calculated.

## 8.2. BPDU

Switches exchange Spanning Tree information using **Bridge Protocol Data Units (BPDUs)**.

BPDUs carry information about items such as:

- switch identity;
- known root bridge;
- path cost to the root;
- topology parameters.

They are sent to a reserved multicast address (`01:80:C2:00:00:00`) and, by default, every 2 seconds (*hello time*). In Packet Tracer's Simulation mode they appear as STP frames.

BPDUs are evidence of the control process.

## 8.3. Bridge ID

STP needs a way to compare switches. It uses a **Bridge ID (BID)** containing values that include priority and a bridge MAC address.

Representation may vary with implementation and extensions, but the conceptual rule is:

> the lower Bridge ID is preferred when electing the root.

On Cisco switches the BID has three parts, compared in this order:

| Part | Size | Value |
|---|---|---|
| Priority | 4 bits | 32768 by default; multiples of 4096 only |
| *Extended system ID* | 12 bits | VLAN number (1 in this unit) |
| MAC address | 48 bits | Switch base MAC |

That is why an unconfigured switch shows priority **32769** (32768 + 1) in VLAN 1.

## 8.4. Root bridge

STP elects one switch as the **root bridge**. That device becomes the logical reference used to calculate preferred paths.

The election follows a simple logic: at startup, every switch announces itself as root; when it receives a BPDU with a lower BID than its own, it stops announcing itself and relays the better candidate's information. After a few seconds, all switches agree on the same root: **the one with the lowest BID**.

In a designed network, we should not leave the root election to chance. The root should be placed consistently with the network design.

Representative command:

```text
show spanning-tree
```

Depending on platform, the output can show:

- root ID;
- local bridge ID;
- path cost;
- port roles;
- port states.

Example output on the switch that is root:

```text
VLAN0001
  Spanning tree enabled protocol ieee
  Root ID    Priority    32769
             Address     0001.C7A1.1111
             This bridge is the root
             Hello Time  2 sec  Max Age 20 sec  Forward Delay 15 sec

  Bridge ID  Priority    32769  (priority 32768 sys-id-ext 1)
             Address     0001.C7A1.1111

Interface        Role Sts Cost      Prio.Nbr Type
---------------- ---- --- --------- -------- --------------------------------
Fa0/1            Desg FWD 19        128.1    P2p
Gi0/1            Desg FWD 4         128.25   P2p
Gi0/2            Desg FWD 4         128.26   P2p
```

*Root ID* describes the root the switch knows about; *Bridge ID* describes the switch itself. If they match, this switch is the root. `protocol ieee` means classic STP (PVST+); with RSTP it would show `protocol rstp` (§10).

### Choosing the root by design

A Cisco switch's BID is made up of **priority** (32768 by default) + **VLAN ID** (*extended system ID*) + **MAC**. If nobody touches the priority, the switch with the lowest MAC wins, which is usually the **oldest** one: exactly the one we don't want at the center of the topology.

To decide it:

```text
SW-CORE(config)# spanning-tree vlan 1 priority 4096
! or, letting IOS calculate a value lower than the current root's:
SW-CORE(config)# spanning-tree vlan 1 root primary
SW-DIST(config)# spanning-tree vlan 1 root secondary
```

- Priority only accepts **multiples of 4096** (0, 4096, 8192…).
- `root primary`/`secondary` are macros that set an appropriate priority at that moment: `root primary` sets **24576** if the current root has a higher priority, or otherwise a value 4096 below the current root's; `root secondary` sets **28672**. Because it is calculated only once, if a switch with an even lower priority appears later, the design is no longer met.
- Verification: in `show spanning-tree`, the root shows “This bridge is the root” and its priority under *Root ID* (for example, 4097 = 4096 + VLAN 1, or 24577 with `root primary`).

# 9. STP cost and port roles

Once the root has been elected, each switch must decide **which ports forward and which don't**. To do that, STP compares the cost of the paths toward the root and assigns each port a **role**. With three simple rules (one Root Port per non-root switch, one Designated Port per segment, the rest not forwarding) you can predict the result for a small topology before looking at the CLI.

| Concept | Question it answers | Rule |
|---|---|---|
| **Root path cost** (*coste de ruta al root*) | Which path toward the root is better? | Sum of link costs; lowest wins |
| **Root Port, RP** (*puerto raíz*) | Through which port does this switch reach the root? | One per non-root switch; the root has none |
| **Designated Port, DP** (*puerto designado*) | Which port forwards on this segment? | One per segment; all root ports are DPs |
| **Non-designated / Alternate port** (*puerto no designado / alternativo*) | Which port stops forwarding to break the loop? | Those that are neither RP nor DP |
| **Tie-breakers** (*desempates*) | What decides when two paths cost the same? | Lowest neighbor BID, then lowest port ID |

We should not confuse a port's **role** (its part in the tree: RP, DP, Alternate) with its **state** (what it does with frames: forward, learn, discard).

## 9.1. Cost to the root

Each path has a cost. STP attempts to retain the best path toward the root bridge.

The relationship between link speed and cost depends on the method used by the implementation, so memorizing a table without context is less important than understanding the stable idea:

> a path with a better STP metric is preferred.

For reference, Cisco switches use these costs by default (“short” method, IEEE 802.1D):

| Link speed | STP cost |
|---|---:|
| 10 Mb/s | 100 |
| 100 Mb/s | 19 |
| 1 Gb/s | 4 |
| 10 Gb/s | 2 |

A switch's **root path cost** is the sum of the costs of the links it must cross to reach the root. With the “long” method (IEEE 802.1t) the values are different (for example, 200,000 for 100 Mb/s), but the rule is the same: lowest wins.

## 9.2. Root Port

On every non-root switch, the **Root Port (RP)** is the port that provides the best path toward the root bridge.

The root bridge does not need a Root Port to reach itself.

## 9.3. Designated Port

Each segment selects a **Designated Port (DP)** as the port offering the preferred path from that segment toward the root.

All ports on the root bridge are designated, because none can be closer to the root than the root itself.

## 9.4. Ports that do not forward to prevent loops

Other redundant ports may be placed in a role/state that does not perform normal forwarding. In RSTP we will use the **Alternate** role.

This does not necessarily mean the link is broken.

A physically `up` interface may intentionally not forward because STP is working correctly.

Remember:

> **blocked/alternate does not mean broken.**

## 9.5. Tie-breakers

When two paths have equal cost, STP uses additional deterministic tie-breakers. Bridge and port identifiers may be involved.

The comparison order for choosing the Root Port is:

1. lowest **root path cost**;
2. if tied, the path through the neighbor with the **lowest Bridge ID**;
3. if still tied (two cables to the same neighbor), the one reaching the neighbor's port with the **lowest port ID** (port priority, 128 by default, + port number; for example `128.25`).

For a segment's Designated Port the same logic applies: the switch advertising the lowest cost to the root wins and, if tied, the one with the lowest BID.

For first-year ASIR, the goal is to reason about small topologies rather than memorize every implementation detail.

## 9.6. Prediction procedure

For a small topology:

1. identify the Bridge IDs;
2. determine the root bridge;
3. compare path costs to the root;
4. select the Root Port on each non-root switch;
5. determine the Designated Port on each segment;
6. identify the redundant path that should not forward;
7. only then run `show spanning-tree`;
8. compare prediction with evidence.

### Worked example: a three-switch triangle

```text
              SW1
     Gi0/1 /       \ Gi0/2
          /         \
   Gi0/1 /           \ Gi0/1
      SW2 ----------- SW3
        Gi0/2     Gi0/2
```

All links are 1 Gb/s (cost 4) and no switch has a modified priority (32769). MACs: SW1 `0000.1111.1111`, SW2 `0000.2222.2222`, SW3 `0000.3333.3333`.

| Step | Reasoning | Result |
|---|---|---|
| Root | Same priority → lowest MAC wins | **SW1** |
| SW2 RP | Direct to SW1: cost 4. Via SW3: 4 + 4 = 8 | SW2 **Gi0/1** |
| SW3 RP | Direct to SW1: cost 4. Via SW2: 8 | SW3 **Gi0/1** |
| Segments SW1–SW2 and SW1–SW3 | Root ports are always DPs | SW1 **Gi0/1 and Gi0/2** |
| Segment SW2–SW3 | Both advertise cost 4 to the root → tie; lower BID (SW2) wins | **SW2 Gi0/2 = DP** |
| Port that does not forward | The remaining one | **SW3 Gi0/2**: *blocking* (STP) / *Alternate* (RSTP) |

If you now apply `spanning-tree vlan 1 root primary` on SW3, the reasoning is repeated with SW3 as root and the blocked port moves to another segment. Predicting it before looking at the CLI is the best exercise to check your understanding.

# 10. Classic STP and RSTP

STP solves loops, but its original version is **slow**: after a change, a port may take up to 50 seconds to forward again, and during that time the affected users have no service. RSTP (*Rapid STP*) keeps the same logic of root, costs, and roles, but converges in a few seconds or less. This section compares both and introduces the roles RSTP adds.

| Concept | Question it answers | Example |
|---|---|---|
| **Convergence** (*convergencia*) | How long does the network take to stabilize after a change? | A link fails; the Alternate starts forwarding |
| **Classic STP** (*IEEE 802.1D*) | How did the original protocol work? | Blocking → Listening → Learning → Forwarding (30–50 s) |
| **RSTP** (*Rapid Spanning Tree, IEEE 802.1w*) | How is fast convergence achieved? | Discarding → Learning → Forwarding |
| **Alternate Port** (*puerto alternativo*) | Which port is ready to replace the Root Port? | The blocked port in the §9.6 example |
| **Backup Port** (*puerto de respaldo*) | Which port backs up a DP of the same switch on the same segment? | Uncommon case (two ports to the same hub) |
| **Edge port** (*puerto de borde*) | Which port connects an end device and can forward without waiting? | A PC port with PortFast |

We should not think RSTP chooses a different root or different paths: the resulting tree is the same; what changes is the **speed** at which it is reached.

## 10.1. Convergence

**Convergence** is the process by which network devices reach a consistent state after a topology change.

A slowly converging network may experience a noticeable outage even when redundancy eventually works.

## 10.2. Classic STP

IEEE 802.1D STP historically used states such as:

- Blocking;
- Listening;
- Learning;
- Forwarding;
- Disabled.

| State | Learns MACs? | Forwards frames? | Typical duration |
|---|---|---|---|
| Blocking | No | No | While it is a non-designated port (up to *Max Age*, 20 s, if BPDUs are lost) |
| Listening | No | No | *Forward Delay*: 15 s |
| Learning | Yes | No | *Forward Delay*: 15 s |
| Forwarding | Yes | Yes | Stable |
| Disabled | No | No | Port shut down |

These transitions protect against loops while topology information is learned, but they may be slow: a newly connected port takes about **30 s** to forward (15 + 15), and after an indirect failure it may take up to **50 s** (20 + 15 + 15).

## 10.3. RSTP

Rapid Spanning Tree Protocol, associated with IEEE 802.1w and later integrated into revisions of 802.1D, improves convergence behavior.

RSTP uses roles and mechanisms that can allow faster transitions when topology conditions permit.

Simplified states include:

- Discarding (combines the old Disabled, Blocking, and Listening);
- Learning;
- Forwarding.

On Cisco, the default mode is **PVST+** (classic STP, one instance per VLAN). To use RSTP, enable **Rapid PVST+**:

```text
SW1(config)# spanning-tree mode rapid-pvst
SW1# show spanning-tree        ! should show "Spanning tree enabled protocol rstp"
```

All switches in the LAN should use the same mode; if they are mixed, links toward switches running classic STP work at classic STP's slower speed.

## 10.4. Alternate Port

An **Alternate Port** provides an alternate path toward the root and remains prepared to become active if the topology changes.

Interpret it correctly:

> an Alternate Port can be evidence that redundancy is working exactly as designed.

RSTP also defines the **Backup Port** role: a port that backs up a Designated Port of the same switch on the same segment (for example, two ports connected to the same hub). It is uncommon in today's networks.

## 10.5. Edge port

A port connected to an end device, where another bridge is not expected, can be treated as an edge port. On Cisco, this concept is related to **PortFast**.

Do not apply the concept blindly. Know what is connected to the port.

# 11. Spanning Tree protections

STP works well as long as every device behaves as expected. But in a real network someone may plug a home switch into a wall jack, a new switch may “win” the root election, or a link may stop receiving BPDUs because of a fault. Cisco offers several protections applied **port by port**, each against a different risk. Choosing well requires knowing **what is connected to each port**.

| Mechanism | Where it is applied | Risk it covers | Reaction |
|---|---|---|---|
| **PortFast** | Access ports to end devices | Unnecessary 30 s wait when a PC connects | The port forwards immediately |
| **BPDU Guard** | Ports with PortFast | Someone connecting a switch where only a PC should be | Port goes `err-disabled` |
| **Root Guard** | Ports toward switches that must never be root | An unauthorized switch becoming root | Port goes *root-inconsistent* (blocked) |
| **Loop Guard** | Non-designated ports between switches | BPDU loss making a port that should be blocked start forwarding | Port goes *loop-inconsistent* (blocked) |

There is no “best” protection: each one addresses a different risk, and applying it on the wrong port can cause outages.

## 11.1. PortFast

PortFast allows an appropriate endpoint-facing port to move rapidly into forwarding without waiting through certain traditional STP transitions.

Typical use:

```text
PC --- access port on a switch
```

Representative configuration:

```text
SW1(config)# interface FastEthernet0/5
SW1(config-if)# spanning-tree portfast
! or, for all access ports at once:
SW1(config)# spanning-tree portfast default
```

IOS displays a warning reminding you that PortFast should only be used on ports connected to a single end device.

It should not be applied indiscriminately to links where another switch or bridge may appear.

PortFast **does not disable STP**. This is a common confusion: the port still sends BPDUs and, if it receives one, it loses its edge status and takes part in STP normally again.

## 11.2. BPDU Guard

BPDU Guard protects a port where **BPDUs are not expected**.

Typical scenario:

- a port intended for an endpoint;
- PortFast enabled;
- a BPDU appears because someone connects a switch.

A common response is to place the port into a protective state such as `err-disabled`, depending on platform/configuration.

Representative configuration:

```text
SW1(config-if)# spanning-tree bpduguard enable
! or, on every port that has PortFast:
SW1(config)# spanning-tree portfast bpduguard default
```

Typical log evidence:

```text
%SPANTREE-2-BLOCK_BPDUGUARD: Received BPDU on port FastEthernet0/5 with BPDU Guard enabled. Disabling port.
```

The correct interpretation is not:

> “the switch broke.”

Instead:

> “a protection feature detected a condition that conflicts with the expected port policy.”

To recover the port: first remove the cause (disconnect the unauthorized switch), then run `shutdown` and `no shutdown` on the interface. Automatic recovery can also be configured (`errdisable recovery cause bpduguard`), but without removing the cause the port will go down again.

## 11.3. Root Guard

Root Guard prevents an external or undesired switch from becoming root through a protected port.

It is useful when network design requires the root to remain in a specific part of the topology.

```text
SW-DIST(config)# interface GigabitEthernet0/2        ! link toward an access switch
SW-DIST(config-if)# spanning-tree guard root
```

If a BPDU advertising a better root arrives on that port, the port becomes **root-inconsistent** and does not forward; it recovers by itself once those BPDUs stop arriving.

The essential idea is protecting the **root position**.

## 11.4. Loop Guard

Loop Guard helps prevent certain BPDU-loss conditions from causing a redundant port to begin forwarding unsafely.

The essential idea is protection against cases where the absence of expected BPDUs could otherwise lead to a loop.

Typical case: a fiber link that stops transmitting in one direction (*unidirectional link*). The blocked port stops receiving BPDUs, “believes” the path has disappeared and, without protection, would start forwarding and create a loop. With Loop Guard it becomes **loop-inconsistent** and keeps not forwarding.

```text
SW2(config-if)# spanning-tree guard loop
```

It is applied on switch-to-switch ports that are not designated (Root Port or Alternate).

Some of these commands (especially Loop Guard) may not be available in every Packet Tracer version.

**BPDU Filter** (`spanning-tree bpdufilter enable`) is not a protection: it makes the port stop sending and processing BPDUs and, if misused, can create loops. It is mentioned only so it is not confused with BPDU Guard.

## 11.5. Comparison

| Mechanism | Main question | Interface command |
|---|---|---|
| PortFast | Can this endpoint-facing port enter forwarding quickly? | `spanning-tree portfast` |
| BPDU Guard | Should an endpoint port be protected if unexpected BPDUs appear? | `spanning-tree bpduguard enable` |
| Root Guard | Should this port prevent an unauthorized root from appearing? | `spanning-tree guard root` |
| Loop Guard | Should this link be protected against unsafe forwarding after abnormal BPDU loss? | `spanning-tree guard loop` |

There is no single “best” protection for every port. Each feature addresses a different risk.

# 12. EtherChannel and LACP

When more capacity is needed between two switches, the intuitive solution is to add several cables in parallel. But STP would see those cables as redundant paths and leave only one forwarding. **EtherChannel** solves the problem by grouping the links into a single logical interface: STP sees it as one link and every cable can carry traffic. **LACP** is the standard protocol the two switches use to negotiate and monitor that group.

| Concept | Question it answers | Example |
|---|---|---|
| **EtherChannel / link aggregation** (*agregación de enlaces*) | How do we combine several links without STP blocking the rest? | 2 × 1 Gb/s between SW1 and SW2 |
| **Port-Channel** (*interfaz lógica*) | Which interface represents the group? | `Port-channel1` (`Po1`) |
| **LACP, IEEE 802.3ad / 802.1AX** (*protocolo de negociación*) | How do both ends agree to form the channel? | `active` / `passive` modes |
| **Member consistency** (*consistencia de miembros*) | What must the links have in common? | Same speed and duplex |
| **Load balancing** (*reparto de carga*) | How is traffic distributed among the cables? | *Hash* of source/destination addresses |

We should not expect a single download to run twice as fast: the channel adds total capacity, but each conversation travels over **one** member.

## 12.1. The problem

Assume two switches have several parallel physical links.

Without aggregation, STP may treat them as independent redundant paths and prevent all of them from forwarding simultaneously.

EtherChannel groups compatible physical links into one logical **Port-Channel** interface.

## 12.2. Benefits

An EtherChannel can provide:

- greater aggregate capacity;
- redundancy among member links;
- one logical interface for certain protocols;
- simpler handling by STP.

This does not mean a single conversation automatically uses the full sum of all link bandwidth. Traffic distribution uses a hashing mechanism that depends on platform and configuration (check it with `show etherchannel load-balance`).

If a member fails, traffic is redistributed among the remaining ones **without STP having to reconverge**, because the logical interface stays up.

## 12.3. Member consistency

Links in the same channel must be compatible. Configuration differences can prevent formation or create unexpected behavior.

Check areas such as:

- speed;
- duplex;
- relevant switching parameters;
- aggregation mode;
- channel-group membership.

In U07 we will also apply consistency to VLAN and trunk parameters.

A channel supports **up to 8 active links**.

## 12.4. LACP

**Link Aggregation Control Protocol (LACP)** is a standards-based protocol for negotiating link aggregation.

Common Cisco modes include:

- `active`: actively initiates LACP negotiation;
- `passive`: responds to LACP negotiation.

Conceptual combinations:

| Side A | Side B | Expected result |
|---|---|---|
| active | active | can form |
| active | passive | can form |
| passive | passive | no initiator; does not form through LACP |

Use the table to reason, but always verify the real state.

There are two other ways to build an EtherChannel that you should recognize:

| Mode | What it is | Note |
|---|---|---|
| `on` | Static channel, no negotiation | Both ends must be `on`. If one end is `on` and the other negotiates (LACP or PAgP), the channel does not form correctly; a cabling mistake goes undetected |
| `desirable` / `auto` | PAgP, Cisco proprietary protocol | Equivalent to `active` / `passive`. Not compatible with LACP |

This unit uses LACP because it is a standard and because it negotiates and monitors the channel.

## 12.5. Representative configuration

Example:

```text
interface range g0/1-2
 channel-group 1 mode active
!
interface port-channel 1
```

Exact syntax may differ by platform.

Complete example on both ends:

```text
SW1(config)# interface range GigabitEthernet0/1 - 2
SW1(config-if-range)# channel-group 1 mode active
SW1(config-if-range)# exit
SW1(config)# interface port-channel 1
SW1(config-if)# description Aggregated link to SW2

SW2(config)# interface range GigabitEthernet0/1 - 2
SW2(config-if-range)# channel-group 1 mode passive
```

`channel-group` automatically creates the `Port-channel1` interface. From then on, whatever is configured under `interface port-channel 1` applies to all members.

## 12.6. Verification

Common commands:

```text
show etherchannel summary
show interfaces port-channel 1
show lacp neighbor
```

Typical `show etherchannel summary` output with the channel formed:

```text
Flags:  D - down        P - bundled in port-channel
        I - stand-alone s - suspended
        S - Layer2      U - in use
...
Group  Port-channel  Protocol    Ports
------+-------------+-----------+----------------------------------
1      Po1(SU)       LACP        Gi0/1(P) Gi0/2(P)
```

| Flag | Meaning |
|---|---|
| `Po1(SU)` | Layer 2 channel (S) in use (U): correct |
| `(P)` on a member | Bundled into the channel: correct |
| `(I)` | *Stand-alone*: works as an individual port; the channel was not negotiated |
| `(s)` | Suspended: incompatible with the other members |
| `(D)` | Member without a link |

In `show spanning-tree` the channel appears as a single interface, `Po1`, instead of Gi0/1 and Gi0/2 separately.

The essential question is:

> Are the links actually bundled and forwarding as members of the same logical channel?

Finding configuration lines in `running-config` is not enough.

# 13. Troubleshooting EtherChannel and LACP

An EtherChannel can be configured and still not work: the two ends don't negotiate, one member is incompatible, or a cable is in another group. This section applies the unit's troubleshooting method to this specific case: **read each member's flags**, form a hypothesis, test it, and correct only the demonstrated difference.

| Concept | Question it answers | Evidence |
|---|---|---|
| **Channel status** (*estado del canal*) | Does the Port-Channel exist and is it in use? | `Po1(SU)` or `Po1(SD)` |
| **Member flags** (*estado de cada miembro*) | Which members are bundled and which are not? | `(P)`, `(I)`, `(s)`, `(D)` |
| **LACP neighbor** (*vecino LACP*) | Is the other end negotiating? | `show lacp neighbor` |
| **Consistency check** (*consistencia*) | Are there speed, duplex, or mode differences? | `show interfaces status`, `show running-config` |
| **Minimal change** (*cambio mínimo*) | What is the only thing that needs fixing? | Only the mismatched parameter |

We should not erase and rebuild the channel “just in case”: the evidence is lost and a new fault may be introduced.

## 13.1. Typical symptom

“There are two cables between the switches, but the Port-Channel does not work as expected.”

Do not immediately erase and rebuild the configuration.

## 13.2. Useful questions

- Does the Port-Channel exist?
- Which members are associated with it?
- What state is each member in?
- Are both sides using compatible negotiation modes?
- Are speed, duplex, or switching settings inconsistent?
- Does LACP see a neighbor?
- Does STP treat the channel as one logical interface?

### Common causes and their evidence

| Cause | Typical evidence |
|---|---|
| `passive` on both ends | `show lacp neighbor` empty; the channel is not in use (`SD`) and members stay stand-alone (`I`) |
| `on` on one end and `active`/`passive` on the other | The channel does not form correctly; on the LACP end, members show `(I)` |
| Different speed or duplex on one member | That member shows as suspended `(s)` |
| One member in a different `channel-group` | It appears under another Port-Channel in the summary |
| Unplugged or damaged cable | Member `(D)` |

## 13.3. Evidence-based flow

Example:

**symptom**

> Port-Channel 1 does not bundle both links.

**hypothesis**

> One member has incompatible settings.

**test**

```text
show etherchannel summary
```

**evidence**

> One link is bundled and the other is not.

**next test**

Compare member configuration and operational parameters on both sides.

**minimum change**

Correct only the demonstrated mismatch.

**verification**

Inspect the summary again and generate controlled traffic.

# 14. Port Security

Until now the switch accepted any device plugged into any port. **Port Security** lets us set a simple policy: **which MAC addresses, and how many, may use an access port** and what the switch does if a different one appears. It is useful to stop someone from connecting an unauthorized device or their own switch to a wall jack, but it has limits worth knowing.

| Concept | Question it answers | Example |
|---|---|---|
| **Port Security** (*seguridad de puerto*) | Who may use this port? | Only the reception PC |
| **Secure MAC address**: static, dynamic, *sticky* (*MAC segura*) | How are the allowed MACs defined? | `mac-address sticky` |
| **Maximum** (*máximo de MAC*) | How many devices may use the port? | `maximum 1` (default value) |
| **Violation mode** (*modo de violación*) | What does the switch do if a non-allowed MAC appears? | `protect`, `restrict`, `shutdown` |
| **err-disabled** (*deshabilitado por error*) | Why did the port stop working? | Violation with `shutdown` mode |

We should not confuse Port Security with **authentication**: a MAC can be spoofed; Port Security limits, but it does not identify the user.

## 14.1. A policy about which devices may use a port

Port Security can limit which MAC addresses use specific access ports and how the switch reacts to violations.

It is not a universal authentication mechanism. It is a Layer 2 control with specific capabilities and limitations.

## 14.2. Secure MAC learning

Depending on configuration, allowed addresses may be defined as:

- static;
- dynamic;
- `sticky`.

Sticky learning can learn addresses and place them into configuration on supported Cisco platforms.

| Type | How it is obtained | Kept after a reboot? |
|---|---|---|
| Static | Typed by the administrator (`mac-address 0060.2f84.3c11`) | Yes, if the configuration is saved |
| Dynamic | Learned from traffic | No |
| Sticky | Learned from traffic and added to the running-config | Yes, if the configuration is saved |

Representative configuration:

```text
SW1(config)# interface FastEthernet0/5
SW1(config-if)# switchport mode access
SW1(config-if)# switchport port-security
SW1(config-if)# switchport port-security maximum 1
SW1(config-if)# switchport port-security mac-address sticky
SW1(config-if)# switchport port-security violation shutdown
```

- `switchport mode access` is required: Port Security cannot be enabled on a port that negotiates its mode dynamically (port modes are covered in U07).
- `switchport port-security` enables the feature; without this line, the others have no effect.
- `maximum 1` and `violation shutdown` are the defaults; they are written out to make the policy explicit.

## 14.3. Violations

If an unauthorized MAC appears, behavior depends on the configured violation mode. Cisco environments may use modes such as:

- protect;
- restrict;
- shutdown.

| Mode | Drops non-allowed traffic | Logs it (log message and violation counter) | Disables the port |
|---|---|---|---|
| `protect` | Yes | No | No |
| `restrict` | Yes | Yes | No |
| `shutdown` (default) | Yes | Yes | Yes (`err-disabled`) |

Do not memorize the names without policy context. Ask:

- Is traffic dropped?
- Is the violation logged?
- Is the port disabled?
- What evidence remains available?

## 14.4. Err-disabled

An `err-disabled` interface has been placed into a protective state because the device detected a condition.

Before recovering it, answer:

1. Which mechanism disabled it?
2. What caused that mechanism to trigger?
3. Is the cause still present?
4. Is it safe to re-enable the port?

Running `shutdown` / `no shutdown` without removing the cause may only hide the problem temporarily.

The correct procedure is: identify the cause (`show interfaces status err-disabled`, `show port-security interface`, `show logging`), remove it (disconnect the unauthorized device or, if the change is legitimate, clear the old secure MAC) and only then run `shutdown` + `no shutdown`.

## 14.5. Representative commands

```text
show port-security
show port-security interface f0/1
show port-security address
show interfaces status
show logging
```

Example of `show port-security interface` after a violation:

```text
Port Security              : Enabled
Port Status                : Secure-shutdown
Violation Mode             : Shutdown
Maximum MAC Addresses      : 1
Total MAC Addresses        : 1
Sticky MAC Addresses       : 1
Last Source Address:Vlan   : 00D0.BA11.2233:1
Security Violation Count   : 1
```

*Secure-shutdown* and a violation count greater than zero confirm that Port Security acted; *Last Source Address* shows which MAC triggered it.

Interpret the output in relation to the expected policy for that port.

# 15. First-hop security: DHCP Snooping and DAI

LAN devices trust two services that nobody authenticates: **DHCP**, which gives them their IP address and gateway, and **ARP**, which tells them which MAC belongs to each IP. An attacker (or a home router plugged in by mistake) can answer instead of the legitimate server and divert or cut off traffic. **First-hop security** groups the controls the access switch applies to prevent this. They are studied at a functional level: what problem they solve, what information they trust, and what evidence they leave.

| Concept | Question it answers | Example |
|---|---|---|
| **First-hop security** (*seguridad de primer salto*) | How does the switch protect the LAN's basic services? | DHCP Snooping + DAI |
| **DHCP Snooping** (*inspección de DHCP*) | How do we stop an unauthorized DHCP server (*rogue DHCP*)? | Drop DHCP offers on user ports |
| **Trusted / untrusted port** (*puerto de confianza / no confiable*) | On which ports may server replies arrive? | Only the uplink toward the legitimate server |
| **Binding table** (*tabla de asociaciones*) | Which MAC and IP were assigned, and on which port? | `show ip dhcp snooping binding` |
| **Dynamic ARP Inspection, DAI** (*inspección dinámica de ARP*) | How do we stop forged ARP replies (*ARP spoofing*)? | Drop ARP that doesn't match the table |

We should not mark ports as *trusted* for convenience: every trusted port is a point where the protection stops acting.

These mechanisms are introduced at a functional level to understand how a switch can protect the LAN from certain unauthorized behaviors.

## 15.1. DHCP Snooping

In U04 we learned that DHCP can provide network configuration to clients.

A security question appears:

> What if an unauthorized device responds as a DHCP server?

DHCP Snooping can classify ports, in simplified terms, as:

- **trusted**: certain server responses are allowed;
- **untrusted**: restrictions apply where DHCP clients are expected.

When DHCP Snooping is enabled, **all ports are untrusted by default**; on them, server-type messages (such as DHCPOFFER and DHCPACK) are dropped.

It can also build a **binding table** containing observed associations such as:

- MAC address;
- IP address;
- switch port;
- network context.

Exact behavior depends on platform.

Representative configuration:

```text
SW1(config)# ip dhcp snooping
SW1(config)# ip dhcp snooping vlan 1
SW1(config)# interface GigabitEthernet0/1          ! toward the legitimate DHCP server
SW1(config-if)# ip dhcp snooping trust
SW1# show ip dhcp snooping
SW1# show ip dhcp snooping binding
```

If clients stop getting an address after DHCP Snooping is enabled, a well-known hypothesis is **option 82**: the switch adds it to requests and some servers reject them. Check it and, if appropriate, fix it with `no ip dhcp snooping information option`.

## 15.2. Why “trusted” must not be used blindly

Marking every uplink or every port as trusted for convenience destroys much of the protection.

Trust decisions must come from the real topology and from where legitimate DHCP server traffic is expected.

## 15.3. Dynamic ARP Inspection

DAI can validate certain ARP messages against trusted information, such as bindings learned through DHCP Snooping.

Its purpose is to reduce ARP spoofing in appropriate environments.

A poorly designed control can also block legitimate traffic.

Representative configuration (requires DHCP Snooping to be active):

```text
SW1(config)# ip arp inspection vlan 1
SW1(config)# interface GigabitEthernet0/1
SW1(config-if)# ip arp inspection trust
SW1# show ip arp inspection
```

A typical case of legitimate traffic being blocked: a device with a **static IP** does not appear in the binding table (it never went through DHCP), so DAI would drop its ARP unless an exception is planned. DAI may not be available in every Packet Tracer version.

Therefore, the professional sequence is:

1. understand the topology;
2. identify what information the feature relies on;
3. verify that information;
4. apply the policy;
5. inspect counters/logs;
6. test legitimate and illegitimate traffic where the lab allows it.

## 15.4. Relationship between mechanisms

DHCP Snooping and DAI illustrate a broader security idea:

> Network security often depends on distinguishing trusted information from untrusted information and enforcing policy at the correct point.

They do not replace authentication, segmentation, firewalls, or other security layers.

# 16. Integrated switching troubleshooting

When “the network is down,” the problem could be in many places. To avoid testing things at random, walk through the switch by **evidence domains**, bottom-up: first the port, then what the switch has learned, then how STP has organized the paths, then the aggregated links, and finally the security controls. Each domain has its own questions and commands, and ruling one out before moving to the next shrinks the problem step by step.

| Domain | Main question | Starting command |
|---|---|---|
| 1. **Interface state** (*estado de interfaz*) | Is the port enabled, with a link, and error-free? | `show interfaces status` |
| 2. **MAC learning** (*aprendizaje MAC*) | Does the switch see the device on the expected port? | `show mac address-table` |
| 3. **Spanning Tree** | Is the port forwarding, or is STP blocking it by design? | `show spanning-tree` |
| 4. **EtherChannel** | Is the channel formed with all its members? | `show etherchannel summary` |
| 5. **Security controls** (*controles de seguridad*) | Is a protection blocking the port or the traffic? | `show logging`, `show port-security` |

We should not start with domain 5 (or by reconfiguring STP) without first ruling out domain 1: most faults are found in the first domains.

## 16.1. Domain 1 — interface state

Questions:

- Is the interface administratively enabled?
- Is the link up?
- Are speed and duplex coherent?
- Are errors or drops increasing?

Possible tests:

```text
show interfaces status
show interfaces
```

## 16.2. Domain 2 — MAC learning

Questions:

- Is the expected MAC present?
- Is it learned on the expected port?
- Is it moving abnormally between ports?

Test:

```text
show mac address-table
```

## 16.3. Domain 3 — Spanning Tree

Questions:

- Which switch is root?
- Does that match the design?
- What role does the port have?
- Is a non-forwarding port actually broken, or is STP behaving correctly?

Test:

```text
show spanning-tree
```

## 16.4. Domain 4 — EtherChannel

Questions:

- Does the channel exist?
- Which members are bundled?
- Did LACP negotiate?
- Is there an inconsistency?

Tests:

```text
show etherchannel summary
show lacp neighbor
```

## 16.5. Domain 5 — security controls

Questions:

- Is the port `err-disabled`?
- Did BPDU Guard trigger?
- Did Port Security detect a violation?
- Are DHCP Snooping or DAI dropping traffic?
- Is that drop correct according to policy?

Possible evidence:

```text
show logging
show port-security
show interfaces status err-disabled
```

plus platform-specific inspection commands.

# 17. Separate facts from hypotheses

The most common troubleshooting mistake is not technical but a reasoning error: taking what the user says, or what we suspect, as if it were verified data. This section shows how to separate what **has been observed** from what **is assumed**, so that every change rests on evidence.

| Concept | What it is | Example |
|---|---|---|
| **Reported symptom** (*síntoma comunicado*) | What someone describes; not yet a cause | “The reception PC has no network” |
| **Fact** (*hecho*) | Something observed and verifiable | The PC's MAC appears on Fa0/8 |
| **Hypothesis** (*hipótesis*) | A possible explanation awaiting a test | The PC's IP is misconfigured |
| **Narrowing the fault domain** (*reducir el dominio del fallo*) | Ruling out areas where the problem can no longer be | Local Layer 2 works |

A hypothesis can be very likely and still be a hypothesis until a test confirms it.

Technical troubleshooting must separate observations from assumptions.

Example:

### Reported symptom

> “The reception PC has no network.”

That is not yet a cause.

### Facts

- the link is `up`;
- the PC MAC appears on `Fa0/8`;
- the port is forwarding;
- input traffic counters increase;
- there are no significant interface errors.

### Hypotheses

- incorrect IP configuration;
- a problem beyond the local switch;
- a logical policy issue not yet tested.

At this point, replacing the cable or changing STP would not be evidence-based.

Layer 2 observation has already helped **reduce the fault domain**.

# 18. Integrated example 1 — a physically active port that does not forward

This example shows the most typical STP misinterpretation: seeing a port that doesn't forward and concluding that something is broken. It is used to practice telling a **failure** apart from **designed behavior**.

| Element | In this case |
|---|---|
| Symptom | Inter-switch link is `up` but carries no user traffic |
| Mechanism involved | STP/RSTP: **Alternate** / *blocking* port (§9–§10) |
| Key evidence | `show spanning-tree`: role `Altn`, state `BLK`, and another path in `FWD` |
| Lesson | A port blocked by design is not a failure |

## Situation

An inter-switch link is physically up, but students observe that it is not carrying user traffic.

## Weak reasoning

> “The port is blocked, so STP is wrong.”

## Better procedure

1. confirm physical state;
2. inspect Spanning Tree;
3. identify root and port role;
4. determine whether the port is Alternate/Discarding;
5. verify that another path is active;
6. compare with the expected topology.

## Possible conclusion

If the port is intentionally redundant and another path is forwarding, the evidence may show that **there is no failure**.

The port is not forwarding precisely because STP is preventing a loop.

# 19. Integrated example 2 — err-disabled after connecting a device

This example deals with a port that a protection mechanism has shut down. The temptation is simply to re-enable it; the goal is to find out **which protection acted and why** before touching anything.

| Element | In this case |
|---|---|
| Symptom | A port that worked stops forwarding when one more device is connected |
| Possible mechanisms | Port Security (§14) or BPDU Guard (§11.2) |
| Key evidence | `show interfaces status` (`err-disabled`), `show logging`, `show port-security interface` |
| Lesson | `err-disabled` is a protection at work: remove the cause first, then re-enable |

## Symptom

A port that previously worked stops forwarding shortly after another device is connected.

## Questions

- What is the interface state?
- What do the logs show?
- Which protections are configured?
- What happened immediately before the state changed?

## Possible explanations

- Port Security violation;
- BPDU Guard after detecting another switch;
- another platform-specific protection condition.

## Principle

Do not re-enable the interface until you understand why it was protected.

`err-disabled` is **evidence of protection**, not a complete diagnosis.

# 20. Integrated example 3 — partial EtherChannel

This example applies the §13 troubleshooting to a channel that only half works. It shows how a single output (`show etherchannel summary`) points the search to **one specific member** instead of redoing the whole configuration.

| Element | In this case |
|---|---|
| Symptom | Of two links, only one appears bundled into the Port-Channel |
| Mechanism involved | EtherChannel/LACP: member consistency (§12.3, §13) |
| Key evidence | One member `(P)` and the other `(I)`, `(s)`, or `(D)` |
| Lesson | Fix only the demonstrated difference; do not rebuild the channel |

## Symptom

Two links should form one Port-Channel, but only one appears correctly bundled.

## Initial evidence

```text
show etherchannel summary
```

shows different states for the two members.

## Reasonable hypothesis

A configuration or negotiation mismatch exists on the second link.

## Next step

Compare:

- member configuration;
- remote-end parameters;
- LACP state;
- speed/duplex;
- required feature consistency.

## Rule

Do not rebuild the entire Port-Channel when a focused test can first identify the exact difference.

# 21. Critical use of tools and AI in troubleshooting

AI assistants, forums, and scripts can suggest commands in seconds. They are useful, but they don't know our network or see our evidence. This section gives criteria to **evaluate an external recommendation** before applying it, just as we would evaluate a colleague's proposal.

| Trait | Helpful recommendation | Recommendation to reject or review |
|---|---|---|
| **Assumed hypothesis** (*hipótesis*) | States it and it can be tested | Takes it for granted |
| **Evidence** (*evidencia*) | Relies on real outputs from our network | Is generic, valid “for any network” |
| **Test vs change** (*tipo de acción*) | Proposes a test first | Goes straight to a change |
| **Verification** (*verificación*) | Says what result to expect and how to check it | Doesn't say how to know whether it worked |

Compare the external proposal with our conclusion **after** we have built it, not before.

A tool can suggest commands quickly, but it cannot replace technical reasoning.

For any external recommendation, ask:

- What hypothesis is it assuming?
- What evidence supports it?
- Is it proposing a test or immediately proposing a change?
- Could that change make the network worse?
- What result do we expect if the hypothesis is correct?
- How will we verify afterward?

A strong technical response is not measured by the number of commands. It is measured by the relationship between:

**question → test → evidence → conclusion**.

# 23. Common conceptual errors

The errors in this section show up again and again in labs and exams. Almost all of them have the same origin: confusing **what you see** (an active link, an accepted command, a blocked port) with **what it means**. The table shows where each correct idea is explained.

| Mistaken belief | Correct idea | Where it is covered |
|---|---|---|
| Link up = everything works | It proves only part of the path | §3.1 |
| The switch learns by looking at the destination | It learns from the source MAC | §4.1 |
| Unknown unicast is dropped | It is flooded | §5.3 |
| A port STP doesn't use = broken | It may be preventing a loop | §9.4, §18 |
| PortFast disables STP | STP stays active on the port | §11.1 |
| BPDU Guard on every port | Only on end-device ports | §11.2 |
| channel-group = channel formed | It must be verified | §12.6 |
| Port Security authenticates users | It only controls MACs per port | §14.1 |
| DHCP Snooping fixes DHCP | It is security; it can block legitimate traffic | §15 |
| Accepted command = correct configuration | Verification is mandatory | Whole unit |

## “Link up means everything works”

No. It proves only part of the path.

## “The switch learns a MAC by looking at the destination”

No. It learns location from source MAC addresses on received frames.

## “Unknown unicast means the frame is dropped”

Normally the switch floods it within the appropriate domain.

## “A port that STP does not use is broken”

Not necessarily. It may be correctly preventing a loop.

## “PortFast disables STP”

No.

## “BPDU Guard belongs on every port”

No. Its use depends on the expected role of the port.

## “Two links in the same channel-group guarantee an EtherChannel”

No. You must verify that the bundle is operational and that member links are compatible.

## “Port Security authenticates users”

No. It controls certain MAC behavior on switch ports; it does not replace full authentication mechanisms.

## “DHCP Snooping fixes any DHCP problem”

No. It is a security feature and can block legitimate traffic if misconfigured.

## “If IOS accepted the command, the configuration is correct”

No. Post-change verification is mandatory.

# 24. Unit summary

This section collects the ideas that should be clear at the end of the unit. The table links each block to the evidence that proves it; the list that follows summarizes the principles.

| Block | Key idea | Evidence that proves it |
|---|---|---|
| Management (§1–§3) | The switch is secured, saved, and observed before it is changed | `show running-config`, `show version`, `show interfaces status` |
| Learning and forwarding (§4–§6) | It learns source MACs and decides by destination MAC | `show mac address-table` |
| Loops and STP/RSTP (§7–§11) | Redundancy is controlled with a root chosen by design and port roles | `show spanning-tree` |
| EtherChannel/LACP (§12–§13) | Several links are combined into one verified logical interface | `show etherchannel summary` |
| Layer 2 security (§14–§15) | We control who uses each port and which information is trusted | `show port-security`, `show ip dhcp snooping binding` |
| Troubleshooting (§16–§21) | Reason by domains and separate facts from hypotheses | All of the above |

A professional switched LAN must be understandable through evidence.

The essential ideas are:

1. a switch **learns** source MAC addresses;
2. it uses its table to make **forwarding** decisions;
3. unknown unicast and broadcast may require **flooding**;
4. uncontrolled physical redundancy can create **Layer 2 loops**;
5. STP/RSTP builds a loop-free logical topology;
6. the root bridge should be part of the design, not an accident;
7. STP roles explain why some links forward and others do not;
8. PortFast and BPDU Guard protect specific edge scenarios;
9. Root Guard and Loop Guard address different risks;
10. EtherChannel/LACP groups compatible links and must be verified operationally;
11. Port Security applies a simple MAC-based policy to access ports;
12. DHCP Snooping and DAI illustrate first-hop security based on trust and evidence;
13. correct troubleshooting separates **symptom, facts, hypothesis, test, evidence, and conclusion**;
14. changes should be minimal and followed by verification.

The professional skill we want to build can be summarized as:

> **Observe first. Explain next. Change only what the evidence justifies. Always verify the result.**

# 26. Bridge to U07

Everything in U06 has been studied on a LAN with a single logical context (VLAN 1). The next unit reuses these ideas on several logical networks that share the same switches.

| Learned in U06 | How U07 reuses it |
|---|---|
| MAC table | Learned and viewed **per VLAN** |
| STP/RSTP and root by design | One STP instance per VLAN (PVST+); the root can differ in each one |
| EtherChannel/LACP | The Port-Channel carries several VLANs as a trunk link |
| Switch access and management | The management IP is configured on an SVI in the management VLAN |

So far, we have studied the switched LAN mainly as one logical context.

The next question is:

> **Can we use the same physical switch infrastructure to build multiple independent logical networks and control which ports belong to each one?**

That need introduces **VLANs**, `access` ports, `trunk` links, and IEEE 802.1Q tagging, which we will develop in U07.
