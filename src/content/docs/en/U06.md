## Introduction

A local network may have every cable connected correctly and still behave poorly. A port may be physically up while accumulating errors. A switch may learn a MAC address on an unexpected interface. Redundant links may create a loop. An aggregated link may look configured while not actually operating. A security feature may disable a port that is physically healthy.

In this unit we will study how a Layer 2 switch **observes, learns, and makes forwarding decisions**, how a switched LAN remains available when redundancy exists, and how basic security controls can be applied without losing sight of one fundamental idea:

> A configuration is not correct simply because a command was accepted. It is correct when the observed behavior matches the expected behavior and evidence proves it.

The goal is not to memorize a collection of Cisco commands. The goal is to build a mental model that lets us answer questions such as:

- What does the switch know right now?
- Why did it forward a frame through that port?
- Why is a physically healthy link not forwarding user traffic?
- Which mechanism is preventing a loop?
- What evidence proves that an EtherChannel is actually formed?
- Why did a port enter `err-disabled`?
- Which test should we run before changing the configuration?

---

# 1. The switch as an observable device

## 1.1. A switch is not a transparent box

A Layer 2 Ethernet switch receives frames on its interfaces and decides where to forward them. It mainly uses information from the Ethernet header, especially **MAC addresses**.

It also maintains internal state, including:

- active and inactive interfaces;
- negotiated speed and duplex;
- traffic and error counters;
- the MAC address table;
- Spanning Tree information;
- EtherChannel information;
- security feature states.

Therefore, when a LAN fails, the switch provides valuable evidence. We should observe that evidence before making changes.

## 1.2. Data plane and management plane

It is useful to distinguish two ideas:

- **data plane**: forwarding user frames;
- **management plane**: accessing the device to inspect and configure it.

A switch may continue forwarding traffic even if management access is broken. Likewise, a switch may be manageable while user traffic is failing.

This distinction prevents us from confusing:

> “I can log in to the switch”

with

> “the network is working correctly.”

## 1.3. Switch LEDs

A switch's first evidence is on its front panel. Cisco Catalyst access switches typically have:

| LED | What it indicates |
|---|---|
| **SYST** | Green: system booted and running. Amber: powered on but faulty |
| **RPS** / power | Redundant power status |
| **STAT / SPEED / DUPLEX / PoE** | Port LED mode; changed with the **MODE** button |
| Per-port LED | In STAT mode: off = no link; green = link; blinking green = activity; amber = port blocked (for example, by STP) or in error |

The exact meaning depends on the model and is found in its documentation. As in U03, an LED is starting evidence, not a diagnosis: a green port doesn't prove it's in the right VLAN or that STP lets it forward.

# 2. IOS access and configuration persistence

## 2.1. Console access

Console access lets us manage the switch without depending on a working IP network. It is especially useful for:

- initial deployment;
- device recovery;
- loss of management connectivity;
- troubleshooting before IP connectivity is available.

The console is an **out-of-band** management channel relative to normal LAN traffic.

## 2.2. Basic IOS modes

Cisco IOS uses different operating modes. Common examples include:

| Mode | Typical prompt | Purpose |
|---|---|---|
| User EXEC | `Switch>` | Limited inspection |
| Privileged EXEC | `Switch#` | Administrative inspection and operations |
| Global configuration | `Switch(config)#` | Global configuration |
| Interface configuration | `Switch(config-if)#` | Interface configuration |

The prompt itself provides context. Before entering a command, check where you are.

## 2.3. Context-sensitive help

IOS provides `?` help and Tab completion. Using these tools is normal professional practice. Engineers do not need to memorize every command and parameter in isolation.

Example:

```text
Switch# show ?
```

shows which options are available after `show` in that context.

## 2.4. Running-config and startup-config

Always distinguish between:

- **running-config**: the active configuration in RAM;
- **startup-config**: the stored configuration used at the next boot.

A change may work now but disappear after a reboot if it is not saved.

Representative commands:

```text
show running-config
show startup-config
copy running-config startup-config
```

The professional question is not only:

> Does it work now?

but also:

> Will it still work after a reboot?

## 2.5. System software and image files

The switch operating system is normally stored in flash memory. A safe software upgrade requires checks such as:

- hardware model and platform;
- release compatibility;
- available storage;
- file integrity;
- transfer method;
- boot settings;
- recovery plan.

Upgrading only because “a newer version exists” without checking need and compatibility creates unnecessary risk.

## 2.6. Image upgrade procedure

A careful procedure for upgrading the switch's operating system:

```text
Switch# show version                       ! current version, boot file, memory
Switch# show flash:                        ! free space and files present
Switch# copy running-config startup-config ! save before touching anything
Switch# copy tftp: flash:                  ! copy the new image from a TFTP server
Switch# verify /md5 flash:NEW_IMAGE.bin    ! check integrity (if the platform supports it)
Switch(config)# boot system flash:NEW_IMAGE.bin
Switch# copy running-config startup-config
Switch# reload
Switch# show version                       ! verify it booted the new image
```

Keep the previous image while there's space, so you can roll back. In Packet Tracer the procedure can be practiced with a TFTP server that holds images.

## 2.7. Securing access and management methods

A switch fresh out of the box doesn't ask for a password. Before connecting it to the production network, access is secured:

```text
Switch(config)# hostname SW1
SW1(config)# enable secret Cl4ve-Privilegiada
SW1(config)# service password-encryption
SW1(config)# banner motd #Authorized access only#
SW1(config)# line console 0
SW1(config-line)# password Cl4ve-Consola
SW1(config-line)# login
SW1(config-line)# exec-timeout 5 0
```

| Command | Effect |
|---|---|
| `enable secret` | Protects privileged mode with a password stored as a *hash* |
| `password` + `login` on console | Requires a password when connecting via console |
| `service password-encryption` | Hides clear-text passwords in the configuration (weak encryption) |
| `exec-timeout` | Closes idle sessions |

**Methods for accessing the configuration:**

| Method | Requirement | Where it's covered |
|---|---|---|
| Console | Console cable (U03) | This unit |
| Telnet / SSH | Management IP address on the switch (SVI) and VTY lines | Management IP in U07 (management VLAN); full SSH in U08 |
| Web / API | Device web server or API | Awareness |

A Layer 2 switch doesn't need an IP address to switch frames; it only needs one to be **managed remotely**. Telnet sends everything in clear text: the professional method is SSH.

# 3. Interfaces: status, speed, duplex, and counters

## 3.1. Administrative and operational state

An interface may report different states. The goal is not to memorize combinations but to interpret them.

Conceptual examples:

| Observed state | Initial interpretation |
|---|---|
| administratively down | The interface was disabled by configuration |
| down/down | No operational link; investigate the physical layer or remote endpoint |
| up/up | The physical/data-link path is operational, but this does not prove end-to-end connectivity |

`up/up` does not prove that the application works. It only narrows the likely fault domain.

## 3.2. Speed and duplex

Modern Ethernet normally uses autonegotiation. Both ends try to agree on compatible settings such as:

- speed;
- duplex.

Manually forcing one side without understanding the other may create abnormal behavior.

A **duplex mismatch** may cause:

- very poor performance;
- upper-layer retransmissions;
- errors or collisions depending on platform;
- poor user experience even though the link appears up.

The general rule is to keep settings consistent and avoid forcing values without a reason.

## 3.3. Counters as evidence

Counters help distinguish “traffic exists” from “traffic is healthy.” Depending on platform, you may observe:

- packets received and sent;
- input errors;
- CRC/FCS errors;
- drops;
- overruns;
- collisions;
- resets;
- output errors.

A single counter value says little. Its **trend** matters.

Example:

1. record the current value;
2. generate controlled traffic;
3. inspect the counter again;
4. compare the increase.

If errors increase during the test, the evidence is much stronger than simply seeing a nonzero value that may have accumulated for months.

## 3.4. Observation commands

Common commands include:

```text
show interfaces status
show interfaces
show interfaces counters errors
```

Exact output varies by model and IOS release, but the stable question is:

> What evidence shows the real interface state, and how does it change when traffic is generated?

# 4. MAC address learning

## 4.1. What the switch learns

When a frame enters a port, the switch reads the **source MAC address** and associates that address with the incoming interface.

Example:

```text
PC-A --- Fa0/1  SW1  Fa0/2 --- PC-B
```

If SW1 receives a frame from PC-A with source MAC `AAAA.AAAA.AAAA` on `Fa0/1`, it can learn:

```text
AAAA.AAAA.AAAA -> Fa0/1
```

This is **source MAC learning**.

A switch does not learn where a host is located by looking at the destination MAC. Location is learned from frames that **arrive from** that host.

## 4.2. MAC address table

The MAC address table—also called a forwarding table or CAM table in some contexts—maintains associations between:

- MAC address;
- interface;
- and, when applicable, a logical context such as a VLAN.

Representative command:

```text
show mac address-table
```

We are not developing VLANs yet. In U07 we will see that MAC learning occurs within a VLAN context.

### Managing the MAC table

Besides viewing it, the administrator can act on the table:

```text
Switch# show mac address-table dynamic
Switch# show mac address-table interface GigabitEthernet0/5
Switch# clear mac address-table dynamic                     ! clears learned entries
Switch(config)# mac address-table static 0050.7966.6800 vlan 1 interface GigabitEthernet0/5
Switch(config)# mac address-table aging-time 600            ! 600 s instead of 300 s
```

- Clearing dynamic entries forces the switch to relearn: useful to check that a moved device shows up on its new port.
- A **static** entry pins a MAC to a port (for example, a critical server); it doesn't age out and doesn't move even if the MAC appears on another port.
- Changing the *aging time* affects how long an entry takes to be forgotten if the device stops transmitting.

## 4.3. Aging

Dynamic entries do not remain forever. If traffic from an address is not observed for a period of time, the entry may expire.

This lets the switch adapt when:

- a device disconnects;
- a laptop moves to another port;
- topology changes occur.

Therefore, the MAC table is a **temporary snapshot of what the switch currently knows**, not a permanent inventory database.

# 5. How the switch makes forwarding decisions

After learning the source MAC, the switch examines the destination MAC.

## 5.1. Known unicast

If the destination MAC is in the table and points to another port, the frame is forwarded only through that port.

Example:

```text
Destination BBBB.BBBB.BBBB -> Fa0/2
```

The frame does not need to leave through every interface.

## 5.2. Destination known on the incoming port

If the table says the destination is reachable through the same port where the frame arrived, forwarding it back to that segment is unnecessary.

The switch can filter it.

## 5.3. Unknown unicast

If the destination MAC is not yet in the table, the switch does not know where that device is located.

The normal response is **flooding** within the appropriate domain: the frame is forwarded through relevant ports except the incoming port.

When the destination responds, the switch learns the source MAC from that reply, and later traffic can become known unicast.

## 5.4. Broadcast

A frame sent to the broadcast MAC:

```text
FF:FF:FF:FF:FF:FF
```

is flooded through the corresponding broadcast domain.

IPv4 ARP uses broadcast for certain requests, so concepts from U02 become useful again here.

## 5.5. Predict before observing

A useful professional exercise is to:

1. draw the topology;
2. write the initial MAC table;
3. identify frame source and destination;
4. predict what the switch will learn;
5. predict where it will forward the frame;
6. generate traffic;
7. inspect the table;
8. compare prediction and evidence.

This makes misunderstandings visible.

# 6. Abnormal MAC table evidence

## 6.1. A MAC address on an unexpected port

If an address appears on a different port than expected, several explanations are possible:

- the device moved;
- another switch or intermediate device exists;
- documentation is outdated;
- a legitimate change occurred;
- the topology is not fully understood;
- a loop or instability exists.

The MAC table is evidence, but it does not explain the cause by itself.

## 6.2. MAC flapping

**MAC flapping** occurs when the same MAC appears to move repeatedly between ports.

It can indicate:

- a Layer 2 loop;
- an incorrect topology;
- special designs or technologies;
- other unexpected behavior that requires investigation.

Do not automatically conclude “there is a loop” without checking additional evidence.

# 7. Why Layer 2 loops are dangerous

## 7.1. Physical redundancy: useful but potentially dangerous

Redundancy improves availability. Two switches connected by multiple paths may continue communicating if one path fails.

However, Layer 2 Ethernet needs a control mechanism to prevent those paths from creating an active logical loop.

Consider:

```text
       link 1
SW1 ------------- SW2
 |                 |
 +-----------------+
       link 2
```

If both links freely forward the same broadcast traffic, frames can circulate repeatedly.

## 7.2. Broadcast storm

A broadcast frame can be replicated again and again by the switches. The amount of traffic may grow rapidly and consume a large portion of available capacity.

Possible symptoms include:

- extreme utilization;
- high CPU use;
- traffic loss;
- latency;
- difficult or impossible management access;
- a network that appears frozen.

## 7.3. Duplicate frames

An endpoint may receive multiple copies of the same frame through redundant paths.

## 7.4. MAC table instability

The same source may arrive alternately on different ports. The switch keeps changing its table, causing MAC flapping and unstable forwarding.

## 7.5. Unlike IP, Ethernet frames do not have an equivalent hop limit

IPv4 uses TTL and IPv6 uses Hop Limit. These fields prevent a Layer 3 packet from circulating forever.

A switched Ethernet frame does not contain an equivalent mechanism that independently solves a Layer 2 loop.

That is why we need a topology-control protocol.

# 8. Spanning Tree Protocol: building a loop-free topology

## 8.1. Core idea

STP allows physical redundancy while building a **loop-free logical topology**.

It does not necessarily remove a physical link. Instead, it decides which paths should forward traffic and which should temporarily stop forwarding to prevent a cycle.

If the topology changes, a new solution can be calculated.

## 8.2. BPDU

Switches exchange Spanning Tree information using **Bridge Protocol Data Units (BPDUs)**.

BPDUs carry information about items such as:

- switch identity;
- known root bridge;
- path cost to the root;
- topology parameters.

BPDUs are evidence of the control process.

## 8.3. Bridge ID

STP needs a way to compare switches. It uses a **Bridge ID (BID)** containing values that include priority and a bridge MAC address.

Representation may vary with implementation and extensions, but the conceptual rule is:

> the lower Bridge ID is preferred when electing the root.

## 8.4. Root bridge

STP elects one switch as the **root bridge**. That device becomes the logical reference used to calculate preferred paths.

In a designed network, we should not leave the root election to chance. The root should be placed consistently with the network design.

Representative command:

```text
show spanning-tree
```

Depending on platform, the output can show:

- root ID;
- local bridge ID;
- path cost;
- port roles;
- port states.

### Choosing the root by design

A Cisco switch's BID is made up of **priority** (32768 by default) + **VLAN ID** (*extended system ID*) + **MAC**. If nobody touches the priority, the switch with the lowest MAC wins, which is usually the **oldest** one: exactly the one we don't want at the center of the topology.

To decide it:

```text
SW-CORE(config)# spanning-tree vlan 1 priority 4096
! or, letting IOS calculate a value lower than the current root's:
SW-CORE(config)# spanning-tree vlan 1 root primary
SW-DIST(config)# spanning-tree vlan 1 root secondary
```

- Priority only accepts **multiples of 4096** (0, 4096, 8192…).
- `root primary`/`secondary` are macros that set an appropriate priority at that moment.
- Verification: in `show spanning-tree`, the root shows "This bridge is the root" and its priority under *Root ID*.

# 9. STP cost and port roles

## 9.1. Cost to the root

Each path has a cost. STP attempts to retain the best path toward the root bridge.

The relationship between link speed and cost depends on the method used by the implementation, so memorizing a table without context is less important than understanding the stable idea:

> a path with a better STP metric is preferred.

## 9.2. Root Port

On every non-root switch, the **Root Port (RP)** is the port that provides the best path toward the root bridge.

The root bridge does not need a Root Port to reach itself.

## 9.3. Designated Port

Each segment selects a **Designated Port (DP)** as the port offering the preferred path from that segment toward the root.

## 9.4. Ports that do not forward to prevent loops

Other redundant ports may be placed in a role/state that does not perform normal forwarding. In RSTP we will use the **Alternate** role.

This does not necessarily mean the link is broken.

A physically `up` interface may intentionally not forward because STP is working correctly.

Remember:

> **blocked/alternate does not mean broken.**

## 9.5. Tie-breakers

When two paths have equal cost, STP uses additional deterministic tie-breakers. Bridge and port identifiers may be involved.

For first-year ASIR, the goal is to reason about small topologies rather than memorize every implementation detail.

## 9.6. Prediction procedure

For a small topology:

1. identify the Bridge IDs;
2. determine the root bridge;
3. compare path costs to the root;
4. select the Root Port on each non-root switch;
5. determine the Designated Port on each segment;
6. identify the redundant path that should not forward;
7. only then run `show spanning-tree`;
8. compare prediction with evidence.

# 10. Classic STP and RSTP

## 10.1. Convergence

**Convergence** is the process by which network devices reach a consistent state after a topology change.

A slowly converging network may experience a noticeable outage even when redundancy eventually works.

## 10.2. Classic STP

IEEE 802.1D STP historically used states such as:

- Blocking;
- Listening;
- Learning;
- Forwarding;
- Disabled.

These transitions protect against loops while topology information is learned, but they may be slow.

## 10.3. RSTP

Rapid Spanning Tree Protocol, associated with IEEE 802.1w and later integrated into revisions of 802.1D, improves convergence behavior.

RSTP uses roles and mechanisms that can allow faster transitions when topology conditions permit.

Simplified states include:

- Discarding;
- Learning;
- Forwarding.

## 10.4. Alternate Port

An **Alternate Port** provides an alternate path toward the root and remains prepared to become active if the topology changes.

Interpret it correctly:

> an Alternate Port can be evidence that redundancy is working exactly as designed.

## 10.5. Edge port

A port connected to an end device, where another bridge is not expected, can be treated as an edge port. On Cisco, this concept is related to **PortFast**.

Do not apply the concept blindly. Know what is connected to the port.

# 11. Spanning Tree protections

## 11.1. PortFast

PortFast allows an appropriate endpoint-facing port to move rapidly into forwarding without waiting through certain traditional STP transitions.

Typical use:

```text
PC --- access port on a switch
```

It should not be applied indiscriminately to links where another switch or bridge may appear.

PortFast **does not disable STP**.

## 11.2. BPDU Guard

BPDU Guard protects a port where **BPDUs are not expected**.

Typical scenario:

- a port intended for an endpoint;
- PortFast enabled;
- a BPDU appears because someone connects a switch.

A common response is to place the port into a protective state such as `err-disabled`, depending on platform/configuration.

The correct interpretation is not:

> “the switch broke.”

Instead:

> “a protection feature detected a condition that conflicts with the expected port policy.”

## 11.3. Root Guard

Root Guard prevents an external or undesired switch from becoming root through a protected port.

It is useful when network design requires the root to remain in a specific part of the topology.

The essential idea is protecting the **root position**.

## 11.4. Loop Guard

Loop Guard helps prevent certain BPDU-loss conditions from causing a redundant port to begin forwarding unsafely.

The essential idea is protection against cases where the absence of expected BPDUs could otherwise lead to a loop.

## 11.5. Comparison

| Mechanism | Main question |
|---|---|
| PortFast | Can this endpoint-facing port enter forwarding quickly? |
| BPDU Guard | Should an endpoint port be protected if unexpected BPDUs appear? |
| Root Guard | Should this port prevent an unauthorized root from appearing? |
| Loop Guard | Should this link be protected against unsafe forwarding after abnormal BPDU loss? |

There is no single “best” protection for every port. Each feature addresses a different risk.

# 12. EtherChannel and LACP

## 12.1. The problem

Assume two switches have several parallel physical links.

Without aggregation, STP may treat them as independent redundant paths and prevent all of them from forwarding simultaneously.

EtherChannel groups compatible physical links into one logical **Port-Channel** interface.

## 12.2. Benefits

An EtherChannel can provide:

- greater aggregate capacity;
- redundancy among member links;
- one logical interface for certain protocols;
- simpler handling by STP.

This does not mean a single conversation automatically uses the full sum of all link bandwidth. Traffic distribution uses a hashing mechanism that depends on platform and configuration.

## 12.3. Member consistency

Links in the same channel must be compatible. Configuration differences can prevent formation or create unexpected behavior.

Check areas such as:

- speed;
- duplex;
- relevant switching parameters;
- aggregation mode;
- channel-group membership.

In U07 we will also apply consistency to VLAN and trunk parameters.

## 12.4. LACP

**Link Aggregation Control Protocol (LACP)** is a standards-based protocol for negotiating link aggregation.

Common Cisco modes include:

- `active`: actively initiates LACP negotiation;
- `passive`: responds to LACP negotiation.

Conceptual combinations:

| Side A | Side B | Expected result |
|---|---|---|
| active | active | can form |
| active | passive | can form |
| passive | passive | no initiator; does not form through LACP |

Use the table to reason, but always verify the real state.

## 12.5. Representative configuration

Example:

```text
interface range g0/1-2
 channel-group 1 mode active
!
interface port-channel 1
```

Exact syntax may differ by platform.

## 12.6. Verification

Common commands:

```text
show etherchannel summary
show interfaces port-channel 1
show lacp neighbor
```

The essential question is:

> Are the links actually bundled and forwarding as members of the same logical channel?

Finding configuration lines in `running-config` is not enough.

# 13. Troubleshooting EtherChannel and LACP

## 13.1. Typical symptom

“There are two cables between the switches, but the Port-Channel does not work as expected.”

Do not immediately erase and rebuild the configuration.

## 13.2. Useful questions

- Does the Port-Channel exist?
- Which members are associated with it?
- What state is each member in?
- Are both sides using compatible negotiation modes?
- Are speed, duplex, or switching settings inconsistent?
- Does LACP see a neighbor?
- Does STP treat the channel as one logical interface?

## 13.3. Evidence-based flow

Example:

**symptom**

> Port-Channel 1 does not bundle both links.

**hypothesis**

> One member has incompatible settings.

**test**

```text
show etherchannel summary
```

**evidence**

> One link is bundled and the other is not.

**next test**

Compare member configuration and operational parameters on both sides.

**minimum change**

Correct only the demonstrated mismatch.

**verification**

Inspect the summary again and generate controlled traffic.

# 14. Port Security

## 14.1. A policy about which devices may use a port

Port Security can limit which MAC addresses use specific access ports and how the switch reacts to violations.

It is not a universal authentication mechanism. It is a Layer 2 control with specific capabilities and limitations.

## 14.2. Secure MAC learning

Depending on configuration, allowed addresses may be defined as:

- static;
- dynamic;
- `sticky`.

Sticky learning can learn addresses and place them into configuration on supported Cisco platforms.

## 14.3. Violations

If an unauthorized MAC appears, behavior depends on the configured violation mode. Cisco environments may use modes such as:

- protect;
- restrict;
- shutdown.

Do not memorize the names without policy context. Ask:

- Is traffic dropped?
- Is the violation logged?
- Is the port disabled?
- What evidence remains available?

## 14.4. Err-disabled

An `err-disabled` interface has been placed into a protective state because the device detected a condition.

Before recovering it, answer:

1. Which mechanism disabled it?
2. What caused that mechanism to trigger?
3. Is the cause still present?
4. Is it safe to re-enable the port?

Running `shutdown` / `no shutdown` without removing the cause may only hide the problem temporarily.

## 14.5. Representative commands

```text
show port-security
show port-security interface f0/1
show interfaces status
show logging
```

Interpret the output in relation to the expected policy for that port.

# 15. First-hop security: DHCP Snooping and DAI

These mechanisms are introduced at a functional level to understand how a switch can protect the LAN from certain unauthorized behaviors.

## 15.1. DHCP Snooping

In U04 we learned that DHCP can provide network configuration to clients.

A security question appears:

> What if an unauthorized device responds as a DHCP server?

DHCP Snooping can classify ports, in simplified terms, as:

- **trusted**: certain server responses are allowed;
- **untrusted**: restrictions apply where DHCP clients are expected.

It can also build a **binding table** containing observed associations such as:

- MAC address;
- IP address;
- switch port;
- network context.

Exact behavior depends on platform.

## 15.2. Why “trusted” must not be used blindly

Marking every uplink or every port as trusted for convenience destroys much of the protection.

Trust decisions must come from the real topology and from where legitimate DHCP server traffic is expected.

## 15.3. Dynamic ARP Inspection

DAI can validate certain ARP messages against trusted information, such as bindings learned through DHCP Snooping.

Its purpose is to reduce ARP spoofing in appropriate environments.

A poorly designed control can also block legitimate traffic.

Therefore, the professional sequence is:

1. understand the topology;
2. identify what information the feature relies on;
3. verify that information;
4. apply the policy;
5. inspect counters/logs;
6. test legitimate and illegitimate traffic where the lab allows it.

## 15.4. Relationship between mechanisms

DHCP Snooping and DAI illustrate a broader security idea:

> Network security often depends on distinguishing trusted information from untrusted information and enforcing policy at the correct point.

They do not replace authentication, segmentation, firewalls, or other security layers.

# 16. Integrated switching troubleshooting

When a switched LAN fails, work through evidence domains.

## 16.1. Domain 1 — interface state

Questions:

- Is the interface administratively enabled?
- Is the link up?
- Are speed and duplex coherent?
- Are errors or drops increasing?

Possible tests:

```text
show interfaces status
show interfaces
```

## 16.2. Domain 2 — MAC learning

Questions:

- Is the expected MAC present?
- Is it learned on the expected port?
- Is it moving abnormally between ports?

Test:

```text
show mac address-table
```

## 16.3. Domain 3 — Spanning Tree

Questions:

- Which switch is root?
- Does that match the design?
- What role does the port have?
- Is a non-forwarding port actually broken, or is STP behaving correctly?

Test:

```text
show spanning-tree
```

## 16.4. Domain 4 — EtherChannel

Questions:

- Does the channel exist?
- Which members are bundled?
- Did LACP negotiate?
- Is there an inconsistency?

Tests:

```text
show etherchannel summary
show lacp neighbor
```

## 16.5. Domain 5 — security controls

Questions:

- Is the port `err-disabled`?
- Did BPDU Guard trigger?
- Did Port Security detect a violation?
- Are DHCP Snooping or DAI dropping traffic?
- Is that drop correct according to policy?

Possible evidence:

```text
show logging
show port-security
```

plus platform-specific inspection commands.

# 17. Separate facts from hypotheses

Technical troubleshooting must separate observations from assumptions.

Example:

### Reported symptom

> “The reception PC has no network.”

That is not yet a cause.

### Facts

- the link is `up`;
- the PC MAC appears on `Fa0/8`;
- the port is forwarding;
- input traffic counters increase;
- there are no significant interface errors.

### Hypotheses

- incorrect IP configuration;
- a problem beyond the local switch;
- a logical policy issue not yet tested.

At this point, replacing the cable or changing STP would not be evidence-based.

Layer 2 observation has already helped **reduce the fault domain**.

# 18. Integrated example 1 — a physically active port that does not forward

## Situation

An inter-switch link is physically up, but students observe that it is not carrying user traffic.

## Weak reasoning

> “The port is blocked, so STP is wrong.”

## Better procedure

1. confirm physical state;
2. inspect Spanning Tree;
3. identify root and port role;
4. determine whether the port is Alternate/Discarding;
5. verify that another path is active;
6. compare with the expected topology.

## Possible conclusion

If the port is intentionally redundant and another path is forwarding, the evidence may show that **there is no failure**.

The port is not forwarding precisely because STP is preventing a loop.

# 19. Integrated example 2 — err-disabled after connecting a device

## Symptom

A port that previously worked stops forwarding shortly after another device is connected.

## Questions

- What is the interface state?
- What do the logs show?
- Which protections are configured?
- What happened immediately before the state changed?

## Possible explanations

- Port Security violation;
- BPDU Guard after detecting another switch;
- another platform-specific protection condition.

## Principle

Do not re-enable the interface until you understand why it was protected.

`err-disabled` is **evidence of protection**, not a complete diagnosis.

# 20. Integrated example 3 — partial EtherChannel

## Symptom

Two links should form one Port-Channel, but only one appears correctly bundled.

## Initial evidence

```text
show etherchannel summary
```

shows different states for the two members.

## Reasonable hypothesis

A configuration or negotiation mismatch exists on the second link.

## Next step

Compare:

- member configuration;
- remote-end parameters;
- LACP state;
- speed/duplex;
- required feature consistency.

## Rule

Do not rebuild the entire Port-Channel when a focused test can first identify the exact difference.

# 21. Critical use of tools and AI in troubleshooting

A tool can suggest commands quickly, but it cannot replace technical reasoning.

For any external recommendation, ask:

- What hypothesis is it assuming?
- What evidence supports it?
- Is it proposing a test or immediately proposing a change?
- Could that change make the network worse?
- What result do we expect if the hypothesis is correct?
- How will we verify afterward?

A strong technical response is not measured by the number of commands. It is measured by the relationship between:

**question → test → evidence → conclusion**.

# 23. Common conceptual errors

## “Link up means everything works”

No. It proves only part of the path.

## “The switch learns a MAC by looking at the destination”

No. It learns location from source MAC addresses on received frames.

## “Unknown unicast means the frame is dropped”

Normally the switch floods it within the appropriate domain.

## “A port that STP does not use is broken”

Not necessarily. It may be correctly preventing a loop.

## “PortFast disables STP”

No.

## “BPDU Guard belongs on every port”

No. Its use depends on the expected role of the port.

## “Two links in the same channel-group guarantee an EtherChannel”

No. You must verify that the bundle is operational and that member links are compatible.

## “Port Security authenticates users”

No. It controls certain MAC behavior on switch ports; it does not replace full authentication mechanisms.

## “DHCP Snooping fixes any DHCP problem”

No. It is a security feature and can block legitimate traffic if misconfigured.

## “If IOS accepted the command, the configuration is correct”

No. Post-change verification is mandatory.

# 24. Unit summary

A professional switched LAN must be understandable through evidence.

The essential ideas are:

1. a switch **learns** source MAC addresses;
2. it uses its table to make **forwarding** decisions;
3. unknown unicast and broadcast may require **flooding**;
4. uncontrolled physical redundancy can create **Layer 2 loops**;
5. STP/RSTP builds a loop-free logical topology;
6. the root bridge should be part of the design, not an accident;
7. STP roles explain why some links forward and others do not;
8. PortFast and BPDU Guard protect specific edge scenarios;
9. Root Guard and Loop Guard address different risks;
10. EtherChannel/LACP groups compatible links and must be verified operationally;
11. Port Security applies a simple MAC-based policy to access ports;
12. DHCP Snooping and DAI illustrate first-hop security based on trust and evidence;
13. correct troubleshooting separates **symptom, facts, hypothesis, test, evidence, and conclusion**;
14. changes should be minimal and followed by verification.

The professional skill we want to build can be summarized as:

> **Observe first. Explain next. Change only what the evidence justifies. Always verify the result.**

# 25. Essential glossary

| Term | Functional meaning |
|---|---|
| MAC address table | Table that associates learned MAC addresses with switching interfaces/contexts |
| Source MAC learning | Learning a MAC location from the source address of a received frame |
| Known unicast | Unicast whose destination location is already known |
| Unknown unicast | Unicast whose destination is not yet in the MAC table |
| Flooding | Forwarding through multiple relevant ports when required by switching behavior |
| Aging | Expiration of dynamic entries after they have not been observed for a period |
| MAC flapping | Repeated movement of one MAC address between ports |
| BPDU | Control message used by Spanning Tree |
| Bridge ID | Identifier used to compare bridges/switches in STP |
| Root bridge | Reference switch for the STP tree |
| Root Port | Best port on a non-root switch toward the root |
| Designated Port | Port selected to forward for a segment according to STP |
| Alternate Port | RSTP alternate path prepared for topology changes |
| PortFast | Edge behavior used to accelerate forwarding on appropriate ports |
| BPDU Guard | Protection against unexpected BPDUs on selected edge ports |
| Root Guard | Protection that prevents an undesired root from appearing through a port |
| Loop Guard | Protection against certain BPDU-loss conditions that could lead to unsafe forwarding |
| EtherChannel | Logical aggregation of multiple physical links |
| Port-Channel | Logical interface created by an EtherChannel |
| LACP | Standards-based protocol for negotiating link aggregation |
| Port Security | Control of selected MAC behavior and violations on access ports |
| DHCP Snooping | DHCP traffic control and binding-table feature on compatible switches |
| DAI | Dynamic validation of selected ARP messages using trusted information |
| err-disabled | Protective interface state triggered by specific detected conditions |
