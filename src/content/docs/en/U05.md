> **Guiding question:** How does a host obtain its IPv6 configuration, where does each parameter come from, and what evidence can prove that IPv6 is actually working?

In U04, we learned how to interpret IPv4 addressing, prefixes, default gateways, subnetting, VLSM, CIDR, and DHCP. IPv6 keeps the idea of **address + prefix**, but it changes important parts of local-network operation and autoconfiguration.

An IPv6 interface can use several addresses at the same time. Routers advertise information through **Router Advertisement (RA)**; a host can generate addresses through **SLAAC**, check for duplicates through **Duplicate Address Detection (DAD)**, and discover neighbors through the **Neighbor Discovery Protocol (NDP)**. DHCPv6 can provide part of the configuration, but **it does not provide the default router**.

The central idea of this unit is to interpret IPv6 as a set of related mechanisms and troubleshoot it through observable evidence:

```text
configuration
→ address type and scope
→ prefix
→ source of each parameter
→ RA / SLAAC / DAD
→ NDP
→ default route
→ DNS
→ IPv6 test
→ packet capture when it adds evidence
→ conclusion
```

| Section | Question it answers |
|---|---|
| 1. Reading and writing addresses | How is an IPv6 address written, compressed, and classified? |
| 2. Prefix planning | How do I divide a block among an organization's LANs? |
| 3. Link-local, RA, SLAAC, and DAD | How does a host get an address without anyone typing it in? |
| 4. Neighbor Discovery and ICMPv6 | How does a host find its neighbors and its router on the link? |
| 5. SLAAC, DHCPv6, RDNSS, and AAAA | Where does each parameter come from: address, gateway, DNS? |
| 6. Verification and dual stack | Which commands check each parameter and each IP family? |
| 7. Wireshark | Which messages can I see in a capture, and what do they prove? |
| 8. Troubleshooting | How do I find which part of the process is failing? |

## By the end of this unit, you should be able to

- read, expand, and compress IPv6 addresses;
- recognize global unicast, link-local, ULA, loopback, multicast, and documentation prefixes;
- plan several `/64` networks from a parent prefix;
- explain the role of link-local addresses, RS, RA, SLAAC, and DAD;
- calculate an EUI-64 interface ID and recognize when the interface ID is random;
- distinguish RS, RA, NS, and NA;
- interpret a basic Neighbor Cache;
- distinguish SLAAC, stateless DHCPv6, stateful DHCPv6, and RDNSS;
- explain where the address, prefix, default router, and DNS information can come from;
- interpret DNS `AAAA` records;
- verify IPv6 separately from IPv4 in a dual-stack environment;
- use Wireshark to observe ICMPv6, NDP, DHCPv6, and DNS;
- troubleshoot IPv6 through tests and evidence instead of drawing conclusions from symptoms alone.

# 1. Reading and writing IPv6 addresses

Before configuring or troubleshooting IPv6, we need to **read** its addresses fluently. They are much longer than IPv4 addresses (128 bits instead of 32) and are written in hexadecimal, so there are rules for shortening them. Without those rules, two identical addresses written differently will look different to us, or we will accept a badly written address as valid.

In addition, an IPv6 interface normally has **several addresses at once**, each with a different **type** and **scope**. This section shows you how to write them, expand them, and recognize what each one is for.

| Concept | Question it answers | Example |
|---|---|---|
| **Multiple addresses per interface** (*varias direcciones por interfaz*) | How many IPv6 addresses can an interface have? | A link-local and a global address at the same time |
| **Hextet** (*hexteto*) | How is a 128-bit address divided? | 8 groups of 16 bits: `2001:0db8:…` |
| **Compression** (*compresión*) | How can I write it shorter without changing the address? | `2001:db8:10:20::42` |
| **Expansion** (*expansión*) | How do I recover the full form? | `2001:0db8:0010:0000:…:0025` |
| **Address type and scope** (*tipo y alcance*) | What is this address for, and how far does it reach? | `fe80::/10` stays on the link |
| **Prefix** (*prefijo*) | Which part identifies the network? | `2001:db8:10:20::/64` |

Do not confuse **representation** with **address**: compressing an address changes how it is written, not which device it identifies.

## 1.1. One interface can have several addresses

In IPv6, it is normal for an interface to use several addresses at the same time.

Example:

```text
Interface: Ethernet

Addresses:
  fe80::a00:27ff:fe12:3456/64
  2001:db8:10:20::25/64

Route:
  default via fe80::1

DNS:
  2001:db8:53::53
```

This example includes:

- a **link-local** address;
- an address in prefix `2001:db8:10:20::/64`;
- a default route using a link-local next hop;
- an IPv6 DNS server.

Do not search for "the IPv6 address" of a host as if only one address could exist. A real device may also show **temporary** addresses (Section 3.4), a ULA, or several global addresses.

## 1.2. Address structure

IPv6 uses **128-bit addresses**, normally written as eight 16-bit hexadecimal groups called **hextets**. Each hexadecimal digit represents 4 bits, so each hextet has at most 4 digits (8 × 16 = 128 bits).

Full form:

```text
2001:0db8:0010:0020:0000:0000:0000:0042
```

### Removing leading zeros

Leading zeros inside a hextet may be omitted:

```text
2001:db8:10:20:0:0:0:42
```

### Using `::`

One continuous sequence of zero hextets may be replaced by `::`:

```text
2001:db8:10:20::42
```

`::` can appear only once in an address.

## 1.3. Compression rules and worked examples

The complete rules (the form recommended by RFC 5952) are:

1. In each hextet, remove **only leading zeros**; never trailing or middle zeros (`0db8` → `db8`, but `1000` stays `1000`).
2. A hextet that is all zeros is written `0`.
3. `::` replaces **one single** run of two or more consecutive `0` hextets.
4. If there are several runs of zeros, compress **the longest one**; if they tie, compress **the first one** (the leftmost).
5. Do not use `::` for a single `0` hextet (it is valid, but it is not the recommended form).
6. Write letters in **lowercase**. Some devices (for example, Cisco IOS) display them in uppercase: `FE80::1` and `fe80::1` are the same address.

| Full form | Step 1: no leading zeros | Compressed form | Rule applied |
|---|---|---|---|
| `2001:0db8:0000:0000:0000:ff00:0042:8329` | `2001:db8:0:0:0:ff00:42:8329` | `2001:db8::ff00:42:8329` | 1 and 3 |
| `2001:0db8:0000:0001:0000:0000:0000:0001` | `2001:db8:0:1:0:0:0:1` | `2001:db8:0:1::1` | 4: compress the run of three zeros, not the single one |
| `2001:0db8:0000:0000:0001:0000:0000:0001` | `2001:db8:0:0:1:0:0:1` | `2001:db8::1:0:0:1` | 4: two runs of two tie → the first one |
| `2001:0db8:1000:0000:0000:0000:0000:0000` | `2001:db8:1000:0:0:0:0:0` | `2001:db8:1000::` | 1: `1000` is not touched |
| `2001:0db8:0010:0000:0020:0030:0040:0050` | `2001:db8:10:0:20:30:40:50` | `2001:db8:10:0:20:30:40:50` | 5: a single `0` is not replaced by `::` |
| `fe80:0000:0000:0000:0000:0000:0000:0001` | `fe80:0:0:0:0:0:0:1` | `fe80::1` | 3 |
| `0000:0000:0000:0000:0000:0000:0000:0001` | `0:0:0:0:0:0:0:1` | `::1` | 3 |

Common mistakes:

| Written as | Problem |
|---|---|
| `2001:db8::1::1` | **Invalid**: `::` appears twice, so you cannot tell how many zeros each one stands for |
| `2001:db8:1::` for `2001:db8:1000::` | **A different address**: trailing zeros were removed |
| `2001:db8:10:20::42:` | **Invalid**: the trailing `:` is not allowed |

## 1.4. Expanding an address

Example:

```text
2001:db8:10::25
```

Expanded form:

```text
2001:0db8:0010:0000:0000:0000:0000:0025
```

Procedure:

1. count the visible hextets;
2. locate `::`;
3. add enough `0000` groups to reach eight hextets;
4. write four hexadecimal digits in each hextet.

In the example there are 4 visible hextets (`2001`, `db8`, `10`, `25`); 8 − 4 = **4** `0000` groups are missing, and they go where `::` was.

Second example:

```text
fe80::a00:27ff:fe12:3456
```

There are 5 visible hextets (`fe80`, `a00`, `27ff`, `fe12`, `3456`) → **3** `0000` groups are missing:

```text
fe80:0000:0000:0000:0a00:27ff:fe12:3456
```

Note that `a00` becomes `0a00` (zeros on the **left**), not `a000`.

## 1.5. Address types and scopes to recognize

Each IPv6 address belongs to a **type** that you can recognize from its first bits (its prefix). The type tells us **what the address is for**, and the **scope** tells us **how far it reaches**: only the link, only the organization, or potentially the whole Internet.

| Type | Prefix or example | Basic use |
|---|---|---|
| **Global unicast** (GUA) | mainly `2000::/3` (starting with `2` or `3`) | Potentially global communication |
| **Link-local** | `fe80::/10` (in practice, `fe80::/64`) | Communication on the local link; routers do not forward it |
| **ULA** (*Unique Local Address*) | `fc00::/7`, commonly `fd00::/8` | Internal networks; not routed on the Internet |
| **Loopback** | `::1/128` | The local host |
| **Unspecified** | `::/128` | "I do not have an address yet"; used as the source during DAD |
| **Multicast** | `ff00::/8` | Communication with groups |
| **Documentation** | `2001:db8::/32` | Examples and labs; never used on real networks |

IPv6 has no broadcast. Many functions use **multicast** instead. These groups will appear in captures and in `show ipv6 interface`:

| Multicast group | Who listens | Where you will see it |
|---|---|---|
| `ff02::1` | All nodes on the link (*all-nodes*) | Destination of periodic RAs |
| `ff02::2` | All routers on the link (*all-routers*) | Destination of RSs |
| `ff02::1:2` | DHCPv6 servers and relays | Destination of DHCPv6 client messages |
| `ff02::1:ffXX:XXXX` | *Solicited-node*: nodes whose address ends in those 24 bits | Destination of NSs (neighbor resolution and DAD) |

`ff02::` means link scope: these messages never leave the local segment. You only need to recognize them; you do not need to calculate solicited-node addresses.

## 1.6. Address and prefix

Example:

```text
2001:db8:10:20::25/64
```

Address:

```text
2001:db8:10:20::25
```

LAN prefix:

```text
2001:db8:10:20::/64
```

In this unit, LANs will normally use `/64` prefixes. In a typical global unicast address, the 128 bits are divided like this:

```text
|   global routing prefix     |  subnet ID   |        interface ID (IID)          |
|          48 bits            |   16 bits    |              64 bits               |
|        2001:db8:10          |      20      |              ::25                  |
```

- **Global routing prefix**: assigned by the provider or registry; it identifies the organization.
- **Subnet ID**: chosen by the organization to number its LANs (Section 2).
- **Interface ID (IID)**: identifies the interface within the LAN; it can be typed manually, generated with EUI-64, or random (Section 3.4).

### Key points

- An IPv6 interface may use several addresses.
- Address and prefix must be interpreted together.
- Compression changes the representation, not the address.
- Only leading zeros are removed, and `::` appears only once.
- Type and scope are recognized from the prefix.

# 2. Simple prefix planning

An organization receives an IPv6 block (for example, a `/48`) and has to divide it among its networks: users, Wi‑Fi, servers, management… This section explains how to do that in an **orderly, documented** way. The difference from U04 is important: in IPv4 we calculated masks to avoid wasting addresses; in IPv6 there are so many addresses that the problem is not saving them but **organizing** them.

The pieces fit together like this: the **parent block** provides many subnets; each LAN receives a **`/64`**, which is distinguished from the others by its **subnet ID**; and everything is recorded in a **documented plan**.

| Concept | Question it answers | Example |
|---|---|---|
| **Parent prefix / block** (*bloque padre*) | What space has the organization been assigned? | `2001:db8:1200::/48` |
| **Subnet ID** (*ID de subred*) | Which bits number each LAN? | 16 bits between `/48` and `/64` → the 4th hextet |
| **/64 LAN prefix** (*`/64` de LAN*) | What size is a normal IPv6 LAN? | `2001:db8:1200:10::/64` |
| **Addressing plan** (*plan de direccionamiento*) | Where is it written which prefix each network uses and how it is configured? | Prefix – use – method table |

Do not carry the U04 VLSM approach over to IPv6: an IPv6 LAN prefix is not sized to the number of hosts.

## 2.1. The `/64` LAN prefix

Example:

```text
2001:db8:1200:20::25/64
```

The subnet is:

```text
2001:db8:1200:20::/64
```

In this unit, LANs will normally be designed as `/64`. Besides being standard practice, SLAAC needs a `/64` prefix to generate the 64-bit interface ID.

## 2.2. Creating `/64` subnets from a parent block

Suppose an organization has:

```text
2001:db8:1200::/48
```

It can allocate several `/64` prefixes:

| Use | Prefix |
|---|---|
| Users | `2001:db8:1200:10::/64` |
| Wi‑Fi | `2001:db8:1200:20::/64` |
| Servers | `2001:db8:1200:30::/64` |
| Management | `2001:db8:1200:40::/64` |
| Laboratory | `2001:db8:1200:50::/64` |

The bits between `/48` and `/64` can identify subnets. That is 16 bits, that is, the entire **fourth hextet**: from `0000` to `ffff`, which gives 2^16 = **65,536** possible `/64` subnets. Because it matches a whole hextet, you can read it directly without converting to binary.

We will not transfer the U04 VLSM model based on minimum host counts to IPv6 LANs. The goal is not to save a few host addresses but to organize prefix space coherently; therefore, LANs will normally use `/64`.

## 2.3. Documenting the plan

A simple plan should be:

- consistent;
- readable;
- scalable;
- documented.

Example:

| Prefix | Use | Planned configuration |
|---|---|---|
| `2001:db8:1200:10::/64` | Users | SLAAC |
| `2001:db8:1200:20::/64` | Wi‑Fi | SLAAC |
| `2001:db8:1200:30::/64` | Servers | According to design |

A useful convention is to reserve a fixed, easy-to-remember interface ID for the router on each LAN (for example, `::1`) and, when VLANs are used, to make the subnet ID match the VLAN number (VLAN 10 → `…:10::/64`; the digits are copied as they are, even though `10` in hexadecimal equals 16). VLANs are covered in U07.

### Key points

- IPv6 LANs normally use `/64`.
- Planning is about organizing prefixes consistently.
- One parent block can provide many `/64` subnets: a `/48` contains 65,536.

# 3. Link-local, Router Advertisement, SLAAC, and DAD

In IPv4, a host without manual configuration depends on a DHCP server. In IPv6, a host can **configure itself** with help from the router on the link. This section explains that autoconfiguration step by step: first the host creates an address to talk on the link (link-local); then it asks the router (RS), and the router advertises the prefix (RA); with that prefix the host builds its address (SLAAC) and checks that nobody else is using it (DAD).

| Concept | Question it answers | Example / evidence |
|---|---|---|
| **Link-local address** (*dirección link-local*) | How does the host talk on the link before it has a global address? | `fe80::a00:27ff:fe12:3456` |
| **Router Solicitation (RS)** (*solicitud de router*) | How does the host ask the router for information? | ICMPv6 type 133 to `ff02::2` |
| **Router Advertisement (RA)** (*anuncio de router*) | How does the host learn the prefix and the default router? | ICMPv6 type 134 carrying the `/64` prefix |
| **SLAAC** (*Stateless Address Autoconfiguration*) | How does the host generate its global address? | Prefix from the RA + interface ID |
| **Interface ID**: EUI-64 or random (*identificador de interfaz*) | Where do the last 64 bits come from? | `…:a00:27ff:fe12:3456` (EUI-64) |
| **DAD** (*Duplicate Address Detection*) | Is the address already in use? | `tentative` state |
| **A, M, and O flags** (*indicadores A, M y O*) | How should the host configure itself? | A = 1 → use SLAAC |

A common confusion: **SLAAC does not mean "an address built from the MAC"**. SLAAC is the mechanism; EUI-64 is just one way to generate the interface ID.

## 3.1. Link-local address

When IPv6 is enabled, an interface normally creates a **link-local** address, with no need for a router or a server.

Example:

```text
fe80::a00:27ff:fe12:3456
```

A link-local address:

- works only on the local link;
- is used to communicate with routers and neighbors;
- participates in Neighbor Discovery;
- may be used as a next-hop address.

Therefore, this is a normal default route:

```text
default via fe80::1
```

Because every interface on a device has a link-local address in `fe80::/64`, when you use a link-local address as a destination you must also specify the interface. On Linux this is written `fe80::1%eth0`; on Windows, with the interface index, for example `fe80::1%12`.

On Cisco routers, the link-local address is generated automatically (with EUI-64) when IPv6 is configured on the interface, but it is common to set it manually so that it is easy to recognize, for example `fe80::1`.

## 3.2. Router Solicitation and Router Advertisement

A host may send a **Router Solicitation (RS)** to request information from routers on the link. It sends it to the group `ff02::2` (all routers).

A router can reply or send periodic **Router Advertisements (RA)**, normally addressed to `ff02::1` (all nodes). The source of an RA is always the router's **link-local** address; that is why the gateway a host learns is an `fe80::` address.

```text
Host                         Router

RS ------------------------->
                  <----------- RA
```

An RA may indicate:

- available prefixes;
- whether a prefix can be used for SLAAC;
- that the sender can act as a default router (*router lifetime* greater than 0);
- other configuration information (M and O flags, DNS servers through RDNSS).

> The IPv6 default router is normally learned through **RA**, not DHCPv6.

On a Cisco router, interfaces send RAs only if IPv6 forwarding is enabled with `ipv6 unicast-routing` (you will configure it systematically in U08).

## 3.3. SLAAC

**SLAAC** (*Stateless Address Autoconfiguration*) allows a host to generate an IPv6 address from an advertised prefix.

Conceptual process:

```text
link-local
    ↓
RS / RA
    ↓
advertised prefix
    ↓
address generation
    ↓
DAD
    ↓
usable address
```

"Stateless" means that no server keeps a record of which address each host has: the router only advertises the prefix, and each host completes its own address.

Modern systems can generate the interface identifier in different ways. Do not assume that every SLAAC address contains the device MAC address.

## 3.4. The interface ID: EUI-64 or random

SLAAC joins two pieces: the 64 bits of the **prefix** (from the RA) and the 64 bits of the **interface ID** (IID), which the host generates itself. There are two broad families of methods, and it is worth recognizing them because they affect privacy and how we read an address.

| Method | How the IID is obtained | Recognized by | Where it usually appears |
|---|---|---|---|
| **EUI-64** (*modified EUI-64*) | From the 48-bit MAC address | `ff:fe` in the middle of the IID | Link-local on Cisco routers, Packet Tracer hosts, older systems |
| **Stable random** (*stable-privacy / semantically opaque*, RFC 7217) | A pseudo-random value, fixed for each network | IID with no recognizable pattern | Current Linux and other systems |
| **Temporary** (*privacy extensions*, RFC 8981) | A random value that changes periodically | Shown as `temporary` | Windows, macOS, desktop Linux; outgoing connections |

### EUI-64 calculation step by step

Start from MAC address `08:00:27:12:34:56`:

1. Split the MAC into two 24-bit halves: `08:00:27` | `12:34:56`.
2. Insert `ff:fe` in the middle: `08:00:27:ff:fe:12:34:56` (now 64 bits).
3. Flip the **seventh bit** of the first byte (the U/L bit, *universal/local*): `08` = `0000 1000` → `0000 1010` = `0a`.
4. Group into hextets: `0a00:27ff:fe12:3456`.
5. Add the prefix and compress:

```text
link-local:  fe80::a00:27ff:fe12:3456
global:      2001:db8:10:20:a00:27ff:fe12:3456   (prefix 2001:db8:10:20::/64)
```

Flipping the seventh bit is the same as adding 2 to the first byte if that bit was 0, or subtracting 2 if it was 1.

More worked examples:

| MAC | First byte → flipped | EUI-64 IID | Resulting address |
|---|---|---|---|
| `a4:5e:60:d1:22:9b` | `a4` (`1010 0100`) → `a6` (`1010 0110`) | `a65e:60ff:fed1:229b` | `2001:db8:1200:10:a65e:60ff:fed1:229b` |
| `0001.6432.a801` (Cisco format) | `00` → `02` | `0201:64ff:fe32:a801` | `2001:db8:10:20:201:64ff:fe32:a801` |
| `02:50:56:aa:bb:cc` | `02` (`0000 0010`) → `00` | `0050:56ff:feaa:bbcc` | `fe80::50:56ff:feaa:bbcc` |

In Cisco IOS, you can ask the interface to complete the address with EUI-64:

```text
R1(config-if)# ipv6 address 2001:db8:10:20::/64 eui-64
```

### Why isn't the MAC always used?

An EUI-64 address contains the MAC address, which does not change when the device moves to another network. That makes it possible to **track** a device across the Internet and reveals the network card's manufacturer. For this reason, current systems prefer random IIDs and usually also create **temporary addresses** for outgoing connections. Practical consequence: on a real laptop you will often see two or more global addresses in the same prefix, and none of them contains `ff:fe`.

## 3.5. DAD

**DAD** (*Duplicate Address Detection*) attempts to check whether an address is already in use on the link. It applies to every unicast address, including the link-local address.

Simplified operation: the host sends an **NS** asking about its own new address, with source `::` (it cannot use the address yet) and the solicited-node group of that address as destination. If someone replies with an **NA**, the address is a duplicate.

During this process, an address may appear as:

```text
tentative
```

If no conflict is detected, the address can normally be used. If there is a conflict, the address is not used: Linux marks it `dadfailed`, Windows shows "Duplicate", and Cisco IOS shows `[DUP]`.

## 3.6. A, M, and O flags

Router Advertisements may include indicators that guide host configuration:

- **A** (*Autonomous*): the prefix can be used for SLAAC;
- **M** (*Managed*): DHCPv6 may be used to obtain an address;
- **O** (*Other*): DHCPv6 may provide other parameters.

M and O are in the RA header; A is inside the information for each advertised prefix. At this stage, you only need to understand their general purpose; the common combinations are summarized in Section 5.4.

### Key points

- Link-local exists before global connectivity is required.
- RS requests information and RA advertises it.
- SLAAC can generate an address.
- The interface ID can be EUI-64 (with `ff:fe`) or random; SLAAC does not imply the MAC.
- DAD checks for duplicates.
- The IPv6 gateway is learned through RA and is a link-local address.

# 4. Neighbor Discovery and ICMPv6

Inside a LAN, devices need to know who is next to them: which router they can use and which MAC address belongs to each neighbor. In IPv4 those tasks were spread out (ARP, DHCP, manual configuration); in IPv6 a single protocol, **NDP**, brings them together, and it travels inside **ICMPv6**. This section presents its messages, the table where the results are stored, and why ICMPv6 cannot be blocked carelessly.

| Concept | Question it answers | Example / evidence |
|---|---|---|
| **NDP** (*Neighbor Discovery Protocol*) | Which protocol organizes life on the local link? | RS, RA, NS, NA, DAD |
| **RS / RA** (*Router Solicitation / Advertisement*) | Who is the router, and which prefix does it advertise? | Types 133 and 134 |
| **NS / NA** (*Neighbor Solicitation / Advertisement*) | What is the MAC for this IPv6 address? Is it a duplicate? | Types 135 and 136 |
| **Solicited-node multicast** (*multicast solicited-node*) | Where is an NS sent without disturbing the whole link? | `ff02::1:ff12:3456` |
| **Neighbor Cache** | Which neighbors does the host know, and in what state? | `fe80::1 … REACHABLE` |
| **ICMPv6** | Which protocol carries NDP, errors, and `ping`? | `icmpv6` in Wireshark |

Do not say that "NDP is ARP for IPv6": NS/NA replace ARP, but NDP also performs router discovery, prefix advertisement, and DAD.

## 4.1. Main messages

| Message | Abbreviation | Function |
|---|---|---|
| Router Solicitation | **RS** | Request router information |
| Router Advertisement | **RA** | Advertise network information |
| Neighbor Solicitation | **NS** | Request information about a neighbor |
| Neighbor Advertisement | **NA** | Reply with neighbor information |

For Wireshark filters, it is useful to recognize:

```text
133 → RS
134 → RA
135 → NS
136 → NA
```

You do not need to memorize many more ICMPv6 types in this unit. (There is also **Redirect**, type 137, which a router uses to tell a host about a better next hop.)

## 4.2. NS and NA: neighbor resolution

In IPv4, ARP maps IPv4 addresses to MAC addresses on the local link.

In IPv6, this function is part of NDP.

```text
Host A                         Host B

NS --------------------------->
                   <----------- NA
```

On Ethernet, NS messages use IPv6 multicast to locate the neighbor. Technical tools and resources may use the term **solicited-node multicast**. In this unit, you only need to recognize its purpose; you do not need to calculate solicited-node multicast addresses. The important idea is that, unlike an ARP broadcast, an NS is processed only by devices whose address ends the same way, not by the whole link.

The result can be stored in the **Neighbor Cache**.

## 4.3. Neighbor Cache

States to recognize:

| State | Initial interpretation |
|---|---|
| **REACHABLE** | Recent evidence that the neighbor is reachable |
| **STALE** | An entry exists but may require confirmation |
| **INCOMPLETE** | Neighbor resolution has not completed |
| **FAILED** | Resolution did not complete successfully |

You may also see **DELAY** and **PROBE**, transient states while the host reconfirms a `STALE` entry. Windows shows `Unreachable` where Linux shows `FAILED`.

`STALE` is a normal state: it does not mean the neighbor has failed, only that it has not been confirmed for a while.

An `INCOMPLETE` entry does not identify the root cause. Investigate the link, address, neighbor, and NDP traffic.

## 4.4. ICMPv6 is essential

ICMPv6 is used for:

- RS and RA;
- NS and NA;
- DAD;
- error messages (for example, destination unreachable or *Packet Too Big*);
- `ping`.

It should not be treated as only "the ping protocol".

Blocking ICMPv6 indiscriminately can break required IPv6 functions.

## 4.5. Initial IPv4/IPv6 comparison

| IPv4 | IPv6 |
|---|---|
| ARP Request / Reply | NS / NA |
| ARP cache | Neighbor Cache |
| Gateway configured or learned through DHCPv4 | Router learned through RA |
| ICMP for control and diagnostics | ICMPv6 also supports NDP and autoconfiguration |
| ARP Request sent as broadcast | NS sent to solicited-node multicast |

### Key points

- NDP performs more functions than ARP.
- NS and NA support neighbor resolution.
- The Neighbor Cache provides local-link evidence.
- ICMPv6 is part of normal IPv6 operation.

# 5. SLAAC, DHCPv6, RDNSS, and DNS AAAA

In IPv4 we usually get everything from one place: the DHCP server hands out address, mask, gateway, and DNS. IPv6 does not work that way: the address can come from SLAAC or DHCPv6, the gateway always comes from the RA, and DNS can arrive through the RA (RDNSS) or through DHCPv6. This section organizes those combinations, because knowing **where each parameter should come from** is the key to troubleshooting.

| Concept | Question it answers | What it provides |
|---|---|---|
| **Parameter sources** (*origen de los parámetros*) | Who delivers each piece of information? | Parameter → source table |
| **Stateless DHCPv6** (*DHCPv6 sin estado*) | Who provides DNS if the address comes from SLAAC? | Other parameters (DNS, domain) |
| **Stateful DHCPv6** (*DHCPv6 con estado*) | Can a server assign and record addresses? | Address + other parameters |
| **RA flags A/M/O** (*indicadores A/M/O*) | Which method does the router indicate? | The host's decision |
| **RDNSS** (*Recursive DNS Server option*) | Can the RA deliver DNS information? | DNS server inside the RA |
| **AAAA record** (*registro AAAA*) | Which IPv6 address belongs to a name? | IPv6 name resolution |

An idea to fix from the start: **DHCPv6 does not provide the gateway**, neither in stateless nor in stateful mode.

## 5.1. Where can each parameter come from?

| Parameter | Possible source |
|---|---|
| Link-local address | The host itself |
| Global / ULA address | SLAAC, DHCPv6, or manual configuration |
| Prefix | Router Advertisement or manual configuration |
| Default router | Router Advertisement (or manual configuration) |
| DNS | RDNSS, DHCPv6, or manual configuration |

This table is fundamental for IPv6 troubleshooting.

## 5.2. Stateless DHCPv6

In a **stateless** design:

```text
SLAAC   → IPv6 address
DHCPv6  → other parameters
```

For example, DHCPv6 may provide DNS information. The server does not keep track of which address each client has; that is why it is "stateless".

## 5.3. Stateful DHCPv6

In a **stateful** design, DHCPv6 may assign an IPv6 address, and the server records the assignment (as DHCPv4 did).

However, the default router is still learned from RA. The prefix length does not come from DHCPv6 either: the host knows which network is local from the prefix advertised in the RA.

| Mechanism | Address | Gateway | Typical DNS source |
|---|---|---|---|
| SLAAC | SLAAC | RA | RDNSS |
| Stateless DHCPv6 | SLAAC | RA | DHCPv6 (and/or RDNSS) |
| Stateful DHCPv6 | DHCPv6 | RA | DHCPv6 |

Facts to recognize: DHCPv6 uses UDP, port **546** on the client and **547** on the server; the client sends its messages to the group `ff02::1:2`. The full exchange is **Solicit → Advertise → Request → Reply**; in stateless mode, **Information-Request → Reply** is enough.

## 5.4. RA flags and the resulting method

The router indicates the method through the flags described in 3.6. Common combinations:

| Method | A | M | O | What the host does |
|---|---:|---:|---:|---|
| SLAAC only (DNS through RDNSS) | 1 | 0 | 0 | Generates its address; DNS from the RA |
| SLAAC + stateless DHCPv6 | 1 | 0 | 1 | Generates its address; asks DHCPv6 for DNS |
| Stateful DHCPv6 | 0 | 1 | (1) | Asks DHCPv6 for the address and other parameters |

In the stateful design the O flag does not matter, because M = 1 already means asking DHCPv6 for everything. If A = 1 and M = 1 at the same time, the host may end up with a SLAAC address **and** a DHCPv6 address: this is not an error, it is a consequence of the design.

In Cisco IOS (you will see it preconfigured in the labs; router administration is covered in U08):

```text
R1(config-if)# ipv6 nd other-config-flag          ! O = 1  → stateless
R1(config-if)# ipv6 nd managed-config-flag        ! M = 1  → stateful
R1(config-if)# ipv6 nd prefix 2001:db8:10:20::/64 no-autoconfig   ! A = 0
```

## 5.5. RDNSS

A Router Advertisement can provide DNS-server information using **RDNSS**.

Therefore:

```text
SLAAC
```

does not mean:

```text
no DNS
```

The actual source depends on the network design. Keep in mind that not every system or simulator processes RDNSS; if a host gets no DNS with "SLAAC only", the stateless DHCPv6 design is the usual alternative.

## 5.6. AAAA records

An **AAAA record** maps a name to an IPv6 address (an **A** record does the same for IPv4).

Example:

```text
srv.example.  AAAA  2001:db8:100::20
```

Possible tools include:

```text
nslookup -type=AAAA srv.example
dig AAAA srv.example
Resolve-DnsName srv.example -Type AAAA
```

A correct AAAA response proves that DNS returned an IPv6 address. It does not prove that the address is reachable or that the service works.

An AAAA query can travel over IPv4 or over IPv6: the record type does not depend on the family used to reach the DNS server.

### Key points

- Address, gateway, and DNS may come from different mechanisms.
- DHCPv6 does not provide the default gateway.
- SLAAC and DHCPv6 can coexist.
- The A, M, and O flags in the RA tell the host which method to use.
- A correct AAAA record does not prove connectivity.

# 6. Verification and dual stack

Knowing the mechanisms is not enough: you must **check** what actually happened on each device. This section collects the commands to read addresses, routes, neighbors, and DNS on Windows, Linux, and Cisco IOS/Packet Tracer; it proposes an order for checking; and it explains **dual stack**, today's most common situation, in which IPv4 and IPv6 coexist and can fail independently.

| Concept | Question it answers | Example of evidence |
|---|---|---|
| **Verification commands** (*comandos de verificación*) | Which command shows each parameter? | `ip -6 route`, `show ipv6 interface brief` |
| **Reading outputs** (*lectura de salidas*) | What do `scope`, `tentative`, `temporary`, `proto ra` mean? | `inet6 … scope link` |
| **Minimum check** (*comprobación mínima*) | In what order do I check? | From link-local to the service |
| **Dual stack** (*doble pila*) | What happens when IPv4 and IPv6 coexist? | `192.0.2.10/24` + `2001:db8:10:20::10/64` |
| **Per-family test** (*prueba por familia*) | Does each family work on its own? | `ping -4` / `ping -6` |

Do not conclude that IPv6 works because "the Internet works": the application may be using IPv4.

## 6.1. What to inspect

| Goal | Windows | Linux | Cisco IOS / Packet Tracer |
|---|---|---|---|
| Addresses | `ipconfig /all` · `Get-NetIPAddress -AddressFamily IPv6` | `ip -6 address` | `show ipv6 interface brief` · `show ipv6 interface g0/0` · PT PC: `ipconfig /all`, `ipv6config` |
| Routes | `route print -6` · `Get-NetRoute -AddressFamily IPv6` | `ip -6 route` | `show ipv6 route` |
| Neighbors | `netsh interface ipv6 show neighbors` · `Get-NetNeighbor -AddressFamily IPv6` | `ip -6 neigh` | `show ipv6 neighbors` |
| Configured DNS | `ipconfig /all` | `resolvectl status` | — |
| DNS AAAA | `nslookup -type=AAAA name` · `Resolve-DnsName name -Type AAAA` | `dig AAAA name` | — |
| DHCPv6 (server) | — | — | `show ipv6 dhcp pool` · `show ipv6 dhcp binding` |
| ICMPv6 | `ping -6` · `tracert -6` | `ping -6` · `traceroute -6` | `ping ipv6 …` or `ping` with an IPv6 address · `traceroute` |

You do not need to memorize every syntax variant. You should know **which information you need and how to interpret it**.

## 6.2. Reading the outputs

Linux, with an EUI-64 address, a temporary address, and the link-local address:

```text
$ ip -6 address show dev enp0s3
2: enp0s3: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500
    inet6 2001:db8:10:20:3c5e:91d2:7a40:b1e8/64 scope global temporary dynamic
       valid_lft 86380sec preferred_lft 14380sec
    inet6 2001:db8:10:20:a00:27ff:fe12:3456/64 scope global dynamic mngtmpaddr
       valid_lft 86380sec preferred_lft 14380sec
    inet6 fe80::a00:27ff:fe12:3456/64 scope link
       valid_lft forever preferred_lft forever

$ ip -6 route
2001:db8:10:20::/64 dev enp0s3 proto ra metric 100
fe80::/64 dev enp0s3 proto kernel metric 256
default via fe80::1 dev enp0s3 proto ra metric 100 expires 1790sec

$ ip -6 neigh
fe80::1 dev enp0s3 lladdr 00:01:64:32:a8:01 router REACHABLE
```

| What you see | What it means |
|---|---|
| `scope link` / `scope global` | Link-local / global address |
| `dynamic` | Obtained automatically (SLAAC or DHCPv6), with a lifetime |
| `temporary` | Temporary privacy address |
| `mngtmpaddr` | Stable address from which temporary addresses are generated |
| `tentative` / `dadfailed` | DAD in progress / DAD detected a duplicate |
| `proto ra` | Route learned from a Router Advertisement |
| `router REACHABLE` | The neighbor is a router and has been confirmed |

On Windows, `ipconfig /all` shows, among others, "IPv6 Address", "Temporary IPv6 Address", and "Link-local IPv6 Address" (the link-local address, with `%` and the interface index), each with its state: "(Preferred)", "(Tentative)", or "(Duplicate)". The IPv6 "Default Gateway" appears as `fe80::…%n`.

On a Cisco router:

```text
R1# show ipv6 interface brief
GigabitEthernet0/0     [up/up]
    FE80::1
    2001:DB8:10:20::1
```

IOS displays addresses in uppercase; they are the same as `fe80::1` and `2001:db8:10:20::1`.

## 6.3. Packet Tracer lab: minimum configuration

In lab sessions the router is usually **preconfigured** or configured with very few commands. Router administration (access, routes, backups) is covered in U08; here what matters is **what effect each command has on the hosts**.

```text
R1(config)# ipv6 unicast-routing                       ! without this there are no RAs
R1(config)# interface g0/0
R1(config-if)# ipv6 address 2001:db8:10:20::1/64
R1(config-if)# ipv6 address fe80::1 link-local
R1(config-if)# no shutdown
```

With this, PCs whose IPv6 setting is automatic (depending on the version, *Automatic* or *Auto Config*) obtain through SLAAC an address `2001:db8:10:20:…` with an EUI-64 IID and the gateway `fe80::1`.

Stateless DHCPv6 (DNS through DHCPv6):

```text
R1(config)# ipv6 dhcp pool LAN-V6
R1(config-dhcpv6)# dns-server 2001:db8:10:20::53
R1(config-dhcpv6)# domain-name asir.local
R1(config-dhcpv6)# exit
R1(config)# interface g0/0
R1(config-if)# ipv6 dhcp server LAN-V6
R1(config-if)# ipv6 nd other-config-flag
```

For a stateful design, add `address prefix 2001:db8:10:20::/64` to the pool and `ipv6 nd managed-config-flag` to the interface. Verification: `show ipv6 interface g0/0` (it states how hosts should configure themselves), `show ipv6 dhcp pool`, and, on the PC, `ipconfig /all`.

## 6.4. Minimum verification

A useful sequence is:

```text
1. Is a link-local address present?
2. Is a global or ULA address present when expected?
3. Has DAD completed?
4. Is a default route present?
5. Is the router known as a neighbor?
6. Is DNS configured?
7. Is an AAAA record available when expected?
8. Does IPv6 connectivity work by address?
9. Does the service respond?
```

The symptom determines which steps are required.

## 6.5. Dual stack

In **dual stack**, IPv4 and IPv6 operate at the same time.

Example:

```text
IPv4:
192.0.2.10/24

IPv6:
2001:db8:10:20::10/64
```

Dual stack does not mean that every packet is sent twice.

An application may use IPv4 or IPv6 depending on name resolution, connectivity, and system behavior. In general, if a name has both A and AAAA records, current systems try IPv6 first and, if it does not answer in time, fall back to IPv4 (*Happy Eyeballs*). As a result, an IPv6 failure can stay hidden: the website "works", just over IPv4.

## 6.6. Test each family separately

To avoid one family hiding a problem in the other:

```text
ping -4 example.net
ping -6 example.net
```

You may find:

```text
IPv4 works
IPv6 fails
```

or the opposite.

If a website works, that does not prove that IPv6 is working.

## 6.7. IPv4 / IPv6 comparison

| Function | IPv4 | IPv6 |
|---|---|---|
| LAN addressing | Address + prefix | Address + prefix |
| Neighbor resolution | ARP | NDP |
| Automatic configuration | DHCPv4 | SLAAC and/or DHCPv6 |
| Default router | Manual/DHCPv4 | RA |
| DNS record | A | AAAA |
| Broadcast | Yes | No; multicast is used for many functions |

### Key points

- IPv4 and IPv6 can fail independently.
- A working application does not prove which IP family was used.
- Dual-stack troubleshooting should test both families separately.
- Each parameter has its own command: address, route, neighbor, and DNS are checked separately.

# 7. Capturing IPv6 traffic with Wireshark

The commands in Section 6 show the **result** of autoconfiguration; Wireshark lets you see the **process**: which messages are exchanged, who sends them, and what they contain. This section collects the useful filters, the sequence you can expect when an interface comes up, and, above all, how to separate what a capture proves from what it only suggests.

| Concept | Question it answers | Example |
|---|---|---|
| **Display filter** (*filtro de visualización*) | How do I isolate the traffic I care about? | `icmpv6.type == 134` |
| **Autoconfiguration sequence** (*secuencia de autoconfiguración*) | What order of messages should I expect? | DAD → RS → RA → DAD → NS/NA |
| **Analysis questions** (*preguntas de análisis*) | What do I look for in the capture? | Which prefix does the RA advertise? |
| **Fact vs. interpretation** (*hecho frente a interpretación*) | What does the capture prove, and what does it not prove? | "No RA visible" ≠ "the router is off" |

Do not confuse **not seeing** a packet with the packet **not existing**: the capture point and capture time always limit the conclusion.

## 7.1. Basic filters

```text
ipv6
icmpv6
dhcpv6
```

For NDP:

```text
icmpv6.type == 133   # RS
icmpv6.type == 134   # RA
icmpv6.type == 135   # NS
icmpv6.type == 136   # NA
icmpv6.type >= 133 && icmpv6.type <= 136   # all NDP
```

For AAAA queries:

```text
dns.qry.type == 28
```

To find a specific address (source or destination):

```text
ipv6.addr == fe80::1
```

In an RA, expand *ICMPv6 Option (Prefix information)* to see the prefix and the A flag, and the header *Flags* for M and O; if it carries DNS, the *Recursive DNS Server* option will appear.

## 7.2. Example sequence

When an interface becomes active, you may observe, depending on the system and timing:

```text
link-local / DAD
      ↓
RS
      ↓
RA
      ↓
global address / DAD
      ↓
(DHCPv6, if M or O indicate it)
      ↓
NS / NA
      ↓
DNS AAAA
      ↓
IPv6 traffic
```

Not every capture will show every step:

- an RA may have arrived before the capture started;
- neighbor information may already be cached;
- DNS data may already be cached;
- DHCPv6 may or may not be used.

## 7.3. Analysis questions

```text
Is an RS visible?
Is an RA visible?
Which address does the router use?
Which prefix is advertised?
Which A, M, and O flags does it carry?
Is an NS or NA visible?
Which neighbor is being resolved?
Is there an AAAA query?
Is there a response?
What cannot be proved from this capture point?
```

## 7.4. Fact and interpretation

**Fact**

```text
An RS is visible.
No RA is visible in this capture.
```

**Careful interpretation**

```text
No Router Advertisement was observed
at this capture point.
```

**Unsupported conclusion**

```text
The router is powered off.
```

The missing packet may have other explanations.

### Key points

- A capture connects protocol messages with their functions.
- Capture time and location limit the conclusions.
- Missing traffic does not automatically identify the cause.

# 8. Systematic IPv6 troubleshooting

This section brings everything together. When something fails in IPv6, the goal is to locate **which part of the process** is not producing the expected result: the address, the RA, the route, the neighbor, DNS, or the service. To do so we follow the reasoning used throughout the module (symptom → question → hypothesis → test → evidence → conclusion) and, when something needs fixing, a **minimal change** followed by **verification**.

| Scenario (*situación*) | First evidence to collect | Line of investigation |
|---|---|---|
| **Link-local only** (*solo link-local*) | Is an RA arriving? With which prefix and flags? | RA, prefix, SLAAC, DHCPv6 if used |
| **No default route** (*global sin ruta por defecto*) | `ip -6 route` / `route print -6` | RA reception, *router lifetime*, manual configuration |
| **INCOMPLETE neighbor** (*vecino incompleto*) | Neighbor Cache + NS/NA capture | Link, address, neighbor, filtering |
| **AAAA OK, service down** (*AAAA correcto, servicio inaccesible*) | `ping -6` to the address | Route, NDP, filters, service |
| **IPv4 OK, IPv6 fails** (*IPv4 funciona, IPv6 no*) | Separate tests for each family | IPv6-specific elements |

Do not confuse **symptom** with **cause**: "there is no global address" is a symptom; the cause has to be proved.

## 8.1. Initial workflow

```text
1. check the physical link;
2. check link-local;
3. check global/ULA addressing;
4. review DAD and RA;
5. check the default route;
6. check the Neighbor Cache;
7. check DNS AAAA;
8. test IPv6 by address;
9. compare with IPv4;
10. capture traffic when it adds useful evidence.
```

Not every step is required in every case.

## 8.2. Only link-local is present

Example:

```text
fe80::...
```

but no global/ULA address is present when one is expected.

Fact:

```text
IPv6 is enabled and a link-local address exists.
```

Investigate:

- Router Advertisements;
- advertised prefix;
- SLAAC;
- DHCPv6 if the design uses it.

Do not automatically conclude that DHCPv6 failed.

In a lab with a Cisco router, a frequent cause is a missing `ipv6 unicast-routing`: the router has IPv6 addresses but sends no RAs. This is a hypothesis to test (capture with no RA, `show running-config`), not an automatic conclusion.

## 8.3. Global address but no default route

Example:

```text
global address → present
route ::/0     → missing
```

Review:

- RA reception;
- router information (an RA with *router lifetime* 0 advertises the prefix but says that router must not be used as the default router);
- manual configuration.

## 8.4. Incomplete Neighbor Cache

Example:

```text
fe80::1  INCOMPLETE
```

Fact:

```text
Neighbor resolution has not completed.
```

Possible investigation areas include:

- the link;
- the address;
- the neighbor;
- NDP traffic;
- filtering or configuration.

## 8.5. AAAA resolves but the service is unreachable

```text
AAAA → 2001:db8:100::20
```

DNS returned an IPv6 address.

You still need to check:

- routes;
- connectivity;
- Neighbor Discovery;
- filtering;
- the service itself.

## 8.6. IPv4 works but IPv6 fails

This means the host still has some network connectivity, so the investigation should focus on IPv6-specific evidence:

- IPv6 address;
- RA;
- routes;
- NDP;
- AAAA;
- IPv6 policies.

## 8.7. Document and verify

Template:

```text
Symptom:
Interface:

Link-local:
Global/ULA:
DAD:
Route ::/0:
Router:
Neighbor Cache:
DNS AAAA:

IPv6 test:
IPv4 test:

Facts:
Hypothesis:
Next test:

Correction:
Verification:
Conclusion:
```

## 8.8. Responsible use of AI assistants

An AI assistant may help to:

- explain outputs;
- distinguish RS, RA, NS, and NA;
- suggest filters;
- generate hypotheses;
- structure a report.

Always check that it does not:

- confuse NDP with ARP;
- claim that DHCPv6 supplies the gateway;
- assume that SLAAC always uses a MAC-derived identifier;
- turn missing traffic into a confirmed root cause;
- ignore the capture point.

Do not share real sensitive captures or production configurations without authorization.

## 8.9. Integrated dual-stack case

Scenario:

```text
IPv4:
  correct address
  correct gateway
  correct A record
  connectivity → works

IPv6:
  link-local → present
  global     → present
  ::/0       → missing
  AAAA       → correct
  remote ping -6 → fails
```

Do not conclude:

```text
"Internet works"
→ "IPv6 works"
```

because IPv4 may be hiding the IPv6 failure.

Procedure:

```text
1. separate the two address families;
2. confirm the IPv6 facts;
3. identify where the default route should come from;
4. look for Router Advertisements;
5. verify after the correction.
```

The leading hypothesis may involve RA/default-route learning, but it still needs evidence.

Another scenario:

```text
link-local → present
global     → missing
RA         → visible
prefix     → advertised
DAD        → failure
```

Here the problem is not simply "no RA". The capture proves that router information is present and directs investigation toward address generation/validation (for example, another device with the same address configured manually).

### Operational rule

In dual stack:

```text
application works
≠
IPv4 and IPv6 both work
```

When the diagnosis depends on the IP family, test each family explicitly.

### Key points

- Link-local, global addressing, route, neighbor state, and DNS are different evidence sources.
- IPv4 can hide an IPv6 failure.
- Every correction should end with verification.
