title: "U05 — IPv6 and Autoconfiguration"
---

> **Guiding question:** How does a host obtain its IPv6 configuration, where does each parameter come from, and what evidence can prove that IPv6 is actually working?

In U04, we learned how to interpret IPv4 addressing, prefixes, default gateways, subnetting, VLSM, CIDR, and DHCP. IPv6 keeps the idea of **address + prefix**, but it changes important parts of local-network operation and autoconfiguration.

An IPv6 interface can use several addresses at the same time. Routers advertise information through **Router Advertisement (RA)**; a host can generate addresses through **SLAAC**, check for duplicates through **Duplicate Address Detection (DAD)**, and discover neighbors through the **Neighbor Discovery Protocol (NDP)**. DHCPv6 can provide part of the configuration, but **it does not provide the default router**.

The central idea of this unit is to interpret IPv6 as a set of related mechanisms and troubleshoot it through observable evidence:

```text
configuration
→ address type and scope
→ prefix
→ source of each parameter
→ RA / SLAAC / DAD
→ NDP
→ default route
→ DNS
→ IPv6 test
→ packet capture when it adds evidence
→ conclusion
```

## By the end of this unit, you should be able to

- read, expand, and compress IPv6 addresses;
- recognize global unicast, link-local, ULA, loopback, multicast, and documentation prefixes;
- plan several `/64` networks from a parent prefix;
- explain the role of link-local addresses, RS, RA, SLAAC, and DAD;
- distinguish RS, RA, NS, and NA;
- interpret a basic Neighbor Cache;
- distinguish SLAAC, stateless DHCPv6, stateful DHCPv6, and RDNSS;
- explain where the address, prefix, default router, and DNS information can come from;
- interpret DNS `AAAA` records;
- verify IPv6 separately from IPv4 in a dual-stack environment;
- use Wireshark to observe ICMPv6, NDP, DHCPv6, and DNS;
- troubleshoot IPv6 through tests and evidence instead of drawing conclusions from symptoms alone.

# 1. Reading and writing IPv6 addresses

## 1.1. One interface can have several addresses

In IPv6, it is normal for an interface to use several addresses at the same time.

Example:

```text
Interface: Ethernet

Addresses:
  fe80::a00:27ff:fe12:3456/64
  2001:db8:10:20::25/64

Route:
  default via fe80::1

DNS:
  2001:db8:53::53
```

This example includes:

- a **link-local** address;
- an address in prefix `2001:db8:10:20::/64`;
- a default route using a link-local next hop;
- an IPv6 DNS server.

Do not search for "the IPv6 address" of a host as if only one address could exist.

## 1.2. Address structure

IPv6 uses **128-bit addresses**, normally written as eight 16-bit hexadecimal groups called **hextets**.

Full form:

```text
2001:0db8:0010:0020:0000:0000:0000:0042
```

### Removing leading zeros

Leading zeros inside a hextet may be omitted:

```text
2001:db8:10:20:0:0:0:42
```

### Using `::`

One continuous sequence of zero hextets may be replaced by `::`:

```text
2001:db8:10:20::42
```

`::` can appear only once in an address.

## 1.3. Expanding an address

Example:

```text
2001:db8:10::25
```

Expanded form:

```text
2001:0db8:0010:0000:0000:0000:0000:0025
```

Procedure:

1. count the visible hextets;
2. locate `::`;
3. add enough `0000` groups to reach eight hextets;
4. write four hexadecimal digits in each hextet.

## 1.4. Address types and scopes to recognize

| Type | Prefix or example | Basic use |
|---|---|---|
| **Global unicast** | mainly `2000::/3` | Potentially global communication |
| **Link-local** | `fe80::/10` | Communication on the local link |
| **ULA** | `fc00::/7`, commonly `fd00::/8` | Internal networks |
| **Loopback** | `::1/128` | The local host |
| **Multicast** | `ff00::/8` | Communication with groups |
| **Documentation** | `2001:db8::/32` | Examples and labs |

IPv6 does not use broadcast in the same way as IPv4. Many functions use **multicast**.

## 1.5. Address and prefix

Example:

```text
2001:db8:10:20::25/64
```

Address:

```text
2001:db8:10:20::25
```

LAN prefix:

```text
2001:db8:10:20::/64
```

In this unit, LANs will normally use `/64` prefixes.

### Key points

- An IPv6 interface may use several addresses.
- Address and prefix must be interpreted together.
- Compression changes the representation, not the address.

# 2. Simple prefix planning

IPv6 LAN planning is not about saving a few host addresses. It is mainly about organizing **prefixes**.

## 2.1. The `/64` LAN prefix

Example:

```text
2001:db8:1200:20::25/64
```

The subnet is:

```text
2001:db8:1200:20::/64
```

In this unit, LANs will normally be designed as `/64`.

## 2.2. Creating `/64` subnets from a parent block

Suppose an organization has:

```text
2001:db8:1200::/48
```

It can allocate several `/64` prefixes:

| Use | Prefix |
|---|---|
| Users | `2001:db8:1200:10::/64` |
| Wi‑Fi | `2001:db8:1200:20::/64` |
| Servers | `2001:db8:1200:30::/64` |
| Management | `2001:db8:1200:40::/64` |
| Laboratory | `2001:db8:1200:50::/64` |

The bits between `/48` and `/64` can identify subnets.

We will not transfer the U04 VLSM model based on minimum host counts to IPv6 LANs. The goal is not to save a few host addresses but to organize prefix space coherently; therefore, LANs will normally use `/64`.

## 2.3. Documenting the plan

A simple plan should be:

- consistent;
- readable;
- scalable;
- documented.

Example:

| Prefix | Use | Planned configuration |
|---|---|---|
| `2001:db8:1200:10::/64` | Users | SLAAC |
| `2001:db8:1200:20::/64` | Wi‑Fi | SLAAC |
| `2001:db8:1200:30::/64` | Servers | According to design |

### Key points

- IPv6 LANs normally use `/64`.
- Planning is about organizing prefixes consistently.
- One parent block can provide many `/64` subnets.

# 3. Link-local, Router Advertisement, SLAAC, and DAD

IPv6 autoconfiguration uses several mechanisms that work together.

## 3.1. Link-local address

When IPv6 is enabled, an interface normally creates a **link-local** address.

Example:

```text
fe80::a00:27ff:fe12:3456
```

A link-local address:

- works only on the local link;
- is used to communicate with routers and neighbors;
- participates in Neighbor Discovery;
- may be used as a next-hop address.

Therefore, this is normal:

```text
default via fe80::1
```

## 3.2. Router Solicitation and Router Advertisement

A host may send a **Router Solicitation (RS)** to request information from routers on the link.

A router can reply or send periodic **Router Advertisements (RA)**.

```text
Host                         Router

RS ------------------------->
                  <----------- RA
```

An RA may indicate:

- available prefixes;
- whether a prefix can be used for SLAAC;
- that the sender can act as a default router;
- other configuration information.

> The IPv6 default router is normally learned through **RA**, not DHCPv6.

## 3.3. SLAAC

**SLAAC** (*Stateless Address Autoconfiguration*) allows a host to generate an IPv6 address from an advertised prefix.

Conceptual process:

```text
link-local
    ↓
RS / RA
    ↓
advertised prefix
    ↓
address generation
    ↓
DAD
    ↓
usable address
```

Modern systems can generate the interface identifier in different ways. Do not assume that every SLAAC address contains the device MAC address.

## 3.4. DAD

**DAD** (*Duplicate Address Detection*) attempts to check whether an address is already in use on the link.

During this process, an address may appear as:

```text
tentative
```

If no conflict is detected, the address can normally be used.

## 3.5. A, M, and O flags

Router Advertisements may include indicators that guide host configuration:

- **A**: the prefix can be used for SLAAC;
- **M**: DHCPv6 may be used to obtain an address;
- **O**: DHCPv6 may provide other parameters.

At this stage, you only need to understand their general purpose.

### Key points

- Link-local exists before global connectivity is required.
- RS requests information and RA advertises it.
- SLAAC can generate an address.
- DAD checks for duplicates.
- The IPv6 gateway is learned through RA.

# 4. Neighbor Discovery and ICMPv6

IPv6 uses **Neighbor Discovery Protocol (NDP)** for several essential local-network functions.

NDP uses **ICMPv6**.

## 4.1. Main messages

| Message | Abbreviation | Function |
|---|---|---|
| Router Solicitation | **RS** | Request router information |
| Router Advertisement | **RA** | Advertise network information |
| Neighbor Solicitation | **NS** | Request information about a neighbor |
| Neighbor Advertisement | **NA** | Reply with neighbor information |

For Wireshark filters, it is useful to recognize:

```text
133 → RS
134 → RA
135 → NS
136 → NA
```

You do not need to memorise many more ICMPv6 types in this unit.

## 4.2. NS and NA: neighbor resolution

In IPv4, ARP maps IPv4 addresses to MAC addresses on the local link.

In IPv6, this function is part of NDP.

```text
Host A                         Host B

NS --------------------------->
                   <----------- NA
```

On Ethernet, NS messages use IPv6 multicast to locate the neighbor. Technical tools and resources may use the term **solicited-node multicast**. In this unit, you only need to recognize its purpose; you do not need to calculate solicited-node multicast addresses.

The result can be stored in the **Neighbor Cache**.

## 4.3. Neighbor Cache

States to recognize:

| State | Initial interpretation |
|---|---|
| **REACHABLE** | Recent evidence that the neighbor is reachable |
| **STALE** | An entry exists but may require confirmation |
| **INCOMPLETE** | Neighbor resolution has not completed |
| **FAILED** | Resolution did not complete successfully |

An `INCOMPLETE` entry does not identify the root cause. Investigate the link, address, neighbor, and NDP traffic.

## 4.4. ICMPv6 is essential

ICMPv6 is used for:

- RS and RA;
- NS and NA;
- DAD;
- error messages;
- `ping`.

It should not be treated as only "the ping protocol".

Blocking ICMPv6 indiscriminately can break required IPv6 functions.

## 4.5. Initial IPv4/IPv6 comparison

| IPv4 | IPv6 |
|---|---|
| ARP Request / Reply | NS / NA |
| ARP cache | Neighbor Cache |
| Gateway configured or learned through DHCPv4 | Router learned through RA |
| ICMP for control and diagnostics | ICMPv6 also supports NDP and autoconfiguration |

### Key points

- NDP performs more functions than ARP.
- NS and NA support neighbor resolution.
- The Neighbor Cache provides local-link evidence.
- ICMPv6 is part of normal IPv6 operation.

# 5. SLAAC, DHCPv6, RDNSS, and DNS AAAA

IPv6 does not necessarily use one mechanism to provide every configuration parameter.

## 5.1. Where can each parameter come from?

| Parameter | Possible source |
|---|---|
| Link-local address | The host itself |
| Global / ULA address | SLAAC, DHCPv6, or manual configuration |
| Prefix | Router Advertisement or manual configuration |
| Default router | Router Advertisement |
| DNS | RDNSS, DHCPv6, or manual configuration |

This table is fundamental for IPv6 troubleshooting.

## 5.2. Stateless DHCPv6

In a **stateless** design:

```text
SLAAC   → IPv6 address
DHCPv6  → other parameters
```

For example, DHCPv6 may provide DNS information.

## 5.3. Stateful DHCPv6

In a **stateful** design, DHCPv6 may assign an IPv6 address.

However, the default router is still learned from RA.

| Mechanism | Address | Gateway |
|---|---|---|
| SLAAC | SLAAC | RA |
| Stateless DHCPv6 | SLAAC | RA |
| Stateful DHCPv6 | DHCPv6 | RA |

## 5.4. RDNSS

A Router Advertisement can provide DNS-server information using **RDNSS**.

Therefore:

```text
SLAAC
```

does not mean:

```text
no DNS
```

The actual source depends on the network design.

## 5.5. AAAA records

An **AAAA record** maps a name to an IPv6 address.

Example:

```text
srv.example.  AAAA  2001:db8:100::20
```

Possible tools include:

```text
nslookup
dig AAAA
Resolve-DnsName -Type AAAA
```

A correct AAAA response proves that DNS returned an IPv6 address. It does not prove that the address is reachable or that the service works.

### Key points

- Address, gateway, and DNS may come from different mechanisms.
- DHCPv6 does not provide the default gateway.
- SLAAC and DHCPv6 can coexist.
- A correct AAAA record does not prove connectivity.

# 6. Verification and dual stack

An IPv6 configuration should be verified in separate parts.

## 6.1. What to inspect

| Goal | Windows | Linux |
|---|---|---|
| Addresses | `ipconfig` / PowerShell | `ip -6 address` |
| Routes | PowerShell | `ip -6 route` |
| Neighbors | PowerShell | `ip -6 neigh` |
| DNS AAAA | `nslookup` / PowerShell | `dig AAAA` |
| ICMPv6 | `ping -6` | `ping -6` |

You do not need to memorise every syntax variant. You should know **which information you need and how to interpret it**.

## 6.2. Minimum verification

A useful sequence is:

```text
1. Is a link-local address present?
2. Is a global or ULA address present when expected?
3. Has DAD completed?
4. Is a default route present?
5. Is the router known as a neighbor?
6. Is DNS configured?
7. Is an AAAA record available when expected?
8. Does IPv6 connectivity work by address?
9. Does the service respond?
```

The symptom determines which steps are required.

## 6.3. Dual stack

In **dual stack**, IPv4 and IPv6 operate at the same time.

Example:

```text
IPv4:
192.0.2.10/24

IPv6:
2001:db8:10:20::10/64
```

Dual stack does not mean that every packet is sent twice.

An application may use IPv4 or IPv6 depending on name resolution, connectivity, and system behavior.

## 6.4. Test each family separately

To avoid one family hiding a problem in the other:

```text
ping -4 example.net
ping -6 example.net
```

You may find:

```text
IPv4 works
IPv6 fails
```

or the opposite.

If a website works, that does not prove that IPv6 is working.

## 6.5. IPv4 / IPv6 comparison

| Function | IPv4 | IPv6 |
|---|---|---|
| LAN addressing | Address + prefix | Address + prefix |
| Neighbor resolution | ARP | NDP |
| Automatic configuration | DHCPv4 | SLAAC and/or DHCPv6 |
| Default router | Manual/DHCPv4 | RA |
| DNS record | A | AAAA |
| Broadcast | Yes | No; multicast is used for many functions |

### Key points

- IPv4 and IPv6 can fail independently.
- A working application does not prove which IP family was used.
- Dual-stack troubleshooting should test both families separately.

# 7. Capturing IPv6 traffic with Wireshark

Wireshark can make autoconfiguration and Neighbor Discovery visible.

## 7.1. Basic filters

```text
ipv6
icmpv6
dhcpv6
```

For NDP:

```text
icmpv6.type == 133   # RS
icmpv6.type == 134   # RA
icmpv6.type == 135   # NS
icmpv6.type == 136   # NA
```

For AAAA queries:

```text
dns.qry.type == 28
```

## 7.2. Example sequence

When an interface becomes active, you may observe:

```text
link-local / DAD
      ↓
RS
      ↓
RA
      ↓
global address / DAD
      ↓
NS / NA
      ↓
DNS AAAA
      ↓
IPv6 traffic
```

Not every capture will show every step:

- an RA may have arrived before the capture started;
- neighbor information may already be cached;
- DNS data may already be cached;
- DHCPv6 may or may not be used.

## 7.3. Analysis questions

```text
Is an RS visible?
Is an RA visible?
Which address does the router use?
Which prefix is advertised?
Is an NS or NA visible?
Which neighbor is being resolved?
Is there an AAAA query?
Is there a response?
What cannot be proved from this capture point?
```

## 7.4. Fact and interpretation

**Fact**

```text
An RS is visible.
No RA is visible in this capture.
```

**Careful interpretation**

```text
No Router Advertisement was observed
at this capture point.
```

**Unsupported conclusion**

```text
The router is powered off.
```

The missing packet may have other explanations.

### Key points

- A capture connects protocol messages with their functions.
- Capture time and location limit the conclusions.
- Missing traffic does not automatically identify the cause.

# 8. Systematic IPv6 troubleshooting

Troubleshooting should identify which part of the expected IPv6 process is missing or incorrect.

## 8.1. Initial workflow

```text
1. check the physical link;
2. check link-local;
3. check global/ULA addressing;
4. review DAD and RA;
5. check the default route;
6. check the Neighbor Cache;
7. check DNS AAAA;
8. test IPv6 by address;
9. compare with IPv4;
10. capture traffic when it adds useful evidence.
```

Not every step is required in every case.

## 8.2. Only link-local is present

Example:

```text
fe80::...
```

but no global/ULA address is present when one is expected.

Fact:

```text
IPv6 is enabled and a link-local address exists.
```

Investigate:

- Router Advertisements;
- advertised prefix;
- SLAAC;
- DHCPv6 if the design uses it.

Do not automatically conclude that DHCPv6 failed.

## 8.3. Global address but no default route

Example:

```text
global address → present
route ::/0     → missing
```

Review:

- RA reception;
- router information;
- manual configuration.

## 8.4. Incomplete Neighbor Cache

Example:

```text
fe80::1  INCOMPLETE
```

Fact:

```text
Neighbor resolution has not completed.
```

Possible investigation areas include:

- the link;
- the address;
- the neighbor;
- NDP traffic;
- filtering or configuration.

## 8.5. AAAA resolves but the service is unreachable

```text
AAAA → 2001:db8:100::20
```

DNS returned an IPv6 address.

You still need to check:

- routes;
- connectivity;
- Neighbor Discovery;
- filtering;
- the service itself.

## 8.6. IPv4 works but IPv6 fails

This means the host still has some network connectivity.

Focus on IPv6-specific evidence:

- IPv6 address;
- RA;
- routes;
- NDP;
- AAAA;
- IPv6 policies.

## 8.7. Document and verify

Template:

```text
Symptom:
Interface:

Link-local:
Global/ULA:
DAD:
Route ::/0:
Router:
Neighbor Cache:
DNS AAAA:

IPv6 test:
IPv4 test:

Facts:
Hypothesis:
Next test:

Correction:
Verification:
Conclusion:
```

## 8.8. Responsible use of AI assistants

An AI assistant may help to:

- explain outputs;
- distinguish RS, RA, NS, and NA;
- suggest filters;
- generate hypotheses;
- structure a report.

Always check that it does not:

- confuse NDP with ARP;
- claim that DHCPv6 supplies the gateway;
- assume that SLAAC always uses a MAC-derived identifier;
- turn missing traffic into a confirmed root cause;
- ignore the capture point.

Do not share real sensitive captures or production configurations without authorisation.


## 8.9. Integrated dual-stack case

Scenario:

```text
IPv4:
  correct address
  correct gateway
  correct A record
  connectivity → works

IPv6:
  link-local → present
  global     → present
  ::/0       → missing
  AAAA       → correct
  remote ping -6 → fails
```

Do not conclude:

```text
"Internet works"
→ "IPv6 works"
```

because IPv4 may be hiding the IPv6 failure.

Procedure:

```text
1. separate the two address families;
2. confirm the IPv6 facts;
3. identify where the default route should come from;
4. look for Router Advertisements;
5. verify after the correction.
```

The leading hypothesis may involve RA/default-route learning, but it still needs evidence.

Another scenario:

```text
link-local → present
global     → missing
RA         → visible
prefix     → advertised
DAD        → failure
```

Here the problem is not simply "no RA". The capture proves that router information is present and directs investigation towards address generation/validation.

### Operational rule

In dual stack:

```text
application works
≠
IPv4 and IPv6 both work
```

When the diagnosis depends on the IP family, test each family explicitly.


### Key points

- Link-local, global addressing, route, neighbor state, and DNS are different evidence sources.
- IPv4 can hide an IPv6 failure.
- Every correction should end with verification.
