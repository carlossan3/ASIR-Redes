> **Guiding question:** How do you manage a router securely, how does it decide where to send each packet, and how do you make sure only the traffic the organization wants to allow gets through?

## Introduction

So far you have worked with networks joined by a single Layer 3 device: the default gateway of a LAN or the router in an inter-VLAN scenario. In this unit the router takes center stage. You will learn to:

- understand how a router is built, how it boots, and where it stores its configuration;
- manage it securely, both locally and remotely;
- bring its interfaces into service;
- read its routing table and understand which route it chooses for each destination;
- build IPv4 and IPv6 static routes that work **in both directions**;
- use it as a DHCP server and as a DHCP relay;
- translate a security policy into access control lists (ACLs);
- protect a zone of public-facing servers (DMZ);
- troubleshoot by following the packet's real path.

The unit is built around two decisions the router makes for every packet:

| Decision | Question | Mechanism |
|---|---|---|
| **Routing** | Where can this packet go? | Routing table |
| **Filtering** | Should it be allowed through here? | ACL |

We study them separately, but in a real network they happen to the same packet and must be verified together.

### Reference topology

Many examples in these notes use the same network. Keep it handy.

```text
        LAN-A                  R1–R2 link                     LAN-B
   192.168.10.0/24            10.0.12.0/30               192.168.20.0/24

  PC-A .10 ──[G0/0 .1] R1 [G0/1 .1]──────[G0/1 .2] R2 [G0/0 .1]── PC-B .10
                        [G0/2 .1]                 [G0/2 .1]
                           │                          │
                      Backup link               SERVERS 192.168.30.0/24
                      10.0.21.0/30              WEB .10   DHCP .20
                           │
                        R2 [G0/3 .2]
```

| Network | Prefix | Gateway / endpoints |
|---|---|---|
| LAN-A | 192.168.10.0/24 | R1 G0/0 = 192.168.10.1 |
| LAN-B | 192.168.20.0/24 | R2 G0/0 = 192.168.20.1 |
| SERVERS | 192.168.30.0/24 | R2 G0/2 = 192.168.30.1 · WEB .10 · DHCP/TFTP .20 · DNS .53 |
| Primary link | 10.0.12.0/30 | R1 G0/1 = .1 · R2 G0/1 = .2 |
| Backup link | 10.0.21.0/30 | R1 G0/2 = .1 · R2 G0/3 = .2 |

For IPv6 we use `2001:db8:acad:10::/64` (LAN-A), `2001:db8:acad:20::/64` (LAN-B), and `2001:db8:acad:12::/64` (R1–R2 link).

> Interface names (`G0/0`, `G0/1`…) depend on the model. In Packet Tracer and on real gear you'll see variants such as `GigabitEthernet0/0/0`. What matters is knowing **which network sits behind each interface**.

# 1. What a router does

## 1.1. From the host's decision to the router's decision

In U04 you saw that a host first decides whether the destination is local or remote:

- if the destination is on its own network, it delivers directly (ARP/ND to learn the destination MAC);
- if the destination is remote, it sends the packet to its **default gateway**.

So the router receives remote traffic **because the host sends it there**. The router doesn't "grab" traffic; it is the next step the host itself planned.

One detail worth nailing down, because it will come up in troubleshooting:

| Header | Destination field when PC-A sends to PC-B |
|---|---|
| Layer 3 (IP) | 192.168.20.10 → **PC-B** (final destination) |
| Layer 2 (Ethernet on LAN-A) | MAC of **R1 G0/0** (the gateway) |

The destination IP says who the packet is for. The destination MAC says who receives the frame **on that link**.

## 1.2. Router vs. switch

| | Switch (Layer 2) | Router (Layer 3) |
|---|---|---|
| Connects | devices on the same network / VLAN | different networks |
| Decides using | destination MAC address | destination IP address |
| Table | MAC address table | routing table |
| Broadcasts | forwards them within the VLAN | does not forward them between networks |
| Frame | forwards it without rewriting addresses | builds a new frame at each hop |

Each router interface belongs to a different network. That is why a router separates broadcast domains, just as you saw with VLANs in U07.

## 1.3. What happens at each hop

When R1 receives a packet destined for PC-B, it:

1. checks that the frame is addressed to its MAC and extracts the IP packet;
2. decrements the **TTL** (in IPv6, the *Hop Limit*); if it reaches 0, it drops the packet and notifies the source with ICMP;
3. looks up the destination IP in the routing table;
4. selects the route and determines the **next hop** and **exit interface**;
5. gets the next hop's MAC (ARP in IPv4, ND in IPv6);
6. builds a new frame and sends it.

```text
               Source IP       Dest. IP        Source MAC    Dest. MAC
LAN-A      :   192.168.10.10   192.168.20.10   PC-A          R1 G0/0
R1-R2 link :   192.168.10.10   192.168.20.10   R1 G0/1       R2 G0/1
LAN-B      :   192.168.10.10   192.168.20.10   R2 G0/0       PC-B
```

IP addresses stay the same along the path (unless NAT is involved, which you'll study in U10). MAC addresses change on every link.

# 2. Hardware, LEDs, and access methods

## 2.1. Physical components

An enterprise router is a specialized computer. It has a CPU, memory, an operating system (on Cisco, **IOS** or IOS XE), and network interfaces. It usually includes:

- built-in **Ethernet ports** (copper and/or SFP for fiber);
- **expansion slots** for modules (more ports, WAN interfaces, voice modules);
- a **console port** (RJ-45 or USB) for local management;
- on older models, an **AUX** port for modem access;
- a USB port for storage or console.

## 2.2. LEDs as first evidence

In U03 you learned that an LED is evidence, not a full diagnosis. A router typically has:

| LED | What it usually indicates |
|---|---|
| SYS / PWR | The device has power and the system booted correctly (solid green) or is booting/has a fault (blinking, amber) |
| ACT | System or interface activity |
| Link / Speed per port | Physical link established and, sometimes, speed |
| Module | Status of each installed module |

The exact meaning of colors and blink patterns **depends on the vendor and model** and is found in the technical documentation. In Packet Tracer, the colored dots at each end of a link (green, amber, red) serve the same purpose.

A lit link LED proves there is a physical signal. It **does not prove** that the interface has an IP address, is enabled in the configuration, or that a route to the destination exists.

## 2.3. Methods for accessing the configuration

| Method | Type | Requirements | Use |
|---|---|---|---|
| **Console** | Local, out-of-band | Console cable and a terminal emulator | Initial setup, recovery, loss of network access |
| **AUX** | Remote via modem (legacy) | Modem | Practically obsolete |
| **Telnet** (TCP 23) | Remote, in-band | Working IP and VTY lines | **Not recommended**: everything travels in clear text |
| **SSH** (TCP 22) | Remote, in-band, encrypted | IP, domain name, RSA keys, local user | Standard remote management method |
| **Web (HTTP/HTTPS)** | Remote, GUI | Device web server enabled | Small devices or setup wizards |
| **API (NETCONF, RESTCONF)** | Remote, programmatic | Modern platforms (IOS XE) | Automation; awareness only in this course |

*In-band* means management traffic travels over the same data network you are managing; if that network fails, you lose access. *Out-of-band* (console, separate management network) doesn't depend on it.

**VTY lines** (*virtual terminal*) are the logical "doors" remote Telnet/SSH sessions come through. A router has several (for example `vty 0 4` or `vty 0 15`), which allows multiple simultaneous sessions.

# 3. Boot process, memory, and configuration files

## 3.1. Router memory

| Memory | Volatile | Main contents |
|---|---|---|
| **ROM** | No | POST, *bootstrap*, and a minimal recovery system (ROMMON) |
| **Flash** | No | IOS operating system image; can store other files |
| **NVRAM** | No | **startup-config**: the configuration loaded at next boot |
| **RAM** | Yes | Running IOS, **running-config**, routing table, ARP table, packet buffers |

Key idea: **what the router is doing right now lives in RAM**, and it is lost at power-off unless it has been saved to NVRAM.

## 3.2. Boot sequence

```text
1. POST (Power-On Self-Test)          → hardware check (ROM)
2. Load the bootstrap                 → small program in ROM
3. Locate and load IOS                → normally from flash
                                        (alternatives: TFTP server, ROMMON)
4. Locate and load the configuration  → startup-config from NVRAM
                                        → copied into RAM as running-config
5. No startup-config found            → initial configuration dialog (setup mode)
```

The IOS search is governed by the **configuration register** (typically `0x2102`) and any `boot system` commands. In this course it's enough to recognize that they exist: changing the register is used, for example, in password recovery procedures, which are not covered here.

A router that boots and shows `Would you like to enter the initial configuration dialog? [yes/no]` **has no startup-config**. It may be a new device or one whose configuration was erased.

## 3.3. `show version`: the device's spec sheet

```text
R1# show version
Cisco IOS Software, ISR Software (X86_64_LINUX_IOSD-UNIVERSALK9-M), Version 16.9.4
...
ROM: IOS-XE ROMMON
R1 uptime is 2 hours, 14 minutes
System image file is "bootflash:isr4300-universalk9.16.09.04.SPA.bin"
...
cisco ISR4331/K9 (1RU) processor ... with 1795979K/6147K bytes of memory.
3 Gigabit Ethernet interfaces
32768K bytes of non-volatile configuration memory.
...
Configuration register is 0x2102
```

It lets you answer with evidence: which IOS version is running, which file it booted from, how long it has been up (a short uptime reveals a recent reboot), which interfaces and memory it has, and which configuration register it uses.

## 3.4. Files and management commands

| Command | What it does |
|---|---|
| `show running-config` | Shows the active configuration (RAM) |
| `show startup-config` | Shows the saved configuration (NVRAM) |
| `copy running-config startup-config` | Saves the active configuration for the next boot |
| `show flash:` (or `dir flash:`) | Lists files in flash (IOS image, others) |
| `copy running-config tftp:` | Sends a backup to a TFTP server |
| `copy tftp: running-config` | Pulls a configuration from TFTP and **merges** it into the active one |
| `copy tftp: startup-config` | Pulls a configuration that will apply at next boot |
| `erase startup-config` | Erases the saved configuration |
| `reload` | Restarts the device |

Two common mistakes:

- **Configuring without saving.** The change works today and disappears after the next power outage.
- **Assuming `copy tftp: running-config` replaces the configuration.** It actually **merges** with the existing one: commands in the file are added or overwritten, but anything not in the file remains. For a clean state, restore to the startup-config and reload.

### Professional backup

Before any significant change:

```text
R1# copy running-config tftp:
Address or name of remote host []? 192.168.30.20
Destination filename [R1-confg]? R1-2026-10-05.cfg
!!
1024 bytes copied
```

A file name with device and date lets you find later which configuration was active at any given time. TFTP provides no encryption or authentication: in production SCP or SFTP is preferred, but TFTP is still common in labs.

# 4. Bringing the router into service: interfaces and connected routes

## 4.1. IOS refresher

From U06 you already know the modes (`R1>`, `R1#`, `R1(config)#`, `R1(config-if)#`), `?` help, and the difference between running and startup. A router works the same way.

## 4.2. Configuring an IPv4 interface

```text
R1(config)# interface GigabitEthernet0/0
R1(config-if)# description LAN-A users
R1(config-if)# ip address 192.168.10.1 255.255.255.0
R1(config-if)# no shutdown
```

- `description` has no technical effect, but it documents the network and saves a lot of time when troubleshooting.
- On Cisco routers, interfaces are **administratively down** by default. Without `no shutdown`, the interface won't work even with an IP address and a cable.

## 4.3. Interpreting interface status

```text
R1# show ip interface brief
Interface              IP-Address      OK? Method Status                Protocol
GigabitEthernet0/0     192.168.10.1    YES manual up                    up
GigabitEthernet0/1     10.0.12.1       YES manual up                    down
GigabitEthernet0/2     10.0.21.1       YES manual administratively down down
```

| Status / Protocol | Interpretation | What to check |
|---|---|---|
| `up / up` | Working at Layers 1 and 2 | — |
| `administratively down / down` | Shut down by configuration | Missing `no shutdown` |
| `down / down` | No physical signal | Cable, remote port shut down, far end disconnected |
| `up / down` | Signal present, but the data link protocol fails | Encapsulation mismatch or remote-end issue |

An `up/up` interface with no IP address contributes no network to the routing table.

## 4.4. Connected (C) and local (L) routes

As soon as an interface with an IPv4 address goes `up/up`, the router automatically installs two routes:

```text
R1# show ip route
...
     192.168.10.0/24 is variably subnetted, 2 subnets, 2 masks
C       192.168.10.0/24 is directly connected, GigabitEthernet0/0
L       192.168.10.1/32 is directly connected, GigabitEthernet0/0
```

- **C (connected):** the whole network the interface belongs to. The router can deliver directly to any host on it.
- **L (local):** a `/32` route to the router's **own address** on that interface. It tells the router that packets addressed to that IP are for itself.

The `L` route is not another network. If the interface goes down, **both** routes disappear. That's why checking whether a connected network is in the table is a quick way to verify the interface's real state.

> **Without configuring a single route**, a router already knows how to reach every network it is directly connected to. It only needs help with networks that sit **behind other routers**.

## 4.5. IPv6 interfaces

From U05 you remember GUA, link-local, and SLAAC. For a router to **route** IPv6, you must enable it globally:

```text
R1(config)# ipv6 unicast-routing
R1(config)# interface GigabitEthernet0/0
R1(config-if)# ipv6 address 2001:db8:acad:10::1/64
R1(config-if)# ipv6 address fe80::1 link-local
R1(config-if)# no shutdown
```

- Without `ipv6 unicast-routing` the router has IPv6 addresses but **does not forward** IPv6 packets or send RA messages to the LAN.
- Assigning an easy-to-read link-local (`fe80::1`) isn't required, but it greatly simplifies troubleshooting and routes that use it.

Verification: `show ipv6 interface brief` and `show ipv6 route`. IPv6 also shows `C` routes (the `/64`) and `L` routes (a `/128` with the router's own address).

# 5. Secure remote management: from Telnet to SSH

## 5.1. The problem with Telnet

Telnet sends **everything in clear text**: username, password, and every command. Anyone capturing traffic along the path can read them. In a Wireshark capture, *Follow TCP Stream* on a Telnet session (port 23) literally shows the typed password. In an SSH session (port 22), after the initial key exchange, you only see encrypted content.

Hence the professional rule: **SSH for remote management; Telnet disabled.**

## 5.2. Protecting local and privileged access

Before opening remote access, lock down basic access:

```text
R1(config)# enable secret Cl4ve-Privilegiada
R1(config)# service password-encryption
R1(config)# security passwords min-length 10
R1(config)# banner motd #Authorized personnel only#
R1(config)# line console 0
R1(config-line)# login local
R1(config-line)# exec-timeout 5 0
```

| Command | Effect |
|---|---|
| `enable secret` | Protects privileged mode with a password stored as a *hash*. Replaces the old `enable password` |
| `service password-encryption` | Hides clear-text passwords in the configuration with weak (type 7) encryption. Stops casual viewing; it is **not** strong protection |
| `security passwords min-length` | Enforces a minimum length for new passwords |
| `exec-timeout 5 0` | Closes the session after 5 minutes of inactivity |
| `banner motd` | Legal warning message on connection |

## 5.3. Configuring SSH

SSH requires five elements:

```text
R1(config)# hostname R1
R1(config)# ip domain-name empresa.local
R1(config)# crypto key generate rsa general-keys modulus 2048
R1(config)# ip ssh version 2
R1(config)# username admin secret Adm1n-Segura!
R1(config)# line vty 0 4
R1(config-line)# login local
R1(config-line)# transport input ssh
R1(config-line)# exec-timeout 5 0
```

| Step | Why it's needed |
|---|---|
| `hostname` other than `Router` | The name is part of the key identifier |
| `ip domain-name` | Together with the hostname, names the RSA keys (`R1.empresa.local`) |
| `crypto key generate rsa ... modulus 2048` | Generates the key pair that encrypts the session. SSH version 2 requires at least 768 bits; 2048 is recommended |
| `ip ssh version 2` | Disables insecure version 1 |
| `username ... secret` | Creates a local account; `secret` stores it as a *hash* |
| `login local` on VTY | Remote sessions authenticate against local accounts |
| `transport input ssh` | Only SSH is accepted on those lines: Telnet is refused |

The router also needs an **IP address reachable** from the management workstation. On a switch you used a management SVI (U07); on a router, any of its working interfaces will do.

## 5.4. Verification

```text
R1# show ip ssh
SSH Enabled - version 2.0
Authentication timeout: 120 secs; Authentication retries: 3

R1# show ssh
Connection Version Encryption  State           Username
0          2.0     aes256-ctr  Session started admin
```

From a PC:

```text
C:\> ssh -l admin 192.168.10.1
```

Positive test: the SSH session opens as user `admin`. Negative test: an attempt to `telnet 192.168.10.1` is refused. Both are needed to prove the configuration does what it is supposed to.

Later (section 17) you'll restrict **which networks** can open an SSH session using an ACL applied to the VTY lines.

# 6. The routing table

## 6.1. What it contains

The routing table is the list of destinations the router knows and how to reach them. Each entry answers three questions: **to which network?**, **which way?**, and **who told me?**

```text
R1# show ip route
Codes: L - local, C - connected, S - static, R - RIP, O - OSPF, ...
       * - candidate default

Gateway of last resort is 10.0.12.2 to network 0.0.0.0

S*    0.0.0.0/0 [1/0] via 10.0.12.2
      10.0.0.0/8 is variably subnetted, 2 subnets, 2 masks
C        10.0.12.0/30 is directly connected, GigabitEthernet0/1
L        10.0.12.1/32 is directly connected, GigabitEthernet0/1
      192.168.10.0/24 is variably subnetted, 2 subnets, 2 masks
C        192.168.10.0/24 is directly connected, GigabitEthernet0/0
L        192.168.10.1/32 is directly connected, GigabitEthernet0/0
S     192.168.20.0/24 [1/0] via 10.0.12.2
```

| Element | Example | Meaning |
|---|---|---|
| Source code | `S`, `C`, `L`, `S*` | How the route was learned |
| Destination / prefix | `192.168.20.0/24` | Network the route represents |
| `[AD/metric]` | `[1/0]` | Administrative distance and metric |
| Next hop | `via 10.0.12.2` | Router the packet is handed to |
| Exit interface | `GigabitEthernet0/1` | Where the packet leaves |
| Gateway of last resort | `10.0.12.2` | Next hop of the default route, if any |

Lines like `10.0.0.0/8 is variably subnetted` are headers that group subnets; they are not usable routes by themselves.

## 6.2. Route sources in this unit

| Code | Source | Default AD |
|---|---|---:|
| `C` | Connected network | 0 |
| `L` | Local address | 0 |
| `S` | Static route | 1 |
| `S*` | Static candidate default route | 1 |

In U09 you'll see routes learned by dynamic protocols (`R` RIP with AD 120, `O` OSPF with AD 110).

## 6.3. Administrative distance (AD)

AD expresses **how much the router trusts the source** of a route. Lower is preferred. It is only used as a tiebreaker when **several sources offer the exact same prefix**.

The **metric** compares paths within a single source (for example, two OSPF paths). Static routes have a metric of 0.

## 6.4. Looking up a specific destination

```text
R1# show ip route 192.168.20.10
Routing entry for 192.168.20.0/24
  Known via "static", distance 1, metric 0
  Routing Descriptor Blocks:
  * 10.0.12.2
      Route metric is 0, traffic share count is 1
```

This command applies the same logic the router uses when forwarding and returns the chosen route. It's the most direct way to answer "what will the router do with this destination?".

# 7. Longest prefix match

## 7.1. Several routes can match

A route *matches* a destination when the first N bits of the destination equal those of the route's network, N being the prefix length. With nested routes, one destination can match several:

```text
S*   0.0.0.0/0           via 10.0.0.254
S    172.16.0.0/16       via 10.0.0.2
S    172.16.40.0/24      via 10.0.0.3
S    172.16.40.128/25    via 10.0.0.4
S    172.16.40.144/28    via 10.0.0.5
S    172.16.40.150/32    via 10.0.0.6
```

## 7.2. The rule

> Among all routes that match the destination, the router picks the one with the **longest prefix**, that is, the most specific.

| Destination | Matching routes | Chosen route | Next hop |
|---|---|---|---|
| 172.16.40.150 | /0, /16, /24, /25, /28, /32 | /32 | 10.0.0.6 |
| 172.16.40.149 | /0, /16, /24, /25, /28 | /28 (144–159) | 10.0.0.5 |
| 172.16.40.130 | /0, /16, /24, /25 | /25 (128–255) | 10.0.0.4 |
| 172.16.40.10 | /0, /16, /24 | /24 | 10.0.0.3 |
| 172.16.41.10 | /0, /16 | /16 | 10.0.0.2 |
| 203.0.113.9 | /0 | /0 | 10.0.0.254 |

To check matches for prefixes that don't end on an octet boundary, use what you learned in U04: work out the network's range (`172.16.40.144/28` → 144–159) and check whether the destination falls inside it.

## 7.3. LPM before AD

Common mistake: comparing the AD of two routes with different prefixes.

```text
S   10.0.0.0/8       [1/0]   via 10.0.12.2
S   10.10.20.0/24    [20/0]  via 10.0.21.2
```

For destination `10.10.20.50`, the router picks the `/24` even though its AD is 20 and the other's is 1. **They don't compete**: they are different prefixes and the more specific one wins. AD only comes into play if two sources offer exactly `10.10.20.0/24`.

```text
1st  Which routes match?          → bit comparison
2nd  Which is the most specific?  → longest prefix match
     (AD was already used earlier to decide which source installs each prefix)
```

## 7.4. A route in the table is not connectivity

A route to a destination only proves the router **knows where to send it**. The next hop, ARP/ND resolution, the return path, an ACL, the service, or the destination host itself can still fail. Keep this limit in mind when interpreting evidence.

# 8. IPv4 static routes

## 8.1. What a static route is

A **static route** is a route the administrator types in by hand. The router uses it as-is until someone changes it or until it becomes unusable (for example, because the interface used to reach the next hop goes down).

| Advantages | Drawbacks |
|---|---|
| Full control over the path | Manual maintenance on every router |
| No CPU or protocol traffic overhead | Doesn't adapt when a remote path fails |
| Predictable and easy to verify | Scales poorly: with many networks it becomes unmanageable and error-prone |
| Useful in small networks, *stub* networks, and default routes | An error propagates silently |

## 8.2. Syntax

```text
ip route  DEST_NETWORK  MASK  { NEXT_HOP | INTERFACE | INTERFACE NEXT_HOP }  [AD]
```

In the reference topology, R1 doesn't know LAN-B. To reach it:

```text
R1(config)# ip route 192.168.20.0 255.255.255.0 10.0.12.2
```

Read it as: "for any destination in `192.168.20.0/24`, hand the packet to `10.0.12.2`".

## 8.3. Three ways to specify the path

| Form | Example | Behavior |
|---|---|---|
| **Next hop** | `ip route 192.168.20.0 255.255.255.0 10.0.12.2` | The router looks up how to reach `10.0.12.2` (recursive lookup). The most common form on Ethernet |
| **Exit interface** | `ip route 192.168.20.0 255.255.255.0 g0/1` | The router treats the destination as if it were connected to that interface. Suitable on point-to-point (serial) links; **not recommended on Ethernet**, because it forces ARP for every destination and relies on the neighbor router's *proxy ARP* |
| **Fully specified** | `ip route 192.168.20.0 255.255.255.0 g0/1 10.0.12.2` | Gives both interface and next hop. Avoids ambiguity and the recursive lookup. Mandatory with a link-local next hop in IPv6 |

## 8.4. Recursive lookup and a reachable next hop

With a next-hop route, the router performs two lookups:

```text
Destination 192.168.20.10
 → matches S 192.168.20.0/24 via 10.0.12.2
 → how do I reach 10.0.12.2?
 → matches C 10.0.12.0/30, GigabitEthernet0/1
 → exits G0/1 toward the MAC of 10.0.12.2
```

If the next hop doesn't belong to any network the router can reach, the route is **not installed** in the table (it shows in the configuration, but not in `show ip route`). So when a configured route "doesn't show up", the first question is:

> How does this router reach its next hop?

Typical mistake: entering the router's **own** address as the next hop, or an address on the far side that isn't on the shared link.

## 8.5. Plan before you type

A static route is the translation of a decision. Before configuring, fill in a matrix per router:

| Router | Remote network | Prefix | Next hop | Next hop on a connected network? |
|---|---|---|---|---|
| R1 | 192.168.20.0 | /24 | 10.0.12.2 | Yes (10.0.12.0/30, G0/1) |
| R1 | 192.168.30.0 | /24 | 10.0.12.2 | Yes |
| R2 | 192.168.10.0 | /24 | 10.0.12.1 | Yes (10.0.12.0/30, G0/1) |

How to fill it in:

1. list every network in the topology;
2. for each router, cross out the ones that are already `C`;
3. for each remaining network, decide which neighbor the traffic should go to;
4. the next hop is the **neighbor's** IP on the shared link.

## 8.6. Verification

```text
R1# show ip route static
S     192.168.20.0/24 [1/0] via 10.0.12.2
S     192.168.30.0/24 [1/0] via 10.0.12.2

R1# show ip route 192.168.30.10
Routing entry for 192.168.30.0/24
  Known via "static", distance 1, metric 0
  * 10.0.12.2
```

Check that the route appears with code `S`, that the prefix is correct (a `/16` instead of a `/24` changes which destinations it covers), that the next hop is the intended one, and that the connectivity test works **in both directions**.

## 8.7. Stub network

A *stub* network has only one way out. For example, a small branch connected to headquarters by a single link. On that router a route per remote network makes no sense: a single **default route** is enough (section 10).

# 9. Forward and return paths

## 9.1. Every conversation has two paths

A `ping` from PC-A to PC-B only works if:

- the *echo request* gets from PC-A to PC-B, **and**
- the *echo reply* gets back from PC-B to PC-A.

Each router decides independently using **its own** table. R1 knowing how to reach LAN-B says nothing about whether R2 knows how to get back to LAN-A.

## 9.2. The typical symptom

```text
R1: S 192.168.20.0/24 via 10.0.12.2      ← correct
R2: (no route to 192.168.10.0/24)        ← return path missing
```

Result:

- the request reaches PC-B;
- PC-B replies to 192.168.10.10 by sending the packet to its gateway, R2;
- R2 has no route to 192.168.10.0/24 and drops it;
- on PC-A, `ping` shows *Request timed out*.

If you only look at R1, "everything is fine". The fault is on another router and in the other direction.

## 9.3. How to follow the packet

```text
FORWARD                               RETURN
1. Source: local or remote dest.?     6. Destination replies to its gateway
2. Source's gateway                   7. Destination's router: route to source?
3. Route chosen at each router        8. Next router: route to source?
4. Next hop reachable                 9. ... until the source network
5. Reaches the destination
```

The forward and return paths don't have to use the same physical route, but **both must exist**.

## 9.4. Useful evidence

- `ping` from the router toward different points: if R1 reaches `10.0.12.2` but not `192.168.20.10`, the problem is beyond R1.
- `traceroute` from the source: shows which hop the replies stop at.
- `show ip route <source-network>` **on the destination's router**: directly checks whether the return path exists.

> A ping from a router uses its exit interface IP as the source. It can succeed even though a ping from a LAN PC fails, because the source networks differ. Extended `ping` lets you set the source (`ping 192.168.20.10 source g0/0`) and reproduce the real case.

# 10. Default route, host route, and floating static

## 10.1. Default route

```text
R1(config)# ip route 0.0.0.0 0.0.0.0 10.0.12.2
```

`0.0.0.0/0` matches **any** IPv4 address, but it is the **least specific** route possible. Under LPM it is only used when nothing more specific matches. Read it as: "for anything you don't know, send it here".

```text
Gateway of last resort is 10.0.12.2 to network 0.0.0.0
S*    0.0.0.0/0 [1/0] via 10.0.12.2
```

The asterisk (`*`) marks it as a candidate default; the *gateway of last resort* is its next hop.

Typical uses:

- *stub* branch routers;
- edge router toward the Internet service provider (U10);
- simplifying tables: specific routes for internal networks, default route for everything else.

**Common mistake:** thinking the default route "always wins". It loses to any longer prefix. Another mistake: using it to hide an incomplete design; the packet "goes somewhere", but that doesn't mean it arrives.

## 10.2. Host route

A route to a single host uses a `/32` prefix:

```text
R1(config)# ip route 192.168.30.10 255.255.255.255 10.0.21.2
```

It is the most specific IPv4 match possible. It's used to force a particular path to one server without affecting the rest of the network. Don't confuse it with `L` routes, which are also `/32` but represent the router's own addresses.

## 10.3. Floating static route

A **floating static** is a backup static route with a higher AD than the primary route **to the same prefix**:

```text
R1(config)# ip route 192.168.20.0 255.255.255.0 10.0.12.2         ! primary, AD 1
R1(config)# ip route 192.168.20.0 255.255.255.0 10.0.21.2 5       ! backup, AD 5
```

While the primary is available, only it is installed in the table; the backup "floats" above it in the configuration, unused. If the primary becomes invalid, the backup takes over.

```text
Normal state:            S 192.168.20.0/24 [1/0] via 10.0.12.2
G0/1 goes down/down:     S 192.168.20.0/24 [5/0] via 10.0.21.2
G0/1 recovers:           S 192.168.20.0/24 [1/0] via 10.0.12.2
```

Requirements for it to work:

- the **same prefix** on both routes (if the prefixes differ they don't compete: LPM applies);
- the backup's AD must be **higher** than the primary's (with statics: higher than 1; if the primary were OSPF, higher than 110);
- the backup's next hop must be reachable through another path.

## 10.4. An important limitation

A static route only disappears when the router detects locally that it can no longer use it: typically, when the interface used to reach the next hop goes down. If the failure is **further away** (the local link stays `up/up`, but the neighbor router has lost its connection to LAN-B), the primary route stays installed and traffic is lost. The backup never kicks in.

Detecting remote failures and reacting requires mechanisms that exchange information between routers: exactly what dynamic routing protocols provide (U09).

Another common mistake is **symmetry**: if R1 switches to the backup link but R2 keeps sending return traffic over the failed primary, the return path fails. The backup is configured **in both directions**.

# 11. IPv6 static routes

## 11.1. Same model

IPv6 changes the address format, not the logic: prefix, LPM, next hop, exit interface, and return path all work the same way.

| IPv4 | IPv6 |
|---|---|
| `ip route 192.168.20.0 255.255.255.0 10.0.12.2` | `ipv6 route 2001:db8:acad:20::/64 2001:db8:acad:12::2` |
| `ip route 0.0.0.0 0.0.0.0 10.0.12.2` | `ipv6 route ::/0 2001:db8:acad:12::2` |
| `/32` host route | `/128` host route |
| `show ip route` | `show ipv6 route` |

Remember to enable `ipv6 unicast-routing`.

## 11.2. Link-local next hop

Neighboring routers always communicate using their link-local addresses, and those stay stable even if the global prefix is renumbered. That's why they're commonly used as next hops:

```text
R1(config)# ipv6 route 2001:db8:acad:20::/64 GigabitEthernet0/1 fe80::2
```

The interface is **mandatory**. A link-local address is only valid within one link, and the same `fe80::2` may exist on several of the router's links. Without the interface, the router wouldn't know which link to look on.

```text
ipv6 route 2001:db8:acad:20::/64 fe80::2            ← rejected / ambiguous
ipv6 route 2001:db8:acad:20::/64 g0/1 fe80::2       ← correct
```

## 11.3. Verification

```text
R1# show ipv6 route
S   ::/0 [1/0]
     via 2001:DB8:ACAD:12::2
C   2001:DB8:ACAD:10::/64 [0/0]
     via GigabitEthernet0/0, directly connected
L   2001:DB8:ACAD:10::1/128 [0/0]
     via GigabitEthernet0/0, receive
S   2001:DB8:ACAD:20::/64 [1/0]
     via FE80::2, GigabitEthernet0/1
```

## 11.4. Dual stack

In a *dual-stack* network, IPv4 and IPv6 behave like two independent logical networks sharing the same cables: each has its own addresses, table, routes, and filters.

> `ping 192.168.20.10` succeeding proves nothing about `ping 2001:db8:acad:20::10`. Each family is verified separately.

# 12. Tracking down problems

## 12.1. Every command answers a question

| Question | Tool |
|---|---|
| Version, uptime, memory? | `show version` |
| Are interfaces up with the right IP? | `show ip interface brief`, `show interfaces` |
| Which networks does the router know? | `show ip route`, `show ipv6 route` |
| What will it do with this specific destination? | `show ip route <destination>` |
| What configuration is active? | `show running-config`, `show running-config \| section ...` |
| Is there an end-to-end reply? | `ping` (and extended `ping` with a source) |
| How far does the packet get? | `traceroute` (on Windows, `tracert`) |
| Do I know the next hop's MAC? | `show ip arp`, `show ipv6 neighbors` |
| What events has the device logged? | `show logging` |
| What is it processing right now? | `debug ...` (with care) |

## 12.2. Reading `ping` and `traceroute`

In Cisco IOS:

| Symbol | Meaning |
|---|---|
| `!` | Reply received |
| `.` | Timed out: no reply came back |
| `U` | Destination unreachable: some router reported it couldn't deliver it |

`U` is a valuable clue: **a router along the path** said it has no route or the packet was filtered. `.` only says nothing came back, without indicating where it was lost.

`traceroute` shows the hops that respond. A `* * *` from some point on means the packet, or its reply, is lost after the last router that answered. Interpret it with caution: a router may not respond by policy even though it forwards traffic, and paths can be asymmetric.

## 12.3. Use `debug` with care

```text
R1# terminal monitor
R1# debug ip icmp
ICMP: echo reply sent, src 192.168.10.1, dst 192.168.10.10
R1# undebug all
```

`debug` shows in real time what the router is processing. It is very informative in a lab, but on a busy production device it can use so much CPU that it affects service. Turn it on for a specific purpose, on the minimum traffic, and turn it off right away (`undebug all`). `terminal monitor` is needed to see the messages in an SSH session.

## 12.4. Method: evidence before change

```text
Symptom        → "PC-A can't ping PC-B"
Facts          → PC-A reaches its gateway; R1 reaches 10.0.12.2
Hypothesis     → R2 is missing the return route
Test           → show ip route 192.168.10.0 on R2
Evidence       → "% Network not in table"
Conclusion     → R2 doesn't know how to get back to LAN-A
Minimal change → ip route 192.168.10.0 255.255.255.0 10.0.12.1 on R2
Verification   → ping PC-A → PC-B succeeds; show ip route on R2 shows the S route
```

A useful order of checks (not a rigid recipe):

```text
interface → address/prefix → C routes → chosen route (LPM) → next hop reachable
→ ARP/ND → next router → destination → return path
```

A failed ping never justifies rewriting every route by itself. First locate **where** the path breaks.

# 13. The router as a DHCP server

## 13.1. Refresher from U04

You already know the DORA exchange (*Discover, Offer, Request, Acknowledge*), the pool concept, exclusions, and the parameters DHCP delivers: address, mask, gateway, DNS, and lease duration. Now you'll configure a Cisco router to act as the server.

## 13.2. Configuration

```text
R1(config)# ip dhcp excluded-address 192.168.10.1 192.168.10.20
R1(config)# ip dhcp pool LAN-A
R1(dhcp-config)# network 192.168.10.0 255.255.255.0
R1(dhcp-config)# default-router 192.168.10.1
R1(dhcp-config)# dns-server 192.168.30.53
R1(dhcp-config)# domain-name empresa.local
R1(dhcp-config)# lease 1
```

| Command | Purpose |
|---|---|
| `ip dhcp excluded-address` | Reserves addresses the server must **not** hand out: gateway, servers, printers with fixed IPs. Configured in global mode, outside the pool |
| `ip dhcp pool NAME` | Creates the pool and enters its configuration |
| `network` | Network whose addresses are assigned. The router uses the pool whose network matches the interface that received the request |
| `default-router` | Gateway the clients will receive. Must be the router's IP **on that LAN** |
| `dns-server` | DNS server |
| `domain-name` | Domain suffix |
| `lease` | Lease duration in days (default 1) |

Common mistakes:

- not excluding the gateway address, or excluding the wrong range → **address conflict**;
- `default-router` set to an IP on another network → the client gets an IP but can't leave its network;
- `network` with a mask different from the interface's → the pool doesn't match the LAN.

## 13.3. Verification

```text
R1# show ip dhcp binding
IP address       Client-ID/Hardware address   Lease expiration     Type
192.168.10.21    0100.50b6.1a2b.3c            Oct 06 2026 10:02 AM Automatic

R1# show ip dhcp pool
Pool LAN-A :
 Total addresses                : 254
 Leased addresses               : 1
 ...
R1# show ip dhcp conflict
```

On the client: `ipconfig /all` (Windows) shows the IP, gateway, DNS, and the DHCP server that replied.

# 14. DHCP relay

## 14.1. The problem

The *DHCP Discover* message is a **broadcast**: the client has no IP yet and doesn't know where the server is. Routers **do not forward broadcasts between networks**. If the DHCP server is on another network, the Discover dies at the router's interface.

Running a DHCP server on every LAN isn't practical. The solution is for the router to act as a **DHCP relay agent**.

## 14.2. Configuration

In the reference topology, the central DHCP server is `192.168.30.20` (SERVERS network, behind R2). For LAN-A clients to get addresses from it:

```text
R1(config)# interface GigabitEthernet0/0
R1(config-if)# ip helper-address 192.168.30.20
```

It goes on the interface that **receives the clients' broadcast** (*client-facing*), not on the interface facing the server.

## 14.3. What the relay does

```text
LAN-A client   ──Discover (broadcast)──►  R1 G0/0
R1             ──Discover (unicast)───►  192.168.30.20
                 giaddr = 192.168.10.1
Server         ──Offer (unicast)──────►  192.168.10.1 (R1)
R1             ──Offer────────────────►  Client
(same for Request and Acknowledge)
```

The relay writes the **giaddr** (*gateway IP address*) field into the message with the IP of the interface that received the request. The server uses that value for two things:

1. **choosing the pool** whose network contains `192.168.10.1` → the LAN-A pool;
2. **sending the reply** to that address.

That's why the server needs a pool for the remote network (with `default-router` = `192.168.10.1`) and a **return route** to `192.168.10.0/24`.

## 14.4. The relay does not replace routing

`ip helper-address` doesn't create any route. For the relay to work:

- R1 must have a route to `192.168.30.20`;
- the server (and intermediate routers) must know how to get back to the client's network;
- the server must have a pool matching the `giaddr`;
- no ACL may block DHCP (UDP 67/68).

> By default `ip helper-address` also forwards some other broadcast-based UDP services (TFTP, DNS, NetBIOS…). In this course we focus on DHCP.

## 14.5. Troubleshooting a client with no IP

| Question | Evidence |
|---|---|
| Is the client set to DHCP? | PC configuration; a `169.254.x.x` (APIPA) address if no reply was received |
| Is there a helper on the client-facing interface? | `show running-config interface g0/0` |
| Is the server IP correct? | Value of `ip helper-address` |
| Does the router reach the server? | `ping 192.168.30.20` |
| Is there a return route? | `show ip route 192.168.10.0` on R2 |
| Is there a pool for the client's network? | Server configuration |
| Does an ACL block UDP 67/68? | `show ip interface`, `show access-lists` |

Changing the helper when the problem is the return route fixes nothing, which is why you gather evidence before making changes.

# 15. Traffic policy and access control lists

## 15.1. From connectivity to policy

Once routing is complete, **everything can reach everything**. That is almost never what an organization wants:

- users should reach the internal website, but not manage its servers;
- only the IT team should open SSH sessions on the routers;
- guests should get to the Internet, but not see the internal network.

These statements are **policy requirements**. An **ACL** (*Access Control List*) is one of the tools that implement them on a router.

## 15.2. Policy before syntax

The first step is never typing commands, but translating the requirements into a **flow matrix**:

| # | Source | Destination | Protocol | Port / type | Action |
|---|---|---|---|---|---|
| 1 | LAN-A (users) | WEB 192.168.30.10 | TCP | 443 (HTTPS) | permit |
| 2 | LAN-A (users) | WEB 192.168.30.10 | TCP | 22 (SSH) | deny |
| 3 | PC-ADMIN 192.168.10.5 | WEB 192.168.30.10 | TCP | 22 (SSH) | permit |
| 4 | LAN-A | any destination | ICMP | echo | permit (troubleshooting) |

A matrix forces you to pin down what a vague requirement leaves out. "Allow the web" doesn't say: from which network?, to which server?, HTTP, HTTPS, or both?, in which direction is the connection started?

## 15.3. Structure of an ACL

An ACL is an ordered list of **ACEs** (*Access Control Entries*). Each ACE has:

- a **condition** (which packets match: source, destination, protocol, ports…);
- an **action**: `permit` or `deny`.

```text
ip access-list extended USERS-TO-SERVERS
 10 permit tcp host 192.168.10.5 host 192.168.30.10 eq 22
 20 deny   tcp 192.168.10.0 0.0.0.255 host 192.168.30.10 eq 22
 30 permit tcp 192.168.10.0 0.0.0.255 host 192.168.30.10 eq 443
 40 permit icmp 192.168.10.0 0.0.0.255 any echo
```

## 15.4. How it is evaluated: first match

The router compares the packet against the ACEs **top to bottom**:

```text
Matches ACE 10?  no  → next
Matches ACE 20?  yes → apply its action and STOP
```

It doesn't keep looking for a "better" rule. The first matching ACE decides.

Consequence: **order is part of the policy**. In the example, if ACE 20 (deny SSH to all of LAN-A) came before 10, PC-ADMIN, which is also on LAN-A, would be blocked.

## 15.5. Implicit deny

Every ACL ends with an invisible rule:

```text
deny any  (IPv4: deny ip any any)
```

If a packet matches no ACE, it is dropped. Consequences:

- an ACL containing only `deny` statements blocks **everything** (what is explicitly denied and everything else);
- any useful ACL must contain at least one `permit`;
- you must account for all legitimate traffic, including traffic the requirement doesn't mention but that is needed (DNS, DHCP, replies…).

Many administrators add an explicit `deny ip any any` at the end: the effect is the same, but it gives you a **counter** for what is being dropped.

## 15.6. Creating is not applying

An ACL defined in the configuration **filters nothing** until it is applied at a specific point:

```text
R1(config)# interface GigabitEthernet0/0
R1(config-if)# ip access-group USERS-TO-SERVERS in
```

Application rules in Cisco IOS:

- **one ACL per interface, per direction, per protocol** (one inbound IPv4, one outbound IPv4, one inbound IPv6, one outbound IPv6);
- applying a second IPv4 ACL in the same direction **replaces** the first;
- applying an ACL that doesn't exist blocks nothing (it behaves as if there were no filter), but it starts acting as soon as it is created.

## 15.7. Inbound (*in*) and outbound (*out*)

Direction is defined **from the router interface's point of view**:

| Direction | Which packets it evaluates |
|---|---|
| `in` | Packets **arriving** at the router on that interface, before the routing table lookup |
| `out` | Packets **about to leave** through that interface, after the routing decision |

```text
packet arrives on G0/0
  → inbound ACL on G0/0     (if deny: dropped, no table lookup)
  → routing table (LPM)     → exit interface G0/1
  → outbound ACL on G0/1
  → leaves toward the next hop
```

`in` and `out` do **not** mean "into/out of the company". To decide, follow the packet and see which interface it enters and which it leaves.

An `out` ACL does not filter traffic **generated by the router itself** (for example, a `ping` launched from its CLI). If you test an outbound ACL by pinging from the router, the result proves nothing.

## 15.8. IPv4 ACL types

| Type | Criteria | Classic numbering | Suggested placement |
|---|---|---|---|
| **Standard** | Source IP only | 1–99, 1300–1999 | Close to the **destination** |
| **Extended** | Protocol, source, destination, ports, and other fields | 100–199, 2000–2699 | Close to the **source** |

They can be **numbered** or **named**. Named ACLs are recommended: the name states the intent (`ADMIN-SOURCES`, `OUTSIDE-IN`), they are more readable, and they are easy to edit by sequence number.

## 15.9. Filtering isn't the only thing an ACL does

In these notes an ACL applied to an interface **filters**: `deny` means the packet doesn't get through. ACLs are also used to **select** traffic for other features. In U10 you'll see that NAT uses an ACL to choose which addresses get translated; there, a `deny` means "don't translate", not "drop". The meaning of `permit`/`deny` depends on the context in which the ACL is used.

# 16. Wildcard masks

## 16.1. What it is

Cisco IPv4 ACLs don't use a subnet mask but a **wildcard mask**. Each bit says whether that bit of the address is compared:

| Wildcard bit | Meaning |
|---|---|
| `0` | This bit **must match** |
| `1` | This bit **doesn't matter** |

It is the inverse logic of a subnet mask, and they shouldn't be mixed up: a wildcard is not "another way" of writing a mask.

## 16.2. Calculating it for a network

For a network defined by a prefix:

```text
wildcard = 255.255.255.255 − mask
```

| Prefix | Mask | Wildcard | Example in an ACE |
|---|---|---|---|
| /24 | 255.255.255.0 | 0.0.0.255 | `192.168.10.0 0.0.0.255` |
| /26 | 255.255.255.192 | 0.0.0.63 | `192.168.10.64 0.0.0.63` → .64–.127 |
| /28 | 255.255.255.240 | 0.0.0.15 | `192.168.10.16 0.0.0.15` → .16–.31 |
| /30 | 255.255.255.252 | 0.0.0.3 | `10.0.12.0 0.0.0.3` |
| /16 | 255.255.0.0 | 0.0.255.255 | `172.16.0.0 0.0.255.255` |

The address that goes with the wildcard should be the **network address**. `192.168.10.70 0.0.0.63` works (IOS corrects it to .64), but it reveals shaky reasoning and may not be what was intended.

## 16.3. Shortcuts

| Keyword | Equivalent to | Meaning |
|---|---|---|
| `host 192.168.10.5` | `192.168.10.5 0.0.0.0` | That address only |
| `any` | `0.0.0.0 255.255.255.255` | Any address |

## 16.4. Common mistake

Writing the mask where the wildcard goes:

```text
permit 192.168.10.0 255.255.255.0     ← WRONG
```

That ACE ignores the first three octets and requires the last one to be `0`: it matches `x.x.x.0` on any network, not LAN-A.

# 17. Standard ACLs and controlling management access

## 17.1. Configuration

```text
R2(config)# ip access-list standard BLOCK-LAN-A
R2(config-std-nacl)# 10 deny 192.168.10.0 0.0.0.255
R2(config-std-nacl)# 20 permit any
R2(config)# interface GigabitEthernet0/2
R2(config-if)# ip access-group BLOCK-LAN-A out
```

Requirement implemented: "LAN-A cannot reach the SERVERS network; all other networks can."

## 17.2. Why close to the destination

A standard ACL only sees the **source**. If it were applied on R1 G0/0 `in`, LAN-A would be blocked from **everywhere** (LAN-B, the Internet…), not just from SERVERS. Placing it on the interface facing SERVERS (R2 G0/2 `out`) filters only the traffic headed to that network.

```text
Standard ACL far from the destination → blocks more than intended
Standard ACL close to the destination → affects only the protected destination
```

It is a guideline, not a law: justify it by following the traffic's path in the actual topology.

## 17.3. Standard ACL on the VTY lines

A very useful application is limiting **where** the router can be managed from:

```text
R1(config)# ip access-list standard ADMIN-SOURCES
R1(config-std-nacl)# permit host 192.168.10.5
R1(config-std-nacl)# permit 192.168.99.0 0.0.0.255
R1(config)# line vty 0 4
R1(config-line)# access-class ADMIN-SOURCES in
```

Now an SSH session is only accepted if it comes from PC-ADMIN or the management network; any other source is rejected by the implicit deny, even if it knows the username and password.

| Command | Where it's applied | What it controls |
|---|---|---|
| `ip access-group NAME in/out` | Interface | Traffic passing through or arriving on that interface |
| `access-class NAME in` | VTY lines | Who can open a remote (SSH) session **to the router itself** |

Remember to apply the ACL to **all** the device's VTY lines (for example, `vty 0 4` and `vty 5 15`); otherwise some lines stay open.

Professional caution: when applying `access-class` remotely, if your own IP isn't permitted, **you cut off your own session** and lock yourself out. Before applying it, check which IP you're connected from and have console access ready.

# 18. Extended ACLs

## 18.1. What they can check

An extended ACL can combine:

- **protocol**: `ip`, `tcp`, `udp`, `icmp`…;
- **source** and **destination** (with wildcard, `host`, or `any`);
- TCP/UDP source or destination **ports**;
- ICMP message types;
- other options (for example, `established`).

General syntax:

```text
{permit|deny} PROTOCOL  SOURCE WILDCARD [port]  DEST WILDCARD [port]  [options]
```

## 18.2. Refresher from U02: IPs identify hosts, ports identify services

| Service | Protocol | Port |
|---|---|---:|
| HTTP | TCP | 80 (`www`) |
| HTTPS | TCP | 443 |
| SSH | TCP | 22 |
| Telnet | TCP | 23 |
| DNS | UDP (and TCP) | 53 |
| DHCP | UDP | 67 server / 68 client |
| TFTP | UDP | 69 |

A port only makes sense with TCP or UDP. So:

```text
permit ip  192.168.10.0 0.0.0.255 host 192.168.30.10 eq 443   ← not valid
permit tcp 192.168.10.0 0.0.0.255 host 192.168.30.10 eq 443   ← correct
```

The service port is normally the request's **destination port**. The client uses an ephemeral (random, high) source port, so the request is almost never filtered by source port.

Operators: `eq` (equal), `neq`, `lt`, `gt`, `range 20 21`.

## 18.3. Full example

The policy from the matrix in section 15.2, applied on R1:

```text
R1(config)# ip access-list extended LAN-A-IN
R1(config-ext-nacl)# 10 permit tcp host 192.168.10.5 host 192.168.30.10 eq 22
R1(config-ext-nacl)# 20 deny   tcp 192.168.10.0 0.0.0.255 host 192.168.30.10 eq 22
R1(config-ext-nacl)# 30 permit tcp 192.168.10.0 0.0.0.255 host 192.168.30.10 eq 443
R1(config-ext-nacl)# 40 permit icmp 192.168.10.0 0.0.0.255 any echo
R1(config-ext-nacl)# 50 permit udp any any eq bootps
R1(config-ext-nacl)# 60 deny   ip any any
R1(config)# interface GigabitEthernet0/0
R1(config-if)# ip access-group LAN-A-IN in
```

Note ACE 50: without it, the final deny would block DHCP Discovers from LAN-A clients. A typical ACL failure is breaking a service nobody mentioned in the requirement.

## 18.4. Why close to the source

Because an extended ACL distinguishes destination and service, it can be placed close to the source without blocking other legitimate destinations. Unwanted traffic is then dropped before it crosses the network and uses up links. In the example, `LAN-A-IN` on R1 G0/0 `in` stops unauthorized SSH before it crosses the R1–R2 link.

## 18.5. Return traffic

The Cisco ACLs you're studying are **stateless**: they evaluate each packet in isolation, without remembering that it belongs to a permitted connection. If an ACL is applied in the direction **replies come back**, they must be explicitly permitted.

For TCP there is the `established` option:

```text
permit tcp any 192.168.10.0 0.0.0.255 established
```

It matches TCP segments with the **ACK** or **RST** bit set, that is, segments belonging to a connection already under way. A segment trying to **open** a connection (SYN only) doesn't match. This permits replies to connections started from inside without permitting new connections from outside.

Limitations: `established` only works for TCP (not for UDP such as DNS), and it doesn't actually check that the connection exists: an attacker can craft packets with ACK set. **Stateful firewalls** keep a connection table and solve this problem; they are the professional tool for the perimeter and fall outside this course.

## 18.6. ICMP

ICMP carries the network's diagnostic and error messages. Blocking it entirely makes troubleshooting harder and can break network functions. The policy should decide which types to permit, for example:

```text
permit icmp any 192.168.10.0 0.0.0.255 echo-reply
permit icmp any 192.168.10.0 0.0.0.255 unreachable
permit icmp any 192.168.10.0 0.0.0.255 time-exceeded
```

# 19. ACL order, editing, and verification

## 19.1. Shadowed rules

```text
10 deny   ip any any
20 permit tcp 192.168.10.0 0.0.0.255 host 192.168.30.10 eq 443
```

ACE 20 is never evaluated: everything matches 10 first. A general ACE placed before a more specific one that falls within it cancels it out. Common pattern: **specific first, general after**.

## 19.2. Editing with sequence numbers

In a named ACL each ACE has a number (10, 20, 30… by default). You can insert or remove an entry without rewriting the list:

```text
R1(config)# ip access-list extended LAN-A-IN
R1(config-ext-nacl)# 15 permit tcp host 192.168.10.6 host 192.168.30.10 eq 22
R1(config-ext-nacl)# no 40
```

Deleting the whole ACL and retyping it while it is applied leaves the interface with no filter, or a partial one, during the process. Editing by sequence number is safer.

## 19.3. Counters

```text
R1# show access-lists LAN-A-IN
Extended IP access list LAN-A-IN
    10 permit tcp host 192.168.10.5 host 192.168.30.10 eq 22 (12 matches)
    20 deny tcp 192.168.10.0 0.0.0.255 host 192.168.30.10 eq 22 (4 matches)
    30 permit tcp 192.168.10.0 0.0.0.255 host 192.168.30.10 eq 443 (187 matches)
    40 permit icmp 192.168.10.0 0.0.0.255 any echo (8 matches)
    50 permit udp any any eq bootps (3 matches)
    60 deny ip any any (0 matches)
```

Counters are evidence of **which ACE is making the decision**. For a specific test: `clear access-list counters`, generate the traffic, then check which counter went up.

A zero counter does **not** prove the ACE is wrong. It may mean that:

- that traffic wasn't generated;
- an earlier ACE matches first;
- the ACL isn't applied, or is applied on another interface or direction;
- the traffic takes another path and never crosses that interface.

## 19.4. Checking where it's applied

```text
R1# show ip interface GigabitEthernet0/0
GigabitEthernet0/0 is up, line protocol is up
  Internet address is 192.168.10.1/24
  ...
  Outgoing access list is not set
  Inbound  access list is LAN-A-IN
```

## 19.5. Positive and negative verification

An ACL implements what **is permitted** and what **is denied**. You must prove both:

| Test | Expected result | What it proves |
|---|---|---|
| LAN-A PC → `https://192.168.30.10` | Works | The ACL didn't break the legitimate service |
| LAN-A PC → `ssh 192.168.30.10` | Fails | The block works |
| PC-ADMIN → `ssh 192.168.30.10` | Works | The exception is correctly ordered |
| Counters 10, 20, 30 | Increase with each test | Each result is produced by the intended ACE |

Checking only that something fails isn't enough: an ACL that blocks everything also "passes" the negative test.

## 19.6. Safe changes

Before: back up the configuration, list the legitimate traffic, prepare a rollback plan and, if working remotely, have console access available.

After: positive test, negative test, counters, and change documentation.

# 20. DMZ: publishing services without exposing the internal network

## 20.1. The problem

An organization wants its web server reachable from the Internet. If that server sits on the internal network and an attacker compromises it, they get direct access to users' machines.

The classic solution is a **DMZ** (*demilitarized zone*): an intermediate network, separate from the internal network, where servers that must accept connections from outside are placed.

## 20.2. Three-zone model

```text
                 OUTSIDE (Internet / ISP)
                 203.0.113.0/30
                        │ G0/2 .1
                   ┌────┴────┐
   INSIDE          │  R-EDGE │          DMZ
192.168.10.0/24 ───┤G0/0  G0/1├─── 172.16.50.0/24
   (users)     .1  └─────────┘  .1    WEB 172.16.50.10
   ADMIN .5
```

| Zone | Trust level | Contains |
|---|---|---|
| INSIDE | High | Users and internal services |
| DMZ | Medium | Servers reachable from outside |
| OUTSIDE | Low | Internet, uncontrolled networks |

The principle: **each zone may only start the connections the policy requires**, and a compromised server in the DMZ must not be able to start connections into INSIDE.

## 20.3. Policy matrix

| # | Source | Destination | Service | Action |
|---|---|---|---|---|
| 1 | OUTSIDE | WEB (DMZ) | TCP 80, 443 | permit |
| 2 | OUTSIDE | INSIDE | new connections | deny |
| 3 | INSIDE | WEB (DMZ) | TCP 443 | permit |
| 4 | ADMIN (INSIDE) | WEB (DMZ) | TCP 22 | permit |
| 5 | DMZ | INSIDE | new connections | deny |
| 6 | INSIDE | OUTSIDE | any | permit |
| 7 | DMZ | OUTSIDE | new connections | deny (replies only) |

## 20.4. Implementation with extended ACLs

An **inbound** ACL on each router interface controls what each zone can start.

```text
ip access-list extended INSIDE-IN
 10 permit tcp 192.168.10.0 0.0.0.255 host 172.16.50.10 eq 443
 20 permit tcp host 192.168.10.5 host 172.16.50.10 eq 22
 30 deny   ip 192.168.10.0 0.0.0.255 172.16.50.0 0.0.0.255
 40 permit ip 192.168.10.0 0.0.0.255 any
!
ip access-list extended DMZ-IN
 10 permit tcp host 172.16.50.10 eq 443 any established
 20 permit tcp host 172.16.50.10 eq www any established
 30 permit tcp host 172.16.50.10 eq 22 host 192.168.10.5 established
 40 deny   ip any any
!
ip access-list extended OUTSIDE-IN
 10 permit tcp any host 172.16.50.10 eq www
 20 permit tcp any host 172.16.50.10 eq 443
 30 permit tcp any 192.168.10.0 0.0.0.255 established
 40 permit icmp any 192.168.10.0 0.0.0.255 echo-reply
 50 permit icmp any 192.168.10.0 0.0.0.255 unreachable
 60 deny   ip any any
!
interface GigabitEthernet0/0
 ip access-group INSIDE-IN in
interface GigabitEthernet0/1
 ip access-group DMZ-IN in
interface GigabitEthernet0/2
 ip access-group OUTSIDE-IN in
```

How each requirement maps to the ACEs:

- **Req. 1:** `OUTSIDE-IN` 10 and 20. The server's replies leave thanks to `DMZ-IN` 10 and 20 (`established`).
- **Req. 2:** `OUTSIDE-IN` 30 only admits TCP replies toward INSIDE; a new SYN from outside falls into deny 60.
- **Req. 3 and 4:** `INSIDE-IN` 10 and 20; replies come back through `DMZ-IN` 10 and 30.
- **Req. 5 and 7:** the DMZ can only send TCP replies from its services; any connection the server tries to start hits `DMZ-IN` 40.
- **Req. 6:** `INSIDE-IN` 40; its replies come in through `OUTSIDE-IN` 30, 40, and 50.
- `INSIDE-IN` 30 comes **before** 40: otherwise 40 would allow INSIDE any service in the DMZ.
- `INSIDE-IN` 40 only accepts sources from the internal network: a packet with a spoofed source IP entering on G0/0 is dropped.

## 20.5. Verifying the policy

| Test | Expected |
|---|---|
| External client → `http://172.16.50.10` | Works |
| External client → `ssh 172.16.50.10` | Fails |
| External client → ping an INSIDE PC | Fails |
| INSIDE PC → `https://172.16.50.10` | Works |
| PC-ADMIN → `ssh 172.16.50.10` | Works |
| Another INSIDE PC → `ssh 172.16.50.10` | Fails |
| From WEB → ping or connect to an INSIDE PC | Fails |
| INSIDE PC → external server over HTTPS | Works |

And in each case, which counter goes up.

## 20.6. Limits of this scenario

- **No NAT.** In this lab the provider's router has routes to INSIDE and the DMZ. In reality, private networks aren't routed on the Internet: publishing is done with NAT, which you'll study in U10.
- **UDP return traffic.** With stateless ACLs, DNS replies (UDP 53) from external servers to INSIDE would need an extra rule that opens more than desirable. It's one of the reasons the real perimeter is protected with stateful firewalls.
- **Layered protection.** Many architectures use two firewalls or a dedicated zone-based firewall. The three-zone model and the policy matrix stay the same.

# 21. Integrated troubleshooting: follow the packet

## 21.1. The full path

A single symptom ("the client can't reach the server") can have causes in different domains. The model that puts them in order is the packet's real path:

```text
host: IP, mask, gateway (correct DHCP?)
 → router's inbound interface (state, IP)
 → inbound ACL on that interface
 → routing table: route chosen by LPM
 → next hop reachable (ARP/ND)
 → outbound ACL on the exit interface
 → following routers (repeat)
 → service on the destination
 → RETURN: repeat everything in the opposite direction
```

## 21.2. Typical cases

| Symptom | Key evidence | Likely cause |
|---|---|---|
| Ping fails; `traceroute` stops at R1 | R1 has no `S` route to the destination | Missing forward route |
| Request arrives (counters/debug at destination) but no reply | `show ip route <source>` on the remote router: no route | Missing return route |
| Route configured but not in the table | Next hop outside the connected networks | Wrong next hop or interface down |
| Ping works, HTTPS doesn't | Counter on a `deny tcp ... eq 443` increases | Extended ACL blocks the service |
| HTTPS fails, ACL counters at 0 | `show ip interface`: ACL on another interface or direction | Wrong placement or direction |
| Client with a 169.254.x.x IP | Helper missing, on another interface, or no route to the server | Relay failure or routing to the DHCP server |
| Backup doesn't take over when the remote path fails | Primary route still installed | Floating static limitation |
| IPv4 works, IPv6 doesn't | `show ipv6 route` missing the route, or no `ipv6 unicast-routing` | IPv6 stack not configured equivalently |

## 21.3. Principles

- A correct route doesn't rule out an ACL, and a correct ACL doesn't rule out a routing fault: `ACL permit + no route = no connectivity`.
- Don't modify an ACL before proving the packet reaches the point where it is applied.
- One change at a time, verifying afterward.
- An answer from an AI tool or a classmate is a hypothesis; evidence comes from device outputs and tests.

# 22. Optional deep dive

## 22.1. IPv6 ACLs

The reasoning is the same, with syntax differences:

```text
R1(config)# ipv6 access-list LAN-A-V6-IN
R1(config-ipv6-acl)# permit tcp 2001:db8:acad:10::/64 host 2001:db8:acad:30::10 eq 443
R1(config-ipv6-acl)# deny ipv6 any any
R1(config)# interface GigabitEthernet0/0
R1(config-if)# ipv6 traffic-filter LAN-A-V6-IN in
```

- There is no standard/extended distinction: all are named and can filter like an extended ACL.
- They use prefixes (`/64`), not wildcards.
- They are applied with `ipv6 traffic-filter`, not `ip access-group`.
- Before the final implicit deny there are implicit permits for *Neighbor Discovery* (NS/NA), which IPv6 needs to work. If you write your own `deny ipv6 any any` at the end, those implicit permits are never reached: you must permit ND explicitly.
- ICMPv6 is essential (ND, RA, *Packet Too Big*): don't block it wholesale.

## 22.2. Other tools

- `ip access-list resequence NAME 10 10`: renumbers an ACL to leave gaps for insertions.
- `login block-for 120 attempts 3 within 60`: temporarily blocks access after several failed attempts.
- Programmatic management (NETCONF/RESTCONF) and automation tools: modern professional practice tends to configure many devices at once from templates, but the concepts in this unit don't change.

# Unit summary

1. A router joins different networks: it keeps the source and destination IPs and rebuilds the frame at each hop.
2. It boots with POST → bootstrap → IOS (flash) → startup-config (NVRAM) and works from the running-config in RAM. Whatever isn't saved is lost.
3. Remote management uses SSH v2 with local users; Telnet exposes credentials.
4. An `up/up` interface with an IP generates `C` and `L` routes. Remote networks need routes.
5. The router first picks the most specific route (LPM); AD only breaks ties between sources for the same prefix.
6. A static route needs a reachable next hop, and every conversation needs a forward **and** a return path.
7. The default route is the least specific; a floating static is a backup with a higher AD that doesn't detect remote failures.
8. IPv6 applies the same model; a link-local next hop requires specifying the interface.
9. A router can be a DHCP server and, with `ip helper-address` on the client-facing interface, a relay to a remote server.
10. An ACL translates a policy: first match, implicit deny, one ACL per interface, direction, and protocol.
11. Standard: source only, close to the destination. Extended: protocol, source, destination, and ports, close to the source.
12. A policy is proven with positive **and** negative tests and with counters.
13. A DMZ separates public services from the internal network; with stateless ACLs, `established` permits TCP replies without opening new connections.

> **Routing decides where the packet can go; the ACL decides whether it may pass. Neither is verified without following the packet there and back.**

# Appendix B. Glossary

| ACE (*Access Control Entry*) | Each rule in an ACL: condition + action |

| Administrative distance (AD) | Preference of a route's source; lower is better |
| Bootstrap | ROM program that starts loading IOS |
| Connected route (C) | Network of a working interface with an IP |
