> **Pregunta guía:** ¿cómo se administra un router de forma segura, cómo decide por dónde enviar cada paquete y cómo se consigue que solo pase el tráfico que la organización quiere permitir?

## Introducción

Hasta ahora has trabajado con redes que un único dispositivo de capa 3 conectaba: el default gateway de una LAN o el router de un escenario inter-VLAN. En esta unidad el router pasa a ser el protagonista. Vas a aprender a:

- conocer cómo está construido un router, cómo arranca y dónde guarda su configuración;
- administrarlo de forma segura, en local y en remoto;
- poner en servicio sus interfaces;
- leer su tabla de routing y entender qué ruta elige para cada destino;
- construir rutas estáticas IPv4 e IPv6 que funcionen **en los dos sentidos**;
- utilizarlo como servidor DHCP y como relay DHCP;
- traducir una política de seguridad en listas de control de acceso (ACL);
- proteger una zona de servidores públicos (DMZ);
- diagnosticar fallos siguiendo el recorrido real del paquete.

La unidad se apoya en dos decisiones que el router toma para cada paquete:

| Decisión | Pregunta | Mecanismo |
|---|---|---|
| **Encaminamiento** (*routing*) | ¿Por dónde puede ir este paquete? | Tabla de routing |
| **Filtrado** (*filtering*) | ¿Debe permitirse que pase por aquí? | ACL |

Ambas decisiones se estudian por separado, pero en la red real ocurren sobre el mismo paquete y deben comprobarse juntas.

### Topología de referencia

Muchos ejemplos de estos apuntes utilizan la misma red. Tenla a mano.

```text
        LAN-A                  Enlace R1–R2                   LAN-B
   192.168.10.0/24            10.0.12.0/30               192.168.20.0/24

  PC-A .10 ──[G0/0 .1] R1 [G0/1 .1]──────[G0/1 .2] R2 [G0/0 .1]── PC-B .10
                        [G0/2 .1]                 [G0/2 .1]
                           │                          │
                    Enlace de respaldo          SERVERS 192.168.30.0/24
                      10.0.21.0/30              WEB .10   DHCP .20
                           │
                        R2 [G0/3 .2]
```

| Red | Prefijo | Gateway / extremos |
|---|---|---|
| LAN-A | 192.168.10.0/24 | R1 G0/0 = 192.168.10.1 |
| LAN-B | 192.168.20.0/24 | R2 G0/0 = 192.168.20.1 |
| SERVERS | 192.168.30.0/24 | R2 G0/2 = 192.168.30.1 · WEB .10 · DHCP/TFTP .20 · DNS .53 |
| Enlace principal | 10.0.12.0/30 | R1 G0/1 = .1 · R2 G0/1 = .2 |
| Enlace de respaldo | 10.0.21.0/30 | R1 G0/2 = .1 · R2 G0/3 = .2 |

Para IPv6 se usan los prefijos `2001:db8:acad:10::/64` (LAN-A), `2001:db8:acad:20::/64` (LAN-B), `2001:db8:acad:12::/64` (enlace R1–R2) y `2001:db8:acad:30::/64` (SERVERS).

> Los nombres de interfaz (`G0/0`, `G0/1`…) dependen del modelo. En Packet Tracer y en equipos reales verás variantes como `GigabitEthernet0/0/0`. Lo importante es identificar **qué red hay detrás de cada interfaz**.

# 1. Qué hace un router

Antes de configurar nada conviene tener claro qué trabajo hace un router y en qué se diferencia de un switch. Este apartado une lo que ya sabes del host (U04) con lo que ocurre dentro del router: por qué le llega el tráfico, qué decide con cada paquete y qué cambia en él en cada salto.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Puerta de enlace predeterminada** (*default gateway*) | ¿A quién entrega el host el tráfico remoto? | PC-A → R1 G0/0 (192.168.10.1) |
| **Router frente a switch** (*router vs. switch*) | ¿Qué equipo une redes distintas y cuál une equipos de una misma red? | R1 une LAN-A con el enlace R1–R2 |
| **Salto** (*hop*) | ¿Qué hace el router con cada paquete que reenvía? | Resta 1 al TTL, consulta la tabla y construye una trama nueva |
| **Dirección IP frente a MAC** (*IP vs. MAC address*) | ¿Qué direcciones se mantienen y cuáles cambian por el camino? | Las IP se mantienen; las MAC cambian en cada enlace |

No debemos confundir el destino final del paquete (IP de destino) con el destinatario de la trama en cada enlace (MAC de destino).

## 1.1. De la decisión del host a la decisión del router

En U04 viste que un host decide primero si el destino es local o remoto:

- si el destino pertenece a su red, lo entrega directamente (ARP/ND para averiguar la MAC del destino);
- si el destino es remoto, envía el paquete a su **default gateway**.

Esto significa que el router recibe tráfico remoto **porque el host se lo envía**. El router no «captura» el tráfico: es el siguiente paso previsto por el propio host.

Un detalle que conviene tener muy claro, porque aparecerá en el diagnóstico:

| Cabecera | Campo destino cuando PC-A envía a PC-B |
|---|---|
| Capa 3 (IP) | 192.168.20.10 → **PC-B** (el destino final) |
| Capa 2 (Ethernet en LAN-A) | MAC de **R1 G0/0** (el gateway) |

La IP de destino indica a quién va dirigido el paquete. La MAC de destino indica a quién se entrega la trama **en ese enlace**.

## 1.2. Router frente a switch

| | Switch (capa 2) | Router (capa 3) |
|---|---|---|
| Une | dispositivos de una misma red / VLAN | redes distintas |
| Decide con | dirección MAC de destino | dirección IP de destino |
| Tabla | tabla MAC | tabla de routing |
| Broadcast | lo reenvía dentro de la VLAN | no lo reenvía entre redes |
| Trama | la reenvía sin reescribir las direcciones | construye una trama nueva en cada salto |

Cada interfaz de un router pertenece a una red distinta. Por eso un router separa dominios de broadcast, igual que viste con las VLAN en U07.

## 1.3. Lo que ocurre en cada salto

Cuando R1 recibe un paquete destinado a PC-B:

1. comprueba que la trama va dirigida a su MAC y extrae el paquete IP;
2. reduce en 1 el **TTL** (en IPv6, *Hop Limit*); si llega a 0, descarta el paquete y avisa al origen con ICMP;
3. consulta la tabla de routing con la IP de destino;
4. elige la ruta y determina **next hop** e **interfaz de salida**;
5. obtiene la MAC del next hop (ARP en IPv4, ND en IPv6);
6. construye una trama nueva y la envía.

```text
               IP origen       IP destino      MAC origen    MAC destino
LAN-A      :   192.168.10.10   192.168.20.10   PC-A          R1 G0/0
Enlace R1-R2:  192.168.10.10   192.168.20.10   R1 G0/1       R2 G0/1
LAN-B      :   192.168.10.10   192.168.20.10   R2 G0/0       PC-B
```

Las direcciones IP no cambian a lo largo del camino (salvo que intervenga NAT, que estudiarás en U10). Las direcciones MAC cambian en cada enlace.

# 2. Hardware, LED y métodos de acceso

Un router es un equipo físico antes que una configuración. Este apartado responde a tres preguntas prácticas: qué tiene la caja, qué nos dicen sus luces y por qué vía podemos entrar a configurarlo. Es la base de la puesta en servicio (apartado 4) y de la administración segura (apartado 5).

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Componentes físicos** (*physical components*) | ¿Qué tiene el equipo y dónde se conecta cada cosa? | Puertos Ethernet/SFP, ranuras de expansión, puerto de consola |
| **LED** (*LEDs*) | ¿Qué evidencia física da el equipo sin abrir la CLI? | SYS en verde fijo; LED de enlace encendido en G0/0 |
| **Métodos de acceso** (*access methods*) | ¿Por qué vía entro a configurarlo? | Consola, SSH, web, API |
| **Líneas VTY** (*virtual terminal lines*) | ¿Por dónde entran las sesiones remotas? | `line vty 0 4` |

Un LED encendido es evidencia física, no prueba de que la red funcione; y cualquier acceso *in-band* (SSH, web) depende de que la propia red esté operativa.

## 2.1. Componentes físicos

Un router empresarial es un ordenador especializado. Contiene CPU, memorias, un sistema operativo (en Cisco, **IOS** o IOS XE) e interfaces de red. Suele incluir:

- **puertos Ethernet** integrados (cobre y/o SFP para fibra);
- **ranuras de expansión** para módulos (más puertos, interfaces WAN, módulos de voz);
- **puerto de consola** (RJ-45 o USB) para administración local;
- en modelos antiguos, puerto **AUX** para acceso por módem;
- puerto USB para almacenamiento o consola.

## 2.2. Los LED como primera evidencia

En U03 aprendiste que un LED es evidencia, pero no diagnóstico completo. En un router suelen encontrarse:

| LED | Qué suele indicar |
|---|---|
| SYS / PWR | El equipo tiene alimentación y el sistema ha arrancado correctamente (verde fijo) o está arrancando/con fallo (parpadeo, ámbar) |
| ACT | Actividad del sistema o de las interfaces |
| Link / Speed por puerto | Enlace físico establecido y, a veces, velocidad |
| Módulo | Estado de cada módulo instalado |

El significado exacto de colores y parpadeos **depende del fabricante y del modelo**: se consulta en la documentación técnica. En Packet Tracer, los puntos de color de cada extremo del enlace (verde, ámbar, rojo) cumplen la misma función.

Un LED de enlace encendido demuestra que hay señal física. **No demuestra** que la interfaz tenga dirección IP, que esté activa en la configuración ni que exista una ruta hacia el destino.

## 2.3. Métodos de acceso a la configuración

| Método | Tipo | Requisitos | Uso |
|---|---|---|---|
| **Consola** | Local, *out-of-band* | Cable de consola y un emulador de terminal | Primera configuración, recuperación, pérdida de acceso por red |
| **AUX** | Remoto por módem (histórico) | Módem | Prácticamente en desuso |
| **Telnet** (TCP 23) | Remoto, *in-band* | IP operativa y líneas VTY | **No recomendado**: todo viaja en texto claro |
| **SSH** (TCP 22) | Remoto, *in-band*, cifrado | IP, nombre de dominio, claves RSA, usuario local | Método estándar de administración remota |
| **Web (HTTP/HTTPS)** | Remoto, interfaz gráfica | Servidor web del equipo activado | Equipos pequeños o asistentes de configuración |
| **API (NETCONF, RESTCONF)** | Remoto, programático | Plataformas modernas (IOS XE) | Automatización; solo reconocimiento en este módulo |

*In-band* significa que la administración viaja por la misma red de datos que administras; si esa red falla, pierdes el acceso. *Out-of-band* (consola, red de gestión separada) no depende de ella.

Las **líneas VTY** (*virtual terminal*) son las «puertas» lógicas por las que entran las sesiones remotas Telnet/SSH. Un router tiene varias (por ejemplo `vty 0 4` o `vty 0 15`), lo que permite varias sesiones simultáneas.

# 3. Arranque, memorias y archivos de configuración

Un router trabaja con varias memorias y con dos copias de su configuración: la que está usando ahora y la que cargará en el próximo arranque. Saber dónde está cada cosa explica errores muy frecuentes (configurar y no guardar) y permite hacer y restaurar copias de seguridad con criterio.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Memorias** (*ROM, flash, NVRAM, RAM*) | ¿Dónde se guarda cada cosa y qué se pierde al apagar? | IOS en flash; startup-config en NVRAM; running-config en RAM |
| **Secuencia de arranque** (*boot sequence*) | ¿Qué pasos sigue el equipo al encenderse? | POST → bootstrap → IOS → configuración |
| **Ficha del equipo** (*`show version`*) | ¿Qué modelo, qué IOS y cuánto tiempo lleva encendido? | *uptime*, imagen de arranque, registro `0x2102` |
| **Archivos de configuración** (*running-config / startup-config*) | ¿Qué configuración está activa y cuál se cargará al reiniciar? | `copy running-config startup-config` |
| **Copia de seguridad** (*backup*) | ¿Cómo conservo y recupero una configuración anterior? | `copy running-config tftp:` |

No debemos confundir **guardar** (de running a startup, dentro del propio equipo) con **hacer una copia de seguridad** (fuera del equipo, en un servidor).

## 3.1. Memorias del router

| Memoria | Volátil | Contenido principal |
|---|---|---|
| **ROM** | No | POST, *bootstrap* y un sistema mínimo de recuperación (ROMMON) |
| **Flash** | No | Imagen del sistema operativo IOS; puede almacenar otros archivos |
| **NVRAM** | No | **startup-config**: la configuración que se cargará en el próximo arranque |
| **RAM** | Sí | IOS en ejecución, **running-config**, tabla de routing, tabla ARP, búferes de paquetes |

La idea clave: **lo que el router está haciendo ahora está en RAM**, y se pierde al apagarlo si no se ha guardado en NVRAM.

## 3.2. Secuencia de arranque

```text
1. POST (Power-On Self-Test)          → comprobación del hardware (ROM)
2. Carga del bootstrap                → pequeño programa en ROM
3. Localización y carga del IOS       → normalmente desde flash
                                        (alternativas: servidor TFTP, ROMMON)
4. Localización y carga de la config  → startup-config desde NVRAM
                                        → se copia a RAM como running-config
5. Si no hay startup-config           → diálogo de configuración inicial (setup mode)
```

La búsqueda del IOS se rige por el **registro de configuración** (*configuration register*, habitualmente `0x2102`) y por posibles órdenes `boot system`. En este módulo basta con reconocer su existencia: modificarlo se usa, por ejemplo, en procedimientos de recuperación de contraseña, que no se desarrollan aquí.

Un router que arranca y muestra `Would you like to enter the initial configuration dialog? [yes/no]` **no tiene startup-config**. Puede ser un equipo nuevo o uno cuya configuración se borró.

## 3.3. `show version`: la ficha técnica del equipo

```text
R1# show version
Cisco IOS Software, ISR Software (X86_64_LINUX_IOSD-UNIVERSALK9-M), Version 16.9.4
...
ROM: IOS-XE ROMMON
R1 uptime is 2 hours, 14 minutes
System image file is "bootflash:isr4300-universalk9.16.09.04.SPA.bin"
...
cisco ISR4331/K9 (1RU) processor ... with 1795979K/6147K bytes of memory.
3 Gigabit Ethernet interfaces
32768K bytes of non-volatile configuration memory.
...
Configuration register is 0x2102
```

Permite responder con evidencia: qué versión de IOS ejecuta, desde qué archivo arrancó, cuánto tiempo lleva encendido (un *uptime* bajo delata un reinicio reciente), qué interfaces y memoria tiene y qué registro de configuración usa.

## 3.4. Archivos y comandos de gestión

| Comando | Qué hace |
|---|---|
| `show running-config` | Muestra la configuración activa (RAM) |
| `show startup-config` | Muestra la configuración guardada (NVRAM) |
| `copy running-config startup-config` | Guarda la configuración activa para el próximo arranque |
| `show flash:` (o `dir flash:`) | Lista los archivos de la flash (imagen IOS, otros) |
| `copy running-config tftp:` | Envía una copia de seguridad a un servidor TFTP |
| `copy tftp: running-config` | Trae una configuración desde TFTP y la **fusiona** con la activa |
| `copy tftp: startup-config` | Trae una configuración que se aplicará en el próximo arranque |
| `erase startup-config` | Borra la configuración guardada |
| `reload` | Reinicia el equipo |

Dos errores frecuentes:

- **Configurar y no guardar.** El cambio funciona hoy y desaparece tras el siguiente corte de luz.
- **Pensar que `copy tftp: running-config` reemplaza la configuración.** En realidad **la fusiona** con la existente: los comandos del archivo se añaden o sobrescriben, pero lo que no aparece en el archivo permanece. Si se quiere un estado limpio, se restaura sobre la startup-config y se reinicia.

### Copia de seguridad profesional

Antes de cualquier cambio relevante:

```text
R1# copy running-config tftp:
Address or name of remote host []? 192.168.30.20
Destination filename [R1-confg]? R1-2026-10-05.cfg
!!
1024 bytes copied
```

Un nombre de archivo con equipo y fecha permite localizar después qué configuración estaba activa en cada momento. TFTP no cifra ni autentica: en producción se prefieren SCP o SFTP, pero TFTP sigue siendo habitual en laboratorio.

# 4. Puesta en servicio: interfaces y rutas conectadas

Un router recién arrancado no reenvía nada útil hasta que sus interfaces tienen dirección y están activas. Este apartado enseña a ponerlas en servicio, a leer su estado y a comprobar el efecto en la tabla de routing: cada interfaz operativa aporta su red como ruta conectada. Es el primer paso de cualquier escenario de routing.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Configuración de interfaz** (*interface configuration*) | ¿Qué necesita una interfaz para funcionar? | `ip address ...` + `no shutdown` |
| **Estado de la interfaz** (*status / protocol*) | ¿Está activa en capa 1 y en capa 2? | `up/up`, `administratively down` |
| **Ruta conectada** (*connected route, C*) | ¿Qué redes conoce el router sin configurar rutas? | `C 192.168.10.0/24` |
| **Ruta local** (*local route, L*) | ¿Cómo sabe el router qué direcciones son suyas? | `L 192.168.10.1/32` |
| **Encaminamiento IPv6** (*IPv6 unicast routing*) | ¿Qué hace falta para que el router reenvíe IPv6? | `ipv6 unicast-routing` |

Una interfaz con cable pero sin `no shutdown`, o `up/up` pero sin dirección IP, no aporta ninguna red a la tabla.

## 4.1. Recuperación de IOS

De U06 ya conoces los modos (`R1>`, `R1#`, `R1(config)#`, `R1(config-if)#`), la ayuda con `?` y la diferencia entre running y startup. En un router se trabaja igual.

## 4.2. Configurar una interfaz IPv4

```text
R1(config)# interface GigabitEthernet0/0
R1(config-if)# description LAN-A usuarios
R1(config-if)# ip address 192.168.10.1 255.255.255.0
R1(config-if)# no shutdown
```

- `description` no tiene efecto técnico, pero documenta la red: en diagnóstico ahorra mucho tiempo.
- En los routers Cisco las interfaces vienen **apagadas administrativamente** por defecto. Sin `no shutdown` la interfaz no funciona aunque tenga IP y cable.

## 4.3. Interpretar el estado

```text
R1# show ip interface brief
Interface              IP-Address      OK? Method Status                Protocol
GigabitEthernet0/0     192.168.10.1    YES manual up                    up
GigabitEthernet0/1     10.0.12.1       YES manual up                    down
GigabitEthernet0/2     10.0.21.1       YES manual administratively down down
```

| Status / Protocol | Interpretación | Qué comprobar |
|---|---|---|
| `up / up` | Operativa en capa 1 y 2 | — |
| `administratively down / down` | Apagada por configuración | Falta `no shutdown` |
| `down / down` | Sin señal física | Cable, puerto remoto apagado, extremo desconectado |
| `up / down` | Hay señal, pero falla el protocolo de enlace | Incompatibilidades de encapsulación o del extremo remoto |

Una interfaz `up/up` sin dirección IP no aporta ninguna red a la tabla de routing.

## 4.4. Rutas conectadas (C) y locales (L)

En cuanto una interfaz con dirección IPv4 pasa a `up/up`, el router instala automáticamente dos rutas:

```text
R1# show ip route
...
     192.168.10.0/24 is variably subnetted, 2 subnets, 2 masks
C       192.168.10.0/24 is directly connected, GigabitEthernet0/0
L       192.168.10.1/32 is directly connected, GigabitEthernet0/0
```

- **C (connected):** la red completa a la que pertenece la interfaz. El router puede entregar directamente a cualquier host de esa red.
- **L (local):** una ruta `/32` hacia la **propia dirección** del router en esa interfaz. Indica al router que los paquetes dirigidos a esa IP son para él mismo.

La `L` no es otra red. Si la interfaz cae, desaparecen **ambas** rutas. Por eso observar si una red conectada está o no en la tabla es una forma rápida de comprobar el estado real de la interfaz.

> **Sin configurar ninguna ruta**, un router ya sabe llegar a todas las redes a las que está directamente conectado. Solo necesita ayuda para las redes que están **detrás de otros routers**.

## 4.5. Interfaces IPv6

De U05 recuerdas GUA, link-local y SLAAC. Para que un router **encamine** IPv6 hay que activarlo globalmente:

```text
R1(config)# ipv6 unicast-routing
R1(config)# interface GigabitEthernet0/0
R1(config-if)# ipv6 address 2001:db8:acad:10::1/64
R1(config-if)# ipv6 address fe80::1 link-local
R1(config-if)# no shutdown
```

- Sin `ipv6 unicast-routing` el router tiene direcciones IPv6 pero **no reenvía** paquetes IPv6 ni envía mensajes RA a la LAN.
- Asignar una link-local fácil de leer (`fe80::1`) no es obligatorio, pero simplifica mucho el diagnóstico y las rutas que la utilizan.

Verificación: `show ipv6 interface brief` y `show ipv6 route`. En IPv6 también aparecen rutas `C` (el `/64`) y `L` (un `/128` con la dirección propia).

# 5. Administración remota segura: de Telnet a SSH

Cuando el router ya tiene IP, puede administrarse a distancia. El problema es hacerlo sin exponer las credenciales: Telnet las envía en claro y SSH las cifra. Este apartado protege primero el acceso local y el modo privilegiado y después configura y verifica SSH. En el apartado 17 se limitará, además, desde qué redes se puede entrar.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Telnet** | ¿Por qué no se usa para administrar? | La contraseña se lee con *Follow TCP Stream* en Wireshark |
| **Contraseña de modo privilegiado** (*enable secret*) | ¿Cómo protejo el paso a `R1#`? | `enable secret ...` |
| **Usuario local** (*local user account*) | ¿Con qué cuenta se autentica cada sesión? | `username admin secret ...` |
| **SSH** (*Secure Shell*) | ¿Cómo administro en remoto de forma cifrada? | Claves RSA + `ip ssh version 2` |
| **Líneas VTY** (*VTY lines*) | ¿Qué protocolo y qué autenticación se admiten en remoto? | `login local`, `transport input ssh` |

Configurar SSH no basta: hay que demostrar que SSH entra (prueba positiva) y que Telnet es rechazado (prueba negativa).

## 5.1. El problema de Telnet

Telnet transmite **todo en texto claro**: usuario, contraseña y cada comando. Cualquiera que capture el tráfico en el camino puede leerlos. En una captura de Wireshark, la opción *Follow TCP Stream* sobre una sesión Telnet (puerto 23) muestra literalmente la contraseña tecleada. En una sesión SSH (puerto 22), tras el intercambio inicial de claves, solo se ve contenido cifrado.

Por eso el criterio profesional es: **SSH para la administración remota; Telnet deshabilitado.**

## 5.2. Proteger el acceso local y privilegiado

Antes de abrir acceso remoto se protegen los accesos básicos:

```text
R1(config)# enable secret Cl4ve-Privilegiada
R1(config)# service password-encryption
R1(config)# security passwords min-length 10
R1(config)# banner motd #Acceso restringido a personal autorizado#
R1(config)# line console 0
R1(config-line)# login local
R1(config-line)# exec-timeout 5 0
```

| Orden | Efecto |
|---|---|
| `enable secret` | Protege el paso a modo privilegiado con una contraseña almacenada como *hash*. Sustituye al antiguo `enable password` |
| `service password-encryption` | Oculta las contraseñas en texto claro de la configuración con un cifrado débil (tipo 7). Evita miradas casuales, **no** es una protección fuerte |
| `security passwords min-length` | Exige longitud mínima a las contraseñas nuevas |
| `exec-timeout 5 0` | Cierra la sesión tras 5 minutos de inactividad |
| `banner motd` | Mensaje de aviso legal al conectar |

> `login local` autentica contra las cuentas locales del router. Crea al menos un usuario (`username ... secret ...`, apartado 5.3) **antes** de cerrar la sesión de consola; si no, puedes bloquear tu propio acceso.

## 5.3. Configurar SSH

SSH necesita todos estos elementos (el hostname y el nombre de dominio deben existir **antes** de generar las claves):

```text
R1(config)# hostname R1
R1(config)# ip domain-name empresa.local
R1(config)# crypto key generate rsa general-keys modulus 2048
R1(config)# ip ssh version 2
R1(config)# username admin secret Adm1n-Segura!
R1(config)# line vty 0 4
R1(config-line)# login local
R1(config-line)# transport input ssh
R1(config-line)# exec-timeout 5 0
```

| Paso | Por qué es necesario |
|---|---|
| `hostname` distinto de `Router` | El nombre forma parte del identificador de las claves |
| `ip domain-name` | Junto con el hostname, da nombre a las claves RSA (`R1.empresa.local`) |
| `crypto key generate rsa ... modulus 2048` | Genera el par de claves que cifra la sesión. SSH versión 2 exige al menos 768 bits; 2048 es lo recomendado |
| `ip ssh version 2` | Desactiva la versión 1, insegura |
| `username ... secret` | Crea una cuenta local; `secret` la guarda como *hash* |
| `login local` en VTY | Las sesiones remotas se autentican con las cuentas locales |
| `transport input ssh` | Solo se admite SSH en esas líneas: Telnet queda rechazado |

Además, el router necesita una **dirección IP alcanzable** desde el equipo de administración. En un switch se usaba una SVI de gestión (U07); en un router basta con cualquiera de sus interfaces operativas.

## 5.4. Verificar

```text
R1# show ip ssh
SSH Enabled - version 2.0
Authentication timeout: 120 secs; Authentication retries: 3

R1# show ssh
Connection Version Encryption  State           Username
0          2.0     aes256-ctr  Session started admin
```

Desde un PC:

```text
C:\> ssh -l admin 192.168.10.1
```

Prueba positiva: la sesión SSH se abre con el usuario `admin`. Prueba negativa: un intento de `telnet 192.168.10.1` es rechazado. Ambas son necesarias para demostrar que la configuración hace lo que se pretende.

Más adelante (apartado 17) restringirás **desde qué redes** se puede abrir una sesión SSH mediante una ACL aplicada a las líneas VTY.

# 6. La tabla de routing

La tabla de routing es lo que el router sabe sobre cómo llegar a otras redes. Antes de añadir rutas hay que saber leerla. Este apartado explica qué significa cada campo de `show ip route`, de dónde vienen las rutas y cómo consultar qué hará el router con un destino concreto.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Código de origen** (*route source code*) | ¿Cómo se aprendió la ruta? | `C`, `L`, `S`, `S*` |
| **Prefijo de destino** (*destination prefix*) | ¿A qué red lleva la ruta? | `192.168.20.0/24` |
| **Siguiente salto / interfaz de salida** (*next hop / exit interface*) | ¿Por dónde sale el paquete? | `via 10.0.12.2`, `GigabitEthernet0/1` |
| **Distancia administrativa** (*administrative distance, AD*) | ¿Cuánto se fía el router de la fuente de la ruta? | Conectada 0, estática 1 |
| **Métrica** (*metric*) | ¿Qué camino es mejor dentro de una misma fuente? | Estática: 0 |
| **Gateway de último recurso** (*gateway of last resort*) | ¿A dónde va lo que no coincide con ninguna otra ruta? | `10.0.12.2` |

No debemos mezclar AD y métrica: la AD compara **fuentes**; la métrica compara **caminos** de una misma fuente.

## 6.1. Qué contiene

La tabla de routing es la lista de destinos que el router conoce y de cómo alcanzarlos. Cada entrada responde a tres preguntas: **¿a qué red?**, **¿por dónde?** y **¿quién me lo ha dicho?**

```text
R1# show ip route
Codes: L - local, C - connected, S - static, R - RIP, O - OSPF, ...
       * - candidate default

Gateway of last resort is 10.0.12.2 to network 0.0.0.0

S*    0.0.0.0/0 [1/0] via 10.0.12.2
      10.0.0.0/8 is variably subnetted, 2 subnets, 2 masks
C        10.0.12.0/30 is directly connected, GigabitEthernet0/1
L        10.0.12.1/32 is directly connected, GigabitEthernet0/1
      192.168.10.0/24 is variably subnetted, 2 subnets, 2 masks
C        192.168.10.0/24 is directly connected, GigabitEthernet0/0
L        192.168.10.1/32 is directly connected, GigabitEthernet0/0
S     192.168.20.0/24 [1/0] via 10.0.12.2
```

| Elemento | Ejemplo | Significado |
|---|---|---|
| Código de origen | `S`, `C`, `L`, `S*` | Cómo se aprendió la ruta |
| Destino / prefijo | `192.168.20.0/24` | Red que representa la ruta |
| `[AD/métrica]` | `[1/0]` | Distancia administrativa y métrica |
| Next hop | `via 10.0.12.2` | Router al que se entrega el paquete |
| Interfaz de salida | `GigabitEthernet0/1` | Por dónde sale el paquete |
| Gateway of last resort | `10.0.12.2` | Next hop de la ruta por defecto, si existe |

Las líneas como `10.0.0.0/8 is variably subnetted` son cabeceras que agrupan subredes; no son rutas utilizables por sí mismas.

## 6.2. Orígenes de las rutas en esta unidad

| Código | Origen | AD por defecto |
|---|---|---:|
| `C` | Red conectada | 0 |
| `L` | Dirección local | 0 |
| `S` | Ruta estática | 1 |
| `S*` | Ruta estática candidata por defecto | 1 |

En U09 aparecerán rutas aprendidas por protocolos dinámicos (`R` RIP con AD 120, `O` OSPF con AD 110).

## 6.3. La distancia administrativa (AD)

La AD expresa **cuánto se fía el router de la fuente** de una ruta. Cuanto menor, más preferida. Solo se utiliza para desempatar cuando **varias fuentes ofrecen el mismo prefijo exacto**.

La **métrica** compara caminos dentro de una misma fuente (por ejemplo, dos caminos OSPF). Las rutas estáticas tienen métrica 0.

## 6.4. Consultar un destino concreto

```text
R1# show ip route 192.168.20.10
Routing entry for 192.168.20.0/24
  Known via "static", distance 1, metric 0
  Routing Descriptor Blocks:
  * 10.0.12.2
      Route metric is 0, traffic share count is 1
```

Esta orden aplica la misma lógica que el router usa al reenviar y devuelve la ruta elegida. Es la forma más directa de responder «¿qué hará el router con este destino?».

# 7. Longest prefix match

Cuando varias rutas de la tabla abarcan el mismo destino, el router necesita una regla para elegir. Esa regla es el *longest prefix match*: gana la ruta más específica. Este apartado la aplica sobre prefijos anidados y aclara su relación con la AD, una de las confusiones más frecuentes.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Coincidencia** (*match*) | ¿Qué rutas abarcan este destino? | 172.16.40.150 coincide con /0, /16, /24, /25, /28 y /32 |
| **Prefijo más largo** (*longest prefix match, LPM*) | ¿Cuál de ellas se usa? | La `/32` antes que la `/24` |
| **LPM antes que AD** (*LPM before AD*) | ¿Cuándo influye la AD? | Solo entre fuentes que ofrecen el mismo prefijo exacto |
| **Ruta frente a conectividad** (*route vs. reachability*) | ¿Qué demuestra que exista una ruta? | Solo que el router sabe por dónde enviar |

No se compara la AD de dos rutas con prefijos distintos: no compiten entre sí.

## 7.1. Varias rutas pueden coincidir

Una ruta *coincide* con un destino cuando los primeros N bits del destino son iguales a los de la red de la ruta, siendo N la longitud del prefijo. Con rutas anidadas, un mismo destino puede coincidir con varias:

```text
S*   0.0.0.0/0           via 10.0.0.254
S    172.16.0.0/16       via 10.0.0.2
S    172.16.40.0/24      via 10.0.0.3
S    172.16.40.128/25    via 10.0.0.4
S    172.16.40.144/28    via 10.0.0.5
S    172.16.40.150/32    via 10.0.0.6
```

## 7.2. La regla

> Entre todas las rutas que coinciden con el destino, el router elige la de **prefijo más largo**, es decir, la más específica.

| Destino | Rutas que coinciden | Ruta elegida | Next hop |
|---|---|---|---|
| 172.16.40.150 | /0, /16, /24, /25, /28, /32 | /32 | 10.0.0.6 |
| 172.16.40.149 | /0, /16, /24, /25, /28 | /28 (144–159) | 10.0.0.5 |
| 172.16.40.130 | /0, /16, /24, /25 | /25 (128–255) | 10.0.0.4 |
| 172.16.40.10 | /0, /16, /24 | /24 | 10.0.0.3 |
| 172.16.41.10 | /0, /16 | /16 | 10.0.0.2 |
| 203.0.113.9 | /0 | /0 | 10.0.0.254 |

Para comprobar la coincidencia con prefijos que no terminan en octeto completo, usa lo que aprendiste en U04: calcula el rango de la red (`172.16.40.144/28` → 144–159) y comprueba si el destino cae dentro.

## 7.3. LPM antes que AD

Error frecuente: comparar la AD de dos rutas con prefijos distintos.

```text
S   10.0.0.0/8       [1/0]   via 10.0.12.2
S   10.10.20.0/24    [20/0]  via 10.0.21.2
```

Para el destino `10.10.20.50`, el router elige `/24` aunque su AD sea 20 y la otra 1. **No compiten**: son prefijos distintos y gana el más específico. La AD solo entra en juego si dos fuentes ofrecen exactamente `10.10.20.0/24`.

```text
1.º  ¿Qué rutas coinciden?        → comparación de bits
2.º  ¿Cuál es la más específica?  → longest prefix match
     (la AD ya se usó antes para decidir qué fuente instala cada prefijo)
```

## 7.4. Ruta en la tabla no significa conectividad

Que exista una ruta hacia un destino solo demuestra que el router **sabe por dónde enviarlo**. Todavía pueden fallar el next hop, la resolución ARP/ND, la ruta de retorno, una ACL, el servicio o el propio host de destino. Recuerda este límite al interpretar evidencias.

# 8. Rutas estáticas IPv4

Un router solo conoce por sí mismo sus redes conectadas. Para alcanzar las redes que están detrás de otros routers hay que enseñárselas; en esta unidad lo hacemos a mano, con rutas estáticas. Este apartado cubre su sintaxis, las formas de indicar el camino, la condición de que el next hop sea alcanzable y el método para planificarlas y verificarlas.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Ruta estática** (*static route*) | ¿Cómo enseño al router una red remota? | `ip route 192.168.20.0 255.255.255.0 10.0.12.2` |
| **Formas de indicar el camino** (*next hop / exit interface / fully specified*) | ¿Indico el vecino, la interfaz o ambos? | `10.0.12.2` · `g0/1` · `g0/1 10.0.12.2` |
| **Resolución recursiva** (*recursive lookup*) | ¿Cómo llega el router a su next hop? | 10.0.12.2 → `C 10.0.12.0/30`, G0/1 |
| **Matriz de rutas** (*routing plan*) | ¿Qué rutas necesita cada router? | Red remota + next hop, router a router |
| **Red *stub*** (*stub network*) | ¿Cuándo basta una sola ruta? | Sede con un único enlace de salida |

Una ruta que aparece en la configuración pero no en `show ip route` no se está usando: casi siempre, su next hop no es alcanzable.

## 8.1. Qué es una ruta estática

Una **ruta estática** es una ruta que el administrador escribe a mano. El router la utiliza tal cual hasta que alguien la cambie o hasta que deje de ser utilizable (por ejemplo, porque cae la interfaz por la que se alcanza el next hop).

| Ventajas | Inconvenientes |
|---|---|
| Control total sobre el camino | Mantenimiento manual en cada router |
| Sin consumo de CPU ni tráfico de protocolos | No se adapta si falla un camino remoto |
| Predecible y fácil de verificar | Escala mal: con muchas redes se vuelve inmanejable y propensa a errores |
| Útil en redes pequeñas, redes *stub* y rutas por defecto | Un error se propaga en silencio |

## 8.2. Sintaxis

```text
ip route  RED_DESTINO  MÁSCARA  { NEXT_HOP | INTERFAZ | INTERFAZ NEXT_HOP }  [AD]
```

En la topología de referencia, R1 no conoce LAN-B. Para alcanzarla:

```text
R1(config)# ip route 192.168.20.0 255.255.255.0 10.0.12.2
```

Se lee: «para cualquier destino de `192.168.20.0/24`, entrega el paquete a `10.0.12.2`».

## 8.3. Tres formas de indicar el camino

| Forma | Ejemplo | Comportamiento |
|---|---|---|
| **Next hop** | `ip route 192.168.20.0 255.255.255.0 10.0.12.2` | El router busca en su tabla cómo llegar a `10.0.12.2` (resolución recursiva). Forma más habitual en Ethernet |
| **Interfaz de salida** | `ip route 192.168.20.0 255.255.255.0 g0/1` | El router trata el destino como si estuviera conectado a esa interfaz. Adecuada en enlaces punto a punto (serie); **no recomendable en Ethernet**, porque obliga a resolver por ARP cada destino y depende del *proxy ARP* del router vecino |
| **Completamente especificada** (*fully specified*) | `ip route 192.168.20.0 255.255.255.0 g0/1 10.0.12.2` | Indica interfaz y next hop. Evita ambigüedades y la búsqueda recursiva. Obligatoria con next hop link-local en IPv6 |

## 8.4. Resolución recursiva y next hop alcanzable

Con una ruta por next hop, el router hace dos búsquedas:

```text
Destino 192.168.20.10
 → coincide con S 192.168.20.0/24 via 10.0.12.2
 → ¿cómo llego a 10.0.12.2?
 → coincide con C 10.0.12.0/30, GigabitEthernet0/1
 → sale por G0/1 hacia la MAC de 10.0.12.2
```

Si el next hop no pertenece a ninguna red que el router pueda alcanzar, la ruta **no se instala** en la tabla (aparece en la configuración, pero no en `show ip route`). Por eso, ante una ruta configurada que «no aparece», la primera pregunta es:

> ¿Cómo llega este router a su next hop?

Error típico: escribir como next hop la dirección **del propio router** o una dirección del otro extremo que no está en el enlace compartido.

## 8.5. Planificar antes de escribir

Una ruta estática es la traducción de una decisión. Antes de configurar, se completa una matriz por router:

| Router | Red remota | Prefijo | Next hop | ¿Next hop en red conectada? |
|---|---|---|---|---|
| R1 | 192.168.20.0 | /24 | 10.0.12.2 | Sí (10.0.12.0/30, G0/1) |
| R1 | 192.168.30.0 | /24 | 10.0.12.2 | Sí |
| R2 | 192.168.10.0 | /24 | 10.0.12.1 | Sí (10.0.12.0/30, G0/1) |

Método para rellenarla:

1. lista todas las redes de la topología;
2. para cada router, tacha las que ya son `C`;
3. para cada red restante, decide hacia qué vecino hay que enviar el tráfico;
4. el next hop es la IP **del vecino** en el enlace compartido.

## 8.6. Verificación

```text
R1# show ip route static
S     192.168.20.0/24 [1/0] via 10.0.12.2
S     192.168.30.0/24 [1/0] via 10.0.12.2

R1# show ip route 192.168.30.10
Routing entry for 192.168.30.0/24
  Known via "static", distance 1, metric 0
  * 10.0.12.2
```

Comprueba: que la ruta aparece con código `S`, que el prefijo es el correcto (un `/16` en lugar de un `/24` cambia qué destinos abarca), que el next hop es el previsto y que la prueba de conectividad funciona **en ambos sentidos**.

## 8.7. Red *stub*

Una red *stub* solo tiene una salida. Por ejemplo, una sede pequeña conectada a la central por un único enlace. En ese router no tiene sentido una ruta por cada red remota: basta una **ruta por defecto** (apartado 10).

# 9. Ida y retorno

Un ping, una web o una sesión SSH necesitan dos viajes: la petición y la respuesta. Cada router decide solo con su propia tabla, así que el hecho de que la ida funcione no dice nada de la vuelta. Este apartado muestra el síntoma típico de un retorno ausente y un método para seguir el paquete en los dos sentidos.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Camino de ida** (*forward path*) | ¿Llega la petición al destino? | PC-A → R1 → R2 → PC-B |
| **Camino de retorno** (*return path*) | ¿Vuelve la respuesta al origen? | R2 necesita una ruta hacia 192.168.10.0/24 |
| **Seguimiento del paquete** (*packet walk*) | ¿En qué router se rompe el camino? | Ruta elegida en cada salto, en ambos sentidos |
| **Ping extendido** (*extended ping*) | ¿Cómo reproduzco desde el router el caso real del PC? | `ping 192.168.20.10 source g0/0` |

Si solo revisamos el router de origen, «todo está bien»: el fallo suele estar en otro router y en el otro sentido.

## 9.1. Toda comunicación tiene dos caminos

Un `ping` de PC-A a PC-B solo funciona si:

- el *echo request* llega de PC-A a PC-B, **y**
- el *echo reply* vuelve de PC-B a PC-A.

Cada router decide de forma independiente con **su propia** tabla. Que R1 sepa llegar a LAN-B no implica nada sobre si R2 sabe volver a LAN-A.

## 9.2. El síntoma típico

```text
R1: S 192.168.20.0/24 via 10.0.12.2      ← correcto
R2: (sin ruta hacia 192.168.10.0/24)     ← falta el retorno
```

Resultado:

- la petición llega a PC-B;
- PC-B responde a 192.168.10.10 enviando el paquete a su gateway R2;
- R2 no tiene ruta hacia 192.168.10.0/24 y lo descarta;
- en PC-A el `ping` muestra *Request timed out*.

Si solo miras R1, «todo está bien». El fallo está en otro router y en el otro sentido.

## 9.3. Método para seguir el paquete

```text
IDA                                   RETORNO
1. Origen: ¿destino local o remoto?   6. Destino: responde a su gateway
2. Gateway del origen                 7. Router del destino: ¿ruta hacia el origen?
3. Ruta elegida en cada router        8. Siguiente router: ¿ruta hacia el origen?
4. Next hop alcanzable                9. ... hasta llegar a la red de origen
5. Llega al destino
```

No es necesario que ida y retorno usen el mismo camino físico, pero **ambos tienen que existir**.

## 9.4. Evidencias útiles

- `ping` desde el router hacia distintos puntos: si R1 alcanza `10.0.12.2` pero no `192.168.20.10`, el problema está más allá de R1.
- `traceroute` desde el origen: muestra hasta qué salto llegan las respuestas.
- `show ip route <red-origen>` **en el router del destino**: comprueba directamente si existe el retorno.

> Un ping desde un router usa como IP de origen la de su interfaz de salida. Puede funcionar aunque falle un ping desde un PC de la LAN, porque las redes de origen son distintas. El `ping` extendido permite fijar el origen (`ping 192.168.20.10 source g0/0`) y reproducir el caso real.

# 10. Ruta por defecto, host route y floating static

Además de las rutas a redes concretas, hay tres usos especiales de la ruta estática que aparecen en casi cualquier red: una ruta para «todo lo demás», una ruta hacia un único equipo y una ruta de respaldo. Las tres se explican con lo que ya sabes: el LPM decide qué ruta se usa y la AD decide qué fuente instala un mismo prefijo.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Ruta por defecto** (*default route*) | ¿A dónde envío lo que no conozco? | `ip route 0.0.0.0 0.0.0.0 10.0.12.2` |
| **Ruta a host** (*host route*) | ¿Cómo fuerzo el camino hacia un solo equipo? | `192.168.30.10/32` |
| **Ruta estática flotante** (*floating static route*) | ¿Qué camino se usa si cae el principal? | Mismo prefijo con AD 5 por el enlace de respaldo |
| **Límite de la ruta estática** (*static route limitation*) | ¿Qué fallos no detecta una estática? | Caída remota con el enlace local en `up/up` |

La ruta por defecto no «gana siempre», y la flotante no es un protocolo de routing: solo entra si el router detecta localmente que la principal ya no sirve.

## 10.1. Ruta por defecto

```text
R1(config)# ip route 0.0.0.0 0.0.0.0 10.0.12.2
```

`0.0.0.0/0` coincide con **cualquier** dirección IPv4, pero es la ruta **menos específica** posible. Por LPM, solo se usa cuando no hay otra coincidencia mejor. Se lee: «para todo lo que no conozcas, envíalo aquí».

```text
Gateway of last resort is 10.0.12.2 to network 0.0.0.0
S*    0.0.0.0/0 [1/0] via 10.0.12.2
```

El asterisco (`*`) la marca como candidata por defecto; el *gateway of last resort* es su next hop.

Usos típicos:

- routers de sedes *stub*;
- router de borde hacia el proveedor de Internet (U10);
- simplificar tablas: rutas específicas para lo interno, ruta por defecto para el resto.

**Error frecuente:** pensar que la ruta por defecto «siempre gana». Pierde frente a cualquier prefijo más largo. Otro error: usarla para ocultar un diseño incompleto; el paquete «sale por algún sitio», pero eso no significa que llegue.

## 10.2. Host route

Una ruta hacia un único host usa prefijo `/32`:

```text
R1(config)# ip route 192.168.30.10 255.255.255.255 10.0.21.2
```

Es la coincidencia IPv4 más específica posible. Sirve para forzar un camino concreto hacia un servidor sin afectar al resto de la red. No debe confundirse con las rutas `L`, que también son `/32` pero representan direcciones del propio router.

## 10.3. Floating static route

Una **floating static** es una ruta estática de respaldo con una AD mayor que la ruta principal **hacia el mismo prefijo**:

```text
R1(config)# ip route 192.168.20.0 255.255.255.0 10.0.12.2         ! principal, AD 1
R1(config)# ip route 192.168.20.0 255.255.255.0 10.0.21.2 5       ! respaldo, AD 5
```

Mientras la principal está disponible, solo ella se instala en la tabla; la de respaldo «flota» por encima, en la configuración, sin usarse. Si la principal deja de ser válida, la de respaldo entra.

```text
Estado normal:           S 192.168.20.0/24 [1/0] via 10.0.12.2
G0/1 cae (down/down):    S 192.168.20.0/24 [5/0] via 10.0.21.2
G0/1 se recupera:        S 192.168.20.0/24 [1/0] via 10.0.12.2
```

Condiciones para que funcione:

- **mismo prefijo** en las dos rutas (si el prefijo es distinto no compiten: se aplica LPM);
- AD del respaldo **mayor** que la de la principal (con estáticas: mayor que 1; si la principal fuese OSPF, mayor que 110);
- el next hop del respaldo debe ser alcanzable por otro camino.

## 10.4. Limitación importante

Una ruta estática solo desaparece cuando el router detecta localmente que ya no puede usarla: típicamente, cuando cae la interfaz por la que llega al next hop. Si el fallo está **más lejos** (el enlace local sigue `up/up`, pero el router vecino ha perdido su conexión con LAN-B), la ruta principal sigue instalada y el tráfico se pierde. El respaldo nunca entra.

Detectar fallos remotos y reaccionar requiere mecanismos que intercambien información entre routers: es precisamente lo que aportan los protocolos de routing dinámico (U09).

Otro error frecuente es la **simetría**: si R1 cambia al enlace de respaldo pero R2 sigue devolviendo el tráfico por el enlace principal caído, el retorno falla. El respaldo se configura en **los dos sentidos**.

# 11. Rutas estáticas IPv6

IPv6 no cambia la lógica del routing: prefijo, LPM, next hop y retorno funcionan igual que en IPv4. Cambian la sintaxis y un detalle importante, el uso de direcciones link-local como next hop. Este apartado traslada el escenario IPv4 a IPv6 y recuerda que en doble pila cada familia se verifica por separado.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Ruta estática IPv6** (*IPv6 static route*) | ¿Cómo se escribe una ruta IPv6? | `ipv6 route 2001:db8:acad:20::/64 2001:db8:acad:12::2` |
| **Ruta por defecto IPv6** (*IPv6 default route*) | ¿Cuál es el «todo lo demás» en IPv6? | `::/0` |
| **Next hop link-local** (*link-local next hop*) | ¿Por qué hay que indicar también la interfaz? | `g0/1 fe80::2` |
| **Doble pila** (*dual stack*) | ¿Si funciona IPv4, funciona IPv6? | No necesariamente: se verifica cada familia |

Sin `ipv6 unicast-routing` el router tiene direcciones IPv6, pero no reenvía paquetes IPv6.

## 11.1. El mismo modelo

IPv6 cambia el formato de las direcciones, no la lógica: prefijo, LPM, next hop, interfaz de salida y retorno funcionan igual.

| IPv4 | IPv6 |
|---|---|
| `ip route 192.168.20.0 255.255.255.0 10.0.12.2` | `ipv6 route 2001:db8:acad:20::/64 2001:db8:acad:12::2` |
| `ip route 0.0.0.0 0.0.0.0 10.0.12.2` | `ipv6 route ::/0 2001:db8:acad:12::2` |
| `/32` host route | `/128` host route |
| `show ip route` | `show ipv6 route` |

Recuerda activar `ipv6 unicast-routing`.

## 11.2. Next hop link-local

Los routers vecinos se comunican siempre mediante sus direcciones link-local, y estas son estables aunque se renumere el prefijo global. Por eso es habitual usarlas como next hop:

```text
R1(config)# ipv6 route 2001:db8:acad:20::/64 GigabitEthernet0/1 fe80::2
```

La interfaz es **obligatoria**. Una dirección link-local solo es válida dentro de un enlace, y la misma dirección `fe80::2` puede existir en varios enlaces distintos del router. Sin la interfaz, el router no sabría en qué enlace buscarla.

```text
ipv6 route 2001:db8:acad:20::/64 fe80::2            ← rechazada / ambigua
ipv6 route 2001:db8:acad:20::/64 g0/1 fe80::2       ← correcta
```

## 11.3. Verificación

```text
R1# show ipv6 route
S   ::/0 [1/0]
     via 2001:DB8:ACAD:12::2
C   2001:DB8:ACAD:10::/64 [0/0]
     via GigabitEthernet0/0, directly connected
L   2001:DB8:ACAD:10::1/128 [0/0]
     via GigabitEthernet0/0, receive
S   2001:DB8:ACAD:20::/64 [1/0]
     via FE80::2, GigabitEthernet0/1
```

## 11.4. Doble pila

En una red *dual stack* IPv4 e IPv6 funcionan como dos redes lógicas independientes que comparten cables: cada una tiene sus direcciones, su tabla, sus rutas y sus filtros.

> Que `ping 192.168.20.10` funcione no demuestra nada sobre `ping 2001:db8:acad:20::10`. Cada familia se verifica por separado.

# 12. Seguimiento de incidencias

Cuando algo falla, la tentación es cambiar la configuración hasta que funcione. Este apartado propone lo contrario: elegir la herramienta según la pregunta, interpretar bien lo que devuelve y cambiar solo cuando la evidencia señala la causa. Es el método que usarás en todos los laboratorios de la unidad.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Comandos `show`** (*show commands*) | ¿Qué estado y qué configuración tiene el router? | `show ip route 192.168.20.10` |
| **`ping` y `traceroute`** | ¿Hay respuesta? ¿Hasta dónde avanza el paquete? | `!`, `.`, `U`; `* * *` |
| **Depuración** (*debug*) | ¿Qué está procesando el router ahora mismo? | `debug ip icmp` y después `undebug all` |
| **Registro de eventos** (*logging*) | ¿Qué ha registrado el equipo? | `show logging` |
| **Método de diagnóstico** (*troubleshooting method*) | ¿En qué orden razono? | Síntoma → hipótesis → prueba → evidencia → cambio mínimo → verificación |

Un ping fallido es un síntoma, no un diagnóstico: primero se localiza **dónde** se rompe el camino.

## 12.1. Cada comando responde a una pregunta

| Pregunta | Herramienta |
|---|---|
| ¿Qué versión, uptime, memorias? | `show version` |
| ¿Las interfaces están operativas y con la IP correcta? | `show ip interface brief`, `show interfaces` |
| ¿Qué redes conoce el router? | `show ip route`, `show ipv6 route` |
| ¿Qué hará con este destino concreto? | `show ip route <destino>` |
| ¿Qué configuración está activa? | `show running-config`, `show running-config \| section ...` |
| ¿Hay respuesta extremo a extremo? | `ping` (y `ping` extendido con origen) |
| ¿Hasta dónde avanza el paquete? | `traceroute` (en Windows, `tracert`) |
| ¿Conozco la MAC del next hop? | `show ip arp`, `show ipv6 neighbors` |
| ¿Qué eventos ha registrado el equipo? | `show logging` |
| ¿Qué está procesando ahora mismo? | `debug ...` (con precaución) |

## 12.2. Leer `ping` y `traceroute`

En Cisco IOS:

| Símbolo | Significado |
|---|---|
| `!` | Respuesta recibida |
| `.` | Tiempo agotado: no llegó respuesta |
| `U` | Destino inalcanzable: algún router informó que no podía entregarlo |

`U` es una pista valiosa: **un router del camino** ha dicho que no tiene ruta o que el paquete fue filtrado. `.` solo dice que no volvió nada, sin indicar dónde se perdió.

`traceroute` muestra los saltos que responden. Un `* * *` a partir de cierto punto indica que el paquete, o su respuesta, se pierde después del último router que contestó. Hay que interpretarlo con cautela: un router puede no responder por política aunque reenvíe tráfico, y los caminos pueden ser asimétricos.

## 12.3. `debug` con precaución

```text
R1# terminal monitor
R1# debug ip icmp
ICMP: echo reply sent, src 192.168.10.1, dst 192.168.10.10
R1# undebug all
```

`debug` muestra en tiempo real lo que procesa el router. Es muy informativo en laboratorio, pero en un equipo de producción cargado puede consumir tanta CPU que afecte al servicio. Se activa con un propósito concreto, sobre el tráfico mínimo, y se desactiva inmediatamente (`undebug all`). `terminal monitor` es necesario para ver los mensajes en una sesión SSH.

## 12.4. Método: evidencia antes que cambio

```text
Síntoma      → «PC-A no alcanza a PC-B por ping»
Hechos       → PC-A alcanza su gateway; R1 alcanza 10.0.12.2
Hipótesis    → falta la ruta de retorno en R2
Prueba       → show ip route 192.168.10.0 en R2
Evidencia    → «% Network not in table»
Conclusión   → R2 no sabe volver a LAN-A
Cambio mínimo→ ip route 192.168.10.0 255.255.255.0 10.0.12.1 en R2
Verificación → ping PC-A → PC-B correcto; show ip route en R2 muestra la S
```

Orden de comprobación útil (no es una receta rígida):

```text
interfaz → dirección/prefijo → rutas C → ruta elegida (LPM) → next hop alcanzable
→ ARP/ND → siguiente router → destino → ruta de retorno
```

Un ping fallido nunca justifica por sí solo reescribir todas las rutas. Primero se localiza **dónde** se rompe el camino.

# 13. El router como servidor DHCP

En U04 estudiaste cómo funciona DHCP; aquí el router pasa a ser el servidor. Es habitual en sedes pequeñas, donde no compensa un servidor dedicado. El apartado recoge la configuración mínima (exclusiones y pool), los errores que provocan conflictos o clientes sin salida y la forma de verificar las concesiones.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Direcciones excluidas** (*excluded addresses*) | ¿Qué direcciones no debe entregar el servidor? | `ip dhcp excluded-address 192.168.10.1 192.168.10.20` |
| **Pool DHCP** (*DHCP pool*) | ¿Qué red se reparte? | `ip dhcp pool LAN-A` + `network ...` |
| **Parámetros del cliente** (*client options*) | ¿Qué recibe el cliente además de la IP? | `default-router`, `dns-server`, `lease` |
| **Concesión** (*binding*) | ¿A quién se ha entregado cada dirección? | `show ip dhcp binding` |

Las exclusiones se configuran en modo global, fuera del pool, y deben incluir el gateway y los equipos con IP fija.

## 13.1. Recuperación de U04

Ya conoces el intercambio DORA (*Discover, Offer, Request, Acknowledge*), el concepto de pool, las exclusiones y los parámetros que entrega DHCP: dirección, máscara, gateway, DNS y duración de la concesión. Ahora vas a configurar un router Cisco para que haga de servidor.

## 13.2. Configuración

```text
R1(config)# ip dhcp excluded-address 192.168.10.1 192.168.10.20
R1(config)# ip dhcp pool LAN-A
R1(dhcp-config)# network 192.168.10.0 255.255.255.0
R1(dhcp-config)# default-router 192.168.10.1
R1(dhcp-config)# dns-server 192.168.30.53
R1(dhcp-config)# domain-name empresa.local
R1(dhcp-config)# lease 1
```

| Orden | Función |
|---|---|
| `ip dhcp excluded-address` | Reserva direcciones que el servidor **no** debe entregar: gateway, servidores, impresoras con IP fija. Se configura en modo global, fuera del pool |
| `ip dhcp pool NOMBRE` | Crea el pool y entra en su configuración |
| `network` | Red cuyas direcciones se asignan. El router usa el pool cuya red coincide con la interfaz que recibe la petición |
| `default-router` | Gateway que recibirán los clientes. Debe ser la IP del router **en esa LAN** |
| `dns-server` | Servidor DNS |
| `domain-name` | Sufijo de dominio |
| `lease` | Duración de la concesión en días (por defecto, 1) |

Errores frecuentes:

- no excluir la dirección del gateway, o excluir un rango equivocado → **conflicto de direcciones**;
- `default-router` con una IP de otra red → el cliente obtiene IP, pero no sale de su red;
- `network` con máscara distinta a la de la interfaz → el pool no corresponde a la LAN.

## 13.3. Verificación

```text
R1# show ip dhcp binding
IP address       Client-ID/Hardware address   Lease expiration     Type
192.168.10.21    0100.50b6.1a2b.3c            Oct 06 2026 10:02 AM Automatic

R1# show ip dhcp pool
Pool LAN-A :
 Total addresses                : 254
 Leased addresses               : 1
 ...
R1# show ip dhcp conflict
```

En el cliente: `ipconfig /all` (Windows) muestra la IP, el gateway, el DNS y el servidor DHCP que respondió.

# 14. DHCP relay

En una empresa lo habitual es un servidor DHCP central que da servicio a muchas LAN. Pero el Discover es un broadcast y los routers no reenvían broadcasts entre redes. El relay resuelve ese problema. Este apartado explica dónde se configura, qué añade al mensaje (giaddr), por qué depende del routing y cómo diagnosticar a un cliente que se queda sin IP.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Agente de retransmisión** (*DHCP relay agent*) | ¿Cómo llega un Discover a un servidor de otra red? | `ip helper-address 192.168.30.20` |
| **Interfaz de los clientes** (*client-facing interface*) | ¿Dónde se configura el helper? | R1 G0/0 (LAN-A) |
| **giaddr** (*gateway IP address*) | ¿Cómo sabe el servidor qué pool usar y a dónde responder? | `192.168.10.1` |
| **Dependencia del routing** (*routing dependency*) | ¿Qué más tiene que funcionar? | Ruta hacia el servidor y ruta de vuelta a la LAN |
| **APIPA** (*Automatic Private IP Addressing*) | ¿Qué indica una dirección 169.254.x.x? | El cliente no recibió respuesta DHCP |

El helper va en la interfaz que **recibe el broadcast de los clientes**, no en la que mira hacia el servidor.

## 14.1. El problema

El mensaje *DHCP Discover* es un **broadcast**: el cliente todavía no tiene IP y no sabe dónde está el servidor. Los routers **no reenvían broadcasts entre redes**. Si el servidor DHCP está en otra red, el Discover muere en la interfaz del router.

Tener un servidor DHCP en cada LAN no es práctico. La solución es que el router actúe como **agente de retransmisión** (*DHCP relay agent*).

## 14.2. Configuración

En la topología de referencia, el servidor DHCP central es `192.168.30.20` (red SERVERS, detrás de R2). Para que los clientes de LAN-A obtengan dirección de él:

```text
R1(config)# interface GigabitEthernet0/0
R1(config-if)# ip helper-address 192.168.30.20
```

Se configura en la interfaz que **recibe el broadcast de los clientes** (*client-facing*), no en la interfaz que mira hacia el servidor.

## 14.3. Qué hace el relay

```text
Cliente LAN-A  ──Discover (broadcast)──►  R1 G0/0
R1             ──Discover (unicast)───►  192.168.30.20
                 giaddr = 192.168.10.1
Servidor       ──Offer (unicast)──────►  192.168.10.1 (R1)
R1             ──Offer────────────────►  Cliente
(igual para Request y Acknowledge)
```

El relay escribe en el mensaje el campo **giaddr** (*gateway IP address*) con la IP de la interfaz que recibió la petición. El servidor usa ese valor para dos cosas:

1. **elegir el pool** cuya red contiene `192.168.10.1` → pool de LAN-A;
2. **enviar la respuesta** a esa dirección.

Por eso el servidor necesita un pool para la red remota (con su `default-router` = `192.168.10.1`) y una **ruta de vuelta** hacia `192.168.10.0/24`.

## 14.4. El relay no sustituye al routing

`ip helper-address` no crea ninguna ruta. Para que el relay funcione:

- R1 debe tener ruta hacia `192.168.30.20`;
- el servidor (y los routers intermedios) deben saber volver a la red del cliente;
- el servidor debe tener un pool que coincida con el `giaddr`;
- ninguna ACL puede bloquear DHCP (UDP 67/68).

> `ip helper-address` también reenvía por defecto algunos otros servicios UDP basados en broadcast (TFTP, DNS, NetBIOS…). En este módulo nos centramos en DHCP.

## 14.5. Diagnóstico de un cliente sin IP

| Pregunta | Evidencia |
|---|---|
| ¿El cliente está configurado como DHCP? | Configuración del PC; dirección `169.254.x.x` (APIPA) si no obtuvo respuesta |
| ¿Hay helper en la interfaz *client-facing*? | `show running-config interface g0/0` |
| ¿La IP del servidor es correcta? | Valor de `ip helper-address` |
| ¿El router alcanza al servidor? | `ping 192.168.30.20` |
| ¿Existe ruta de vuelta? | `show ip route 192.168.10.0` en R2 |
| ¿Hay pool para la red del cliente? | Configuración del servidor |
| ¿Alguna ACL bloquea UDP 67/68? | `show ip interface`, `show access-lists` |

Cambiar el helper cuando el problema es la ruta de retorno no resuelve nada: por eso se recoge evidencia antes de modificar.

# 15. Política de tráfico y listas de control de acceso

Con el routing completo, todo alcanza a todo. Una organización necesita decidir qué tráfico se permite, y la ACL es la herramienta del router para aplicar esa decisión. Este apartado todavía no se centra en la sintaxis: explica cómo pasar de requisitos a una matriz de flujos, cómo evalúa el router una ACL, dónde y en qué sentido se aplica y qué tipos existen. Los apartados 16 a 20 desarrollan cada pieza.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Matriz de flujos** (*traffic flow matrix*) | ¿Qué tráfico debe permitirse o denegarse? | LAN-A → WEB, TCP 443: permitir |
| **Entrada de control de acceso** (*Access Control Entry, ACE*) | ¿Qué es cada línea de la ACL? | `20 deny tcp ... eq 22` |
| **Primera coincidencia** (*first match*) | ¿Qué ACE decide? | La primera que coincide, de arriba abajo |
| **Denegación implícita** (*implicit deny*) | ¿Qué pasa con lo que no coincide con nada? | Se descarta |
| **Aplicación y sentido** (*applying: in / out*) | ¿Dónde y en qué momento se evalúa? | `ip access-group LAN-A-IN in` en G0/0 |
| **ACL estándar / extendida** (*standard / extended ACL*) | ¿Qué campos puede comprobar? | Solo origen / protocolo, origen, destino y puertos |

No debemos confundir **filtrar** con **seleccionar**: en U10 la misma sintaxis servirá para elegir qué tráfico traduce NAT.

## 15.1. De la conectividad a la política

Cuando el routing está completo, **todo puede alcanzar a todo**. Casi nunca es lo que una organización quiere:

- los usuarios deben acceder a la web interna, pero no administrar sus servidores;
- solo el equipo de sistemas debe abrir sesiones SSH en los routers;
- los invitados deben salir a Internet, pero no ver la red interna.

Estas frases son **requisitos de política**. Una **ACL** (*Access Control List*) es una de las herramientas que permiten implementarlos en el router.

## 15.2. Política antes que sintaxis

El primer paso nunca es escribir comandos, sino traducir los requisitos a una **matriz de flujos**:

| # | Origen | Destino | Protocolo | Puerto / tipo | Acción |
|---|---|---|---|---|---|
| 1 | LAN-A (usuarios) | WEB 192.168.30.10 | TCP | 443 (HTTPS) | permitir |
| 2 | LAN-A (usuarios) | WEB 192.168.30.10 | TCP | 22 (SSH) | denegar |
| 3 | PC-ADMIN 192.168.10.5 | WEB 192.168.30.10 | TCP | 22 (SSH) | permitir |
| 4 | LAN-A | cualquier destino | ICMP | echo | permitir (diagnóstico) |

Una matriz obliga a concretar lo que un requisito vago no dice. «Permitir la web» no indica: ¿desde qué red?, ¿a qué servidor?, ¿HTTP, HTTPS o ambos?, ¿en qué sentido se inicia la comunicación?

## 15.3. Estructura de una ACL

Una ACL es una lista ordenada de **ACE** (*Access Control Entries*). Cada ACE tiene:

- una **condición** (qué paquetes coinciden: origen, destino, protocolo, puertos…);
- una **acción**: `permit` o `deny`.

```text
ip access-list extended USERS-TO-SERVERS
 10 permit tcp host 192.168.10.5 host 192.168.30.10 eq 22
 20 deny   tcp 192.168.10.0 0.0.0.255 host 192.168.30.10 eq 22
 30 permit tcp 192.168.10.0 0.0.0.255 host 192.168.30.10 eq 443
 40 permit icmp 192.168.10.0 0.0.0.255 any echo
```

## 15.4. Cómo se evalúa: primera coincidencia

El router compara el paquete con las ACE **de arriba abajo**:

```text
¿Coincide con la ACE 10?  no → siguiente
¿Coincide con la ACE 20?  sí → aplicar su acción y DETENERSE
```

No sigue buscando una regla «mejor». La primera ACE que coincide decide.

Consecuencia: **el orden forma parte de la política**. En el ejemplo, si la ACE 20 (denegar SSH a toda LAN-A) estuviera antes que la 10, PC-ADMIN, que también pertenece a LAN-A, quedaría bloqueado.

## 15.5. Deny implícito

Toda ACL termina con una regla invisible:

```text
deny any  (IPv4: deny ip any any)
```

Si un paquete no coincide con ninguna ACE, se descarta. Consecuencias:

- una ACL con solo `deny` bloquea **todo** (lo denegado explícitamente y todo lo demás);
- toda ACL útil debe contener al menos un `permit`;
- hay que prever todo el tráfico legítimo, incluido el que no aparece en el requisito pero es necesario (DNS, DHCP, respuestas…).

Muchos administradores añaden un `deny ip any any` explícito al final: el efecto es el mismo, pero así aparece un **contador** de lo que se descarta.

## 15.6. Crear no es aplicar

Una ACL definida en la configuración **no filtra nada** hasta que se aplica en un punto concreto:

```text
R1(config)# interface GigabitEthernet0/0
R1(config-if)# ip access-group USERS-TO-SERVERS in
```

Reglas de aplicación en Cisco IOS:

- **una ACL por interfaz, por sentido y por protocolo** (una IPv4 de entrada, una IPv4 de salida, una IPv6 de entrada, una IPv6 de salida);
- aplicar una segunda ACL IPv4 en el mismo sentido **sustituye** a la primera;
- aplicar una ACL que no existe no bloquea nada (se comporta como si no hubiera filtro), pero en cuanto se cree empezará a actuar.

## 15.7. Entrada (*in*) y salida (*out*)

El sentido se define **desde el punto de vista de la interfaz del router**:

| Sentido | Qué paquetes evalúa |
|---|---|
| `in` | Los que **llegan** al router por esa interfaz, antes de consultar la tabla de routing |
| `out` | Los que **van a salir** por esa interfaz, después de la decisión de routing |

```text
paquete entra por G0/0
  → ACL in de G0/0          (si deny: descartado, sin consultar la tabla)
  → tabla de routing (LPM)  → interfaz de salida G0/1
  → ACL out de G0/1
  → sale hacia el next hop
```

`in` y `out` **no** significan «hacia dentro/fuera de la empresa». Para decidir hay que seguir el paquete y ver por qué interfaz entra y por cuál sale.

Una ACL `out` no filtra el tráfico **generado por el propio router** (por ejemplo, un `ping` lanzado desde su CLI). Si pruebas una ACL de salida haciendo ping desde el router, el resultado no demuestra nada.

## 15.8. Tipos de ACL IPv4

| Tipo | Criterios | Numeración clásica | Colocación orientativa |
|---|---|---|---|
| **Estándar** | Solo IP de **origen** | 1–99, 1300–1999 | Cerca del **destino** |
| **Extendida** | Protocolo, origen, destino, puertos y otros campos | 100–199, 2000–2699 | Cerca del **origen** |

Pueden ser **numeradas** o **nombradas**. Se recomiendan las nombradas: el nombre expresa la intención (`ADMIN-SOURCES`, `OUTSIDE-IN`), son más legibles y se editan fácilmente por número de secuencia.

## 15.9. Filtrar no siempre es lo único que hace una ACL

En estos apuntes una ACL aplicada a una interfaz **filtra**: `deny` significa que el paquete no pasa. Las ACL también se usan para **seleccionar** tráfico para otras funciones. En U10 verás que NAT usa una ACL para elegir qué direcciones se traducen; allí, un `deny` significa «no traducir», no «descartar». El significado de `permit`/`deny` depende del contexto en que se usa la ACL.

# 16. Wildcard

Para indicar en una ACL qué direcciones coinciden, Cisco no usa la máscara de subred, sino la **wildcard**. Parece la máscara escrita al revés, pero su significado es distinto y no deben confundirse. Este apartado explica qué indica cada bit, cómo calcularla para una red y los atajos `host` y `any`. La volverás a usar en U09 (OSPF) y en U10 (ACL de NAT).

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Máscara comodín** (*wildcard mask*) | ¿Qué bits de la dirección se comparan? | 0 = debe coincidir; 1 = no importa |
| **Cálculo** (*calculation*) | ¿Qué wildcard corresponde a un prefijo? | /26 → `0.0.0.63` |
| **`host`** | ¿Cómo indico una sola dirección? | `host 192.168.10.5` = `192.168.10.5 0.0.0.0` |
| **`any`** | ¿Cómo indico cualquier dirección? | `0.0.0.0 255.255.255.255` |

Escribir la máscara donde va la wildcard produce una ACE que IOS acepta sin avisar, pero con un significado completamente distinto.

## 16.1. Qué es

Las ACL IPv4 de Cisco no usan máscara de subred, sino **wildcard** (máscara comodín). Cada bit indica si ese bit de la dirección se compara:

| Bit wildcard | Significado |
|---|---|
| `0` | Este bit **debe coincidir** |
| `1` | Este bit **no importa** |

Es la lógica inversa de la máscara de subred, y conviene no mezclarlas: una wildcard no es «otra forma» de escribir una máscara.

## 16.2. Calcularla para una red

Para una red definida por un prefijo:

```text
wildcard = 255.255.255.255 − máscara
```

| Prefijo | Máscara | Wildcard | Ejemplo en ACE |
|---|---|---|---|
| /24 | 255.255.255.0 | 0.0.0.255 | `192.168.10.0 0.0.0.255` |
| /26 | 255.255.255.192 | 0.0.0.63 | `192.168.10.64 0.0.0.63` → .64–.127 |
| /28 | 255.255.255.240 | 0.0.0.15 | `192.168.10.16 0.0.0.15` → .16–.31 |
| /30 | 255.255.255.252 | 0.0.0.3 | `10.0.12.0 0.0.0.3` |
| /16 | 255.255.0.0 | 0.0.255.255 | `172.16.0.0 0.0.255.255` |

La dirección que acompaña a la wildcard debe ser la **dirección de red**. `192.168.10.70 0.0.0.63` funciona (IOS la corrige a .64), pero delata un razonamiento dudoso y puede no ser lo que se pretendía.

## 16.3. Atajos

| Palabra clave | Equivale a | Significado |
|---|---|---|
| `host 192.168.10.5` | `192.168.10.5 0.0.0.0` | Solo esa dirección |
| `any` | `0.0.0.0 255.255.255.255` | Cualquier dirección |

## 16.4. Error frecuente

Escribir la máscara donde va la wildcard:

```text
permit 192.168.10.0 255.255.255.0     ← INCORRECTO
```

Esa ACE ignora los tres primeros octetos y exige que el último sea `0`: coincide con `x.x.x.0` de cualquier red, no con LAN-A.

# 17. ACL estándar y control del acceso de administración

La ACL estándar es la más sencilla: solo mira la dirección de **origen**. Eso la hace útil para dos cosas: impedir que una red acceda a un destino concreto (colocándola cerca de ese destino) y, sobre todo, limitar desde qué equipos se puede administrar el router por SSH. Este apartado retoma el SSH del apartado 5.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **ACL estándar nombrada** (*named standard ACL*) | ¿Cómo filtro según el origen? | `ip access-list standard BLOCK-LAN-A` |
| **Colocación cerca del destino** (*placement near the destination*) | ¿Dónde se aplica para no bloquear de más? | R2 G0/2 `out` |
| **Control de acceso a VTY** (*`access-class`*) | ¿Quién puede abrir sesiones remotas al propio router? | `access-class ADMIN-SOURCES in` en `line vty` |

`ip access-group` (interfaz: tráfico que atraviesa el router) y `access-class` (líneas VTY: sesiones al propio router) no son intercambiables.

## 17.1. Configuración

```text
R2(config)# ip access-list standard BLOCK-LAN-A
R2(config-std-nacl)# 10 deny 192.168.10.0 0.0.0.255
R2(config-std-nacl)# 20 permit any
R2(config)# interface GigabitEthernet0/2
R2(config-if)# ip access-group BLOCK-LAN-A out
```

Requisito implementado: «LAN-A no puede acceder a la red SERVERS; el resto de redes, sí».

## 17.2. Por qué cerca del destino

Una ACL estándar solo ve el **origen**. Si se aplicara en R1 G0/0 `in`, LAN-A quedaría bloqueada hacia **todas** partes (LAN-B, Internet…), no solo hacia SERVERS. Colocándola en la interfaz que da a SERVERS (R2 G0/2 `out`), solo se filtra el tráfico que va a esa red.

```text
ACL estándar lejos del destino → bloquea más de lo pretendido
ACL estándar cerca del destino → afecta solo al destino protegido
```

Es una orientación, no una ley: se justifica siguiendo el recorrido del tráfico en la topología concreta.

## 17.3. ACL estándar en las líneas VTY

Una aplicación muy útil es limitar **desde dónde** se puede administrar el router:

```text
R1(config)# ip access-list standard ADMIN-SOURCES
R1(config-std-nacl)# permit host 192.168.10.5
R1(config-std-nacl)# permit 192.168.99.0 0.0.0.255
R1(config)# line vty 0 4
R1(config-line)# access-class ADMIN-SOURCES in
```

Ahora una sesión SSH solo se acepta si procede de PC-ADMIN o de la red de gestión; cualquier otro origen es rechazado por el deny implícito, aunque conozca el usuario y la contraseña.

| Orden | Dónde se aplica | Qué controla |
|---|---|---|
| `ip access-group NOMBRE in/out` | Interfaz | Tráfico que atraviesa o llega a esa interfaz |
| `access-class NOMBRE in` | Líneas VTY | Quién puede abrir una sesión remota (SSH) **al propio router** |

Recuerda aplicar la ACL en **todas** las líneas VTY que tenga el equipo (por ejemplo, `vty 0 4` y `vty 5 15`); si no, quedan líneas abiertas.

Precaución profesional: al aplicar `access-class` en remoto, si tu propia IP no está permitida, **cortas tu sesión** y quedas fuera. Antes de aplicarla, comprueba desde qué IP estás conectado y ten preparado un acceso por consola.

# 18. ACL extendidas

Las ACL extendidas permiten expresar políticas realistas: no solo **quién**, sino **hacia dónde** y **a qué servicio**. Este apartado recupera los puertos de U02, muestra un ejemplo completo basado en la matriz del apartado 15.2, explica por qué se colocan cerca del origen y trata dos asuntos que causan muchos fallos: el tráfico de retorno y el ICMP.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Criterios de coincidencia** (*match criteria*) | ¿Qué campos puede comprobar? | Protocolo, origen, destino, puertos |
| **Puerto de destino** (*destination port*) | ¿Cómo identifico el servicio? | `eq 443`, `eq 22`, `eq bootps` |
| **Colocación cerca del origen** (*placement near the source*) | ¿Dónde se aplica? | R1 G0/0 `in` |
| **Conexión establecida** (*`established`*) | ¿Cómo permito respuestas TCP sin abrir conexiones nuevas? | `permit tcp any 192.168.10.0 0.0.0.255 established` |
| **Tipos de ICMP** (*ICMP types*) | ¿Qué mensajes de diagnóstico dejo pasar? | `echo-reply`, `unreachable`, `time-exceeded` |

Las ACL de estos apuntes son **sin estado** (*stateless*): no recuerdan las conexiones, por eso el tráfico de retorno hay que pensarlo de forma explícita.

## 18.1. Qué pueden comprobar

Una ACL extendida puede combinar:

- **protocolo**: `ip`, `tcp`, `udp`, `icmp`…;
- **origen** y **destino** (con wildcard, `host` o `any`);
- **puertos** TCP/UDP de origen o destino;
- tipos de mensaje ICMP;
- otras opciones (por ejemplo, `established`).

Sintaxis general:

```text
{permit|deny} PROTOCOLO  ORIGEN WILDCARD [puerto]  DESTINO WILDCARD [puerto]  [opciones]
```

## 18.2. Recuperación de U02: IP identifica equipos, puertos identifican servicios

| Servicio | Protocolo | Puerto |
|---|---|---:|
| HTTP | TCP | 80 (`www`) |
| HTTPS | TCP | 443 |
| SSH | TCP | 22 |
| Telnet | TCP | 23 |
| DNS | UDP (y TCP) | 53 |
| DHCP | UDP | 67 servidor / 68 cliente |
| TFTP | UDP | 69 |

Un puerto solo tiene sentido con TCP o UDP. Por eso:

```text
permit ip  192.168.10.0 0.0.0.255 host 192.168.30.10 eq 443   ← no válido
permit tcp 192.168.10.0 0.0.0.255 host 192.168.30.10 eq 443   ← correcto
```

El puerto del servicio es, normalmente, el **puerto de destino** de la petición. El cliente usa un puerto de origen efímero (aleatorio y alto), por lo que casi nunca se filtra por puerto de origen en la petición.

Operadores: `eq` (igual), `neq`, `lt`, `gt`, `range 20 21`.

## 18.3. Ejemplo completo

Política de la matriz del apartado 15.2, aplicada en R1:

```text
R1(config)# ip access-list extended LAN-A-IN
R1(config-ext-nacl)# 10 permit tcp host 192.168.10.5 host 192.168.30.10 eq 22
R1(config-ext-nacl)# 20 deny   tcp 192.168.10.0 0.0.0.255 host 192.168.30.10 eq 22
R1(config-ext-nacl)# 30 permit tcp 192.168.10.0 0.0.0.255 host 192.168.30.10 eq 443
R1(config-ext-nacl)# 40 permit icmp 192.168.10.0 0.0.0.255 any echo
R1(config-ext-nacl)# 50 permit udp any any eq bootps
R1(config-ext-nacl)# 60 deny   ip any any
R1(config)# interface GigabitEthernet0/0
R1(config-if)# ip access-group LAN-A-IN in
```

Observa la ACE 50: sin ella, el deny final bloquearía los Discover de DHCP de los clientes de LAN-A. Un fallo típico de ACL es romper un servicio que nadie mencionó en el requisito.

## 18.4. Por qué cerca del origen

Como la extendida distingue destino y servicio, puede colocarse cerca del origen sin bloquear otros destinos legítimos. Así el tráfico no deseado se descarta antes de recorrer la red y consumir enlaces. En el ejemplo, `LAN-A-IN` en R1 G0/0 `in` detiene el SSH no autorizado antes de que cruce el enlace R1–R2.

## 18.5. El tráfico de retorno

Las ACL de Cisco que estás estudiando son **sin estado** (*stateless*): evalúan cada paquete de forma aislada, sin recordar que forma parte de una conexión permitida. Si una ACL se aplica en el sentido por el que **vuelven las respuestas**, hay que permitirlas explícitamente.

Para TCP existe la opción `established`:

```text
permit tcp any 192.168.10.0 0.0.0.255 established
```

Coincide con segmentos TCP que llevan el bit **ACK** o **RST** activo, es decir, que pertenecen a una conexión ya iniciada. Un segmento que intenta **abrir** una conexión (solo SYN) no coincide. Permite así las respuestas a conexiones iniciadas desde dentro sin permitir conexiones nuevas desde fuera.

Limitaciones: `established` solo sirve para TCP (no para UDP como DNS) y no comprueba realmente que exista la conexión: un atacante puede fabricar paquetes con ACK. Los **firewalls con estado** (*stateful*) mantienen una tabla de conexiones y resuelven este problema; son la herramienta profesional para el perímetro y quedan fuera de este módulo.

## 18.6. ICMP

ICMP transporta los mensajes de diagnóstico y de error de la red. Bloquearlo por completo dificulta el diagnóstico y puede romper funciones de red. La política debe decidir qué tipos permitir, por ejemplo:

```text
permit icmp any 192.168.10.0 0.0.0.255 echo-reply
permit icmp any 192.168.10.0 0.0.0.255 unreachable
permit icmp any 192.168.10.0 0.0.0.255 time-exceeded
```

# 19. Orden, edición y verificación de ACL

Una ACL casi nunca se escribe perfecta a la primera ni se queda igual para siempre. Este apartado trata lo que ocurre después de escribirla: cómo el orden puede anular reglas, cómo editarla sin dejar la interfaz desprotegida y cómo demostrar, con contadores y pruebas, que hace exactamente lo que dice la política.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Regla sombreada** (*shadowed rule*) | ¿Hay ACE que nunca llegan a evaluarse? | `deny ip any any` antes de un `permit` |
| **Número de secuencia** (*sequence number*) | ¿Cómo inserto o borro una ACE sin reescribir la lista? | `15 permit ...`, `no 40` |
| **Contadores** (*match counters*) | ¿Qué ACE está decidiendo? | `(4 matches)` |
| **Comprobación de la aplicación** (*applied ACL check*) | ¿En qué interfaz y en qué sentido está? | `show ip interface g0/0` |
| **Prueba positiva y negativa** (*positive / negative test*) | ¿Permite lo que debe y bloquea lo que debe? | HTTPS funciona; SSH falla |
| **Cambio seguro** (*safe change*) | ¿Cómo cambio sin quedarme sin servicio ni sin acceso? | Copia de seguridad, consola disponible, plan de vuelta atrás |

Un contador a cero es un dato, no un diagnóstico.

## 19.1. Reglas sombreadas (*shadowing*)

```text
10 deny   ip any any
20 permit tcp 192.168.10.0 0.0.0.255 host 192.168.30.10 eq 443
```

La ACE 20 nunca se evalúa: todo coincide antes con la 10. Una ACE general situada antes que otra más específica que cae dentro de ella la anula. Patrón habitual: **específico primero, general después**.

## 19.2. Editar con números de secuencia

En una ACL nombrada cada ACE tiene un número (10, 20, 30… por defecto). Se puede insertar o eliminar una entrada sin reescribir la lista:

```text
R1(config)# ip access-list extended LAN-A-IN
R1(config-ext-nacl)# 15 permit tcp host 192.168.10.6 host 192.168.30.10 eq 22
R1(config-ext-nacl)# no 40
```

Borrar la ACL completa y volver a escribirla mientras está aplicada deja la interfaz sin filtro, o con un filtro parcial, durante el proceso. La edición por secuencia es más segura.

## 19.3. Contadores

```text
R1# show access-lists LAN-A-IN
Extended IP access list LAN-A-IN
    10 permit tcp host 192.168.10.5 host 192.168.30.10 eq 22 (12 matches)
    20 deny tcp 192.168.10.0 0.0.0.255 host 192.168.30.10 eq 22 (4 matches)
    30 permit tcp 192.168.10.0 0.0.0.255 host 192.168.30.10 eq 443 (187 matches)
    40 permit icmp 192.168.10.0 0.0.0.255 any echo (8 matches)
    50 permit udp any any eq bootps (3 matches)
    60 deny ip any any (0 matches)
```

Los contadores son evidencia de **qué ACE está decidiendo**. Para una prueba concreta: `clear access-list counters`, generar el tráfico, volver a mirar qué contador ha subido.

Un contador a cero **no** demuestra que la ACE esté mal. Puede significar que:

- no se generó ese tráfico;
- una ACE anterior coincide antes;
- la ACL no está aplicada, o lo está en otra interfaz o sentido;
- el tráfico sigue otro camino y nunca pasa por esa interfaz.

## 19.4. Comprobar dónde está aplicada

```text
R1# show ip interface GigabitEthernet0/0
GigabitEthernet0/0 is up, line protocol is up
  Internet address is 192.168.10.1/24
  ...
  Outgoing access list is not set
  Inbound  access list is LAN-A-IN
```

## 19.5. Verificación positiva y negativa

Una ACL implementa lo que **se permite** y lo que **se deniega**. Hay que demostrar las dos cosas:

| Prueba | Resultado esperado | Qué demuestra |
|---|---|---|
| PC de LAN-A → `https://192.168.30.10` | Funciona | La ACL no ha roto el servicio legítimo |
| PC de LAN-A → `ssh 192.168.30.10` | Falla | El bloqueo funciona |
| PC-ADMIN → `ssh 192.168.30.10` | Funciona | La excepción está bien ordenada |
| Contadores 10, 20, 30 | Suben según cada prueba | Cada resultado lo produce la ACE prevista |

Comprobar solo que algo falla no basta: una ACL que bloquea todo también «pasa» la prueba negativa.

## 19.6. Cambios seguros

Antes: copia de seguridad de la configuración, lista del tráfico legítimo, plan de vuelta atrás y, si se trabaja en remoto, acceso por consola disponible.

Después: prueba positiva, prueba negativa, contadores y documentación del cambio.

# 20. DMZ: publicar servicios sin exponer la red interna

Este apartado integra todo lo anterior en un caso profesional: publicar un servidor web sin poner en riesgo la red interna. La red se organiza en tres zonas con distinta confianza, la política se escribe como matriz, se implementa con una ACL de entrada por zona y se demuestra con pruebas. Es un escenario enrutado de laboratorio, **sin NAT**; en U10 esta misma DMZ se publicará con NAT.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Zona desmilitarizada** (*DMZ, demilitarized zone*) | ¿Dónde coloco los servidores accesibles desde fuera? | 172.16.50.0/24 |
| **Zonas de confianza** (*INSIDE / DMZ / OUTSIDE*) | ¿Qué nivel de confianza tiene cada red? | Alto / medio / bajo |
| **Matriz de política entre zonas** (*inter-zone policy matrix*) | ¿Quién puede iniciar qué comunicación? | OUTSIDE → WEB, TCP 80 y 443: permitir |
| **ACL de entrada por zona** (*per-zone inbound ACL*) | ¿Cómo se implementa? | `INSIDE-IN`, `DMZ-IN`, `OUTSIDE-IN` |
| **Sin estado frente a con estado** (*stateless vs. stateful*) | ¿Qué límites tiene hacerlo con ACL? | Retorno UDP; en producción, firewall con estado |

La DMZ no es una «red abierta»: sus servidores aceptan conexiones desde fuera, pero no pueden iniciarlas hacia INSIDE.

## 20.1. El problema

Una organización quiere que su servidor web sea accesible desde Internet. Si ese servidor está en la red interna y un atacante lo compromete, tendrá acceso directo a los equipos de los usuarios.

La solución clásica es una **DMZ** (*demilitarized zone*): una red intermedia, separada de la red interna, donde se colocan los servidores que deben recibir conexiones desde el exterior.

## 20.2. Modelo de tres zonas

```text
                 OUTSIDE (Internet / ISP)
                 203.0.113.0/30
                        │ G0/2 .1
                   ┌────┴────┐
   INSIDE          │  R-EDGE │          DMZ
192.168.10.0/24 ───┤G0/0  G0/1├─── 172.16.50.0/24
   (usuarios)  .1  └─────────┘  .1    WEB 172.16.50.10
   ADMIN .5
```

| Zona | Nivel de confianza | Contiene |
|---|---|---|
| INSIDE | Alto | Usuarios y servicios internos |
| DMZ | Medio | Servidores accesibles desde fuera |
| OUTSIDE | Bajo | Internet, redes no controladas |

El principio es: **cada zona solo puede iniciar las comunicaciones que la política necesita**, y un servidor comprometido en la DMZ no debe poder iniciar conexiones hacia INSIDE.

## 20.3. Matriz de política

| # | Origen | Destino | Servicio | Acción |
|---|---|---|---|---|
| 1 | OUTSIDE | WEB (DMZ) | TCP 80, 443 | permitir |
| 2 | OUTSIDE | INSIDE | nuevas conexiones | denegar |
| 3 | INSIDE | WEB (DMZ) | TCP 443 | permitir |
| 4 | ADMIN (INSIDE) | WEB (DMZ) | TCP 22 | permitir |
| 5 | DMZ | INSIDE | nuevas conexiones | denegar |
| 6 | INSIDE | OUTSIDE | cualquiera | permitir |
| 7 | DMZ | OUTSIDE | nuevas conexiones | denegar (solo respuestas) |

## 20.4. Implementación con ACL extendidas

Una ACL de **entrada** en cada interfaz del router controla qué puede iniciar cada zona.

```text
ip access-list extended INSIDE-IN
 10 permit tcp 192.168.10.0 0.0.0.255 host 172.16.50.10 eq 443
 20 permit tcp host 192.168.10.5 host 172.16.50.10 eq 22
 30 deny   ip 192.168.10.0 0.0.0.255 172.16.50.0 0.0.0.255
 40 permit ip 192.168.10.0 0.0.0.255 any
!
ip access-list extended DMZ-IN
 10 permit tcp host 172.16.50.10 eq 443 any established
 20 permit tcp host 172.16.50.10 eq www any established
 30 permit tcp host 172.16.50.10 eq 22 host 192.168.10.5 established
 40 deny   ip any any
!
ip access-list extended OUTSIDE-IN
 10 permit tcp any host 172.16.50.10 eq www
 20 permit tcp any host 172.16.50.10 eq 443
 30 permit tcp any 192.168.10.0 0.0.0.255 established
 40 permit icmp any 192.168.10.0 0.0.0.255 echo-reply
 50 permit icmp any 192.168.10.0 0.0.0.255 unreachable
 60 deny   ip any any
!
interface GigabitEthernet0/0
 ip access-group INSIDE-IN in
interface GigabitEthernet0/1
 ip access-group DMZ-IN in
interface GigabitEthernet0/2
 ip access-group OUTSIDE-IN in
```

Cómo se relaciona cada requisito con las ACE:

- **Req. 1:** `OUTSIDE-IN` 10 y 20. Las respuestas del servidor salen gracias a `DMZ-IN` 10 y 20 (`established`).
- **Req. 2:** `OUTSIDE-IN` 30 solo admite respuestas TCP hacia INSIDE; un SYN nuevo desde fuera cae en el deny 60.
- **Req. 3 y 4:** `INSIDE-IN` 10 y 20; las respuestas vuelven por `DMZ-IN` 10 y 30.
- **Req. 5 y 7:** la DMZ solo puede enviar respuestas TCP de sus servicios; cualquier conexión que el servidor intente iniciar cae en `DMZ-IN` 40.
- **Req. 6:** `INSIDE-IN` 40; sus respuestas entran por `OUTSIDE-IN` 30, 40 y 50.
- `INSIDE-IN` 30 va **antes** que la 40: si no, la 40 permitiría a INSIDE cualquier servicio de la DMZ.
- `INSIDE-IN` 40 solo acepta orígenes de la red interna: un paquete con IP de origen falsificada que entre por G0/0 se descarta.
- Si R-EDGE fuese también servidor DHCP o relay para INSIDE, habría que añadir antes de la 40 una ACE `permit udp any any eq bootps`: el Discover sale con origen `0.0.0.0`, que no pertenece a 192.168.10.0/24 (ver 18.3).

## 20.5. Verificar la política

| Prueba | Esperado |
|---|---|
| Cliente externo → `http://172.16.50.10` | Funciona |
| Cliente externo → `ssh 172.16.50.10` | Falla |
| Cliente externo → ping a un PC de INSIDE | Falla |
| PC de INSIDE → `https://172.16.50.10` | Funciona |
| PC-ADMIN → `ssh 172.16.50.10` | Funciona |
| Otro PC de INSIDE → `ssh 172.16.50.10` | Falla |
| Desde WEB → ping o conexión a un PC de INSIDE | Falla |
| PC de INSIDE → servidor externo por HTTPS | Funciona |

Y en cada caso, qué contador sube.

## 20.6. Límites de este escenario

- **Sin NAT.** En este laboratorio el router del proveedor tiene rutas hacia INSIDE y DMZ. En la realidad, las redes privadas no se enrutan en Internet: la publicación se hace con NAT, que estudiarás en U10.
- **Tráfico UDP de retorno.** Con ACL sin estado, las respuestas DNS (UDP 53) de servidores externos hacia INSIDE necesitarían una regla adicional que abre más de lo deseable. Es uno de los motivos por los que el perímetro real se protege con firewalls con estado.
- **Doble protección.** Muchas arquitecturas usan dos firewalls o un firewall dedicado con zonas. El modelo de tres zonas y la matriz de política son los mismos.

# 21. Diagnóstico integrado: seguir el paquete

El mismo síntoma («el cliente no accede al servidor») puede deberse al host, a una interfaz, a una ruta, a una ACL, al DHCP o al propio servicio. Este apartado reúne toda la unidad en un único recorrido ordenado del paquete, con una tabla de casos típicos y unos principios de trabajo. Es la base de los repasos y del examen integrador.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Recorrido del paquete** (*packet path*) | ¿En qué orden compruebo? | Host → interfaz → ACL `in` → ruta → ACL `out` → … → retorno |
| **Casos típicos** (*typical cases*) | ¿Qué evidencia apunta a qué causa? | Sube el contador de un `deny ... eq 443` → la ACL bloquea el servicio |
| **Principios de trabajo** (*working principles*) | ¿Cómo evito cambios a ciegas? | Un cambio cada vez, verificando después |

Routing y ACL se verifican juntos: `ACL permit + sin ruta = sin conectividad`.

## 21.1. Recorrido completo

Un mismo síntoma («el cliente no accede al servidor») puede tener causas en dominios distintos. El modelo que permite ordenarlas es el recorrido real del paquete:

```text
host: IP, máscara, gateway (¿DHCP correcto?)
 → interfaz de entrada del router (estado, IP)
 → ACL in de esa interfaz
 → tabla de routing: ruta elegida por LPM
 → next hop alcanzable (ARP/ND)
 → ACL out de la interfaz de salida
 → siguientes routers (repetir)
 → servicio del destino
 → RETORNO: repetir todo en sentido contrario
```

## 21.2. Casos típicos

| Síntoma | Evidencia clave | Causa probable |
|---|---|---|
| Ping falla; `traceroute` se detiene en R1 | R1 no tiene `S` hacia el destino | Falta ruta de ida |
| La petición llega (contadores/debug en destino) pero no hay respuesta | `show ip route <origen>` en el router remoto: sin ruta | Falta ruta de retorno |
| Ruta configurada pero no aparece en la tabla | Next hop fuera de las redes conectadas | Next hop incorrecto o interfaz caída |
| Ping funciona, HTTPS no | Contador de un `deny tcp ... eq 443` sube | ACL extendida bloquea el servicio |
| HTTPS no funciona, contadores de la ACL a 0 | `show ip interface`: ACL en otra interfaz o sentido | Placement o sentido incorrectos |
| Cliente con IP 169.254.x.x | Helper ausente, en otra interfaz o sin ruta al servidor | Fallo de relay o de routing hacia el servidor DHCP |
| El respaldo no entra al caer el camino remoto | La ruta principal sigue instalada | Limitación de la floating static |
| IPv4 funciona, IPv6 no | `show ipv6 route` sin la ruta, o falta `ipv6 unicast-routing` | La pila IPv6 no está configurada igual |

## 21.3. Principios

- Una ruta correcta no descarta una ACL, y una ACL correcta no descarta un fallo de routing: `ACL permit + sin ruta = sin conectividad`.
- No se modifica una ACL antes de demostrar que el paquete llega al punto donde está aplicada.
- Un cambio cada vez, verificando después.
- La respuesta de una IA o de un compañero es una hipótesis; la evidencia la dan las salidas de los equipos y las pruebas.

# 22. Profundización opcional

Este apartado es **opcional**: amplía la unidad para quien quiera ir más allá, pero no es necesario para seguir U09 y U10. Aplica a IPv6 lo aprendido sobre ACL y presenta algunas herramientas profesionales de mantenimiento y de protección del acceso.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|

| **Renumerar una ACL** (*resequence*) | ¿Cómo hago hueco para nuevas ACE? | `ip access-list resequence NOMBRE 10 10` |
| **Bloqueo de inicio de sesión** (*login block-for*) | ¿Cómo freno los intentos repetidos de acceso? | `login block-for 120 attempts 3 within 60` |
| **Gestión programática** (*NETCONF / RESTCONF*) | ¿Cómo se administran muchos equipos a la vez? | Plantillas y automatización |

## 22.1. ACL IPv6

El razonamiento es el mismo, con diferencias de sintaxis:

```text
R1(config)# ipv6 access-list LAN-A-V6-IN
R1(config-ipv6-acl)# permit tcp 2001:db8:acad:10::/64 host 2001:db8:acad:30::10 eq 443
R1(config-ipv6-acl)# deny ipv6 any any
R1(config)# interface GigabitEthernet0/0
R1(config-if)# ipv6 traffic-filter LAN-A-V6-IN in
```

- No hay ACL estándar/extendida: todas son nombradas y pueden filtrar como una extendida.
- Se usan prefijos (`/64`), no wildcard.
- Se aplican con `ipv6 traffic-filter`, no con `ip access-group`.
- Antes del deny implícito final existen permisos implícitos para *Neighbor Discovery* (NS/NA), necesarios para que IPv6 funcione. Si escribes tu propio `deny ipv6 any any` al final, esos permisos implícitos dejan de alcanzarse: debes permitir ND explícitamente.
- ICMPv6 es imprescindible (ND, RA, *Packet Too Big*): no se bloquea en bloque.

## 22.2. Otras herramientas

- `ip access-list resequence NOMBRE 10 10`: renumera una ACL para dejar huecos donde insertar.
- `login block-for 120 attempts 3 within 60`: bloquea temporalmente el acceso tras varios intentos fallidos.
- Gestión programática (NETCONF/RESTCONF) y herramientas de automatización: la administración profesional moderna tiende a configurar muchos equipos a la vez desde plantillas, pero los conceptos de esta unidad no cambian.

# Síntesis de la unidad

1. El router une redes distintas: mantiene las IP de origen y destino y reconstruye la trama en cada salto.
2. Arranca con POST → bootstrap → IOS (flash) → startup-config (NVRAM); trabaja con la running-config en RAM. Lo que no se guarda se pierde.
3. La administración remota se hace por SSH v2 con usuarios locales; Telnet expone las credenciales.
4. Una interfaz `up/up` con IP genera rutas `C` y `L`. Las redes remotas necesitan rutas.
5. El router elige primero la ruta más específica (LPM); la AD solo desempata entre fuentes del mismo prefijo.
6. Una ruta estática necesita un next hop alcanzable, y toda comunicación necesita ida **y** retorno.
7. La ruta por defecto es la menos específica; la floating static es un respaldo con AD mayor que no detecta fallos remotos.
8. IPv6 aplica el mismo modelo; un next hop link-local exige indicar la interfaz.
9. El router puede ser servidor DHCP y, con `ip helper-address` en la interfaz de los clientes, relay hacia un servidor remoto.
10. Una ACL traduce una política: primera coincidencia, deny implícito, una ACL por interfaz, sentido y protocolo.
11. Estándar: solo origen, cerca del destino. Extendida: protocolo, origen, destino y puertos, cerca del origen.
12. Una política se demuestra con pruebas positivas **y** negativas y con contadores.
13. Una DMZ separa los servicios públicos de la red interna; con ACL sin estado, `established` permite respuestas TCP sin abrir conexiones nuevas.

> **Routing decide por dónde puede ir el paquete; la ACL decide si puede pasar. Ninguna de las dos se verifica sin seguir el paquete de ida y de vuelta.**

# Anexo B. Glosario

| Término | Significado |
|---|---|
| ACE (*Access Control Entry*) | Cada regla de una ACL: condición + acción |
| ACL (*Access Control List*) | Lista ordenada de ACE para filtrar o seleccionar tráfico |
| Administrative distance (AD) | Preferencia de la fuente de una ruta; menor es mejor |
| Bootstrap | Programa en ROM que inicia la carga del IOS |
| Connected route (C) | Red de una interfaz operativa con IP |
| Default route | Ruta `0.0.0.0/0` o `::/0`; se usa si no hay coincidencia más específica |
| DHCP relay | Función que reenvía peticiones DHCP a un servidor de otra red |
| DMZ | Red intermedia para servidores accesibles desde el exterior |
| Established | Opción de ACL que coincide con segmentos TCP con ACK o RST |
| Flash | Memoria no volátil donde reside la imagen IOS |
| Floating static route | Ruta estática de respaldo con AD mayor que la principal |
| Gateway of last resort | Next hop de la ruta por defecto |
| giaddr | Campo DHCP con la IP de la interfaz del relay que recibió la petición |
| Host route | Ruta a un único host (`/32` en IPv4, `/128` en IPv6) |
| Implicit deny | Denegación final invisible de toda ACL |
| Inbound / outbound | Evaluación al entrar / al salir por una interfaz |
| Local route (L) | Ruta `/32` o `/128` a la dirección propia del router |
| Longest prefix match (LPM) | Selección de la ruta coincidente más específica |
| Next hop | Dirección del siguiente router al que se entrega el paquete |
| NVRAM | Memoria no volátil donde se guarda la startup-config |
| POST | Autocomprobación del hardware al arrancar |
| Return path | Camino de las respuestas hacia el origen |
| Running-config / startup-config | Configuración activa (RAM) / guardada (NVRAM) |
| SSH | Protocolo de administración remota cifrada (TCP 22) |
| Stateless / stateful | Sin memoria de conexiones / con tabla de conexiones |
| Static route (S) | Ruta configurada manualmente |
| VTY | Líneas virtuales para sesiones remotas |
| Wildcard | Patrón de bits de ACL: 0 debe coincidir, 1 no importa |
