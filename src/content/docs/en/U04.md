> **Guiding question:** How do we design and verify an IPv4 addressing plan that lets hosts correctly decide which destinations are local, which require a gateway, and how their network parameters should be configured?

In U03 we studied the infrastructure required for a link to exist. Now we add the **IPv4 logical organization**.

The goal of this unit is not to memorize subnetting tricks. You must learn a procedure you can **explain, verify, document, and use to troubleshoot errors**.

The progression is:

```text
read a configuration
→ interpret address and prefix
→ calculate boundaries
→ determine membership
→ decide local/remote
→ divide address space
→ choose sizes
→ design with VLSM
→ summarize with CIDR when appropriate
→ document
→ configure
→ verify
→ troubleshoot
```

# 1. Reading an IPv4 configuration

Before calculating a network, we must understand the information in front of us. When we run `ipconfig /all` on Windows or `ip address` on Linux, the system shows several values. Each one has a different job, and we should not mix them up: the **address** and the **prefix** together define which network the host belongs to; the **gateway** is the "door" to other networks and must be inside that network; **DNS** translates names and can be on any network the host can reach.

This section teaches you to **read** those values, recognize some special address types, and know which tool shows each item. Checking whether they are coherent comes later.

| Concept | Question it answers | Example |
|---|---|---|
| **IPv4 address** (*dirección IPv4*) | What logical identifier does this interface have? | `192.168.10.25` |
| **Prefix length / subnet mask** (*prefijo / máscara*) | Which part of the address identifies the network? Which destinations are local? | `/24` = `255.255.255.0` |
| **Default gateway** (*puerta de enlace predeterminada*) | Who do I hand non-local traffic to? | `192.168.10.1` |
| **DNS server** (*servidor DNS*) | Who translates names into IP addresses? | `192.168.10.53` |
| **Inspection tools** (*herramientas de consulta*) | Where do I see these values on each system? | `ipconfig /all`, `ip address` |
| **Special-purpose addresses** (*rangos especiales*) | Is this address private, loopback, self-assigned…? | `127.0.0.1`, `169.254.x.x` |

> Do not confuse **reading** with **validating**: seeing values on screen does not prove they are correct.

Example:

```text
IPv4:    192.168.10.25
Prefix:  /24
Gateway: 192.168.10.1
DNS:     192.168.10.53
```

These four values answer different questions.

## 1.1. IPv4 address

An IPv4 address logically identifies an interface within the IPv4 address space.

IPv4 uses **32 bits**, usually represented as four decimal octets:

```text
192.168.10.25
```

An address should not be interpreted by itself. To determine its network, we also need its prefix:

```text
192.168.10.25/24
```

## 1.2. Prefix and subnet mask

The **prefix length** tells us how many bits belong to the network portion.

```text
/24
→ 24 bits describe the network prefix
→ 8 bits remain for positions inside the block
```

The same information can be represented as a **subnet mask**:

```text
/24
=
255.255.255.0
```

You should not infer the mask by looking only at the first octet of the address.

## 1.3. Default gateway

The **default gateway** is the next hop a host uses for traffic destined for networks it does not consider local.

```text
gateway
≠
Internet
```

The gateway is normally a router interface directly reachable from the host's local network.

## 1.4. DNS

A DNS server resolves names such as:

```text
www.example.com
```

into IP addresses.

Do not confuse:

```text
DNS
≠
gateway
```

DNS resolves names. The gateway participates in forwarding traffic toward other networks.

## 1.5. Inspection tools

Each tool provides different evidence. Before running a command, know which question it answers:

| Tool | System | Evidence it provides |
|---|---|---|
| `ipconfig /all` | Windows | IP, mask, gateway, DNS, MAC, whether DHCP is used, and lease details |
| `Get-NetIPConfiguration` | Windows (PowerShell) | Per-interface summary: IP, gateway, and DNS |
| `route print` | Windows | Host routing table (local network, default route) |
| `arp -a` | Windows / Linux | ARP cache: which local IPs already have a known MAC |
| `ip address` | Linux | Addresses and prefixes on each interface |
| `ip route` | Linux | Host routes and default route (`default via …`) |
| `ip neigh` | Linux | Known IPv4 neighbors (equivalent to the ARP cache) |
| `resolvectl status` or `/etc/resolv.conf` | Linux | DNS servers the system uses |

### Windows

```text
ipconfig /all
Get-NetIPConfiguration
route print
arp -a
```

### Linux

```text
ip address
ip route
ip neigh
resolvectl status
```

The goal is not to memorize every option, but to know **what evidence each tool can provide**.

## 1.6. Reading is not the same as validating

Consider:

```text
IPv4:    192.168.20.37
Prefix:  /27
Gateway: 192.168.20.1
DNS:     192.168.50.53
```

We can read these values, but we do not yet know whether all of them are coherent.

We need to answer questions such as:

- Which network contains `192.168.20.37/27`?
- Does the gateway belong to that network?
- Can the DNS server be in another network?
- If it is remote, is there a route to reach it?

We will solve this case in Section 5.7, once we know how to calculate the network.

> **Key idea:** configuration output contains observable facts. Deciding whether the configuration is correct requires interpreting those facts.

## 1.7. Address ranges you should recognize

When reading a configuration, it helps to recognize some reserved ranges at a glance. Knowing that an address is private, loopback, or self-assigned is already troubleshooting information.

| Range | Name | What it means when you see it |
|---|---|---|
| `10.0.0.0/8` | Private (RFC 1918) | Internal network; not routed on the Internet without NAT (U10) |
| `172.16.0.0/12` (from `172.16.0.0` to `172.31.255.255`) | Private (RFC 1918) | Internal network |
| `192.168.0.0/16` | Private (RFC 1918) | Internal network (common at home and in labs) |
| `127.0.0.0/8` | Loopback | The host itself (`127.0.0.1`); never leaves the host |
| `169.254.0.0/16` | Link-local / APIPA | The host requested DHCP and **got no answer**; it assigned itself an address |
| `0.0.0.0` | Unspecified address | "I have no address yet" (e.g., a DHCP client starting up) or, as `0.0.0.0/0`, "any destination" (default route) |
| `255.255.255.255` | Limited broadcast | All hosts on the local link |
| `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24` | Documentation (RFC 5737) | Example "public" addresses for manuals and labs |

A host with `169.254.x.x` is not necessarily "offline": it has a link, but it has not received configuration from a DHCP server (Section 12.8).

# 2. Useful binary, masks, and prefixes

Masks and prefixes are really a **bit pattern**: ones that mark the network part and zeros that mark the host part. To understand why `192.168.10.70/26` belongs to network `192.168.10.64`, we need to look at that pattern, at least in the octet where it changes.

This section does not expect you to keep converting full addresses to binary. Binary explains **the foundation** (logical AND); afterward we will use the block-size method, which is faster and gives the same result.

| Concept | Function | Example |
|---|---|---|
| **Octet** (*octeto*) | Group of 8 bits; value 0 to 255 | `192` |
| **Binary place values** (*pesos binarios*) | Value of each bit in an octet | `128 64 32 16 8 4 2 1` |
| **Subnet mask** (*máscara de subred*) | Contiguous ones for the network, zeros for the host | `255.255.255.192` |
| **Prefix length** (*longitud de prefijo*) | Number of ones in the mask | `/26` |
| **Bitwise AND** (*AND lógico*) | IP AND mask operation that gives the network address | `70 AND 192 = 64` |
| **Classful addressing** (*direccionamiento con clases*) | Historical system that inferred the mask from the first octet | **Do not use** for calculations |

> Do not confuse the **prefix** (an explicit value that accompanies the address) with the old **class** (a historical rule that no longer applies).

## 2.1. Binary place values

The place values in one octet are:

```text
128 64 32 16 8 4 2 1
```

Example:

```text
192 = 128 + 64
    = 11000000
```

```text
25 = 16 + 8 + 1
   = 00011001
```

Binary is a **tool for understanding** how masks work. You do not need to convert all 32 bits every time.

## 2.2. Common masks

| Prefix | Subnet mask | Host bits |
|---:|---|---:|
| /24 | 255.255.255.0 | 8 |
| /25 | 255.255.255.128 | 7 |
| /26 | 255.255.255.192 | 6 |
| /27 | 255.255.255.224 | 5 |
| /28 | 255.255.255.240 | 4 |
| /29 | 255.255.255.248 | 3 |
| /30 | 255.255.255.252 | 2 |

`/31` and `/32` exist and have real uses, but they are not the focus of the first calculations in this unit.

Because a mask is a run of **contiguous** ones followed by zeros, a mask octet can only be:

```text
0, 128, 192, 224, 240, 248, 252, 254, 255
```

A "mask" such as `255.255.255.200` is not valid.

## 2.3. Prefix boundaries do not have to match decimal dots

Example:

```text
192.168.10.25/26
```

`/26` means:

```text
24 full bits in the first three octets
+
2 bits in the fourth octet
```

The network/host boundary can be inside an octet.

## 2.4. Logical AND

A network address can be obtained with:

```text
IP address
AND
subnet mask
=
network address
```

Simplified example using the fourth octet:

```text
IP:       70 = 01000110
Mask:    192 = 11000000
AND:      64 = 01000000
```

Therefore, for `192.168.10.70/26`:

```text
network = 192.168.10.64
```

Understanding AND explains the foundation. For faster work, we will also use the **block-size method**.

## 2.5. Do not use historical classes as a calculation method

This is not valid reasoning:

```text
192.x.x.x
→ always /24
```

Modern networks use:

```text
address + explicit prefix
```

Example:

```text
192.168.10.25/26
```

is a `/26` network even though the address begins with `192`.

# 3. Network address, broadcast, host range, and capacity

An IPv4 subnet is a **block of consecutive addresses**. Knowing its mask is not enough to work with it: we need to know where it starts, where it ends, which addresses we can give to devices, and how many fit. These four values appear in every addressing plan, in every DHCP server configuration, and in every route.

The four pieces are related: the first address identifies the network, the last one is the broadcast, the addresses in between are the hosts, and capacity depends on the number of host bits.

| Concept | What it is | Example for `192.168.10.64/26` |
|---|---|---|
| **Network address** (*dirección de red*) | First address in the block; identifies the network | `192.168.10.64` |
| **Broadcast address** (*dirección de broadcast*) | Last address in the block; reaches all hosts in the subnet | `192.168.10.127` |
| **Host range** (*rango de hosts*) | Addresses that can be assigned to interfaces | `192.168.10.65`–`192.168.10.126` |
| **Capacity / usable hosts** (*capacidad*) | How many hosts fit: `2^h − 2` | 62 |

> Common mistake: assigning the network address or the broadcast address to a device. In a conventional subnet, neither is valid for a host.

## 3.1. Network address

The **network address** represents the block.

Example:

```text
192.168.10.64/26
```

The address `192.168.10.64` identifies that network.

## 3.2. Broadcast

In a conventional IPv4 subnet, the last address in the block is the **broadcast address**.

For:

```text
192.168.10.64/26
```

broadcast is:

```text
192.168.10.127
```

## 3.3. Host range

In the conventional cases used first in this unit:

```text
first host = network + 1
last host = broadcast - 1
```

Example:

```text
Network:    192.168.10.64/26
First host: 192.168.10.65
Last host:  192.168.10.126
Broadcast:  192.168.10.127
```

## 3.4. Capacity

If `h` bits remain for hosts:

```text
total addresses = 2^h
```

For conventional subnets in this unit:

```text
usable hosts = 2^h - 2
```

Example `/26`:

```text
h = 6
2^6 = 64 addresses
64 - 2 = 62 usable hosts
```

## 3.5. Complete example

Calculate `172.16.5.140/27`.

Mask:

```text
/27 = 255.255.255.224
```

Block size:

```text
256 - 224 = 32
```

Fourth-octet boundaries:

```text
0, 32, 64, 96, 128, 160, 192, 224
```

`140` falls between `128` and `159`.

Result:

```text
Network:    172.16.5.128/27
Broadcast:  172.16.5.159
First host: 172.16.5.129
Last host:  172.16.5.158
Capacity:   30 hosts
```

> **Key idea:** calculating a subnet means more than finding the mask. We must identify its boundaries and capacity.

# 4. Block-size method and subnet membership

Logical AND always works, but it is slow for everyday work. The **block-size method** takes advantage of a simple property: for a given prefix, every subnet has the same size and starts at a multiple of that size. If we know the block size, we only need to find which two multiples the address falls between.

This method also answers the **membership** question: two addresses are in the same subnet if they fall inside the same block.

| Concept | Question it answers | Example with `/26` |
|---|---|---|
| **Interesting octet** (*octeto variable*) | Which octet contains the network/host boundary? | The fourth (mask `192`) |
| **Block size** (*tamaño de bloque*) | How often does a new subnet start? | `256 − 192 = 64` |
| **Subnet boundaries** (*límites válidos*) | Where can a subnet of this size start? | `0, 64, 128, 192` |
| **Subnet membership** (*pertenencia*) | Are two addresses in the same block? | `.20` and `.50` yes; `.20` and `.70` no |

> Membership depends on **IP address + prefix**, not on addresses "looking similar."

## 4.1. Block size

For `/26`:

```text
variable-octet mask = 192
block size = 256 - 192 = 64
```

The boundaries are:

```text
0
64
128
192
```

## 4.2. Locating an address

For:

```text
192.168.10.70/26
```

`70` falls in:

```text
64–127
```

Therefore:

```text
Network:   192.168.10.64/26
Broadcast: 192.168.10.127
Hosts:     192.168.10.65–126
```

## 4.3. Stable procedure

```text
prefix
→ subnet mask
→ variable octet
→ block size
→ interval
→ network
→ broadcast
→ host range
```

## 4.4. Membership

Consider:

```text
192.168.10.20/26
192.168.10.50/26
```

Both belong to:

```text
192.168.10.0/26
```

But:

```text
192.168.10.70/26
```

belongs to:

```text
192.168.10.64/26
```

Two addresses can look close and still belong to different networks.

## 4.5. Common error: “the first three octets match”

```text
192.168.10.20/26
192.168.10.70/26
```

share `192.168.10`, but they are **not** in the same subnet.

Membership depends on:

```text
IP address + prefix
```

not on decimal appearance.

## 4.6. When the variable octet is not the fourth

The method is the same when the boundary falls in another octet. Only **where** we apply the block size changes.

Calculate `172.16.45.200/20`:

```text
/20 = 255.255.240.0
variable octet = the third (mask 240)
block size = 256 - 240 = 16
third-octet boundaries: 0, 16, 32, 48, 64, ...
45 falls between 32 and 47
```

Result:

```text
Network:    172.16.32.0/20
Broadcast:  172.16.47.255
First host: 172.16.32.1
Last host:  172.16.47.254
Capacity:   2^12 - 2 = 4094 hosts
```

Notice that, to the right of the variable octet, the network address has all `0` and the broadcast has all `255`.

# 5. Local destinations, remote destinations, and the default gateway

Subnetting is not just arithmetic. Every time a host sends a packet, it must make a decision: if the destination is in its own network, it delivers the packet directly; if not, it hands it to the gateway. That decision depends on the host's address and prefix, and it is the practical reason for everything we have calculated so far.

This section connects calculation with what happens on the network: the host routing table, the gateway, and ARP (seen in U02).

| Concept | Question it answers | Example |
|---|---|---|
| **Local destination** (*destino local*) | Is the destination in my subnet? → direct delivery | `10.20.30.70/27` → `10.20.30.94` |
| **Remote destination** (*destino remoto*) | Is it in another network? → send to the gateway | `192.168.50.20/26` → `8.8.8.8` |
| **Default gateway** | Who is my first hop toward other networks? | `192.168.50.1` |
| **Host routing table** (*tabla de rutas del host*) | Which routes does the host know? | local network + `default via …` |
| **Longest prefix match** (*coincidencia del prefijo más largo*) | If several routes match, which one wins? | the most specific one |
| **ARP** (*Address Resolution Protocol*) | Which MAC belongs to the local IP I am sending the frame to? | `arp -a`, `ip neigh` |

> Even when the packet goes to the gateway, the **destination IP** remains the final destination; what changes is the **destination MAC** of the frame.

The host asks:

```text
Is the destination in my network?
```

## 5.1. Local destination

If the destination belongs to the same subnet:

```text
source host
→ local link
→ destination host
```

The host does not need to send the packet to the default gateway to reach that destination.

## 5.2. Remote destination

If the destination belongs to another network:

```text
source host
→ default gateway
→ other networks
```

The host keeps the **destination IP address** of the final destination, but in the first Ethernet frame it may use the **destination MAC address** of the gateway.

This connects to U02:

```text
destination IP
→ final destination

first-frame destination MAC
→ local next hop
```

## 5.3. The gateway must be locally reachable

Coherent example:

```text
Host:    192.168.50.20/26
Gateway: 192.168.50.1
```

Both belong to:

```text
192.168.50.0/26
```

Incoherent example:

```text
Host:    192.168.50.20/26
Gateway: 192.168.50.129
```

The supposed gateway belongs to another `/26` block (`192.168.50.128/26`).

## 5.4. Host routing table

At an introductory level, recognize:

- local network route;
- default route;
- interface;
- gateway.

Windows:

```text
route print
```

Linux:

```text
ip route
```

Simplified example:

```text
192.168.50.0/26 dev eth0
default via 192.168.50.1
```

This means the local network is directly reachable and other destinations may be sent to the gateway.

On Windows, the default route appears in `route print` as network destination `0.0.0.0` with netmask `0.0.0.0` and the gateway's IP in the "Gateway" column.

### Which route is chosen: the longest prefix

The default route is equivalent to `0.0.0.0/0`: it matches **any** destination. The local network route (`/26`) only matches destinations in that network. When several routes match a destination, the host chooses the **most specific** one, that is, the one with the **longest prefix** (*longest prefix match*):

```text
Destination 192.168.50.30  → matches /26 and /0 → /26 wins → direct delivery
Destination 8.8.8.8        → matches only /0     → gateway 192.168.50.1
```

Routers apply the same rule; you will study it in depth in U08.

## 5.5. ARP as local evidence

To send a frame to the gateway in IPv4, a host may need to know its MAC address.

```text
arp -a
ip neigh
```

An ARP entry for the gateway is evidence of recent local discovery/communication, but it **does not by itself prove** that Internet access or any remote destination works.

## 5.6. Decision example

```text
Host: 10.20.30.70/27
GW:   10.20.30.65
Dest: 10.20.30.94
```

For `/27`, block size is `32`.

`70` belongs to:

```text
10.20.30.64–95
```

Therefore:

```text
Network:   10.20.30.64/27
Broadcast: 10.20.30.95
```

The gateway `10.20.30.65` is local.

The destination `10.20.30.94` is also local.

Conclusion:

```text
the host does not need to send this packet to the default gateway
```

## 5.7. Solving the case from Section 1.6

```text
IPv4:    192.168.20.37/27
Gateway: 192.168.20.1
DNS:     192.168.50.53
```

For `/27`, block size is `32`. `37` falls between `32` and `63`:

```text
Network:   192.168.20.32/27
Hosts:     192.168.20.33–62
Broadcast: 192.168.20.63
```

- The gateway `192.168.20.1` is in a different block (`192.168.20.0/27`, from `.0` to `.31`): it is **not locally reachable**. The configuration is incoherent.
- The DNS server `192.168.50.53` is in another network. That is acceptable: many DNS servers are on a different subnet. But the host needs a valid gateway to reach it; with this error, name resolution will also fail.

Minimal correction: use a gateway inside `192.168.20.33–62` (for example, `192.168.20.33` if that is the organization's convention and a router interface actually exists there), or check whether the documented prefix was different.

# 6. Subnetting with FLSM

An organization rarely uses a large block as a single network: it divides it to separate departments, limit broadcast traffic, or apply different policies. **Subnetting** means dividing one block into smaller blocks. The simplest way is to divide it into **equal** parts (FLSM), which lets us learn a stable procedure before moving on to different sizes (VLSM, Section 8).

The central idea is a trade-off: every bit we "borrow" from the host part for the network part **doubles** the number of subnets and **halves** their size.

| Concept | Meaning | Example |
|---|---|---|
| **Subnetting** | Dividing a block into smaller blocks | `/24` → four `/26` |
| **Parent block** (*bloque padre*) | Starting address space that is divided | `192.168.10.0/24` |
| **Borrowed bits** (*bits prestados*) | Host bits that now identify the subnet | `s = 2` |
| **FLSM** (*Fixed Length Subnet Masking*) | Every subnet uses the same prefix | four `/26` of 64 addresses |
| **Reverse check** (*comprobación inversa*) | Number of subnets × size = parent size | `4 × 64 = 256` |

> Do not mix up the **number of subnets** (`2^s`, depends on borrowed bits) with **hosts per subnet** (`2^h − 2`, depends on the remaining bits).

## 6.1. Why divide a network?

It can help us:

- separate departments;
- reduce broadcast domains;
- apply policies;
- organize addressing;
- simplify troubleshooting;
- reserve room for growth;
- prepare VLAN and routing designs.

## 6.2. FLSM

With **Fixed Length Subnet Masking (FLSM)**, all subnets use the same prefix.

Example:

```text
Parent block: 192.168.10.0/24
Requirement:  4 equal subnets
```

We need 2 bits to identify 4 subnets:

```text
2^2 = 4
```

The prefix changes from `/24` to `/26`.

Result:

```text
192.168.10.0/26
192.168.10.64/26
192.168.10.128/26
192.168.10.192/26
```

Each subnet contains:

```text
64 addresses
62 usable hosts in the conventional case
```

## 6.3. FLSM procedure

```text
1. identify the parent block
2. determine how many subnets are required
3. calculate how many bits must be borrowed
4. obtain the new prefix
5. calculate the block size
6. list the subnet boundaries
7. verify that every subnet remains inside the parent block
```

## 6.4. Number of subnets

If we borrow `s` bits:

```text
subnets = 2^s
```

We do not use historical rules that subtracted two subnets.

If the required number of subnets is not a power of 2, choose the smallest `s` such that `2^s` is **greater than or equal to** the requirement:

```text
Block: 192.168.10.0/24
Requirement: 5 subnets
2^2 = 4 → not enough
2^3 = 8 → enough → s = 3 → /27

/27 subnets (block 32, 30 hosts each):
.0  .32  .64  .96  .128  .160  .192  .224
```

We use five and keep three free for growth.

## 6.5. Reverse check

When a block is divided completely and evenly:

```text
number of subnets
×
size of each subnet
=
size of the parent block
```

Example:

```text
4 × 64 = 256
```

which matches the size of a `/24`.

# 7. Choosing a prefix from a host requirement

In real designs, we are not always told “use `/27`.” We may instead receive a requirement:

> We need a network for 25 hosts.

We must convert a **requirement** into a **prefix**. This is the reverse of Section 3: there we started from the prefix and calculated capacity; here we start from the required capacity and look for the prefix. The answer is not only mathematical: we also have to decide how much margin to leave.

| Concept | Question it answers | Example |
|---|---|---|
| **Host requirement** (*requisito de hosts*) | How many interfaces need an IP in that network? | 25 devices |
| **Host bits** (*bits de host*, `h`) | How many bits do I need so they all fit? | `2^5 − 2 = 30 ≥ 25` → `h = 5` |
| **Minimum prefix** (*prefijo mínimo*) | Which prefix results? | `32 − 5 = /27` |
| **Growth margin** (*margen de crecimiento*) | How much room is left for the future? | 30 − 25 = 5 free |

> The **minimum** prefix is not always the **right** prefix: if the network grows, a design without margin forces renumbering.

## 7.1. Procedure

Find the smallest number of host bits that provides enough capacity.

Example: 25 hosts.

Test:

```text
2^4 - 2 = 14
→ not enough

2^5 - 2 = 30
→ enough
```

We need 5 host bits.

```text
32 - 5 = /27
```

Therefore:

```text
25 hosts
→ /27
```

When counting hosts, include **every interface that needs an IP** on that network: computers, printers, servers, and also the router interface that will act as the gateway, unless the requirement says otherwise.

## 7.2. Practical table

| Prefix | Addresses | Conventional usable hosts |
|---:|---:|---:|
| /24 | 256 | 254 |
| /25 | 128 | 126 |
| /26 | 64 | 62 |
| /27 | 32 | 30 |
| /28 | 16 | 14 |
| /29 | 8 | 6 |
| /30 | 4 | 2 |

A `/30` (2 hosts) is the classic size for a point-to-point link between two routers; you will use it in U08.

## 7.3. Do not always choose the largest subnet

If we need 20 hosts, a `/24` would work, but it wastes significant address space.

A better goal is usually:

```text
enough capacity
+
reasonable margin
+
coherent use of address space
```

## 7.4. Growth

The mathematically smallest prefix is not always the best professional decision.

If a network already has 28 devices and is growing:

```text
/27 → 30 usable hosts
```

may leave too little margin.

A design should consider expected requirements, not only the current snapshot.

# 8. VLSM: different subnet sizes

FLSM is simple, but it does not always use address space efficiently: if all subnets must be equal, the largest one sets the size for all of them. **Variable Length Subnet Masking (VLSM)** allows different prefixes within one addressing plan, so each network gets the size it needs.

In exchange, we must be more careful: blocks have different sizes and must be placed on **valid boundaries**, without **overlapping** and without leaving the parent block. That is why VLSM follows an ordered procedure and always ends with checking and documentation.

| Concept | Question it answers | Example |
|---|---|---|
| **VLSM** (*Variable Length Subnet Masking*) | Can I give each network the size it needs? | `/25`, `/26`, `/27`, `/28` in one `/24` |
| **Largest first** (*orden de mayor a menor*) | Where do I start assigning? | First the 100-host network |
| **Valid boundary / alignment** (*límite válido*) | Where can a block of this size start? | a `/26` only at `.0`, `.64`, `.128`, `.192` |
| **Overlap** (*solapamiento*) | Do two blocks share addresses? | `.128/26` and `.160/27` overlap |
| **Free space** (*espacio libre*) | What remains available for growth? | `192.168.100.240/28` |

> A VLSM error is not always visible during configuration: two overlapping networks may work "sometimes" and fail when routes or devices are added.

Suppose we have these requirements:

```text
USERS   100 hosts
SERVERS 30 hosts
VOICE   20 hosts
MGMT    10 hosts
```

Assigning the same size to every subnet can waste many addresses. With FLSM, the 100-host network forces a `/25` (128 addresses) for all four: 4 × 128 = 512 addresses, which **do not even fit** in a `/24`. With VLSM, `/25` + `/27` + `/27` + `/28` = 128 + 32 + 32 + 16 = 208 addresses are enough.

## 8.1. Stable procedure

```text
1. sort requirements from largest to smallest
2. calculate the minimum appropriate prefix for each requirement
3. assign the largest block first
4. continue at the next valid boundary
5. verify that no blocks overlap
6. verify that every block remains inside the parent block
7. document the result
```

## 8.2. Example

Available block:

```text
192.168.100.0/24
```

Requirements:

```text
A: 100 hosts
B: 50 hosts
C: 20 hosts
D: 10 hosts
```

Prefixes:

```text
100 hosts → /25 → 126 hosts
50 hosts  → /26 → 62 hosts
20 hosts  → /27 → 30 hosts
10 hosts  → /28 → 14 hosts
```

Assignment:

```text
A → 192.168.100.0/25
B → 192.168.100.128/26
C → 192.168.100.192/27
D → 192.168.100.224/28
```

Remaining space:

```text
192.168.100.240/28
```

## 8.3. Documentation table

| Network | Requirement | Prefix | Network address | Host range | Broadcast |
|---|---:|---:|---|---|---|
| A | 100 | /25 | 192.168.100.0 | .1–.126 | .127 |
| B | 50 | /26 | 192.168.100.128 | .129–.190 | .191 |
| C | 20 | /27 | 192.168.100.192 | .193–.222 | .223 |
| D | 10 | /28 | 192.168.100.224 | .225–.238 | .239 |
| Free | — | /28 | 192.168.100.240 | .241–.254 | .255 |

## 8.4. Valid boundaries

A subnet of a given size cannot begin at any arbitrary address.

A `/26` uses blocks of 64:

```text
0, 64, 128, 192
```

Therefore:

```text
192.168.100.96/26
```

does not represent a valid `/26` boundary. `96` is a valid `/27` boundary (a multiple of 32), but not a `/26` boundary (not a multiple of 64): with a `/26` mask, `192.168.100.96` would be a host in network `192.168.100.64/26`.

## 8.5. Why start with the largest subnet?

If we assign small blocks first in a random order, we can fragment the available space and make it impossible to place a large contiguous subnet later.

Sorting from largest to smallest reduces that risk.

## 8.6. Checking overlap

Two subnets overlap when they share any address.

Every assignment should be checked using its boundaries:

```text
block start
→ block end
→ next block starts after it
```

Overlap example:

```text
B: 192.168.100.128/26 → .128–.191
X: 192.168.100.160/27 → .160–.191
```

`X` lies completely inside `B`: they share 32 addresses. It is a design error even though each network, on its own, is calculated correctly.

## 8.7. Design and growth

VLSM does not mean always choosing the smallest possible prefix with no margin.

A good design balances:

- current requirements;
- growth;
- simplicity;
- documentation;
- parent-block availability.

# 9. CIDR and simple aggregation

**Classless Inter-Domain Routing (CIDR)** uses explicit prefixes and allows blocks to be represented without depending on historical address classes. It is how every IPv4 address is written and allocated today, from a classroom to an Internet service provider.

CIDR has two sides that we use in this unit: the **notation** (`address/prefix`), which you have already been using, and **aggregation**: representing several contiguous networks with one shorter prefix. Aggregation lets a router advertise "all my networks" in a single line; here we only learn to check whether a simple summary is correct.

| Concept | Question it answers | Example |
|---|---|---|
| **CIDR** (*Classless Inter-Domain Routing*) | How do I express a block without classes? | `10.20.30.32/27` |
| **Prefix / slash notation** (*notación de prefijo*) | Where is the network/host boundary? | `/27` |
| **Aggregation / summarization** (*agregación o resumen*) | Can I represent several networks with one prefix? | `192.168.0.0/24` + `192.168.1.0/24` = `192.168.0.0/23` |
| **Summary boundary** (*límite de resumen*) | Does the summary start where it should and cover only what I want? | a `/23` starts at an even third octet |

> Two networks being **consecutive** does not mean they can be summarized **exactly** with a single prefix.

## 9.1. An address without a prefix is incomplete for many calculations

```text
10.20.30.40
```

by itself does not tell us whether it belongs to a `/8`, `/16`, `/24`, `/27`, or another block.

We need:

```text
10.20.30.40/27
```

to interpret the boundary.

## 9.2. Aggregation

**Aggregation** or **route summarization** represents multiple blocks with one common prefix when their boundaries allow it.

Example:

```text
192.168.0.0/24
192.168.1.0/24
```

can be summarized as:

```text
192.168.0.0/23
```

because `/23` covers:

```text
192.168.0.0
through
192.168.1.255
```

## 9.3. Consecutive networks are not automatically summarizable exactly

A summary must:

- begin at a valid boundary;
- cover the intended interval exactly, or make clear what extra blocks it includes;
- share enough common prefix bits.

For example:

```text
192.168.1.0/24
192.168.2.0/24
```

cannot be represented by one `/23` containing only those two networks, because `/23` boundaries start on the appropriate even third-octet values (`0`, `2`, `4`, ...).

The smallest single prefix that contains both is `192.168.0.0/22` (from `192.168.0.0` to `192.168.3.255`), which also includes `192.168.0.0/24` and `192.168.3.0/24`. That may be acceptable if those networks do not exist elsewhere, but you must know it and document it.

## 9.4. Checking a summary with binary

We want to summarize four networks:

```text
172.16.4.0/24
172.16.5.0/24
172.16.6.0/24
172.16.7.0/24
```

Only the third octet changes. Convert it to binary:

```text
4 = 000001 00
5 = 000001 01
6 = 000001 10
7 = 000001 11
```

The first 6 bits of the third octet are common. Summary prefix: `16 + 6 = /22`.

```text
Summary: 172.16.4.0/22  (mask 255.255.252.0)
Covers:  172.16.4.0 – 172.16.7.255
```

Checks: `4` is a multiple of 4 (a valid `/22` boundary in the third octet), and the `/22` contains exactly the four networks, no more.

## 9.5. Later use

In U09 we will reuse aggregation and prefixes when studying dynamic routing. In U04, the goal is to understand block logic and verify a simple summary.

# 10. Addressing plans and basic IPAM

A mathematically correct design can still be difficult to operate if it is not documented. An addressing plan answers questions that calculation does not: which address the gateway uses, which addresses DHCP hands out, which are fixed, and what space remains free. If those decisions are not written down, each technician makes them differently and conflicts appear.

Organized management of that plan is called **IPAM**. In this unit you do not need a professional tool: a well-maintained, reviewed table is enough to apply its principles.

| Concept | Question it answers | Example |
|---|---|---|
| **Addressing plan** (*plan de direccionamiento*) | Which network, gateway, and use does each segment have? | USERS → `172.16.10.0/25`, gw `.1` |
| **IPAM** (*IP Address Management*) | Where is address-space usage documented and maintained? | Table of networks, ranges, and assignments |
| **Gateway convention** (*convención de gateway*) | Which address does the gateway always use? | first usable host in each subnet |
| **Static / dynamic / reservation** (*estático, dinámico, reserva*) | How does each device type get its IP? | fixed servers, DHCP clients |
| **Cross-check** (*validación cruzada*) | Is the plan coherent before deployment? | no overlaps, pools outside fixed addresses |

> A **correct** plan (the calculations work) is not the same as a **maintainable** plan (another technician can understand, extend, and audit it).

## 10.1. What a good plan should provide

It should be:

- coherent;
- readable;
- documented;
- verifiable;
- expandable;
- maintainable.

## 10.2. Example requirements

```text
USERS    → 100 hosts
SERVERS  → 30 hosts
VOICE    → 20 hosts
MGMT     → 10 hosts
```

The work does not stop after choosing prefixes. We also need to decide:

- network blocks;
- gateways;
- dynamic ranges;
- reserved addresses;
- free space;
- naming/documentation conventions.

Section 10.7 shows a complete plan for these requirements.

## 10.3. IPAM

**IP Address Management (IPAM)** means organized management of IP address space.

In this unit, a well-maintained table can be enough:

| Name | Network/prefix | Gateway | Host range | Broadcast | Assignment | Notes |
|---|---|---|---|---|---|---|

An enterprise IPAM platform is not required to apply good IPAM principles.

## 10.4. Gateway convention

An organization may decide, for example:

```text
gateway = first usable host
```

or use another consistent convention.

There is no single universal rule. What matters is:

```text
known rule
+
consistent application
+
documentation
```

## 10.5. Static and dynamic addresses

One possible policy is:

```text
infrastructure → static
servers        → static or reservation
clients        → DHCP
```

The correct choice depends on operational needs.

## 10.6. Cross-checking the plan

Before deployment, verify that:

- no blocks overlap;
- every gateway belongs to its subnet;
- DHCP pools do not include excluded or static addresses;
- every subnet has sufficient capacity;
- free space is identified;
- conventions are consistent.

## 10.7. Complete IPAM plan example

Parent block: `172.16.10.0/24`. Requirements from Section 10.2. Conventions: gateway = first usable host; in DHCP networks, the first addresses are reserved for infrastructure.

Prefix decisions (largest to smallest):

```text
USERS   100 → /25 (126 hosts)
SERVERS  30 → /27 would give 30 hosts: zero margin → choose /26 (62 hosts) for growth
VOICE    20 → /27 (30 hosts)
MGMT     10 → /28 (14 hosts)
Total: 128 + 64 + 32 + 16 = 240 of 256 addresses → it fits; 16 remain free
```

| Name | Network/prefix | Gateway | Host range | Broadcast | Assignment | Notes |
|---|---|---|---|---|---|---|
| USERS | 172.16.10.0/25 | .1 | .1–.126 | .127 | DHCP: pool .11–.126 | .2–.10 excluded (infrastructure); pool of 116 addresses |
| SERVERS | 172.16.10.128/26 | .129 | .129–.190 | .191 | Static or reservation | Internal DNS at .130 |
| VOICE | 172.16.10.192/27 | .193 | .193–.222 | .223 | DHCP: pool .201–.222 | .194–.200 excluded; pool of 22 addresses |
| MGMT | 172.16.10.224/28 | .225 | .225–.238 | .239 | Static | Switch and AP management |
| Free | 172.16.10.240/28 | — | .241–.254 | .255 | Unassigned | Reserved for growth |

Cross-check: the blocks end at `.127`, `.191`, `.223`, and `.239`, and each next block starts right after (no overlaps); every gateway is inside its network; the pools include neither the gateway nor the excluded addresses; every network meets its requirement.

# 11. Static IPv4 configuration and verification

Once the addressing plan has been designed, we must apply it and prove that it works. These are two different tasks: **configuring** means entering values; **verifying** means obtaining evidence that those values produce the expected communication. A professional technician does not consider a change finished until it has been verified.

This section covers which parameters a host needs, where they are entered on each system, in which order to check them, and what to do if something fails.

| Concept | Question it answers | Example |
|---|---|---|
| **Host parameters** (*parámetros del host*) | What does a device need to communicate? | IP, prefix, gateway, DNS |
| **Static configuration** (*configuración estática*) | How do I enter them manually? | Network settings, `New-NetIPAddress`, `nmcli` |
| **Progressive verification** (*verificación progresiva*) | In which order do I check? | interface → IP → gateway → remote → DNS |
| **Evidence** (*evidencia*) | What does each test prove? | `ping` to the gateway ≠ Internet access |
| **One change at a time** (*cambiar una sola variable*) | How do I know what fixed the problem? | correct only the gateway and test again |

> **Configuration is not verification.**

## 11.1. Common host parameters

A host usually needs:

```text
IPv4 address
subnet mask / prefix
default gateway
DNS server
```

## 11.2. Progressive verification

A useful order is:

```text
1. interface
2. address and prefix
3. calculated network
4. local neighbor
5. gateway
6. remote destination by IP
7. DNS
8. application/service
```

This does not mean we must always perform eight tests. It means we should select the next test that best reduces uncertainty.

## 11.3. Configuration is not verification

Typing values into an interface only proves that we changed the configuration.

To prove connectivity, we need evidence.

Examples:

```text
ipconfig /all
ip address
ip route
ping
arp -a
ip neigh
nslookup
```

Each tool answers a different question.

## 11.4. Change one variable at a time

When troubleshooting, avoid changing all of these at once:

- IP address;
- mask;
- gateway;
- DNS.

If we change everything and the system then works, we know something was wrong, but we have not demonstrated what caused the problem.

## 11.5. Case

```text
PC1
IP: 192.168.40.34/27
GW: 192.168.40.33

PC2
IP: 192.168.40.62/27
GW: 192.168.40.33
```

For `/27`, block size is 32.

Both addresses fall inside:

```text
192.168.40.32–63
```

Therefore:

```text
Network:   192.168.40.32/27
Hosts:     192.168.40.33–62
Broadcast: 192.168.40.63
```

The gateway `192.168.40.33` is valid and local.

A successful ping between PC1 and PC2 proves IP connectivity between those hosts at that time, but it does not by itself prove:

- that DNS works;
- that Internet routing exists;
- that every application is responding.

## 11.6. Where the configuration is entered

The parameters are the same on every system; only the tool changes. Example using PC1 from the previous case (assumed DNS: `192.168.40.53`):

**Packet Tracer (PC):** *Desktop → IP Configuration → Static*: IPv4 Address, Subnet Mask, Default Gateway, and DNS Server.

**Windows (GUI):** *Network settings → Change adapter options* (`ncpa.cpl`) → adapter properties → *Internet Protocol Version 4 (TCP/IPv4)*.

**Windows (PowerShell, as administrator):**

```text
New-NetIPAddress -InterfaceAlias "Ethernet" -IPAddress 192.168.40.34 -PrefixLength 27 -DefaultGateway 192.168.40.33
Set-DnsClientServerAddress -InterfaceAlias "Ethernet" -ServerAddresses 192.168.40.53
```

**Linux with NetworkManager (persistent):**

```text
nmcli connection modify "Wired connection 1" ipv4.method manual ipv4.addresses 192.168.40.34/27 ipv4.gateway 192.168.40.33 ipv4.dns 192.168.40.53
nmcli connection up "Wired connection 1"
```

**Linux with `ip` (temporary, lost after reboot):**

```text
sudo ip address add 192.168.40.34/27 dev eth0
sudo ip route add default via 192.168.40.33
```

The interface or connection name (`Ethernet`, `eth0`, `Wired connection 1`…) varies by device: check it first with `Get-NetAdapter`, `ip address`, or `nmcli connection show`. Other distributions use other persistent systems (for example, *netplan* on Ubuntu Server); the parameters remain the same.

# 12. DHCP: dynamic IPv4 parameter assignment

Once we understand the parameters a host needs, we can automate their delivery. Configuring hundreds of devices by hand is slow and causes errors (duplicate addresses, wrong gateways). **Dynamic Host Configuration Protocol (DHCP)** lets a server provide network configuration to clients based on what we defined in the addressing plan.

DHCP does not replace design: the server hands out exactly what we configured, right or wrong. That is why we relate each DHCP element to the IPAM plan and to client-side verification.

| Concept | Question it answers | Example |
|---|---|---|
| **DHCP** (*Dynamic Host Configuration Protocol*) | How does a device receive its configuration automatically? | client set to "DHCP" |
| **DORA** (*Discover, Offer, Request, Acknowledgment*) | Which messages are exchanged? | 4 UDP messages, ports 67/68 |
| **Scope / address pool** (*ámbito o pool*) | Which addresses can the server assign in a network? | `172.16.10.11`–`172.16.10.126` |
| **Exclusion** (*exclusión*) | Which addresses must never be assigned? | gateway, servers, printers |
| **Reservation** (*reserva*) | How do I always give a specific device the same IP through DHCP? | printer's MAC → `.9` |
| **Lease** (*concesión*) | How long may the client use the address? | 1 day, 8 days |
| **DHCP relay agent** (*agente de retransmisión*) | How does a client reach a server on another network? | configured in U08 |

> **Where it's configured in this course.** In this unit the DHCP server is a server device (the *DHCP* service on a Packet Tracer server, or a Windows/Linux server). Configuring a **Cisco router** as a DHCP server (`ip dhcp pool`) and as a relay (`ip helper-address`) is covered in U08, once routers are being administered.

## 12.1. Parameters DHCP can provide

Among others:

- IPv4 address;
- subnet mask/prefix;
- default gateway;
- DNS server;
- lease duration.

DHCP automates delivery. It does not change the meaning of these parameters.

## 12.2. DORA

The simplified initial exchange is:

```text
Discover
→ Offer
→ Request
→ Acknowledgment
```

In U02 we observed this exchange as traffic. Here we relate it to the **addressing plan**.

| Message | Sent by | Purpose | Typical addresses |
|---|---|---|---|
| **Discover** | Client | "Is there a DHCP server?" | `0.0.0.0` → `255.255.255.255` (broadcast) |
| **Offer** | Server | "I offer you this IP and these parameters" | server → client |
| **Request** | Client | "I accept this server's offer" | `0.0.0.0` → `255.255.255.255` (so every server learns the choice) |
| **Acknowledgment (ACK)** | Server | "Confirmed: the lease is yours" | server → client |

DHCP uses **UDP**: the server listens on port **67** and the client on port **68**. Because the client has no address yet, it starts with source `0.0.0.0` and a broadcast destination; that is why, without a relay, the messages do not leave the local network.

## 12.3. DHCP pool

A **pool** is the set of addresses a DHCP server can assign dynamically for a specific network.

It must be coherent with:

- network;
- prefix;
- gateway;
- exclusions;
- other options.

## 12.4. Exclusions

An excluded address must not be assigned dynamically.

Common examples:

- gateway;
- infrastructure interfaces;
- selected servers;
- printers with fixed configurations.

## 12.5. Reservation

A **reservation** lets a specific client receive a planned address through the DHCP server's mechanism.

It is not the same as manually configuring that address on the client.

A reservation is usually tied to the client's **MAC address**: the device stays in DHCP mode, but the server always gives it the same IP. The advantage is that the address is managed and documented in a single place.

## 12.6. Lease

A dynamic assignment is a **temporary lease**.

You should be able to interpret:

- assigned address;
- mask/prefix;
- gateway;
- DNS;
- DHCP server;
- lease duration.

The client does not wait for the lease to expire: halfway through (50%, called T1) it tries to **renew** it with the same server; if that fails, it tries again with any server at about 87.5% (T2). If the lease expires without renewal, the client stops using the address.

Useful client commands:

```text
Windows:  ipconfig /all        (DHCP server, lease obtained and lease expires)
          ipconfig /release    (releases the lease)
          ipconfig /renew      (requests a new one)
Linux:    ip address           (address and remaining lifetime, valid_lft)
          sudo dhclient -r eth0 ; sudo dhclient eth0   (release and request, if dhclient is used)
          nmcli connection up "<connection>"           (with NetworkManager)
```

## 12.7. Client-side verification

It is not enough to say:

> “The client received an IP address, so DHCP is correct.”

We must verify that the received parameters are the expected ones.

Example:

```text
correct IP address
correct mask
incorrect gateway
```

The client received a lease, but the configuration is not functional for remote destinations.

## 12.8. Four common failures

Each DHCP failure leaves a different symptom pattern. Recognizing the pattern helps you choose the first test, but it does not replace evidence.

| Failure | Typical client symptom | First useful check |
|---|---|---|
| No valid address | No IP, or `169.254.x.x` (APIPA) | Is there a link? Is the server running, on the same network (or reachable through a relay), and with free addresses? |
| Incorrect gateway | Local works, remote does not | Compare the received gateway with the plan and the calculated network |
| Incorrect DNS | `ping` by IP works, by name does not | `nslookup` and the DNS shown in `ipconfig /all` |
| Pool overlaps a static address | Intermittent IP conflicts | Compare the pool with exclusions and the IPAM table |

### No valid address

Possible areas to investigate:

- DHCP service unavailable;
- client cannot reach the service;
- pool exhausted;
- incorrect server configuration;
- link/access problem.

We should not select a cause without evidence.

If the client shows `169.254.x.x/16`, we know something specific: the host requested configuration through DHCP and **received no answer**, so it assigned itself a link-local address (APIPA). With it, it could only talk to other hosts in the same situation; it has no gateway.

### Correct address, incorrect gateway

Possible pattern:

```text
local communication → yes
remote communication → no
```

### Incorrect DNS

Possible pattern:

```text
correct IP
correct gateway
remote destination by IP works
name resolution fails
```

### Pool overlaps a static address

This can create conflicts or inconsistent assignments.

## 12.9. DHCP relay

When DHCP clients and the server are on different networks, a **relay** mechanism may be required.

In U04, it is enough to recognize the need: Discover is a broadcast, and routers do not forward broadcasts. A **relay agent**, usually the router on the client's network, picks up that broadcast and forwards it as unicast to the server. You will configure it in U08 (`ip helper-address`), once you master routing between networks.

## 12.10. What it looks like on a DHCP server

The concepts are the same on every server; only the option names change.

| Concept | Packet Tracer server (*Services → DHCP*) | Windows Server (DHCP role) | Linux (isc-dhcp-server / Kea) |
|---|---|---|---|
| Network and mask | *Subnet Mask* (the network is set by *Start IP Address*) | Scope with mask or length | `subnet … netmask …` / `"subnet"` |
| Assignable range | *Start IP Address* + *Maximum Number of Users* | Scope start and end addresses | `range` / `"pools"` |
| Exclusions | Implicit: whatever is outside the range | Exclusion range | Whatever is outside `range` |
| Gateway | *Default Gateway* | Option 003 *Router* | `option routers` |
| DNS | *DNS Server* | Option 006 *DNS Servers* | `option domain-name-servers` |
| Reservation | Not available | Reservations (by MAC) | `host { hardware ethernet …; fixed-address …; }` / `"reservations"` |
| Lease | Not configurable | Lease duration (8 days by default) | `default-lease-time` / `"valid-lifetime"` |

Packet Tracer example for the USERS network in plan 10.7 (the server has a static IP inside the network, e.g., `172.16.10.10/25`, in the excluded zone):

```text
Service:                 On
Pool Name:               USERS
Default Gateway:         172.16.10.1
DNS Server:              172.16.10.130
Start IP Address:        172.16.10.11
Subnet Mask:             255.255.255.128
Maximum Number of Users: 116        (from .11 to .126: 126 - 11 + 1 = 116)
```

Check: the pool ends at `.126`, the last host of `172.16.10.0/25`; it includes neither the gateway (`.1`), the server (`.10`), nor the broadcast (`.127`).

# 13. Evidence-based IPv4 troubleshooting

A message such as:

> “I have no network.”

is a **symptom**, not a cause. This section brings everything together into a working method: instead of trying random commands or changing parameters "to see if it works," we state a hypothesis, choose the test that confirms or rules it out, and base the conclusion on evidence. It is the same method you used in U01–U03, now applied to IPv4 configuration.

| Step | Question it answers | Example |
|---|---|---|
| **Symptom** (*síntoma*) | What does the user observe? | "No website opens" |
| **Hypothesis** (*hipótesis*) | What could explain it? | gateway outside the subnet |
| **Test** (*prueba*) | Which check distinguishes my hypotheses? | calculate the network and compare it with the gateway |
| **Evidence** (*evidencia*) | What result did I get? | network `.64/27`, gateway `.1` |
| **Conclusion** (*conclusión*) | What do I state, based on the evidence? | the gateway is not local |
| **Minimal change / verification** (*cambio mínimo y verificación*) | What do I fix, and how do I prove it now works? | change only the gateway and repeat the test |

> Do not confuse a **fact** ("ipconfig shows…") with a **hypothesis** ("it might be the gateway") or a **conclusion** ("the gateway is wrong because…").

A useful framework is:

```text
symptom
→ question
→ hypothesis
→ test
→ evidence
→ conclusion
```

If a correction is required:

```text
→ minimal change
→ verification
```

## 13.1. Dependency chain

For an IPv4 problem, we can consider:

```text
interface
→ IP address
→ prefix
→ network
→ membership
→ gateway
→ route
→ ARP/neighbor
→ remote destination by IP
→ DNS
→ service
```

We should not mechanically run every command. The real question is:

> **Which test now gives me the information I need to distinguish between my hypotheses?**

## 13.2. Fact, hypothesis, and conclusion

Example:

```text
Fact:
ipconfig shows 192.168.50.70/27
```

```text
Hypothesis:
the gateway may be outside the local subnet
```

```text
Test:

```

```text

the network is 192.168.50.64/27 (hosts .65–.94) and the configured gateway is 192.168.50.1
```

```text
Conclusion:
the configured gateway does not belong to the host's local subnet
```

The conclusion is linked to observable evidence.

## 13.3. Do not change settings before understanding the problem

Changing parameters without knowing what you are trying to prove can hide the original cause.

A professional troubleshooting process aims for:

```text
one concrete hypothesis
→ one appropriate test
→ one minimal correction
→ one verification after the change
```

# 16. Common mistakes to avoid

Almost every mistake in this unit has the same origin: replacing calculation or evidence with an impression ("they look alike," "it has an IP, so it works"). The table summarizes each mistake and the correct way to reason; each one is explained afterward.

| Mistake | Why it is wrong | What to do |
|---|---|---|
| Inferring the mask from the class (*classful assumption*) | Classes are no longer used | Use the explicit prefix |
| Nearby addresses = same subnet | Membership depends on the prefix | Calculate the block |
| Gateway outside the local network | The host cannot reach it directly | Check that it is in the host range |
| Memorizing without checking boundaries | A block only starts at multiples of its size | Verify the valid boundary |
| Starting VLSM with small networks | It fragments the space | Sort largest to smallest |
| DHCP reservation = manual static IP | They are managed in different places | Distinguish server and client |
| "It has an IP, so DHCP is fine" | It may have received wrong parameters | Check mask, gateway, and DNS |
| Changing several parameters at once | The cause is not demonstrated | One change, one verification |

## Inferring the mask from the old address class

Incorrect:

```text
192.x.x.x → /24
```

Correct:

```text
use the explicit prefix
```

## Assuming nearby addresses are in the same subnet

```text
192.168.1.30
192.168.1.70
```

may or may not be in the same network depending on the prefix. With `/24` they are in the same network; with `/26` they are not (`.30` is in `192.168.1.0/26` and `.70` is in `192.168.1.64/26`).

## Choosing a gateway outside the local subnet

The host must be able to reach its configured gateway directly.

## Memorizing results without checking boundaries

A prefix implies a block size and valid boundaries.

## Starting VLSM with the smallest networks

This can fragment the available space and prevent placement of larger subnets.

## Confusing a DHCP reservation with a manually configured static IP

Both can produce a stable address, but they are managed differently.

## Assuming DHCP is correct because an address exists

The mask, gateway, DNS, and addressing-plan coherence must also be checked.

## Changing several parameters at once

This makes it harder to demonstrate the actual cause.

# 18. Final summary

By the end of this unit, keep these ideas. They are grouped into four blocks that follow the path of the unit: calculate, decide, design, and operate.

| Block | Ideas | What you should be able to demonstrate |
|---|---|---|
| **Calculate** (*calcular*) | 1–4 | Network, broadcast, range, capacity, and membership for any IP/prefix |
| **Decide** (*decidir*) | 5 | Whether a destination is local or remote and whether the gateway is valid |
| **Design** (*diseñar*) | 6–9 | An FLSM/VLSM plan with no overlaps, with margin, summarizable, and documented |
| **Operate** (*operar*) | 10–12 | Configure (static or DHCP), verify, and troubleshoot with evidence |

1. An IPv4 address is interpreted together with its **prefix**.
2. The prefix defines which bits describe the network and how much space remains inside the block.
3. A subnet has a **network address, broadcast address, host range, and capacity**.
4. Membership is calculated; it is not decided by decimal appearance.
5. A host uses the **default gateway** when the destination is not local.
6. FLSM divides a block into equal-size subnets; VLSM allows different sizes.
7. Choosing a prefix is a **capacity and design** decision, not just arithmetic.
8. CIDR uses explicit prefixes and enables aggregation when boundaries are correct.
9. A professional addressing plan must be **documented** with IPAM or another maintainable representation.
10. DHCP automates parameters that we must first understand.
11. Configuration is not the same as verification.
12. Troubleshooting must connect **hypotheses to tests and conclusions to evidence**.

The professional goal is not merely to answer “what mask does this IP have?” quickly, but to defend statements such as:

> “This host belongs to this subnet, this gateway is locally reachable, this block meets the required capacity, and these tests demonstrate where the fault is.”
