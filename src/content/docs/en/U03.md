---
title: "U03 — Infrastructure and Connectivity"
---

> **Guiding question:** What physical and access conditions must a network meet so that devices can connect reliably, verifiably, and with the expected performance?

In U01 we built an initial map of a network. In U02 we formalized layers, encapsulation, and traffic analysis. This unit moves down to the infrastructure that makes communication physically possible: interfaces, copper, fiber, radio, terminations, negotiation, power delivery, measurements, documentation, and status evidence.

The main question in U03 is not yet whether an IPv4 subnet has been calculated correctly. That belongs in U04. Here we first learn to answer a different question: **does correct physical or wireless connectivity actually exist, and can we prove it with evidence?**

Our professional troubleshooting thread will be:

```text
symptom → question → hypothesis → test → evidence → conclusion
```

When a real fault must be corrected, we add two more steps:

```text
→ minimum change → verification
```

The goal is not to memorize catalogs of cables or connectors. The goal is to understand what each element does, which limitations it introduces, and which evidence lets us decide whether it is working correctly.

# 1. From the Device to the Physical Link

Before any protocol can work, there must be a physical or wireless path capable of carrying signals.

## Basic concepts

| Concept | Meaning |
|---|---|
| **Network adapter** | Hardware that allows a device to use a network technology |
| **Interface** | Physical or logical point through which a device participates in a network |
| **Medium** | Environment through which the signal propagates |
| **Signal** | Physical representation of information |
| **Link** | Communication connection between two interfaces |
| **Channel** | Complete cabling path between endpoints |
| **Transceiver** | Component that adapts a signal to an interface/medium |

Examples of media and signals:

| Medium | Signal |
|---|---|
| Copper | Electrical |
| Fiber optic | Optical |
| Air | Radio |

## Network adapters

A device may use:

- integrated Ethernet;
- PCIe NIC;
- USB-to-Ethernet adapter;
- Wi‑Fi;
- virtual interface;
- virtual-machine interface.

A switch or router may include:

- copper ports;
- optical interfaces;
- modules;
- transceivers;
- logical interfaces.

In U03, our main focus is the **physical/access state**.

## Interface

An interface can provide information such as:

```text
state
speed
duplex
physical address
statistics
configuration
```

Examples:

```text
Ethernet
Wi-Fi
Gi1/0/18
SFP interface
vNIC
```

Do not confuse:

```text
device
≠
adapter
≠
interface
≠
medium
```

## Physical path

A real connection may be:

```text
PC
→ Ethernet interface
→ patch cord
→ network outlet
→ horizontal cable
→ patch panel
→ rack patch cord
→ switch port
```

Each element can be a dependency.

Therefore, the symptom:

> “The PC has no network”

does not prove which component has failed.

## LEDs as initial evidence

LED behavior varies by manufacturer/model, but LEDs may indicate:

- power;
- system state;
- link presence;
- activity;
- speed;
- PoE.

Example:

```text
link LED off
→ initial evidence
→ inspect the physical path
```

But:

```text
LED on
≠
proven IP connectivity
```

An LED does not prove:

- correct addressing;
- correct VLAN;
- correct routing;
- DNS;
- application availability.

## Link up and link down

```text
link down
→ no operational physical link is detected

link up
→ some form of link has been detected
```

But:

```text
link up
+
incorrect logical configuration
=
no useful communication
```

Therefore:

> **`link up` proves something, but not everything.**

# 2. Performance and Medium Degradation

An interface can be active and still perform far below expectations.

## Nominal capacity and throughput

**Nominal capacity** expresses an expected maximum data rate under certain conditions.

Examples:

```text
100 Mb/s
1 Gb/s
10 Gb/s
```

**Throughput** is the actual amount of useful data transferred.

Therefore:

```text
nominal capacity
≠
actual throughput
```

Performance may be affected by:

- overhead;
- errors;
- retransmissions;
- congestion;
- endpoint limitations;
- software limitations;
- interference;
- medium characteristics;
- the application itself.

## Negotiated speed

Observed link speed may be:

```text
100 Mb/s
1 Gb/s
2.5 Gb/s
10 Gb/s
```

This is not the same as throughput.

Example:

```text
negotiated speed = 1 Gb/s
measured throughput = 420 Mb/s
```

can be entirely possible.

## Attenuation

**Attenuation** is the reduction in signal strength as it propagates.

It can increase because of:

- distance;
- connectors;
- splices;
- damage;
- bends;
- poor installation.

Advanced formulas are not required.

The goal is to connect the phenomenon to symptoms.

## Noise and interference

Noise adds unwanted energy.

Possible sources include:

- motors;
- electrical power systems;
- nearby cables;
- radio transmissions;
- other electronic devices.

It may cause:

- errors;
- retransmissions;
- lower throughput;
- renegotiation;
- link loss.

## Crosstalk

**Crosstalk** is interference between nearby conductors or pairs.

Twisting helps reduce it.

Therefore:

```text
correct continuity
+
too much untwisting
→
performance degradation may still occur
```

## A symptom is not a cause

| Observation | Compatible hypotheses |
|---|---|
| 100 Mb/s link when 1 Gb/s was expected | Pairs, termination, cable, negotiation, adapter |
| Increasing CRC/FCS errors | Medium, connectors, interference, interface |
| Link flaps | Cable, connector, power, transceiver, interface |
| Unstable Wi‑Fi | Coverage, interference, utilization, client |

This table does not diagnose the fault.

It generates hypotheses.

The proper sequence is:

```text
symptom
→ hypothesis
→ test
→ evidence
```

---

## Case

Observed:

```text
expected: 1 Gb/s
observed: 100 Mb/s
```

Write at least four hypotheses.

Then select the **highest-value first test**.

# 3. Copper and Structured Cabling

## Twisted pair

Typical Ethernet copper cable contains four twisted pairs.

Twisting helps:

- reduce interference;
- reduce crosstalk;
- maintain electrical balance.

The twist should be preserved as close to the termination as practical.

## Categories to recognize

| Category | Typical use |
|---|---|
| **Cat 5e** | Gigabit Ethernet in suitable installations |
| **Cat 6** | Gigabit and higher performance depending on technology/distance |
| **Cat 6A** | 10GBASE-T on a suitable channel |

You do not need to memorize every existing category.

## Cable is not the same as channel

Professional principle:

```text
cable category
≠
guaranteed channel performance
```

A channel may include:

```text
patch cord
+
outlet/keystone
+
horizontal cable
+
patch panel
+
patch cord
+
terminations
```

One weak component may limit the whole path.

Example:

```text
Cat 6A horizontal cable
+
Cat 5e keystone
+
Cat 6A patch cords
→
does not prove the complete channel is Cat 6A
```

## Shielding

Common designations:

| Designation | Initial meaning |
|---|---|
| U/UTP | Unshielded |
| F/UTP | Overall foil shield |
| U/FTP | Shielding around pairs |
| S/FTP | Overall braid + shielded pairs |

The goal is not to memorize every combination.

Shielding must be part of a coherent installation system.

## Material quality

A marketing label does not replace good installation practice.

Poor materials or terminations may cause:

- excessive resistance;
- heating;
- poorer PoE behavior;
- reduced signal margin;
- reduced reliability;
- worse high-frequency behavior.

---

## Structured cabling

Structured cabling organizes the infrastructure so it can be:

- maintained;
- expanded;
- traced;
- verified;
- documented.

Typical elements include:

- network outlet;
- keystone;
- horizontal cable;
- patch panel;
- patch cord;
- rack;
- cable managers;
- labels.

## Permanent link

Fixed part:

```text
outlet
→ horizontal cable
→ patch panel
```

## Channel

Complete path:

```text
device
→ patch cord
→ permanent link
→ patch cord
→ switch
```

## 8P8C and “RJ45”

The common modular Ethernet connector is technically **8P8C**.

The term “RJ45” is widely used informally.

You should recognize both.

## T568A and T568B

| Pin | T568A | T568B |
|---:|---|---|
| 1 | white/green | white/orange |
| 2 | green | orange |
| 3 | white/orange | white/green |
| 4 | blue | blue |
| 5 | white/blue | white/blue |
| 6 | orange | green |
| 7 | white/brown | white/brown |
| 8 | brown | brown |

Both wiring schemes are valid.

The important point is to apply the intended scheme consistently.

## Straight-through and crossover cables

Straight-through:

```text
A ↔ A
B ↔ B
```

Crossover:

```text
A ↔ B
```

Historically, the cable type was selected based on connected device types.

Many modern devices support **Auto MDI-X**.

Therefore:

> “PC-to-switch is always straight-through and switch-to-switch is always crossover”

should not be learned as a universal current rule.

## Auto MDI-X

Auto MDI-X can automatically adapt transmit/receive pair roles.

It does not repair:

- open conductors;
- shorts;
- split pairs;
- poor terminations.

```text
Auto MDI-X
≠
automatic cable repair
```

## Console cable

The **console cable** doesn't carry network traffic: it connects the management (*console*) port of a switch or router to a computer's serial or USB port, so the device can be configured with a terminal emulator (PuTTY, Tera Term, `screen`).

| Type | Connectors | Notes |
|---|---|---|
| Rollover (classic) | RJ-45 ↔ DB-9, or RJ-45 ↔ RJ-45 + adapter | Wires are reversed end to end (1↔8, 2↔7…) |
| USB | USB ↔ device mini-USB/USB-C | Common on current devices; requires a driver |
| USB-to-serial adapter | USB ↔ DB-9 | For laptops without a serial port |

Typical terminal settings: **9600 baud, 8 data bits, no parity, 1 stop bit, no flow control (9600 8N1)**.

A console cable isn't checked with a standard Ethernet wiremap tester like a patch cable: its wiring scheme is intentionally different.

## Ethernet over copper

Reference technologies:

| Technology | Speed | Pairs used |
|---|---:|---:|
| 100BASE-TX | 100 Mb/s | 2 |
| 1000BASE-T | 1 Gb/s | 4 |
| 10GBASE-T | 10 Gb/s | 4 |

2.5GBASE-T and 5GBASE-T also exist.

A defect affecting certain pairs may allow a link to come up while preventing the expected speed.

# 4. Autonegotiation, Duplex, and PoE

## Autonegotiation

Endpoints can automatically agree on:

- speed;
- duplex;
- selected capabilities.

Negotiated speed is an **observation**, not a root cause.

Example:

```text
Gigabit NIC
+
Gigabit switch
+
observed speed = 100 Mb/s
```

Compatible hypotheses:

- missing pairs;
- termination problem;
- cable issue;
- actual capability;
- configuration;
- adapter issue.

## Full-duplex

In **full-duplex**, data can be transmitted and received at the same time.

```text
PC ⇄ switch
```

This is the normal expected behavior in modern switched Ethernet in many scenarios.

## Duplex as evidence

An unexpected duplex value may indicate a negotiation/configuration issue.

But it should be interpreted together with:

- speed;
- errors;
- configuration;
- link type.

## PoE

**Power over Ethernet (PoE)** carries power and data over Ethernet cabling.

Common uses:

- access point;
- IP camera;
- IP phone.

Before concluding “PoE is broken,” verify:

- powered-device compatibility;
- power-source/switch capability;
- required power;
- available power;
- channel quality.

In U03, PoE is studied functionally.

Complex power-budget design is not required.

## Data and power share infrastructure dependencies

A cabling fault can affect:

```text
data
+
power
```

Example:

```text
AP restarts
+
link flaps
+
PoE
```

may justify checking the channel and power conditions before blaming software.

# 5. Cabling Tests

A tool is useful only when we understand **what it measures** and **what it cannot prove**.

## Visual inspection

Before using a tester:

- inspect connectors;
- look for damage;
- check locking tabs;
- detect crushing;
- inspect conductor order;
- inspect excessive untwisting;
- verify labels.

Visual inspection does not replace measurement.

But it can prevent unnecessary tests.

## Wiremap

A basic cable tester can show conductor relationships.

| Result | Initial interpretation |
|---|---|
| **Open** | No continuity |
| **Short** | Conductors improperly connected |
| **Reversed / miswired** | Incorrect conductor order |
| **Crossed** | Different end mappings |
| **Split pair** | Pin continuity exists but electrical pairs are incorrect |

## Split pair

This is an especially important fault.

It can produce:

```text
apparently correct pin continuity
+
incorrect pair grouping
=
electrically poor channel behavior
```

## Length and distance to fault

Some testers can estimate:

- cable length;
- approximate distance to a defect.

Not every tester supports these functions.

## Limits of a basic tester

It can provide evidence about:

- continuity;
- conductor order;
- selected faults;
- sometimes length.

But it does not automatically prove:

- effective channel category;
- crosstalk within limits;
- actual throughput;
- 10G suitability;
- complete standards compliance.

Therefore:

```text
correct wiremap
≠
certified channel
```

## Testing a hypothesis

Example:

```text
Symptom:
1 Gb/s expected → 100 Mb/s observed

Hypothesis:
one pair is not available

Test:
wiremap

Result:
open pair
```

Cautious interpretation:

> The result is consistent with the hypothesis.

Do not claim more than the test supports.

# 6. Building, Repairing, and Verifying Patch Cables

Building a cable is only one part of the skill.

The complete process is:

```text
build
→ inspect
→ test
→ interpret
→ repair
→ test again
→ document
```

## Safety and organization

- keep the workbench clear;
- use crimpers and cutting tools correctly;
- remove wire scraps;
- avoid unnecessary work on powered equipment;
- identify each cable.

## Cable-building procedure

1. select T568A or T568B;
2. strip the outer jacket without damaging conductors;
3. preserve twisting as much as possible;
4. order the pairs;
5. verify color order;
6. trim evenly;
7. insert into the 8P8C connector;
8. visually verify;
9. crimp;
10. repeat for the other end.

## The lab does not end after crimping

Next:

```text
inspection
→ wiremap
→ interpretation
```

This is not enough:

```text
“the LED lights up”
→ lab complete
```

## Troubleshooting prepared faults

Students may receive an unknown faulty cable containing:

- open;
- swapped conductors;
- split pair;
- poor termination.

Procedure:

```text
result
→ inspection
→ wiremap
→ hypothesis
→ locate fault
→ repair
→ retest
```

## Record

| Cable | Scheme | Initial result | Diagnosis | Action | Final result |
|---|---|---|---|---|---|

The lab is complete when the student can prove:

- what was built;
- what was measured;
- what result appeared;
- what change was made;
- what final result was obtained.

# 7. Fiber Optics and Transceivers

Fiber carries information using light.

## Advantages

It can provide:

- high capacity;
- long distances;
- electromagnetic immunity;
- electrical isolation.

Do not memorize:

```text
fiber = always better
```

Selection depends on:

- distance;
- technology;
- cost;
- environment;
- equipment;
- maintenance.

## Single-mode and multimode

| Characteristic | Single-mode | Multimode |
|---|---|---|
| Typical use | longer distances / backbone | short/medium distances |
| Reference designation | OS2 | OM3 / OM4 |
| Core | smaller | larger |

There is no universal rule such as:

```text
multimode = X meters
single-mode = Y kilometers
```

Reach depends on:

```text
Ethernet technology
+
transceiver
+
fiber
+
actual link conditions
```

## Connectors

Recognize especially:

- LC;
- SC.

A complete connector catalog is not required.

## Polarity

For duplex fiber:

```text
TX A → RX B
RX A ← TX B
```

Connecting transmitters to each other will not create the expected link.

## Transceivers

A transceiver must be compatible with:

- speed;
- fiber type;
- wavelength;
- reach;
- connector;
- platform/device.

Important principle:

```text
it physically fits
≠
it is technically compatible
```

## Safety

- do not look directly into fiber ends;
- do not assume a fiber is inactive;
- protect connectors;
- avoid touching optical surfaces;
- respect bend radius;
- follow lab procedures.

# 8. Wi‑Fi as a Shared Medium

Wi‑Fi uses radio.

Multiple devices share the medium.

```text
Wi-Fi client
      ↕
      AP
      ↕
wired network
```

## Shared medium

Unlike a dedicated full-duplex switched Ethernet link between host and switch, multiple wireless clients may compete for airtime.

Therefore:

```text
PHY rate
≠
throughput
```

## Coverage and obstacles

Signal quality may degrade because of:

- distance;
- walls;
- materials;
- geometry;
- placement;
- interference.

Advanced RF propagation physics is not required here.

## Bands

### 2.4 GHz

- relatively greater range;
- less spectrum;
- higher probability of interference.

### 5 GHz

- more spectrum/channels;
- strong performance potential;
- relatively shorter range.

### 6 GHz

- additional spectrum;
- requires compatible devices;
- depends on platform/regulation.

Complete channel tables are not a memorization goal.

## Initial metrics

| Metric | What it tells us |
|---|---|
| RSSI | Received signal strength |
| SNR | Signal-to-noise ratio |
| Channel utilization | Airtime/resource occupancy |
| PHY rate | Negotiated physical-layer rate |
| Retries | Repeated transmissions |
| Throughput | Useful data transfer |

There is no universal rule:

```text
high RSSI
=
high throughput
```

## Access stages

Simplified sequence:

```text
detect WLAN
→ select SSID
→ authenticate / satisfy security
→ associate
→ obtain configuration
→ test connectivity
→ test service
```

These stages are different.

Example:

```text
SSID visible
≠
authentication successful
≠
IP configuration correct
≠
Internet reachable
```

## Basic security

Recognize:

- open network;
- WPA2;
- WPA3.

U03 does not aim to teach:

- 802.1X in depth;
- EAP;
- WLC;
- CAPWAP;
- complete enterprise WLAN architecture.

## Stage-based troubleshooting

Ask:

```text
Is the SSID visible?
→ Is signal quality sufficient?
→ Does authentication succeed?
→ Does association succeed?
→ Does the client obtain configuration?
→ Is there connectivity?
→ Is performance acceptable?
```

This separates:

```text
radio
≠
Wi-Fi access
≠
IP configuration
≠
service
```

# 9. Documentation, Maps, and Traceability

Managing a network also means being able to answer:

> **Which switch port is this device actually connected to?**

## Rack

A rack may contain:

- patch panels;
- switches;
- routers;
- cable managers;
- fiber;
- PDU;
- UPS.

The goal is not to design a full data center.

It is to understand organization and traceability.

## Labeling

A connection should be traceable:

```text
outlet
→ patch panel
→ switch port
```

Example:

```text
A1-023
→ PP03-18
→ SW02-Gi1/0/18
```

A naming convention should be:

- unique;
- consistent;
- documented;
- maintainable.

## Minimum record

| Outlet | Patch panel | Switch port | Medium | State |
|---|---|---|---|---|
| A1-023 | PP03-18 | SW02-Gi1/0/18 | Cat 6A | Operational |

## Physical map

Represents:

- device;
- location;
- interface;
- medium;
- outlet;
- panel;
- port.

Example:

```text
PC-07
→ outlet A1-023
→ PP03-18
→ SW02 Gi1/0/18
```

## Basic logical map

Represents functional relationships:

- device names;
- roles;
- links;
- segments;
- services.

It does not need to reproduce the exact physical layout.

Physical and logical maps answer different questions.

## Verify documentation

Documentation represents an **expected** state.

The real network provides the **observed** state.

```text
documentation
→ verify
→ compare
→ update
```

Do not make changes first and document them later from memory.

## CDP and LLDP as evidence

In a managed environment, a prepared output may show:

```text
Local interface: Gi0/1
Neighbor: SW2
Remote port: Gi0/2
```

This can be used to compare against the documented map.

U03 does not configure CDP/LLDP.

It only interprets the output.

# 10. Interface State, Counters, and SNMP

The final U03 skill is moving from:

```text
“it does not work”
```

to:

```text
symptom
→ scope
→ physical path
→ state
→ counter
→ test
→ hypothesis
→ minimum change
→ new measurement
→ verification
→ documentation
```

## Interface state

Useful information includes:

- up/down;
- speed;
- duplex;
- autonegotiation;
- errors;
- drops;
- link flaps;
- PoE;
- transceiver.

### Windows

```powershell
Get-NetAdapter
Get-NetAdapterStatistics
```

### Linux

```bash
ip link
ethtool <interface>
```

### Cisco IOS

At interpretation level:

```text
show interfaces
show interfaces status
show interfaces counters errors
```

Full switch CLI administration is not required yet.

## Counters

A counter is cumulative.

Example:

```text
CRC = 245
```

by itself does not prove that an active fault exists now.

We need to observe change over time.

### Case A

```text
initial CRC = 245
final CRC   = 245
```

No new CRC errors were observed during the interval.

### Case B

```text
initial CRC = 245
final CRC   = 390
```

The counter increased.

Procedure:

```text
record
→ reproduce traffic/problem
→ measure again
→ compare
```

## State, counter, and rate

- **state**: current condition;
- **counter**: accumulated events;
- **rate**: change over an interval;
- **baseline**: normal reference value.

## A counter does not automatically identify the cause

Increasing CRC errors may be compatible with:

- cable;
- connector;
- noise;
- interface;
- transceiver;
- other physical problems.

Relate:

```text
counter
+
symptom
+
physical test
+
controlled change
```

## SNMP as an observation tool

SNMP allows a management system to obtain information from network devices.

Basic model:

```text
NMS / manager
      ↕
    agent
      ↕
managed information
```

### NMS / manager

System that queries or receives information.

### Agent

Component on the managed device that exposes information.

### MIB

Structure that organizes managed information.

### OID

Identifier for one specific managed value.

Examples of observable information:

- interface state;
- octets;
- errors;
- CPU;
- temperature.

## Polling and notification

Two basic ideas:

```text
NMS
→ periodic query
→ polling
```

and:

```text
device
→ reports an event
→ notification / trap
```

U03 does not configure SNMPv3 or communities.

The goal is to understand that monitoring can provide evidence even when you are not physically standing in front of the device.

# 11. Integrated Physical Troubleshooting Case

Scenario:

> A workstation that normally links at 1 Gb/s now negotiates at 100 Mb/s and experiences intermittent disconnections.

Initial evidence:

```text
link up
speed = 100 Mb/s
full-duplex
autonegotiation = on
CRC = 245
```

## Step 1 — Do not interpret the counter too quickly

Ask:

> Are CRC errors increasing now?

Record the value.

Reproduce traffic.

Measure again.

## Step 2 — Trace the path

```text
PC
→ patch cord
→ outlet
→ horizontal cable
→ patch panel
→ patch cord
→ switch
```

## Step 3 — Wiremap

Suppose the result is:

```text
open pair
```

A copper-channel hypothesis becomes stronger.

## Step 4 — Minimum change

Instead of changing all of these at once:

- NIC;
- switch;
- configuration;
- cabling;

change one controlled component, for example:

```text
patch cord
```

## Step 5 — Verification

After the change:

```text
speed = 1 Gb/s
CRC stable
no new link flaps
```

Now there is evidence of improvement.

## Step 6 — Documentation

```text
Symptom:
Scope:
Physical path:
State:
Initial counters:
Test:
Result:
Hypothesis:
Change:
Final counters:
Verification:
Cause:
Prevention:
Conclusion:
```

# 14. What Comes Next in U04 and U05

U03 ends when you can answer:

> **Is there a correct physical or wireless infrastructure, and what evidence proves it?**

U04 will answer:

> **Is the device correctly integrated into IPv4?**

U05 will answer:

> **Is it correctly integrated into IPv6?**

The progression is:

```text
U03
medium / link / access
        ↓
U04
IPv4 / subnetting / DHCP
        ↓
U05
IPv6 / autoconfiguration
```

The professional rule that remains is:

```text
expected state
≠
observed state
≠
proven cause
```

and:

```text
observe
→ measure
→ interpret
→ change one variable
→ measure again
→ verify
→ document
```
