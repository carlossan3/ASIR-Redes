> **Guiding question:** What physical and access conditions must a network meet so that devices can connect reliably, verifiably, and with the expected performance?

In U01 we built an initial map of a network. In U02 we formalized layers, encapsulation, and traffic analysis. This unit moves down to the infrastructure that makes communication physically possible: interfaces, copper, fiber, radio, terminations, negotiation, power delivery, measurements, documentation, and status evidence.

The main question in U03 is not yet whether an IPv4 subnet has been calculated correctly. That belongs in U04. Here we first learn to answer a different question: **does correct physical or wireless connectivity actually exist, and can we prove it with evidence?**

Our professional troubleshooting thread will be:

```text
symptom → question → hypothesis → test → evidence → conclusion
```

When a real fault must be corrected, we add two more steps:

```text
→ minimum change → verification
```

The goal is not to memorize catalogs of cables or connectors. The goal is to understand what each element does, which limitations it introduces, and which evidence lets us decide whether it is working correctly.

# 1. From the Device to the Physical Link

Before any protocol can work, there must be a physical or wireless path capable of carrying signals. This section gives a name to each piece of that path: the device hardware, the point where it connects, the medium the signal travels through, and the connection formed between two endpoints.

When a user says “I have no network,” the problem could be in any of those pieces. If we can tell them apart and know what evidence each one provides (an LED, an `up`/`down` state), we can start looking in the right place instead of trying things at random.

| Concept | What it is | Question it answers | Example |
|---|---|---|---|
| **Network adapter** (NIC) | Hardware that allows a device to use a network technology | Which hardware does the device connect with? | Integrated Ethernet card, USB Wi‑Fi adapter |
| **Interface** | Physical or logical point through which a device participates in a network | Through which point does communication enter or leave? | `Ethernet`, `Wi-Fi`, `Gi1/0/18` |
| **Medium** | Environment through which the signal propagates | Where does the signal travel? | Copper, fiber, air |
| **Signal** | Physical representation of information | What physical form does the information take? | Electrical, optical, radio |
| **Link** | Communication connection between two interfaces | Is there a connection between these two endpoints? | PC ↔ switch port |
| **Channel** | Complete cabling path between endpoints | Which elements does the connection pass through? | Patch cord + outlet + cable + panel + patch cord |
| **Transceiver** | Component that adapts a signal to an interface/medium | What adapts the interface to a specific medium? | Fiber SFP module |

We should not confuse the device with its adapter, the adapter with the interface, or the interface with the medium: they are different levels, and each one can fail on its own.

## 1.1. Media and signals

| Medium | Signal |
|---|---|
| Copper | Electrical |
| Fiber optic | Optical |
| Air | Radio |

## 1.2. Network adapters

A device may use:

- integrated Ethernet;
- PCIe NIC;
- USB-to-Ethernet adapter;
- Wi‑Fi;
- virtual interface;
- virtual-machine interface.

A switch or router may include:

- copper ports;
- optical interfaces;
- modules;
- transceivers;
- logical interfaces.

In U03, our main focus is the **physical/access state**.

## 1.3. Wired and wireless adapters in different operating systems

Integrating a device into the network starts by checking that the operating system **recognizes the adapter**, that it has a **driver**, and that the interface is **enabled**. Only then does it make sense to look at the link, the Wi‑Fi association and, in U04, the IP configuration.

| System | Where to see it (GUI) | Query commands |
|---|---|---|
| **Windows** | Settings → Network & Internet; Device Manager (driver) | `Get-NetAdapter`, `ipconfig /all`, `netsh wlan show interfaces` (Wi‑Fi: SSID, signal, rate) |
| **Linux** | NetworkManager (applet or `nmtui`) | `ip link`, `nmcli device status`, `ethtool <interface>` (cable), `iw dev <interface> link` (Wi‑Fi), `lspci` / `lsusb` (hardware) |
| **macOS** | System Settings → Network | `networksetup -listallhardwareports`, `ifconfig` |

Adapter check sequence:

```text
Does the OS detect the hardware?
→ Does it have the correct driver?
→ Is the interface enabled?
→ Is there a link (cable) or an association (Wi-Fi)?
→ [U04] Does it have a consistent IP configuration?
```

Interface names vary by system (`Ethernet`, `Wi-Fi`, `eth0`, `enp3s0`, `wlan0`, `wlp2s0`, `en0`). What matters is identifying **which interface belongs to which adapter and which medium**.

## 1.4. Interface

An interface can provide information such as:

```text
state
speed
duplex
physical address
statistics
configuration
```

Examples:

```text
Ethernet
Wi-Fi
Gi1/0/18
SFP interface
vNIC
```

Do not confuse:

```text
device
≠
adapter
≠
interface
≠
medium
```

## 1.5. Physical path

A real connection may be:

```text
PC
→ Ethernet interface
→ patch cord
→ network outlet
→ horizontal cable
→ patch panel
→ rack patch cord
→ switch port
```

Each element can be a dependency.

Therefore, the symptom:

> “The PC has no network”

does not prove which component has failed.

## 1.6. LEDs as initial evidence

LED behavior varies by manufacturer/model, but LEDs may indicate:

- power;
- system state;
- link presence;
- activity;
- speed;
- PoE.

Example:

```text
link LED off
→ initial evidence
→ inspect the physical path
```

But:

```text
LED on
≠
proven IP connectivity
```

An LED does not prove:

- correct addressing;
- correct VLAN;
- correct routing;
- DNS;
- application availability.

(The detailed meaning of Cisco switch LEDs is covered in U06.)

## 1.7. Link up and link down

```text
link down
→ no operational physical link is detected

link up
→ some form of link has been detected
```

But:

```text
link up
+
incorrect logical configuration
=
no useful communication
```

Therefore:

> **`link up` proves something, but not everything.**

# 2. Performance and Medium Degradation

An interface can be active and still perform far below expectations. This section separates three ideas that are often mixed up: the speed the device “shows,” the speed actually achieved, and the physical phenomena that degrade the signal along the way.

This lets us explain common situations, such as a slow download over a 1 Gb/s link, and relate each phenomenon (attenuation, noise, crosstalk) to the symptoms it causes, without formulas.

| Concept | Question it answers | Example |
|---|---|---|
| **Nominal capacity** | What is the technology's expected maximum rate? | 1 Gb/s for 1000BASE-T |
| **Negotiated speed** (link speed) | What speed did both endpoints agree on? | `speed = 100 Mb/s` on the interface |
| **Throughput** | How much useful data is actually transferred? | 420 Mb/s measured during a file copy |
| **Attenuation** | How much strength does the signal lose as it travels? | Very long link or many connectors |
| **Noise and interference** | What unwanted energy is added to the signal? | Cable next to a motor or power line |
| **Crosstalk** | Do neighboring pairs interfere with each other? | Untwisted pairs at the termination |

The typical trap is treating capacity, negotiated speed, and throughput as synonyms: they are three different measurements and can have very different values at the same time.

## 2.1. Nominal capacity and throughput

**Nominal capacity** expresses an expected maximum data rate under certain conditions.

Examples:

```text
100 Mb/s
1 Gb/s
10 Gb/s
```

**Throughput** is the actual amount of useful data transferred.

Therefore:

```text
nominal capacity
≠
actual throughput
```

Performance may be affected by:

- overhead;
- errors;
- retransmissions;
- congestion;
- endpoint limitations;
- software limitations;
- interference;
- medium characteristics;
- the application itself.

## 2.2. Negotiated speed

Observed link speed may be:

```text
100 Mb/s
1 Gb/s
2.5 Gb/s
10 Gb/s
```

This is not the same as throughput.

Example:

```text
negotiated speed = 1 Gb/s
measured throughput = 420 Mb/s
```

can be entirely possible.

## 2.3. Attenuation

**Attenuation** is the reduction in signal strength as it propagates.

It can increase because of:

- distance;
- connectors;
- splices;
- damage;
- bends;
- poor installation.

Advanced formulas are not required.

The goal is to connect the phenomenon to symptoms.

## 2.4. Noise and interference

Noise adds unwanted energy.

Possible sources include:

- motors;
- electrical power systems;
- nearby cables;
- radio transmissions;
- other electronic devices.

It may cause:

- errors;
- retransmissions;
- lower throughput;
- renegotiation;
- link loss.

## 2.5. Crosstalk

**Crosstalk** is interference between nearby conductors or pairs.

Twisting helps reduce it.

Therefore:

```text
correct continuity
+
too much untwisting
→
performance degradation may still occur
```

## 2.6. A symptom is not a cause

| Observation | Compatible hypotheses |
|---|---|
| 100 Mb/s link when 1 Gb/s was expected | Pairs, termination, cable, negotiation, adapter |
| Increasing CRC/FCS errors | Medium, connectors, interference, interface |
| Link flaps | Cable, connector, power, transceiver, interface |
| Unstable Wi‑Fi | Coverage, interference, utilization, client |

This table does not diagnose the fault.

It generates hypotheses.

The proper sequence is:

```text
symptom
→ hypothesis
→ test
→ evidence
```

## 2.7. Case

Observed:

```text
expected: 1 Gb/s
observed: 100 Mb/s
```

Write at least four hypotheses.

Then select the **highest-value first test**.

# 3. Copper and Structured Cabling

Twisted-pair copper is still the most common medium for connecting workstations, IP phones, cameras, and access points. This section studies the cable itself but, above all, the **complete channel** it is installed in: the wall outlet, the cable running through the ceiling, the rack panel, and the patch cords at each end.

The central idea is that a channel performs only as well as its weakest element, and that installations are governed by **standards** (which categories, which lengths, which color schemes). At the end we look at the cable types built with these connectors: straight-through, crossover, and the **console cable**, which does not carry network data but is essential for managing switches and routers.

| Concept | Question it answers | Example |
|---|---|---|
| **Twisted pair** | How is the cable built, and why is it twisted? | 4-pair U/UTP |
| **Category** | What performance does the component support? | Cat 5e, Cat 6, Cat 6A |
| **Shielding** | Does it have a shield against interference? | U/UTP, F/UTP, S/FTP |
| **Structured cabling** | How is a maintainable installation organized? | Outlets, panels, rack, labels |
| **Permanent link and channel** | Which part is fixed, and which part is the complete path? | Outlet → panel (fixed); device → switch (channel) |
| **Cabling standards** | Who defines categories, lengths, and schemes? | TIA-568, ISO/IEC 11801, IEEE 802.3 |
| **8P8C / “RJ45” connector** | Which connector terminates the cable? | Patch cord connector |
| **T568A / T568B** (wiring schemes) | What color order goes on each pin? | T568B on both ends |
| **Straight-through / crossover cable** | Are pairs kept or swapped end to end? | PC–switch (straight-through) |
| **Auto MDI-X** | Can the port adapt to the cable type? | Modern switch with any patch cord |
| **Console cable** (rollover) | How do I connect a PC to a network device's management port? | RJ-45 ↔ DB-9 or USB |
| **Ethernet over copper** (BASE-T) | Which Ethernet technology uses the cable, and how many pairs? | 1000BASE-T uses 4 pairs |

We should not mix the **category** (what a component supports) with **channel performance** (what the installed whole supports), nor the **color scheme** (T568A/B) with the **cable type** (straight-through, crossover, or console).

## 3.1. Twisted pair

Typical Ethernet copper cable contains four twisted pairs.

Twisting helps:

- reduce interference;
- reduce crosstalk;
- maintain electrical balance.

The twist should be preserved as close to the termination as practical.

## 3.2. Categories to recognize

| Category | Typical use |
|---|---|
| **Cat 5e** | Gigabit Ethernet in suitable installations |
| **Cat 6** | Gigabit and higher performance depending on technology/distance (10GBASE-T only on short channels, around 55 m) |
| **Cat 6A** | 10GBASE-T on a suitable channel (up to 100 m) |

You do not need to memorize every existing category.

## 3.3. Cable is not the same as channel

Professional principle:

```text
cable category
≠
guaranteed channel performance
```

A channel may include:

```text
patch cord
+
outlet/keystone
+
horizontal cable
+
patch panel
+
patch cord
+
terminations
```

One weak component may limit the whole path.

Example:

```text
Cat 6A horizontal cable
+
Cat 5e keystone
+
Cat 6A patch cords
→
does not prove the complete channel is Cat 6A
```

## 3.4. Shielding

Common designations:

| Designation | Initial meaning |
|---|---|
| U/UTP | Unshielded |
| F/UTP | Overall foil shield |
| U/FTP | Shielding around pairs |
| S/FTP | Overall braid + shielded pairs |

The goal is not to memorize every combination.

Shielding must be part of a coherent installation system.

## 3.5. Material quality

A marketing label does not replace good installation practice.

Poor materials or terminations may cause:

- excessive resistance;
- heating;
- poorer PoE behavior;
- reduced signal margin;
- reduced reliability;
- worse high-frequency behavior.

## 3.6. Structured cabling

Structured cabling organizes the infrastructure so it can be:

- maintained;
- expanded;
- traced;
- verified;
- documented.

Instead of running a cable from each PC to the switch, a **fixed** part is installed (outlets, cable through ceilings or raceways, panels), and devices are connected with **interchangeable** patch cords. That way, moving a workstation or changing ports does not require touching the building work.

| Element | Function | Where it is |
|---|---|---|
| **Network outlet** | User connection point | Wall or floor at the workstation |
| **Keystone** | Connection module that snaps into the outlet or panel | Inside the outlet or panel |
| **Horizontal cable** | Fixed run between the outlet and the wiring closet | Ceiling, raised floor, raceway |
| **Patch panel** | Terminates the horizontal cables in the closet | Rack |
| **Patch cord** | Short, flexible cable joining device and outlet, or panel and switch | Workstation and rack |
| **Rack** | Cabinet that houses panels and equipment | Telecommunications room |
| **Cable managers** | Keep patch cords organized | Rack |
| **Labeling** | Identifies each outlet, port, and cable | All elements |

### Permanent link

Fixed part:

```text
outlet
→ horizontal cable
→ patch panel
```

### Channel

Complete path:

```text
device
→ patch cord
→ permanent link
→ patch cord
→ switch
```

### Maximum copper channel length

Standards limit a twisted-pair channel to **100 m** in total:

```text
permanent link ≤ 90 m
+
patch cords (both ends) ≤ 10 m
=
channel ≤ 100 m
```

Exceeding that length increases attenuation and may cause errors, negotiation at a lower speed, or no link at all. For longer distances (between floors or buildings), **fiber** is usually used.

### Subsystems

| Subsystem | What it connects | Usual medium |
|---|---|---|
| **Horizontal** | User outlets ↔ floor wiring closet | Twisted pair |
| **Backbone / vertical** | Floor closets ↔ equipment room | Fiber (or copper over short distances) |
| **Campus** | Buildings to each other | Fiber |

## 3.7. Reference standards

You do not need to memorize the text of the standards, but you should know **what each one covers**, because they appear in quotes, datasheets, and certification reports.

| Standard | What it covers |
|---|---|
| **ANSI/TIA-568** | Structured cabling (U.S.): categories, lengths, T568A/T568B schemes |
| **ISO/IEC 11801** (and **EN 50173** in Europe) | International/European structured cabling: channel classes (e.g., Class EA ≈ Cat 6A) |
| **IEEE 802.3** | Ethernet technologies: 100BASE-TX, 1000BASE-T, 10GBASE-T, fiber, PoE |
| **IEEE 802.11** | Wi‑Fi wireless networks (section 8) |

## 3.8. Connectors, schemes, and cable types

The same connectors are used to build cables with different functions. What sets them apart is **which pin on one end is joined to which pin on the other**.

| Cable type | Ends | Use |
|---|---|---|
| **Straight-through** | Same scheme on both ends (T568B–T568B) | Usual device ↔ switch connection |
| **Crossover** | One end T568A, the other T568B | Historical connection between devices of the same type (switch–switch, PC–PC) |
| **Console** (rollover) | Wire order reversed end to end | Local management of switches and routers |

### 8P8C and “RJ45”

The common modular Ethernet connector is technically **8P8C**.

The term “RJ45” is widely used informally.

You should recognize both.

### T568A and T568B

| Pin | T568A | T568B |
|---:|---|---|
| 1 | white/green | white/orange |
| 2 | green | orange |
| 3 | white/orange | white/green |
| 4 | blue | blue |
| 5 | white/blue | white/blue |
| 6 | orange | green |
| 7 | white/brown | white/brown |
| 8 | brown | brown |

Both wiring schemes are valid.

The important point is to apply the intended scheme consistently.

### Straight-through and crossover cables

Straight-through:

```text
A ↔ A
B ↔ B
```

Crossover:

```text
A ↔ B
```

In a crossover cable, the orange and green pairs swap positions: pins **1-2** on one end reach pins **3-6** on the other, and vice versa. That way, what one device transmits arrives at the other device's receive pins.

Historically, the cable type was selected based on connected device types.

Many modern devices support **Auto MDI-X**.

Therefore:

> “PC-to-switch is always straight-through and switch-to-switch is always crossover”

should not be learned as a universal current rule.

### Auto MDI-X

Auto MDI-X can automatically adapt transmit/receive pair roles.

It does not repair:

- open conductors;
- shorts;
- split pairs;
- poor terminations.

```text
Auto MDI-X
≠
automatic cable repair
```

### Console cable

The **console cable** doesn't carry network traffic: it connects the management (*console*) port of a switch or router to a computer's serial or USB port, so the device can be configured with a terminal emulator (PuTTY, Tera Term, `screen`).

It is the access method that works **even when the device has no network configuration yet**, which is why it is the first one used with a new device or when remote access has been lost.

| Type | Connectors | Notes |
|---|---|---|
| Rollover (classic) | RJ-45 ↔ DB-9, or RJ-45 ↔ RJ-45 + adapter | Wires are reversed end to end (1↔8, 2↔7…) |
| USB | USB ↔ device mini-USB/USB-C | Common on current devices; requires a driver |
| USB-to-serial adapter | USB ↔ DB-9 | For laptops without a serial port |

Typical terminal settings: **9600 baud, 8 data bits, no parity, 1 stop bit, no flow control (9600 8N1)**.

On the PC, the port appears as `COM3`, `COM4`… (Windows, in Device Manager) or as `/dev/ttyUSB0`, `/dev/ttyACM0` (Linux). That port must be selected in the terminal emulator.

A console cable isn't checked with a standard Ethernet wiremap tester like a patch cable: its wiring scheme is intentionally different.

(Using the console to manage a switch is developed in U06, and secure remote access over SSH in U08.)

## 3.9. Ethernet over copper

Reference technologies (IEEE 802.3):

| Technology | Speed | Pairs used |
|---|---:|---:|
| 100BASE-TX | 100 Mb/s | 2 |
| 1000BASE-T | 1 Gb/s | 4 |
| 10GBASE-T | 10 Gb/s | 4 |

2.5GBASE-T and 5GBASE-T also exist.

A defect affecting certain pairs may allow a link to come up while preventing the expected speed. For example, if one of the pairs used only by 1000BASE-T fails, many adapters **drop to 100 Mb/s** (which needs only two pairs) instead of losing the link.

# 4. Autonegotiation, Duplex, and PoE

When we plug in a cable, the two endpoints do not simply start transmitting: first they **agree** on how to do it (speed and duplex). In addition, on many ports the same cable also carries the device's **electrical power**. This section explains both mechanisms and how to read their values as evidence.

The practical consequence is important: a cabling fault can show up as “it's slow,” as “it's running half-duplex,” or as “the access point keeps restarting,” and in all three cases the cause may be the same.

| Concept | Question it answers | Example |
|---|---|---|
| **Autonegotiation** | What speed and duplex did the endpoints agree on? | `a-1000`, `a-full` |
| **Full-duplex** | Can they transmit and receive at the same time? | Modern PC ⇄ switch |
| **Half-duplex** | Do they have to take turns transmitting? | Old hub; failed negotiation |
| **Duplex mismatch** | Is each end running a different duplex mode? | One end fixed at full, the other falls back to half |
| **PoE** (Power over Ethernet) | Does the cable also carry power? | AP, IP camera, IP phone |
| **PSE / PD** (power sourcing equipment / powered device) | Who supplies power and who receives it? | PoE switch (PSE) → AP (PD) |

Negotiated speed and duplex are **observations**, not causes: they tell us what happened, but not why.

## 4.1. Autonegotiation

Endpoints can automatically agree on:

- speed;
- duplex;
- selected capabilities.

Negotiated speed is an **observation**, not a root cause.

Example:

```text
Gigabit NIC
+
Gigabit switch
+
observed speed = 100 Mb/s
```

Compatible hypotheses:

- missing pairs;
- termination problem;
- cable issue;
- actual capability;
- configuration;
- adapter issue.

## 4.2. Full-duplex and half-duplex

In **full-duplex**, data can be transmitted and received at the same time.

```text
PC ⇄ switch
```

This is the normal expected behavior in modern switched Ethernet in many scenarios.

In **half-duplex**, an endpoint transmits **or** receives, but not both at once. This was normal with old hubs and shared media; today, seeing it on a host–switch link is usually a symptom of a negotiation problem.

## 4.3. Duplex as evidence

An unexpected duplex value may indicate a negotiation/configuration issue.

But it should be interpreted together with:

- speed;
- errors;
- configuration;
- link type.

Typical **duplex mismatch** case:

```text
end A: speed and duplex set manually (full), autonegotiation disabled
end B: autonegotiation enabled
→ B receives no negotiation and, by standard, assumes half-duplex
→ A at full, B at half
```

Common symptoms: the link is `up`, but performance is very poor, with late collisions on the half-duplex side and CRC errors on the full-duplex side.

Recommendation: **autonegotiation on both ends**, or identical fixed settings on both.

## 4.4. PoE

**Power over Ethernet (PoE)** carries power and data over Ethernet cabling.

Common uses:

- access point;
- IP camera;
- IP phone.

The device that supplies power (switch or injector) is the **PSE**; the one that receives it is the **PD**. Reference standards (IEEE 802.3):

| Standard | Common name | Max. power at the PSE | Approx. power available at the PD |
|---|---|---:|---:|
| 802.3af | PoE | 15.4 W | 12.95 W |
| 802.3at | PoE+ | 30 W | 25.5 W |
| 802.3bt (Type 3) | PoE++ | 60 W | 51 W |
| 802.3bt (Type 4) | PoE++ | 90 W | 71.3 W |

The difference between what the PSE delivers and what reaches the PD is lost in the cable.

Before concluding “PoE is broken,” verify:

- powered-device compatibility;
- power-source/switch capability;
- required power;
- available power;
- channel quality.

In U03, PoE is studied functionally.

Complex power-budget design is not required.

## 4.5. Data and power share infrastructure dependencies

A cabling fault can affect:

```text
data
+
power
```

Example:

```text
AP restarts
+
link flaps
+
PoE
```

may justify checking the channel and power conditions before blaming software.

# 5. Cabling Tests

A tool is useful only when we understand **what it measures** and **what it cannot prove**. This section presents the ways to check a cable, from looking at it carefully to using a tester, and teaches how to read the results without giving them more weight than they deserve.

Checks go from simple to advanced: first visual inspection, then the wiremap and, if needed, length or performance tests with more advanced equipment. Each step is chosen to **test a specific hypothesis**, not out of routine.

| Concept | Question it answers | Example |
|---|---|---|
| **Visual inspection** | Is there a defect that can be seen? | Broken tab, untwisted pairs |
| **Wiremap** | Does each conductor reach the correct pin on the other end? | `open` result on pair 7-8 |
| **Length / distance to fault** | How long is the cable, and where is the defect? | Break at 23 m |
| **Tester types** (verifier, qualifier, certifier) | What level of evidence do I need? | Verifier in class; certifier to hand over an installation |
| **Split pair** | Is there correct continuity but badly formed pairs? | Apparently valid wiremap with errors |

The typical confusion is believing that “the tester says OK” means “the channel meets the category”: a basic tester does not measure performance.

## 5.1. Visual inspection

Before using a tester:

- inspect connectors;
- look for damage;
- check locking tabs;
- detect crushing;
- inspect conductor order;
- inspect excessive untwisting;
- verify labels.

Visual inspection does not replace measurement.

But it can prevent unnecessary tests.

## 5.2. Tester types

| Type | What it checks | Question it answers |
|---|---|---|
| **Verifier** (wiremap tester) | Continuity and wiremap; some also length | Is it wired correctly? |
| **Qualifier** | Whether the link can support a specific technology | Will it work at 1 Gb/s? |
| **Certifier** | Electrical parameters (attenuation, crosstalk…) against a standard and category | Does the channel meet Cat 6A according to the standard? |

Fiber uses other tools: the **optical power meter** (measures link loss) and the **visual fault locator** (VFL, a red light that reveals breaks and tight bends).

## 5.3. Wiremap

A basic cable tester can show conductor relationships.

| Result | Initial interpretation |
|---|---|
| **Open** | No continuity |
| **Short** | Conductors improperly connected |
| **Reversed / miswired** | Incorrect conductor order |
| **Crossed** | Different end mappings |
| **Split pair** | Pin continuity exists but electrical pairs are incorrect |

## 5.4. Split pair

This is an especially important fault.

It can produce:

```text
apparently correct pin continuity
+
incorrect pair grouping
=
electrically poor channel behavior
```

## 5.5. Length and distance to fault

Some testers can estimate:

- cable length;
- approximate distance to a defect.

Not every tester supports these functions. Those that do usually rely on **TDR** (time domain reflectometry): they send a pulse and measure how long the reflection from the defect takes to return.

## 5.6. Limits of a basic tester

It can provide evidence about:

- continuity;
- conductor order;
- selected faults;
- sometimes length.

But it does not automatically prove:

- effective channel category;
- crosstalk within limits;
- actual throughput;
- 10G suitability;
- complete standards compliance.

Therefore:

```text
correct wiremap
≠
certified channel
```

## 5.7. Testing a hypothesis

Example:

```text
Symptom:
1 Gb/s expected → 100 Mb/s observed

Hypothesis:
one pair is not available

Test:
wiremap

Result:
open pair
```

Cautious interpretation:

> The result is consistent with the hypothesis.

Do not claim more than the test supports.

# 6. Building, Repairing, and Verifying Patch Cables

Building a cable is only one part of the skill. In a professional setting, what matters is being able to **prove** that the cable works, or to locate and repair the fault in one that does not, and to leave a record of it.

This section describes the complete work cycle, from preparing the workbench to the final record, and how to approach a cable with an unknown fault.

| Phase | Question it answers | Evidence it leaves |
|---|---|---|
| **Build / terminate** | Did I terminate the cable according to the chosen scheme? | Scheme applied (T568A/B) |
| **Inspect** | Can any defect be seen before testing? | Visual observations |
| **Test** | What does the tester say? | Wiremap result |
| **Interpret** | What does that result mean? | Hypothesis about the fault |
| **Repair** | What minimum change fixes the fault? | Action taken |
| **Retest** | Did the change solve it? | Final result |
| **Document** | Can someone else verify what I did? | Cable record |

The lab does not end when “the LED lights up”: it ends when the result has been measured and recorded.

The complete process is:

```text
build
→ inspect
→ test
→ interpret
→ repair
→ test again
→ document
```

## 6.1. Safety and organization

- keep the workbench clear;
- use crimpers and cutting tools correctly;
- remove wire scraps;
- avoid unnecessary work on powered equipment;
- identify each cable.

## 6.2. Cable-building procedure

1. select T568A or T568B;
2. strip the outer jacket without damaging conductors;
3. preserve twisting as much as possible;
4. order the pairs;
5. verify color order;
6. trim evenly;
7. insert into the 8P8C connector;
8. visually verify;
9. crimp;
10. repeat for the other end.

For a **crossover** cable, the second end is terminated with the other scheme (T568A on one end and T568B on the other). A **rollover console cable** is built with the same procedure, but with the color order **reversed** on the second end (pin 1 on one side reaches pin 8 on the other); in practice, the manufacturer's cable or a USB cable is usually used.

## 6.3. The lab does not end after crimping

Next:

```text
inspection
→ wiremap
→ interpretation
```

This is not enough:

```text
“the LED lights up”
→ lab complete
```

## 6.4. Troubleshooting prepared faults

Students may receive an unknown faulty cable containing:

- open;
- swapped conductors;
- split pair;
- poor termination.

Procedure:

```text
result
→ inspection
→ wiremap
→ hypothesis
→ locate fault
→ repair
→ retest
```

## 6.5. Record

| Cable | Scheme | Initial result | Diagnosis | Action | Final result |
|---|---|---|---|---|---|

The lab is complete when the student can prove:

- what was built;
- what was measured;
- what result appeared;
- what change was made;
- what final result was obtained.

# 7. Fiber Optics and Transceivers

Fiber carries information using light. It is used when copper cannot reach (more than 100 m), when there is heavy electrical interference, or when high capacity is needed, for example between wiring closets, floors, or buildings.

To choose and connect a fiber link, you must decide the **fiber type**, recognize the **connectors**, respect **polarity** (which end transmits and which receives), and choose a **transceiver** compatible with all of the above.

| Concept | Question it answers | Example |
|---|---|---|
| **Single-mode fiber** (SM) | Do I need long distances? | OS2 on a link between buildings |
| **Multimode fiber** (MM) | Is it a short or medium distance inside the building? | OM3/OM4 between closets |
| **Connector** | Which termination does the cable have? | LC, SC |
| **Polarity** | Does TX on one end reach RX on the other? | TX A → RX B |
| **Transceiver** | Which module converts the electrical signal into light for that fiber? | 1000BASE-LX SFP |
| **Optical safety** | How do I avoid harm to people and connectors? | Do not look into the fiber end |

The typical confusion is assuming that a transceiver that “fits” the port will work: it must also match speed, fiber type, wavelength, and reach.

## 7.1. Advantages

It can provide:

- high capacity;
- long distances;
- electromagnetic immunity;
- electrical isolation.

Do not memorize:

```text
fiber = always better
```

Selection depends on:

- distance;
- technology;
- cost;
- environment;
- equipment;
- maintenance.

## 7.2. Single-mode and multimode

| Characteristic | Single-mode | Multimode |
|---|---|---|
| Typical use | longer distances / backbone | short/medium distances |
| Reference designation | OS2 | OM3 / OM4 |
| Core | smaller (≈ 9 µm) | larger (50 µm; 62.5 µm in legacy OM1) |
| Usual wavelength | 1310 / 1550 nm | 850 nm |

There is no universal rule such as:

```text
multimode = X meters
single-mode = Y kilometers
```

Reach depends on:

```text
Ethernet technology
+
transceiver
+
fiber
+
actual link conditions
```

## 7.3. Connectors

Recognize especially:

- LC;
- SC.

A complete connector catalog is not required.

## 7.4. Polarity

For duplex fiber:

```text
TX A → RX B
RX A ← TX B
```

Connecting transmitters to each other will not create the expected link.

## 7.5. Transceivers

A transceiver must be compatible with:

- speed;
- fiber type;
- wavelength;
- reach;
- connector;
- platform/device.

Examples of Ethernet-over-fiber technologies (IEEE 802.3) that appear on module datasheets:

| Technology | Speed | Fiber | Usual module |
|---|---:|---|---|
| 1000BASE-SX | 1 Gb/s | Multimode, 850 nm | SFP |
| 1000BASE-LX | 1 Gb/s | Single-mode, 1310 nm | SFP |
| 10GBASE-SR | 10 Gb/s | Multimode, 850 nm | SFP+ |
| 10GBASE-LR | 10 Gb/s | Single-mode, 1310 nm | SFP+ |

Rule for reading the name: **S** (short) usually means multimode and short reach; **L** (long) means single-mode and longer reach.

Important principle:

```text
it physically fits
≠
it is technically compatible
```

## 7.6. Safety

- do not look directly into fiber ends;
- do not assume a fiber is inactive;
- protect connectors;
- avoid touching optical surfaces;
- respect bend radius;
- follow lab procedures.

# 8. Wi‑Fi as a Shared Medium

Wi‑Fi uses radio, and multiple devices share the same medium. That changes many of the rules we have seen for cable: the signal weakens with distance and obstacles, other devices can interfere, and all the clients of an access point share transmission time.

This section explains how a client connects to a wireless network, which standards and bands exist, which metrics help assess link quality, and how to troubleshoot a problem **in stages**, separating radio, access, and configuration.

| Concept | Question it answers | Example |
|---|---|---|
| **Shared medium** | Do clients compete for airtime? | 30 laptops on the same AP |
| **Wi‑Fi standard** (IEEE 802.11 / Wi‑Fi generation) | Which technology do the AP and client use? | 802.11ax = Wi‑Fi 6 |
| **Band** | Which frequencies are used? | 2.4 / 5 / 6 GHz |
| **Coverage** | Does enough signal reach the client? | Classroom at the end of the hallway |
| **Metrics** (RSSI, SNR, retries…) | What is the quality of the radio link? | RSSI −70 dBm, many retries |
| **Access stages** (association, authentication) | At which step does the client get stuck? | Sees the SSID but cannot connect |
| **Basic security** (WPA2 / WPA3) | How is access protected? | WPA3-Personal with a passphrase |

We should not mix **radio** (there is signal), **Wi‑Fi access** (I am associated and authenticated), and **IP configuration** (I have an address and a way out): they are different stages with different evidence.

```text
Wi-Fi client
      ↕
      AP
      ↕
wired network
```

## 8.1. Shared medium

Unlike a dedicated full-duplex switched Ethernet link between host and switch, multiple wireless clients may compete for airtime.

Therefore:

```text
PHY rate
≠
throughput
```

## 8.2. IEEE 802.11 standards

Wi‑Fi standards are defined by **IEEE 802.11**; the **Wi‑Fi Alliance** certifies equipment and gives it simpler commercial names.

| IEEE standard | Commercial name | Bands |
|---|---|---|
| 802.11b / a / g | (legacy, no generation name) | 2.4 GHz (b, g) · 5 GHz (a) |
| 802.11n | Wi‑Fi 4 | 2.4 and 5 GHz |
| 802.11ac | Wi‑Fi 5 | 5 GHz |
| 802.11ax | Wi‑Fi 6 / Wi‑Fi 6E | 2.4 and 5 GHz; 6E adds 6 GHz |
| 802.11be | Wi‑Fi 7 | 2.4, 5, and 6 GHz |

The speeds advertised by manufacturers are **theoretical maximums**; the client and the AP use the highest common standard they both support.

## 8.3. Coverage and obstacles

Signal quality may degrade because of:

- distance;
- walls;
- materials;
- geometry;
- placement;
- interference.

Advanced RF propagation physics is not required here.

## 8.4. Bands

### 2.4 GHz

- relatively greater range;
- less spectrum;
- higher probability of interference.

### 5 GHz

- more spectrum/channels;
- strong performance potential;
- relatively shorter range.

### 6 GHz

- additional spectrum;
- requires compatible devices;
- depends on platform/regulation.

Complete channel tables are not a memorization goal.

## 8.5. Initial metrics

| Metric | What it tells us |
|---|---|
| RSSI | Received signal strength |
| SNR | Signal-to-noise ratio |
| Channel utilization | Airtime/resource occupancy |
| PHY rate | Negotiated physical-layer rate |
| Retries | Repeated transmissions |
| Throughput | Useful data transfer |

RSSI is expressed in dBm with negative values: **the closer to 0, the stronger the signal** (−50 dBm is better than −75 dBm).

There is no universal rule:

```text
high RSSI
=
high throughput
```

On the client, these metrics can be checked with `netsh wlan show interfaces` (Windows) or `iw dev <interface> link` / `nmcli device wifi list` (Linux).

## 8.6. Access stages

Simplified sequence:

```text
detect WLAN
→ select SSID
→ 802.11 authentication and association with the AP
→ pass the network security (WPA2/WPA3: passphrase or credentials)
→ obtain configuration
→ test connectivity
→ test service
```

On WPA2/WPA3 networks, the passphrase (or user credentials) is checked **after** association; the earlier “802.11 authentication” is only an initial exchange with the AP.

These stages are different.

Example:

```text
SSID visible
≠
authentication successful
≠
IP configuration correct
≠
Internet reachable
```

## 8.7. Basic security

Recognize:

- open network;
- WPA2;
- WPA3.

Both WPA2 and WPA3 have a **Personal** mode (one shared passphrase) and an **Enterprise** mode (per-user credentials checked against a server). WPA3 is the recommended option when all devices support it, and it is mandatory in the 6 GHz band.

U03 does not aim to teach:

- 802.1X in depth;
- EAP;
- WLC;
- CAPWAP;
- complete enterprise WLAN architecture.

## 8.8. Stage-based troubleshooting

Ask:

```text
Is the SSID visible?
→ Is signal quality sufficient?
→ Does association succeed?
→ Does authentication (passphrase/credentials) succeed?
→ Does the client obtain configuration?
→ Is there connectivity?
→ Is performance acceptable?
```

This separates:

```text
radio
≠
Wi-Fi access
≠
IP configuration
≠
service
```

# 9. Documentation, Maps, and Traceability

Managing a network also means being able to answer:

> **Which switch port is this device actually connected to?**

Without documentation, every fault starts by tracing cables by hand. This section explains how a rack is physically organized, how each connection is labeled so it can be reconstructed, and the difference between a **physical** map (where each thing is and where each cable runs) and a **logical** map (what role each device plays and how they relate).

We will also see that documentation describes the **expected** state and must be compared with the **observed** state, for example with the neighbor information provided by CDP or LLDP.

| Concept | Question it answers | Example |
|---|---|---|
| **Rack** | Where and how are panels and equipment housed? | Rack with 2 patch panels and 2 switches |
| **Labeling** | How do I identify each outlet, panel, and port? | `A1-023 → PP03-18 → SW02-Gi1/0/18` |
| **Cabling record** | Where is each connection and its state recorded? | Outlet–panel–port table |
| **Physical map** | Where is each device, and where does each cable run? | Floor plan with outlets and closet |
| **Logical map** | What function does each device have, and how do they relate? | PC–switch–router–server diagram |
| **CDP / LLDP** (neighbor discovery) | Which device is actually on the other side of this port? | Neighbor `SW2`, port `Gi0/2` |

The typical confusion is treating documentation as the truth: it is an expected state that must be verified and kept up to date.

## 9.1. Rack

A rack may contain:

- patch panels;
- switches;
- routers;
- cable managers;
- fiber;
- PDU;
- UPS.

The goal is not to design a full data center.

It is to understand organization and traceability.

## 9.2. Labeling

A connection should be traceable:

```text
outlet
→ patch panel
→ switch port
```

Example:

```text
A1-023
→ PP03-18
→ SW02-Gi1/0/18
```

A naming convention should be:

- unique;
- consistent;
- documented;
- maintainable.

## 9.3. Minimum record

| Outlet | Patch panel | Switch port | Medium | State |
|---|---|---|---|---|
| A1-023 | PP03-18 | SW02-Gi1/0/18 | Cat 6A | Operational |

## 9.4. Physical map

Represents:

- device;
- location;
- interface;
- medium;
- outlet;
- panel;
- port.

Example:

```text
PC-07
→ outlet A1-023
→ PP03-18
→ SW02 Gi1/0/18
```

## 9.5. Basic logical map

Represents functional relationships:

- device names;
- roles;
- links;
- segments;
- services.

It does not need to reproduce the exact physical layout.

Physical and logical maps answer different questions.

## 9.6. Verify documentation

Documentation represents an **expected** state.

The real network provides the **observed** state.

```text
documentation
→ verify
→ compare
→ update
```

Do not make changes first and document them later from memory.

## 9.7. CDP and LLDP as evidence

**CDP** (Cisco Discovery Protocol) is Cisco-proprietary; **LLDP** (Link Layer Discovery Protocol, IEEE 802.1AB) is the equivalent multivendor standard. Both make each device announce its name and the port it is connected through to its directly connected neighbor.

In a managed environment, a prepared output may show:

```text
Local interface: Gi0/1
Neighbor: SW2
Remote port: Gi0/2
```

This can be used to compare against the documented map.

U03 does not configure CDP/LLDP.

It only interprets the output.

# 10. Interface State, Counters, and SNMP

The final U03 skill is moving from:

```text
“it does not work”
```

to:

```text
symptom
→ scope
→ physical path
→ state
→ counter
→ test
→ hypothesis
→ minimum change
→ new measurement
→ verification
→ documentation
```

To do that, we need **data** from the device itself: its current state and the error counters it accumulates. This section shows how to query them on Windows, Linux, and Cisco IOS, how to interpret a counter **by comparing two measurements over time**, and how SNMP lets us collect the same data remotely and continuously.

| Concept | Question it answers | Example |
|---|---|---|
| **Interface status** | What is the interface's condition right now? | `up`, 1 Gb/s, full-duplex |
| **Counter** | How many events have accumulated since the last restart or reset? | `CRC = 245` |
| **Rate** | How much did the counter change over an interval? | +145 CRC in 5 minutes |
| **Baseline** | What value is normal on this network? | 0 errors/day on that port |
| **SNMP** (Simple Network Management Protocol) | How do I obtain that data remotely and periodically? | An NMS polls the switch every 5 min |

The typical confusion is reading a high counter as a current fault: a counter is accumulated history, and only its **trend** shows whether the problem is still happening.

## 10.1. Interface state

Useful information includes:

- up/down;
- speed;
- duplex;
- autonegotiation;
- errors;
- drops;
- link flaps;
- PoE;
- transceiver.

### Windows

```powershell
Get-NetAdapter
Get-NetAdapterStatistics
```

### Linux

```bash
ip link
ethtool <interface>
```

### Cisco IOS

At interpretation level:

```text
show interfaces
show interfaces status
show interfaces counters errors
```

Full switch CLI administration is not required yet.

## 10.2. Counters

A counter is cumulative.

Example:

```text
CRC = 245
```

by itself does not prove that an active fault exists now.

We need to observe change over time.

### Case A

```text
initial CRC = 245
final CRC   = 245
```

No new CRC errors were observed during the interval.

### Case B

```text
initial CRC = 245
final CRC   = 390
```

The counter increased.

Procedure:

```text
record
→ reproduce traffic/problem
→ measure again
→ compare
```

## 10.3. State, counter, and rate

- **state**: current condition;
- **counter**: accumulated events;
- **rate**: change over an interval;
- **baseline**: normal reference value.

## 10.4. A counter does not automatically identify the cause

Increasing CRC errors may be compatible with:

- cable;
- connector;
- noise;
- interface;
- transceiver;
- other physical problems.

Relate:

```text
counter
+
symptom
+
physical test
+
controlled change
```

## 10.5. SNMP as an observation tool

SNMP allows a management system to obtain information from network devices.

| Component | Function | Example |
|---|---|---|
| **NMS / manager** | Queries or receives information | Zabbix, LibreNMS, PRTG |
| **Agent** | Exposes the device's information | SNMP service on the switch |
| **MIB** (Management Information Base) | Organizes managed information in a tree | Interfaces MIB (IF-MIB) |
| **OID** (Object Identifier) | Identifies one specific value | Operational status of an interface |

Basic model:

```text
NMS / manager
      ↕
    agent
      ↕
managed information
```

### NMS / manager

System that queries or receives information.

### Agent

Component on the managed device that exposes information.

### MIB

Structure that organizes managed information.

### OID

Identifier for one specific managed value.

Examples of observable information:

- interface state;
- octets;
- errors;
- CPU;
- temperature.

## 10.6. Polling and notification

Two basic ideas:

```text
NMS
→ periodic query
→ polling
```

and:

```text
device
→ reports an event
→ notification / trap
```

Queries reach the agent on **UDP 161**; notifications (traps) are sent to the NMS on **UDP 162**.

## 10.7. SNMP versions

| Version | Security | Use |
|---|---|---|
| **SNMPv1** | Community string in clear text | Obsolete |
| **SNMPv2c** | Community string in clear text; better counters and operations | Very widespread, only on controlled management networks |
| **SNMPv3** | Users with authentication and encryption | Recommended |

U03 does not configure SNMPv3 or communities.

The goal is to understand that monitoring can provide evidence even when you are not physically standing in front of the device.

# 11. Integrated Physical Troubleshooting Case

This section brings everything together in a single case: physical path, interface state, counters, tester, controlled change, and documentation. It serves as a model for solving real incidents in an orderly way, without changing several things at once or drawing conclusions before there is evidence.

| Step | Question it answers | Evidence |
|---|---|---|
| **1. Counter trend** | Is the problem happening now? | Initial and final CRC |
| **2. Physical path** | Which elements does the connection pass through? | PC → switch path |
| **3. Physical test** (wiremap) | Is there a measurable defect in the copper? | Tester result |
| **4. Minimum change** | Which single element do I change? | Replaced component |
| **5. Verification** | Has it improved measurably? | Speed, CRC, flaps |
| **6. Documentation** | Is there a record for others? | Incident report |

Scenario:

> A workstation that normally links at 1 Gb/s now negotiates at 100 Mb/s and experiences intermittent disconnections.

Initial evidence:

```text
link up
speed = 100 Mb/s
full-duplex
autonegotiation = on
CRC = 245
```

## 11.1. Step 1 — Do not interpret the counter too quickly

Ask:

> Are CRC errors increasing now?

Record the value.

Reproduce traffic.

Measure again.

## 11.2. Step 2 — Trace the path

```text
PC
→ patch cord
→ outlet
→ horizontal cable
→ patch panel
→ patch cord
→ switch
```

## 11.3. Step 3 — Wiremap

Suppose the result is:

```text
open pair
```

A copper-channel hypothesis becomes stronger.

## 11.4. Step 4 — Minimum change

Instead of changing all of these at once:

- NIC;
- switch;
- configuration;
- cabling;

change one controlled component, for example:

```text
patch cord
```

## 11.5. Step 5 — Verification

After the change:

```text
speed = 1 Gb/s
CRC stable
no new link flaps
```

Now there is evidence of improvement.

## 11.6. Step 6 — Documentation

```text
Symptom:
Scope:
Physical path:
State:
Initial counters:
Test:
Result:
Hypothesis:
Change:
Final counters:
Verification:
Cause:
Prevention:
Conclusion:
```

# 14. What Comes Next in U04 and U05

U03 ends when you can answer:

> **Is there a correct physical or wireless infrastructure, and what evidence proves it?**

Once the physical path has been proven to work, the next question is whether the device is correctly **integrated logically** into the network. The next two units answer that question and complete RA2.

| Unit | Question it answers | Contents |
|---|---|---|
| **U03** | Is there correct physical or wireless infrastructure? | Medium, link, access, testing, SNMP |
| **U04** | Is the device correctly integrated into IPv4? | IPv4, subnetting, VLSM, CIDR, DHCP |
| **U05** | Is it correctly integrated into IPv6? | IPv6, SLAAC, DHCPv6, dual stack |

Later, **U06** returns to the switch from the inside (LEDs, console, MAC table, STP, Layer 2 security), and **U08** covers secure remote access over SSH.

U04 will answer:

> **Is the device correctly integrated into IPv4?**

U05 will answer:

> **Is it correctly integrated into IPv6?**

The progression is:

```text
U03
medium / link / access
        ↓
U04
IPv4 / subnetting / DHCP
        ↓
U05
IPv6 / autoconfiguration
```

The professional rule that remains is:

```text
expected state
≠
observed state
≠
proven cause
```

and:

```text
observe
→ measure
→ interpret
→ change one variable
→ measure again
→ verify
→ document
```
