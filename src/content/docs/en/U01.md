# 1. From Everyday Communication to a Network

We all use networks every day without thinking about them: we send messages, watch videos, print documents, or log in to a learning platform. For a technician, each of those actions is a **communication** that depends on many elements the user never sees.

This section starts from everyday life and builds three basic ideas:

| Idea | Question it answers |
|---|---|
| **Communication** | Which elements are needed for information to arrive? |
| **Data network** | Which organized system makes those communications possible? |
| **Internet** | What happens when we need to communicate with other networks? |

By the end of the section, you will see that a simple application depends on a **chain of elements**, and that knowing that chain is the first step in troubleshooting.

## 1.1. Communicating information

Imagine that you send a photo from your phone to another person. To the user, it looks simple, but several technical elements are involved.

| Element | Role | Example |
|---|---|---|
| **Sender** | Originates the information | Your phone |
| **Receiver** | Receives the information | Destination phone |
| **Message** | Information being exchanged | Photo |
| **Medium** | Carries the signal | Radio, copper, or fiber |
| **Encoding** | Represents information for transmission | Electrical, optical, or radio signal |
| **Protocol** | Defines communication rules | Ethernet, IP, TCP, HTTPS |

A **protocol** is a set of rules that allows two or more systems to exchange information in a compatible way. There is no single protocol that solves the entire communication process. In a real connection, several protocols work together, each solving a different part of the problem.

## 1.2. What is a data network?

A **data network** is an organized system of devices, interfaces, media, protocols, and services that allows applications and systems to exchange information.

A professional network may include:

- desktop computers, laptops, and phones;
- physical or virtual servers;
- network printers, cameras, and sensors;
- switches, routers, access points, and firewalls;
- physical and virtual interfaces;
- copper, fiber, or wireless links;
- services such as DNS or DHCP;
- local, remote, or cloud-hosted resources.

Therefore:

```text
network ≠ a group of computers connected by cables
```

A network also needs to be manageable, scalable, secure, observable, and able to recover from certain failures.

## 1.3. A network is not the same as the Internet

A network can work correctly without Internet access.

```text
PC ── switch ── local server
```

The Internet is a **global interconnection of networks** operated by many different organizations.

```text
PC
 │
switch
 │
router
 │
service provider
 │
Internet
```

This difference matters because an Internet problem does not automatically mean the local network is broken.

## 1.4. Dependencies

A simple application may depend on many components:

```text
client
 → local network
 → gateway
 → provider
 → DNS
 → server
 → application
```

The more dependencies there are, the more important it becomes to separate:

- what we know;
- what we assume;
- what we still need to test.

This way of thinking will be essential for troubleshooting.

# 2. Network Components

A network is made of very different elements: user devices, network devices, cables, radio waves, and services that work “behind the scenes.” To analyze a network, it is useful to classify its elements by the **function** they perform.

| Group | Useful question |
|---|---|
| **End device** (host) | Where is the information created or consumed? |
| **Intermediary device** | Which device connects, forwards, filters, or protects? |
| **Interface** | Through which point does the communication enter or leave? |
| **Medium** | Where does the signal travel? |
| **Service** | Which infrastructure function is being used? |

The same device can belong to several groups depending on what we analyze: a home router, for example, combines router, switch, access point, and firewall functions in one box.

## 2.1. End devices

**End devices** are systems where user or application communications originate or terminate.

Examples:

- desktop computer;
- laptop;
- smartphone;
- server;
- network printer;
- IP phone;
- camera;
- sensor.

A server is also an end device from the network point of view: it sends and receives traffic even though it usually provides services to other systems.

## 2.2. Intermediary devices

**Intermediary devices** help forward, direct, filter, or control traffic. They are not usually the source or destination of the user's information, but without them the information would not arrive.

| Device | Main function | Where it usually is |
|---|---|---|
| **Switch** | Connects devices inside the same local network | Wiring closet, rack, under a desk |
| **Router** | Connects different networks and chooses where to send traffic | At the edge of the network, toward other networks or the provider |
| **Access point (AP)** | Gives wireless access to the wired network | Ceiling or wall of classrooms and offices |
| **Firewall** | Allows or blocks traffic according to rules | Border between networks; also as software on devices |

### Switch

A switch connects devices inside a local area network and makes forwarding decisions based on link-layer information. Later, you will study how it learns MAC addresses and how it chooses the correct port for a frame.

### Router

A router connects different networks and decides where to forward IP traffic. For now, keep one basic idea:

```text
same network → direct communication may be possible
different network → a router is normally involved
```

### Access point

An **access point** connects wireless devices to the network. It provides Wi-Fi access, but it should not automatically be confused with a router.

### Firewall

A firewall applies security policies to traffic. It may be integrated into another device or exist as a separate system.

## 2.3. Interfaces

A **network interface** is the point through which a device connects to a network.

It may be:

- Ethernet;
- Wi-Fi;
- fiber;
- virtual;
- logical.

A single device may have several interfaces and may therefore participate in more than one network or communication path.

## 2.4. Media

Information can travel over different physical or wireless media:

- copper;
- fiber optics;
- radio.

In U03, you will study these media in more detail: connectors, categories, range, loss, interference, structured cabling, and verification.

## 2.5. Infrastructure services

A network does not depend only on hardware. It also depends on services.

Two examples that will appear repeatedly are:

- **DNS**: relates names to addresses;
- **DHCP**: automatically provides network configuration parameters.

In this unit, you only need to recognize their role. Detailed analysis comes later.

# 3. Representing a Network

A technician cannot see a whole network at a glance: cables run above false ceilings, devices sit in closets, and information is invisible. That is why technicians work with **representations**: diagrams and topologies that show what matters and hide the rest.

This section answers three questions:

| Question | Concept |
|---|---|
| How do I draw a network so another technician can understand it? | Physical and logical **topology** |
| Which typical shapes do networks have, and what are their advantages? | Star, hierarchical, mesh, bus, and ring |
| What happens if one element fails? | **Redundancy** and **single point of failure (SPOF)** |

A good representation is the basis of network documentation and of any later troubleshooting.

## 3.1. Why we use representations

A real network contains too much detail to analyze all at once. We therefore use **diagrams and topologies**.

A useful representation should help answer questions such as:

- What devices exist?
- How are they connected?
- Which links are critical?
- Which systems depend on others?
- What path could a communication follow?

## 3.2. Physical and logical topology

A **physical topology** describes the physical connections between devices and links.

A **logical topology** describes how communication is organized or flows from a functional point of view.

They do not always match.

Before looking at each topology, it helps to have an overview:

| Topology | Idea | Current use |
|---|---|---|
| **Star** | All devices connect to a central point | Ethernet and Wi-Fi LANs |
| **Hierarchical** (extended star) | Several stars joined to a core | Company and school networks |
| **Mesh** | Several paths between devices | Network cores, links between sites |
| **Bus** | One medium shared by all | Historical (coaxial Ethernet) |
| **Ring** | Each node passes information to the next one | Historical and some fiber rings |

## 3.3. Star topology

In a star topology, several devices connect to a central point.

```text
 PC1
  |
PC2 ─ switch ─ PC3
  |
 PC4
```

Common advantages:

- easy to expand;
- failure of one access link usually affects only one device;
- easier fault isolation in many cases.

Risk:

- if the central device has no redundancy, it may become a single point of failure.

## 3.4. Hierarchical structure

Enterprise networks are often organized in levels to improve scalability, administration, and redundancy.

You do not need to memorize a complete campus design yet. The important idea is that large networks are usually divided into functional blocks.

## 3.5. Mesh

In a mesh topology, multiple paths may exist between certain points.

This can improve resilience, but it also increases:

- cost;
- complexity;
- the need for control mechanisms.

## 3.6. Bus and ring

Bus and ring topologies are important for understanding the evolution of networking and some current systems, although they are not the typical design of a modern Ethernet LAN.

## 3.7. Redundancy and SPOF

**Redundancy** provides alternate components or paths in order to reduce the impact of failures.

A **SPOF** (*Single Point of Failure*) is a component whose failure may completely interrupt a function or service.

Example:

```text
PCs ─ single switch ─ single router ─ Internet
```

The switch or router may be a SPOF depending on the service being analyzed.

The right question is not only:

> “Is there redundancy?”

but:

> “What service are we trying to keep available, and which component could remove all alternatives?”

# 4. Network Types and Service Architectures

The same network can be classified from several points of view: by its **scope**, by **who manages it and who may use it**, or by how **services are organized** among devices. We should not mix these criteria: a network can be a LAN, private, and client-server at the same time.

| Criterion | Question | Examples |
|---|---|---|
| **Scope** | What geographic area does it cover? | PAN, LAN, WLAN, MAN, WAN |
| **Management and access** | Who manages it and who can connect? | Private network, public network |
| **Service architecture** | How are roles shared among devices? | Client-server, P2P |

At the end of the section, you will also see why networks **keep changing**, and where you will study those changes in this course.

## 4.1. Classification by scope

Network-type acronyms are useful only if the classification criterion is understood.

| Type | General idea |
|---|---|
| **PAN** | short-range personal environment |
| **LAN** | local network, typically within a home, classroom, office, or building |
| **WLAN** | LAN that provides wireless access |
| **MAN** | metropolitan area network: connects sites within one city (e.g., municipal fiber) |
| **WAN** | connects geographically separated sites or networks |

These categories do not fully describe a network by themselves.

The same network can simultaneously be:

- a LAN;
- private;
- Ethernet-based;
- client-server.

Those are different criteria.

## 4.2. Public and private networks

“Public” and “private” may be used in different contexts. Do not interpret “public network” as “everything is open.”

For example, a library may provide public Wi-Fi access, while:

- the infrastructure is still managed;
- users cannot access every resource;
- filtering and policies may exist;
- being able to connect does not grant control over the network.

## 4.3. Client and server are roles

A **client** requests a service.

A **server** provides a service.

These terms describe roles in a communication, not necessarily permanent device types.

The same machine may act as a client in one communication and as a server in another.

Example:

```text
PC → DNS server
PC = client
DNS = server
```

An application server may itself be a client of a database server.

## 4.4. Client-server architecture

In a client-server architecture, some systems provide services to others.

Common advantages:

- centralized administration;
- access control;
- more organized backups;
- shared data;
- common policies.

Risks:

- dependency on central services;
- need for redundancy;
- high impact when a central component fails without an alternative.

## 4.5. Peer-to-peer architecture

In a **peer-to-peer (P2P)** model, systems may share resources directly with each other.

This does not mean “no network” or “no rules.” It only changes how roles and resources are distributed.

## 4.6. Factors driving network evolution

Networks keep growing and changing. Knowing why helps you understand why new technologies appear and others are abandoned.

| Factor | What it demands from the network | Example |
|---|---|---|
| Mobility | Access from anywhere and on any device | Building-wide Wi-Fi, 4G/5G |
| Cloud services | Reliable Internet connectivity with enough capacity | Cloud email, office apps, and storage |
| Video and collaboration | High bandwidth and low latency | Video calls, streaming, online training |
| Internet of Things (IoT) | Huge numbers of addressable devices | Sensors, cameras, HVAC |
| Virtualization | Networks that also exist inside servers | Virtual machines, containers |
| Remote work | Secure access from outside the organization | VPN, published services |
| Security | Segmentation, access control, logging | VLANs, ACLs, encryption |
| IPv4 exhaustion | New addressing | IPv6, NAT |
| Automation | Configuring many devices at once | Templates, APIs, management tools |

Many of these factors come back throughout the course: IPv6 in U05, VLANs in U07, ACLs in U08, NAT in U10.

# 5. Layered Architecture: A First TCP/IP Map

When something fails in a network, the list of possible causes is huge: a cable, a setting, a service, the application itself… To stay organized, technicians use **layered models**: they divide communication into levels, and each level solves one specific problem.

In this section, you will build a first map with the **five-layer TCP/IP model** and meet the **OSI model** as a reference. The goal is not to memorize lists, but to have one question for each layer:

| Layer | Question |
|---|---|
| Application | Which service does the application need? |
| Transport | Which process should receive the data? |
| Network | Which network and host should it reach? |
| Data Link | How is it delivered on the local link? |
| Physical | How is the signal transmitted? |

In U02, you will study in detail how these layers work together (encapsulation, headers, and traffic analysis).

## 5.1. Why layers are useful

Network communication solves several different problems at the same time:

- transmitting bits;
- delivering data across a local link;
- reaching another network;
- communicating between processes;
- providing application services.

Trying to explain all of this as one single mechanism would be too complex.

We therefore use **layers**: related functions are grouped together so we can study each problem at the appropriate level.

## 5.2. Five-layer TCP/IP model

We will use a five-layer TCP/IP model as our initial map:

| Layer | Initial functional question | Examples |
|---|---|---|
| **Application** | What service is the application using? | HTTP, DNS, DHCP, SSH |
| **Transport** | Which process or service should receive the data? | TCP, UDP, ports |
| **Network** | Which IP interface/network should the data reach? | IPv4, IPv6, routing |
| **Data link** | How is data delivered on the local link? | Ethernet, MAC |
| **Physical** | How is the signal transmitted? | copper, fiber, radio |

This model does not mean that “every problem belongs to exactly one layer.” It is a tool for organizing functions and questions.

## 5.3. OSI as a reference model

The OSI model divides communication into seven layers. It is still useful as a conceptual and professional reference.

You do not need to memorize every detail yet. In U02, both models will be related more precisely.

## 5.4. First troubleshooting use

Suppose a user says:

> “I cannot open a website.”

We still do not know whether the problem involves:

- the physical connection;
- the local network;
- IP addressing;
- routing;
- DNS;
- the server;
- the application.

Layers help us avoid premature conclusions and ask better questions.

# 6. Identifiers: Name, Port, IP, MAC, and Gateway

For a communication to reach its destination, we need to identify **what** we want, **where** it is, and **how to leave** our network. Different identifiers exist because they answer different questions, and each one belongs to a different layer of the model in the previous section.

| Identifier | Layer | Example | Seen by the user |
|---|---|---|---|
| **Name** | Application | `www.example.com` | Yes |
| **Port** | Transport | `443` | Sometimes (in the URL) |
| **IP address** | Network | `192.168.10.25` | Rarely |
| **MAC address** | Data Link | `00:1A:2B:3C:4D:5E` | No |
| **Default gateway** | Network | `192.168.10.1` | No |

Understanding what each one does will later help you decide what to check when something fails: a name problem is not fixed by changing a MAC address.

## 6.1. Functional map

| Element | Question it helps answer |
|---|---|
| **Name** | What resource or system do I want to use? |
| **Port** | What service or process do I want to reach? |
| **IP address** | Which IP interface is the destination? |
| **MAC address** | Which interface participates on the local link? |
| **Default gateway** | Which router receives traffic for remote networks? |

They are not equivalent or interchangeable.

## 6.2. Name

Names are easier for people to remember than addresses.

Example:

```text
www.example.com
```

To communicate using IP, that name normally needs to be related to an address. DNS participates in that process.

## 6.3. Port

A host can run several network applications at the same time. **Port numbers** help identify transport-layer services or processes.

Common examples:

- HTTP: 80/TCP;
- HTTPS: 443/TCP;
- DNS: 53/UDP and 53/TCP depending on the case;
- SSH: 22/TCP.

Transport will be studied in more depth in U02.

## 6.4. IP address

An IP address identifies an interface in the context of an IP network.

IPv4 example:

```text
192.168.10.25
```

An address is not interpreted in isolation. We also need information such as the prefix or subnet mask.

Network, broadcast, subnetting, and VLSM calculations belong to U04.

## 6.5. MAC address

A MAC address is used by link-layer technologies such as Ethernet to identify interfaces on the local link.

Example:

```text
00:1A:2B:3C:4D:5E
```

In U02, you will observe MAC addresses inside frames. In U06, you will study how switches use them.

## 6.5.1. Decimal, binary, and hexadecimal

Identifiers are binary numbers that we write in a more convenient way:

| Identifier | Size | How it is written | Example |
|---|---|---|---|
| IPv4 | 32 bits | 4 decimal numbers (0–255) separated by dots | `192.168.0.1` |
| MAC | 48 bits | 12 hexadecimal digits | `00E0.A357.B5AB` |

An octet (8 bits) has the weights `128 64 32 16 8 4 2 1`. For example:

```text
192 = 128 + 64          → 1100 0000 → C0
255 = all bits set to 1 → 1111 1111 → FF
```

Each hexadecimal digit (0–9, A–F) represents **4 bits**, so one octet is written with two digits. You will practice conversions in depth in U04 (subnetting) and U05 (IPv6).

## 6.6. Default gateway

The **default gateway** is normally the address of the router to which a host sends traffic for networks it does not consider local.

A useful first model is:

```text
local destination
→ communication inside the local network

remote destination
→ a path to other networks is needed
→ the default gateway is normally used
```

The exact local/remote decision will be studied with IPv4 and IPv6.

# 7. Host State and First Tools

When an incident occurs, the first step is not to change anything, but to **observe the state** of the affected device and run simple tests. Every operating system includes tools for this, and in this section you will learn which question each one answers.

| Tool | Question it answers |
|---|---|
| `ipconfig` / `ip addr` / `ip route` | What network configuration does the device have? |
| `ping` | Is there IP communication with a specific destination? |
| `nslookup` / `dig` | Is a name correctly translated into an address? |
| `tracert` / `traceroute` | Which routers does the traffic cross toward a destination? |

Before the tools, it is worth separating three ideas that are often confused: **connectivity**, **performance**, and **availability**.

## 7.1. Connectivity, performance, and availability

These concepts are not the same.

### Connectivity

Indicates whether communication is possible between two points.

### Performance

Describes how communication behaves in terms such as:

- available bandwidth;
- throughput;
- latency;
- loss;
- delay variation.

### Availability

Describes how long a service or system remains operational and reachable.

A service may have connectivity but still provide unacceptable performance.

## 7.2. Read the configuration before changing it

Before modifying a network, first observe its current state.

On Windows:

```powershell
ipconfig
ipconfig /all
```

On Linux, commands may include:

```bash
ip addr
ip route
```

Depending on the system, you may observe:

- interfaces;
- IP address;
- prefix or subnet mask;
- default gateway;
- DNS servers;
- interface status.

The goal is not to memorize every line. The first goal is to locate relevant information.

## 7.3. `ping`

`ping` uses ICMP to provide evidence of IP reachability under certain conditions.

Example:

```bash
ping 192.168.1.1
```

A successful `ping` provides evidence that IP communication exists between source and destination for that test.

However, a failed `ping` **does not prove the cause by itself**. Possible causes include:

- a link problem;
- incorrect addressing;
- missing routing;
- filtering;
- a powered-off host;
- a policy blocking ICMP.

Therefore:

```text
test result ≠ complete diagnosis
```

## 7.4. DNS lookup

If communication to an IP address works but a name does not, name resolution should be checked.

Common tools:

```text
nslookup
dig
```

Example:

```bash
nslookup www.example.com
```

This separates two questions:

1. Can I reach an IP address?
2. Can I correctly resolve the name?

## 7.5. `traceroute` / `tracert`

These tools help observe part of the path toward a destination.

Windows:

```powershell
tracert 8.8.8.8
```

Linux:

```bash
traceroute 8.8.8.8
```

Their output should not be interpreted as a perfect map of the Internet. Some devices may not respond to specific probes, and routing may be asymmetric.

# 8. First Look at Wireshark

The tools in the previous section show **results** (it answers / it does not). A **packet analyzer** such as Wireshark goes one step further: it lets you see the messages that actually travel across the network.

Wireshark is a free tool widely used by professionals. In U01, we use it for one main idea:

> a technical claim becomes stronger when it can be related to observable evidence.

| In U01 | In U02 and later |
|---|---|
| Open a capture, filter (`dns`, `icmp`), count, and read the *Info* column | Headers, fields, ports, capture filters, and protocol analysis |

## 8.1. Capture responsibly

Traffic captures may reveal sensitive information. Use Wireshark only:

- on authorized systems and networks;
- for legitimate educational or professional purposes;
- while avoiding unnecessary collection of personal data;
- according to school or organizational rules.

## 8.2. What to observe first

In a simple capture, you may recognize:

- time;
- source;
- destination;
- identified protocol;
- length;
- packet summary.

You do not need to interpret every field yet.

The initial question is simpler:

> “What communication am I observing, and what evidence does it provide?”

## 8.3. The capture point matters

A capture only shows traffic visible from the point where it is taken.

Therefore, the absence of packets does not always mean “the traffic does not exist.” It may also mean that you are observing from a location that cannot see it.

This idea becomes essential in U02.

# 9. Evidence-Based Troubleshooting

A good technician is not the one who knows the most commands, but the one who **reasons** best with the data collected. Troubleshooting does not mean running random commands until something works: it means asking questions, testing them, and drawing conclusions the evidence can support.

A useful framework is:

```text
symptom
→ question
→ hypothesis
→ test
→ evidence
→ conclusion
```

When an incident is corrected:

```text
conclusion
→ minimum change
→ verification
```

| Term | Meaning | Example |
|---|---|---|
| **Symptom** | What is observed or reported | “No website opens” |
| **Fact** | Something that has been checked | `ping 8.8.8.8` replies |
| **Hypothesis** | A possible explanation | “The configured DNS server does not answer” |
| **Test** | An action that answers a question | `nslookup www.example.com` |
| **Evidence** | The observable result of the test | “DNS request timed out” |

This is not a rigid recipe. It is a way to avoid unsupported changes.

## 9.1. Symptom

A symptom describes what the user or technician observes.

Weak description:

> “The Internet is broken.”

Better description:

> “The host can open local resources but cannot resolve external names.”

The more precise the symptom, the better the next questions can be.

## 9.2. Fact

A **fact** is something observed or verified.

Examples:

- the interface is up;
- the host has an IP address;
- `ping` to the gateway succeeds;
- `nslookup` returns an error.

## 9.3. Hypothesis

A **hypothesis** is a possible explanation.

Example:

> “The configured DNS service may not be responding.”

It should not be treated as a conclusion until evidence is collected.

## 9.4. Test

A test should answer a specific question.

Example:

> “If I want to know whether the issue is limited to name resolution, I will compare an IP-based test with a DNS lookup.”

## 9.5. Evidence

Evidence is the observable result of a test.

It should help you:

- support a hypothesis;
- weaken it;
- eliminate a possibility;
- decide what to test next.

## 9.6. Guided case: IP works, name does not

Symptom:

> A host can reach `8.8.8.8`, but it cannot open a website by name.

Initial facts:

- there is IP reachability to an external destination;
- name-based access fails.

Reasonable hypothesis:

- the problem may involve name resolution.

Next test:

```bash
nslookup www.example.com
```

Correct conclusion:

- the lookup result will provide evidence about DNS.

Incorrect conclusion:

> “The network works perfectly.”

Reachability to one specific IP address does not prove that every network service is working.

# 10. Reading a Complete Situation

In practice, incidents do not arrive in order: they arrive as a sentence from the user (“it doesn't work”) and a set of incomplete data. This section proposes a way to **organize the information** before acting, bringing together everything in the unit.

When you face a simple incident, separate these questions:

| Question | What you get |
|---|---|
| What is the user trying to do? | The affected service |
| Which components are involved? | The chain of dependencies |
| What information do I have? | The facts |
| What information is missing? | What you must not assume |
| Which test gives the most information? | The next step |

## 10.1. What is the user trying to do?

Example:

> access a web application by name.

## 10.2. What components are involved?

For example:

```text
PC
→ interface
→ switch
→ router
→ DNS
→ server
```

## 10.3. What information do I already have?

- IP address;
- gateway;
- DNS;
- interface state;
- test result.

## 10.4. What information is missing?

Do not fill information gaps with assumptions.

You may still need to know:

- whether the gateway is reachable;
- whether the name resolves;
- whether other hosts have the same issue;
- whether the server is available.

## 10.5. Which test gives the most useful information?

A good test is not simply a command you know how to run. It is a test that helps distinguish between hypotheses.

# 11. Responsible Use of AI Assistants

AI assistants have become a common tool for technical questions. They can save time, but **they cannot see your network**: they answer based on what you tell them and on general patterns, and they can be wrong with great confidence.

An AI-generated answer may include:

- a correct explanation;
- an excessive simplification;
- an unsupported assumption;
- an unnecessary command;
- a conclusion not justified by the evidence.

Use AI as a support tool, not as a replacement for technical reasoning.

A useful process is:

1. identify the claims being made;
2. separate facts from hypotheses;
3. check what evidence is used;
4. verify commands and concepts;
5. compare the answer with documentation and real results;
6. correct the answer when necessary.

Never change a critical configuration only because an AI system suggested it.

# 12. U01 Summary

At the end of this unit, keep these ideas.

## 12.1. A network is a system

It includes:

```text
devices
+ interfaces
+ media
+ protocols
+ services
+ configurations
+ dependencies
```

## 12.2. The Internet is not the same as a network

A local network can work without Internet access.

## 12.3. Devices have different roles

- host: originates or receives communication;
- switch: connects devices inside a LAN;
- router: connects networks;
- access point: provides wireless access;
- firewall: applies traffic policies.

## 12.4. A topology helps us reason

It makes connections, dependencies, redundancy, and single points of failure visible.

## 12.5. Layers organize functions

The TCP/IP model helps separate problems and questions without forcing us to study the entire communication process at once.

## 12.6. Identifiers answer different questions

```text
name → resource
port → service/process
IP → IP destination
MAC → interface on the local link
gateway → path toward remote networks
```

## 12.7. Observe before changing

Read the configuration, check the state, and collect evidence before making changes.

## 12.8. Troubleshooting means reasoning

```text
symptom
→ question
→ hypothesis
→ test
→ evidence
→ conclusion
```

# 13. Professional Terms You Should Recognize

| Term | Initial meaning |
|---|---|
| **host** | end device participating in communications |
| **interface** | point where a device connects to a network |
| **switch** | device that connects systems inside a LAN |
| **router** | device that connects networks |
| **access point (AP)** | wireless access device |
| **firewall** | system that applies traffic policies |
| **LAN** | local area network |
| **WLAN** | LAN with wireless access |
| **WAN** | wide area network |
| **topology** | representation of network connections and relationships |
| **redundancy** | alternate resources or paths |
| **SPOF** | single point of failure |
| **protocol** | communication rules |
| **IP address** | IP identifier of an interface |
| **MAC address** | identifier used on the local link |
| **port** | transport service/process identifier |
| **default gateway** | router used to reach remote networks |
| **DNS** | name-resolution service |
| **DHCP** | automatic network-configuration service |
| **latency** | delay |
| **throughput** | effective amount of data transferred per unit of time |
| **packet capture** | captured network traffic |
| **evidence** | observable result supporting a technical conclusion |
| **troubleshooting** | systematic diagnostic and problem-solving process |
