# 1. From Everyday Communication to a Network

We all use networks every day without thinking about them: we send messages, watch videos, print documents, or log in to a learning platform. For a technician, each of those actions is a **communication** that depends on many elements the user never sees.

This section starts from everyday life and builds three basic ideas:

| Idea | Question it answers |
|---|---|
| **Communication** | Which elements are needed for information to arrive? |
| **Data network** | Which organized system makes those communications possible? |
| **Internet** | What happens when we need to communicate with other networks? |

By the end of the section, you will see that a simple application depends on a **chain of elements**, and that knowing that chain is the first step in troubleshooting.

## 1.1. Communicating information

Imagine that you send a photo from your phone to another person. To the user, it looks simple, but several technical elements are involved.

| Element | Role | Example |
|---|---|---|
| **Sender** | Originates the information | Your phone |
| **Receiver** | Receives the information | Destination phone |
| **Message** | Information being exchanged | Photo |
| **Medium** | Carries the signal | Radio, copper, or fiber |
| **Encoding** | Represents information for transmission | Electrical, optical, or radio signal |
| **Protocol** | Defines communication rules | Ethernet, IP, TCP, HTTPS |

A **protocol** is a set of rules that allows two or more systems to exchange information in a compatible way. There is no single protocol that solves the entire communication process. In a real connection, several protocols work together, each solving a different part of the problem.

## 1.2. What is a data network?

A **data network** is an organized system of devices, interfaces, media, protocols, and services that allows applications and systems to exchange information.

A professional network may include:

- desktop computers, laptops, and phones;
- physical or virtual servers;
- network printers, cameras, and sensors;
- switches, routers, access points, and firewalls;
- physical and virtual interfaces;
- copper, fiber, or wireless links;
- services such as DNS or DHCP;
- local, remote, or cloud-hosted resources.

Therefore:

```text
network ≠ a group of computers connected by cables
```

A network also needs to be manageable, scalable, secure, observable, and able to recover from certain failures.

## 1.3. A network is not the same as the Internet

A network can work correctly without Internet access.

```text
PC ── switch ── local server
```

The Internet is a **global interconnection of networks** operated by many different organizations.

```text
PC
 │
switch
 │
router
 │
service provider
 │
Internet
```

This difference matters because an Internet problem does not automatically mean the local network is broken.

## 1.4. Dependencies

A simple application may depend on many components:

```text
client
 → local network
 → gateway
 → provider
 → DNS
 → server
 → application
```

The more dependencies there are, the more important it becomes to separate:

- what we know;
- what we assume;
- what we still need to test.

This way of thinking will be essential for troubleshooting.

### Key ideas

- Every communication needs a sender, a receiver, a message, a medium, encoding, and **protocols**; no single protocol solves the whole communication.
- A network is not just a set of devices connected by cables: it includes services, configurations, and the need to administer it.
- A local network can work perfectly well without the Internet.
- A simple application depends on a **chain of elements**: separate what you know, what you assume, and what you need to verify.

### Check your understanding

1. A user says "the network is down" because an external website will not load, but they can print to the classroom printer without problems. What would you tell them?
2. Name three elements of a network that are **not** devices.
3. You open the school intranet by name; both its server and its DNS server are inside the school network. In the chain `client → local network → gateway → provider → DNS → server`, which elements are not involved?

# 2. Network Components

A network is made of very different elements: user devices, network devices, cables, radio waves, and services that work “behind the scenes.” To analyze a network, it is useful to classify its elements by the **function** they perform.

| Group | Useful question |
|---|---|
| **End device** (host) | Where is the information created or consumed? |
| **Intermediary device** | Which device connects, forwards, filters, or protects? |
| **Interface** | Through which point does the communication enter or leave? |
| **Medium** | Where does the signal travel? |
| **Service** | Which infrastructure function is being used? |

The same device can belong to several groups depending on what we analyze: a home router, for example, combines router, switch, access point, and firewall functions in one box.

## 2.1. End devices

**End devices** are systems where user or application communications originate or terminate.

Examples:

- desktop computer;
- laptop;
- smartphone;
- server;
- network printer;
- IP phone;
- camera;
- sensor.

A server is also an end device from the network point of view: it sends and receives traffic even though it usually provides services to other systems.

## 2.2. Intermediary devices

**Intermediary devices** help forward, direct, filter, or control traffic. They are not usually the source or destination of the user's information, but without them the information would not arrive.

| Device | Main function | Where it usually is |
|---|---|---|
| **Switch** | Connects devices inside the same local network | Wiring closet, rack, under a desk |
| **Router** | Connects different networks and chooses where to send traffic | At the edge of the network, toward other networks or the provider |
| **Access point (AP)** | Gives wireless access to the wired network | Ceiling or wall of classrooms and offices |
| **Firewall** | Allows or blocks traffic according to rules | Border between networks; also as software on devices |

### Switch

A switch connects devices inside a local area network and makes forwarding decisions based on link-layer information. Later, you will study how it learns MAC addresses and how it chooses the correct port for a frame.

### Router

A router connects different networks and decides where to forward IP traffic. For now, keep one basic idea:

```text
same network → direct communication may be possible
different network → a router is normally involved
```

### Access point

An **access point** connects wireless devices to the network. It provides Wi-Fi access, but it should not automatically be confused with a router.

### Firewall

A firewall applies security policies to traffic. It may be integrated into another device or exist as a separate system.

## 2.3. Interfaces

A **network interface** is the point through which a device connects to a network.

It may be:

- Ethernet;
- Wi-Fi;
- fiber;
- virtual;
- logical.

A single device may have several interfaces and may therefore participate in more than one network or communication path.

## 2.4. Media

Information can travel over different physical or wireless media:

- copper;
- fiber optics;
- radio.

In U03, you will study these media in more detail: connectors, categories, range, loss, interference, structured cabling, and verification.

## 2.5. Infrastructure services

A network does not depend only on hardware. It also depends on services.

Two examples that will appear repeatedly are:

- **DNS**: relates names to addresses;
- **DHCP**: automatically provides network configuration parameters.

In this unit, you only need to recognize their role. Detailed analysis comes later.

### Key ideas

- We classify network elements by their **function**: end device, intermediary device, interface, medium, and service.
- A switch connects devices inside a local network; a router connects different networks; an access point provides wireless access (it is not automatically a router); a firewall applies policies.
- A device can have several interfaces, and a single box can combine several functions (the home "router").
- DNS and DHCP are **infrastructure services**: the network depends on them even if users never see them.

1. Classify: smartphone, access point, fiber cable, DHCP server, laptop Wi-Fi adapter.
2. Why is a server an **end** device if it provides services to other devices?
3. Which functions does the "router" that an ISP installs in a home usually combine?

# 3. Representing a Network

A technician cannot see an entire network at a glance: cables run through drop ceilings, equipment sits in cabinets, and information is invisible. That is why technicians work with **representations**: diagrams that show what matters and hide the rest. In this module, you will also build and test many networks in a simulator, **Cisco Packet Tracer**, which is itself a "live" diagram.

| Concept | Question it answers | Example |
|---|---|---|
| **Physical topology** | Where are the devices, and where does each cable run? | Classroom floor plan with the rack and wall jacks |
| **Logical topology** | How is communication organized: which networks exist and how are they connected? | Diagram with two networks joined by a router |
| **Link** | What joins two devices, and through which interfaces? | `SW-20 G0/1 ↔ R-20 G0/0/0` |
| **Interface name** | Which specific port is it? | `Fa0/2`, `G0/0/1` |
| **Link light** | Is there a link on that port? | Green, amber, red |
| **Network simulator** | How can I build and test a network without real equipment? | Packet Tracer |

A good representation is the foundation of documentation and of any later troubleshooting. But keep in mind from the start an idea we will repeat: **a diagram shows how the network should be; only a test shows how it behaves**.

## 3.1. Why we use representations

A real network contains too much detail to analyze all at once. We therefore use **diagrams and topologies**.

A useful representation should help answer questions such as:

- What devices exist?
- How are they connected?
- Which links are critical?
- Which systems depend on others?
- What path could a communication follow?

## 3.2. Physical and logical topology

The **physical topology** describes how devices are physically connected: where each device is, which cable leaves each port, and which cabinet it reaches.

The **logical topology** describes how communication is organized from a functional point of view: which networks exist, which devices belong to each one, and where traffic passes between them.

They do not always match. Two examples:

| Situation | Physical view | Logical view |
|---|---|---|
| A classroom with 20 wired PCs and 10 laptops on Wi-Fi | PCs cabled to a switch in the rack; laptops connected by radio to an access point on the ceiling | A single network: PCs and laptops communicate as if they were in the same "place" |
| A school with administration and students on the same floor | All devices connected to the same switch | Two separate networks that can communicate only through a router and its rules (you will build this in U07) |

Historically, old *hubs* offered another classic example: physically they formed a star, but logically they behaved like a **bus**, because everything that arrived on one port was repeated on all the others.

A technician needs both views: the physical one to **find** a cable or a port, and the logical one to **understand** why two devices can or cannot communicate.

## 3.3. Reading a diagram: devices, interfaces, and links

A network diagram is always read with the same elements:

| Element | How it appears | What you should read |
|---|---|---|
| **Device** | Icon with a name (`PC-07`, `SW-20`, `R-20`) | What type of device it is and what it is called |
| **Interface** | Label next to the cable end (`Fa0/2`, `G0/1`) | Which specific port the communication enters or leaves |
| **Link** | Line between two interfaces | Which two interfaces it joins, and with what type of medium |
| **Cloud** | Cloud icon (Internet, provider) | A part we **do not** detail: every diagram simplifies |

A link is read from one end to the other: **device + interface ↔ interface + device**. For example:

```text
SW-20 G0/1  ↔  G0/0/0 R-20
```

It reads: "interface GigabitEthernet 0/1 on switch SW-20 is connected to interface GigabitEthernet 0/0/0 on router R-20."

### Interface names

Network devices name each port by its **type** and its **position**:

| Name (short) | Full name | Maximum speed | How to read the position |
|---|---|---|---|
| `Fa0/2` | FastEthernet0/2 | 100 Mb/s | module 0, port 2 |
| `G0/1` or `Gi0/1` | GigabitEthernet0/1 | 1 Gb/s | module 0, port 1 |
| `G0/0/1` | GigabitEthernet0/0/1 | 1 Gb/s | slot 0, module 0, port 1 (modular routers) |
| `Fa0` / `G0` | FastEthernet0 / GigabitEthernet0 | — | the only interface of a PC or printer |

You do not need to memorize the numbering of every model: you only need to read it and copy it exactly into the documentation. A one-digit mistake in a diagram sends the next technician to the wrong port.

## 3.4. Reading a network in Packet Tracer

**Cisco Packet Tracer** is a free network simulator that you will use throughout the module. It lets you build a topology, configure devices, and **test** communication without the real equipment. In this unit, we use it mainly to **represent and observe**.

### Elements of the window

| Element | What it is for |
|---|---|
| **Logical workspace** | The usual view: devices, links, and labels. It is the logical topology, drawn |
| **Physical workspace** | Buildings, wiring closets, and racks: the physical location of the devices |
| **Device and connection panels** (bottom) | Choose devices (*Network Devices*, *End Devices*…) and cables (*Connections*) |
| **Realtime / Simulation mode** (bottom-right corner) | Real time, or step by step to see each message (you will use it in U02) |
| **Fast Forward Time** | Moves the simulation clock forward so you do not have to wait for ports to come up |

### The device window

Clicking a device opens its window, which has several tabs:

| Tab | What it contains | Devices |
|---|---|---|
| **Physical** | What the device looks like: modules, ports, power button | All |
| **Config** | Settings with forms: *Display Name*, interfaces, IP | All |
| **Desktop** | User utilities: *IP Configuration*, *Command Prompt*, web browser | PCs, laptops, servers |
| **CLI** | The device's command line (Cisco IOS) | Switches and routers |

Watch out for a common confusion: the **Display Name** (*Config* tab) is the name you see on the diagram; the *hostname* configured from the CLI is the device's internal name. In this unit, we document with the *Display Name*.

### Link lights

Each end of a link shows a colored indicator. It is your first evidence of the physical state:

| Color | What it means | What to do |
|---|---|---|
| **Green** | There is a link: the interface can send and receive | Nothing, but remember that green does not prove that the devices communicate |
| **Amber** | A switch port is getting ready before forwarding traffic (a few seconds; the reason is covered in U06) | Wait or use *Fast Forward Time*; do not replace the cable |
| **Red** | No link: cable in the wrong port, other end powered off, or **interface disabled** | Check the configuration of both interfaces before replacing the cable |

On routers, interfaces are **disabled** by default: a red link between two newly connected routers is expected, not a faulty cable.

### Cables

Packet Tracer offers several connection types: automatic (lightning-bolt icon: the program chooses the cable), copper straight-through, copper crossover, console, fiber, and serial. In this unit, it is enough to choose the automatic cable or **straight-through** copper between a PC and a switch. Why the others exist is covered in U03.

### Testing communication: *Add Simple PDU*

The **Add Simple PDU** tool (closed-envelope icon) sends a communication test between two devices: click **the source first** and then the destination. The result appears in the bottom-right list as **Successful** or **Failed**. If a result surprises you right after connecting a cable, press *Fast Forward Time* and repeat the test.

### Documenting inside the file

- **Port labels:** *Options → Preferences → Interface → Always Show Port Labels in Logical Workspace* (in some versions, on another *Preferences* tab). If you do not enable them, hovering over a link also shows its ports.
- **Notes** (*Place Note*): free text on the diagram to explain a decision or a state.
- **Saving:** Packet Tracer files use the `.pkt` extension. Save with a name that says what the file contains.

## 3.5. A diagram does not prove communication

A diagram, even one with every light green, **does not guarantee** that two devices can communicate. An address may be missing, an interface may be disabled at the other end, or the devices may be on different networks without a configured router.

```text
drawn                 ≠  connected
connected (green)     ≠  communicating
communicating         →  only a test can prove it
```

That is why, in any network you build or receive, the sequence will always be: **observe → predict → test**.

### Key ideas

- The **physical** topology tells you where devices and cables are; the **logical** topology tells you how communication is organized. They do not always match.
- A link is read end to end: **device + interface ↔ interface + device** (`SW-20 G0/1 ↔ G0/0/0 R-20`).
- In Packet Tracer: green = link; amber = port getting ready; red = no link or interface disabled.
- A diagram, even with everything green, does not prove communication: you need a **test**.

### Check your understanding

1. Read this link and name each part: `AP-03 G0 ↔ G0/12 SW-03`.
2. You open a Packet Tracer file and the link between two routers is red at both ends. Your classmate suggests replacing the cable. What do you say?
3. Give an example in which the physical and logical topologies do not match.

# 4. Network Types and Service Architectures

The same network can be classified from several points of view: by its **scope**, by **who manages it and who may use it**, or by how **services are organized** among devices. We should not mix these criteria: a network can be a LAN, private, and client-server at the same time.

| Criterion | Question | Examples |
|---|---|---|
| **Scope** | What geographic area does it cover? | PAN, LAN, WLAN, MAN, WAN |
| **Management and access** | Who manages it and who can connect? | Private network, public network |
| **Service architecture** | How are roles shared among devices? | Client-server, P2P |

At the end of the section, you will also see why networks **keep changing**, and where you will study those changes in this course.

## 4.1. Classification by scope

Network-type acronyms are useful only if the classification criterion is understood.

| Type | General idea |
|---|---|
| **PAN** | short-range personal environment |
| **LAN** | local network, typically within a home, classroom, office, or building |
| **WLAN** | LAN that provides wireless access |
| **MAN** | metropolitan area network: connects sites within one city (e.g., municipal fiber) |
| **WAN** | connects geographically separated sites or networks |

These categories do not fully describe a network by themselves.

The same network can simultaneously be:

- a LAN;
- private;
- Ethernet-based;
- client-server.

Those are different criteria.

## 4.2. Public and private networks

By **who administers the network and who may use it**:

| Type | Idea | Examples |
|---|---|---|
| **Private network** | Administered by an organization and usable only by its authorized users | School network, company network, your home network |
| **Public network** | Access is offered to the general public, usually with conditions | Library or airport Wi-Fi, a telecommunications provider's network |

"Public" does not mean "everything is open." A library can offer public Wi-Fi, but:

- the infrastructure is still administered;
- users do not have access to every resource;
- filters and policies may apply;
- being able to connect does not give anyone control over the network.

**Do not confuse three uses of the same words:**

| Expression | Refers to… | Where it is studied |
|---|---|---|
| Public / private network | Who administers the network and who may connect | This section |
| Public / private IP address | Whether an address can be used directly on the Internet (`203.0.113.80`) or only inside an organization (`192.168.10.25`) | U04 and U10 |
| Windows "Public" / "Private" network profile | How restrictive the computer's firewall is on that connection (in a café, choose "Public") | Operating system security |

For example, a library's **public** Wi-Fi usually gives users **private** IP addresses, and the library's router reaches the Internet with a **public** address.

## 4.3. Client and server are roles

A **client** requests a service.

A **server** provides a service.

These terms describe roles in a communication, not necessarily permanent device types.

The same machine may act as a client in one communication and as a server in another.

Example:

```text
PC → DNS server
PC = client
DNS = server
```

An application server may itself be a client of a database server.

## 4.4. Client-server architecture

In a client-server architecture, some systems provide services to others.

Common advantages:

- centralized administration;
- access control;
- more organized backups;
- shared data;
- common policies.

Risks:

- dependency on central services;
- need for redundancy;
- high impact when a central component fails without an alternative.

## 4.5. Peer-to-peer architecture

In a **peer-to-peer (P2P)** model, devices share resources **as equals**: each device can request and offer at the same time, without a central server organizing everything.

Examples:

- two laptops sharing a folder directly on a home network;
- direct file transfer between nearby phones;
- file-sharing applications (for example, BitTorrent), where each device downloads parts from others and offers them at the same time.

| | Client-server | P2P |
|---|---|---|
| Who provides the service | Dedicated devices (servers) | Any participating device |
| Administration and backups | Centralized | Spread across devices |
| If one device fails | The service may go down if it was the server | The others can continue |
| Scale | Servers must be sized for demand | Grows with participants, but is hard to control |

P2P does not mean "no network" or "no rules": it changes how roles and resources are distributed. Organizations usually restrict it because it makes access control and backups harder.

## 4.6. Factors driving network evolution

Networks keep growing and changing. Knowing why helps you understand why new technologies appear and others are abandoned.

| Factor | What it demands from the network | Example |
|---|---|---|
| Mobility | Access from anywhere and on any device | Building-wide Wi-Fi, 4G/5G |
| Cloud services | Reliable Internet connectivity with enough capacity | Cloud email, office apps, and storage |
| Video and collaboration | High bandwidth and low latency | Video calls, streaming, online training |
| Internet of Things (IoT) | Huge numbers of addressable devices | Sensors, cameras, HVAC |
| Virtualization | Networks that also exist inside servers | Virtual machines, containers |
| Remote work | Secure access from outside the organization | VPN, published services |
| Security | Segmentation, access control, logging | VLANs, ACLs, encryption |
| IPv4 exhaustion | New addressing | IPv6, NAT |
| Automation | Configuring many devices at once | Templates, APIs, management tools |

Many of these factors come back throughout the course: IPv6 in U05, VLANs in U07, ACLs in U08, NAT in U10.

### Key ideas

- A network is classified with **different criteria** that should not be mixed: scope (PAN, LAN, WLAN, MAN, WAN), administration and access (public/private), and service architecture (client-server, P2P).
- A public/private network (who uses it) is **not the same** as a public/private IP address (where an address is valid).
- Client and server are **roles** in a communication, not fixed device types.
- Networks evolve driven by mobility, the cloud, video, IoT, virtualization, remote work, security, IPv4 exhaustion, and automation.

# 5. Topologies, Dependencies, and Redundancy

Once you can read a diagram, the next question is practical: **what happens if an element fails?** The answer depends on the shape of the network, that is, its topology, and on which service we want to keep running.

| Concept | Question it answers | Example |
|---|---|---|
| **Topology** | What shape do the connections have? | Star, hierarchical, mesh |
| **Dependency** | Which elements does a service depend on? | Web browsing depends on the switch, the router, and the provider |
| **Redundancy** | Are there alternative paths or components? | Two links between switches |
| **Single point of failure** (*SPOF*) | Which element leaves the service with no alternative if it fails? | The only exit router |

## 5.1. Overview

| Topology | Idea | Current use |
|---|---|---|
| **Star** | All devices connect to a central point | Ethernet and Wi-Fi LANs |
| **Hierarchical** (*extended star*) | Several stars joined in levels | Company and school networks |
| **Mesh** | Several paths between devices | Network cores, links between sites |
| **Bus** | One medium shared by all | Historical (coaxial Ethernet) |
| **Ring** | Each node passes information to the next | Historical, and some fiber rings |

## 5.2. Star topology

In a star topology, several devices connect to a central point.

```text
 PC1
  |
PC2 ─ switch ─ PC3
  |
 PC4
```

Common advantages:

- easy to expand;
- failure of one access link usually affects only one device;
- easier fault isolation in many cases.

Risk:

- if the central device has no redundancy, it may become a single point of failure.

## 5.3. Hierarchical structure

Company and school networks are organized in **levels**, each with its own function. This lets them grow block by block, be administered in an orderly way, and add redundancy where it matters most.

```text
CORE             SW-C1 ═══════ SW-C2
                   │  ╲       ╱  │
                   │    ╲   ╱    │
                   │      ╳      │
                   │    ╱   ╲    │
DISTRIBUTION     SW-D1         SW-D2
                 ╱    ╲       ╱    ╲
ACCESS        SW-A1  SW-A2  SW-A3  SW-A4
                │      │      │      │
               PC     PC     AP    printers
```

| Level | Function | What connects to it |
|---|---|---|
| **Access** | Connect users and end devices | PCs, access points, printers, IP phones |
| **Distribution** | Aggregate the access switches of an area and apply policies between networks | Access switches of a floor or building |
| **Core** | Carry traffic very fast between blocks and toward the exit | Distribution switches, servers, exit routers |

In small and medium networks, such as a high school, distribution and core are often merged into a single level: this is the **collapsed core** design, with two levels instead of three.

You do not need to memorize a complete campus design. What matters is recognizing that a large network is organized in **blocks with different functions**, and that the upper levels affect the most devices if they fail; that is why they are usually duplicated.

## 5.4. Mesh

In a **mesh** topology there are several possible paths between certain points.

```text
Full mesh (4 nodes)             Partial mesh (4 nodes)
   A ───── B                       A ───── B
   │ ╲   ╱ │                       │     ╱ │
   │   ╳   │                       │   ╱   │
   │ ╱   ╲ │                       │ ╱     │
   C ───── D                       C       D
```

- In a **full mesh**, every node connects to every other node. The number of links grows very quickly: *n* nodes need *n·(n−1)/2* links (4 nodes → 6 links; 10 nodes → 45).
- In a **partial mesh**, only the most important paths are duplicated. This is the usual approach in practice.

A mesh improves **resilience**, but it also increases cost, complexity, and the need for control mechanisms that stop traffic from looping (STP in U06, routing protocols in U09).

## 5.5. Bus and ring

```text
Bus                                   Ring
PC1   PC2   PC3   PC4                 PC1 ──── PC2
 │     │     │     │                   │        │
═╧═════╧═════╧═════╧═  (shared cable)  PC4 ──── PC3
```

- In a **bus**, all devices share a single cable. What one device sends, everyone receives; only one can transmit at a time, and a break in the cable affects the whole network. It was the basis of the first Ethernet networks over coaxial cable.
- In a **ring**, each device receives from the previous one and delivers to the next. It was used in older local area networks and is still used in some provider and metropolitan **fiber rings**, with mechanisms to recover if a section is cut.

Ethernet LANs are no longer designed as a bus or a ring, but knowing them helps you understand why the star won and why they appear in older documentation.

## 5.6. Redundancy and SPOF

**Redundancy** provides alternate components or paths in order to reduce the impact of failures.

A **SPOF** (*Single Point of Failure*) is a component whose failure may completely interrupt a function or service.

Example:

```text
PCs ─ single switch ─ single router ─ Internet
```

The switch or router may be a SPOF depending on the service being analyzed.

The right question is not only:

> “Is there redundancy?”

but:

> “What service are we trying to keep available, and which component could remove all alternatives?”

## 5.7. Analyzing the impact of a failure

To analyze a topology, it is not enough to "look for the central element." Follow the same steps every time:

1. choose the **service** you want to keep running;
2. trace that service's **chain of dependencies** on the diagram;
3. mark the elements with no alternative: they are its **SPOFs**;
4. propose an improvement and weigh its **cost**.

**Worked example.** A dental clinic has three PCs at the front desk, an access point for the tablets in the treatment rooms, and its appointment book in a cloud service.

```text
PC-R1 ─┐
PC-R2 ─┼── SW-CL ── R-CL ── provider ── Internet ── cloud appointment book
PC-R3 ─┤
AP-CL ─┘
```

| Service | Chain of dependencies | SPOFs | Possible improvement | Drawback |
|---|---|---|---|---|
| Check the appointment book from the front desk | PC → SW-CL → R-CL → provider → Internet → cloud | SW-CL, R-CL, and the provider | Second line from another provider (for example, 5G) on the router | Monthly cost; the router is still a SPOF |
| PC-R1 and PC-R2 share a folder | PC → SW-CL → PC | SW-CL | Preconfigured spare switch in the cabinet | Someone has to swap it in |
| Check the appointment book from the tablets | Tablet → AP-CL → SW-CL → R-CL → … | AP-CL plus the previous ones | Second access point | Cost and channel planning (U03) |

Notice that **the SPOF depends on the service**: the provider is a SPOF for the appointment book, but not for sharing a folder. And adding redundancy at one point (two providers) does not remove the other SPOFs (the router and the switch are still single).

### Key ideas

- The star is the dominant LAN topology; its central point can be a **SPOF**.
- Large networks are organized in levels (access, distribution, core); medium networks use a **collapsed core**.
- A mesh provides alternative paths at the cost of money and complexity; in practice, **partial** mesh is used.
- The SPOF depends on the **service** you analyze, and adding redundancy at one point does not remove every SPOF.

### Check your understanding

1. How many links does a full mesh of 5 routers need?
2. A company duplicates its core switch but keeps a single router to the Internet. For the "web browsing" service, which SPOF has it removed, and which one remains?
3. Why did coaxial-cable bus networks stop being used in LANs?

# 6. Layered Architecture: A First TCP/IP Map

When something fails in a network, the list of possible causes is huge: a cable, a setting, a service, the application itself… To stay organized, technicians use **layered models**: they divide communication into levels, and each level solves one specific problem.

In this section, you will build a first map with the **five-layer TCP/IP model** and meet the **OSI model** as a reference. The goal is not to memorize lists, but to have one question for each layer:

| Layer | Question |
|---|---|
| Application | Which service does the application need? |
| Transport | Which process should receive the data? |
| Network | Which network and host should it reach? |
| Data Link | How is it delivered on the local link? |
| Physical | How is the signal transmitted? |

In U02, you will study in detail how these layers work together (encapsulation, headers, and traffic analysis).

## 6.1. Why layers are useful

Network communication solves several different problems at the same time:

- transmitting bits;
- delivering data across a local link;
- reaching another network;
- communicating between processes;
- providing application services.

Trying to explain all of this as one single mechanism would be too complex.

We therefore use **layers**: related functions are grouped together so we can study each problem at the appropriate level.

## 6.2. Five-layer TCP/IP model

We will use a five-layer TCP/IP model as our initial map:

| Layer | Initial functional question | Examples |
|---|---|---|
| **Application** | What service is the application using? | HTTP, DNS, DHCP, SSH |
| **Transport** | Which process or service should receive the data? | TCP, UDP, ports |
| **Network** | Which IP interface/network should the data reach? | IPv4, IPv6, routing |
| **Data link** | How is data delivered on the local link? | Ethernet, MAC |
| **Physical** | How is the signal transmitted? | copper, fiber, radio |

This model does not mean that “every problem belongs to exactly one layer.” It is a tool for organizing functions and questions.

## 6.3. OSI as a reference model

The OSI model divides communication into seven layers. It is still useful as a conceptual and professional reference.

You do not need to memorize every detail yet. In U02, both models will be related more precisely.

## 6.4. First troubleshooting use

Suppose a user says:

> “I cannot open a website.”

We still do not know whether the problem involves:

- the physical connection;
- the local network;
- IP addressing;
- routing;
- DNS;
- the server;
- the application.

Layers help us avoid premature conclusions and ask better questions.

### Key ideas

- Layers split a communication into smaller problems; each layer has **its own question**.
- The five-layer TCP/IP model is the module's map; OSI is used as a reference and vocabulary.
- A problem does not always belong to a single layer: layers organize questions, they do not assign blame.
- Thinking in layers prevents premature conclusions when the symptom is vague.

### Check your understanding

1. Match each situation with a layer: unplugged cable; a name that does not translate to an address; port 443; a MAC address.
2. What question does the network layer answer?

# 7. Identifiers: Name, Port, IP, MAC, and Gateway

For a communication to reach its destination, we need to identify **what** we want, **where** it is, and **how to leave** our network. Different identifiers exist because they answer different questions, and each one belongs to a different layer of the model in the previous section.

| Identifier | Layer | Example | Seen by the user |
|---|---|---|---|
| **Name** | Application | `www.example.com` | Yes |
| **Port** | Transport | `443` | Sometimes (in the URL) |
| **IP address** | Network | `192.168.10.25` | Rarely |
| **MAC address** | Data Link | `00:1A:2B:3C:4D:5E` | No |
| **Default gateway** | Network | `192.168.10.1` | No |

Understanding what each one does will later help you decide what to check when something fails: a name problem is not fixed by changing a MAC address.

## 7.1. Functional map

| Element | Question it helps answer |
|---|---|
| **Name** | What resource or system do I want to use? |
| **Port** | What service or process do I want to reach? |
| **IP address** | Which IP interface is the destination? |
| **MAC address** | Which interface participates on the local link? |
| **Default gateway** | Which router receives traffic for remote networks? |

They are not equivalent or interchangeable.

## 7.2. Name

Names are easier for people to remember than addresses.

Example:

```text
www.example.com
```

To communicate using IP, that name normally needs to be related to an address. DNS participates in that process.

## 7.3. Port

A host can run several network applications at the same time. **Port numbers** help identify transport-layer services or processes.

Common examples:

- HTTP: 80/TCP;
- HTTPS: 443/TCP;
- DNS: 53/UDP and 53/TCP depending on the case;
- SSH: 22/TCP.

Transport will be studied in more depth in U02.

## 7.4. IP address

An IP address identifies an interface in the context of an IP network.

IPv4 example:

```text
192.168.10.25
```

An address is not interpreted in isolation. We also need information such as the prefix or subnet mask.

Network, broadcast, subnetting, and VLSM calculations belong to U04.

## 7.5. MAC address

A MAC address is used by link-layer technologies such as Ethernet to identify interfaces on the local link.

Example:

```text
00:1A:2B:3C:4D:5E
```

In U02, you will observe MAC addresses inside frames. In U06, you will study how switches use them.

## 7.6. Default gateway

The **default gateway** is normally the address of the router to which a host sends traffic for networks it does not consider local.

A useful first model is:

```text
local destination
→ communication inside the local network

remote destination
→ a path to other networks is needed
→ the default gateway is normally used
```

The exact local/remote decision will be studied with IPv4 and IPv6.

## 7.7. How identifiers are written: decimal, binary, and hexadecimal

Devices work with **bits** (0s and 1s). People write those bits in a more convenient way: IPv4 addresses in **decimal** and MAC addresses in **hexadecimal**.

| Identifier | Size | How it is written | Example |
|---|---|---|---|
| IPv4 | 32 bits = 4 octets | 4 decimal numbers (0–255) separated by dots | `192.168.10.25` |
| MAC | 48 bits = 6 octets | 12 hexadecimal digits | `00:1A:2B:3C:4D:5E` |

### From an octet to decimal

An **octet** is 8 bits. Each position has a weight:

```text
weight: 128  64  32  16   8   4   2   1
bits:     1   1   0   0   0   0   0   0   →  128 + 64 = 192
```

Examples:

```text
192 = 128 + 64             → 1100 0000 → C0
168 = 128 + 32 + 8         → 1010 1000 → A8
255 = all bits set to 1    → 1111 1111 → FF
```

### From binary to hexadecimal

Each hexadecimal digit (0–9 and A–F, where A = 10 … F = 15) represents **4 bits**; that is why an octet is written with **two** hexadecimal digits: `1010 1000` → `A` `8` → `A8`.

### The same MAC address written three ways

| System | Format | Example |
|---|---|---|
| Linux, Wireshark | Pairs separated by colons | `00:1a:2b:3c:4d:5e` |
| Windows | Pairs separated by hyphens | `00-1A-2B-3C-4D-5E` |
| Cisco IOS and Packet Tracer | Groups of four separated by dots | `001a.2b3c.4d5e` |

All three represent **the same address**; uppercase and lowercase do not change the value. That is why Packet Tracer shows a MAC as `00E0.A357.B5AB` and Windows shows it as `00-E0-A3-57-B5-AB`.

You will practice conversion in depth in U04 (subnetting) and U05 (IPv6).

### Key ideas

- Name, port, IP address, MAC address, and gateway answer **different questions** and are not interchangeable.
- An IP address is interpreted together with its mask or prefix; a MAC address only makes sense on the **local link**.
- The **default gateway** is the exit toward destinations the host does not consider local.
- IPv4: 32 bits written in decimal; MAC: 48 bits written in hexadecimal, in three formats depending on the system.

### Check your understanding

1. In the address `https://www.example.com`, which identifiers appear, which one is implicit, and which ones are not visible?
2. Convert 172 to binary and hexadecimal.
3. Are `00-1A-2B-3C-4D-5E` and `001a.2b3c.4d5e` the same address?

# 8. Host State and First Tools

When a problem is reported, the first step is not to change anything, but to **observe the state** of the affected device and run simple tests. Every operating system includes tools for this. In this section, you will learn to read their output and, above all, **what question each one answers and what it does not prove**.

| Tool | Question it answers |
|---|---|
| `ipconfig /all` (Windows) · `ip addr`, `ip route`, `resolvectl status` (Linux) | How is the device configured? |
| `ping` | Is there IP communication with a specific destination? |
| `nslookup` · `Resolve-DnsName` · `dig` | Is a name correctly translated into an address? |
| `tracert` / `traceroute` | Which routers does traffic pass through on the way to a destination? |
| `Test-NetConnection -Port` · `nc -zv` | Does a specific **service** (a port) answer at the destination? |

Before looking at the tools, it helps to separate three ideas that are often confused: **connectivity**, **performance**, and **availability**.

## 8.1. Connectivity, performance, and availability

| Concept | Question | Expressed in |
|---|---|---|
| **Connectivity** | Can there be communication between two points? | Yes / no, for a specific test |
| **Performance** | How well does that communication work? | Mb/s, ms, % |
| **Availability** | For how much of the time is the service operational and reachable? | % of time |

### Performance

| Measure | What it is | Usual unit | Example |
|---|---|---|---|
| **Bandwidth** | Maximum capacity of the link or the contract | Mb/s, Gb/s | 600 Mb/s fiber |
| **Throughput** | Data actually transferred | Mb/s | A real download at 480 Mb/s |
| **Latency** | Time it takes information to travel (and come back) | ms | `ping`: time = 12 ms |
| **Jitter** | How much latency varies from one packet to the next | ms | Critical for voice and video |
| **Packet loss** | Percentage of packets that do not arrive | % | `ping`: 25% loss |

**Bits and bytes.** Network speeds are expressed in **bits** per second (b/s); browsers and download managers usually show **bytes** per second (B/s). A byte is 8 bits: a 100 Mb/s connection downloads at most about 12.5 MB/s.

### Availability

It is expressed as the percentage of time the service works:

| Availability | Maximum downtime per year |
|---|---|
| 99% | ≈ 3.65 days |
| 99.9% | ≈ 8.8 hours |
| 99.99% | ≈ 53 minutes |

A service may have connectivity but unacceptable performance (a video call that freezes), or work well when you test it but have low availability (it goes down every afternoon).

## 8.2. Read the configuration before changing it

Before changing anything, observe the current state. The goal is not to memorize the output, but to **know where to look** for each piece of data.

**Windows** (`ipconfig /all`, shortened output):

```text
Ethernet adapter Ethernet:

   Description . . . . . . . . . . . : Intel(R) Ethernet Connection I219-V
   Physical Address. . . . . . . . . : 3C-52-82-1A-7B-04
   DHCP Enabled. . . . . . . . . . . : Yes
   Link-local IPv6 Address . . . . . : fe80::8d4c:2e1a:93b0:5f12%12(Preferred)
   IPv4 Address. . . . . . . . . . . : 192.168.10.25(Preferred)
   Subnet Mask . . . . . . . . . . . : 255.255.255.0
   Default Gateway . . . . . . . . . : 192.168.10.1
   DHCP Server . . . . . . . . . . . : 192.168.10.1
   DNS Servers . . . . . . . . . . . : 192.168.30.53
```

| Line | What it tells you |
|---|---|
| Physical Address | The interface's **MAC address** (Windows format, with hyphens) |
| DHCP Enabled: Yes | The configuration was obtained automatically |
| IPv4 Address + Subnet Mask | The device's address and the information needed to know what is local (U04) |
| Default Gateway | Which router receives traffic for other networks |
| DNS Servers | Who the device asks to translate names; it may be on another network, as here |
| Link-local IPv6 Address (`fe80::…`) | An IPv6 address the device creates by itself (U05). It is **not** "the IP" you are looking for |

In PowerShell, `Get-NetIPConfiguration` shows the same data in a more compact form. In Packet Tracer, the equivalent is in **Desktop → Command Prompt** (`ipconfig /all`) or **Desktop → IP Configuration**.

**Linux** (shortened output):

```text
$ ip -br addr
lo        UNKNOWN   127.0.0.1/8 ::1/128
enp0s3    UP        192.168.10.40/24 fe80::a00:27ff:fe4e:66a1/64

$ ip route
default via 192.168.10.1 dev enp0s3 proto dhcp metric 100
192.168.10.0/24 dev enp0s3 proto kernel scope link src 192.168.10.40

$ resolvectl status enp0s3
Link 2 (enp0s3)
Current DNS Server: 192.168.30.53
```

| Output | What it tells you |
|---|---|
| `enp0s3 UP 192.168.10.40/24` | Active interface, its address, and its prefix (`/24` is equivalent to mask 255.255.255.0) |
| `default via 192.168.10.1` | The **default gateway** |
| `Current DNS Server` | The DNS server in use |
| `lo 127.0.0.1` | The *loopback* interface: the device itself. It is not used to communicate with others |

## 8.3. An address that reveals a problem: 169.254.x.x

If a Windows device is set to obtain its address through DHCP and **nobody answers**, it assigns itself an address from the **169.254.0.0/16** range. This mechanism is called **APIPA** (*Automatic Private IP Addressing*).

```text
   Autoconfiguration IPv4 Address. . : 169.254.112.47(Preferred)
   Subnet Mask . . . . . . . . . . . : 255.255.0.0
   Default Gateway . . . . . . . . . :
```

| You can state | You cannot state yet |
|---|---|
| The device asked for automatic configuration and did not receive it | That the DHCP server is down |
| It has no gateway: it will not reach other networks | That the cable is fine (if there is no link, the reply cannot arrive either) |

The next questions would be: is there a link (light, `Media State`)? Do other devices on the same network receive an address? DHCP is observed in U02 and configured in U04. Linux does not usually assign a 169.254 address automatically: the interface simply has no IPv4 address.

## 8.4. `ping`

`ping` sends ICMP echo messages and waits for the reply. It provides evidence of IP reachability **for that test**.

**Successful reply:**

```text
C:\> ping 192.168.10.1

Pinging 192.168.10.1 with 32 bytes of data:
Reply from 192.168.10.1: bytes=32 time<1ms TTL=255
Reply from 192.168.10.1: bytes=32 time<1ms TTL=255
Reply from 192.168.10.1: bytes=32 time=1ms TTL=255
Reply from 192.168.10.1: bytes=32 time<1ms TTL=255

Ping statistics for 192.168.10.1:
    Packets: Sent = 4, Received = 4, Lost = 0 (0% loss),
```

`time` is the round-trip latency; you will study `TTL` in U02.

**Three failures that do not mean the same thing:**

| Output | What it indicates | What you still do not know |
|---|---|---|
| `Request timed out.` | The request was sent and no reply arrived in time | Whether the destination exists, is powered off, a firewall blocks ICMP, or the return path fails |
| `Reply from 192.168.10.25: Destination host unreachable.` | The **device itself** (or an intermediate router, if the IP is a different one) reports that it cannot deliver the packet | Why: on the local network, usually because the destination does not answer on the link (U02) |
| `Ping request could not find host www.example.cm.` | The ping was never sent: the **name** could not be translated | Whether it is a typo or a DNS problem |

**Common trap:** in the "Destination host unreachable" case, Windows counts the replies as **received** and shows `0% loss`. Always read the lines, not just the summary.

And the general rule: a failed `ping` **does not by itself prove** the cause. It could be a link problem, a wrong address, a missing route, filtering, a powered-off host, or a policy that blocks ICMP.

```text
test result ≠ complete diagnosis
```

## 8.5. DNS lookup

If an IP address works but a name does not, check name resolution directly.

```text
C:\> nslookup www.example.com
Server:  UnKnown
Address:  192.168.30.53

Non-authoritative answer:
Name:    www.example.com
Address:  203.0.113.80
```

- The first two lines tell you **which DNS server answered**: always check them. `UnKnown` only means the server has no registered name; it is not an error.
- "Non-authoritative answer" is normal: the organization's DNS server answers with information it obtained from another server.

| Result (approximate text) | What it indicates |
|---|---|
| Returns an address | Resolution works **from this device and with this server** |
| `DNS request timed out` | The configured DNS server **does not answer**: the query does not reach it, there is no DNS service at that address, or the reply does not come back |
| `*** UnKnown can't find www.exmple.com: Non-existent domain` | The server **does** answer, but that name does not exist (often a typo) |

In PowerShell, `Resolve-DnsName www.example.com` performs the same lookup; in Linux, use `dig www.example.com` or `resolvectl query www.example.com`. The exact output text changes with the system and language: learn to recognize the **idea**.

## 8.6. `traceroute` / `tracert`

These tools show the routers that **answer** along the path to a destination.

```text
C:\> tracert www.example.com

Tracing route to www.example.com [203.0.113.80]
over a maximum of 30 hops:

  1    <1 ms    <1 ms    <1 ms  192.168.10.1
  2     3 ms     2 ms     3 ms  198.51.100.1
  3     *        *        *     Request timed out.
  4    12 ms    11 ms    12 ms  203.0.113.80

Trace complete.
```

- Each line is a **hop** (a router); the three columns are three latency measurements.
- Hop 1 is usually your **default gateway**.
- `* * *` on an intermediate hop, with the destination answering afterward, means that router **does not answer the probes**, not that it is broken.

The output is not a perfect picture of the Internet: some devices do not answer, and the return path may differ from the outbound path.

## 8.7. Testing a service, not just a device

`ping` tells you whether a device answers ICMP, not whether it offers the service the user needs. To check a specific **port**:

```text
PS C:\> Test-NetConnection www.example.com -Port 443

ComputerName     : www.example.com
RemoteAddress    : 203.0.113.80
RemotePort       : 443
SourceAddress    : 192.168.10.25
TcpTestSucceeded : True
```

`TcpTestSucceeded : True` proves that the service is listening on port 443 and that a connection can be opened to it from this device. In Linux, `nc -zv www.example.com 443` performs an equivalent check.

This test is especially useful when ICMP is filtered: a web server may **not** answer `ping` and still serve pages without any problem.

## 8.8. What each test proves

| Test | If it succeeds, it proves… | If it fails… |
|---|---|---|
| `ipconfig /all` / `ip addr` | How the device is configured right now | — (it is an observation, not a test) |
| `ping` to the gateway | IP communication with the local router | It does not prove the cause |
| `ping` to an external IP | IP communication to that destination and back | It does not prove the cause |
| `nslookup name` | That this DNS server translates that name | It separates "no answer" from "does not exist" |
| `tracert` | Which hops answer along the path | `*` does not prove a fault |
| `Test-NetConnection -Port` | That the service is listening on that port | It does not tell a filter from a stopped service |

### Key ideas

- Before changing anything, **observe**: IP address, mask, gateway, DNS, and MAC.
- Connectivity, performance, and availability are different things; speeds are measured in **bits** per second (100 Mb/s ≈ 12.5 MB/s).
- A **169.254.x.x** address means the device did not receive automatic configuration.
- Each test answers **one** question; a failure does not prove the cause.
- Answering `ping` is not the same as offering a service: for that, test the **port**.

### Check your understanding

1. A laptop shows the address 169.254.30.7 and no default gateway; another laptop in the same classroom works. What do you know, and what would you check first?
2. `ping` to the web server succeeds, but the browser does not load the page. Which test would you run, and what would it prove?
3. A download runs at 12 MB/s on a 100 Mb/s connection. Is that poor performance?
4. `ping 192.168.10.77` shows "Destination host unreachable" four times, and the summary says "0% loss." Did it work?

# 9. First Look at Wireshark

The tools in the previous section show **results** (it answers / it does not). A **packet analyzer** such as Wireshark goes one step further: it lets you see the messages that actually travel across the network.

Wireshark is a free tool widely used by professionals. In U01, we use it for one main idea:

> a technical claim becomes stronger when it can be related to observable evidence.

| In U01 | In U02 and later |
|---|---|
| Open a capture, filter (`dns`, `icmp`), count, and read the *Info* column | Headers, fields, ports, capture filters, and protocol analysis |

## 9.1. Capture responsibly

Traffic captures may reveal sensitive information. Use Wireshark only:

- on authorized systems and networks;
- for legitimate educational or professional purposes;
- while avoiding unnecessary collection of personal data;
- according to school or organizational rules.

## 9.2. What to observe first

In a simple capture, you may recognize:

- time;
- source;
- destination;
- identified protocol;
- length;
- packet summary.

You do not need to interpret every field yet.

The initial question is simpler:

> “What communication am I observing, and what evidence does it provide?”

## 9.3. The capture point matters

A capture only shows traffic visible from the point where it is taken.

Therefore, the absence of packets does not always mean “the traffic does not exist.” It may also mean that you are observing from a location that cannot see it.

This idea becomes essential in U02.

### Key ideas

- Wireshark shows the **messages** that travel across the network, not just a result.
- Capture only on **authorized** networks and devices.
- In U01, it is enough to open a capture, apply a filter (`dns`, `icmp`), count, and read the *Info* column.
- Not seeing something in a capture does not prove it does not exist: it depends on the **capture point**.

1. You apply the `dns` filter to a capture and nothing appears. Give two explanations other than "there were no DNS queries."

# 10. Evidence-Based Troubleshooting

A good technician is not the one who knows the most commands, but the one who **reasons** best with the data collected. Troubleshooting does not mean running random commands until something works: it means asking questions, testing them, and drawing conclusions the evidence can support.

A useful framework is:

```text
symptom
→ question
→ hypothesis
→ test
→ evidence
→ conclusion
```

When an incident is corrected:

```text
conclusion
→ minimum change
→ verification
```

| Term | Meaning | Example |
|---|---|---|
| **Symptom** | What is observed or reported | “No website opens” |
| **Fact** | Something that has been checked | `ping 8.8.8.8` replies |
| **Hypothesis** | A possible explanation | “The configured DNS server does not answer” |
| **Test** | An action that answers a question | `nslookup www.example.com` |
| **Evidence** | The observable result of the test | “DNS request timed out” |

This is not a rigid recipe. It is a way to avoid unsupported changes.

## 10.1. Symptom

A symptom describes what the user or technician observes.

Weak description:

> “The Internet is broken.”

Better description:

> “The host can open local resources but cannot resolve external names.”

The more precise the symptom, the better the next questions can be.

## 10.2. Fact

A **fact** is something observed or verified.

Examples:

- the interface is up;
- the host has an IP address;
- `ping` to the gateway succeeds;
- `nslookup` returns an error.

## 10.3. Hypothesis

A **hypothesis** is a possible explanation.

Example:

> “The configured DNS service may not be responding.”

It should not be treated as a conclusion until evidence is collected.

## 10.4. Test

A test should answer a specific question.

Example:

> “If I want to know whether the issue is limited to name resolution, I will compare an IP-based test with a DNS lookup.”

## 10.5. Evidence

Evidence is the observable result of a test.

It should help you:

- support a hypothesis;
- weaken it;
- eliminate a possibility;
- decide what to test next.

## 10.6. Guided case: IP works, name does not

Symptom:

> A device can reach `203.0.113.80`, but cannot open `www.example.com` in the browser.

Initial facts:

- there is IP connectivity to an external destination;
- communication by name fails.

Reasonable hypothesis:

- there may be a name-resolution problem.

Next test:

```bash
nslookup www.example.com
```

It is a good test because it **distinguishes between hypotheses**. What you do next depends on the result:

| `nslookup` result | What it indicates | Reasonable next step |
|---|---|---|
| Returns the expected address | Resolution works: the DNS hypothesis weakens | Test the service (`Test-NetConnection www.example.com -Port 443`) and check the browser |
| Request timed out | The configured DNS server does not answer | `ping` the DNS server's address; check which DNS server is configured and compare with a device that works |
| `Non-existent domain` | The DNS server answers, but does not know that name | Check how the name is spelled |

Incorrect conclusion, whatever the result:

> "The network is working perfectly."

Connectivity to one specific address does not prove that every network service works.

If you finally change something (for example, the configured DNS server), change **only that** and verify by repeating **the same test** that failed.

### Key ideas

- Troubleshooting follows a framework: **symptom → question → hypothesis → test → evidence → conclusion**; if you fix something, **minimal change → verification**.
- A **fact** has been verified; a **hypothesis** is a possible explanation that has not been verified yet.
- A precise symptom ("local resources open, but external names do not resolve") produces better questions than a vague one ("the Internet is broken").
- The conclusion must not claim more than the evidence supports.

### Check your understanding

1. Classify as symptom, fact, or hypothesis: "the website is slow"; "`ping` to the gateway: 0% loss"; "the switch might be overloaded."
2. What is a minimal change, and why is it verified with the same test that failed?

# 11. Reading a Complete Situation

In practice, incidents do not arrive in order: they arrive as a sentence from the user (“it doesn't work”) and a set of incomplete data. This section proposes a way to **organize the information** before acting, bringing together everything in the unit.

When you face a simple incident, separate these questions:

| Question | What you get |
|---|---|
| What is the user trying to do? | The affected service |
| Which components are involved? | The chain of dependencies |
| What information do I have? | The facts |
| What information is missing? | What you must not assume |
| Which test gives the most information? | The next step |

## 11.1. What is the user trying to do?

Example:

> access a web application by name.

## 11.2. What components are involved?

For example:

```text
PC
→ interface
→ switch
→ router
→ DNS
→ server
```

## 11.3. What information do I already have?

- IP address;
- gateway;
- DNS;
- interface state;
- test result.

## 11.4. What information is missing?

Do not fill information gaps with assumptions.

You may still need to know:

- whether the gateway is reachable;
- whether the name resolves;
- whether other hosts have the same issue;
- whether the server is available.

## 11.5. Which test gives the most useful information?

A good test is not simply a command you know how to run. It is a test that helps distinguish between hypotheses.

### Key ideas

- Before acting, organize the information: what the user is trying to do, which components are involved, what you know, what is missing, and which test gives the most information.
- The best test is not the one you can run, but the one that **distinguishes between hypotheses**.

### Check your understanding

1. A user cannot print, but her coworkers in the same office can. What information is missing before you act, and what does it tell you that her coworkers can print?

# 12. Responsible Use of AI Assistants

AI assistants have become a common tool for technical questions. They can save time, but **they cannot see your network**: they answer based on what you tell them and on general patterns, and they can be wrong with great confidence.

An AI-generated answer may include:

- a correct explanation;
- an excessive simplification;
- an unsupported assumption;
- an unnecessary command;
- a conclusion not justified by the evidence.

Use AI as a support tool, not as a replacement for technical reasoning.

A useful process is:

1. identify the claims being made;
2. separate facts from hypotheses;
3. check what evidence is used;
4. verify commands and concepts;
5. compare the answer with documentation and real results;
6. correct the answer when necessary.

Never change a critical configuration only because an AI system suggested it.

### Key ideas

- An AI assistant **cannot see your network**: it answers from general patterns and can be wrong with great confidence.
- Check every claim against evidence and documentation before applying it.
- Never change a critical configuration just because an AI suggests it.

### Check your understanding

1. For "IP works, name does not," an AI answers: "Your DNS server is down; reinstall the network adapter driver and restart the router." Point out two problems with that answer.
