# U02 — Layers, Encapsulation, and Traffic Analysis

> **Guiding question:** How does information change from the moment an application generates it until it reaches its destination, and what can we prove by observing network traffic?

In U01 we built the first map of a network: devices, interfaces, media, services, topologies, identifiers, and local/remote communication paths.

U02 answers the next question:

> **I already know what elements make up a network. What actually happens when those elements communicate?**

The goal of this unit is not to memorize every header or every acronym. The goal is to follow communication through the layers and connect that explanation to **real or simulated evidence**.

# 1. Layers and the TCP/IP Model

When you open a web page, it looks like a single thing happens, but several very different problems are being solved at the same time: knowing what to request, delivering it to the right program, finding the destination host, passing from one device to the next, and turning everything into signals. If we tried to study all of this at once, it would be impossible to understand or to locate a failure.

That is why networks are described with **layered models**: each layer takes care of one specific problem and relies on the layer below. In U01 you saw the five-layer map; in this section we formalize it, see what a **protocol stack** is, and apply it to a real web request.

| Concept | Question it answers | Example |
|---|---|---|
| **Layer** (*capa*) | Which group of related functions solves a specific problem? | The Transport layer delivers data to the correct process |
| **Layered model** (*modelo por capas*) | How is the whole communication organized? | Five-layer TCP/IP, OSI |
| **TCP/IP model** (*modelo TCP/IP*) | Which map will we use throughout the module? | Application, Transport, Network, Data Link, Physical |
| **Protocol stack / protocol suite** (*pila de protocolos*) | Which specific protocols work together, one per layer? | HTTPS + TCP + IPv4 + Ethernet |

We should not confuse a **layer** with a **device**: the same device takes part in several layers at once, and a layer is not a box you can touch.

## 1.1. Why do we use layers?

Network communication has to solve different problems:

- an application generates or consumes data;
- data must reach the correct process;
- endpoints must be identified;
- information may need to cross one or more networks;
- each link must deliver information to the next device;
- the physical medium must carry signals.

If we tried to explain all of this as one single function, it would be very difficult to:

- replace technologies;
- understand responsibilities;
- isolate failures;
- interpret captures.

Layered models separate related functions.

```text
layer
=
group of related functions
```

Layers are not physical devices.

A single computer can participate in functions from all layers at the same time.

Practical advantages of working in layers:

| Advantage | What it means | Example |
|---|---|---|
| **Modularity** | One layer can change without redoing the others | Moving from cable to Wi‑Fi does not require changing the browser |
| **Interoperability** | Different vendors can cooperate if they follow the same protocol at each layer | A laptop from one brand browses through a router from another |
| **Troubleshooting** | You can ask, layer by layer, where the failure is | “Is there a link? Is there IP? Does the name resolve? Does the service respond?” |
| **Learning** | Each problem is studied at the right level of detail | Media in U03, addressing in U04, and so on |

## 1.2. Five-layer TCP/IP model

This module primarily uses this model (you already saw it in U01; here we add the layer number, which you will use a lot in professional language):

| Layer | Main question | Examples |
|---:|---|---|
| **5. Application** | Which service does the application use? | HTTP(S), DNS, DHCP, SSH |
| **4. Transport** | Which process should receive the data? | TCP, UDP |
| **3. Network** | How is the destination identified and reached across networks? | IPv4, IPv6, ICMP |
| **2. Data Link** | How is information delivered on a specific link? | Ethernet, Wi‑Fi |
| **1. Physical** | How does the signal travel through the medium? | copper, fiber, radio |

Conceptual example:

```text
HTTPS
  ↓
TCP
  ↓
IPv4
  ↓
Ethernet
  ↓
signal
```

Each layer uses services from the layer below and provides services to the layer above.

**Note: four or five layers.** The original TCP/IP definition (RFC 1122) uses **four layers**: Application, Transport, Internet, and Link. The five-layer model we use splits the last one into **Data Link** and **Physical**, because it makes it easier to reason about cables and frames separately. If other documentation shows four layers, it is not a mistake: it is the same idea divided differently.

| Four-layer TCP/IP (RFC 1122) | Five-layer TCP/IP (this module) |
|---|---|
| Application | Application |
| Transport | Transport |
| Internet | Network |
| Link | Data Link + Physical |

## 1.3. Protocol stack

A model describes **functions**; a **protocol stack** is the specific set of protocols that implement those functions and work together on a device. The set of Internet protocols is known as the **TCP/IP protocol suite**: it is named after two of its most important protocols, but it includes many more.

| Layer | Common protocols in the TCP/IP suite |
|---|---|
| Application | HTTP, HTTPS (HTTP over TLS), DNS, DHCP, SSH, SMTP, FTP, TFTP |
| Transport | TCP, UDP |
| Network | IPv4, IPv6, ICMP, ICMPv6 |
| Data Link | Ethernet (IEEE 802.3), Wi‑Fi (IEEE 802.11), ARP (between Data Link and Network) |
| Physical | Cable, connector, fiber, and radio specifications (U03) |

In each specific communication, **one protocol per layer** is chosen and they are “stacked”:

```text
browsing a website   →  HTTPS / TCP / IPv4 / Ethernet / copper
looking up a name    →  DNS   / UDP / IPv4 / Wi‑Fi    / radio
```

ARP appears in the table between Data Link and Network because it relates addresses from both layers; you will study it in section 5.

## 1.4. One action, several functions: a web request example

A user types `https://www.example.test` in the browser. These are some of the functions that must be performed and the layer that handles each one:

| Required function | Layer | Protocol or element |
|---|---|---|
| Request the page and receive it securely | Application | HTTPS (HTTP + TLS) |
| Translate `www.example.test` into an IP address | Application | DNS |
| Deliver the data to the web server process and not to another one | Transport | TCP, port 443 |
| Identify the destination host, even if it is on another network | Network | IPv4 (destination address) |
| Deliver the information to the next device on the link (the gateway) | Data Link | Ethernet (destination MAC) |
| Find out the gateway’s MAC address | Data Link/Network | ARP |
| Transmit the bits over the cable | Physical | electrical signal on twisted pair |

Notice that **a single user action generates several communications** (DNS, ARP, TCP…) and that each function belongs to a different layer. This table is the basis for everything we will do in the unit.

# 2. OSI, Service, Protocol, and Interface

TCP/IP is not the only model you will find. Technical documentation, certifications, and professional conversations constantly use the **OSI model**, especially its **layer numbers**: “it’s a Layer 1 problem,” “a Layer 2 switch,” “a Layer 3 switch.” This section relates the two models and clarifies three terms that are often mixed up: **service**, **protocol**, and **layer interface**.

| Concept | Question it answers | Example |
|---|---|---|
| **OSI reference model** (*modelo OSI*) | Which seven-layer model does documentation use as a common reference? | “L2,” “L3,” “L7” |
| **Model mapping** (*correspondencia TCP/IP–OSI*) | Which OSI layers does each TCP/IP layer group together? | TCP/IP Application ≈ OSI layers 5, 6, and 7 |
| **Service** (*servicio*) | What does a layer offer to the layer above? | TCP offers reliable transport to the application |
| **Protocol** (*protocolo*) | Which rules do two entities of the same layer on different devices follow? | Client TCP ↔ server TCP |
| **Layer interface** (*interfaz entre capas*) | How does one layer use another inside the same device? | The application hands data to TCP |

You do not need to memorize OSI as a goal in itself: what matters is to **understand the function** and then apply the correct label.

## 2.1. OSI as a reference model

The OSI model organizes communication into seven layers:

| OSI | General function |
|---:|---|
| 7. Application | Services used by applications |
| 6. Presentation | Data representation and transformation |
| 5. Session | Dialog organization |
| 4. Transport | Process-to-process communication |
| 3. Network | Addressing and communication across networks |
| 2. Data Link | Delivery over a local link |
| 1. Physical | Signal transmission |

OSI is a **reference model**: it is used to describe and compare, not the stack that actually runs on the Internet. In practice, presentation and session functions (for example, TLS encryption or data formats) are usually handled inside applications or their protocols.

### Layer numbers as professional language

Even when we work with TCP/IP, layer numbers are taken from OSI:

| Expression | Meaning |
|---|---|
| “Layer 1 problem” (L1) | Cable, connector, signal, power |
| “Layer 2 device” (L2) | Works with frames and MAC addresses (switch) |
| “Layer 3 device” (L3) | Works with packets and IP addresses (router, multilayer switch) |
| “Layer 4 filtering” (L4) | Decides based on TCP/UDP ports |
| “Layer 7” (L7) | Refers to the application (HTTP, DNS…) |

## 2.2. Mapping TCP/IP to OSI

Approximate mapping:

| Five-layer TCP/IP | OSI |
|---|---|
| Application | Application + Presentation + Session |
| Transport | Transport |
| Network | Network |
| Data Link | Data Link |
| Physical | Physical |

This mapping is not a mathematically exact equivalence.

The useful rule is:

> **Understand the function first; learn the label second.**

## 2.3. Service, protocol, and layer interface

These are not synonyms. A simple way to see it: **service** and **interface** are **vertical** relationships (between layers on the same device); **protocol** is a **horizontal** relationship (between the same layer on two devices, called peer entities or *peers*).

```text
      Device A                         Device B
   ┌─────────────┐    protocol     ┌─────────────┐
   │ Application │ <─────────────> │ Application │
   ├─────────────┤                 ├─────────────┤
   │  Transport  │ <─────────────> │  Transport  │
   ├─────────────┤                 ├─────────────┤
   │   Network   │ <─────────────> │   Network   │
   └─────────────┘                 └─────────────┘
     ↑ service / interface (vertical, inside the device)
```

### Service

A function that one layer provides to another.

Example:

```text
TCP
→ provides a reliable transport service to an application
```

### Protocol

A set of rules followed by peer entities.

Conceptually:

```text
client TCP  ↔  server TCP
client IP   ↔  server IP
```

### Layer interface

The way one layer uses the services of another layer inside the same system.

```text
Application
   │ uses
   v
Transport
   │ uses
   v
Network
   │ uses
   v
Data Link
```

Therefore:

```text
service
≠
protocol
≠
layer interface
```

# 3. Encapsulation, Decapsulation, and PDUs

We already know that each layer solves one problem. Now we see **how** it does it: each layer adds to the data the control information it needs (addresses, ports, checks…). Going down the stack, the data is progressively “wrapped”; at the destination, each layer removes its own wrapper and passes the rest upward. Understanding this process is essential for reading a capture, because Wireshark shows exactly those wrappers, one inside another.

| Concept | Question it answers | Example |
|---|---|---|
| **Encapsulation** (*encapsulación*) | What happens to data as it goes down the sender’s stack? | TCP, IP, and Ethernet headers are added |
| **Decapsulation** (*desencapsulación*) | What happens at the receiver? | Each layer reads and removes its header |
| **PDU** (*Protocol Data Unit*) | What is the unit of information called at each layer? | Segment, packet, frame |
| **Header** (*cabecera*) | Where does a layer’s control information go? | Source and destination IP addresses |
| **Payload** (*carga útil*) | What is carried inside? | The IP packet inside the frame |
| **Trailer** (*tráiler*) | Which control information goes at the end? | Ethernet FCS |

A common mistake is to think that every network device “opens” all the layers. It does not: a switch works with the frame, a router goes up to the packet, and only the endpoints go all the way up to the application (see 3.5).

## 3.1. Encapsulation

When an application generates data, that information moves down the protocol stack.

Each layer adds control information needed to perform its job.

Example using TCP and IPv4:

```text
Application
[ data ]
    ↓
Transport
[ TCP header | data ]
    ↓
Network
[ IP header | TCP header | data ]
    ↓
Data Link
[ Ethernet header | IP packet | trailer ]
    ↓
Physical
bits / signals
```

This process is called **encapsulation**.

Each header takes up bytes that are not user data. This control information is called **overhead**: it is the “price” of letting each layer do its job.

## 3.2. Decapsulation

The reverse process happens at the destination.

```text
signal
  ↓
frame
  ↓
packet
  ↓
segment/datagram
  ↓
application data
```

Each layer:

1. interprets the control information that belongs to it;
2. performs its function;
3. passes the payload to the upper layer.

How does each layer know where to hand over the payload? Its header says so:

| Layer | Field that identifies the next protocol | Example |
|---|---|---|
| Data Link (Ethernet) | **EtherType** | `0x0800` → IPv4 |
| Network (IPv4) | **Protocol** | `6` → TCP |
| Transport (TCP/UDP) | **Destination port** | `443` → HTTPS server |

These fields are studied in sections 5 and 6.

## 3.3. PDU

A **PDU** (*Protocol Data Unit*) is the unit of information associated with a layer.

| Layer | Common PDU |
|---:|---|
| Application | Data / message |
| Transport with TCP | Segment |
| Transport with UDP | Datagram |
| Network | Packet |
| Data Link | Frame |
| Physical | Bits / symbols |

Terminology may vary in technical documentation. Understanding the function matters more than memorizing a vocabulary list.

## 3.4. Header, payload, and trailer

A PDU may contain:

- **header**: control information placed at the beginning;
- **payload**: the data being carried;
- **trailer**: control information placed at the end when used by that protocol.

Example:

```text
Ethernet frame
├── Ethernet header
├── IPv4 packet
└── FCS
```

The IPv4 packet is Ethernet’s payload.

Likewise:

```text
IPv4 packet
├── IPv4 header
└── TCP segment
```

The TCP segment is IPv4’s payload.

This leads to a key idea:

> The PDU from one layer can become the payload of the layer below.

## 3.5. Which layers each device processes

Each device “opens” the PDU only up to the layer it needs to make its decision (RA1: devices by layer):

| Device | Highest layer it normally processes | What it looks at to decide |
|---|---|---|
| **Repeater / hub** (historical) | 1 — Physical | Nothing: it regenerates and repeats the signal on every port |
| **Switch** | 2 — Data Link | Destination MAC of the frame |
| **Access point** | 2 — Data Link | Moves frames between the wireless and the wired network |
| **Router** | 3 — Network | Destination IP of the packet |
| **Multilayer switch** | 3 — Network | MAC or IP, depending on the function |
| **Firewall** | 3–4 (up to 7 on advanced devices) | IP, protocol, ports, and sometimes application data |
| **Host** (PC, server) | 5 — Application | The whole stack: it is the endpoint of the communication |

Practical consequence: when a packet crosses a router, the router **decapsulates** the frame, processes the packet, and **re-encapsulates** it in a new frame for the next link. We will look at this in detail in 5.6.

## 3.6. Observing encapsulation in Packet Tracer

In Packet Tracer, **Simulation mode** lets you follow a PDU step by step:

1. switch from *Realtime* to *Simulation* mode;
2. generate traffic (for example, a `ping` or a simple PDU);
3. advance with *Capture/Forward* and watch the *Event List*;
4. click the PDU envelope on a device:
   - **OSI Model** tab: incoming (*In Layers*) and outgoing (*Out Layers*) layers processed by that device;
   - **Inbound / Outbound PDU Details** tabs: headers of the PDU entering and leaving.

Comparing a switch and a router, you will see that the switch only reaches Layer 2, while the router reaches Layer 3 and builds a new frame. Packet Tracer is a **simulation**: it is useful to see the model, but it does not replace a real capture when the goal is to learn to interpret evidence.

# 4. Wireshark: Observe Before Interpreting

In U01 you opened a ready-made capture and filtered `dns` or `icmp`. From now on, you will capture on your own. And a new problem appears: a capture is not “the truth about the network,” but **partial evidence** that depends on where, when, and how it was obtained. This section teaches you to obtain useful, reproducible captures before you start interpreting protocols.

| Concept | Question it answers | Example |
|---|---|---|
| **Technical question** (*pregunta técnica*) | What do I want to find out with this capture? | “Does the TCP handshake complete?” |
| **Capture interface** (*interfaz de captura*) | Which adapter carries the traffic I am looking for? | Ethernet, Wi‑Fi, loopback |
| **Wireshark panes** (*packet list / details / bytes*) | Where do I see the summary, the fields, and the bytes? | List, details, bytes |
| **Display filter** (*filtro de visualización*) | Which part of what I captured do I want to see now? | `dns`, `tcp.port == 443` |
| **Capture filter** (*filtro de captura*) | Which traffic do I want to store? | `host 192.168.10.20` |
| **Capture point** (*punto de captura*) | From which place in the network am I observing? | On the client, on the server |
| **Capture context** (*contexto*) | Which data must I record so others understand the capture? | Host, interface, action, time, filter |

Wireshark is not used to “look at packets.”

It is used to answer technical questions with evidence.

## 4.1. A reproducible capture, step by step

A well-made capture always follows the same sequence:

```text
1. goal         → which question do I want to answer?
2. interface    → where will that traffic pass?
3. start        → begin capturing
4. action       → generate the traffic (ping, open a website, nslookup…)
5. stop         → stop as soon as the action ends
6. filter       → apply a display filter
7. record       → write down the context and save the file (.pcapng)
```

Short captures with one specific action are much easier to interpret than long “just in case” captures.

## 4.2. Before capturing: define a question

Examples:

```text
Is a DNS query sent?
Is a response received?
Does ARP occur?
Does the TCP handshake complete?
Which destination MAC is used?
Which destination port appears?
```

A specific question makes the capture easier to analyze.

## 4.3. Choose the interface

A system may have:

- Ethernet;
- Wi‑Fi;
- loopback;
- VPN;
- virtual interfaces.

The first practical question is:

> Which interface should carry the traffic I want to observe?

Choosing the wrong interface can make the target communication appear to be “missing.”

Tip: on the start screen, Wireshark shows a small activity graph next to each interface; the interface that has traffic and the IP address you see in `ipconfig` / `ip addr` is usually the right one.

## 4.4. Three main panes

Wireshark commonly displays:

1. **packet list**;
2. **packet details** (protocol details);
3. **packet bytes**.

```text
┌─────────────────────────┐
│ Packet list             │
├─────────────────────────┤
│ Packet details          │
├─────────────────────────┤
│ Bytes                   │
└─────────────────────────┘
```

| Pane | What it shows | What we use it for |
|---|---|---|
| Packet list | One row per packet: `No.`, `Time`, `Source`, `Destination`, `Protocol`, `Length`, `Info` | Seeing the sequence and locating packets |
| Packet details | The layers of the selected packet, one below another, expandable | Reading fields: MAC, IP, TTL, ports, flags… |
| Packet bytes | The content in hexadecimal and ASCII | Checking which bytes belong to a field |

The details pane is **encapsulation made visible**: from top to bottom you will see `Frame` (capture information), `Ethernet II`, `Internet Protocol Version 4`, `Transmission Control Protocol` or `User Datagram Protocol`, and finally the application protocol.

You do not need to interpret every byte.

**Fact and interpretation inside Wireshark.** The bytes are what was captured; field names, the *Protocol* column, and the *Info* text are the **interpretation** Wireshark makes with its protocol analyzers (*dissectors*). It is usually correct, but sometimes Wireshark guesses the protocol only from the port number. If something does not fit, check the fields.

## 4.5. Display filters

Examples:

```text
arp
icmp
dns
tcp
udp
dhcp
```

By address:

```text
ip.addr == 192.168.10.20
```

By port:

```text
tcp.port == 443
```

Combining conditions:

| Operator | Meaning | Example |
|---|---|---|
| `&&` (or `and`) | and | `ip.addr == 192.168.10.20 && tcp.port == 443` |
| `\|\|` (or `or`) | or | `arp \|\| icmp` |
| `!` (or `not`) | not | `!arp` |

A display filter:

- does not delete packets;
- does not modify the capture;
- only changes what is shown.

The filter bar turns **green** when the syntax is valid and **red** when it is not. In older Wireshark versions, DHCP was filtered with `bootp` instead of `dhcp`.

## 4.6. Capture filter versus display filter

A **capture filter** determines what traffic is stored.

A **display filter** determines what already captured traffic is shown.

| | Capture filter | Display filter |
|---|---|---|
| When it applies | Before capturing | Afterward, on what was captured |
| What happens to the rest | It is not stored: it is lost | It is only hidden; it can be shown again |
| Syntax | BPF: `host 192.168.10.20`, `port 53`, `arp` | Wireshark: `ip.addr == 192.168.10.20`, `udp.port == 53` |

The two syntaxes are **different**: `ip.addr == …` does not work as a capture filter, and `host …` does not work as a display filter.

U02 prioritizes display filters so evidence is not unnecessarily lost. Capture filters are reserved for busy networks or long captures.

## 4.7. Capture point

The capture depends on where we observe the network.

Capturing on the client may show:

```text
what the client sends
what the client receives
```

but does not automatically prove:

- what reached the server;
- what happened after another router;
- what an intermediate firewall dropped;
- what happened on another segment.

In addition, when connected to a normal switch port, your host only sees its own traffic and broadcast traffic: it does not see communications between two other hosts. Observing them would require techniques such as port mirroring, which are not covered in this unit.

Principle:

```text
absence in my capture
≠
proven absence everywhere in the network
```

## 4.8. Record context

A useful capture should include:

```text
Question:
Host:
Interface:
Capture point:
Date/time:
Action:
Duration:
Filter:
```

A PCAP without context can be difficult to interpret. Save the capture in **`.pcapng`** format (Wireshark’s default) with a name that says what it contains, and write down the **packet number** (`No.`) of the packets you use as evidence.

## 4.9. Capture with authorization

A packet capture may contain sensitive data.

Good practices:

- capture only in authorized environments;
- limit capture duration;
- avoid unrelated traffic;
- anonymize where appropriate;
- store captures securely;
- do not upload real captures to external services or AI assistants without authorization.

Section 10 develops these rules.

# 5. Ethernet, MAC, ARP, and ICMP on the Local Network

For an IPv4 packet to leave a host, knowing the destination IP is not enough: it must be delivered, frame by frame, to the **next device on the link**. Ethernet does that with MAC addresses. To know which MAC to use, IPv4 needs **ARP**. Finally, `ping` (ICMP) gives us a simple way to generate traffic and check the complete sequence in a local capture: ARP first, then ICMP.

| Concept | Question it answers | Example |
|---|---|---|
| **Ethernet frame** (*trama Ethernet*) | How is information packaged on the link? | Destination MAC, source MAC, EtherType, data, FCS |
| **MAC address** (*dirección MAC*) | Which interface on the link sends or receives the frame? | `00:11:22:33:44:55` |
| **Broadcast** (*difusión*) | How is a frame sent to every host on the link? | `ff:ff:ff:ff:ff:ff` |
| **EtherType** | Which protocol is inside the frame? | `0x0806` → ARP |
| **Local / remote destination** (*destino local / remoto*) | Which MAC do I send the frame to? | To the destination itself or to the gateway |
| **ARP** (*Address Resolution Protocol*) | Which MAC matches an IPv4 address on my network? | “Who has 192.168.10.1?” |
| **ICMP** (*Internet Control Message Protocol*) | How are control and diagnostic messages sent? | Echo Request / Echo Reply (`ping`) |

We should not confuse the **destination IP** (the final destination) with the **destination MAC** (the next device on the link): when the destination is remote, they are different.

## 5.1. Ethernet frame

Ethernet is a fundamental Data Link technology in wired LANs.

At this stage, recognize:

```text
destination MAC
source MAC
EtherType
payload
FCS
```

| Field | Function |
|---|---|
| Destination MAC | Identifies the destination on the link |
| Source MAC | Identifies the frame sender |
| EtherType | Identifies the protocol carried in the payload |
| Payload | Information being carried |
| FCS | Detects certain transmission errors |

Common EtherType values:

| Value | Meaning |
|---|---|
| `0x0800` | IPv4 |
| `0x0806` | ARP |
| `0x86DD` | IPv6 |

The FCS may not appear in some captures because the network interface may not pass it to the operating system. The **FCS** (*Frame Check Sequence*) lets the receiver **detect** that a frame arrived damaged and discard it; it does not correct it. The physical errors that cause this are studied in U03.

In Wireshark, the frame appears as `Ethernet II` in the details pane.

## 5.2. MAC address

An Ethernet MAC address has 48 bits and is commonly written in hexadecimal:

```text
00:11:22:33:44:55
```

Depending on the system, you will see it written differently, but it is the same address:

| System | Format |
|---|---|
| Linux, Wireshark | `00:11:22:33:44:55` |
| Windows | `00-11-22-33-44-55` |
| Cisco IOS | `0011.2233.4455` |

The first 24 bits form the **OUI** (*Organizationally Unique Identifier*), which identifies the manufacturer; that is why Wireshark can show names such as `Intel_33:44:55`.

Types of destination MAC:

| Type | Recipient | Example |
|---|---|---|
| **Unicast** | A single interface | `00:11:22:33:44:55` |
| **Broadcast** | Every interface on the link (broadcast domain) | `ff:ff:ff:ff:ff:ff` |
| **Multicast** | A group of interfaces | `01:00:5e:…` (IPv4), `33:33:…` (IPv6) |

Its function is associated with the **local link**.

A switch uses MAC information to forward frames. Detailed MAC table learning belongs to U06.

## 5.3. Local destination

Scenario:

```text
PC-A
 │
SW1
 │
PC-B
```

If PC-A considers PC-B a local destination:

- the destination IP remains PC-B;
- local-link information is required to deliver the frame;
- the frame is directed toward PC-B’s MAC address.

## 5.4. Remote destination

Scenario:

```text
PC-A
 │
SW1
 │
R1
 │
remote network
 │
Server
```

PC-A wants to reach the remote server.

The key idea is:

```text
destination IP
→ remote server

destination MAC of the first frame
→ local gateway
```

The host does not need to know the remote server’s MAC address.

It needs to know how to reach its **local next hop**.

How the host decides whether a destination is local or remote (by comparing its address and mask) is studied formally in U04. In U02, it is enough to know that both cases exist and to recognize them in a capture.

## 5.5. ARP

ARP resolves a relationship between an IPv4 address and a MAC address on the local network.

Example:

```text
ARP Request:
Who has 192.168.10.1?

        ↓

ARP Reply:
192.168.10.1 is at 00:11:22:33:44:55
```

How each message travels:

| Message | Destination MAC of the frame | Who processes it |
|---|---|---|
| **ARP Request** (opcode 1) | Broadcast `ff:ff:ff:ff:ff:ff` | Every host on the link receives it; only the one with that IP replies |
| **ARP Reply** (opcode 2) | Unicast, to the MAC of the host that asked | Only the host that asked |

In Wireshark, the *Info* column summarizes it like this:

```text
Who has 192.168.10.1? Tell 192.168.10.20
192.168.10.1 is at 00:11:22:33:44:55
```

The host may temporarily store that association in its **ARP cache**.

Windows:

```text
arp -a
```

Linux:

```text
ip neigh
```

Important consequence for capturing: **if the entry is already in the cache, no ARP is sent**, and you will not see it in the capture. On a lab host, the cache can be cleared before the test (`arp -d *` on Windows or `sudo ip neigh flush all` on Linux, both with administrator privileges).

ARP is not transported inside IPv4.

Ethernet can directly carry:

```text
ARP
or
IPv4
```

ARP works only with IPv4 and only within the local link. In IPv6, this function is performed by NDP, which is studied in U05.

## 5.6. What happens at a router?

Suppose:

```text
PC-A
→ SW1
→ R1
→ SW2
→ SRV
```

The router:

1. receives a frame valid for the incoming link;
2. processes the IP packet inside it;
3. decides how to continue;
4. builds a new frame for the outgoing link.

On a normal path without NAT:

```text
MAC addresses
→ change from link to link

endpoint IP addresses
→ continue to represent original source and final destination
```

What changes and what stays the same at each router hop (without NAT):

| Element | Does it change at the router? | Reason |
|---|---|---|
| Source and destination MAC | **Yes** | The frame is new on each link |
| FCS | **Yes** | It is calculated for the new frame |
| Source and destination IP | No | They identify the endpoints of the communication |
| TTL | **Yes**, decreases by 1 | Prevents endless loops (section 6) |
| IPv4 header checksum | **Yes** | Recalculated because the TTL changed |
| TCP/UDP ports and data | No | The router does not work at those layers |

Address translation (NAT), which does modify IP addresses and ports, is studied in U10; how the router chooses the exit (routing table) is studied in U08.

## 5.7. ICMP

ICMP carries control and diagnostic messages. It is a Network layer protocol, but its messages travel **inside** an IPv4 packet (`Protocol` field = 1).

Examples:

| Message | ICMP type | When it appears |
|---|---:|---|
| Echo Request | 8 | Sent by `ping` |
| Echo Reply | 0 | Reply to an Echo Request |
| Destination Unreachable | 3 | Delivery is not possible (network, host, or port unreachable) |
| Time Exceeded | 11 | TTL reached 0 at a router (basis of `tracert`) |

`ping` uses ICMP Echo messages.

## 5.8. ARP → ICMP sequence in a local capture

Case: PC-A (`192.168.10.20`) runs `ping 192.168.10.30` to PC-B, on the same LAN, with an empty ARP cache. Display filter: `arp || icmp`.

| No. | Source | Destination | Protocol | Info |
|---:|---|---|---|---|
| 1 | PC-A (MAC) | Broadcast | ARP | Who has 192.168.10.30? Tell 192.168.10.20 |
| 2 | PC-B (MAC) | PC-A (MAC) | ARP | 192.168.10.30 is at … |
| 3 | 192.168.10.20 | 192.168.10.30 | ICMP | Echo (ping) request |
| 4 | 192.168.10.30 | 192.168.10.20 | ICMP | Echo (ping) reply |

Reading it:

- ARP comes **first** because PC-A needs PC-B’s MAC to build the frame for the Echo Request;
- in the ARP rows the list shows MAC addresses (there is no IP header); in the ICMP rows it shows IP addresses;
- if the destination were remote, ARP would ask for the **gateway’s** IP, not the destination’s;
- if you repeat the `ping`, ARP normally no longer appears (the entry is cached).

## 5.9. What does a ping prove?

If we observe:

```text
Echo Request
→ Echo Reply
```

we can state that a specific ICMP communication received a response.

We cannot automatically state that:

- DNS works;
- HTTPS works;
- TCP port 443 is reachable;
- the application works;
- no intermittent loss exists;
- every network path is healthy.

And the other way around: if there is **no** Echo Reply, we do not yet know why (host powered off, firewall blocking ICMP, return-path failure…). As you saw in U01, a result is not a diagnosis.

General principle:

> **A test proves only what it actually tests.**

# 6. IPv4, TCP, UDP, and Ports

In the previous section we stayed on the local link. Now we move up two layers. The **IPv4 header** contains a few fields that answer very useful questions: who is communicating with whom, roughly how many routers the packet has crossed, and which protocol it carries. At the **Transport layer**, **ports** indicate which process or service is involved, and TCP and UDP offer two different ways to carry data.

| Concept | Question it answers | Example |
|---|---|---|
| **IPv4 Source / Destination Address** (*dirección origen / destino*) | Which IP endpoints are communicating? | `192.168.10.20` → `203.0.113.80` |
| **TTL** (*Time To Live*) | How many more hops can the packet make? | `64` |
| **Protocol** | What does the IPv4 packet carry? | `6` = TCP |
| **Port** (*puerto*) | Which process or service? | `443` |
| **Ephemeral port** (*puerto efímero*) | Which temporary port does the client use? | `53124` |
| **TCP** (*Transmission Control Protocol*) | How is data carried reliably and in order? | Web, SSH |
| **Three-way handshake** | How is a TCP connection established? | SYN, SYN/ACK, ACK |
| **UDP** (*User Datagram Protocol*) | How is data carried without prior setup? | DNS, DHCP |

Selective depth: we only study the fields that help answer specific questions. IPv4 planning, subnetting, VLSM, and CIDR belong to U04; here, IPv4 is studied as **observable packet information**.

## 6.1. Basic IPv4 fields

In a capture, recognize:

- Source Address;
- Destination Address;
- TTL;
- Protocol;
- Total Length.

You do not need to memorize the entire IPv4 header.

Example:

```text
IPv4
├── Source:      192.168.10.20
├── Destination: 203.0.113.80
├── TTL:         64
└── Protocol:    6 (TCP)
```

| Field | Question it answers |
|---|---|
| Source Address | Who sends the packet (source IP endpoint)? |
| Destination Address | Who is it finally addressed to? |
| TTL | How many more routers can it cross? |
| Protocol | Which protocol does it carry (ICMP, TCP, UDP)? |
| Total Length | How long is the whole packet (header + data), in bytes? |

## 6.2. Source and Destination

These fields identify the IP endpoints of the communication.

Within the scope studied here:

```text
Source Address
→ IP source

Destination Address
→ final IP destination
```

Useful filters: `ip.src == 192.168.10.20`, `ip.dst == 203.0.113.80`, or `ip.addr == …` (either of the two).

## 6.3. TTL

**TTL (Time To Live)** prevents a packet from circulating indefinitely.

Each router decreases the value by 1.

When the value reaches zero, the router discards the packet and normally sends an ICMP **Time Exceeded** message back to the source.

Common initial values (they can be changed):

| System | Typical initial TTL |
|---|---:|
| Linux, macOS, Android | 64 |
| Windows | 128 |
| Many network devices (Cisco routers) | 255 |

But:

```text
observed TTL = 57
```

does not automatically prove:

```text
the packet crossed exactly 7 routers
```

unless the original TTL is known. If we know the sender is a Linux host (TTL 64), “about 7 hops” is a **reasonable inference**, not an observed fact.

**Link to `tracert` (U01).** `tracert`/`traceroute` takes advantage of TTL: it sends probes with TTL = 1, 2, 3… and each router that brings the TTL to 0 replies with ICMP Time Exceeded, revealing its address. Windows (`tracert`) uses ICMP Echo probes; Linux (`traceroute`) uses UDP by default. That is why a router that does not answer those messages appears as `*`.

## 6.4. Protocol

The IPv4 `Protocol` field identifies the upper-layer protocol carried by IPv4.

Common values:

| Value | Protocol |
|---:|---|
| 1 | ICMP |
| 6 | TCP |
| 17 | UDP |

It is the Network layer equivalent of EtherType at the Data Link layer (section 3.2).

## 6.5. IP and port answer different questions

The Transport layer allows many processes to use the network at the same time.

```text
IP
→ which logical endpoint?

port
→ which process or service?
```

Example:

```text
203.0.113.80:443
```

The IP address identifies the IP endpoint.

The port helps identify the transport service.

The combination **IP + port** is called a *socket*. A specific connection is identified by five values (*5-tuple*): protocol, source IP, source port, destination IP, and destination port.

Ports you should recognize:

| Service | Transport | Port |
|---|---|---:|
| HTTP | TCP | 80 |
| HTTPS | TCP (and UDP with HTTP/3) | 443 |
| SSH | TCP | 22 |
| Telnet | TCP | 23 |
| DNS | UDP (and TCP) | 53 |
| DHCP | UDP | 67 server / 68 client |
| TFTP | UDP | 69 |

## 6.6. Source and destination ports

Servers commonly listen on known service ports.

Clients commonly use temporary or **ephemeral** ports.

| Range (IANA) | Name | Use |
|---|---|---|
| 0–1023 | Well-known ports | Standard services (22, 53, 80, 443…) |
| 1024–49151 | Registered ports | Specific applications |
| 49152–65535 | Dynamic or ephemeral ports | The client’s temporary source port |

The actual ephemeral range depends on the operating system (for example, many Linux systems use 32768–60999), so do not be surprised to see client ports outside 49152–65535.

Example:

```text
client 53124
→ server 443
```

Another connection may use:

```text
client 53125
→ server 443
```

This allows simultaneous communications to remain distinct.

In the reply, the ports appear **reversed**: source 443 → destination 53124.

## 6.7. TCP

TCP provides a connection-oriented transport service with reliability mechanisms.

For U02, understand these concepts:

- connection establishment;
- sequence numbers;
- acknowledgments;
- retransmissions;
- ordered delivery;
- flow control.

Advanced algorithms, detailed window behavior, and congestion control are not studied in depth here.

In Wireshark, sequence numbers are shown as **relative** values (starting at 0) to make them easier to read; the real (*raw*) value is a large randomly chosen number.

## 6.8. Three-way handshake

Initial establishment:

```text
Client                     Server

SYN ------------------------>
                 <----------- SYN, ACK
ACK ------------------------>
```

Application exchange can begin after this.

In a capture:

```text
SYN
SYN, ACK
ACK
```

is evidence that the initial TCP establishment completed **in the observed traffic**.

It does not prove that the application worked afterward.

A useful filter to see only connection starts: `tcp.flags.syn == 1`.

## 6.9. Basic TCP flags

Recognize:

| Flag | Initial function |
|---|---|
| SYN | Participates in connection establishment |
| ACK | Acknowledges information |
| FIN | Participates in orderly connection close |
| RST | Rejects or aborts a connection |

A `SYN` answered with `RST, ACK` usually means the destination host is reachable but **no service is listening** on that port: this is different evidence from “no response.”

## 6.10. UDP

UDP also uses ports, but it does not perform an establishment equivalent to TCP’s three-way handshake.

Its header is simpler: source port, destination port, length, and checksum.

Conceptually, it provides:

- lower overhead;
- datagram delivery;
- no built-in acknowledgments/retransmissions equivalent to TCP.

If an application running over UDP needs reliability, it implements it itself (for example, DNS asks again if it gets no answer).

Do not memorize:

```text
TCP = good
UDP = bad
```

or:

```text
TCP = slow
UDP = fast
```

Applications choose the transport service they need.

## 6.11. Functional comparison

| Characteristic | TCP | UDP |
|---|---|---|
| Uses ports | Yes | Yes |
| Connection setup | Yes | No equivalent setup |
| Built-in ACK behavior | Yes | Not as a general transport mechanism |
| Built-in retransmission | Yes | Not as a general transport function |
| Ordered delivery | Yes | Not a general property |
| Overhead | Higher | Lower |
| PDU | Segment | Datagram |
| Examples | HTTP(S), SSH | DNS, DHCP, TFTP, real-time voice and video |

# 7. DNS, DHCP, and Encrypted Traffic

DNS and DHCP appear here because they allow us to observe several layers working together: they are application protocols that travel over UDP, inside IPv4, inside Ethernet. In addition, each one leaves **different evidence**: resolving a name, obtaining a configuration, or opening an encrypted connection do not prove the same thing. This section teaches you to recognize that evidence and its limits. Detailed administration belongs to later units.

| Concept | Question it answers | Example in a capture |
|---|---|---|
| **DNS query / response** (*consulta / respuesta DNS*) | Was a name resolved, and with what result? | `Standard query A www.example.test` |
| **DNS record** (*resource record*, *registro DNS*) | What kind of information is requested? | A, AAAA, CNAME, MX |
| **DHCP (DORA)** | How does a host obtain its IP configuration? | Discover, Offer, Request, ACK |
| **Initial broadcast** (*difusión inicial*) | How does a host with no IP yet ask for one? | `0.0.0.0` → `255.255.255.255` |
| **Encrypted traffic** (TLS, HTTPS; *tráfico cifrado*) | What can and cannot be seen in a protected connection? | `Client Hello`, `Application Data` |
| **Encrypted DNS** (DoH / DoT; *DNS cifrado*) | Why do DNS queries sometimes not appear? | Resolution inside HTTPS |

We should not mix **resolving a name**, **having IP connectivity**, and **receiving the service**: they are three different checks.

## 7.1. DNS

DNS retrieves information associated with names.

Example:

```text
www.example.test
→ DNS query
→ DNS response
→ 203.0.113.80
```

A separate communication may then begin toward the returned address.

In a capture, DNS normally uses **UDP port 53** (destination 53 in the query, source 53 in the response). Query and response carry the same **Transaction ID**, which lets you pair them. Wireshark summarizes it like this:

```text
Standard query 0x1a2b A www.example.test
Standard query response 0x1a2b A www.example.test A 203.0.113.80
```

The `nslookup` tool you used in U01 generates exactly this kind of traffic.

## 7.2. Resolution is not reachability or service availability

Separate:

```text
name resolution
≠
IP connectivity
≠
application service
```

Examples:

- DNS can reply while the web server is down;
- `ping` can reply while HTTPS is blocked;
- HTTPS can work while ICMP is filtered.

## 7.3. Basic record types

Recognize:

| Type | Initial function |
|---|---|
| A | IPv4 address |
| AAAA | IPv6 address |
| CNAME | Alias |
| MX | Mail server |

You do not need to memorize every DNS record type.

It is common for a host to ask for both A and AAAA records for the same name: you will see two consecutive queries.

## 7.4. DNS and transport

Many DNS queries use UDP.

DNS can also use TCP (for example, for large responses or transfers between servers).

Do not memorize:

```text
DNS = always UDP
```

The capture shows which transport is actually being used in a specific case.

## 7.5. Why DNS sometimes does not appear in the capture

The fact that the `dns` filter shows nothing **does not prove** that no resolution took place:

| Cause | What happens | How to check |
|---|---|---|
| **DNS cache** (*caché DNS*) | The host already knew the answer and does not ask | `ipconfig /displaydns`; clear it with `ipconfig /flushdns` before the test |
| **Encrypted DNS** (DNS over HTTPS / DNS over TLS) | The browser or the system resolves inside an encrypted connection (TCP 443 or TCP 853) | Check the browser or system settings |
| **Wrong interface or capture point** | The query leaves through another interface | Review section 4 |

## 7.6. DHCP

DHCP lets a client obtain network parameters automatically.

A typical initial exchange follows:

```text
Discover
→ Offer
→ Request
→ Acknowledgment
```

This is commonly remembered as **DORA**.

| Message | Sent by | Purpose |
|---|---|---|
| **Discover** | Client | “Is there any DHCP server?” |
| **Offer** | Server | Offers an address and parameters |
| **Request** | Client | Formally requests the chosen offer |
| **ACK** (*Acknowledgment*) | Server | Confirms the lease |

DHCP can provide:

- IP address;
- mask/prefix;
- gateway;
- DNS server;
- lease time;
- additional parameters.

DHCP uses **UDP**: port **67** on the server and **68** on the client. Display filter: `dhcp`.

A **renewal** of an existing lease usually shows up only as Request → ACK. To observe a full DORA exchange on a Windows lab host, use `ipconfig /release` followed by `ipconfig /renew` (on Linux, it depends on the network manager the system uses).

Addressing design and DHCP server configuration are studied in U04; the router as a DHCP server and relay agent in U08; *DHCP snooping* protection in U06.

## 7.7. Initial broadcast

A client that does not yet have complete configuration may need to send certain messages in a way that can be received within the local broadcast domain.

In a typical Discover capture:

```text
Ethernet: source client MAC  → destination ff:ff:ff:ff:ff:ff
IPv4:     source 0.0.0.0     → destination 255.255.255.255
UDP:      port 68            → port 67
```

The client uses `0.0.0.0` because it has no address yet, and sends to everyone because it does not yet know where the server is. Since routers do not forward broadcasts, the DHCP server must be on the same network or a **relay** must exist (U08).

This prepares later work with relay mechanisms and routing, but those are not configured here.

## 7.8. Encrypted traffic

HTTPS protects application content using **TLS** (*Transport Layer Security*).

That does not mean:

```text
encrypted traffic
=
invisible traffic
```

Depending on the situation, we may still observe:

- IP addresses;
- ports;
- packet sizes;
- timing;
- TCP handshake;
- parts of cryptographic negotiation.

But we normally cannot directly read:

- passwords;
- form contents;
- page body;
- protected HTTP headers.

In an HTTPS capture, after the TCP handshake you will see TLS messages such as `Client Hello` and `Server Hello`, followed by `Application Data` (encrypted content). The `Client Hello` usually shows the requested **server name** in clear text (the **SNI** field, *Server Name Indication*), although some recent technologies try to hide it. Filter: `tls`.

Two modern precautions:

- many browsers use **HTTP/3 over QUIC**, which travels over **UDP 443**: if you filter `tcp.port == 443`, you may see nothing even though the website works (try `quic` or `udp.port == 443`);
- **encrypted DNS** (section 7.5) also hides name queries.

## 7.9. What each piece of evidence proves

| Observed evidence | What it lets you state | What it does NOT let you state |
|---|---|---|
| DNS query + response with an address | The name was resolved at that moment, from that point | That the server is reachable or the website works |
| DHCP Discover, Offer, Request, ACK | The client received a lease from a DHCP server | That the gateway or DNS received are correct or working |
| SYN, SYN/ACK, ACK to port 443 | The TCP connection with the server was established | That the page loaded correctly |
| TLS Client Hello + Server Hello + Application Data | An encrypted session was negotiated and data was exchanged | What content was exchanged or whether it was the expected one |

# 8. The Life of a Packet: Integrating the Layers

So far we have studied each layer and each protocol separately. In reality, they all act together and in a specific order. This section rebuilds, step by step, what happens when a user opens a website on a remote server, relating each step to the layer involved and to what a capture taken on the client would show.

| Step | Main layer | Protocol | Evidence in the client capture |
|---|---|---|---|
| Resolve the name | Application | DNS | Query and response |
| Decide local or remote | Network | IPv4 (mask) | Not visible: it is an internal host decision |
| Find the gateway’s MAC | Data Link/Network | ARP | Request and reply (if not cached) |
| Establish the connection | Transport | TCP | SYN, SYN/ACK, ACK |
| Negotiate encryption and exchange data | Application | TLS / HTTPS | Client Hello, Server Hello, Application Data |
| Cross the router | Network + Data Link | IPv4 + Ethernet | Not visible from the client; the TTL of replies is |

A single user “click” therefore generates **several different communications**; some may not appear in the capture (ARP cache, DNS cache) without meaning there is a failure.

Scenario:

```text
PC-A
→ SW1
→ R1
→ remote network
→ web server
```

The user enters:

```text
https://www.example.test
```

We will reconstruct the process without introducing advanced subnetting or routing.

## 8.1. Resolve the name

```text
name
→ DNS
→ server IP
```

Name resolution is its own communication.

It is not “part of HTTPS” in a magical way.

If the DNS server is also on another network, PC-A already needs the gateway’s MAC to send the query: that is why in many captures the **gateway ARP appears before the DNS query**.

## 8.2. Local or remote?

The host determines whether the destination is local or whether the gateway must be used.

Formal subnet calculations belong to U04.

In this example, the destination is remote.

## 8.3. Resolve the gateway MAC address

If no valid entry exists:

```text
ARP
→ gateway IP
→ gateway MAC
```

## 8.4. Build the communication

Conceptually:

```text
HTTPS
↓
TCP
↓
IPv4
↓
Ethernet
↓
signal
```

First frame:

```text
source MAC      → PC-A
destination MAC → gateway
```

Packet:

```text
source IP      → PC-A
destination IP → server
```

## 8.5. Router

R1:

1. receives the frame;
2. processes the IPv4 packet;
3. decreases TTL;
4. determines how to continue;
5. creates a new frame for the next link.

Within the scope studied here and without NAT:

```text
Layer 2 information
→ changes per link

endpoint IP information
→ continues to represent source and final destination
```

(See the “what changes and what stays the same” table in section 5.6.)

## 8.6. Transport

If the service uses TCP:

```text
SYN
→ SYN/ACK
→ ACK
```

Application communication may then begin: with HTTPS, first the TLS negotiation and then the encrypted data.

## 8.7. Return path

Communication needs a path in both directions.

```text
the packet left the client
≠
the response can return
```

This becomes essential in later routing and troubleshooting work.

## 8.8. Expected sequence in the client capture

Display filter: `arp || dns || tcp.port == 443 || tls`. A typical sequence (simplified, with empty caches) would be:

| Order | Protocol | Info (summary) | Layer / function |
|---:|---|---|---|
| 1 | ARP | Who has 192.168.10.1? (gateway) | Data Link: MAC of the next hop |
| 2 | ARP | 192.168.10.1 is at … | Data Link |
| 3 | DNS | Standard query A www.example.test | Application: resolution |
| 4 | DNS | Standard query response … A 203.0.113.80 | Application |
| 5 | TCP | 53124 → 443 [SYN] | Transport: establishment |
| 6 | TCP | 443 → 53124 [SYN, ACK] | Transport |
| 7 | TCP | 53124 → 443 [ACK] | Transport |
| 8 | TLS | Client Hello (SNI = www.example.test) | Application: encrypted negotiation |
| 9 | TLS | Server Hello, … | Application |
| 10 | TLS | Application Data | Application: encrypted content |

In every packet PC-A sends toward the Internet, the **destination MAC is the gateway’s** and the **destination IP is the server’s** (or the DNS server’s). This table is a model: in a real capture the order may vary, steps may be missing (caches), or others may appear (AAAA queries, QUIC, traffic from other applications).

# 9. Integrated Analysis and Building Evidence

A capture does not speak for itself: it has to be turned into statements that another technician can check. The most common risk is not ignorance of a protocol, but **concluding more than the evidence allows** (“there is no SYN/ACK, so the server is powered off”). This section proposes a reproducible method and a vocabulary to separate what you see from what you deduce.

| Concept | Question it answers | Example |
|---|---|---|
| **Evidence / fact** (*evidencia / hecho*) | What is directly observed? | “Packet 12 is a DNS response with 203.0.113.80” |
| **Inference** (*inferencia*) | What do I reasonably deduce from what I observed? | “The name was resolved” |
| **Hypothesis** (*hipótesis*) | Which possible explanation is not yet proven? | “The HTTPS service may not be listening” |
| **Conclusion** (*conclusión*) | What do I state with enough evidence, and with what limits? | “From the client, resolution works; the TCP connection does not complete” |
| **Limitation** (*limitación*) | What can I not know from this capture? | “No capture was taken on the server” |
| **Reproducibility** (*reproducibilidad*) | Could another technician repeat and check my analysis? | File, filter, and packet numbers |

The difference between a good and a bad analysis usually lies in the **conclusion**: it must say what the capture proves and also what it does not prove.

Traffic analysis is not random packet inspection.

Use a reproducible process.

## 9.1. Basic method

```text
1. define the question
2. record the capture point
3. identify endpoints
4. isolate relevant traffic
5. identify protocols
6. follow the sequence
7. relate layers and identifiers
8. record facts
9. form inferences
10. form hypotheses if needed
11. state limitations
12. propose the next test
13. write a limited conclusion
```

## 9.2. Evidence

A directly observable data point.

Example:

```text
A DNS response containing 203.0.113.80 is visible.
```

## 9.3. Inference

A reasonable interpretation derived from evidence.

```text
The name query received a DNS response.
```

## 9.4. Hypothesis

A possible explanation not yet proven.

```text
The HTTPS service may not be listening.
```

## 9.5. Conclusion

A statement supported by sufficient evidence.

A good conclusion includes limitations when relevant.

## 9.6. Careful technical language

The way you write shows whether you distinguish fact, inference, and hypothesis:

| To… | Useful expressions |
|---|---|
| Describe a fact | “The capture shows…,” “Packet N contains…,” “No … is visible in this capture” |
| State an inference | “This indicates…,” “This is consistent with…” |
| Propose a hypothesis | “One possible explanation is…,” “This could be caused by…” |
| Point out a limitation | “This capture does not prove…,” “From this capture point, it is not possible to know…” |

Avoid absolute statements (“definitely,” “the network is fine,” “the server is down”) if the evidence does not support them.

## 9.7. TCP example

Question:

> Does TCP connection establishment complete?

Capture:

```text
SYN
SYN
SYN
```

Fact:

```text
Client SYN packets are visible.
No SYN/ACK is visible in this capture.
```

Compatible hypotheses:

- service unavailable;
- filtering/firewall;
- wrong destination;
- return-path problem;
- incomplete capture;
- traffic not visible from this capture point.

Unjustified conclusion:

```text
“The server is powered off.”
```

Careful conclusion:

```text
From the client, the TCP connection to port 443 does not complete: three
SYN packets are visible with no reply. This capture does not show whether
the SYNs reached the server. Next test: capture on the server or test from
another host on the same network as the server.
```

The repeated SYNs are **retransmissions**: TCP tries again because it receives no reply.

## 9.8. DNS example

Question:

> Does the client receive a DNS response?

If we observe:

```text
DNS Query
DNS Response
```

we can state that query-and-response evidence exists at that capture point.

We cannot automatically state:

```text
the website works
```

## 9.9. Reproducibility

An analysis is reproducible when another person, with your file and your notes, can reach the same observations. To achieve this:

- save the capture (`.pcapng`) with a descriptive name;
- record the context (section 4.8);
- state the exact **filter** you used;
- cite the **packet numbers** (`No.`) that serve as evidence;
- separate facts, inferences, and hypotheses in the report.

## 9.10. Basic report

Use:

```text
Technical question:

Capture point:
Interface:
Action performed:
Filter:

Relevant packets/sequence:

Observed facts:
1.
2.
3.

Inferences:
1.
2.

Remaining hypotheses:

Limitations:

Next test:

Conclusion:
```

# 10. Security, Privacy, and Responsible Use of Packet Captures

A packet analyzer is a very powerful professional tool, and that is exactly why it demands responsibility: a capture may contain personal information or credentials, and capturing other people’s traffic without authorization may be illegal. In addition, it is now common to ask AI assistants for help interpreting captures; they can be useful, but they **do not see your network** and are not a source of evidence.

| Concept | Question it answers | Example |
|---|---|---|
| **Sensitive data** (*datos sensibles*) | What sensitive information may a capture contain? | DNS queries, cookies, credentials |
| **Authorization** (*autorización*) | Where and when may I capture? | Only on authorized lab networks and hosts |
| **Anonymization** (*anonimización*) | How do I share a capture without exposing data? | Replace real addresses and names |
| **AI as support** (*IA como apoyo*) | What is it useful for, and what not? | It explains a field, but provides no evidence |

We should not confuse **being able to capture** (the tool allows it) with **being authorized to capture**.

## 10.1. What a capture may contain

A capture may contain:

- addresses;
- hostnames;
- DNS queries;
- identifiers;
- unencrypted content;
- cookies;
- credentials in insecure protocols;
- personal information.

Therefore:

1. capture only in authorized environments;
2. limit scope and duration;
3. avoid unnecessary real-user traffic;
4. anonymize data when appropriate;
5. store capture files securely;
6. do not share real captures with external services without authorization.

## 10.2. AI as support

An AI assistant can help:

- explain a field;
- recall filter syntax;
- summarize a sequence;
- suggest hypotheses;
- improve a report.

But:

```text
AI
≠
network evidence
```

AI output must be checked against:

```text
capture
+
test
+
documentation
```

Traffic or fields that are not present must never be invented.

Example of a critical review:

| The AI says… | Checking against the evidence |
|---|---|
| “Since there is no SYN/ACK, the server is powered off.” | The capture only shows unanswered SYNs from the client. That is one hypothesis among several (firewall, return path, stopped service…), not a conclusion. |
| “The filter `ip.addr = 192.168.10.20` shows the host’s traffic.” | The correct syntax is `ip.addr == 192.168.10.20` (the bar turns red with `=`). |
| “Packet 15 shows the user’s password.” | Check packet 15: if it is TLS traffic (`Application Data`), the content is encrypted and that statement is false. |

# 12. Professional Terms You Should Recognize

Wireshark, vendor documentation, RFCs, and professional tools are in English. The goal is not only to translate these terms but to **recognize them and know what they mean**. The table gathers the unit’s terms in the order in which they appear.

| Term | Initial meaning |
|---|---|
| **layer** (*capa*) | group of related functions |
| **protocol** (*protocolo*) | set of rules between peer entities |
| **protocol stack / suite** (*pila de protocolos*) | set of protocols that work together |
| **service** (*servicio*) | function a layer offers to the layer above |
| **layer interface** (*interfaz entre capas*) | how one layer uses another on the same device |
| **encapsulation** (*encapsulación*) | adding control information going down the stack |
| **decapsulation** (*desencapsulación*) | removing that information going up the stack |
| **PDU** | data unit of a layer |
| **header** (*cabecera*) | control information at the start of the PDU |
| **payload** (*carga útil*) | what is being carried |
| **trailer** (*tráiler*) | control information at the end (e.g., FCS) |
| **overhead** (*sobrecarga*) | extra bytes added by headers |
| **segment** (*segmento*) | TCP PDU |
| **datagram** (*datagrama*) | UDP PDU |
| **packet** (*paquete*) | Network layer PDU |
| **frame** (*trama*) | Data Link layer PDU |
| **source** (*origen*) | sender side |
| **destination** (*destino*) | receiver side |
| **MAC address** (*dirección MAC*) | address of the interface on the local link |
| **OUI** | part of the MAC that identifies the manufacturer |
| **broadcast** (*difusión*) | delivery to every host on the link |
| **EtherType** | field that indicates which protocol the frame carries |
| **FCS** | frame check sequence |
| **ARP** | IPv4-to-MAC resolution on the local link |
| **ARP cache** (*caché ARP*) | temporary table of IP–MAC associations |
| **TTL** | time to live: remaining hops for a packet |
| **ICMP** | IP control and diagnostic messages |
| **Echo Request / Echo Reply** | ICMP messages used by `ping` |
| **Time Exceeded** | ICMP message sent when TTL reaches 0 |
| **port** (*puerto*) | transport identifier of a process or service |
| **ephemeral port** (*puerto efímero*) | client’s temporary port |
| **socket** | combination of IP address and port |
| **SYN / ACK / FIN / RST** | basic TCP flags |
| **three-way handshake** | TCP connection establishment |
| **retransmission** (*retransmisión*) | resending unacknowledged data |
| **DNS query / DNS response** (*consulta / respuesta DNS*) | name-resolution request and reply |
| **DNS cache** (*caché DNS*) | temporarily stored DNS answers |
| **DHCP Discover / Offer / Request / Acknowledgment** | DORA messages |
| **lease** (*concesión*) | DHCP address assignment for a period of time |
| **TLS** | encryption protocol used by HTTPS |
| **SNI** | server name visible in the Client Hello |
| **display filter** (*filtro de visualización*) | filter applied to what was captured |
| **capture filter** (*filtro de captura*) | filter that decides what is stored |
| **capture point** (*punto de captura*) | place from which traffic is observed |
| **packet list / packet details / packet bytes** | Wireshark panes |
| **dissector** | Wireshark component that interprets a protocol |
| **evidence** (*evidencia*) | observable result |
| **inference** (*inferencia*) | reasonable deduction from evidence |
| **hypothesis** (*hipótesis*) | possible explanation not yet proven |
| **conclusion** (*conclusión*) | statement supported by enough evidence |

These terms appear naturally in Wireshark, operating systems, RFCs, Cisco documentation, and professional tools.
