# 1. Capas y modelo TCP/IP

Cuando abres una página web parece que ocurre una sola cosa, pero en realidad se resuelven a la vez varios problemas muy distintos: saber qué pedir, entregarlo al programa correcto, encontrar el equipo de destino, pasar de un dispositivo al siguiente y convertir todo en señales. Si intentáramos estudiarlo todo junto, sería imposible entenderlo o localizar un fallo.

Por eso las redes se describen con **modelos por capas**: cada capa se ocupa de un problema concreto y se apoya en la capa inferior. En U01 viste el mapa de cinco capas; en este apartado lo formalizamos, vemos qué es una **pila de protocolos** y lo aplicamos a una petición web real.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Capa** (*layer*) | ¿Qué grupo de funciones relacionadas resuelve un problema concreto? | La capa de transporte entrega datos al proceso correcto |
| **Modelo por capas** (*layered model*) | ¿Cómo se organiza la comunicación completa? | TCP/IP de cinco capas, OSI |
| **Modelo TCP/IP** (*TCP/IP model*) | ¿Qué mapa usaremos durante el módulo? | Aplicación, Transporte, Red, Enlace, Física |
| **Pila de protocolos** (*protocol stack / protocol suite*) | ¿Qué protocolos concretos trabajan juntos, uno en cada capa? | HTTPS + TCP + IPv4 + Ethernet |

No debemos confundir **capa** con **dispositivo**: un mismo equipo participa en varias capas a la vez, y una capa no es una caja que se pueda tocar.

## 1.1. ¿Por qué se utilizan capas?

Una comunicación de red debe resolver problemas diferentes:

- una aplicación genera o consume datos;
- los datos deben llegar al proceso correcto;
- los extremos deben identificarse;
- la información debe poder atravesar una o varias redes;
- cada enlace debe entregar información al siguiente dispositivo;
- el medio físico debe transportar señales.

Si intentáramos explicar todo como una sola función sería muy difícil:

- sustituir tecnologías;
- entender responsabilidades;
- localizar fallos;
- interpretar una captura.

Los modelos por capas permiten separar funciones relacionadas.

```text
capa
=
grupo de funciones relacionadas
```

Las capas no son dispositivos físicos.

Un mismo equipo puede participar simultáneamente en funciones de todas las capas.

Ventajas prácticas de trabajar por capas:

| Ventaja | Qué significa | Ejemplo |
|---|---|---|
| **Modularidad** | Se puede cambiar una capa sin rehacer las demás | Pasar de cable a Wi‑Fi no obliga a cambiar el navegador |
| **Interoperabilidad** | Fabricantes distintos pueden cooperar si respetan el mismo protocolo en cada capa | Un portátil de una marca navega a través de un router de otra |
| **Diagnóstico** | Se puede preguntar capa por capa dónde está el fallo | «¿Hay enlace? ¿Hay IP? ¿Resuelve el nombre? ¿Responde el servicio?» |
| **Aprendizaje** | Se estudia cada problema con el nivel de detalle adecuado | En U03 medios, en U04 direccionamiento, etc. |

## 1.2. Modelo TCP/IP de cinco capas

En este módulo utilizaremos principalmente este modelo (ya lo viste en U01; aquí añadimos el número de capa, que usarás mucho en lenguaje profesional):

| Capa | Pregunta principal | Ejemplos |
|---:|---|---|
| **5. Aplicación** | ¿Qué servicio utiliza la aplicación? | HTTP(S), DNS, DHCP, SSH |
| **4. Transporte** | ¿Qué proceso debe recibir los datos? | TCP, UDP |
| **3. Red** | ¿Cómo se identifica y alcanza el destino entre redes? | IPv4, IPv6, ICMP |
| **2. Enlace** (de datos) | ¿Cómo se entrega la información en un enlace concreto? | Ethernet, Wi‑Fi |
| **1. Física** | ¿Cómo viaja la señal por el medio? | cobre, fibra, radio |

Ejemplo conceptual:

```text
HTTPS
  ↓
TCP
  ↓
IPv4
  ↓
Ethernet
  ↓
señal
```

Cada capa utiliza servicios de la capa inferior y proporciona un servicio a la superior.

**Nota: cuatro o cinco capas.** La definición original de TCP/IP (RFC 1122) usa **cuatro capas**: Aplicación, Transporte, Internet y Acceso a la red (*Link*). El modelo de cinco capas que usamos divide esa última en **Enlace** y **Física**, porque así es más fácil razonar sobre cables y tramas por separado. Si en otra documentación ves cuatro capas, no es un error: es la misma idea con otra división.

| TCP/IP de cuatro capas (RFC 1122) | TCP/IP de cinco capas (este módulo) |
|---|---|
| Aplicación | Aplicación |
| Transporte | Transporte |
| Internet | Red |
| Acceso a la red (*Link*) | Enlace + Física |

## 1.3. Pila de protocolos

Un modelo describe **funciones**; una **pila de protocolos** (*protocol stack*) es el conjunto concreto de protocolos que implementan esas funciones y trabajan juntos en un equipo. El conjunto de protocolos de Internet se conoce como **familia o suite TCP/IP** (*TCP/IP protocol suite*): recibe el nombre de dos de sus protocolos más importantes, pero incluye muchos más.

| Capa | Protocolos habituales de la suite TCP/IP |
|---|---|
| Aplicación | HTTP, HTTPS (HTTP sobre TLS), DNS, DHCP, SSH, SMTP, FTP, TFTP |
| Transporte | TCP, UDP |
| Red | IPv4, IPv6, ICMP, ICMPv6 |
| Enlace | Ethernet (IEEE 802.3), Wi‑Fi (IEEE 802.11), ARP (entre enlace y red) |
| Física | Especificaciones de cable, conectores, fibra y radio (U03) |

En cada comunicación concreta se elige **un protocolo por capa** y se «apilan»:

```text
navegar por una web     →  HTTPS / TCP / IPv4 / Ethernet / cobre
consultar un nombre     →  DNS   / UDP / IPv4 / Wi‑Fi   / radio
```

ARP aparece en la tabla entre enlace y red porque sirve para relacionar direcciones de ambas capas; lo estudiarás en el apartado 5.

## 1.4. Una acción, varias funciones: ejemplo de petición web

Un usuario escribe `https://www.example.test` en el navegador. Estas son algunas funciones que deben cumplirse y la capa que las asume:

| Función necesaria | Capa | Protocolo o elemento |
|---|---|---|
| Pedir la página y recibirla de forma segura | Aplicación | HTTPS (HTTP + TLS) |
| Traducir `www.example.test` a una dirección IP | Aplicación | DNS |
| Entregar los datos al proceso servidor web y no a otro | Transporte | TCP, puerto 443 |
| Identificar el equipo de destino, aunque esté en otra red | Red | IPv4 (dirección destino) |
| Entregar la información al siguiente dispositivo del enlace (el gateway) | Enlace | Ethernet (MAC destino) |
| Averiguar la MAC del gateway | Enlace/Red | ARP |
| Transmitir los bits por el cable | Física | señal eléctrica en par trenzado |

Observa que **una sola acción del usuario genera varias comunicaciones** (DNS, ARP, TCP…) y que cada función pertenece a una capa distinta. Esta tabla es la base de todo lo que haremos en la unidad.

# 2. OSI, servicio, protocolo e interfaz

TCP/IP no es el único modelo que encontrarás. En documentación técnica, certificaciones y conversaciones profesionales se usa constantemente el **modelo OSI**, sobre todo sus **números de capa**: «es un problema de capa 1», «un switch de capa 2», «un switch de capa 3». Este apartado relaciona los dos modelos y precisa tres términos que a menudo se mezclan: **servicio**, **protocolo** e **interfaz entre capas**.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Modelo OSI** (*OSI reference model*) | ¿Qué modelo de siete capas usa la documentación como referencia común? | «L2», «L3», «L7» |
| **Correspondencia TCP/IP–OSI** (*model mapping*) | ¿Qué capas OSI agrupa cada capa TCP/IP? | Aplicación TCP/IP ≈ capas 5, 6 y 7 OSI |
| **Servicio** (*service*) | ¿Qué ofrece una capa a la capa superior? | TCP ofrece transporte fiable a la aplicación |
| **Protocolo** (*protocol*) | ¿Qué reglas siguen dos entidades de la misma capa en equipos distintos? | TCP del cliente ↔ TCP del servidor |
| **Interfaz entre capas** (*layer interface*) | ¿Cómo usa una capa a otra dentro del mismo equipo? | La aplicación entrega datos a TCP |

No hay que memorizar OSI como fin en sí mismo: lo importante es **entender la función** y después poner la etiqueta correcta.

## 2.1. OSI como modelo de referencia

El modelo OSI organiza las funciones en siete capas:

| OSI | Función general |
|---:|---|
| 7. Aplicación | Servicios utilizados por aplicaciones |
| 6. Presentación | Representación y transformación de datos |
| 5. Sesión | Organización del diálogo |
| 4. Transporte | Comunicación entre procesos |
| 3. Red | Direccionamiento y comunicación entre redes |
| 2. Enlace de datos | Entrega dentro de un enlace |
| 1. Física | Transmisión de señales |

OSI es un **modelo de referencia**: sirve para describir y comparar, no es la pila que funciona en Internet. En la práctica, las funciones de presentación y sesión (por ejemplo, el cifrado TLS o el formato de los datos) suelen resolverse dentro de las aplicaciones o de sus protocolos.

### El número de capa como lenguaje profesional

Aunque trabajemos con TCP/IP, los números de capa se toman de OSI:

| Expresión | Significado |
|---|---|
| «problema de capa 1» (L1) | Cable, conector, señal, alimentación |
| «dispositivo de capa 2» (L2) | Trabaja con tramas y direcciones MAC (switch) |
| «dispositivo de capa 3» (L3) | Trabaja con paquetes y direcciones IP (router, switch multicapa) |
| «filtrado de capa 4» (L4) | Decide según puertos TCP/UDP |
| «capa 7» (L7) | Se refiere a la aplicación (HTTP, DNS…) |

## 2.2. Correspondencia entre TCP/IP y OSI

Relación aproximada:

| TCP/IP de cinco capas | OSI |
|---|---|
| Aplicación | Aplicación + Presentación + Sesión |
| Transporte | Transporte |
| Red | Red |
| Enlace | Enlace de datos |
| Física | Física |

Esta correspondencia no debe entenderse como una equivalencia matemática perfecta.

La regla útil es:

> **Primero comprende la función; después aprende la etiqueta.**

## 2.3. Servicio, protocolo e interfaz entre capas

No son sinónimos. Una forma sencilla de verlo: el **servicio** y la **interfaz** son relaciones **verticales** (entre capas del mismo equipo); el **protocolo** es una relación **horizontal** (entre la misma capa de dos equipos, llamadas entidades pares o *peers*).

```text
      Equipo A                         Equipo B
   ┌─────────────┐   protocolo     ┌─────────────┐
   │ Aplicación  │ <─────────────> │ Aplicación  │
   ├─────────────┤                 ├─────────────┤
   │ Transporte  │ <─────────────> │ Transporte  │
   ├─────────────┤                 ├─────────────┤
   │     Red     │ <─────────────> │     Red     │
   └─────────────┘                 └─────────────┘
     ↑ servicio / interfaz (vertical, dentro del equipo)
```

### Servicio

Una función que una capa ofrece a otra.

Ejemplo:

```text
TCP
→ proporciona a una aplicación un servicio de transporte fiable
```

### Protocolo

Conjunto de reglas utilizadas por entidades equivalentes.

Conceptualmente:

```text
TCP del cliente  ↔  TCP del servidor
IP del cliente   ↔  IP del servidor
```

### Interfaz entre capas

Forma en la que una capa utiliza los servicios de otra dentro del mismo sistema.

```text
Aplicación
   │ utiliza
   v
Transporte
   │ utiliza
   v
Red
   │ utiliza
   v
Enlace
```

Por tanto:

```text
servicio
≠
protocolo
≠
interfaz entre capas
```

# 3. Encapsulación, desencapsulación y PDU

Ya sabemos que cada capa resuelve un problema. Ahora vemos **cómo** lo hace: cada capa añade a los datos la información de control que necesita (direcciones, puertos, comprobaciones…). Al bajar por la pila, los datos se van «envolviendo»; al llegar al destino, cada capa quita su envoltorio y pasa el resto hacia arriba. Entender este proceso es imprescindible para leer una captura, porque Wireshark muestra precisamente esos envoltorios uno dentro de otro.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Encapsulación** (*encapsulation*) | ¿Qué ocurre con los datos al bajar por la pila del emisor? | Se añaden cabeceras TCP, IP y Ethernet |
| **Desencapsulación** (*decapsulation*) | ¿Qué ocurre en el receptor? | Cada capa lee y retira su cabecera |
| **PDU** (*Protocol Data Unit*) | ¿Cómo se llama la unidad de información en cada capa? | Segmento, paquete, trama |
| **Cabecera** (*header*) | ¿Dónde va la información de control de una capa? | Direcciones IP de origen y destino |
| **Carga útil** (*payload*) | ¿Qué se transporta dentro? | El paquete IP dentro de la trama |
| **Tráiler** (*trailer*) | ¿Qué información de control va al final? | FCS de Ethernet |

Un error típico es pensar que cada dispositivo de la red «abre» todas las capas. No es así: un switch trabaja con la trama, un router llega hasta el paquete, y solo los extremos llegan hasta la aplicación (lo verás en 3.5).

## 3.1. Encapsulación

Cuando una aplicación genera datos, la información desciende por la pila.

Cada capa añade información de control necesaria para realizar su función.

Ejemplo con TCP e IPv4:

```text
Aplicación
[ datos ]
    ↓
Transporte
[ cabecera TCP | datos ]
    ↓
Red
[ cabecera IP | cabecera TCP | datos ]
    ↓
Enlace
[ cabecera Ethernet | paquete IP | tráiler ]
    ↓
Física
bits / señales
```

Este proceso se denomina **encapsulación**.

Cada cabecera ocupa bytes que no son datos del usuario. Esa información de control se llama **sobrecarga** (*overhead*): es el «precio» de que cada capa pueda hacer su trabajo.

## 3.2. Desencapsulación

En el destino ocurre el proceso inverso.

```text
señal
  ↓
trama
  ↓
paquete
  ↓
segmento/datagrama
  ↓
datos de aplicación
```

Cada capa:

1. interpreta la información que le corresponde;
2. procesa su función;
3. entrega la carga útil a la capa superior.

¿Cómo sabe cada capa a quién entregar la carga útil? Porque su cabecera lo indica:

| Capa | Campo que indica el siguiente protocolo | Ejemplo |
|---|---|---|
| Enlace (Ethernet) | **EtherType** | `0x0800` → IPv4 |
| Red (IPv4) | **Protocol** | `6` → TCP |
| Transporte (TCP/UDP) | **Puerto destino** | `443` → servidor HTTPS |

Estos campos se estudian en los apartados 5 y 6.

## 3.3. PDU

Una **PDU** (*Protocol Data Unit*) es la unidad de información asociada a una capa.

| Capa | PDU habitual |
|---:|---|
| Aplicación | Datos / mensaje |
| Transporte con TCP | Segmento |
| Transporte con UDP | Datagrama |
| Red | Paquete |
| Enlace | Trama |
| Física | Bits / símbolos |

La terminología puede variar en documentación técnica. Lo importante es comprender la función.

## 3.4. Cabecera, carga útil y tráiler

Una PDU puede contener:

- **cabecera**: información de control al inicio;
- **carga útil** (*payload*): información transportada;
- **tráiler**: información de control al final, cuando el protocolo lo utiliza.

Ejemplo:

```text
Trama Ethernet
├── cabecera Ethernet
├── paquete IPv4
└── FCS
```

El paquete IPv4 es la carga útil de Ethernet.

A su vez:

```text
Paquete IPv4
├── cabecera IPv4
└── segmento TCP
```

El segmento TCP es la carga útil de IPv4.

Esto conduce a una idea fundamental:

> La PDU de una capa puede convertirse en la carga útil de la capa inferior.

## 3.5. Qué capas procesa cada dispositivo

Cada dispositivo «abre» la PDU solo hasta la capa que necesita para tomar su decisión (RA1: dispositivos por nivel):

| Dispositivo | Capa más alta que procesa normalmente | Qué mira para decidir |
|---|---|---|
| **Repetidor / hub** (*hub*, histórico) | 1 — Física | Nada: regenera y repite la señal por todos los puertos |
| **Switch** | 2 — Enlace | MAC destino de la trama |
| **Punto de acceso** (*access point*) | 2 — Enlace | Traslada tramas entre la red inalámbrica y la cableada |
| **Router** | 3 — Red | IP destino del paquete |
| **Switch multicapa** (*multilayer switch*) | 3 — Red | MAC o IP según la función |
| **Firewall** | 3–4 (y hasta 7 en equipos avanzados) | IP, protocolo, puertos y, a veces, datos de aplicación |
| **Host** (PC, servidor) | 5 — Aplicación | Toda la pila: es el extremo de la comunicación |

Consecuencia práctica: cuando un paquete atraviesa un router, el router **desencapsula** la trama, procesa el paquete y **vuelve a encapsular** en una trama nueva para el siguiente enlace. Lo veremos con detalle en 5.6.

## 3.6. Observar la encapsulación en Packet Tracer

En Packet Tracer, el **modo Simulación** permite seguir una PDU paso a paso:

1. cambia de modo *Realtime* a *Simulation*;
2. genera tráfico (por ejemplo, un `ping` o una PDU simple);
3. avanza con *Capture/Forward* y observa la *Event List*;
4. haz clic en el sobre de la PDU en un dispositivo:
   - pestaña **OSI Model**: capas de entrada (*In Layers*) y de salida (*Out Layers*) que procesa ese dispositivo;
   - pestañas **Inbound / Outbound PDU Details**: cabeceras de la PDU que entra y que sale.

Comparando un switch y un router verás que el switch solo llega a la capa 2, mientras que el router llega a la capa 3 y construye una trama nueva. Packet Tracer es una **simulación**: sirve para ver el modelo, pero no sustituye a una captura real cuando el objetivo es aprender a interpretar evidencia.

# 4. Wireshark: observar antes de interpretar

En U01 abriste una captura ya hecha y filtraste `dns` o `icmp`. A partir de ahora capturarás tú mismo. Y aparece un problema nuevo: una captura no es «la verdad de la red», sino una **evidencia parcial** que depende de dónde, cuándo y cómo se obtuvo. Este apartado enseña a obtener capturas útiles y reproducibles antes de empezar a interpretar protocolos.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Pregunta técnica** (*technical question*) | ¿Qué quiero averiguar con esta captura? | «¿Se completa el handshake TCP?» |
| **Interfaz de captura** (*capture interface*) | ¿Por qué tarjeta pasa el tráfico que busco? | Ethernet, Wi‑Fi, loopback |
| **Paneles de Wireshark** (*packet list / details / bytes*) | ¿Dónde veo el resumen, los campos y los bytes? | Lista, detalles, bytes |
| **Filtro de visualización** (*display filter*) | ¿Qué parte de lo capturado quiero ver ahora? | `dns`, `tcp.port == 443` |
| **Filtro de captura** (*capture filter*) | ¿Qué tráfico quiero guardar? | `host 192.168.10.20` |
| **Punto de captura** (*capture point*) | ¿Desde qué lugar de la red observo? | En el cliente, en el servidor |
| **Contexto** (*capture context*) | ¿Qué datos necesito anotar para que otro entienda la captura? | Equipo, interfaz, acción, hora, filtro |

Wireshark no se utiliza para «mirar paquetes».

Se utiliza para responder preguntas técnicas mediante evidencia.

## 4.1. Una captura reproducible paso a paso

Una captura bien hecha sigue siempre la misma secuencia:

```text
1. objetivo      → ¿qué pregunta quiero responder?
2. interfaz      → ¿por dónde pasará ese tráfico?
3. iniciar       → empezar a capturar
4. acción        → generar el tráfico (ping, abrir web, nslookup…)
5. detener       → parar en cuanto termine la acción
6. filtrar       → aplicar un filtro de visualización
7. registrar     → anotar contexto y guardar el archivo (.pcapng)
```

Capturas cortas y con una acción concreta son mucho más fáciles de interpretar que capturas largas «por si acaso».

## 4.2. Antes de capturar: formular una pregunta

Ejemplos:

```text
¿se realiza una consulta DNS?
¿se obtiene respuesta?
¿aparece ARP?
¿se completa el handshake TCP?
¿qué dirección MAC se utiliza?
¿qué puerto de destino aparece?
```

Una pregunta concreta produce una captura más fácil de interpretar.

## 4.3. Elegir la interfaz

Un equipo puede disponer de:

- Ethernet;
- Wi‑Fi;
- loopback;
- VPN;
- interfaces virtuales.

La primera pregunta práctica es:

> ¿Por qué interfaz debería circular el tráfico que quiero observar?

Elegir la interfaz equivocada puede producir una captura aparentemente «vacía» para la comunicación buscada.

Pista: en la pantalla inicial Wireshark muestra junto a cada interfaz una pequeña gráfica de actividad; la interfaz con tráfico y con la IP que ves en `ipconfig` / `ip addr` suele ser la buena.

## 4.4. Tres paneles principales

Wireshark suele presentar:

1. **lista de paquetes** (*packet list*);
2. **detalles de protocolos** (*packet details*);
3. **bytes capturados** (*packet bytes*).

```text
┌─────────────────────────┐
│ Lista de paquetes       │
├─────────────────────────┤
│ Detalles del paquete    │
├─────────────────────────┤
│ Bytes                   │
└─────────────────────────┘
```

| Panel | Qué muestra | Para qué lo usamos |
|---|---|---|
| Lista de paquetes | Una fila por paquete: `No.`, `Time`, `Source`, `Destination`, `Protocol`, `Length`, `Info` | Ver la secuencia y localizar paquetes |
| Detalles del paquete | Las capas del paquete seleccionado, una debajo de otra, desplegables | Leer campos: MAC, IP, TTL, puertos, flags… |
| Bytes | El contenido en hexadecimal y ASCII | Comprobar qué bytes corresponden a un campo |

El panel de detalles es **la encapsulación hecha visible**: de arriba abajo verás `Frame` (información de la captura), `Ethernet II`, `Internet Protocol Version 4`, `Transmission Control Protocol` o `User Datagram Protocol` y, por último, el protocolo de aplicación.

No es necesario interpretar todos los bytes.

**Hecho e interpretación dentro de Wireshark.** Los bytes son lo capturado; los nombres de campos, la columna *Protocol* y el texto de *Info* son la **interpretación** que hace Wireshark con sus analizadores (*dissectors*). Normalmente es correcta, pero a veces Wireshark deduce el protocolo solo por el número de puerto. Si algo no encaja, comprueba los campos.

## 4.5. Filtros de visualización

Ejemplos:

```text
arp
icmp
dns
tcp
udp
dhcp
```

Por dirección:

```text
ip.addr == 192.168.10.20
```

Por puerto:

```text
tcp.port == 443
```

Combinando condiciones:

| Operador | Significado | Ejemplo |
|---|---|---|
| `&&` (o `and`) | y | `ip.addr == 192.168.10.20 && tcp.port == 443` |
| `\|\|` (o `or`) | o | `arp \|\| icmp` |
| `!` (o `not`) | no | `!arp` |

Un filtro de visualización:

- no elimina paquetes;
- no modifica la captura;
- solo cambia qué paquetes se muestran.

La barra del filtro se pone **verde** si la sintaxis es válida y **roja** si no lo es. En versiones antiguas de Wireshark, DHCP se filtraba con `bootp` en lugar de `dhcp`.

## 4.6. Filtro de captura frente a filtro de visualización

Un **capture filter** decide qué tráfico se almacena.

Un **display filter** decide qué tráfico ya capturado se muestra.

| | Filtro de captura (*capture filter*) | Filtro de visualización (*display filter*) |
|---|---|---|
| Cuándo se aplica | Antes de capturar | Después, sobre lo capturado |
| Qué hace con el resto | No lo guarda: se pierde | Solo lo oculta; se puede volver a ver |
| Sintaxis | BPF: `host 192.168.10.20`, `port 53`, `arp` | Wireshark: `ip.addr == 192.168.10.20`, `udp.port == 53` |

Las dos sintaxis son **distintas**: `ip.addr == …` no funciona como filtro de captura y `host …` no funciona como filtro de visualización.

En U02 se priorizan filtros de visualización para evitar perder evidencia innecesariamente. Los filtros de captura se reservan para redes con mucho tráfico o capturas largas.

## 4.7. Punto de captura

La captura depende del lugar desde el que observamos.

Capturar en el cliente puede mostrar:

```text
qué envía el cliente
qué recibe el cliente
```

pero no demuestra automáticamente:

- qué llegó al servidor;
- qué ocurrió después de otro router;
- qué descartó un firewall intermedio;
- qué ocurrió en otro segmento.

Además, conectado a un puerto normal de un switch, tu equipo solo ve su propio tráfico y el tráfico de difusión (*broadcast*): no ve las comunicaciones entre otros dos equipos. Para observarlas harían falta técnicas como la réplica de puertos (*port mirroring*), que no se tratan en esta unidad.

Principio:

```text
ausencia en mi captura
≠
ausencia demostrada en toda la red
```

## 4.8. Registrar contexto

Una captura útil debe incluir contexto:

```text
Pregunta:
Equipo:
Interfaz:
Punto de captura:
Fecha/hora:
Acción:
Duración:
Filtro:
```

Un PCAP sin contexto puede ser difícil de interpretar. Guarda la captura en formato **`.pcapng`** (el formato por defecto de Wireshark) con un nombre que indique qué contiene, y anota el **número de paquete** (`No.`) de los paquetes que uses como evidencia.

## 4.9. Capturar con autorización

Una captura puede contener datos sensibles.

Buenas prácticas:

- capturar solo en entornos autorizados;
- limitar duración;
- evitar tráfico ajeno innecesario;
- anonimizar cuando proceda;
- almacenar de forma segura;
- no subir capturas reales a servicios externos o asistentes de IA sin autorización.

El apartado 10 desarrolla estas normas.

# 5. Ethernet, MAC, ARP e ICMP en la red local

Para que un paquete IPv4 salga de un equipo no basta con conocer la IP de destino: hay que entregarlo, trama a trama, al **siguiente dispositivo del enlace**. Eso lo hace Ethernet con direcciones MAC. Y para saber qué MAC usar, IPv4 necesita **ARP**. Finalmente, `ping` (ICMP) nos da una forma sencilla de generar tráfico y comprobar la secuencia completa en una captura local: primero ARP, después ICMP.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Trama Ethernet** (*Ethernet frame*) | ¿Cómo se empaqueta la información en el enlace? | MAC destino, MAC origen, EtherType, datos, FCS |
| **Dirección MAC** (*MAC address*) | ¿Qué interfaz del enlace envía o recibe la trama? | `00:11:22:33:44:55` |
| **Difusión** (*broadcast*) | ¿Cómo se envía una trama a todos los equipos del enlace? | `ff:ff:ff:ff:ff:ff` |
| **EtherType** | ¿Qué protocolo va dentro de la trama? | `0x0806` → ARP |
| **Destino local / remoto** (*local / remote destination*) | ¿A qué MAC envío la trama? | Al propio destino o al gateway |
| **ARP** (*Address Resolution Protocol*) | ¿Qué MAC corresponde a una IPv4 de mi red? | «¿Quién tiene 192.168.10.1?» |
| **ICMP** (*Internet Control Message Protocol*) | ¿Cómo se envían mensajes de control y diagnóstico? | Echo Request / Echo Reply (`ping`) |

No debemos confundir **IP destino** (el destino final) con **MAC destino** (el siguiente equipo del enlace): cuando el destino es remoto, no coinciden.

## 5.1. Trama Ethernet

Ethernet es una tecnología de enlace fundamental en LAN cableadas.

En una trama interesa reconocer inicialmente:

```text
MAC destino
MAC origen
EtherType
carga útil
FCS
```

| Campo | Función |
|---|---|
| MAC destino | Identifica el destinatario en el enlace |
| MAC origen | Identifica al emisor de la trama |
| EtherType | Indica qué protocolo contiene la carga útil |
| Carga útil | Información transportada |
| FCS | Permite detectar determinados errores |

Valores EtherType frecuentes:

| Valor | Significado |
|---|---|
| `0x0800` | IPv4 |
| `0x0806` | ARP |
| `0x86DD` | IPv6 |

En algunas capturas el FCS no aparece porque la interfaz no lo entrega al sistema operativo. El **FCS** (*Frame Check Sequence*) permite al receptor **detectar** que una trama llegó dañada y descartarla; no la corrige. Los errores físicos que lo provocan se estudian en U03.

En Wireshark, la trama aparece como `Ethernet II` en el panel de detalles.

## 5.2. Dirección MAC

Una MAC Ethernet tiene 48 bits y suele representarse en hexadecimal:

```text
00:11:22:33:44:55
```

Según el sistema la verás escrita de forma distinta, pero es la misma dirección:

| Sistema | Formato |
|---|---|
| Linux, Wireshark | `00:11:22:33:44:55` |
| Windows | `00-11-22-33-44-55` |
| Cisco IOS | `0011.2233.4455` |

Los primeros 24 bits forman el **OUI** (*Organizationally Unique Identifier*), que identifica al fabricante; por eso Wireshark puede mostrar nombres como `Intel_33:44:55`.

Tipos de MAC de destino:

| Tipo | Destinatario | Ejemplo |
|---|---|---|
| **Unicast** | Una sola interfaz | `00:11:22:33:44:55` |
| **Broadcast** | Todas las interfaces del enlace (dominio de difusión) | `ff:ff:ff:ff:ff:ff` |
| **Multicast** | Un grupo de interfaces | `01:00:5e:…` (IPv4), `33:33:…` (IPv6) |

Su función está asociada al **enlace local**.

Un switch utiliza información MAC para reenviar tramas. El aprendizaje y funcionamiento detallado de la tabla MAC pertenece a U06.

## 5.3. Destino local

Escenario:

```text
PC-A
 │
SW1
 │
PC-B
```

Si PC-A considera a PC-B un destino local:

- mantiene como destino IP a PC-B;
- necesita información de enlace para poder entregarle la trama;
- la trama se dirige a la MAC correspondiente a PC-B.

## 5.4. Destino remoto

Escenario:

```text
PC-A
 │
SW1
 │
R1
 │
red remota
 │
Servidor
```

PC-A quiere llegar al servidor remoto.

La idea fundamental es:

```text
IP destino
→ servidor remoto

MAC destino de la primera trama
→ gateway local
```

El host no necesita conocer la MAC del servidor remoto.

Necesita conocer cómo llegar al **siguiente salto local**.

Cómo decide el host si un destino es local o remoto (comparando su dirección y su máscara) se estudia formalmente en U04. En U02 basta con saber que existen los dos casos y reconocerlos en una captura.

## 5.5. ARP

ARP permite resolver una relación entre IPv4 y MAC en el ámbito local.

Ejemplo:

```text
ARP Request:
¿Quién tiene 192.168.10.1?

        ↓

ARP Reply:
192.168.10.1 está en 00:11:22:33:44:55
```

Cómo viaja cada mensaje:

| Mensaje | MAC destino de la trama | Quién lo procesa |
|---|---|---|
| **ARP Request** (*opcode* 1) | Broadcast `ff:ff:ff:ff:ff:ff` | Todos los equipos del enlace lo reciben; solo responde el que tiene esa IP |
| **ARP Reply** (*opcode* 2) | Unicast, a la MAC de quien preguntó | Solo el que preguntó |

En Wireshark la columna *Info* lo resume así:

```text
Who has 192.168.10.1? Tell 192.168.10.20
192.168.10.1 is at 00:11:22:33:44:55
```

El host puede almacenar temporalmente la asociación en su **caché ARP** (*ARP cache*).

Windows:

```text
arp -a
```

Linux:

```text
ip neigh
```

Consecuencia importante para capturar: **si la entrada ya está en la caché, no se envía ARP** y no lo verás en la captura. En un equipo de laboratorio puede vaciarse la caché antes de la prueba (`arp -d *` en Windows o `sudo ip neigh flush all` en Linux, ambos con privilegios de administrador).

ARP no se transporta dentro de IPv4.

Ethernet puede transportar directamente:

```text
ARP
o
IPv4
```

ARP solo funciona en IPv4 y dentro del enlace local. En IPv6 esa función la realiza NDP, que se estudia en U05.

## 5.6. Qué ocurre al atravesar un router

Supongamos:

```text
PC-A
→ SW1
→ R1
→ SW2
→ SRV
```

El router:

1. recibe una trama válida para el enlace de entrada;
2. procesa el paquete IP contenido;
3. decide por dónde continuar;
4. construye una nueva trama para el enlace de salida.

En un recorrido normal sin NAT:

```text
direcciones MAC
→ cambian entre enlaces

direcciones IP de los extremos
→ permanecen asociadas a origen y destino final
```

Qué cambia y qué permanece en cada salto por un router (sin NAT):

| Elemento | ¿Cambia al atravesar el router? | Motivo |
|---|---|---|
| MAC origen y MAC destino | **Sí** | La trama es nueva en cada enlace |
| FCS | **Sí** | Se calcula para la nueva trama |
| IP origen e IP destino | No | Identifican los extremos de la comunicación |
| TTL | **Sí**, disminuye en 1 | Evita bucles infinitos (apartado 6) |
| Suma de comprobación de la cabecera IPv4 | **Sí** | Se recalcula porque ha cambiado el TTL |
| Puertos TCP/UDP y datos | No | El router no trabaja en esas capas |

La traducción de direcciones (NAT), que sí modifica IP y puertos, se estudia en U10; la forma en que el router elige la salida (tabla de routing), en U08.

## 5.7. ICMP

ICMP transporta mensajes de control y diagnóstico. Es un protocolo de la capa de red, pero sus mensajes viajan **dentro** de un paquete IPv4 (campo `Protocol` = 1).

Ejemplos:

| Mensaje | Tipo ICMP | Cuándo aparece |
|---|---:|---|
| Echo Request | 8 | Lo envía `ping` |
| Echo Reply | 0 | Respuesta al Echo Request |
| Destination Unreachable | 3 | No se puede entregar (red, host o puerto inalcanzable) |
| Time Exceeded | 11 | El TTL llegó a 0 en un router (base de `tracert`) |

`ping` utiliza ICMP Echo.

## 5.8. Secuencia ARP → ICMP en una captura local

Caso: PC-A (`192.168.10.20`) hace `ping 192.168.10.30` a PC-B, en la misma LAN, con la caché ARP vacía. Filtro de visualización: `arp || icmp`.

| No. | Source | Destination | Protocol | Info |
|---:|---|---|---|---|
| 1 | PC-A (MAC) | Broadcast | ARP | Who has 192.168.10.30? Tell 192.168.10.20 |
| 2 | PC-B (MAC) | PC-A (MAC) | ARP | 192.168.10.30 is at … |
| 3 | 192.168.10.20 | 192.168.10.30 | ICMP | Echo (ping) request |
| 4 | 192.168.10.30 | 192.168.10.20 | ICMP | Echo (ping) reply |

Lectura:

- ARP va **antes** porque PC-A necesita la MAC de PC-B para construir la trama del Echo Request;
- en las filas ARP la lista muestra MAC (no hay cabecera IP); en las ICMP muestra IP;
- si el destino fuera remoto, el ARP preguntaría por la IP del **gateway**, no por la del destino;
- si repites el `ping`, normalmente ya no aparece ARP (la entrada está en caché).

## 5.9. Qué demuestra un ping

Si observamos:

```text
Echo Request
→ Echo Reply
```

podemos afirmar que una comunicación ICMP concreta ha tenido respuesta.

No podemos afirmar automáticamente:

- que DNS funciona;
- que HTTPS funciona;
- que el puerto 443 está accesible;
- que la aplicación funciona;
- que no existen pérdidas en otros momentos;
- que todos los caminos de la red están bien.

Y al revés: si **no** hay Echo Reply, no sabemos todavía por qué (equipo apagado, firewall que bloquea ICMP, fallo de retorno…). Como viste en U01, un resultado no es un diagnóstico.

Principio general:

> **Una prueba solo demuestra aquello que realmente comprueba.**

# 6. IPv4, TCP, UDP y puertos

En el apartado anterior nos quedamos en el enlace local. Ahora subimos dos capas. En la **cabecera IPv4** hay unos pocos campos que responden a preguntas muy útiles: quién comunica con quién, cuántos routers ha atravesado aproximadamente el paquete y qué protocolo lleva dentro. En la **capa de transporte**, los **puertos** indican qué proceso o servicio participa, y TCP y UDP ofrecen dos formas distintas de transportar los datos.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Dirección origen / destino IPv4** (*Source / Destination Address*) | ¿Qué extremos IP comunican? | `192.168.10.20` → `203.0.113.80` |
| **TTL** (*Time To Live*) | ¿Cuántos saltos más puede dar el paquete? | `64` |
| **Protocol** | ¿Qué lleva dentro el paquete IPv4? | `6` = TCP |
| **Puerto** (*port*) | ¿Qué proceso o servicio? | `443` |
| **Puerto efímero** (*ephemeral port*) | ¿Qué puerto temporal usa el cliente? | `53124` |
| **TCP** (*Transmission Control Protocol*) | ¿Cómo se transporta de forma fiable y ordenada? | Web, SSH |
| **Three-way handshake** | ¿Cómo se establece una conexión TCP? | SYN, SYN/ACK, ACK |
| **UDP** (*User Datagram Protocol*) | ¿Cómo se transporta sin conexión previa? | DNS, DHCP |

Profundidad selectiva: solo estudiaremos los campos que sirven para responder preguntas concretas. La planificación IPv4, el subnetting, VLSM y CIDR pertenecen a U04; aquí IPv4 se estudia como **información observable dentro de un paquete**.

## 6.1. Campos básicos de IPv4

En una captura interesa reconocer:

- Source Address;
- Destination Address;
- TTL;
- Protocol;
- Total Length.

No es necesario memorizar la cabecera completa.

Ejemplo:

```text
IPv4
├── Source:      192.168.10.20
├── Destination: 203.0.113.80
├── TTL:         64
└── Protocol:    6 (TCP)
```

| Campo | Pregunta que responde |
|---|---|
| Source Address | ¿Quién envía el paquete (extremo IP de origen)? |
| Destination Address | ¿A quién va dirigido finalmente? |
| TTL | ¿Cuántos routers más puede atravesar? |
| Protocol | ¿Qué protocolo transporta (ICMP, TCP, UDP)? |
| Total Length | ¿Cuánto mide el paquete completo (cabecera + datos), en bytes? |

## 6.2. Source y Destination

Permiten identificar los extremos IP de la comunicación.

En el alcance estudiado:

```text
Source Address
→ origen IP

Destination Address
→ destino IP final
```

Filtros útiles: `ip.src == 192.168.10.20`, `ip.dst == 203.0.113.80` o `ip.addr == …` (cualquiera de los dos).

## 6.3. TTL

**TTL (Time To Live)** impide que un paquete pueda circular indefinidamente.

Cada router lo reduce en 1.

Cuando alcanza cero, el router descarta el paquete y normalmente envía al origen un mensaje ICMP **Time Exceeded**.

Valores iniciales habituales (pueden cambiarse):

| Sistema | TTL inicial típico |
|---|---:|
| Linux, macOS, Android | 64 |
| Windows | 128 |
| Muchos equipos de red (routers Cisco) | 255 |

Pero:

```text
TTL observado = 57
```

no permite afirmar automáticamente:

```text
el paquete ha atravesado exactamente 7 routers
```

si no conocemos el TTL inicial. Si sabemos que el emisor es un Linux (TTL 64), «unos 7 saltos» es una **inferencia razonable**, no un hecho observado.

**Relación con `tracert` (U01).** `tracert`/`traceroute` aprovecha el TTL: envía sondas con TTL = 1, 2, 3… y cada router que pone el TTL a 0 responde con ICMP Time Exceeded, revelando su dirección. Windows (`tracert`) usa sondas ICMP Echo; Linux (`traceroute`) usa por defecto UDP. Por eso un router que no responde a esos mensajes aparece como `*`.

## 6.4. Protocol

El campo `Protocol` identifica qué protocolo superior transporta IPv4.

Valores frecuentes:

| Valor | Protocolo |
|---:|---|
| 1 | ICMP |
| 6 | TCP |
| 17 | UDP |

Es el equivalente, en la capa de red, del EtherType en la capa de enlace (apartado 3.2).

## 6.5. IP y puerto responden a preguntas distintas

La capa de transporte permite que muchos procesos utilicen la red simultáneamente.

```text
IP
→ ¿qué extremo lógico?

puerto
→ ¿qué proceso o servicio?
```

Ejemplo:

```text
203.0.113.80:443
```

La dirección IP identifica el extremo IP.

El puerto ayuda a identificar el servicio de transporte.

La combinación **IP + puerto** se llama *socket*. Una conexión concreta queda identificada por cinco datos (*5-tuple*): protocolo, IP origen, puerto origen, IP destino y puerto destino.

Puertos que debes reconocer:

| Servicio | Transporte | Puerto |
|---|---|---:|
| HTTP | TCP | 80 |
| HTTPS | TCP (y UDP con HTTP/3) | 443 |
| SSH | TCP | 22 |
| Telnet | TCP | 23 |
| DNS | UDP (y TCP) | 53 |
| DHCP | UDP | 67 servidor / 68 cliente |
| TFTP | UDP | 69 |

## 6.6. Puerto origen y destino

Los servidores suelen escuchar en puertos conocidos.

Los clientes suelen utilizar puertos temporales o **efímeros**.

| Rango (IANA) | Nombre | Uso |
|---|---|---|
| 0–1023 | Puertos bien conocidos (*well-known*) | Servicios estándar (22, 53, 80, 443…) |
| 1024–49151 | Registrados (*registered*) | Aplicaciones concretas |
| 49152–65535 | Dinámicos o efímeros (*dynamic / ephemeral*) | Puerto origen temporal del cliente |

El rango efímero real depende del sistema operativo (por ejemplo, muchos Linux usan 32768–60999), así que no te sorprendas si ves puertos de cliente fuera de 49152–65535.

Ejemplo:

```text
cliente 53124
→ servidor 443
```

Otra conexión puede utilizar:

```text
cliente 53125
→ servidor 443
```

Esto permite distinguir comunicaciones simultáneas.

En la respuesta, los puertos aparecen **invertidos**: origen 443 → destino 53124.

## 6.7. TCP

TCP proporciona un servicio orientado a conexión con mecanismos de fiabilidad.

En U02 debemos comprender conceptualmente:

- establecimiento;
- números de secuencia;
- ACK;
- retransmisiones;
- entrega ordenada;
- control de flujo.

No se estudian todavía algoritmos avanzados, ventanas o control de congestión en profundidad.

En Wireshark, los números de secuencia aparecen como **relativos** (empiezan en 0) para facilitar la lectura; el valor real (*raw*) es un número grande elegido al azar.

## 6.8. Three-way handshake

Establecimiento inicial:

```text
Cliente                     Servidor

SYN ------------------------>
                 <----------- SYN, ACK
ACK ------------------------>
```

Después puede comenzar el intercambio de aplicación.

En una captura:

```text
SYN
SYN, ACK
ACK
```

es evidencia de que se completó el establecimiento inicial de TCP **en el tráfico observado**.

No demuestra que la aplicación haya funcionado después.

Filtro útil para ver solo los inicios de conexión: `tcp.flags.syn == 1`.

## 6.9. Flags básicos

Conviene reconocer:

| Flag | Función inicial |
|---|---|
| SYN | Participa en el establecimiento |
| ACK | Confirma información |
| FIN | Participa en cierre ordenado |
| RST | Rechaza o aborta una comunicación |

Un `SYN` respondido con `RST, ACK` suele indicar que el equipo destino está accesible pero **no hay ningún servicio escuchando** en ese puerto: es una evidencia distinta de «no hay respuesta».

## 6.10. UDP

UDP también utiliza puertos, pero no realiza un establecimiento equivalente al three-way handshake.

Su cabecera es más simple: puerto origen, puerto destino, longitud y suma de comprobación.

Conceptualmente ofrece:

- menor sobrecarga;
- entrega de datagramas;
- sin confirmaciones/retransmisiones propias equivalentes a TCP.

Si una aplicación sobre UDP necesita fiabilidad, la implementa ella misma (por ejemplo, DNS vuelve a preguntar si no recibe respuesta).

No debemos memorizar:

```text
TCP = bueno
UDP = malo
```

ni:

```text
TCP = lento
UDP = rápido
```

Cada aplicación elige el servicio que necesita.

## 6.11. Comparación funcional

| Característica | TCP | UDP |
|---|---|---|
| Puertos | Sí | Sí |
| Establecimiento previo | Sí | No equivalente |
| ACK propios | Sí | No como mecanismo general |
| Retransmisión propia | Sí | No como función general |
| Entrega ordenada | Sí | No como propiedad general |
| Sobrecarga | Mayor | Menor |
| PDU | Segmento | Datagrama |
| Ejemplos | HTTP(S), SSH | DNS, DHCP, TFTP, voz y vídeo en tiempo real |

# 7. DNS, DHCP y tráfico cifrado

DNS y DHCP aparecen aquí porque permiten observar varias capas trabajando juntas: son protocolos de aplicación que viajan sobre UDP, dentro de IPv4, dentro de Ethernet. Además, cada uno deja **evidencias diferentes**: resolver un nombre, obtener una configuración o abrir una conexión cifrada no demuestran lo mismo. Este apartado enseña a reconocer esas evidencias y sus límites. Su administración detallada se desarrolla posteriormente.

| Concepto | Pregunta que responde | Ejemplo en captura |
|---|---|---|
| **Consulta / respuesta DNS** (*DNS query / response*) | ¿Se ha resuelto un nombre y con qué resultado? | `Standard query A www.example.test` |
| **Registro DNS** (*resource record*) | ¿Qué tipo de información se pide? | A, AAAA, CNAME, MX |
| **DHCP (DORA)** | ¿Cómo obtiene un equipo su configuración IP? | Discover, Offer, Request, ACK |
| **Difusión inicial** (*initial broadcast*) | ¿Cómo pregunta un equipo que aún no tiene IP? | `0.0.0.0` → `255.255.255.255` |
| **Tráfico cifrado** (*encrypted traffic*: TLS, HTTPS) | ¿Qué se ve y qué no en una conexión protegida? | `Client Hello`, `Application Data` |
| **DNS cifrado** (*DoH / DoT*) | ¿Por qué a veces no aparecen consultas DNS? | Resolución dentro de HTTPS |

No debemos mezclar **resolver un nombre**, **tener conectividad IP** y **recibir el servicio**: son tres comprobaciones distintas.

## 7.1. DNS

DNS permite obtener información asociada a nombres.

Ejemplo:

```text
www.example.test
→ consulta DNS
→ respuesta DNS
→ 203.0.113.80
```

Después puede comenzar una comunicación distinta hacia la dirección obtenida.

En la captura, DNS usa normalmente **UDP puerto 53** (destino 53 en la consulta, origen 53 en la respuesta). Consulta y respuesta llevan el mismo **identificador de transacción** (*Transaction ID*), lo que permite emparejarlas. Wireshark lo resume así:

```text
Standard query 0x1a2b A www.example.test
Standard query response 0x1a2b A www.example.test A 203.0.113.80
```

La herramienta `nslookup` que usaste en U01 genera exactamente este tipo de tráfico.

## 7.2. Resolver no es alcanzar ni prestar servicio

Debemos separar:

```text
resolución de nombre
≠
conectividad IP
≠
servicio final
```

Ejemplos:

- DNS puede responder y la web estar caída;
- `ping` puede responder y HTTPS estar bloqueado;
- HTTPS puede funcionar aunque ICMP esté filtrado.

## 7.3. Registros básicos

Conviene reconocer:

| Tipo | Función inicial |
|---|---|
| A | Dirección IPv4 |
| AAAA | Dirección IPv6 |
| CNAME | Alias |
| MX | Servidor de correo |

No es necesario memorizar todos los tipos existentes.

Es habitual que un equipo pregunte a la vez por A y por AAAA del mismo nombre: verás dos consultas seguidas.

## 7.4. DNS y transporte

Muchas consultas DNS utilizan UDP.

Pero DNS también puede utilizar TCP (por ejemplo, con respuestas grandes o transferencias entre servidores).

No memorices:

```text
DNS = siempre UDP
```

La captura nos permite observar qué transporte se está utilizando realmente.

## 7.5. Por qué a veces no aparece DNS en la captura

Que el filtro `dns` no muestre nada **no demuestra** que no haya habido resolución:

| Causa | Qué ocurre | Cómo comprobarlo |
|---|---|---|
| **Caché DNS** (*DNS cache*) | El equipo ya conocía la respuesta y no pregunta | `ipconfig /displaydns`; vaciarla con `ipconfig /flushdns` antes de la prueba |
| **DNS cifrado** (*DNS over HTTPS / DNS over TLS*) | El navegador o el sistema resuelve dentro de una conexión cifrada (TCP 443 o TCP 853) | Revisar la configuración del navegador o del sistema |
| **Interfaz o punto de captura equivocado** | La consulta sale por otra interfaz | Revisar el apartado 4 |

## 7.6. DHCP

DHCP permite obtener parámetros de red automáticamente.

Una adquisición inicial típica sigue:

```text
Discover
→ Offer
→ Request
→ Acknowledgment
```

Se conoce habitualmente como **DORA**.

| Mensaje | Quién lo envía | Para qué |
|---|---|---|
| **Discover** | Cliente | «¿Hay algún servidor DHCP?» |
| **Offer** | Servidor | Ofrece una dirección y parámetros |
| **Request** | Cliente | Pide formalmente la oferta elegida |
| **ACK** (*Acknowledgment*) | Servidor | Confirma la concesión |

DHCP puede proporcionar:

- dirección IP;
- máscara/prefijo;
- gateway;
- DNS;
- tiempo de concesión;
- otros parámetros.

DHCP usa **UDP**: puerto **67** en el servidor y **68** en el cliente. Filtro de visualización: `dhcp`.

Una **renovación** de una concesión existente suele verse solo como Request → ACK. Para observar DORA completo en un equipo de laboratorio Windows se usa `ipconfig /release` seguido de `ipconfig /renew` (en Linux depende del gestor de red que use el sistema).

El diseño del direccionamiento y la configuración de un servidor DHCP se estudian en U04; el router como servidor y agente de retransmisión (*relay*), en U08; la protección *DHCP snooping*, en U06.

## 7.7. Broadcast inicial

Un cliente que todavía no dispone de toda su configuración puede necesitar enviar determinados mensajes de forma que puedan ser recibidos dentro del dominio local.

En una captura típica del Discover:

```text
Ethernet: origen MAC del cliente → destino ff:ff:ff:ff:ff:ff
IPv4:     origen 0.0.0.0        → destino 255.255.255.255
UDP:      puerto 68             → puerto 67
```

El cliente usa `0.0.0.0` porque aún no tiene dirección, y envía a todos porque aún no sabe dónde está el servidor. Como los routers no reenvían broadcast, el servidor DHCP debe estar en la misma red o debe existir un **relay** (U08).

Esto prepara contenidos posteriores sobre relays y routing, pero no se configuran todavía.

## 7.8. Tráfico cifrado

HTTPS protege contenido de aplicación mediante **TLS** (*Transport Layer Security*).

Eso no significa:

```text
tráfico cifrado
=
tráfico invisible
```

Todavía pueden ser observables, según el caso:

- direcciones IP;
- puertos;
- tamaños;
- tiempos;
- handshake TCP;
- parte de la negociación criptográfica.

Pero normalmente no podremos leer directamente:

- contraseñas;
- formularios;
- cuerpo de la página;
- cabeceras HTTP protegidas.

En una captura de HTTPS verás, después del handshake TCP, mensajes TLS como `Client Hello` y `Server Hello` y, a continuación, `Application Data` (contenido cifrado). En el `Client Hello` suele aparecer en claro el **nombre del servidor** solicitado (campo **SNI**, *Server Name Indication*), aunque algunas tecnologías recientes intentan ocultarlo. Filtro: `tls`.

Dos precauciones modernas:

- muchos navegadores usan **HTTP/3 sobre QUIC**, que viaja por **UDP 443**: si filtras `tcp.port == 443` puedes no ver nada aunque la web funcione (prueba `quic` o `udp.port == 443`);
- el **DNS cifrado** (apartado 7.5) oculta también las consultas de nombres.

## 7.9. Qué demuestra cada evidencia

| Evidencia observada | Qué permite afirmar | Qué NO permite afirmar |
|---|---|---|
| DNS query + response con una dirección | El nombre se resolvió en ese momento, desde ese punto | Que el servidor esté accesible o que la web funcione |
| DHCP Discover, Offer, Request, ACK | El cliente recibió una concesión de un servidor DHCP | Que el gateway o el DNS recibidos sean correctos o funcionen |
| SYN, SYN/ACK, ACK hacia el puerto 443 | Se estableció la conexión TCP con el servidor | Que la página se cargara correctamente |
| TLS Client Hello + Server Hello + Application Data | Se negoció una sesión cifrada y se intercambiaron datos | Qué contenido se intercambió o si fue el esperado |

# 8. La vida de un paquete: integrar las capas

Hasta ahora hemos estudiado cada capa y cada protocolo por separado. En la realidad todos actúan juntos y en un orden concreto. Este apartado reconstruye paso a paso lo que ocurre cuando un usuario abre una web en un servidor remoto, relacionando cada paso con la capa que actúa y con lo que se vería en una captura hecha en el cliente.

| Paso | Capa principal | Protocolo | Evidencia en la captura del cliente |
|---|---|---|---|
| Resolver el nombre | Aplicación | DNS | Query y response |
| Decidir local o remoto | Red | IPv4 (máscara) | No se ve: es una decisión interna del host |
| Averiguar la MAC del gateway | Enlace/Red | ARP | Request y reply (si no estaba en caché) |
| Establecer la conexión | Transporte | TCP | SYN, SYN/ACK, ACK |
| Negociar el cifrado e intercambiar datos | Aplicación | TLS / HTTPS | Client Hello, Server Hello, Application Data |
| Atravesar el router | Red + Enlace | IPv4 + Ethernet | Desde el cliente no se ve; sí el TTL de las respuestas |

Un mismo «clic» del usuario genera, por tanto, **varias comunicaciones distintas**; algunas pueden no aparecer en la captura (caché ARP, caché DNS) sin que eso signifique que haya un fallo.

Escenario:

```text
PC-A
→ SW1
→ R1
→ red remota
→ servidor web
```

El usuario introduce:

```text
https://www.example.test
```

Vamos a reconstruir el proceso sin introducir todavía subnetting o routing avanzado.

## 8.1. Resolución del nombre

```text
nombre
→ DNS
→ IP del servidor
```

La resolución es una comunicación propia.

No forma parte «mágicamente» de HTTPS.

Si el servidor DNS también está en otra red, para enviarle la consulta PC-A ya necesita la MAC del gateway: por eso en muchas capturas el **ARP del gateway aparece antes que la consulta DNS**.

## 8.2. Local o remoto

El host determina si el destino se encuentra en su red local o debe utilizar gateway.

El cálculo formal se estudiará en U04.

En este caso el destino es remoto.

## 8.3. Resolver la MAC del gateway

Si no existe entrada válida:

```text
ARP
→ IP gateway
→ MAC gateway
```

## 8.4. Construir la comunicación

Conceptualmente:

```text
HTTPS
↓
TCP
↓
IPv4
↓
Ethernet
↓
señal
```

Primera trama:

```text
MAC origen  → PC-A
MAC destino → gateway
```

Paquete:

```text
IP origen  → PC-A
IP destino → servidor
```

## 8.5. Router

R1:

1. recibe trama;
2. procesa paquete IPv4;
3. reduce TTL;
4. selecciona cómo continuar;
5. crea una nueva trama para el siguiente enlace.

En el alcance estudiado sin NAT:

```text
información L2
→ cambia por enlace

IP de extremos
→ mantiene la comunicación origen-destino
```

(Ver la tabla «qué cambia y qué permanece» del apartado 5.6.)

## 8.6. Transporte

Si el servicio utiliza TCP:

```text
SYN
→ SYN/ACK
→ ACK
```

Después puede comenzar la comunicación de aplicación: en HTTPS, primero la negociación TLS y después los datos cifrados.

## 8.7. Retorno

Una comunicación necesita camino de ida y vuelta.

```text
el paquete salió
≠
la respuesta puede volver
```

Esta idea será esencial en routing y troubleshooting posteriores.

## 8.8. Secuencia esperada en la captura del cliente

Filtro de visualización: `arp || dns || tcp.port == 443 || tls`. Una secuencia típica (simplificada, con cachés vacías) sería:

| Orden | Protocolo | Info (resumen) | Capa / función |
|---:|---|---|---|
| 1 | ARP | Who has 192.168.10.1? (gateway) | Enlace: MAC del siguiente salto |
| 2 | ARP | 192.168.10.1 is at … | Enlace |
| 3 | DNS | Standard query A www.example.test | Aplicación: resolución |
| 4 | DNS | Standard query response … A 203.0.113.80 | Aplicación |
| 5 | TCP | 53124 → 443 [SYN] | Transporte: establecimiento |
| 6 | TCP | 443 → 53124 [SYN, ACK] | Transporte |
| 7 | TCP | 53124 → 443 [ACK] | Transporte |
| 8 | TLS | Client Hello (SNI = www.example.test) | Aplicación: negociación cifrada |
| 9 | TLS | Server Hello, … | Aplicación |
| 10 | TLS | Application Data | Aplicación: contenido cifrado |

En todos los paquetes enviados por PC-A a Internet, la **MAC destino es la del gateway** y la **IP destino es la del servidor** (o la del servidor DNS). Esta tabla es un modelo: en una captura real el orden puede variar, pueden faltar pasos (cachés) o aparecer otros (consultas AAAA, QUIC, tráfico de otras aplicaciones).

# 9. Análisis integrado y elaboración de evidencias

Una captura no habla sola: hay que convertirla en afirmaciones que otro técnico pueda comprobar. El riesgo más habitual no es desconocer un protocolo, sino **concluir más de lo que la evidencia permite** («no hay SYN/ACK, luego el servidor está apagado»). Este apartado propone un método reproducible y un vocabulario para separar lo que se ve de lo que se deduce.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Evidencia / hecho** (*evidence / fact*) | ¿Qué se observa directamente? | «El paquete 12 es una respuesta DNS con 203.0.113.80» |
| **Inferencia** (*inference*) | ¿Qué deduzco razonablemente de lo observado? | «El nombre se resolvió» |
| **Hipótesis** (*hypothesis*) | ¿Qué explicación posible aún no está demostrada? | «El servicio HTTPS puede no estar escuchando» |
| **Conclusión** (*conclusion*) | ¿Qué afirmo con suficiente evidencia y con qué límites? | «Desde el cliente, la resolución funciona; la conexión TCP no se completa» |
| **Limitación** (*limitation*) | ¿Qué no puedo saber con esta captura? | «No se capturó en el servidor» |
| **Reproducibilidad** (*reproducibility*) | ¿Podría otro técnico repetir y comprobar mi análisis? | Archivo, filtro y números de paquete |

La diferencia entre un buen y un mal análisis suele estar en la **conclusión**: debe decir lo que la captura demuestra y también lo que no demuestra.

Analizar tráfico no consiste en abrir paquetes al azar.

Conviene seguir un procedimiento reproducible.

## 9.1. Método básico

```text
1. definir la pregunta
2. registrar el punto de captura
3. identificar los extremos
4. aislar el tráfico relevante
5. identificar protocolos
6. seguir la secuencia
7. relacionar capas e identificadores
8. registrar hechos
9. formular inferencias
10. formular hipótesis si es necesario
11. indicar limitaciones
12. proponer siguiente prueba
13. escribir conclusión limitada
```

## 9.2. Evidencia

Dato directamente observable.

Ejemplo:

```text
Se observa una respuesta DNS con 203.0.113.80.
```

## 9.3. Inferencia

Interpretación razonable derivada de evidencia.

```text
La consulta del nombre ha recibido una respuesta DNS.
```

## 9.4. Hipótesis

Posible explicación todavía no demostrada.

```text
El servicio HTTPS puede no estar escuchando.
```

## 9.5. Conclusión

Afirmación respaldada por suficiente evidencia.

Debe incluir límites cuando sean relevantes.

## 9.6. Lenguaje técnico prudente

La forma de redactar muestra si distingues hecho, inferencia e hipótesis:

| Para… | Expresiones útiles |
|---|---|
| Describir un hecho | «La captura muestra…», «En el paquete N se observa…», «No se observa… en esta captura» |
| Formular una inferencia | «Esto indica…», «Esto es compatible con…» |
| Plantear una hipótesis | «Una posible explicación es…», «Podría deberse a…» |
| Señalar un límite | «Esta captura no permite demostrar…», «Desde este punto de captura no se puede saber…» |

Evita expresiones absolutas («seguro que», «la red está bien», «el servidor está caído») si la evidencia no las sostiene.

## 9.7. Ejemplo TCP

Pregunta:

> ¿Se completa el establecimiento TCP?

Captura:

```text
SYN
SYN
SYN
```

Hecho:

```text
Se observan SYN del cliente.
No se observa SYN/ACK en esta captura.
```

Hipótesis compatibles:

- servicio no disponible;
- filtro/firewall;
- destino incorrecto;
- problema de retorno;
- captura incompleta;
- tráfico no visible desde ese punto.

Conclusión no justificada:

```text
«El servidor está apagado.»
```

Conclusión prudente:

```text
Desde el cliente, la conexión TCP al puerto 443 no se completa: se observan
tres SYN sin respuesta. Esta captura no permite saber si los SYN llegaron
al servidor. Siguiente prueba: capturar en el servidor o probar desde otro
equipo de la misma red que el servidor.
```

Los SYN repetidos son **retransmisiones**: TCP vuelve a intentarlo porque no recibe respuesta.

## 9.8. Ejemplo DNS

Pregunta:

> ¿El cliente obtiene respuesta DNS?

Si observamos:

```text
DNS Query
DNS Response
```

podemos afirmar que hay evidencia de consulta y respuesta en ese punto.

No podemos afirmar por ello:

```text
la web funciona
```

## 9.9. Reproducibilidad

Un análisis es reproducible cuando otra persona, con tu archivo y tus notas, puede llegar a las mismas observaciones. Para ello:

- guarda la captura (`.pcapng`) con un nombre descriptivo;
- anota el contexto (apartado 4.8);
- indica el **filtro** exacto que usaste;
- cita los **números de paquete** (`No.`) que sirven de evidencia;
- separa en el informe hechos, inferencias e hipótesis.

## 9.10. Informe básico

Utiliza:

```text
Pregunta técnica:

Punto de captura:
Interfaz:
Acción realizada:
Filtro:

Paquetes/secuencia relevante:

Hechos:
1.
2.
3.

Inferencias:
1.
2.

Hipótesis pendientes:

Limitaciones:

Siguiente prueba:

Conclusión:
```

# 10. Seguridad, privacidad y uso responsable de las capturas

Un analizador de tráfico es una herramienta profesional muy potente, y precisamente por eso exige responsabilidad: una captura puede contener información personal o credenciales, y capturar tráfico ajeno sin autorización puede ser ilegal. Además, hoy es habitual pedir ayuda a asistentes de IA para interpretar capturas; pueden ser útiles, pero **no ven tu red** y no son una fuente de evidencia.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Datos sensibles** (*sensitive data*) | ¿Qué información delicada puede haber en una captura? | Consultas DNS, cookies, credenciales |
| **Autorización** (*authorization*) | ¿Dónde y cuándo puedo capturar? | Solo en redes y equipos de laboratorio autorizados |
| **Anonimización** (*anonymization*) | ¿Cómo comparto una captura sin exponer datos? | Sustituir direcciones y nombres reales |
| **IA como apoyo** (*AI assistant*) | ¿Para qué sirve y para qué no? | Explica un campo, pero no aporta evidencia |

No debemos confundir **poder capturar** (la herramienta lo permite) con **estar autorizado a capturar**.

## 10.1. Qué puede contener una captura

Una captura puede contener:

- direcciones;
- nombres de host;
- consultas DNS;
- identificadores;
- contenido sin cifrar;
- cookies;
- credenciales en protocolos inseguros;
- información personal.

Por ello:

1. solo se captura en entornos autorizados;
2. se limita duración y alcance;
3. se evita tráfico real innecesario;
4. se anonimizan datos cuando proceda;
5. se almacenan los archivos de forma segura;
6. no se comparten capturas con servicios externos sin autorización.

## 10.2. IA como apoyo

Un asistente de IA puede ayudar a:

- explicar un campo;
- recordar una sintaxis de filtro;
- resumir una secuencia;
- proponer hipótesis;
- mejorar un informe.

Pero:

```text
IA
≠
fuente de evidencia de la red
```

Una respuesta debe contrastarse con:

```text
captura
+
prueba
+
documentación
```

Nunca debe «inventarse» tráfico que no aparece.

Ejemplo de revisión crítica:

| La IA dice… | Contraste con la evidencia |
|---|---|
| «Como no hay SYN/ACK, el servidor está apagado.» | La captura solo muestra SYN sin respuesta desde el cliente. Es una hipótesis entre varias (firewall, retorno, servicio parado…), no una conclusión. |
| «El filtro `ip.addr = 192.168.10.20` muestra el tráfico del equipo.» | La sintaxis correcta es `ip.addr == 192.168.10.20` (la barra se pone roja con `=`). |
| «En el paquete 15 se ve la contraseña del usuario.» | Comprobar el paquete 15: si es tráfico TLS (`Application Data`), el contenido está cifrado y esa afirmación es falsa. |

# 12. Términos profesionales que debes reconocer

Wireshark, la documentación de fabricantes, los RFC y las herramientas profesionales están en inglés. No necesitas traducirlos: necesitas **reconocerlos y saber qué significan**. La tabla reúne los términos de la unidad en el orden en que aparecen.

| Término | Significado inicial |
|---|---|
| **layer** | capa: grupo de funciones relacionadas |
| **protocol** | conjunto de reglas entre entidades pares |
| **protocol stack / suite** | pila o familia de protocolos que trabajan juntos |
| **service** | función que una capa ofrece a la superior |
| **layer interface** | forma en que una capa usa a otra en el mismo equipo |
| **encapsulation** | añadir información de control al bajar por la pila |
| **decapsulation** | retirar esa información al subir por la pila |
| **PDU** | unidad de datos de una capa |
| **header** | cabecera: control al inicio de la PDU |
| **payload** | carga útil: lo transportado |
| **trailer** | tráiler: control al final (p. ej., FCS) |
| **overhead** | sobrecarga que añaden las cabeceras |
| **segment** | PDU de TCP |
| **datagram** | PDU de UDP |
| **packet** | PDU de la capa de red |
| **frame** | PDU de la capa de enlace |
| **source** | origen |
| **destination** | destino |
| **MAC address** | dirección de la interfaz en el enlace local |
| **OUI** | parte de la MAC que identifica al fabricante |
| **broadcast** | envío a todos los equipos del enlace |
| **EtherType** | campo que indica qué protocolo lleva la trama |
| **FCS** | secuencia de comprobación de la trama |
| **ARP** | resolución de IPv4 a MAC en el enlace local |
| **ARP cache** | tabla temporal de asociaciones IP–MAC |
| **TTL** | tiempo de vida: saltos restantes de un paquete |
| **ICMP** | mensajes de control y diagnóstico de IP |
| **Echo Request / Echo Reply** | mensajes ICMP de `ping` |
| **Time Exceeded** | mensaje ICMP cuando el TTL llega a 0 |
| **port** | identificador de proceso o servicio de transporte |
| **ephemeral port** | puerto temporal del cliente |
| **socket** | combinación de IP y puerto |
| **SYN / ACK / FIN / RST** | flags básicos de TCP |
| **three-way handshake** | establecimiento de conexión TCP |
| **retransmission** | reenvío de datos no confirmados |
| **DNS query / DNS response** | consulta y respuesta de resolución de nombres |
| **DNS cache** | respuestas DNS guardadas temporalmente |
| **DHCP Discover / Offer / Request / Acknowledgment** | mensajes DORA |
| **lease** | concesión DHCP |
| **TLS** | protocolo de cifrado usado por HTTPS |
| **SNI** | nombre del servidor visible en el Client Hello |
| **display filter** | filtro de visualización |
| **capture filter** | filtro de captura |
| **capture point** | punto de captura |
| **packet list / packet details / packet bytes** | paneles de Wireshark |
| **dissector** | analizador de Wireshark que interpreta un protocolo |
| **evidence** | evidencia observable |
| **inference** | inferencia |
| **hypothesis** | hipótesis |
| **conclusion** | conclusión |

Estos términos aparecen de manera natural en Wireshark, documentación, RFC, Cisco, sistemas operativos y herramientas profesionales.

# 13. Qué se estudiará después

U02 completa RA1 junto con U01, pero no pretende configurar todo lo que aparece en una captura. Casi todo lo que has visto como tráfico observable volverá más adelante como algo que tendrás que **configurar, administrar y verificar**. La tabla muestra dónde.

| Unidad | Qué se estudiará | Qué de U02 reutiliza |
|---|---|---|
| U03 | Medios, cableado, interfaces físicas, Wi‑Fi y conectividad | Capa física, FCS y errores de enlace |
| U04 | IPv4, subnetting, VLSM, CIDR y DHCP | Decisión local/remoto, campos IPv4, DORA |
| U05 | IPv6 y autoconfiguración (SLAAC, NDP, DHCPv6) | EtherType `0x86DD`, NDP como sustituto de ARP |
| U06 | Switching y tabla MAC, STP, EtherChannel y seguridad L2 | Tramas, MAC, broadcast, ARP, DHCP snooping |
| U07 | VLAN y trunks (802.1Q), inter-VLAN | Trama Ethernet (se le añade una etiqueta) |
| U08 | Routing estático, router DHCP y relay, ACL y SSH | Qué cambia en un router, TTL, protocolos y puertos en las ACL |
| U09 | Routing dinámico (RIP, OSPF) | Paquetes IP entre routers, multicast |
| U10 | WAN, Internet y NAT/PAT | IP y puertos que NAT modifica |

La administración de servicios como DNS o servidores web pertenece a otros módulos del ciclo; aquí solo los observamos.

La frontera profesional puede resumirse así:

```text
U01
reconocer la red

        ↓

U02
observar cómo se comunica

        ↓

resto del módulo
configurar, administrar, verificar y diagnosticar
```

Y la regla que se conservará durante todo el curso será:

```text
configuración esperada
≠
estado observado
≠
servicio demostrado
```

junto con:

```text
observar
→ interpretar
→ comprobar
→ cambiar
→ verificar
```

U02 no pretende que «sepas usar Wireshark» como una lista de botones y filtros.

Pretende que empieces a **pensar con evidencias de red**.
