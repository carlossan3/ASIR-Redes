# U02 — Capas, encapsulación y análisis de tráfico

> **Pregunta guía:** ¿Cómo se transforma la información desde que una aplicación la genera hasta que llega al destino y qué podemos demostrar observando el tráfico?

En U01 construimos el primer mapa de una red: dispositivos, interfaces, medios, servicios, topologías, identificadores y recorrido local/remoto.

U02 responde a la siguiente pregunta:

> **Ya sé qué elementos forman una red. ¿Qué ocurre realmente cuando esos elementos se comunican?**

El objetivo de esta unidad no es memorizar todas las cabeceras ni todas las siglas. El objetivo es aprender a seguir una comunicación por capas y relacionar esa explicación con **evidencias reales o simuladas**.

El procedimiento general será:

```text
función
→ capa
→ protocolo
→ PDU
→ campo observable
→ secuencia
→ evidencia
→ interpretación
→ límite de la conclusión
```

Al finalizar U02 deberías poder mirar una captura pequeña y responder:

```text
¿Qué pregunta intento responder?
¿Qué protocolo estoy observando?
¿Qué capa cumple esa función?
¿Qué direcciones y puertos aparecen?
¿Qué ocurrió primero?
¿Qué ocurrió después?
¿Qué puedo afirmar como hecho?
¿Qué estoy infiriendo?
¿Qué todavía necesito comprobar?
```

La configuración detallada de IPv4, DHCP, switching, routing y servicios se desarrolla en unidades posteriores. En U02 esos protocolos se estudian **como mecanismos observables**, no como bloques de administración.

# 1. Capas, servicios, protocolos y encapsulación

## 1.1. ¿Por qué se utilizan capas?

Una comunicación de red debe resolver problemas diferentes:

- una aplicación genera o consume datos;
- los datos deben llegar al proceso correcto;
- los extremos deben identificarse;
- la información debe poder atravesar una o varias redes;
- cada enlace debe entregar información al siguiente dispositivo;
- el medio físico debe transportar señales.

Si intentáramos explicar todo como una sola función sería muy difícil:

- sustituir tecnologías;
- entender responsabilidades;
- localizar fallos;
- interpretar una captura.

Los modelos por capas permiten separar funciones relacionadas.

```text
capa
=
grupo de funciones relacionadas
```

Las capas no son dispositivos físicos.

Un mismo equipo puede participar simultáneamente en funciones de todas las capas.

## 1.2. Modelo TCP/IP de cinco capas

En este módulo utilizaremos principalmente:

| Capa | Pregunta principal | Ejemplos |
|---:|---|---|
| **5. Aplicación** | ¿Qué servicio utiliza la aplicación? | HTTP(S), DNS, DHCP, SSH |
| **4. Transporte** | ¿Qué proceso debe recibir los datos? | TCP, UDP |
| **3. Red** | ¿Cómo se identifica y alcanza el destino entre redes? | IPv4, IPv6, ICMP |
| **2. Enlace** | ¿Cómo se entrega la información en un enlace concreto? | Ethernet, Wi‑Fi |
| **1. Física** | ¿Cómo viaja la señal por el medio? | cobre, fibra, radio |

Ejemplo conceptual:

```text
HTTPS
  ↓
TCP
  ↓
IPv4
  ↓
Ethernet
  ↓
señal
```

Cada capa utiliza servicios de la capa inferior y proporciona un servicio a la superior.

## 1.3. OSI como modelo de referencia

El modelo OSI organiza las funciones en siete capas:

| OSI | Función general |
|---:|---|
| 7. Aplicación | Servicios utilizados por aplicaciones |
| 6. Presentación | Representación y transformación de datos |
| 5. Sesión | Organización del diálogo |
| 4. Transporte | Comunicación entre procesos |
| 3. Red | Direccionamiento y comunicación entre redes |
| 2. Enlace de datos | Entrega dentro de un enlace |
| 1. Física | Transmisión de señales |

Relación aproximada:

| TCP/IP de cinco capas | OSI |
|---|---|
| Aplicación | Aplicación + Presentación + Sesión |
| Transporte | Transporte |
| Red | Red |
| Enlace | Enlace de datos |
| Física | Física |

Esta correspondencia no debe entenderse como una equivalencia matemática perfecta.

La regla útil es:

> **Primero comprende la función; después aprende la etiqueta.**

## 1.4. Servicio, protocolo e interfaz entre capas

No son sinónimos.

### Servicio

Una función que una capa ofrece a otra.

Ejemplo:

```text
TCP
→ proporciona a una aplicación un servicio de transporte fiable
```

### Protocolo

Conjunto de reglas utilizadas por entidades equivalentes.

Conceptualmente:

```text
TCP del cliente  ↔  TCP del servidor
IP del cliente   ↔  IP del servidor
```

### Interfaz entre capas

Forma en la que una capa utiliza los servicios de otra dentro del mismo sistema.

```text
Aplicación
   │ utiliza
   v
Transporte
   │ utiliza
   v
Red
   │ utiliza
   v
Enlace
```

Por tanto:

```text
servicio
≠
protocolo
≠
interfaz entre capas
```

## 1.5. Encapsulación

Cuando una aplicación genera datos, la información desciende por la pila.

Cada capa añade información de control necesaria para realizar su función.

Ejemplo con TCP e IPv4:

```text
Aplicación
[ datos ]
    ↓
Transporte
[ cabecera TCP | datos ]
    ↓
Red
[ cabecera IP | cabecera TCP | datos ]
    ↓
Enlace
[ cabecera Ethernet | paquete IP | tráiler ]
    ↓
Física
bits / señales
```

Este proceso se denomina **encapsulación**.

## 1.6. Desencapsulación

En el destino ocurre el proceso inverso.

```text
señal
  ↓
trama
  ↓
paquete
  ↓
segmento/datagrama
  ↓
datos de aplicación
```

Cada capa:

1. interpreta la información que le corresponde;
2. procesa su función;
3. entrega la carga útil a la capa superior.

## 1.7. PDU

Una **PDU** (*Protocol Data Unit*) es la unidad de información asociada a una capa.

| Capa | PDU habitual |
|---:|---|
| Aplicación | Datos / mensaje |
| Transporte con TCP | Segmento |
| Transporte con UDP | Datagrama |
| Red | Paquete |
| Enlace | Trama |
| Física | Bits / símbolos |

La terminología puede variar en documentación técnica. Lo importante es comprender la función.

## 1.8. Cabecera, carga útil y tráiler

Una PDU puede contener:

- **cabecera**: información de control al inicio;
- **carga útil** (*payload*): información transportada;
- **tráiler**: información de control al final, cuando el protocolo lo utiliza.

Ejemplo:

```text
Trama Ethernet
├── cabecera Ethernet
├── paquete IPv4
└── FCS
```

El paquete IPv4 es la carga útil de Ethernet.

A su vez:

```text
Paquete IPv4
├── cabecera IPv4
└── segmento TCP
```

El segmento TCP es la carga útil de IPv4.

Esto conduce a una idea fundamental:

> La PDU de una capa puede convertirse en la carga útil de la capa inferior.

# 2. Ethernet, MAC, ARP y destino local/remoto

Ethernet es una tecnología de enlace fundamental en LAN cableadas.

## 2.1. Trama Ethernet

En una trama interesa reconocer inicialmente:

```text
MAC destino
MAC origen
EtherType
carga útil
FCS
```

| Campo | Función |
|---|---|
| MAC destino | Identifica el destinatario en el enlace |
| MAC origen | Identifica al emisor de la trama |
| EtherType | Indica qué protocolo contiene la carga útil |
| Carga útil | Información transportada |
| FCS | Permite detectar determinados errores |

Valores EtherType frecuentes:

| Valor | Significado |
|---|---|
| `0x0800` | IPv4 |
| `0x0806` | ARP |
| `0x86DD` | IPv6 |

En algunas capturas el FCS no aparece porque la interfaz no lo entrega al sistema operativo.

## 2.2. Dirección MAC

Una MAC Ethernet suele representarse en hexadecimal:

```text
00:11:22:33:44:55
```

Su función está asociada al **enlace local**.

Un switch utiliza información MAC para reenviar tramas. El aprendizaje y funcionamiento detallado de la tabla MAC pertenece a U06.

## 2.3. Destino local

Escenario:

```text
PC-A
 │
SW1
 │
PC-B
```

Si PC-A considera a PC-B un destino local:

- mantiene como destino IP a PC-B;
- necesita información de enlace para poder entregarle la trama;
- la trama se dirige a la MAC correspondiente a PC-B.

## 2.4. Destino remoto

Escenario:

```text
PC-A
 │
SW1
 │
R1
 │
red remota
 │
Servidor
```

PC-A quiere llegar al servidor remoto.

La idea fundamental es:

```text
IP destino
→ servidor remoto

MAC destino de la primera trama
→ gateway local
```

El host no necesita conocer la MAC del servidor remoto.

Necesita conocer cómo llegar al **siguiente salto local**.

## 2.5. ARP

ARP permite resolver una relación entre IPv4 y MAC en el ámbito local.

Ejemplo:

```text
ARP Request:
¿Quién tiene 192.168.10.1?

        ↓

ARP Reply:
192.168.10.1 está en 00:11:22:33:44:55
```

El host puede almacenar temporalmente la asociación.

Windows:

```text
arp -a
```

Linux:

```text
ip neigh
```

ARP no se transporta dentro de IPv4.

Ethernet puede transportar directamente:

```text
ARP
o
IPv4
```

## 2.6. Qué ocurre al atravesar un router

Supongamos:

```text
PC-A
→ SW1
→ R1
→ SW2
→ SRV
```

El router:

1. recibe una trama válida para el enlace de entrada;
2. procesa el paquete IP contenido;
3. decide por dónde continuar;
4. construye una nueva trama para el enlace de salida.

En un recorrido normal sin NAT:

```text
direcciones MAC
→ cambian entre enlaces

direcciones IP de los extremos
→ permanecen asociadas a origen y destino final
```

El TTL sí cambia al atravesar routers, como veremos después.

# 3. IPv4 e ICMP como evidencia

La planificación IPv4, subnetting, VLSM y CIDR pertenecen a U04.

Aquí IPv4 se estudia como **información observable dentro de un paquete**.

## 3.1. Campos básicos de IPv4

En una captura interesa reconocer:

- Source Address;
- Destination Address;
- TTL;
- Protocol;
- Total Length.

No es necesario memorizar la cabecera completa.

Ejemplo:

```text
IPv4
├── Source:      192.168.10.20
├── Destination: 203.0.113.80
├── TTL:         64
└── Protocol:    6 (TCP)
```

## 3.2. Source y Destination

Permiten identificar los extremos IP de la comunicación.

En el alcance estudiado:

```text
Source Address
→ origen IP

Destination Address
→ destino IP final
```

## 3.3. TTL

**TTL (Time To Live)** impide que un paquete pueda circular indefinidamente.

Cada router lo reduce.

Cuando alcanza cero, el paquete no continúa.

Pero:

```text
TTL observado = 57
```

no permite afirmar automáticamente:

```text
el paquete ha atravesado exactamente 7 routers
```

si no conocemos el TTL inicial.

## 3.4. Protocol

El campo `Protocol` identifica qué protocolo superior transporta IPv4.

Valores frecuentes:

| Valor | Protocolo |
|---:|---|
| 1 | ICMP |
| 6 | TCP |
| 17 | UDP |

## 3.5. ICMP

ICMP transporta mensajes de control y diagnóstico.

Ejemplos:

- Echo Request;
- Echo Reply;
- Destination Unreachable;
- Time Exceeded.

`ping` utiliza ICMP Echo.

## 3.6. Qué demuestra un ping

Si observamos:

```text
Echo Request
→ Echo Reply
```

podemos afirmar que una comunicación ICMP concreta ha tenido respuesta.

No podemos afirmar automáticamente:

- que DNS funciona;
- que HTTPS funciona;
- que el puerto 443 está accesible;
- que la aplicación funciona;
- que no existen pérdidas en otros momentos;
- que todos los caminos de la red están bien.

Principio general:

> **Una prueba solo demuestra aquello que realmente comprueba.**

# 4. TCP, UDP y puertos

La capa de transporte permite que muchos procesos utilicen la red simultáneamente.

## 4.1. IP y puerto responden a preguntas distintas

```text
IP
→ ¿qué extremo lógico?

puerto
→ ¿qué proceso o servicio?
```

Ejemplo:

```text
203.0.113.80:443
```

La dirección IP identifica el extremo IP.

El puerto ayuda a identificar el servicio de transporte.

## 4.2. Puerto origen y destino

Los servidores suelen escuchar en puertos conocidos.

Los clientes suelen utilizar puertos temporales o **efímeros**.

Ejemplo:

```text
cliente 53124
→ servidor 443
```

Otra conexión puede utilizar:

```text
cliente 53125
→ servidor 443
```

Esto permite distinguir comunicaciones simultáneas.

## 4.3. TCP

TCP proporciona un servicio orientado a conexión con mecanismos de fiabilidad.

En U02 debemos comprender conceptualmente:

- establecimiento;
- números de secuencia;
- ACK;
- retransmisiones;
- entrega ordenada;
- control de flujo.

No se estudian todavía algoritmos avanzados, ventanas o control de congestión en profundidad.

## 4.4. Three-way handshake

Establecimiento inicial:

```text
Cliente                     Servidor

SYN ------------------------>
                 <----------- SYN, ACK
ACK ------------------------>
```

Después puede comenzar el intercambio de aplicación.

En una captura:

```text
SYN
SYN, ACK
ACK
```

es evidencia de que se completó el establecimiento inicial de TCP **en el tráfico observado**.

No demuestra que la aplicación haya funcionado después.

## 4.5. Flags básicos

Conviene reconocer:

| Flag | Función inicial |
|---|---|
| SYN | Participa en el establecimiento |
| ACK | Confirma información |
| FIN | Participa en cierre ordenado |
| RST | Rechaza o aborta una comunicación |

## 4.6. UDP

UDP también utiliza puertos, pero no realiza un establecimiento equivalente al three-way handshake.

Su cabecera es más simple.

Conceptualmente ofrece:

- menor sobrecarga;
- entrega de datagramas;
- sin confirmaciones/retransmisiones propias equivalentes a TCP.

No debemos memorizar:

```text
TCP = bueno
UDP = malo
```

ni:

```text
TCP = lento
UDP = rápido
```

Cada aplicación elige el servicio que necesita.

## 4.7. Comparación funcional

| Característica | TCP | UDP |
|---|---|---|
| Puertos | Sí | Sí |
| Establecimiento previo | Sí | No equivalente |
| ACK propios | Sí | No como mecanismo general |
| Retransmisión propia | Sí | No como función general |
| Entrega ordenada | Sí | No como propiedad general |
| Sobrecarga | Mayor | Menor |

# 5. DNS y DHCP como protocolos observables

DNS y DHCP aparecen aquí porque permiten observar varias capas trabajando juntas.

Su administración detallada se desarrolla posteriormente.

## 5.1. DNS

DNS permite obtener información asociada a nombres.

Ejemplo:

```text
www.example.test
→ consulta DNS
→ respuesta DNS
→ 203.0.113.80
```

Después puede comenzar una comunicación distinta hacia la dirección obtenida.

## 5.2. Resolver no es alcanzar ni prestar servicio

Debemos separar:

```text
resolución de nombre
≠
conectividad IP
≠
servicio final
```

Ejemplos:

- DNS puede responder y la web estar caída;
- `ping` puede responder y HTTPS estar bloqueado;
- HTTPS puede funcionar aunque ICMP esté filtrado.

## 5.3. Registros básicos

Conviene reconocer:

| Tipo | Función inicial |
|---|---|
| A | Dirección IPv4 |
| AAAA | Dirección IPv6 |
| CNAME | Alias |
| MX | Servidor de correo |

No es necesario memorizar todos los tipos existentes.

## 5.4. DNS y transporte

Muchas consultas DNS utilizan UDP.

Pero DNS también puede utilizar TCP.

No memorices:

```text
DNS = siempre UDP
```

La captura nos permite observar qué transporte se está utilizando realmente.

## 5.5. DHCP

DHCP permite obtener parámetros de red automáticamente.

Una adquisición inicial típica sigue:

```text
Discover
→ Offer
→ Request
→ Acknowledgment
```

Se conoce habitualmente como **DORA**.

DHCP puede proporcionar:

- dirección IP;
- máscara/prefijo;
- gateway;
- DNS;
- tiempo de concesión;
- otros parámetros.

## 5.6. Broadcast inicial

Un cliente que todavía no dispone de toda su configuración puede necesitar enviar determinados mensajes de forma que puedan ser recibidos dentro del dominio local.

Esto prepara contenidos posteriores sobre relays y routing, pero no se configuran todavía.

# 6. Wireshark: capturar, filtrar e interpretar

Wireshark no se utiliza para “mirar paquetes”.

Se utiliza para responder preguntas técnicas mediante evidencia.

## 6.1. Antes de capturar: formular una pregunta

Ejemplos:

```text
¿se realiza una consulta DNS?
¿se obtiene respuesta?
¿aparece ARP?
¿se completa el handshake TCP?
¿qué dirección MAC se utiliza?
¿qué puerto de destino aparece?
```

Una pregunta concreta produce una captura más fácil de interpretar.

## 6.2. Elegir la interfaz

Un equipo puede disponer de:

- Ethernet;
- Wi‑Fi;
- loopback;
- VPN;
- interfaces virtuales.

La primera pregunta práctica es:

> ¿Por qué interfaz debería circular el tráfico que quiero observar?

Elegir la interfaz equivocada puede producir una captura aparentemente “vacía” para la comunicación buscada.

## 6.3. Tres paneles principales

Wireshark suele presentar:

1. **lista de paquetes**;
2. **detalles de protocolos**;
3. **bytes capturados**.

```text
┌─────────────────────────┐
│ Lista de paquetes       │
├─────────────────────────┤
│ Detalles del paquete    │
├─────────────────────────┤
│ Bytes                   │
└─────────────────────────┘
```

No es necesario interpretar todos los bytes.

## 6.4. Filtros de visualización

Ejemplos:

```text
arp
icmp
dns
tcp
udp
dhcp
```

Por dirección:

```text
ip.addr == 192.168.10.20
```

Por puerto:

```text
tcp.port == 443
```

Un filtro de visualización:

- no elimina paquetes;
- no modifica la captura;
- solo cambia qué paquetes se muestran.

## 6.5. Filtro de captura frente a filtro de visualización

Un **capture filter** decide qué tráfico se almacena.

Un **display filter** decide qué tráfico ya capturado se muestra.

En U02 se priorizan filtros de visualización para evitar perder evidencia innecesariamente.

## 6.6. Punto de captura

La captura depende del lugar desde el que observamos.

Capturar en el cliente puede mostrar:

```text
qué envía el cliente
qué recibe el cliente
```

pero no demuestra automáticamente:

- qué llegó al servidor;
- qué ocurrió después de otro router;
- qué descartó un firewall intermedio;
- qué ocurrió en otro segmento.

Principio:

```text
ausencia en mi captura
≠
ausencia demostrada en toda la red
```

## 6.7. Registrar contexto

Una captura útil debe incluir contexto:

```text
Pregunta:
Equipo:
Interfaz:
Punto de captura:
Fecha/hora:
Acción:
Duración:
Filtro:
```

Un PCAP sin contexto puede ser difícil de interpretar.

## 6.8. Tráfico cifrado

HTTPS protege contenido de aplicación.

Eso no significa:

```text
tráfico cifrado
=
tráfico invisible
```

Todavía pueden ser observables, según el caso:

- direcciones IP;
- puertos;
- tamaños;
- tiempos;
- handshake TCP;
- parte de la negociación criptográfica.

Pero normalmente no podremos leer directamente:

- contraseñas;
- formularios;
- cuerpo de la página;
- cabeceras HTTP protegidas.

## 6.9. Privacidad

Una captura puede contener datos sensibles.

Buenas prácticas:

- capturar solo en entornos autorizados;
- limitar duración;
- evitar tráfico ajeno innecesario;
- anonimizar cuando proceda;
- almacenar de forma segura;
- no subir capturas reales a servicios externos o asistentes de IA sin autorización.

# 7. La vida de un paquete: integrar las capas

Escenario:

```text
PC-A
→ SW1
→ R1
→ red remota
→ servidor web
```

El usuario introduce:

```text
https://www.example.test
```

Vamos a reconstruir el proceso sin introducir todavía subnetting o routing avanzado.

## 7.1. Resolución del nombre

```text
nombre
→ DNS
→ IP del servidor
```

La resolución es una comunicación propia.

No forma parte “mágicamente” de HTTPS.

## 7.2. Local o remoto

El host determina si el destino se encuentra en su red local o debe utilizar gateway.

El cálculo formal se estudiará en U04.

En este caso el destino es remoto.

## 7.3. Resolver la MAC del gateway

Si no existe entrada válida:

```text
ARP
→ IP gateway
→ MAC gateway
```

## 7.4. Construir la comunicación

Conceptualmente:

```text
HTTPS
↓
TCP
↓
IPv4
↓
Ethernet
↓
señal
```

Primera trama:

```text
MAC origen  → PC-A
MAC destino → gateway
```

Paquete:

```text
IP origen  → PC-A
IP destino → servidor
```

## 7.5. Router

R1:

1. recibe trama;
2. procesa paquete IPv4;
3. reduce TTL;
4. selecciona cómo continuar;
5. crea una nueva trama para el siguiente enlace.

En el alcance estudiado sin NAT:

```text
información L2
→ cambia por enlace

IP de extremos
→ mantiene la comunicación origen-destino
```

## 7.6. Transporte

Si el servicio utiliza TCP:

```text
SYN
→ SYN/ACK
→ ACK
```

Después puede comenzar la comunicación de aplicación.

## 7.7. Retorno

Una comunicación necesita camino de ida y vuelta.

```text
el paquete salió
≠
la respuesta puede volver
```

Esta idea será esencial en routing y troubleshooting posteriores.

# 8. Análisis integrado y elaboración de evidencias

Analizar tráfico no consiste en abrir paquetes al azar.

Conviene seguir un procedimiento reproducible.

## 8.1. Método básico

```text
1. definir la pregunta
2. registrar el punto de captura
3. identificar los extremos
4. aislar el tráfico relevante
5. identificar protocolos
6. seguir la secuencia
7. relacionar capas e identificadores
8. registrar hechos
9. formular inferencias
10. formular hipótesis si es necesario
11. indicar limitaciones
12. proponer siguiente prueba
13. escribir conclusión limitada
```

## 8.2. Evidencia

Dato directamente observable.

Ejemplo:

```text
Se observa una respuesta DNS con 203.0.113.80.
```

## 8.3. Inferencia

Interpretación razonable derivada de evidencia.

```text
La consulta del nombre ha recibido una respuesta DNS.
```

## 8.4. Hipótesis

Posible explicación todavía no demostrada.

```text
El servicio HTTPS puede no estar escuchando.
```

## 8.5. Conclusión

Afirmación respaldada por suficiente evidencia.

Debe incluir límites cuando sean relevantes.

## 8.6. Ejemplo TCP

Pregunta:

> ¿Se completa el establecimiento TCP?

Captura:

```text
SYN
SYN
SYN
```

Hecho:

```text
Se observan SYN del cliente.
No se observa SYN/ACK en esta captura.
```

Hipótesis compatibles:

- servicio no disponible;
- filtro/firewall;
- destino incorrecto;
- problema de retorno;
- captura incompleta;
- tráfico no visible desde ese punto.

Conclusión no justificada:

```text
“El servidor está apagado.”
```

## 8.7. Ejemplo DNS

Pregunta:

> ¿El cliente obtiene respuesta DNS?

Si observamos:

```text
DNS Query
DNS Response
```

podemos afirmar que hay evidencia de consulta y respuesta en ese punto.

No podemos afirmar por ello:

```text
la web funciona
```

# 9. Seguridad, privacidad y uso responsable de las capturas

Una captura puede contener:

- direcciones;
- nombres de host;
- consultas DNS;
- identificadores;
- contenido sin cifrar;
- cookies;
- credenciales en protocolos inseguros;
- información personal.

Por ello:

1. solo se captura en entornos autorizados;
2. se limita duración y alcance;
3. se evita tráfico real innecesario;
4. se anonimizan datos cuando proceda;
5. se almacenan los archivos de forma segura;
6. no se comparten capturas con servicios externos sin autorización.

## IA como apoyo

Un asistente de IA puede ayudar a:

- explicar un campo;
- recordar una sintaxis de filtro;
- resumir una secuencia;
- proponer hipótesis;
- mejorar un informe.

Pero:

```text
IA
≠
fuente de evidencia de la red
```

Una respuesta debe contrastarse con:

```text
captura
+
prueba
+
documentación
```

Nunca debe “inventarse” tráfico que no aparece.
