> **Pregunta guía:** ¿Cómo obtiene un host su configuración IPv6, de dónde procede cada parámetro y qué evidencias permiten comprobar que IPv6 funciona realmente?

En U04 aprendimos a interpretar direccionamiento IPv4, prefijos, gateway, subnetting, VLSM, CIDR y DHCP. IPv6 conserva la idea de **dirección + prefijo**, pero cambia de forma importante el funcionamiento de la red local y la autoconfiguración.

Una interfaz IPv6 puede utilizar varias direcciones al mismo tiempo. Los routers anuncian información mediante **Router Advertisement (RA)**; un host puede generar direcciones mediante **SLAAC**, comprobar duplicidades mediante **Duplicate Address Detection (DAD)** y descubrir vecinos mediante **Neighbor Discovery Protocol (NDP)**. DHCPv6 puede participar en la configuración, pero **no proporciona el router predeterminado**.

La idea central de esta unidad es aprender a interpretar IPv6 como un sistema de mecanismos relacionados y a diagnosticarlo mediante evidencias observables:

```text
configuración
→ tipo y alcance de dirección
→ prefijo
→ origen de los parámetros
→ RA / SLAAC / DAD
→ NDP
→ ruta por defecto
→ DNS
→ prueba IPv6
→ captura si aporta evidencia
→ conclusión
```

Mapa de la unidad:

| 3. Link-local, RA, SLAAC y DAD | ¿Cómo consigue un host una dirección sin que nadie se la escriba? |

| 6. Verificación y dual stack | ¿Con qué comandos compruebo cada parámetro y cada familia IP? |
| 7. Wireshark | ¿Qué mensajes puedo ver en una captura y qué demuestran? |

# 1. Leer y escribir direcciones IPv6

Antes de configurar o diagnosticar IPv6 necesitamos **leer** sus direcciones con soltura. Son mucho más largas que las IPv4 (128 bits frente a 32) y se escriben en hexadecimal, por eso existen reglas para acortarlas. Si no dominamos esas reglas, dos direcciones iguales escritas de forma distinta nos parecerán diferentes, o daremos por válida una dirección mal escrita.

Además, en IPv6 una misma interfaz tiene normalmente **varias direcciones a la vez**, cada una con un **tipo** y un **alcance** distintos. Este apartado te enseña a escribirlas, a expandirlas y a reconocer para qué sirve cada una.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Varias direcciones por interfaz** (*multiple addresses per interface*) | ¿Cuántas direcciones IPv6 puede tener una interfaz? | Una link-local y una global a la vez |
| **Hexteto** (*hextet*) | ¿Cómo se divide una dirección de 128 bits? | 8 grupos de 16 bits: `2001:0db8:…` |
| **Compresión** (*compression*) | ¿Cómo se escribe más corta sin cambiar la dirección? | `2001:db8:10:20::42` |
| **Expansión** (*expansion*) | ¿Cómo recupero la forma completa? | `2001:0db8:0010:0000:…:0025` |
| **Tipo y alcance** (*address type and scope*) | ¿Para qué sirve y hasta dónde llega esta dirección? | `fe80::/10` solo en el enlace |
| **Prefijo** (*prefix*) | ¿Qué parte identifica la red? | `2001:db8:10:20::/64` |

No debemos confundir **representación** con **dirección**: comprimir una dirección cambia cómo se escribe, no a qué equipo identifica.

## 1.1. Una interfaz puede tener varias direcciones

En IPv6 es normal que una interfaz utilice varias direcciones al mismo tiempo.

Ejemplo:

```text
Interfaz: Ethernet

Direcciones:
  fe80::a00:27ff:fe12:3456/64
  2001:db8:10:20::25/64

Ruta:
  default via fe80::1

DNS:
  2001:db8:53::53
```

En este ejemplo aparecen:

- una dirección **link-local**;
- una dirección del prefijo `2001:db8:10:20::/64`;
- una ruta predeterminada cuyo siguiente salto es link-local;
- un servidor DNS accesible mediante IPv6.

No debemos buscar «la dirección IPv6» de un host como si necesariamente existiera una sola. En un equipo real pueden aparecer también direcciones **temporales** (apartado 3.4), una ULA o varias globales.

## 1.2. Estructura de una dirección

IPv6 utiliza direcciones de **128 bits**, representadas mediante ocho grupos hexadecimales de 16 bits o **hextetos**. Cada dígito hexadecimal equivale a 4 bits, así que cada hexteto tiene como máximo 4 dígitos (8 × 16 = 128 bits).

Forma completa:

```text
2001:0db8:0010:0020:0000:0000:0000:0042
```

### Eliminar ceros iniciales

Los ceros a la izquierda de cada hexteto pueden omitirse:

```text
2001:db8:10:20:0:0:0:42
```

### Utilizar `::`

Una secuencia continua de hextetos `0` puede sustituirse por `::`:

```text
2001:db8:10:20::42
```

`::` solo puede aparecer una vez en una dirección.

## 1.3. Reglas de compresión y ejemplos resueltos

Las reglas completas (forma recomendada por RFC 5952) son:

1. En cada hexteto se eliminan **solo los ceros a la izquierda**; nunca los de la derecha ni los del medio (`0db8` → `db8`, pero `1000` sigue siendo `1000`).
2. Un hexteto que es todo ceros se escribe `0`.
3. `::` sustituye **una sola** secuencia de dos o más hextetos `0` consecutivos.
4. Si hay varias secuencias de ceros, se comprime **la más larga**; si empatan, **la primera** (la de la izquierda).
5. No se usa `::` para un único hexteto `0` (es válido, pero no es la forma recomendada).
6. Se escriben las letras en **minúscula**. Algunos equipos (por ejemplo, Cisco IOS) las muestran en mayúscula: `FE80::1` y `fe80::1` son la misma dirección.

| Forma completa | Paso 1: sin ceros iniciales | Forma comprimida | Regla que se aplica |
|---|---|---|---|
| `2001:0db8:0000:0000:0000:ff00:0042:8329` | `2001:db8:0:0:0:ff00:42:8329` | `2001:db8::ff00:42:8329` | 1 y 3 |
| `2001:0db8:0000:0001:0000:0000:0000:0001` | `2001:db8:0:1:0:0:0:1` | `2001:db8:0:1::1` | 4: se comprime el bloque de tres ceros, no el de uno |
| `2001:0db8:0000:0000:0001:0000:0000:0001` | `2001:db8:0:0:1:0:0:1` | `2001:db8::1:0:0:1` | 4: empate de dos bloques de dos → el primero |
| `2001:0db8:1000:0000:0000:0000:0000:0000` | `2001:db8:1000:0:0:0:0:0` | `2001:db8:1000::` | 1: el `1000` no se toca |
| `2001:0db8:0010:0000:0020:0030:0040:0050` | `2001:db8:10:0:20:30:40:50` | `2001:db8:10:0:20:30:40:50` | 5: un único `0` no se sustituye por `::` |
| `fe80:0000:0000:0000:0000:0000:0000:0001` | `fe80:0:0:0:0:0:0:1` | `fe80::1` | 3 |
| `0000:0000:0000:0000:0000:0000:0000:0001` | `0:0:0:0:0:0:0:1` | `::1` | 3 |

Errores típicos:

| Escritura | Problema |
|---|---|
| `2001:db8::1::1` | **No válida**: `::` aparece dos veces y no se sabe cuántos ceros representa cada uno |
| `2001:db8:1::` para `2001:db8:1000::` | **Otra dirección**: se han quitado ceros de la derecha |
| `2001:db8:10:20::42:` | **No válida**: los `:` finales sobran |

## 1.4. Expandir una dirección

Ejemplo:

```text
2001:db8:10::25
```

Forma expandida:

```text
2001:0db8:0010:0000:0000:0000:0000:0025
```

Procedimiento:

1. contar los hextetos visibles;
2. localizar `::`;
3. añadir los grupos `0000` necesarios hasta completar ocho;
4. completar cada hexteto con cuatro dígitos.

En el ejemplo hay 4 hextetos visibles (`2001`, `db8`, `10`, `25`); faltan 8 − 4 = **4** grupos `0000`, que se colocan donde estaba `::`.

Segundo ejemplo:

```text
fe80::a00:27ff:fe12:3456
```

Hay 5 hextetos visibles (`fe80`, `a00`, `27ff`, `fe12`, `3456`) → faltan **3** grupos `0000`:

```text
fe80:0000:0000:0000:0a00:27ff:fe12:3456
```

Observa que `a00` se completa a `0a00` (ceros a la **izquierda**), no a `a000`.

## 1.5. Tipos y alcances que debemos reconocer

Cada dirección IPv6 pertenece a un **tipo** que se reconoce por sus primeros bits (su prefijo). El tipo nos dice **para qué sirve** y el **alcance** (*scope*) nos dice **hasta dónde llega**: solo el enlace, solo la organización o potencialmente todo Internet.

| Tipo | Prefijo o ejemplo | Uso básico |
|---|---|---|
| **Global unicast** (GUA) | principalmente `2000::/3` (empiezan por `2` o `3`) | Comunicación con alcance potencialmente global |
| **Link-local** | `fe80::/10` (en la práctica, `fe80::/64`) | Comunicación dentro del enlace; no la reenvían los routers |
| **ULA** (*Unique Local Address*) | `fc00::/7`, habitualmente `fd00::/8` | Redes internas; no se encaminan en Internet |
| **Loopback** | `::1/128` | El propio host |
| **No especificada** (*unspecified*) | `::/128` | «Todavía no tengo dirección»; se usa como origen durante DAD |
| **Multicast** | `ff00::/8` | Comunicación dirigida a grupos |
| **Documentación** | `2001:db8::/32` | Ejemplos y prácticas; no se usa en redes reales |

IPv6 no utiliza broadcast como IPv4. Muchas funciones utilizan **multicast**. Estos grupos aparecerán en capturas y en `show ipv6 interface`:

| Grupo multicast | Quién lo escucha | Dónde lo verás |
|---|---|---|
| `ff02::1` | Todos los nodos del enlace (*all-nodes*) | Destino de los RA periódicos |
| `ff02::2` | Todos los routers del enlace (*all-routers*) | Destino de los RS |
| `ff02::1:2` | Servidores y relays DHCPv6 | Destino de los mensajes del cliente DHCPv6 |
| `ff02::1:ffXX:XXXX` | *Solicited-node*: los nodos cuya dirección termina en esos 24 bits | Destino de los NS (resolución de vecinos y DAD) |

`ff02::` indica alcance de enlace: estos mensajes no salen del segmento local. Basta con reconocerlos; no es necesario calcular direcciones *solicited-node*.

## 1.6. Dirección y prefijo

Ejemplo:

```text
2001:db8:10:20::25/64
```

Dirección:

```text
2001:db8:10:20::25
```

Prefijo de la LAN:

```text
2001:db8:10:20::/64
```

En esta unidad trabajaremos normalmente con redes LAN `/64`. En una dirección global unicast típica, los 128 bits se reparten así:

```text
|  prefijo global de routing  | ID de subred |   identificador de interfaz (IID)  |
|          48 bits            |   16 bits    |              64 bits               |
|        2001:db8:10          |      20      |              ::25                  |
```

- **Prefijo global de routing** (*global routing prefix*): lo asigna el proveedor u organismo; identifica la organización.
- **ID de subred** (*subnet ID*): lo decide la organización para numerar sus LAN (apartado 2).
- **Identificador de interfaz** (*interface ID, IID*): identifica la interfaz dentro de la LAN; puede escribirse a mano, generarse con EUI-64 o ser aleatorio (apartado 3.4).

### Ideas clave

- Una interfaz IPv6 puede utilizar varias direcciones.
- Dirección y prefijo deben interpretarse conjuntamente.
- La escritura comprimida no cambia la dirección: solo cambia su representación.
- Solo se eliminan ceros a la izquierda, y `::` aparece una sola vez.
- El tipo y el alcance se reconocen por el prefijo.

# 2. Planificación sencilla de prefijos

Una organización recibe un bloque IPv6 (por ejemplo, un `/48`) y tiene que repartirlo entre sus redes: usuarios, Wi-Fi, servidores, gestión… Este apartado explica cómo hacerlo de forma **ordenada y documentada**. La diferencia con U04 es importante: en IPv4 calculábamos máscaras para no desperdiciar direcciones; en IPv6 hay tantas que el problema no es ahorrar, sino **organizar**.

Las piezas se relacionan así: del **bloque padre** salen muchas subredes; cada LAN recibe un **`/64`**, que se distingue de las demás por su **ID de subred**; y todo queda recogido en un **plan documentado**.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Bloque padre** (*parent prefix / block*) | ¿Qué espacio tiene asignado la organización? | `2001:db8:1200::/48` |
| **ID de subred** (*subnet ID*) | ¿Qué bits numeran cada LAN? | 16 bits entre `/48` y `/64` → el 4.º hexteto |
| **`/64` de LAN** (*/64 LAN prefix*) | ¿Qué tamaño tiene una LAN IPv6 normal? | `2001:db8:1200:10::/64` |
| **Plan de direccionamiento** (*addressing plan*) | ¿Dónde queda escrito qué prefijo usa cada red y cómo se configura? | Tabla prefijo – uso – método |

No debemos trasladar a IPv6 el VLSM de U04: en una LAN IPv6 no se ajusta el prefijo al número de hosts.

## 2.1. El `/64` de una LAN

Ejemplo:

```text
2001:db8:1200:20::25/64
```

La subred es:

```text
2001:db8:1200:20::/64
```

En esta unidad las LAN se diseñarán normalmente como `/64`. Además de ser la práctica habitual, SLAAC necesita un prefijo `/64` para generar el identificador de interfaz de 64 bits.

## 2.2. Crear `/64` desde un bloque padre

Supongamos que una organización dispone de:

```text
2001:db8:1200::/48
```

Podemos asignar varios `/64`:

| Uso | Prefijo |
|---|---|
| Usuarios | `2001:db8:1200:10::/64` |
| Wi‑Fi | `2001:db8:1200:20::/64` |
| Servidores | `2001:db8:1200:30::/64` |
| Gestión | `2001:db8:1200:40::/64` |
| Laboratorio | `2001:db8:1200:50::/64` |

La parte comprendida entre `/48` y `/64` permite identificar subredes. Son 16 bits, es decir, el **cuarto hexteto** completo: de `0000` a `ffff`, lo que da 2^16 = **65 536** subredes `/64` posibles. Como coincide con un hexteto, se puede leer directamente sin pasar a binario.

No trasladaremos aquí el modelo VLSM de U04 basado en necesidades mínimas de hosts. En IPv6, el objetivo de una LAN no es ahorrar unas pocas direcciones, sino organizar de forma coherente el espacio de prefijos; por ello trabajaremos normalmente con `/64`.

## 2.3. Documentar el plan

Un plan sencillo debe ser:

- coherente;
- legible;
- ampliable;
- documentado.

Ejemplo:

| Prefijo | Uso | Método previsto |
|---|---|---|
| `2001:db8:1200:10::/64` | Usuarios | SLAAC |
| `2001:db8:1200:20::/64` | Wi‑Fi | SLAAC |
| `2001:db8:1200:30::/64` | Servidores | Según diseño |

Un criterio útil es reservar un identificador fijo y fácil de recordar para el router de cada LAN (por ejemplo, `::1`) y, si hay VLAN, hacer coincidir el ID de subred con el número de VLAN (VLAN 10 → `…:10::/64`; se copian los dígitos tal cual, aunque en hexadecimal `10` valga 16). Las VLAN se estudian en U07.

### Ideas clave

- En LAN IPv6 trabajaremos normalmente con `/64`.
- La planificación consiste en organizar prefijos de forma coherente.
- Un bloque padre puede proporcionar numerosos `/64`: un `/48` contiene 65 536.

# 3. Link-local, Router Advertisement, SLAAC y DAD

En IPv4 un host sin configuración manual depende de un servidor DHCP. En IPv6 un host puede **configurarse solo** con la ayuda del router del enlace. Este apartado explica esa autoconfiguración paso a paso: primero el host crea una dirección para hablar en el enlace (link-local); después pregunta al router (RS) y este le anuncia el prefijo (RA); con ese prefijo el host fabrica su dirección (SLAAC) y comprueba que nadie la usa ya (DAD).

| Concepto | Pregunta que responde | Ejemplo / evidencia |
|---|---|---|
| **Dirección link-local** (*link-local address*) | ¿Cómo habla el host en el enlace antes de tener dirección global? | `fe80::a00:27ff:fe12:3456` |
| **Solicitud de router** (*Router Solicitation, RS*) | ¿Cómo pide el host información al router? | ICMPv6 tipo 133 a `ff02::2` |
| **Anuncio de router** (*Router Advertisement, RA*) | ¿Cómo conoce el host el prefijo y el router predeterminado? | ICMPv6 tipo 134 con el prefijo `/64` |
| **SLAAC** (*Stateless Address Autoconfiguration*) | ¿Cómo genera el host su dirección global? | Prefijo del RA + identificador de interfaz |
| **Identificador de interfaz** (*interface ID*): EUI-64 o aleatorio | ¿De dónde salen los 64 bits finales? | `…:a00:27ff:fe12:3456` (EUI-64) |
| **DAD** (*Duplicate Address Detection*) | ¿Está ya en uso la dirección? | Estado `tentative` |
| **Indicadores A, M y O** (*A, M, O flags*) | ¿Cómo debe configurarse el host? | A = 1 → usar SLAAC |

Una confusión frecuente: **SLAAC no significa «dirección construida con la MAC»**. SLAAC es el mecanismo; EUI-64 es solo una de las formas de generar el identificador.

## 3.1. Dirección link-local

Cuando IPv6 está habilitado, una interfaz genera normalmente una dirección **link-local**, sin necesidad de router ni de servidor.

Ejemplo:

```text
fe80::a00:27ff:fe12:3456
```

Una dirección link-local:

- funciona únicamente en el enlace;
- permite comunicarse con routers y vecinos;
- participa en Neighbor Discovery;
- puede utilizarse como dirección del siguiente salto.

Por eso es normal observar:

```text
default via fe80::1
```

como ruta predeterminada.

Como todas las interfaces de un equipo tienen una link-local en `fe80::/64`, al usar una link-local como destino hay que indicar también la interfaz. En Linux se escribe `fe80::1%eth0`; en Windows, con el índice de interfaz, por ejemplo `fe80::1%12`.

En routers Cisco la link-local se genera automáticamente (con EUI-64) al configurar IPv6 en la interfaz, pero es habitual fijarla a mano para que sea fácil de reconocer, por ejemplo `fe80::1`.

## 3.2. Router Solicitation y Router Advertisement

Un host puede enviar un **Router Solicitation (RS)** para solicitar información a los routers del enlace. Lo envía al grupo `ff02::2` (todos los routers).

El router responde o anuncia periódicamente mediante un **Router Advertisement (RA)**, dirigido normalmente a `ff02::1` (todos los nodos). El origen del RA es siempre la **link-local** del router; por eso el gateway que aprende el host es una dirección `fe80::`.

```text
Host                         Router

RS ------------------------->
                  <----------- RA
```

Un RA puede indicar:

- qué prefijos están disponibles;
- si un prefijo puede utilizarse para SLAAC;
- que el emisor puede actuar como router predeterminado (*router lifetime* mayor que 0);
- otros parámetros de configuración (indicadores M y O, servidores DNS mediante RDNSS).

> El router predeterminado IPv6 se aprende normalmente mediante **RA**, no mediante DHCPv6.

En un router Cisco, las interfaces solo envían RA si el router tiene activado el reenvío IPv6 con `ipv6 unicast-routing` (lo configurarás de forma sistemática en U08).

## 3.3. SLAAC

**SLAAC** (*Stateless Address Autoconfiguration*) permite que un host genere una dirección utilizando un prefijo anunciado.

Proceso conceptual:

```text
link-local
    ↓
RS / RA
    ↓
prefijo anunciado
    ↓
generación de dirección
    ↓
DAD
    ↓
dirección utilizable
```

«Sin estado» (*stateless*) significa que ningún servidor lleva un registro de qué dirección tiene cada host: el router solo anuncia el prefijo y cada host completa su dirección.

Los sistemas actuales pueden generar el identificador de interfaz de diferentes formas. No debemos asumir que una dirección SLAAC contiene siempre la MAC del dispositivo.

## 3.4. El identificador de interfaz: EUI-64 o aleatorio

SLAAC une dos piezas: los 64 bits del **prefijo** (del RA) y los 64 bits del **identificador de interfaz** (IID), que genera el propio host. Hay dos grandes familias de métodos, y conviene reconocerlas porque influyen en la privacidad y en cómo leemos una dirección.

| Método | Cómo se obtiene el IID | Se reconoce por | Dónde suele aparecer |
|---|---|---|---|
| **EUI-64** (*modified EUI-64*) | A partir de la MAC de 48 bits | `ff:fe` en el centro del IID | Link-local de routers Cisco, hosts de Packet Tracer, sistemas antiguos |
| **Estable aleatorio** (*stable-privacy / semantically opaque*, RFC 7217) | Un valor pseudoaleatorio, fijo para cada red | IID sin patrón reconocible | Linux actual y otros sistemas |
| **Temporal** (*temporary / privacy extensions*, RFC 8981) | Un valor aleatorio que cambia periódicamente | Aparece como `temporary` / «temporal» | Windows, macOS, Linux de escritorio; conexiones salientes |

### Cálculo EUI-64 paso a paso

Partimos de la MAC `08:00:27:12:34:56`:

1. Dividir la MAC en dos mitades de 24 bits: `08:00:27` | `12:34:56`.
2. Insertar `ff:fe` en el centro: `08:00:27:ff:fe:12:34:56` (ya son 64 bits).
3. Invertir el **séptimo bit** del primer byte (bit U/L, *universal/local*): `08` = `0000 1000` → `0000 1010` = `0a`.
4. Agrupar en hextetos: `0a00:27ff:fe12:3456`.
5. Añadir el prefijo y comprimir:

```text
link-local:  fe80::a00:27ff:fe12:3456
global:      2001:db8:10:20:a00:27ff:fe12:3456   (prefijo 2001:db8:10:20::/64)
```

Invertir el séptimo bit equivale a sumar 2 al primer byte si ese bit valía 0, o a restar 2 si valía 1.

Más ejemplos resueltos:

| MAC | Primer byte → invertido | IID EUI-64 | Dirección resultante |
|---|---|---|---|
| `a4:5e:60:d1:22:9b` | `a4` (`1010 0100`) → `a6` (`1010 0110`) | `a65e:60ff:fed1:229b` | `2001:db8:1200:10:a65e:60ff:fed1:229b` |
| `0001.6432.a801` (formato Cisco) | `00` → `02` | `0201:64ff:fe32:a801` | `2001:db8:10:20:201:64ff:fe32:a801` |
| `02:50:56:aa:bb:cc` | `02` (`0000 0010`) → `00` | `0050:56ff:feaa:bbcc` | `fe80::50:56ff:feaa:bbcc` |

En Cisco IOS se puede pedir a la interfaz que complete la dirección con EUI-64:

```text
R1(config-if)# ipv6 address 2001:db8:10:20::/64 eui-64
```

### ¿Por qué no se usa siempre la MAC?

Una dirección EUI-64 contiene la MAC, que no cambia aunque el equipo se mueva de red. Eso permite **seguir** a un dispositivo por Internet y revela el fabricante de la tarjeta. Por eso los sistemas actuales prefieren IID aleatorios y suelen crear, además, **direcciones temporales** para las conexiones salientes. Consecuencia práctica: en un portátil real verás a menudo dos o más direcciones globales en el mismo prefijo, y ninguna contiene `ff:fe`.

## 3.5. DAD

**DAD** (*Duplicate Address Detection*) intenta comprobar que una dirección no está siendo utilizada ya en el enlace. Se aplica a todas las direcciones unicast, también a la link-local.

Funcionamiento simplificado: el host envía un **NS** preguntando por su propia dirección nueva, con origen `::` (todavía no puede usarla) y destino el grupo *solicited-node* de esa dirección. Si alguien responde con un **NA**, la dirección está duplicada.

Mientras se realiza, la dirección puede aparecer como:

```text
tentative
```

Si no se detecta conflicto, puede pasar a utilizarse normalmente. Si hay conflicto, la dirección no se usa: Linux la marca como `dadfailed`, Windows como «Duplicado» y Cisco IOS como `[DUP]`.

## 3.6. Indicadores A, M y O

En los Router Advertisement pueden aparecer indicadores que ayudan al host a decidir cómo configurarse:

- **A** (*Autonomous*): el prefijo puede utilizarse para SLAAC;
- **M** (*Managed*): puede utilizarse DHCPv6 para obtener una dirección;
- **O** (*Other*): DHCPv6 puede proporcionar otros parámetros.

M y O van en la cabecera del RA; A va dentro de la información de cada prefijo anunciado. En esta unidad basta con interpretar su función general; las combinaciones habituales se resumen en el apartado 5.4.

### Ideas clave

- Link-local aparece antes de necesitar conectividad global.
- RS solicita información y RA la anuncia.
- SLAAC permite generar una dirección.
- El identificador de interfaz puede ser EUI-64 (con `ff:fe`) o aleatorio; SLAAC no implica MAC.
- DAD intenta detectar duplicidades.
- El gateway IPv6 se aprende mediante RA y es una link-local.

# 4. Neighbor Discovery e ICMPv6

Dentro de una LAN, los equipos necesitan saber quién está a su lado: qué router pueden usar y qué dirección MAC corresponde a cada vecino. En IPv4 esas tareas estaban repartidas (ARP, DHCP, configuración manual); en IPv6 las reúne un solo protocolo, **NDP**, que viaja dentro de **ICMPv6**. Este apartado presenta sus mensajes, la tabla donde se guarda el resultado y por qué ICMPv6 no se puede bloquear a la ligera.

| Concepto | Pregunta que responde | Ejemplo / evidencia |
|---|---|---|
| **NDP** (*Neighbor Discovery Protocol*) | ¿Qué protocolo organiza la vida del enlace local? | RS, RA, NS, NA, DAD |
| **RS / RA** (*Router Solicitation / Advertisement*) | ¿Quién es el router y qué prefijo anuncia? | Tipos 133 y 134 |
| **NS / NA** (*Neighbor Solicitation / Advertisement*) | ¿Qué MAC tiene esta dirección IPv6? ¿Está duplicada? | Tipos 135 y 136 |
| **Multicast solicited-node** (*solicited-node multicast*) | ¿A quién se envía un NS sin molestar a todo el enlace? | `ff02::1:ff12:3456` |
| **Neighbor Cache** | ¿Qué vecinos conoce el host y en qué estado? | `fe80::1 … REACHABLE` |
| **ICMPv6** | ¿Qué protocolo transporta NDP, errores y `ping`? | `icmpv6` en Wireshark |

No debemos decir que «NDP es ARP para IPv6»: NS/NA sustituyen a ARP, pero NDP hace además descubrimiento de routers, anuncio de prefijos y DAD.

## 4.1. Mensajes principales

| Mensaje | Abreviatura | Función |
|---|---|---|
| Router Solicitation | **RS** | Solicitar información a routers |
| Router Advertisement | **RA** | Anunciar información de red |
| Neighbor Solicitation | **NS** | Solicitar información sobre un vecino |
| Neighbor Advertisement | **NA** | Responder sobre un vecino |

Para filtros de Wireshark conviene reconocer también:

```text
133 → RS
134 → RA
135 → NS
136 → NA
```

No es necesario memorizar muchos más tipos en esta unidad. (Existe también el **Redirect**, tipo 137, con el que un router indica a un host un siguiente salto mejor.)

## 4.2. NS y NA: resolver vecinos

En IPv4 utilizamos ARP para relacionar IPv4 y MAC dentro del enlace.

En IPv6 esa función forma parte de NDP.

```text
Host A                         Host B

NS --------------------------->
                   <----------- NA
```

En Ethernet, los mensajes NS utilizan multicast IPv6 para localizar al vecino. En herramientas o recursos técnicos puede aparecer el término **solicited-node multicast**. En esta unidad basta con reconocer su función; no es necesario calcular esas direcciones multicast. La idea importante es que, a diferencia del broadcast de ARP, el NS solo lo procesan los equipos cuya dirección termina igual, no todo el enlace.

El resultado puede almacenarse en la **Neighbor Cache**.

## 4.3. Neighbor Cache

Estados que conviene reconocer:

| Estado | Interpretación inicial |
|---|---|
| **REACHABLE** | Existe evidencia reciente de alcanzabilidad |
| **STALE** | Existe una entrada, pero puede requerir nueva confirmación |
| **INCOMPLETE** | La resolución todavía no se ha completado |
| **FAILED** | La resolución no se completó correctamente |

Pueden aparecer también **DELAY** y **PROBE**, estados transitorios mientras el host vuelve a confirmar una entrada `STALE`. Windows muestra `Unreachable` donde Linux muestra `FAILED`.

`STALE` es un estado normal: no significa que el vecino haya fallado, sino que hace tiempo que no se ha confirmado.

Una entrada `INCOMPLETE` no indica por sí sola la causa del problema. Debe investigarse el enlace, la dirección, el vecino y el tráfico NDP.

## 4.4. ICMPv6 es esencial

ICMPv6 participa en:

- RS y RA;
- NS y NA;
- DAD;
- mensajes de error (por ejemplo, destino inalcanzable o *Packet Too Big*);
- `ping`.

Por ello, no debe considerarse simplemente «el protocolo de ping».

Bloquear ICMPv6 de forma indiscriminada puede impedir funciones necesarias de IPv6.

## 4.5. Comparación inicial con IPv4

| IPv4 | IPv6 |
|---|---|
| ARP Request / Reply | NS / NA |
| Caché ARP | Neighbor Cache |
| Gateway configurado o recibido mediante DHCPv4 | Router aprendido mediante RA |
| ICMP para control y diagnóstico | ICMPv6 también soporta NDP y autoconfiguración |
| ARP Request por broadcast | NS por multicast solicited-node |

### Ideas clave

- NDP realiza más funciones que ARP.
- NS y NA permiten resolver vecinos.
- La Neighbor Cache aporta evidencias sobre el enlace.
- ICMPv6 forma parte del funcionamiento básico de IPv6.

# 5. SLAAC, DHCPv6, RDNSS y DNS AAAA

En IPv4 solemos recibir todo de un único sitio: el servidor DHCP entrega dirección, máscara, gateway y DNS. En IPv6 no ocurre así: la dirección puede salir de SLAAC o de DHCPv6, el gateway sale siempre del RA y el DNS puede llegar por RA (RDNSS) o por DHCPv6. Este apartado ordena esas combinaciones, porque saber **de dónde debería venir cada parámetro** es la clave para diagnosticar.

| Concepto | Pregunta que responde | Qué aporta |
|---|---|---|
| **Origen de los parámetros** (*parameter sources*) | ¿Quién entrega cada dato? | Tabla parámetro → origen |
| **DHCPv6 sin estado** (*stateless DHCPv6*) | ¿Quién da el DNS si la dirección sale de SLAAC? | Otros parámetros (DNS, dominio) |
| **DHCPv6 con estado** (*stateful DHCPv6*) | ¿Puede un servidor asignar y registrar direcciones? | Dirección + otros parámetros |
| **Indicadores A/M/O** (*RA flags*) | ¿Qué método indica el router? | La decisión del host |
| **RDNSS** (*Recursive DNS Server option*) | ¿Puede el RA entregar el DNS? | Servidor DNS dentro del RA |
| **Registro AAAA** (*AAAA record*) | ¿Qué dirección IPv6 corresponde a un nombre? | Resolución de nombres IPv6 |

Idea que hay que fijar desde el principio: **DHCPv6 no proporciona el gateway**; ni en modo stateless ni en modo stateful.

## 5.1. ¿De dónde puede proceder cada parámetro?

| Parámetro | Posible origen |
|---|---|
| Link-local | El propio host |
| Dirección global / ULA | SLAAC, DHCPv6 o configuración manual |
| Prefijo | Router Advertisement o configuración manual |
| Router predeterminado | Router Advertisement (o configuración manual) |
| DNS | RDNSS, DHCPv6 o configuración manual |

Esta tabla es fundamental para diagnosticar IPv6.

## 5.2. DHCPv6 stateless

En un diseño **stateless**:

```text
SLAAC   → dirección IPv6
DHCPv6  → otros parámetros
```

Por ejemplo, DHCPv6 puede proporcionar información DNS. El servidor no guarda qué dirección tiene cada cliente; por eso es «sin estado».

## 5.3. DHCPv6 stateful

En un diseño **stateful**, DHCPv6 puede proporcionar una dirección al cliente y el servidor registra la asignación (como hacía DHCPv4).

Sin embargo, el router predeterminado continúa aprendiéndose mediante RA. Tampoco la longitud del prefijo llega por DHCPv6: el host sabe qué red es local gracias al prefijo anunciado en el RA.

| Mecanismo | Dirección | Gateway | DNS habitual |
|---|---|---|---|
| SLAAC | SLAAC | RA | RDNSS |
| DHCPv6 stateless | SLAAC | RA | DHCPv6 (y/o RDNSS) |
| DHCPv6 stateful | DHCPv6 | RA | DHCPv6 |

Datos de reconocimiento: DHCPv6 usa UDP, puerto **546** en el cliente y **547** en el servidor; el cliente envía sus mensajes al grupo `ff02::1:2`. El intercambio completo es **Solicit → Advertise → Request → Reply**; en modo stateless basta **Information-Request → Reply**.

## 5.4. Indicadores del RA y método resultante

El router indica el método mediante los indicadores vistos en 3.6. Combinaciones habituales:

| Método | A | M | O | Qué hace el host |
|---|---:|---:|---:|---|
| Solo SLAAC (DNS por RDNSS) | 1 | 0 | 0 | Genera su dirección; DNS del RA |
| SLAAC + DHCPv6 stateless | 1 | 0 | 1 | Genera su dirección; pide DNS a DHCPv6 |
| DHCPv6 stateful | 0 | 1 | (1) | Pide dirección y demás parámetros a DHCPv6 |

En el diseño stateful el indicador O es indiferente, porque M = 1 ya implica pedir todo a DHCPv6. Si A = 1 y M = 1 a la vez, el host puede terminar con una dirección SLAAC **y** otra DHCPv6: no es un error, es consecuencia del diseño.

En Cisco IOS (lo verás preparado en los laboratorios; la administración del router se estudia en U08):

```text
R1(config-if)# ipv6 nd other-config-flag          ! O = 1  → stateless
R1(config-if)# ipv6 nd managed-config-flag        ! M = 1  → stateful
R1(config-if)# ipv6 nd prefix 2001:db8:10:20::/64 no-autoconfig   ! A = 0
```

## 5.5. RDNSS

Un Router Advertisement puede proporcionar información DNS mediante **RDNSS**.

Por tanto:

```text
SLAAC
```

no significa:

```text
sin DNS
```

El origen concreto depende del diseño. Ten en cuenta que no todos los sistemas ni todos los simuladores procesan RDNSS; si un host no obtiene DNS con «solo SLAAC», el diseño stateless con DHCPv6 es la alternativa habitual.

## 5.6. Registros AAAA

Un registro **AAAA** relaciona un nombre con una dirección IPv6 (el registro **A** hace lo mismo con IPv4).

Ejemplo:

```text
srv.example.  AAAA  2001:db8:100::20
```

Herramientas de consulta:

```text
nslookup -type=AAAA srv.example
dig AAAA srv.example
Resolve-DnsName srv.example -Type AAAA
```

Un AAAA correcto demuestra que DNS ha devuelto una dirección IPv6. No demuestra que exista conectividad hacia ella ni que el servicio esté disponible.

La consulta AAAA puede viajar sobre IPv4 o sobre IPv6: el tipo de registro no depende de la familia que se use para preguntar al servidor DNS.

### Ideas clave

- Dirección, gateway y DNS pueden tener orígenes diferentes.
- DHCPv6 no proporciona el gateway predeterminado.
- SLAAC y DHCPv6 pueden coexistir.
- Los indicadores A, M y O del RA dicen al host qué método usar.
- Un registro AAAA correcto no garantiza conectividad.

# 6. Verificación y dual stack

Conocer los mecanismos no basta: hay que **comprobar** qué ha ocurrido de verdad en cada equipo. Este apartado reúne los comandos para leer direcciones, rutas, vecinos y DNS en Windows, Linux y Cisco IOS/Packet Tracer; propone un orden de comprobación; y explica el **dual stack**, la situación más frecuente hoy, en la que IPv4 e IPv6 conviven y pueden fallar por separado.

| Concepto | Pregunta que responde | Ejemplo de evidencia |
|---|---|---|
| **Comandos de verificación** (*verification commands*) | ¿Qué comando muestra cada parámetro? | `ip -6 route`, `show ipv6 interface brief` |
| **Lectura de salidas** (*reading outputs*) | ¿Qué significan `scope`, `tentative`, `temporary`, `proto ra`? | `inet6 … scope link` |
| **Comprobación mínima** (*minimum check*) | ¿En qué orden reviso? | De link-local a servicio |
| **Doble pila** (*dual stack*) | ¿Qué ocurre cuando conviven IPv4 e IPv6? | `192.0.2.10/24` + `2001:db8:10:20::10/64` |
| **Prueba por familia** (*per-family test*) | ¿Funciona cada familia por separado? | `ping -4` / `ping -6` |

No debemos concluir que IPv6 funciona porque «Internet funciona»: la aplicación puede estar usando IPv4.

## 6.1. Qué debemos consultar

| Objetivo | Windows | Linux | Cisco IOS / Packet Tracer |
|---|---|---|---|
| Direcciones | `ipconfig /all` · `Get-NetIPAddress -AddressFamily IPv6` | `ip -6 address` | `show ipv6 interface brief` · `show ipv6 interface g0/0` · PC de PT: `ipconfig /all`, `ipv6config` |
| Rutas | `route print -6` · `Get-NetRoute -AddressFamily IPv6` | `ip -6 route` | `show ipv6 route` |
| Vecinos | `netsh interface ipv6 show neighbors` · `Get-NetNeighbor -AddressFamily IPv6` | `ip -6 neigh` | `show ipv6 neighbors` |
| DNS configurado | `ipconfig /all` | `resolvectl status` | — |
| DNS AAAA | `nslookup -type=AAAA nombre` · `Resolve-DnsName nombre -Type AAAA` | `dig AAAA nombre` | — |
| DHCPv6 (servidor) | — | — | `show ipv6 dhcp pool` · `show ipv6 dhcp binding` |
| ICMPv6 | `ping -6` · `tracert -6` | `ping -6` · `traceroute -6` | `ping ipv6 …` o `ping` con dirección IPv6 · `traceroute` |

No es necesario memorizar todas las variantes. Debemos saber **qué información buscamos y cómo interpretarla**.

## 6.2. Leer las salidas

Linux, con una dirección EUI-64, una temporal y la link-local:

```text
$ ip -6 address show dev enp0s3
2: enp0s3: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500
    inet6 2001:db8:10:20:3c5e:91d2:7a40:b1e8/64 scope global temporary dynamic
       valid_lft 86380sec preferred_lft 14380sec
    inet6 2001:db8:10:20:a00:27ff:fe12:3456/64 scope global dynamic mngtmpaddr
       valid_lft 86380sec preferred_lft 14380sec
    inet6 fe80::a00:27ff:fe12:3456/64 scope link
       valid_lft forever preferred_lft forever

$ ip -6 route
2001:db8:10:20::/64 dev enp0s3 proto ra metric 100
fe80::/64 dev enp0s3 proto kernel metric 256
default via fe80::1 dev enp0s3 proto ra metric 100 expires 1790sec

$ ip -6 neigh
fe80::1 dev enp0s3 lladdr 00:01:64:32:a8:01 router REACHABLE
```

| Lo que ves | Qué significa |
|---|---|
| `scope link` / `scope global` | Link-local / dirección global |
| `dynamic` | Obtenida automáticamente (SLAAC o DHCPv6), con tiempo de vida |
| `temporary` | Dirección temporal de privacidad |
| `mngtmpaddr` | Dirección estable a partir de la cual se generan las temporales |
| `tentative` / `dadfailed` | DAD en curso / DAD ha detectado un duplicado |
| `proto ra` | Ruta aprendida de un Router Advertisement |
| `router REACHABLE` | El vecino es un router y está confirmado |

En Windows, `ipconfig /all` muestra, entre otras, «Dirección IPv6», «Dirección IPv6 temporal» y «Vínculo: dirección IPv6 local» (la link-local, con `%` e índice de interfaz), cada una con su estado: «(Preferido)», «(Tentativo)» o «(Duplicado)». La «Puerta de enlace predeterminada» IPv6 aparece como `fe80::…%n`.

En un router Cisco:

```text
R1# show ipv6 interface brief
GigabitEthernet0/0     [up/up]
    FE80::1
    2001:DB8:10:20::1
```

IOS muestra las direcciones en mayúsculas; son las mismas que `fe80::1` y `2001:db8:10:20::1`.

## 6.3. Laboratorio en Packet Tracer: configuración mínima

En las sesiones de laboratorio el router suele estar **preparado** o se configura con muy pocas órdenes. La administración de routers (acceso, rutas, copias) se trabaja en U08; aquí interesa **qué efecto tiene cada orden en los hosts**.

```text
R1(config)# ipv6 unicast-routing                       ! sin esto no hay RA
R1(config)# interface g0/0
R1(config-if)# ipv6 address 2001:db8:10:20::1/64
R1(config-if)# ipv6 address fe80::1 link-local
R1(config-if)# no shutdown
```

Con esto los PC que tengan IPv6 en modo automático (según versión, *Automatic* o *Auto Config*) obtienen por SLAAC una dirección `2001:db8:10:20:…` con IID EUI-64 y el gateway `fe80::1`.

DHCPv6 stateless (DNS por DHCPv6):

```text
R1(config)# ipv6 dhcp pool LAN-V6
R1(config-dhcpv6)# dns-server 2001:db8:10:20::53
R1(config-dhcpv6)# domain-name asir.local
R1(config-dhcpv6)# exit
R1(config)# interface g0/0
R1(config-if)# ipv6 dhcp server LAN-V6
R1(config-if)# ipv6 nd other-config-flag
```

Para un diseño stateful se añade en el pool `address prefix 2001:db8:10:20::/64` y en la interfaz `ipv6 nd managed-config-flag`. Verificación: `show ipv6 interface g0/0` (indica cómo deben configurarse los hosts), `show ipv6 dhcp pool` y, en el PC, `ipconfig /all`.

## 6.4. Comprobación mínima

Una secuencia útil es:

```text
1. ¿Existe link-local?
2. ¿Existe global o ULA cuando debería?
3. ¿DAD ha finalizado?
4. ¿Existe ruta por defecto?
5. ¿Se conoce al router como vecino?
6. ¿Existe DNS?
7. ¿Existe un AAAA cuando corresponde?
8. ¿Funciona IPv6 por dirección?
9. ¿Responde el servicio?
```

El síntoma determinará qué pasos son necesarios.

## 6.5. Dual stack

En **dual stack**, IPv4 e IPv6 funcionan simultáneamente.

Ejemplo:

```text
IPv4:
192.0.2.10/24

IPv6:
2001:db8:10:20::10/64
```

Dual stack no significa que cada paquete se envíe dos veces.

Una aplicación puede terminar utilizando IPv4 o IPv6 según la resolución, la conectividad y el comportamiento del sistema. Por lo general, si un nombre tiene registros A y AAAA, los sistemas actuales intentan primero IPv6 y, si no responde a tiempo, pasan a IPv4 (*Happy Eyeballs*). Así, un fallo IPv6 puede quedar oculto: la web «funciona», solo que por IPv4.

## 6.6. Probar cada familia por separado

Para evitar que una familia oculte el fallo de la otra:

```text
ping -4 example.net
ping -6 example.net
```

Podemos encontrar:

```text
IPv4 funciona
IPv6 falla
```

o lo contrario.

Si una web funciona, eso no demuestra por sí solo que IPv6 esté funcionando.

## 6.7. Comparación IPv4 / IPv6

| Función | IPv4 | IPv6 |
|---|---|---|
| Dirección LAN | Dirección + prefijo | Dirección + prefijo |
| Resolución de vecino | ARP | NDP |
| Configuración automática | DHCPv4 | SLAAC y/o DHCPv6 |
| Router predeterminado | Manual/DHCPv4 | RA |
| Registro DNS | A | AAAA |
| Broadcast | Sí | No; utiliza multicast para muchas funciones |

### Ideas clave

- IPv4 e IPv6 pueden fallar de forma independiente.
- Una aplicación funcionando no demuestra qué familia utilizó.
- El diagnóstico dual stack requiere probar ambas familias por separado.
- Cada parámetro tiene su comando: dirección, ruta, vecino y DNS se comprueban por separado.

# 7. Captura de tráfico IPv6 con Wireshark

Los comandos del apartado 6 muestran el **resultado** de la autoconfiguración; Wireshark permite ver el **proceso**: qué mensajes se intercambian, quién los envía y qué contienen. Este apartado reúne los filtros útiles, la secuencia que cabe esperar al activar una interfaz y, sobre todo, cómo separar lo que la captura demuestra de lo que solo sugiere.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Filtro de visualización** (*display filter*) | ¿Cómo aíslo el tráfico que me interesa? | `icmpv6.type == 134` |
| **Secuencia de autoconfiguración** (*autoconfiguration sequence*) | ¿Qué orden de mensajes cabe esperar? | DAD → RS → RA → DAD → NS/NA |
| **Preguntas de análisis** (*analysis questions*) | ¿Qué busco en la captura? | ¿Qué prefijo anuncia el RA? |
| **Hecho frente a interpretación** (*fact vs. interpretation*) | ¿Qué demuestra y qué no demuestra la captura? | «No se ve RA» ≠ «el router está apagado» |

No debemos confundir **no ver** un paquete con que **no exista**: el punto y el momento de captura limitan siempre la conclusión.

## 7.1. Filtros básicos

```text
ipv6
icmpv6
dhcpv6
```

Para NDP:

```text
icmpv6.type == 133   # RS
icmpv6.type == 134   # RA
icmpv6.type == 135   # NS
icmpv6.type == 136   # NA
icmpv6.type >= 133 && icmpv6.type <= 136   # todo NDP
```

Para consultas AAAA:

```text
dns.qry.type == 28
```

Para buscar una dirección concreta (origen o destino):

```text
ipv6.addr == fe80::1
```

En un RA, despliega *ICMPv6 Option (Prefix information)* para ver el prefijo y el indicador A, y los *Flags* de la cabecera para M y O; si incluye DNS, aparecerá la opción *Recursive DNS Server*.

## 7.2. Secuencia orientativa

Al activar una interfaz pueden aparecer, según el sistema y el momento:

```text
link-local / DAD
      ↓
RS
      ↓
RA
      ↓
dirección global / DAD
      ↓
(DHCPv6, si M u O lo indican)
      ↓
NS / NA
      ↓
DNS AAAA
      ↓
tráfico IPv6
```

No todas las capturas mostrarán todos los pasos:

- puede haberse recibido un RA antes de iniciar la captura;
- los vecinos pueden estar en caché;
- DNS puede utilizar información almacenada;
- DHCPv6 puede utilizarse o no.

## 7.3. Preguntas de análisis

```text
¿Se observa RS?
¿Se observa RA?
¿Qué dirección utiliza el router?
¿Qué prefijo anuncia?
¿Qué indicadores A, M y O lleva?
¿Se observa NS o NA?
¿Qué vecino se está resolviendo?
¿Existe una consulta AAAA?
¿Existe respuesta?
¿Qué no puede demostrarse desde este punto?
```

## 7.4. Hecho e interpretación

**Hecho**

```text
Se observa un RS.
No se observa RA en esta captura.
```

**Interpretación prudente**

```text
No se ha observado un Router Advertisement
desde este punto de captura.
```

**Conclusión no demostrada**

```text
El router está apagado.
```

La ausencia del paquete puede tener otras explicaciones.

### Ideas clave

- La captura permite relacionar mensajes con funciones.
- El punto y el momento de captura limitan lo que podemos concluir.
- No observar un mensaje no demuestra automáticamente su causa.

# 8. Diagnóstico sistemático de IPv6

Este apartado integra todo lo anterior. Cuando algo falla en IPv6, el objetivo es localizar **qué parte del proceso** no produce el resultado esperado: la dirección, el RA, la ruta, el vecino, el DNS o el servicio. Para ello seguimos el razonamiento de todo el módulo (síntoma → pregunta → hipótesis → prueba → evidencia → conclusión) y, si hay que corregir, un **cambio mínimo** seguido de **verificación**.

| Situación (*scenario*) | Primera evidencia a obtener | Línea de investigación |
|---|---|---|
| **Solo hay link-local** (*link-local only*) | ¿Llega RA? ¿Con qué prefijo e indicadores? | RA, prefijo, SLAAC, DHCPv6 si procede |
| **Global sin ruta por defecto** (*no default route*) | `ip -6 route` / `route print -6` | Recepción de RA, *router lifetime*, configuración manual |
| **Vecino incompleto** (*INCOMPLETE neighbor*) | Neighbor Cache + captura NS/NA | Enlace, dirección, vecino, filtrado |
| **AAAA correcto, servicio inaccesible** (*AAAA OK, service down*) | `ping -6` a la dirección | Ruta, NDP, filtros, servicio |
| **IPv4 funciona, IPv6 no** (*IPv4 OK, IPv6 fails*) | Pruebas separadas por familia | Elementos propios de IPv6 |

No debemos confundir **síntoma** con **causa**: «no hay dirección global» es un síntoma; la causa hay que demostrarla.

## 8.1. Procedimiento inicial

```text
1. comprobar el enlace;
2. comprobar link-local;
3. comprobar dirección global o ULA;
4. revisar DAD y RA;
5. comprobar ruta por defecto;
6. comprobar Neighbor Cache;
7. comprobar DNS AAAA;
8. probar IPv6 por dirección;
9. comparar con IPv4;
10. capturar tráfico si aporta evidencia.
```

No todos los pasos son obligatorios en todos los casos.

## 8.2. Solo existe link-local

Ejemplo:

```text
fe80::...
```

pero no aparece global/ULA cuando debería.

Hecho:

```text
IPv6 está activo y existe link-local.
```

Investigar:

- Router Advertisement;
- prefijo anunciado;
- SLAAC;
- DHCPv6, si forma parte del diseño.

No debe concluirse automáticamente que DHCPv6 ha fallado.

En un laboratorio con router Cisco, una causa frecuente es que falte `ipv6 unicast-routing`: el router tiene direcciones IPv6 pero no envía RA. Es una hipótesis que se comprueba (captura sin RA, `show running-config`), no una conclusión automática.

## 8.3. Dirección global pero sin ruta por defecto

Ejemplo:

```text
dirección global → presente
ruta ::/0        → ausente
```

Conviene revisar:

- recepción de RA;
- información del router (un RA con *router lifetime* 0 anuncia el prefijo pero indica que ese router no debe usarse como predeterminado);
- configuración manual.

## 8.4. Neighbor Cache incompleta

Ejemplo:

```text
fe80::1  INCOMPLETE
```

Hecho:

```text
La resolución del vecino no se ha completado.
```

Posibles líneas de investigación:

- enlace;
- dirección;
- vecino;
- tráfico NDP;
- filtrado o configuración.

## 8.5. AAAA correcto pero servicio inaccesible

```text
AAAA → 2001:db8:100::20
```

DNS ha devuelto una dirección.

Todavía debemos comprobar:

- ruta;
- conectividad;
- Neighbor Discovery;
- filtros;
- servicio.

## 8.6. IPv4 funciona e IPv6 falla

Esto indica que el equipo conserva algún tipo de conectividad, por lo que conviene concentrar la investigación en elementos IPv6:

- dirección;
- RA;
- ruta;
- NDP;
- AAAA;
- políticas IPv6.

## 8.7. Documentar y verificar

Plantilla:

## 8.8. Uso responsable de asistentes de IA

Un asistente puede ayudar a:

- explicar salidas;
- diferenciar RS, RA, NS y NA;
- proponer filtros;
- formular hipótesis;
- estructurar un informe.

Debe verificarse que no:

- confunda NDP con ARP;
- atribuya el gateway a DHCPv6;
- suponga que SLAAC siempre incorpora una MAC;
- convierta una ausencia de paquete en una causa confirmada;
- ignore el punto de captura.

No deben compartirse capturas o configuraciones reales sensibles sin autorización.

## 8.9. Caso integrado dual stack

Escenario:

```text
IPv4:
  dirección correcta
  gateway correcto
  DNS A correcto
  conectividad → funciona

IPv6:
  link-local → presente
  global     → presente
  ::/0       → ausente
  AAAA       → correcto
  ping -6 remoto → falla
```

No debemos concluir:

```text
"Internet funciona"
→ "IPv6 funciona"
```

porque IPv4 puede estar ocultando el fallo.

Procedimiento:

```text
1. separar las dos familias;
2. confirmar los hechos IPv6;
3. comprobar de dónde debería proceder la ruta por defecto;
4. buscar Router Advertisement;
5. verificar después de corregir.
```

La hipótesis principal puede apuntar a RA/ruta por defecto, pero debe contrastarse.

Otro escenario:

```text
link-local → presente
global     → ausente
RA         → visible
prefijo    → anunciado
DAD        → fallo
```

Aquí el problema no es simplemente «no llega RA». La captura demuestra que sí llega información del router y orienta la investigación hacia la generación/validación de la dirección (por ejemplo, otro equipo con la misma dirección configurada a mano).

### Regla operativa

En dual stack:

```text
aplicación funciona
≠
IPv4 e IPv6 funcionan
```

Cuando el diagnóstico dependa de la familia IP, probar ambas de forma explícita.

### Ideas clave

- Link-local, dirección global, ruta, vecino y DNS son evidencias distintas.
- IPv4 puede ocultar un fallo IPv6.
- Toda corrección debe terminar con una nueva verificación.

## Anexo A. Glosario esencial

| Español | English technical term | Significado |
|---|---|---|
| Dirección IPv6 | IPv6 address | Dirección lógica de 128 bits |
| Hexteto | hextet | Grupo hexadecimal de 16 bits |
| Prefijo | prefix | Parte que identifica la red |
| ID de subred | subnet ID | Bits que numeran las LAN dentro del bloque de la organización |
| Identificador de interfaz | interface ID (IID) | 64 bits finales que identifican la interfaz en la LAN |
| EUI-64 | modified EUI-64 | IID generado a partir de la MAC (inserta `ff:fe` e invierte el bit U/L) |
| Dirección temporal | temporary address | Dirección aleatoria que cambia periódicamente, por privacidad |
| Link-local | link-local | Dirección válida dentro del enlace |
| Global unicast | global unicast | Dirección con alcance potencialmente global |
| ULA | Unique Local Address | Dirección para redes internas |
| Dirección no especificada | unspecified address | `::`, usada cuando aún no hay dirección (DAD) |
| Multicast | multicast | Dirección utilizada para comunicarse con grupos |
| Multicast solicited-node | solicited-node multicast | Grupo al que se envían los NS |
| Router Solicitation | RS | Solicitud de información a routers |
| Router Advertisement | RA | Anuncio de información de red |
| Indicadores A, M, O | A, M, O flags | Indican SLAAC, dirección por DHCPv6 u otros parámetros por DHCPv6 |
| SLAAC | Stateless Address Autoconfiguration | Autoconfiguración basada en prefijos anunciados |
| DAD | Duplicate Address Detection | Comprobación de posible dirección duplicada |
| Neighbor Solicitation | NS | Solicitud relacionada con un vecino |
| Neighbor Advertisement | NA | Respuesta relacionada con un vecino |
| Neighbor Cache | Neighbor Cache | Información almacenada sobre vecinos IPv6 |
| ICMPv6 | ICMPv6 | Protocolo esencial para control, NDP y diagnóstico |
| DHCPv6 stateless | stateless DHCPv6 | DHCPv6 proporciona otros parámetros, no la dirección SLAAC |
| DHCPv6 stateful | stateful DHCPv6 | DHCPv6 puede proporcionar la dirección |
| RDNSS | Recursive DNS Server | Información DNS incluida en Router Advertisement |
| Registro AAAA | AAAA record | Registro DNS que contiene una dirección IPv6 |
| Dual stack | dual stack | Uso simultáneo de IPv4 e IPv6 |
