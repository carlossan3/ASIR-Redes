title: "U05 — IPv6 y autoconfiguración"
---

> **Pregunta guía:** ¿Cómo obtiene un host su configuración IPv6, de dónde procede cada parámetro y qué evidencias permiten comprobar que IPv6 funciona realmente?

En U04 aprendimos a interpretar direccionamiento IPv4, prefijos, gateway, subnetting, VLSM, CIDR y DHCP. IPv6 conserva la idea de **dirección + prefijo**, pero cambia de forma importante el funcionamiento de la red local y la autoconfiguración.

Una interfaz IPv6 puede utilizar varias direcciones al mismo tiempo. Los routers anuncian información mediante **Router Advertisement (RA)**; un host puede generar direcciones mediante **SLAAC**, comprobar duplicidades mediante **Duplicate Address Detection (DAD)** y descubrir vecinos mediante **Neighbor Discovery Protocol (NDP)**. DHCPv6 puede participar en la configuración, pero **no proporciona el router predeterminado**.

La idea central de esta unidad es aprender a interpretar IPv6 como un sistema de mecanismos relacionados y a diagnosticarlo mediante evidencias observables:

```text
configuración
→ tipo y alcance de dirección
→ prefijo
→ origen de los parámetros
→ RA / SLAAC / DAD
→ NDP
→ ruta por defecto
→ DNS
→ prueba IPv6
→ captura si aporta evidencia
→ conclusión
```

## Al finalizar esta unidad deberías ser capaz de

- leer, expandir y comprimir direcciones IPv6;
- reconocer global unicast, link-local, ULA, loopback, multicast y prefijos de documentación;
- planificar varios `/64` a partir de un bloque padre;
- explicar la función de link-local, RS, RA, SLAAC y DAD;
- diferenciar RS, RA, NS y NA;
- interpretar una Neighbor Cache básica;
- diferenciar SLAAC, DHCPv6 stateless, DHCPv6 stateful y RDNSS;
- explicar de dónde pueden proceder dirección, prefijo, router predeterminado y DNS;
- interpretar registros DNS `AAAA`;
- verificar IPv6 y distinguirlo de IPv4 en un entorno dual stack;
- utilizar Wireshark para observar ICMPv6, NDP, DHCPv6 y DNS;
- diagnosticar fallos IPv6 mediante pruebas y evidencias, evitando conclusiones basadas únicamente en síntomas.

# 1. Leer y escribir direcciones IPv6

## 1.1. Una interfaz puede tener varias direcciones

En IPv6 es normal que una interfaz utilice varias direcciones al mismo tiempo.

Ejemplo:

```text
Interfaz: Ethernet

Direcciones:
  fe80::a00:27ff:fe12:3456/64
  2001:db8:10:20::25/64

Ruta:
  default via fe80::1

DNS:
  2001:db8:53::53
```

En este ejemplo aparecen:

- una dirección **link-local**;
- una dirección del prefijo `2001:db8:10:20::/64`;
- una ruta predeterminada cuyo siguiente salto es link-local;
- un servidor DNS accesible mediante IPv6.

No debemos buscar «la dirección IPv6» de un host como si necesariamente existiera una sola.

## 1.2. Estructura de una dirección

IPv6 utiliza direcciones de **128 bits**, representadas mediante ocho grupos hexadecimales de 16 bits o **hextetos**.

Forma completa:

```text
2001:0db8:0010:0020:0000:0000:0000:0042
```

### Eliminar ceros iniciales

Los ceros a la izquierda de cada hexteto pueden omitirse:

```text
2001:db8:10:20:0:0:0:42
```

### Utilizar `::`

Una secuencia continua de hextetos `0` puede sustituirse por `::`:

```text
2001:db8:10:20::42
```

`::` solo puede aparecer una vez en una dirección.

## 1.3. Expandir una dirección

Ejemplo:

```text
2001:db8:10::25
```

Forma expandida:

```text
2001:0db8:0010:0000:0000:0000:0000:0025
```

Procedimiento:

1. contar los hextetos visibles;
2. localizar `::`;
3. añadir los grupos `0000` necesarios hasta completar ocho;
4. completar cada hexteto con cuatro dígitos.

## 1.4. Tipos y alcances que debemos reconocer

| Tipo | Prefijo o ejemplo | Uso básico |
|---|---|---|
| **Global unicast** | principalmente `2000::/3` | Comunicación con alcance potencialmente global |
| **Link-local** | `fe80::/10` | Comunicación dentro del enlace |
| **ULA** | `fc00::/7`, habitualmente `fd00::/8` | Redes internas |
| **Loopback** | `::1/128` | El propio host |
| **Multicast** | `ff00::/8` | Comunicación dirigida a grupos |
| **Documentación** | `2001:db8::/32` | Ejemplos y prácticas |

IPv6 no utiliza broadcast como IPv4. Muchas funciones utilizan **multicast**.

## 1.5. Dirección y prefijo

Ejemplo:

```text
2001:db8:10:20::25/64
```

Dirección:

```text
2001:db8:10:20::25
```

Prefijo de la LAN:

```text
2001:db8:10:20::/64
```

En esta unidad trabajaremos normalmente con redes LAN `/64`.

### Ideas clave

- Una interfaz IPv6 puede utilizar varias direcciones.
- Dirección y prefijo deben interpretarse conjuntamente.
- La escritura comprimida no cambia la dirección: solo cambia su representación.

# 2. Planificación sencilla de prefijos

En IPv6 la planificación de una LAN no consiste en ahorrar direcciones de host. Se organiza el espacio mediante **prefijos**.

## 2.1. El `/64` de una LAN

Ejemplo:

```text
2001:db8:1200:20::25/64
```

La subred es:

```text
2001:db8:1200:20::/64
```

En esta unidad las LAN se diseñarán normalmente como `/64`.

## 2.2. Crear `/64` desde un bloque padre

Supongamos que una organización dispone de:

```text
2001:db8:1200::/48
```

Podemos asignar varios `/64`:

| Uso | Prefijo |
|---|---|
| Usuarios | `2001:db8:1200:10::/64` |
| Wi‑Fi | `2001:db8:1200:20::/64` |
| Servidores | `2001:db8:1200:30::/64` |
| Gestión | `2001:db8:1200:40::/64` |
| Laboratorio | `2001:db8:1200:50::/64` |

La parte comprendida entre `/48` y `/64` permite identificar subredes.

No trasladaremos aquí el modelo VLSM de U04 basado en necesidades mínimas de hosts. En IPv6, el objetivo de una LAN no es ahorrar unas pocas direcciones, sino organizar de forma coherente el espacio de prefijos; por ello trabajaremos normalmente con `/64`.

## 2.3. Documentar el plan

Un plan sencillo debe ser:

- coherente;
- legible;
- ampliable;
- documentado.

Ejemplo:

| Prefijo | Uso | Método previsto |
|---|---|---|
| `2001:db8:1200:10::/64` | Usuarios | SLAAC |
| `2001:db8:1200:20::/64` | Wi‑Fi | SLAAC |
| `2001:db8:1200:30::/64` | Servidores | Según diseño |

### Ideas clave

- En LAN IPv6 trabajaremos normalmente con `/64`.
- La planificación consiste en organizar prefijos de forma coherente.
- Un bloque padre puede proporcionar numerosos `/64`.

# 3. Link-local, Router Advertisement, SLAAC y DAD

La autoconfiguración IPv6 utiliza varios mecanismos coordinados.

## 3.1. Dirección link-local

Cuando IPv6 está habilitado, una interfaz genera normalmente una dirección **link-local**.

Ejemplo:

```text
fe80::a00:27ff:fe12:3456
```

Una dirección link-local:

- funciona únicamente en el enlace;
- permite comunicarse con routers y vecinos;
- participa en Neighbor Discovery;
- puede utilizarse como dirección del siguiente salto.

Por eso es normal observar:

```text
default via fe80::1
```

como ruta predeterminada.

## 3.2. Router Solicitation y Router Advertisement

Un host puede enviar un **Router Solicitation (RS)** para solicitar información a los routers del enlace.

El router responde o anuncia periódicamente mediante un **Router Advertisement (RA)**.

```text
Host                         Router

RS ------------------------->
                  <----------- RA
```

Un RA puede indicar:

- qué prefijos están disponibles;
- si un prefijo puede utilizarse para SLAAC;
- que el emisor puede actuar como router predeterminado;
- otros parámetros de configuración.

> El router predeterminado IPv6 se aprende normalmente mediante **RA**, no mediante DHCPv6.

## 3.3. SLAAC

**SLAAC** (*Stateless Address Autoconfiguration*) permite que un host genere una dirección utilizando un prefijo anunciado.

Proceso conceptual:

```text
link-local
    ↓
RS / RA
    ↓
prefijo anunciado
    ↓
generación de dirección
    ↓
DAD
    ↓
dirección utilizable
```

Los sistemas actuales pueden generar el identificador de interfaz de diferentes formas. No debemos asumir que una dirección SLAAC contiene siempre la MAC del dispositivo.

## 3.4. DAD

**DAD** (*Duplicate Address Detection*) intenta comprobar que una dirección no está siendo utilizada ya en el enlace.

Mientras se realiza, la dirección puede aparecer como:

```text
tentative
```

Si no se detecta conflicto, puede pasar a utilizarse normalmente.

## 3.5. Indicadores A, M y O

En los Router Advertisement pueden aparecer indicadores que ayudan al host a decidir cómo configurarse:

- **A**: el prefijo puede utilizarse para SLAAC;
- **M**: puede utilizarse DHCPv6 para obtener una dirección;
- **O**: DHCPv6 puede proporcionar otros parámetros.

En esta unidad basta con interpretar su función general.

### Ideas clave

- Link-local aparece antes de necesitar conectividad global.
- RS solicita información y RA la anuncia.
- SLAAC permite generar una dirección.
- DAD intenta detectar duplicidades.
- El gateway IPv6 se aprende mediante RA.

# 4. Neighbor Discovery e ICMPv6

IPv6 utiliza **Neighbor Discovery Protocol (NDP)** para varias funciones necesarias de la red local.

NDP utiliza **ICMPv6**.

## 4.1. Mensajes principales

| Mensaje | Abreviatura | Función |
|---|---|---|
| Router Solicitation | **RS** | Solicitar información a routers |
| Router Advertisement | **RA** | Anunciar información de red |
| Neighbor Solicitation | **NS** | Solicitar información sobre un vecino |
| Neighbor Advertisement | **NA** | Responder sobre un vecino |

Para filtros de Wireshark conviene reconocer también:

```text
133 → RS
134 → RA
135 → NS
136 → NA
```

No es necesario memorizar muchos más tipos en esta unidad.

## 4.2. NS y NA: resolver vecinos

En IPv4 utilizamos ARP para relacionar IPv4 y MAC dentro del enlace.

En IPv6 esa función forma parte de NDP.

```text
Host A                         Host B

NS --------------------------->
                   <----------- NA
```

En Ethernet, los mensajes NS utilizan multicast IPv6 para localizar al vecino. En herramientas o recursos técnicos puede aparecer el término **solicited-node multicast**. En esta unidad basta con reconocer su función; no es necesario calcular esas direcciones multicast.

El resultado puede almacenarse en la **Neighbor Cache**.

## 4.3. Neighbor Cache

Estados que conviene reconocer:

| Estado | Interpretación inicial |
|---|---|
| **REACHABLE** | Existe evidencia reciente de alcanzabilidad |
| **STALE** | Existe una entrada, pero puede requerir nueva confirmación |
| **INCOMPLETE** | La resolución todavía no se ha completado |
| **FAILED** | La resolución no se completó correctamente |

Una entrada `INCOMPLETE` no indica por sí sola la causa del problema. Debe investigarse el enlace, la dirección, el vecino y el tráfico NDP.

## 4.4. ICMPv6 es esencial

ICMPv6 participa en:

- RS y RA;
- NS y NA;
- DAD;
- mensajes de error;
- `ping`.

Por ello, no debe considerarse simplemente «el protocolo de ping».

Bloquear ICMPv6 de forma indiscriminada puede impedir funciones necesarias de IPv6.

## 4.5. Comparación inicial con IPv4

| IPv4 | IPv6 |
|---|---|
| ARP Request / Reply | NS / NA |
| Caché ARP | Neighbor Cache |
| Gateway configurado o recibido mediante DHCPv4 | Router aprendido mediante RA |
| ICMP para control y diagnóstico | ICMPv6 también soporta NDP y autoconfiguración |

### Ideas clave

- NDP realiza más funciones que ARP.
- NS y NA permiten resolver vecinos.
- La Neighbor Cache aporta evidencias sobre el enlace.
- ICMPv6 forma parte del funcionamiento básico de IPv6.

# 5. SLAAC, DHCPv6, RDNSS y DNS AAAA

En IPv6 no existe necesariamente un único mecanismo que entregue todos los parámetros de configuración.

## 5.1. ¿De dónde puede proceder cada parámetro?

| Parámetro | Posible origen |
|---|---|
| Link-local | El propio host |
| Dirección global / ULA | SLAAC, DHCPv6 o configuración manual |
| Prefijo | Router Advertisement o configuración manual |
| Router predeterminado | Router Advertisement |
| DNS | RDNSS, DHCPv6 o configuración manual |

Esta tabla es fundamental para diagnosticar IPv6.

## 5.2. DHCPv6 stateless

En un diseño **stateless**:

```text
SLAAC   → dirección IPv6
DHCPv6  → otros parámetros
```

Por ejemplo, DHCPv6 puede proporcionar información DNS.

## 5.3. DHCPv6 stateful

En un diseño **stateful**, DHCPv6 puede proporcionar una dirección al cliente.

Sin embargo, el router predeterminado continúa aprendiéndose mediante RA.

| Mecanismo | Dirección | Gateway |
|---|---|---|
| SLAAC | SLAAC | RA |
| DHCPv6 stateless | SLAAC | RA |
| DHCPv6 stateful | DHCPv6 | RA |

## 5.4. RDNSS

Un Router Advertisement puede proporcionar información DNS mediante **RDNSS**.

Por tanto:

```text
SLAAC
```

no significa:

```text
sin DNS
```

El origen concreto depende del diseño.

## 5.5. Registros AAAA

Un registro **AAAA** relaciona un nombre con una dirección IPv6.

Ejemplo:

```text
srv.example.  AAAA  2001:db8:100::20
```

Herramientas de consulta:

```text
nslookup
dig AAAA
Resolve-DnsName -Type AAAA
```

Un AAAA correcto demuestra que DNS ha devuelto una dirección IPv6. No demuestra que exista conectividad hacia ella ni que el servicio esté disponible.

### Ideas clave

- Dirección, gateway y DNS pueden tener orígenes diferentes.
- DHCPv6 no proporciona el gateway predeterminado.
- SLAAC y DHCPv6 pueden coexistir.
- Un registro AAAA correcto no garantiza conectividad.

# 6. Verificación y dual stack

Una configuración IPv6 debe comprobarse por partes.

## 6.1. Qué debemos consultar

| Objetivo | Windows | Linux |
|---|---|---|
| Direcciones | `ipconfig` / PowerShell | `ip -6 address` |
| Rutas | PowerShell | `ip -6 route` |
| Vecinos | PowerShell | `ip -6 neigh` |
| DNS AAAA | `nslookup` / PowerShell | `dig AAAA` |
| ICMPv6 | `ping -6` | `ping -6` |

No es necesario memorizar todas las variantes. Debemos saber **qué información buscamos y cómo interpretarla**.

## 6.2. Comprobación mínima

Una secuencia útil es:

```text
1. ¿Existe link-local?
2. ¿Existe global o ULA cuando debería?
3. ¿DAD ha finalizado?
4. ¿Existe ruta por defecto?
5. ¿Se conoce al router como vecino?
6. ¿Existe DNS?
7. ¿Existe un AAAA cuando corresponde?
8. ¿Funciona IPv6 por dirección?
9. ¿Responde el servicio?
```

El síntoma determinará qué pasos son necesarios.

## 6.3. Dual stack

En **dual stack**, IPv4 e IPv6 funcionan simultáneamente.

Ejemplo:

```text
IPv4:
192.0.2.10/24

IPv6:
2001:db8:10:20::10/64
```

Dual stack no significa que cada paquete se envíe dos veces.

Una aplicación puede terminar utilizando IPv4 o IPv6 según la resolución, la conectividad y el comportamiento del sistema.

## 6.4. Probar cada familia por separado

Para evitar que una familia oculte el fallo de la otra:

```text
ping -4 example.net
ping -6 example.net
```

Podemos encontrar:

```text
IPv4 funciona
IPv6 falla
```

o lo contrario.

Si una web funciona, eso no demuestra por sí solo que IPv6 esté funcionando.

## 6.5. Comparación IPv4 / IPv6

| Función | IPv4 | IPv6 |
|---|---|---|
| Dirección LAN | Dirección + prefijo | Dirección + prefijo |
| Resolución de vecino | ARP | NDP |
| Configuración automática | DHCPv4 | SLAAC y/o DHCPv6 |
| Router predeterminado | Manual/DHCPv4 | RA |
| Registro DNS | A | AAAA |
| Broadcast | Sí | No; utiliza multicast para muchas funciones |

### Ideas clave

- IPv4 e IPv6 pueden fallar de forma independiente.
- Una aplicación funcionando no demuestra qué familia utilizó.
- El diagnóstico dual stack requiere probar ambas familias por separado.

# 7. Captura de tráfico IPv6 con Wireshark

Wireshark permite observar la autoconfiguración y Neighbor Discovery.

## 7.1. Filtros básicos

```text
ipv6
icmpv6
dhcpv6
```

Para NDP:

```text
icmpv6.type == 133   # RS
icmpv6.type == 134   # RA
icmpv6.type == 135   # NS
icmpv6.type == 136   # NA
```

Para consultas AAAA:

```text
dns.qry.type == 28
```

## 7.2. Secuencia orientativa

Al activar una interfaz pueden aparecer, según el sistema y el momento:

```text
link-local / DAD
      ↓
RS
      ↓
RA
      ↓
dirección global / DAD
      ↓
NS / NA
      ↓
DNS AAAA
      ↓
tráfico IPv6
```

No todas las capturas mostrarán todos los pasos:

- puede haberse recibido un RA antes de iniciar la captura;
- los vecinos pueden estar en caché;
- DNS puede utilizar información almacenada;
- DHCPv6 puede utilizarse o no.

## 7.3. Preguntas de análisis

```text
¿Se observa RS?
¿Se observa RA?
¿Qué dirección utiliza el router?
¿Qué prefijo anuncia?
¿Se observa NS o NA?
¿Qué vecino se está resolviendo?
¿Existe una consulta AAAA?
¿Existe respuesta?
¿Qué no puede demostrarse desde este punto?
```

## 7.4. Hecho e interpretación

**Hecho**

```text
Se observa un RS.
No se observa RA en esta captura.
```

**Interpretación prudente**

```text
No se ha observado un Router Advertisement
desde este punto de captura.
```

**Conclusión no demostrada**

```text
El router está apagado.
```

La ausencia del paquete puede tener otras explicaciones.

### Ideas clave

- La captura permite relacionar mensajes con funciones.
- El punto y el momento de captura limitan lo que podemos concluir.
- No observar un mensaje no demuestra automáticamente su causa.

# 8. Diagnóstico sistemático de IPv6

El diagnóstico debe identificar qué parte del proceso no produce el resultado esperado.

## 8.1. Procedimiento inicial

```text
1. comprobar el enlace;
2. comprobar link-local;
3. comprobar dirección global o ULA;
4. revisar DAD y RA;
5. comprobar ruta por defecto;
6. comprobar Neighbor Cache;
7. comprobar DNS AAAA;
8. probar IPv6 por dirección;
9. comparar con IPv4;
10. capturar tráfico si aporta evidencia.
```

No todos los pasos son obligatorios en todos los casos.

## 8.2. Solo existe link-local

Ejemplo:

```text
fe80::...
```

pero no aparece global/ULA cuando debería.

Hecho:

```text
IPv6 está activo y existe link-local.
```

Investigar:

- Router Advertisement;
- prefijo anunciado;
- SLAAC;
- DHCPv6, si forma parte del diseño.

No debe concluirse automáticamente que DHCPv6 ha fallado.

## 8.3. Dirección global pero sin ruta por defecto

Ejemplo:

```text
dirección global → presente
ruta ::/0        → ausente
```

Conviene revisar:

- recepción de RA;
- información del router;
- configuración manual.

## 8.4. Neighbor Cache incompleta

Ejemplo:

```text
fe80::1  INCOMPLETE
```

Hecho:

```text
La resolución del vecino no se ha completado.
```

Posibles líneas de investigación:

- enlace;
- dirección;
- vecino;
- tráfico NDP;
- filtrado o configuración.

## 8.5. AAAA correcto pero servicio inaccesible

```text
AAAA → 2001:db8:100::20
```

DNS ha devuelto una dirección.

Todavía debemos comprobar:

- ruta;
- conectividad;
- Neighbor Discovery;
- filtros;
- servicio.

## 8.6. IPv4 funciona e IPv6 falla

Esto indica que el equipo conserva algún tipo de conectividad, por lo que conviene concentrar la investigación en elementos IPv6:

- dirección;
- RA;
- ruta;
- NDP;
- AAAA;
- políticas IPv6.

## 8.7. Documentar y verificar

Plantilla:

```text
Síntoma:
Interfaz:

Link-local:
Global/ULA:
DAD:
Ruta ::/0:
Router:
Neighbor Cache:
DNS AAAA:

Prueba IPv6:
Prueba IPv4:

Hechos:
Hipótesis:
Siguiente prueba:

Corrección:
Verificación:
Conclusión:
```

## 8.8. Uso responsable de asistentes de IA

Un asistente puede ayudar a:

- explicar salidas;
- diferenciar RS, RA, NS y NA;
- proponer filtros;
- formular hipótesis;
- estructurar un informe.

Debe verificarse que no:

- confunda NDP con ARP;
- atribuya el gateway a DHCPv6;
- suponga que SLAAC siempre incorpora una MAC;
- convierta una ausencia de paquete en una causa confirmada;
- ignore el punto de captura.

No deben compartirse capturas o configuraciones reales sensibles sin autorización.


## 8.9. Caso integrado dual stack

Escenario:

```text
IPv4:
  dirección correcta
  gateway correcto
  DNS A correcto
  conectividad → funciona

IPv6:
  link-local → presente
  global     → presente
  ::/0       → ausente
  AAAA       → correcto
  ping -6 remoto → falla
```

No debemos concluir:

```text
"Internet funciona"
→ "IPv6 funciona"
```

porque IPv4 puede estar ocultando el fallo.

Procedimiento:

```text
1. separar las dos familias;
2. confirmar los hechos IPv6;
3. comprobar de dónde debería proceder la ruta por defecto;
4. buscar Router Advertisement;
5. verificar después de corregir.
```

La hipótesis principal puede apuntar a RA/ruta por defecto, pero debe contrastarse.

Otro escenario:

```text
link-local → presente
global     → ausente
RA         → visible
prefijo    → anunciado
DAD        → fallo
```

Aquí el problema no es simplemente «no llega RA». La captura demuestra que sí llega información del router y orienta la investigación hacia la generación/validación de la dirección.

### Regla operativa

En dual stack:

```text
aplicación funciona
≠
IPv4 e IPv6 funcionan
```

Cuando el diagnóstico dependa de la familia IP, probar ambas de forma explícita.


### Ideas clave

- Link-local, dirección global, ruta, vecino y DNS son evidencias distintas.
- IPv4 puede ocultar un fallo IPv6.
- Toda corrección debe terminar con una nueva verificación.

| Neighbor Advertisement | NA | Respuesta relacionada con un vecino |
