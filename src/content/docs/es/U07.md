> **Pregunta guía:** ¿Cómo se segmenta una red local y cómo se comunican después los segmentos?

## Introducción

Una red local puede utilizar muchos switches y, aun así, comportarse como un único dominio de capa 2. Esto resulta cómodo cuando la red es pequeña, pero genera problemas cuando crece: todos los equipos reciben determinados broadcasts, distintas funciones comparten el mismo espacio lógico y la infraestructura se vuelve más difícil de organizar.

Una **VLAN — Virtual LAN** permite dividir una infraestructura física de switching en varios dominios lógicos de capa 2.

La idea central de esta unidad es:

```text
misma infraestructura física
+
segmentación lógica
=
varias redes de capa 2 independientes
```

Pero una VLAN no es simplemente un número configurado en un switch. Para que el diseño funcione deben mantenerse coherentes varios elementos:

```text
función
→ VLAN
→ puerto
→ trunk
→ subred
→ gateway
→ routing
→ documentación
```

Durante toda la unidad debemos mantener separadas tres ideas:

```text
VLAN ≠ subred ≠ política de seguridad
```

- una **VLAN** define separación lógica de capa 2;
- una **subred IP** define un dominio de direccionamiento de capa 3;
- una **política de seguridad** decide qué tráfico se permite o bloquea.

Habitualmente una VLAN de usuarios se asocia a una subred IP, pero ambas cosas pertenecen a capas distintas y no deben confundirse.

La unidad se organiza en tres bloques:

| Bloque | Apartados | Pregunta que responde |
|---|---|---|
| **Segmentar** (*segmentation*) | 1–3 | ¿Por qué dividir la red y cómo coloco cada equipo en su VLAN? |
| **Transportar** (*VLAN transport*) | 4–8 | ¿Cómo viajan varias VLAN entre switches y cómo se mantiene la coherencia? |
| **Comunicar y operar** (*inter-VLAN routing and operations*) | 9–13 | ¿Cómo se comunican las VLAN, cómo se documenta el despliegue y cómo se diagnostica? |

Los apartados 14–18 son de consulta: comandos, errores frecuentes, síntesis, glosario y mapa de diagnóstico.

# 1. De una red plana a una red segmentada

Este apartado explica **por qué** existen las VLAN antes de ver ningún comando. Partimos de una red «plana», en la que todos los equipos comparten el mismo dominio de capa 2, y vemos qué problemas plantea cuando crece. Después introducimos la VLAN como solución y la situamos respecto a otros dos conceptos con los que se confunde a menudo: la subred IP y la seguridad.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Red plana** (*flat network*) | ¿Qué ocurre si todos los equipos comparten un único dominio L2? | Administración, alumnado y servidores reciben los mismos broadcasts |
| **VLAN** (*Virtual LAN*) | ¿Cómo separo lógicamente equipos conectados a la misma infraestructura? | VLAN 10 ADMIN, VLAN 20 USERS |
| **Dominio de difusión** (*broadcast domain*) | ¿Hasta dónde llega un broadcast? | Un broadcast de VLAN 20 no llega a VLAN 10 |
| **Subred** (*subnet*) | ¿Qué direccionamiento IP usa cada VLAN? | VLAN 20 ↔ `10.10.20.0/24` |
| **Segmentación frente a autorización** (*segmentation vs. authorization*) | ¿Separar equipos basta para decidir qué tráfico se permite? | No: hacen falta ACL o firewall (U08) |
| **Ventajas y límites** (*benefits and limitations*) | ¿Qué gano y qué no gano al usar VLAN? | Menos broadcast, organización por función |
| **Tipos de VLAN** (*VLAN types*) | ¿Qué papeles puede tener una VLAN en el diseño? | Datos, voz, gestión, nativa, por defecto |
| **Matriz VLAN** (*VLAN matrix*) | ¿Cómo documento el diseño antes de configurar? | Tabla VLAN–nombre–subred–gateway |

No debemos confundir **separar** (VLAN, capa 2), **direccionar** (subred, capa 3) y **autorizar** (política de seguridad): se diseñan juntas, pero son decisiones distintas.

## 1.1. Qué ocurre en una red plana

Supongamos una organización con:

- Administración;
- alumnado;
- servidores;
- telefonía IP;
- dispositivos de gestión.

Si todos los equipos pertenecen al mismo dominio de capa 2, determinados broadcasts pueden propagarse por toda esa red lógica.

Además, el diseño no expresa ninguna separación entre funciones.

```text
PC Administración ─┐
PC Usuarios ────────┼── switching LAN ── Servidores
Teléfono IP ────────┤
Gestión ────────────┘
```

La pregunta no es únicamente «¿funciona?», sino:

> ¿es razonable que todos estos sistemas pertenezcan al mismo dominio lógico?

## 1.2. Una VLAN crea un dominio lógico de capa 2

Cuando configuramos VLAN, un mismo switch físico puede participar en varios dominios de broadcast separados.

Ejemplo:

```text
VLAN 10 → ADMIN
VLAN 20 → USERS
VLAN 30 → SERVERS
VLAN 40 → VOICE
VLAN 99 → MGMT
```

Los equipos de VLAN 10 no comparten el mismo dominio de broadcast de capa 2 que los de VLAN 20.

Esto permite organizar la red de acuerdo con funciones o requisitos.

## 1.3. VLAN y dominio de broadcast

Una VLAN delimita un **broadcast domain** de capa 2.

Si un host de VLAN 20 emite un broadcast Ethernet, el switch lo reenvía dentro de los puertos que pertenecen a esa VLAN y por los trunks que transportan esa VLAN.

No debe aparecer automáticamente en VLAN 10, 30 o 40.

Lo mismo ocurre con las tramas unicast desconocidas (*unknown unicast*) que el switch inunda: la inundación queda limitada a los puertos de la VLAN.

## 1.4. VLAN y subred

En un diseño típico se utiliza una subred distinta para cada VLAN.

Ejemplo:

| VLAN | Función | Subred | Gateway |
|---:|---|---|---|
| 10 | ADMIN | `10.10.10.0/24` | `10.10.10.1` |
| 20 | USERS | `10.10.20.0/24` | `10.10.20.1` |
| 30 | SERVERS | `10.10.30.0/24` | `10.10.30.1` |
| 40 | VOICE | `10.10.40.0/24` | `10.10.40.1` |
| 99 | MGMT | `10.10.99.0/24` | `10.10.99.1` |

Esta asociación facilita diseño, routing, documentación y diagnóstico.

Pero debemos evitar una afirmación imprecisa:

> «Una VLAN es una subred».

No lo es.

Una VLAN es capa 2; una subred es capa 3.

## 1.5. VLAN y seguridad

Separar equipos en VLAN diferentes **no define por sí mismo una política completa de seguridad**.

La segmentación puede ayudar a reducir exposición y organizar controles, pero la decisión sobre qué tráfico se permite entre redes requiere mecanismos de capa 3 o superiores, como ACL o firewalls (U08).

Por eso:

```text
segmentación ≠ autorización
```

## 1.6. Ventajas y límites de las VLAN

Las VLAN se usan en casi todas las redes profesionales porque aportan varias ventajas a la vez:

| Ventaja | Qué significa | Ejemplo |
|---|---|---|
| **Menos tráfico de difusión** (*smaller broadcast domains*) | Cada broadcast solo llega a los equipos de su VLAN | Un ARP de USERS no molesta a SERVERS |
| **Organización por función** (*logical grouping*) | Se agrupan equipos por función, no por ubicación física | Profesorado de tres plantas en la misma VLAN |
| **Base para la seguridad** (*security foundation*) | Crea fronteras donde aplicar controles | ACL entre USERS y SERVERS en el gateway (U08) |
| **Menor coste** (*cost reduction*) | Varias redes lógicas con los mismos switches y cables | No hace falta un switch por departamento |
| **Administración más sencilla** (*easier management*) | Mover a un usuario es cambiar la VLAN de un puerto | Cambio de despacho sin recablear |
| **Políticas por grupo** (*per-group policies*) | Tratamiento distinto para cada tipo de tráfico | VLAN de voz separada de la de datos |

También tienen **límites** que conviene conocer desde el principio:

- las VLAN distintas **no se comunican** sin un dispositivo de capa 3 (apartado 9);
- añaden **complejidad**: más elementos que deben ser coherentes (puertos, trunks, gateways);
- un error de configuración puede dejar sin servicio a una VLAN entera;
- mal configuradas pueden ser atacadas (por ejemplo, *VLAN hopping*, apartado 6.7): la VLAN **no sustituye** a la política de seguridad.

## 1.7. Tipos de VLAN según su función

En un diseño se habla de VLAN con papeles distintos. No son «clases» técnicas diferentes, sino **usos** dentro del diseño:

| Tipo | Función | Recomendación habitual |
|---|---|---|
| **VLAN por defecto** (*default VLAN*) | VLAN 1 en Cisco: al principio todos los puertos pertenecen a ella | No usarla para usuarios ni gestión; no se puede borrar ni renombrar |
| **VLAN de datos** (*data VLAN*, *user VLAN*) | Tráfico de los usuarios y servidores | Una por función: ADMIN, USERS, SERVERS… |
| **VLAN de voz** (*voice VLAN*) | Tráfico de telefonía IP | Separada de datos (apartado 3) |
| **VLAN de gestión** (*management VLAN*) | Acceso de administración a los equipos de red | VLAN dedicada, p. ej. 99 (apartado 11) |
| **VLAN nativa** (*native VLAN*) | Tráfico sin etiqueta en un trunk 802.1Q | VLAN sin usuarios, p. ej. 999 (apartado 6) |
| **VLAN «aparcamiento»** (*parking / black-hole VLAN*) | Destino de los puertos no utilizados | VLAN sin gateway y puertos en `shutdown` (apartado 6.7) |

## 1.8. Diseñar antes de configurar

Antes de escribir comandos conviene elaborar una matriz VLAN.

| VLAN | Nombre | Función | Subred | Gateway |
|---:|---|---|---|---|
| 10 | ADMIN | Administración | `10.10.10.0/24` | `10.10.10.1` |
| 20 | USERS | Usuarios | `10.10.20.0/24` | `10.10.20.1` |
| 30 | SERVERS | Servidores | `10.10.30.0/24` | `10.10.30.1` |

La configuración debería ser consecuencia del diseño, no al revés.

### Idea clave

> Una VLAN es una decisión de arquitectura de capa 2, no solamente un identificador numérico.

# 2. Crear VLAN y configurar puertos access

Una vez diseñada la matriz, hay que llevarla al switch. Este apartado cubre los dos pasos básicos —**crear** la VLAN y **asignar** puertos a ella— y, sobre todo, cómo **comprobar** que el estado del switch coincide con el diseño. También veremos dónde guarda el switch las VLAN y qué ocurre si se borra una VLAN que todavía tiene puertos.

| Concepto | Pregunta que responde | Comando / ejemplo |
|---|---|---|
| **Crear y nombrar una VLAN** (*VLAN creation*) | ¿Existe la VLAN en este switch? | `vlan 20` · `name USERS` |
| **Puerto de acceso** (*access port*) | ¿A qué VLAN pertenece el equipo conectado? | `switchport mode access` · `switchport access vlan 20` |
| **Tramas sin etiqueta** (*untagged frames*) | ¿El PC tiene que saber en qué VLAN está? | No: el switch clasifica por el puerto de entrada |
| **Tabla MAC por VLAN** (*per-VLAN MAC table*) | ¿Dónde está cada MAC y en qué VLAN? | `show mac address-table` |
| **Verificación** (*verification*) | ¿El estado observado coincide con el diseño? | `show vlan brief` · `show interfaces switchport` |
| **Rangos y base de datos VLAN** (*VLAN ranges, vlan.dat*) | ¿Qué números puedo usar y dónde se guardan? | 1–1005 normales, 1006–4094 extendidas; `flash:vlan.dat` |

Un error típico es pensar que **crear** la VLAN ya **mete** puertos en ella: son dos pasos distintos y cada uno se verifica por separado.

## 2.1. Crear y nombrar una VLAN

En Cisco IOS puede crearse una VLAN mediante:

```text
Switch(config)# vlan 20
Switch(config-vlan)# name USERS
Switch(config-vlan)# exit
```

El nombre no modifica el funcionamiento técnico, pero mejora mucho la lectura y documentación.

Un identificador como `20` es menos informativo que:

```text
20 USERS
```

Para eliminar una VLAN se usa `no vlan 20` (ver 2.8 antes de hacerlo).

## 2.2. Verificación

Una comprobación habitual es:

```text
show vlan brief
```

Salida representativa:

```text
VLAN Name                             Status    Ports
---- -------------------------------- --------- -------------------------------
1    default                          active    Gi0/3, Gi0/4, Gi0/5, Gi0/6
10   ADMIN                            active    Gi0/1
20   USERS                            active    Gi0/2, Gi0/8
30   SERVERS                          active
1002 fddi-default                     act/unsup
1003 token-ring-default               act/unsup
1004 fddinet-default                  act/unsup
1005 trnet-default                    act/unsup
```

La salida permite observar:

- VLAN existentes;
- nombre;
- estado;
- puertos access asociados.

Dos detalles importantes al leerla:

- los **puertos trunk no aparecen** en la columna `Ports`: que un puerto no figure aquí no significa que esté «perdido»; hay que mirarlo con `show interfaces trunk` (apartado 5);
- una VLAN puede existir sin ningún puerto (VLAN 30 en el ejemplo).

La pregunta profesional no es «¿he escrito el comando?», sino:

> ¿el estado observado coincide con el diseño?

## 2.3. Puerto access

Un puerto access se utiliza normalmente para conectar un endpoint perteneciente a una VLAN de datos.

Ejemplo:

```text
interface GigabitEthernet0/8
 switchport mode access
 switchport access vlan 20
```

Hay dos decisiones diferentes:

```text
modo del puerto = access
VLAN asignada = 20
```

Confundirlas puede producir diagnósticos incorrectos.

Si varios puertos comparten la misma configuración, puede usarse `interface range`:

```text
Switch(config)# interface range GigabitEthernet0/1 - 6
Switch(config-if-range)# switchport mode access
Switch(config-if-range)# switchport access vlan 20
```

Dos comportamientos de Cisco IOS que conviene conocer:

- si se asigna a un puerto una VLAN que **no existe**, el switch la crea automáticamente (aviso `% Access VLAN does not exist. Creating vlan 30`), pero **sin nombre**: el diseño queda incompleto;
- `no switchport access vlan` devuelve el puerto a la VLAN 1.

Para comprobar el modo y la VLAN de un puerto concreto:

```text
Switch# show interfaces GigabitEthernet0/8 switchport
Name: Gi0/8
Switchport: Enabled
Administrative Mode: static access
Operational Mode: static access
Administrative Trunking Encapsulation: dot1q
Negotiation of Trunking: Off
Access Mode VLAN: 20 (USERS)
Trunking Native Mode VLAN: 1 (default)
Voice VLAN: none
```

`Administrative Mode` es lo configurado; `Operational Mode` es lo que el puerto está haciendo realmente.

## 2.4. ¿Qué ocurre con las tramas del host?

Un PC conectado a un access port normal no necesita añadir una etiqueta 802.1Q a cada trama.

El switch conoce la VLAN asociada al puerto de entrada y clasifica el tráfico dentro de ese contexto lógico.

Simplificando:

```text
trama sin etiqueta desde PC
→ entra por Gi0/8
→ Gi0/8 pertenece a VLAN20
→ switch trata la trama como tráfico de VLAN20
```

## 2.5. Relación puerto–VLAN–MAC

La tabla MAC debe interpretarse dentro del contexto VLAN.

Un switch no solo necesita saber:

```text
MAC → puerto
```

sino conceptualmente:

```text
VLAN + MAC → puerto
```

Esto permite que una misma infraestructura mantenga dominios L2 independientes.

Comando de observación:

```text
show mac address-table
show mac address-table vlan 20
```

Salida representativa:

```text
          Mac Address Table
-------------------------------------------
Vlan    Mac Address       Type        Ports
----    -----------       --------    -----
  20    0050.7966.6801    DYNAMIC     Gi0/8
  20    0060.2f3a.1b02    DYNAMIC     Gi0/24
```

La MAC aprendida por `Gi0/24` (un trunk) pertenece a un equipo de VLAN 20 conectado a otro switch.

## 2.6. Cambiar un host de VLAN

Si un host se conecta a un puerto que pertenece a otra VLAN, cambia su pertenencia lógica de capa 2.

Si su configuración IP sigue perteneciendo a la subred anterior, puede aparecer una incoherencia:

```text
puerto → VLAN 20
IP host → subred de VLAN 10
```

El enlace físico puede estar `up` y, aun así, la conectividad ser incorrecta.

### Error frecuente

> Ver `up/up` y concluir que el host está en la VLAN correcta.

El estado físico no demuestra la pertenencia lógica.

## 2.7. Rangos de VLAN y base de datos

El identificador de VLAN (VID) ocupa 12 bits en la etiqueta 802.1Q (apartado 4): hay 4096 valores, de los que 0 y 4095 están reservados. Por eso las VLAN utilizables van de **1 a 4094**.

| Rango | VLAN | Observaciones |
|---|---|---|
| **Normal** (*normal range*) | 1–1005 | 1 = VLAN por defecto; 1002–1005 reservadas (tecnologías antiguas FDDI/Token Ring), no se pueden borrar |
| **Extendido** (*extended range*) | 1006–4094 | Uso en redes grandes; con VTP v1/v2 requieren modo transparente (apartado 8) |

Las VLAN de rango normal se guardan en el archivo **`vlan.dat`** de la memoria flash, **no** en la `startup-config`. Consecuencia práctica en laboratorio:

```text
erase startup-config   → borra la configuración, pero NO las VLAN
delete flash:vlan.dat  → borra la base de datos VLAN
reload                 → reinicio para partir de cero
```

## 2.8. Borrar una VLAN que tiene puertos

Si se ejecuta `no vlan 20` mientras hay puertos asignados a VLAN 20:

- los puertos **siguen configurados** con `switchport access vlan 20`;
- pero la VLAN ya no existe, así que quedan **inactivos** y sus equipos pierden conectividad;
- esos puertos **desaparecen** de `show vlan brief`, lo que puede despistar.

Antes de borrar una VLAN hay que reasignar sus puertos. Si ya ha ocurrido, basta con volver a crear la VLAN (o reasignar los puertos) y verificar.

### Idea clave

> Un access port clasifica el tráfico del endpoint dentro de una VLAN concreta.

# 3. Voz y datos en un mismo puerto

En muchas oficinas hay un único punto de red por puesto y en él se conectan un teléfono IP y, a través del teléfono, el PC. Este apartado explica cómo un solo puerto del switch puede atender a los dos equipos manteniéndolos en VLAN distintas, y qué consecuencias tiene para otras configuraciones, como Port Security (U06).

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **VLAN de datos** (*data VLAN*, *access VLAN*) | ¿En qué VLAN entra el tráfico del PC? | `switchport access vlan 20` |
| **VLAN de voz** (*voice VLAN*) | ¿En qué VLAN entra el tráfico del teléfono? | `switchport voice vlan 40` |
| **Etiquetado de voz** (*tagged voice traffic*) | ¿Cómo distingue el switch ambos tráficos? | Voz con etiqueta 802.1Q; datos sin etiqueta |
| **Varias MAC legítimas** (*multiple legitimate MACs*) | ¿Cuántas MAC aparecen en el puerto? | Dos: teléfono + PC |

La VLAN de voz **no** es una lección de QoS ni de telefonía: aquí solo interesa la coexistencia de dos VLAN en el mismo acceso físico.

## 3.1. Escenario habitual

En algunas redes un teléfono IP se conecta al switch y un PC se conecta al teléfono.

```text
Switch ── Teléfono IP ── PC
```

Un único puerto físico del switch puede transportar:

- tráfico de datos del PC;
- tráfico de voz del teléfono.

## 3.2. Configuración conceptual

Ejemplo Cisco:

```text
interface GigabitEthernet0/10
 switchport mode access
 switchport access vlan 20
 switchport voice vlan 40
```

Interpretación:

```text
VLAN 20 → datos
VLAN 40 → voz
```

Verificación: `show interfaces GigabitEthernet0/10 switchport` muestra `Access Mode VLAN: 20 (USERS)` y `Voice VLAN: 40 (VOICE)`.

## 3.3. Tagged y untagged en este escenario

En el escenario Cisco estudiado, el tráfico de datos del PC suele llegar sin etiqueta al switch, mientras que el teléfono etiqueta el tráfico de voz con 802.1Q.

El teléfono Cisco **aprende qué VLAN de voz debe usar** gracias a CDP (en entornos multifabricante, LLDP-MED); por eso no hay que configurarlo a mano en el teléfono.

Esto permite que dos tipos de tráfico compartan el enlace físico manteniendo separación lógica. Aunque transporte dos VLAN, el puerto sigue siendo un **puerto de acceso** con una VLAN de voz añadida, no un trunk.

## 3.4. Varias MAC legítimas

En ese puerto pueden aparecer varias MAC legítimas:

- MAC del teléfono;
- MAC del PC.

Esto es importante al recuperar Port Security de U06. Una política demasiado restrictiva (por ejemplo, `maximum 1`) podría bloquear un escenario correcto.

## 3.5. Lo que no estudiaremos aquí

Una voice VLAN no equivale a una lección completa sobre:

- QoS;
- señalización VoIP;
- codecs;
- Call Manager.

Aquí interesa comprender la coexistencia de voz y datos en el mismo acceso físico.

### Idea clave

> Compartir un puerto físico no obliga a compartir la misma VLAN.

# 4. IEEE 802.1Q

Mientras cada puerto pertenece a una sola VLAN, el switch sabe la VLAN de cada trama por el puerto de entrada. El problema aparece cuando **un mismo enlace** debe llevar tramas de varias VLAN, por ejemplo entre dos switches: el receptor necesita una marca en cada trama. Este apartado presenta esa marca, la **etiqueta 802.1Q**, y cómo observarla.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Etiqueta 802.1Q** (*802.1Q tag*) | ¿Cómo se marca la VLAN de una trama en un enlace compartido? | 4 bytes insertados en la cabecera Ethernet |
| **TPID** (*Tag Protocol Identifier*) | ¿Cómo sabe el receptor que la trama lleva etiqueta? | Valor `0x8100` |
| **VID** (*VLAN Identifier*) | ¿A qué VLAN pertenece la trama? | VID = 20 |
| **Tagged / untagged** (*con / sin etiqueta*) | ¿La trama lleva etiqueta en este punto? | Untagged en access; tagged en trunk |
| **Punto de captura** (*capture point*) | ¿Por qué una captura muestra o no la etiqueta? | Captura en el PC ≠ captura en el trunk |

No hace falta memorizar cada bit de la etiqueta: basta con saber dónde va, para qué sirve y qué campo identifica la VLAN.

## 4.1. El problema

Entre switches necesitamos transportar tramas de varias VLAN por un mismo enlace.

Si una trama atraviesa ese enlace, el switch receptor necesita saber a qué VLAN pertenece.

La solución habitual es **IEEE 802.1Q**, el estándar abierto de etiquetado de VLAN. (Cisco tuvo un protocolo propio, ISL, hoy obsoleto.)

## 4.2. Etiqueta 802.1Q

802.1Q inserta una etiqueta de **4 bytes** en la trama Ethernet, entre la **dirección MAC de origen** y el campo **EtherType**. Como la trama cambia, el switch **recalcula el FCS**.

```text
Sin etiqueta:  | MAC destino | MAC origen |              | EtherType | Datos | FCS |
Con etiqueta:  | MAC destino | MAC origen | Tag 802.1Q   | EtherType | Datos | FCS |
                                           (4 bytes)
```

Campos de la etiqueta:

| Campo | Tamaño | Función |
|---|---:|---|
| **TPID** | 16 bits | Indica que hay etiqueta 802.1Q (`0x8100`) |
| **PCP** (*Priority Code Point*) | 3 bits | Prioridad de la trama (802.1p); la usa, por ejemplo, la voz |
| **DEI** (*Drop Eligible Indicator*) | 1 bit | Marca tramas que pueden descartarse ante congestión |
| **VID** (*VLAN Identifier*) | 12 bits | Identifica la VLAN (1–4094) |

A nivel de esta unidad interesa reconocer especialmente:

- **TPID**: identifica la presencia del tag 802.1Q;
- **VID — VLAN Identifier**: identifica la VLAN.

## 4.3. VLAN ID

El VID identifica el contexto VLAN de la trama transportada.

Ejemplo conceptual:

```text
trama Ethernet
+
VID 20
→ pertenece a VLAN20 durante el transporte etiquetado
```

Con 12 bits hay 4096 valores; se reservan 0 y 4095, de ahí el rango 1–4094 del apartado 2.7.

## 4.4. Access frente a trunk

### Access

Normalmente conecta un endpoint y transporta una VLAN de datos. Las tramas salen y entran **sin etiqueta**.

### Trunk

Transporta múltiples VLAN entre dispositivos que necesitan conservar esa información lógica. Las tramas viajan **con etiqueta**, salvo las de la native VLAN (apartado 6).

```text
access → clasificación local del endpoint
trunk  → transporte de múltiples VLAN
```

El recorrido completo de una trama de VLAN 20 entre dos switches:

```text
PC (sin etiqueta) → SW1 access Gi0/8 (VLAN 20)
→ SW1 añade tag VID 20 al salir por el trunk
→ SW2 recibe, lee VID 20, quita el tag
→ SW2 entrega sin etiqueta por un access de VLAN 20
```

## 4.5. Punto de observación

La presencia o ausencia de un tag depende de dónde capturamos el tráfico.

Una captura realizada en un host conectado a un access port no tiene por qué mostrar el mismo formato que una captura realizada sobre un enlace trunk.

Por tanto:

> una captura siempre debe interpretarse teniendo en cuenta el punto de captura.

## 4.6. Observar 802.1Q en Packet Tracer y Wireshark

- **Packet Tracer (modo Simulación):** al abrir la PDU en el enlace trunk, los detalles de la trama muestran la cabecera 802.1Q con el VID; en el enlace access, no.
- **Wireshark:** en una captura hecha sobre un trunk (normalmente una captura preparada o tomada con un puerto espejo), la trama muestra una línea `802.1Q Virtual LAN, PRI: 0, DEI: 0, ID: 20`. Filtros útiles:

```text
vlan
vlan.id == 20
```

Muchas tarjetas de red retiran la etiqueta antes de entregar la trama al sistema operativo; por eso una captura en un PC normal casi nunca la muestra.

### Idea clave

> 802.1Q permite conservar la pertenencia VLAN cuando varias VLAN comparten un enlace.

# 5. Enlaces trunk y VLAN permitidas

Con 802.1Q ya sabemos **cómo** se marca la VLAN de cada trama; ahora hay que configurar **los enlaces** que llevan esas tramas etiquetadas. Este apartado trata el trunk estático, su verificación y el control de qué VLAN lo atraviesan. La idea más importante es que «trunk operativo» no equivale a «todas las VLAN funcionan».

| Concepto | Pregunta que responde | Comando / ejemplo |
|---|---|---|
| **Trunk** (*trunk link*) | ¿Qué enlace transporta varias VLAN? | `switchport mode trunk` |
| **Encapsulación del trunk** (*trunk encapsulation*) | ¿Hay que elegir 802.1Q explícitamente? | `switchport trunk encapsulation dot1q` (en switches que admiten ISL) |
| **VLAN permitidas** (*allowed VLANs*) | ¿Qué VLAN puede transportar el trunk? | `switchport trunk allowed vlan 10,20,30,99` |
| **Añadir / quitar** (*add / remove*) | ¿Cómo cambio la lista sin reemplazarla? | `switchport trunk allowed vlan add 40` |
| **Permitidas y activas** (*allowed and active*) | ¿La VLAN permitida existe realmente en el switch? | `show interfaces trunk` + `show vlan brief` |

No hay que confundir **permitida** (lo que autoriza la configuración del trunk) con **activa** (lo que existe y funciona en el switch).

## 5.1. Qué es un trunk

Un **trunk** es un enlace capaz de transportar tráfico de varias VLAN.

Se utiliza habitualmente entre:

- switches;
- switch y router en router-on-a-stick;
- switch y otros dispositivos que entienden 802.1Q (por ejemplo, servidores de virtualización o puntos de acceso con varias SSID).

## 5.2. Configuración estática

Ejemplo:

```text
interface GigabitEthernet0/24
 switchport mode trunk
```

En switches que admiten dos encapsulaciones (ISL y 802.1Q), como los multicapa Catalyst 3560 de Packet Tracer, hay que **elegir primero la encapsulación**; si no, IOS rechaza el modo trunk:

```text
interface GigabitEthernet0/1
 switchport trunk encapsulation dot1q
 switchport mode trunk
```

En un Catalyst 2960, que solo admite 802.1Q, el primer comando no existe ni hace falta.

## 5.3. Verificación

Comando especialmente útil:

```text
show interfaces trunk
```

Salida representativa:

```text
Port        Mode         Encapsulation  Status        Native vlan
Gi0/24      on           802.1q         trunking      999

Port        Vlans allowed on trunk
Gi0/24      10,20,30,99

Port        Vlans allowed and active in management domain
Gi0/24      10,20,99

Port        Vlans in spanning tree forwarding state and not pruned
Gi0/24      10,20,99
```

Puede aportar evidencia sobre:

- interfaces en trunk (`Status: trunking`);
- modo (`on` = trunk estático; `auto` o `desirable` = negociado por DTP);
- encapsulación;
- native VLAN;
- VLAN permitidas;
- VLAN permitidas **y activas** (en el ejemplo, VLAN 30 está permitida pero no existe en este switch);
- VLAN en estado forwarding de STP.

Si un puerto no aparece en `show interfaces trunk`, **no** está funcionando como trunk.

## 5.4. Un trunk `up` no garantiza servicio para todas las VLAN

Este razonamiento es esencial.

Podemos tener:

```text
trunk operativo
VLAN10 funciona
VLAN20 falla
```

Eso reduce hipótesis.

Si VLAN10 atraviesa el mismo enlace, el medio físico y parte de la configuración del trunk ya han demostrado funcionar.

Debemos buscar una diferencia específica de VLAN20.

## 5.5. Allowed VLAN

Por defecto, un trunk permite **todas** las VLAN (1–4094). Puede limitarse qué VLAN está autorizado a transportar.

Ejemplo:

```text
switchport trunk allowed vlan 10,20,30,99
```

La lista debe responder al diseño.

No existe ventaja en transportar una VLAN por un enlace que no necesita esa VLAN: solo añade broadcasts innecesarios y superficie de error.

## 5.6. Reemplazar frente a añadir

En Cisco IOS, `switchport trunk allowed vlan <lista>` **reemplaza** la lista completa. Es uno de los errores más frecuentes: querer añadir una VLAN y dejar fuera todas las demás.

| Comando | Efecto |
|---|---|
| `switchport trunk allowed vlan 10,20` | La lista pasa a ser **exactamente** 10 y 20 |
| `switchport trunk allowed vlan add 30` | **Añade** 30 a la lista existente |
| `switchport trunk allowed vlan remove 20` | **Quita** 20 de la lista existente |
| `switchport trunk allowed vlan except 30` | Permite todas **salvo** 30 |
| `switchport trunk allowed vlan all` | Vuelve a permitir todas |
| `switchport trunk allowed vlan none` | No permite ninguna |

Ejemplo del error:

```text
Estado: allowed 10,20,99
Se escribe: switchport trunk allowed vlan 30
Resultado: allowed 30   → VLAN 10, 20 y 99 dejan de pasar
Correcto: switchport trunk allowed vlan add 30
```

Antes de cambiarla debemos comprobar el estado actual.

La secuencia profesional es:

```text
leer estado actual
→ comparar con diseño
→ decidir cambio
→ aplicar mínimo cambio
→ verificar
```

## 5.7. `allowed` frente a `allowed and active`

Una VLAN puede estar autorizada en el trunk y, sin embargo, no existir localmente o no estar activa.

Por eso conviene distinguir:

```text
permitida en política del trunk
≠
existente y activa
```

La combinación de:

```text
show interfaces trunk
show vlan brief
```

puede aportar evidencias complementarias.

Recuerda: la VLAN debe existir en **todos** los switches por los que pasa, incluidos los intermedios que solo la transportan por trunks y no tienen ningún puerto access en ella.

### Idea clave

> Un enlace trunk operativo no demuestra que todas las VLAN necesarias estén pasando correctamente.

# 6. Native VLAN y DTP

Un trunk tiene dos detalles de configuración que causan muchos problemas si se dejan al azar: la **native VLAN**, que decide qué pasa con las tramas sin etiqueta, y **DTP**, el protocolo de Cisco que puede convertir un puerto en trunk sin que lo hayamos decidido. Este apartado explica ambos, cómo detectar incoherencias entre extremos y qué buenas prácticas protegen el diseño.

| Concepto | Pregunta que responde | Comando / ejemplo |
|---|---|---|
| **VLAN nativa** (*native VLAN*) | ¿A qué VLAN se asignan las tramas sin etiqueta del trunk? | `switchport trunk native vlan 999` |
| **Discrepancia de VLAN nativa** (*native VLAN mismatch*) | ¿Coincide la native en ambos extremos? | SW1 = 999, SW2 = 1 → incoherencia |
| **DTP** (*Dynamic Trunking Protocol*) | ¿Puede un puerto negociar solo si es trunk? | `dynamic auto`, `dynamic desirable` |
| **Configuración explícita** (*static mode, nonegotiate*) | ¿Cómo evito que la negociación decida por mí? | `switchport mode trunk` + `switchport nonegotiate` |
| **Buenas prácticas de seguridad** (*VLAN hardening*) | ¿Cómo reduzco ataques como *VLAN hopping*? | Native sin usuarios, DTP desactivado, puertos libres aparcados |

DTP decide **si** un enlace es trunk; nunca decide **qué** VLAN deben pasar ni **cuál** debe ser la native: eso es diseño.

## 6.1. Native VLAN

En un trunk 802.1Q existe el concepto de **native VLAN**.

En configuraciones Cisco típicas, el tráfico perteneciente a la native VLAN se transporta **sin etiqueta**, y cualquier trama sin etiqueta que llega por el trunk se asigna a la native VLAN. Por defecto, la native VLAN es la **VLAN 1**.

Se cambia en la interfaz trunk:

```text
interface GigabitEthernet0/24
 switchport mode trunk
 switchport trunk native vlan 999
```

Lo importante para nosotros es la coherencia entre extremos: **ambos lados del trunk deben usar la misma native VLAN**.

## 6.2. Native VLAN mismatch

Supongamos:

```text
SW1 Gi0/24 native VLAN = 99
SW2 Gi0/24 native VLAN = 1
```

Existe una discrepancia de diseño. El tráfico sin etiqueta que SW1 envía como VLAN 99 lo recibe SW2 como VLAN 1: dos VLAN distintas quedan «mezcladas».

Evidencias típicas en Cisco:

- mensajes de CDP en consola del tipo `%CDP-4-NATIVE_VLAN_MISMATCH: Native VLAN mismatch discovered on GigabitEthernet0/24 (99), with SW2 GigabitEthernet0/24 (1)`;
- columna `Native vlan` distinta en `show interfaces trunk` de cada extremo;
- STP puede bloquear el puerto para esas VLAN como medida de protección.

No debemos «arreglarla» cambiando un lado al azar.

Primero debemos saber cuál era el diseño esperado.

Después:

```text
estado esperado
→ estado observado en ambos extremos
→ discrepancia
→ cambio mínimo
→ verificación
```

## 6.3. DTP

**DTP — Dynamic Trunking Protocol** es un protocolo propietario de Cisco que puede participar en la negociación del estado trunk de un enlace.

Modos de un puerto de switch:

| Modo | Comando | Comportamiento |
|---|---|---|
| **Access** | `switchport mode access` | Siempre access; no forma trunk |
| **Trunk** | `switchport mode trunk` | Siempre trunk; además envía mensajes DTP |
| **Dynamic auto** | `switchport mode dynamic auto` | Espera: forma trunk solo si el otro lado lo pide |
| **Dynamic desirable** | `switchport mode dynamic desirable` | Pide activamente formar trunk |

Resultado de la negociación (visión de conjunto, no para memorizar):

| SW1 \ SW2 | access | trunk | dynamic auto | dynamic desirable |
|---|---|---|---|---|
| **access** | access | incoherente (evitar) | access | access |
| **trunk** | incoherente (evitar) | trunk | trunk | trunk |
| **dynamic auto** | access | trunk | **access** | trunk |
| **dynamic desirable** | access | trunk | trunk | trunk |

La casilla más importante es **auto + auto = access**: dos switches con la configuración por defecto de muchos modelos (por ejemplo, el 2960 usa `dynamic auto`) **no** forman trunk aunque el alumno lo espere.

Lo importante es comprender que una configuración basada en negociación puede producir un estado diferente al que un principiante esperaba. `show interfaces <int> switchport` muestra la diferencia entre `Administrative Mode` (configurado) y `Operational Mode` (resultado real).

## 6.4. Configuración explícita

En muchos diseños profesionales se prefiere configurar de forma explícita si un enlace debe ser access o trunk.

Esto mejora:

- previsibilidad;
- legibilidad;
- seguridad operativa;
- troubleshooting.

Cuando no se necesita negociación DTP puede utilizarse:

```text
interface GigabitEthernet0/24
 switchport mode trunk
 switchport nonegotiate
```

`switchport nonegotiate` deja de enviar mensajes DTP. Solo se admite si el puerto está en modo `access` o `trunk` estático; con un modo `dynamic` IOS lo rechaza. En un puerto access, `switchport mode access` ya desactiva la negociación de trunk.

## 6.5. DTP no sustituye el diseño

Que dos interfaces negocien un trunk no responde preguntas como:

- ¿qué VLAN deben atravesarlo?;
- ¿cuál debe ser la native VLAN?;
- ¿debería existir ese trunk?;
- ¿es coherente con la topología?

## 6.6. Una plantilla de trunk explícito

Juntando los apartados 5 y 6, un trunk bien definido entre dos switches queda así (y **debe ser igual en ambos extremos**):

```text
interface GigabitEthernet0/24
 description TRUNK a SW2 Gi0/24
 switchport mode trunk
 switchport trunk native vlan 999
 switchport trunk allowed vlan 10,20,40,99
 switchport nonegotiate
```

## 6.7. Buenas prácticas de seguridad en VLAN

Una VLAN mal configurada puede permitir que un atacante envíe tráfico a otra VLAN (**VLAN hopping**). Las dos técnicas clásicas son:

- **suplantación de switch** (*switch spoofing*): el equipo atacante negocia un trunk mediante DTP con un puerto en modo `dynamic`;
- **doble etiquetado** (*double tagging*): el atacante, en la native VLAN, envía tramas con dos etiquetas; el primer switch quita la exterior y la interior lleva la trama a otra VLAN.

Buenas prácticas que las evitan:

| Práctica | Qué evita |
|---|---|
| Puertos de usuario en `switchport mode access` | Negociar trunks desde un PC |
| `switchport nonegotiate` en trunks | Mensajes DTP innecesarios |
| Native VLAN dedicada y sin usuarios (p. ej. 999), distinta de VLAN 1 | Doble etiquetado |
| No usar VLAN 1 para usuarios ni gestión | Exponer la VLAN por defecto |
| Puertos libres en una VLAN «aparcamiento» y en `shutdown` | Conexiones no autorizadas |
| Lista `allowed` limitada al diseño | Transportar VLAN innecesarias |

Ejemplo de puertos no utilizados:

```text
interface range GigabitEthernet0/15 - 22
 switchport mode access
 switchport access vlan 666
 shutdown
```

Estas medidas completan las de seguridad L2 vistas en U06 (Port Security, BPDU Guard, DHCP Snooping).

### Idea clave

> La negociación automática nunca sustituye una decisión de arquitectura.

# 7. VLAN con STP y EtherChannel

En U06 estudiamos STP (evitar bucles) y EtherChannel (agregar enlaces). Cuando esos mismos enlaces pasan a ser trunks que llevan varias VLAN, aparecen preguntas nuevas: ¿STP decide igual para todas las VLAN?, ¿dónde se configura el trunk en un Port-channel? Este apartado **no** vuelve a enseñar STP ni LACP; solo los conecta con las VLAN.

| Concepto | Pregunta que responde | Comando / ejemplo |
|---|---|---|
| **STP por VLAN** (*PVST+ / Rapid PVST+*) | ¿Qué camino usa STP para cada VLAN? | `show spanning-tree vlan 20` |
| **Root por VLAN** (*per-VLAN root*) | ¿Puedo repartir la carga eligiendo root distinto por VLAN? | `spanning-tree vlan 10 root primary` |
| **Una VLAN falla, otra funciona** (*VLAN-specific failure*) | ¿Qué diferencia específica tiene la VLAN que falla? | allowed, existencia, STP, gateway |
| **EtherChannel como trunk** (*Port-channel trunk*) | ¿Dónde se configura el trunk de un bundle? | En `interface Port-channel1` |
| **Orden de comprobación** (*verification order*) | ¿Qué miro primero si falla un Po trunk? | `show etherchannel summary` → `show interfaces trunk` |

Un fallo puede estar en la VLAN, en el trunk, en STP o en el bundle: la evidencia debe separar esas capas de decisión.

## 7.1. Recuperación de U06

En U06 aprendimos que:

- STP/RSTP evita bucles de capa 2;
- EtherChannel agrupa varios enlaces en una interfaz lógica;
- LACP permite negociar la agregación.

U07 reutiliza esos conceptos cuando los enlaces transportan VLAN.

## 7.2. STP y VLAN

Los switches Cisco ejecutan por defecto **una instancia de STP por cada VLAN** (PVST+ o Rapid PVST+). Por eso el Bridge ID incluye el número de VLAN (*extended system ID*), como vimos en U06.

En entornos Cisco podemos observar información STP asociada a una VLAN concreta.

Ejemplo:

```text
show spanning-tree vlan 20
```

Esto ayuda a responder:

- ¿qué switch actúa como root para esa VLAN?;
- ¿qué puertos reenvían?;
- ¿qué camino está bloqueado?

Como cada VLAN tiene su propio árbol, se puede **repartir la carga** eligiendo un root distinto para cada grupo de VLAN:

```text
SW1(config)# spanning-tree vlan 10,99 root primary
SW2(config)# spanning-tree vlan 20,40 root primary
```

Así, un enlace que está bloqueado para VLAN 10 puede estar reenviando para VLAN 20.

No necesitamos reaprender STP desde cero.

## 7.3. Una VLAN falla y otra funciona

Este patrón es especialmente informativo.

Si dos VLAN utilizan enlaces similares pero una funciona y otra no, debemos buscar diferencias específicas:

- allowed VLAN;
- existencia de la VLAN;
- STP para esa VLAN;
- gateway de esa VLAN.

## 7.4. EtherChannel como trunk

Un Port-channel puede configurarse para transportar varias VLAN.

Conceptualmente:

```text
miembros físicos
→ LACP
→ Port-channel
→ trunk sobre interfaz lógica
```

La configuración de switching debe aplicarse de forma coherente al interfaz lógico correspondiente:

```text
interface range GigabitEthernet0/1 - 2
 channel-group 1 mode active
!
interface Port-channel1
 switchport mode trunk
 switchport trunk native vlan 999
 switchport trunk allowed vlan 10,20,30,40,99
```

Los miembros deben tener parámetros compatibles (modo, native, allowed, velocidad). Una discrepancia en un miembro puede dejarlo fuera del bundle (en U06, estado suspendido).

## 7.5. Orden de comprobación

Si el diseño utiliza `Po1` como trunk y aparece un fallo, conviene comprobar primero:

```text
show etherchannel summary
```

Después:

```text
show interfaces trunk
```

En la salida de `show interfaces trunk` debe aparecer `Po1`, no los miembros físicos.

No tiene sentido diagnosticar solo un miembro físico ignorando el estado del bundle.

### Idea clave

> VLAN, STP y EtherChannel son capas de decisión relacionadas: un fallo puede estar en cualquiera de ellas y la evidencia debe separar hipótesis.

# 8. Administración centralizada de VLAN con VTP

Crear las mismas VLAN a mano en veinte switches es lento y propenso a errores. Cisco ofrece **VTP** para distribuir la lista de VLAN desde un punto central. Este apartado explica qué hace VTP, qué no hace, sus modos y, sobre todo, su **riesgo operativo**: un switch mal introducido puede borrar las VLAN de toda la red.

| Concepto | Pregunta que responde | Comando / ejemplo |
|---|---|---|
| **VTP** (*VLAN Trunking Protocol*) | ¿Cómo distribuyo la lista de VLAN a varios switches? | Anuncios VTP por los trunks |
| **Dominio VTP** (*VTP domain*) | ¿Qué switches comparten la misma información? | `vtp domain EMPRESA` |
| **Modos** (*server / client / transparent*) | ¿Quién crea VLAN y quién las recibe? | `vtp mode client` |
| **Número de revisión** (*configuration revision*) | ¿Qué versión de la base VLAN es la más reciente? | Revision 12 > revision 8 |
| **Verificación** (*verification*) | ¿En qué dominio, modo y revisión está el switch? | `show vtp status` |
| **VTPv3** | ¿Cómo se reduce el riesgo en versiones modernas? | *Primary server* |

VTP solo distribuye **la lista de VLAN** (número y nombre). No configura puertos access, trunks, gateways ni routing.

## 8.1. Qué problema intenta resolver

En una red con muchos switches, crear manualmente la misma información VLAN en todos ellos puede generar inconsistencias.

**VTP — VLAN Trunking Protocol** es una tecnología Cisco que permite distribuir determinada información VLAN dentro de un dominio VTP. Los anuncios VTP viajan **solo por enlaces trunk**.

## 8.2. Qué NO hace VTP

VTP no sustituye:

- trunks;
- puertos access;
- gateways;
- routing;
- ACL;
- documentación.

Su función es más limitada.

## 8.3. Dominio VTP

Los dispositivos que participan deben pertenecer al dominio administrativo adecuado: mismo **nombre de dominio** (distingue mayúsculas y minúsculas), misma **versión** y, si se usa, misma **contraseña**.

Una discrepancia de dominio puede impedir el comportamiento esperado.

Un switch nuevo tiene el dominio vacío (*null*) y adopta el dominio del primer anuncio VTP que recibe por un trunk.

## 8.4. Modos clásicos

| Modo | ¿Crea / modifica / borra VLAN? | ¿Aplica los anuncios? | ¿Reenvía los anuncios? | Dónde guarda las VLAN |
|---|---|---|---|---|
| **Server** (por defecto) | Sí | Sí | Sí | `vlan.dat` |
| **Client** | No (VTP v1/v2) | Sí | Sí | `vlan.dat` |
| **Transparent** | Sí, solo localmente | No | Sí (sin aplicarlos) | `vlan.dat` y `running-config` |

### Server

Puede crear/modificar información VLAN y participar en su distribución. Es el modo por defecto.

### Client

Recibe información dentro del dominio y la aplica. En VTP v1/v2 no permite crear, modificar ni borrar VLAN localmente.

### Transparent

No aplica la base VLAN distribuida: mantiene sus propias VLAN locales y se limita a reenviar los anuncios por sus trunks. Es el modo necesario para usar VLAN de rango extendido con VTP v1/v2.

El comportamiento exacto depende de versión y plataforma; por eso debemos verificar el estado real y no memorizar una descripción sin contexto.

Configuración básica:

```text
Switch(config)# vtp domain EMPRESA
Switch(config)# vtp mode server
Switch(config)# vtp password Clave-VTP
Switch(config)# vtp version 2
```

En los demás switches del dominio: `vtp domain EMPRESA`, `vtp mode client` y la misma contraseña.

## 8.5. Configuration revision

En VTP clásico, la **configuration revision** representa el estado de la base distribuida. Cada cambio en las VLAN de un server incrementa el número en 1.

Un switch del dominio acepta la base anunciada si su revisión es **mayor** que la suya, **aunque venga de un client**.

Históricamente, conectar un switch con información VTP inesperada ha podido provocar cambios no deseados en un dominio: por ejemplo, un switch reutilizado de un laboratorio, con el mismo dominio y una revisión más alta, puede **sobrescribir** la lista de VLAN de toda la red y dejar puertos sin VLAN.

Antes de incorporar un switch usado, su revisión se pone a 0, por ejemplo pasándolo a modo transparente (o cambiando el nombre de dominio) y volviendo después al modo previsto.

Por eso VTP debe tratarse con disciplina operativa.

## 8.6. Verificación

Comando típico:

```text
show vtp status
```

Puede aportar información sobre:

- versión (`VTP Version`);
- dominio (`VTP Domain Name`);
- modo (`VTP Operating Mode`);
- revision (`Configuration Revision`);
- número de VLAN (`Number of existing VLANs`).

Otra opción útil es `show vtp password` para comprobar la contraseña configurada.

## 8.7. VTPv3 y VTP pruning

VTPv3 introduce mejoras de control y el concepto de **primary server**: solo ese servidor puede modificar la base VLAN, lo que reduce el riesgo de sobrescrituras accidentales. También admite VLAN de rango extendido.

**VTP pruning** (`vtp pruning` en el server) evita enviar por un trunk el tráfico de difusión de VLAN que no tienen puertos activos al otro lado.

En este curso ambos se estudian como evolución profesional, no como un bloque de configuración exhaustivo.

## 8.8. Por qué VTP tiene un peso limitado en esta unidad

Comprender VTP ayuda a interpretar redes Cisco y determinados escenarios curriculares.

Pero una red VLAN profesional debe poder diseñarse y diagnosticarse sin hacer de VTP el centro de la arquitectura. Muchas organizaciones usan **modo transparent** (o VTP desactivado) y crean las VLAN a mano o con herramientas de automatización.

### Idea clave

> Centralizar información puede reducir trabajo repetitivo, pero también amplifica el impacto de una configuración errónea.

# 9. Por qué se necesita routing entre VLAN

Hasta ahora hemos separado la red en VLAN. Pero la separación tiene un precio: un equipo de USERS ya no puede hablar con un servidor de SERVERS solo a través de los switches. Este apartado explica **por qué** hace falta un dispositivo de capa 3 y qué papel juega el **default gateway**, antes de configurar ninguna solución.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Frontera L2/L3** (*Layer 2 / Layer 3 boundary*) | ¿Por qué dos VLAN no se hablan a través del switch? | VLAN distintas = subredes distintas |
| **Gateway por VLAN** (*per-VLAN default gateway*) | ¿A quién envía el host el tráfico remoto? | VLAN 20 → `10.10.20.1` |
| **Transporte frente a routing** (*switching vs. routing*) | ¿Un trunk comunica VLAN? | No: solo las transporta |
| **Routing entre VLAN** (*inter-VLAN routing*) | ¿Qué dispositivos lo pueden hacer? | Router (ROAS) o switch multicapa (SVI) |

Este apartado recupera la decisión **local/remoto** de U04: el host compara la IP de destino con su prefijo y, si es remota, envía la trama a su gateway.

## 9.1. La frontera entre capa 2 y capa 3

Supongamos:

```text
PC-A → VLAN10 → 10.10.10.25/24
PC-B → VLAN20 → 10.10.20.30/24
```

Son VLAN diferentes y subredes diferentes.

PC-A determina mediante su máscara que `10.10.20.30` no pertenece a su red local.

Por tanto, no intenta entregar directamente la comunicación al destino mediante switching local.

Necesita su **default gateway**.

## 9.2. Gateway por VLAN

Cada subred necesita un gateway adecuado si debe comunicarse con otras redes.

Ejemplo:

```text
VLAN10 / 10.10.10.0/24 → gateway 10.10.10.1
VLAN20 / 10.10.20.0/24 → gateway 10.10.20.1
```

El gateway debe estar **en la misma VLAN y subred** que los hosts: si no, el host no puede alcanzarlo por ARP.

## 9.3. Switching no sustituye routing

Un trunk puede transportar VLAN10 y VLAN20 entre switches, pero eso no significa que permita automáticamente comunicación entre ambas.

```text
trunk = transporta dominios L2
routing = comunica redes L3 distintas
```

## 9.4. Flujo simplificado

Cuando PC-A comunica con PC-B:

```text
PC-A detecta destino remoto
→ envía al gateway de VLAN10 (ARP para la MAC del gateway)
→ dispositivo L3 recibe
→ selecciona red de VLAN20
→ reenvía hacia VLAN20 (ARP para la MAC de PC-B)
→ PC-B recibe
```

## 9.5. Tres formas de hacer routing entre VLAN

| Solución | Cómo funciona | Uso actual |
|---|---|---|
| **Routing inter-VLAN clásico** (*legacy inter-VLAN routing*) | Una interfaz física del router por VLAN, cada una a un access port | Obsoleto: no escala (una interfaz y un cable por VLAN) |
| **Router-on-a-stick** (*ROAS*) | Una interfaz física del router con subinterfaces, sobre un trunk | Redes pequeñas y laboratorios (apartado 10) |
| **Switch multicapa con SVI** (*Layer 3 switch*) | Interfaces virtuales por VLAN dentro del propio switch | Redes de campus (apartado 11) |

### Idea clave

> Una VLAN separa dominios de capa 2; para comunicar subredes diferentes necesitamos una decisión de capa 3.

# 10. Router-on-a-stick

La primera solución práctica de routing entre VLAN usa **un router y un solo cable**. El truco es combinar lo visto en el bloque anterior (un trunk 802.1Q) con una idea nueva del lado del router: las **subinterfaces**, una por VLAN, cada una con la IP que hará de gateway.

| Concepto | Pregunta que responde | Comando / ejemplo |
|---|---|---|
| **Router-on-a-stick** (*ROAS*) | ¿Cómo enruta un router varias VLAN con una sola interfaz? | Trunk + subinterfaces |
| **Lado del switch** (*switch-side trunk*) | ¿Cómo llega cada VLAN al router? | Puerto hacia el router en `switchport mode trunk` |
| **Subinterfaz** (*subinterface*) | ¿Qué interfaz lógica representa cada VLAN en el router? | `interface GigabitEthernet0/0.10` |
| **Encapsulación dot1Q** (*dot1Q encapsulation*) | ¿Qué VLAN atiende cada subinterfaz? | `encapsulation dot1Q 10` |
| **Dirección del gateway** (*gateway address*) | ¿Qué IP ponen los hosts como puerta de enlace? | `10.10.10.1` |
| **Verificación** (*verification*) | ¿Funciona cada pieza: switch, router y host? | `show interfaces trunk`, `show ip interface brief`, `show ip route` |

El número de la subinterfaz (`.10`) es solo un nombre; lo que la une a la VLAN es `encapsulation dot1Q 10`. Por claridad se hacen coincidir.

## 10.1. Concepto

**Router-on-a-stick — ROAS** permite que una única interfaz física de un router participe en el routing de varias VLAN mediante subinterfaces.

```text
Switch ===== trunk ===== Router
                         ├─ .10 → VLAN10
                         ├─ .20 → VLAN20
                         └─ .30 → VLAN30
```

## 10.2. Lado del switch

El enlace hacia el router debe transportar las VLAN necesarias.

Conceptualmente:

```text
puerto al router
→ trunk
→ allowed VLAN adecuadas
```

Ejemplo:

```text
interface GigabitEthernet0/1
 description TRUNK a R1 Gi0/0
 switchport mode trunk
 switchport trunk allowed vlan 10,20,30,99
```

Los routers no negocian DTP: el puerto del switch debe estar en `switchport mode trunk` estático.

## 10.3. Subinterfaces

Ejemplo representativo:

```text
interface GigabitEthernet0/0
 no ip address
 no shutdown
!
interface GigabitEthernet0/0.10
 encapsulation dot1Q 10
 ip address 10.10.10.1 255.255.255.0
!
interface GigabitEthernet0/0.20
 encapsulation dot1Q 20
 ip address 10.10.20.1 255.255.255.0
```

Cada subinterfaz se asocia a una VLAN mediante `encapsulation dot1Q`. Hay que escribir `encapsulation` **antes** que `ip address`; si no, IOS no acepta la dirección.

Detalles importantes:

- la **interfaz física** no lleva IP, pero **sí** necesita `no shutdown`: si está apagada, todas sus subinterfaces lo están;
- si la native VLAN del trunk transporta tráfico que el router debe atender, su subinterfaz se marca como nativa: `encapsulation dot1Q 999 native` (debe coincidir con la native del switch).

## 10.4. La dirección del gateway

La dirección configurada en la subinterfaz suele actuar como gateway de los hosts de esa VLAN.

Por ejemplo:

```text
VLAN20
red 10.10.20.0/24
gateway 10.10.20.1
```

Cuando las subinterfaces están activas, el router tiene una **ruta conectada** para cada VLAN, así que ya puede enrutar entre ellas sin rutas adicionales (el routing estático se estudia en U08).

Si los hosts obtienen la IP por DHCP y el servidor está en otra VLAN, el gateway necesitará un agente de retransmisión (`ip helper-address`), que se trabaja en U08.

## 10.5. Verificación

### En el switch

```text
show vlan brief
show interfaces trunk
```

### En el router

```text
show ip interface brief
show running-config interface GigabitEthernet0/0.20
show ip route
show vlans
```

`show ip route` debe mostrar una ruta `C` (conectada) por cada subinterfaz: `C 10.10.10.0/24 is directly connected, GigabitEthernet0/0.10`. `show vlans` (en el router) muestra qué VLAN atiende cada subinterfaz.

### En el host

- dirección IP;
- máscara/prefijo;
- gateway;
- conectividad al gateway;
- conectividad a otra VLAN.

## 10.6. Error frecuente: culpar al routing demasiado pronto

Si un host ni siquiera alcanza su gateway, debemos considerar antes:

- puerto access;
- VLAN incorrecta;
- trunk;
- VLAN no permitida;
- subinterfaz incorrecta (por ejemplo, `encapsulation dot1Q 20` en la subinterfaz de VLAN 10);
- interfaz física del router en `shutdown`;
- dirección del host.

## 10.7. Límites de ROAS

- **Un único enlace** lleva todo el tráfico entre VLAN, que sube al router y vuelve a bajar por el mismo cable: puede convertirse en cuello de botella.
- **Punto único de fallo:** si falla el enlace o el router, se pierde toda la comunicación entre VLAN.

Por eso ROAS es adecuado para redes pequeñas y laboratorios, y en redes mayores se prefiere un switch multicapa.

### Idea clave

> ROAS combina un trunk de capa 2 con varias interfaces lógicas de capa 3.

# 11. SVI, switch multicapa y VLAN de gestión

La segunda solución de routing entre VLAN lleva el gateway **dentro del propio switch**: un switch multicapa tiene una interfaz virtual (SVI) por VLAN y enruta entre ellas sin cable adicional. La misma herramienta, la SVI, tiene un segundo uso en los switches de capa 2: dar al switch una **dirección IP de gestión**. Este apartado distingue ambos usos, porque se confunden con facilidad.

| Concepto | Pregunta que responde | Comando / ejemplo |
|---|---|---|
| **SVI** (*Switch Virtual Interface*) | ¿Qué interfaz L3 representa a una VLAN dentro del switch? | `interface vlan 20` |
| **Switch multicapa** (*multilayer / Layer 3 switch*) | ¿Puede un switch enrutar entre VLAN? | `ip routing` + una SVI por VLAN |
| **Puerto enrutado** (*routed port*) | ¿Cómo conecto el switch L3 a un router como si fuera una interfaz de router? | `no switchport` + `ip address` |
| **SVI de gestión** (*management SVI*) | ¿Cómo administro por IP un switch de capa 2? | `interface vlan 99` + `ip default-gateway` |
| **Estado de la SVI** (*SVI status*) | ¿Por qué una SVI está `down`? | VLAN inexistente o sin puertos activos |
| **ROAS frente a multicapa** (*ROAS vs. Layer 3 switch*) | ¿Qué solución elijo? | Tamaño, rendimiento, equipamiento |

Tener una SVI **no** significa que el switch enrute: en un switch de capa 2 la SVI solo sirve para gestionarlo.

## 11.1. Qué es una SVI

Una **SVI — Switch Virtual Interface** es una interfaz lógica asociada a una VLAN.

Ejemplo:

```text
interface vlan 20
 ip address 10.10.20.1 255.255.255.0
 no shutdown
```

La función exacta depende del tipo de switch y del diseño.

## 11.2. SVI como gateway

En un **multilayer switch**, una SVI puede actuar como gateway de una VLAN cuando el equipo realiza routing.

Con varias SVI:

```text
VLAN10 → SVI 10 → 10.10.10.1
VLAN20 → SVI 20 → 10.10.20.1
VLAN30 → SVI 30 → 10.10.30.1
```

Con routing habilitado, el switch multicapa puede enrutar entre esas redes.

En Cisco IOS el routing se activa con:

```text
ip routing
```

Configuración mínima completa en un switch multicapa (por ejemplo, Catalyst 3560 en Packet Tracer):

```text
MLS(config)# ip routing
MLS(config)# vlan 10
MLS(config-vlan)# name ADMIN
MLS(config-vlan)# vlan 20
MLS(config-vlan)# name USERS
MLS(config-vlan)# exit
MLS(config)# interface vlan 10
MLS(config-if)# ip address 10.10.10.1 255.255.255.0
MLS(config-if)# no shutdown
MLS(config-if)# interface vlan 20
MLS(config-if)# ip address 10.10.20.1 255.255.255.0
MLS(config-if)# no shutdown
```

Sin `ip routing`, el switch tiene IP en cada VLAN (se puede hacer ping a cada SVI desde su VLAN) pero **no reenvía** entre ellas. `show ip route` muestra entonces `Default gateway is not set` o similar en lugar de las rutas conectadas.

Para conectar el switch multicapa a un router (por ejemplo, hacia Internet), se puede convertir un puerto en **puerto enrutado**:

```text
interface GigabitEthernet0/1
 no switchport
 ip address 10.10.255.1 255.255.255.252
```

El routing hacia otras redes desde ese punto se estudia en U08 (estático) y U09 (dinámico).

## 11.3. SVI de gestión

En un switch de capa 2, una SVI puede utilizarse para administración IP del propio dispositivo.

Ejemplo conceptual:

```text
VLAN99 → MGMT
SVI VLAN99 → dirección de administración del switch
```

Configuración en un switch de acceso de capa 2 (SW1):

```text
SW1(config)# vlan 99
SW1(config-vlan)# name MGMT
SW1(config-vlan)# exit
SW1(config)# interface vlan 99
SW1(config-if)# ip address 10.10.99.11 255.255.255.0
SW1(config-if)# no shutdown
SW1(config-if)# exit
SW1(config)# ip default-gateway 10.10.99.1
```

- `ip default-gateway` es imprescindible para administrar el switch **desde otra subred**: un switch de capa 2 no enruta y necesita saber a quién enviar las respuestas.
- La VLAN de gestión debe estar permitida en los trunks que llevan hasta el equipo de administración.
- Buena práctica: usar una VLAN dedicada (no la VLAN 1).
- El acceso remoto seguro (SSH, líneas VTY) sobre esta IP se trabaja en U08.

Esto no significa automáticamente que el switch esté haciendo routing entre todas las VLAN.

## 11.4. Estado operativo de una SVI

Una SVI no debe interpretarse únicamente por su configuración escrita.

Debemos comprobar su estado real.

Comandos útiles:

```text
show ip interface brief
show vlan brief
```

Una SVI está `up/up` solo si se cumplen **las tres** condiciones:

1. la VLAN **existe** en la base de datos del switch;
2. hay **al menos un puerto activo** en esa VLAN (un access conectado o un trunk que la transporte en estado forwarding);
3. la SVI **no** está en `shutdown`.

Ejemplo de diagnóstico: `Vlan30 10.10.30.1 YES manual up down` indica que la SVI está habilitada pero no hay ningún puerto activo en VLAN 30 (o la VLAN no existe).

## 11.5. ROAS frente a switch multicapa

| Aspecto | Router-on-a-stick | Switch multicapa |
|---|---|---|
| Gateway | subinterfaces de router | SVI |
| Transporte al gateway | trunk hacia router | interno al switch L3 |
| Rendimiento | limitado por un único enlace | conmutación L3 por hardware, mucho mayor |
| Escalabilidad | adecuada en escenarios pequeños/lab | mejor para redes de campus |
| Dependencia | enlace físico al router | capacidad L3 del switch |
| Comando clave | `encapsulation dot1Q` | `ip routing` + `interface vlan` |

No existe una única solución universal; depende del tamaño, requisitos y equipamiento.

## 11.6. IPv6

La misma idea general de separación por VLAN y gateway puede aplicarse a IPv6, aunque la configuración y mecanismos de descubrimiento pertenezcan al modelo IPv6 estudiado en U05.

Aquí basta con reconocer que una VLAN puede transportar tráfico IPv4, IPv6 o ambos, y que una subinterfaz o una SVI pueden tener también dirección IPv6 (`ipv6 address`), con `ipv6 unicast-routing` activado si el equipo debe enrutar IPv6.

### Idea clave

> Una SVI es una interfaz lógica asociada a una VLAN; puede servir para gestión o para routing según el dispositivo y el diseño.

# 12. Diseño y despliegue integrado

Hasta aquí hemos visto cada pieza por separado. En una red real todas deben encajar y, además, quedar **documentadas** para que otra persona pueda entenderlas y cambiarlas sin romper nada. Este apartado reúne las piezas en cuatro documentos de diseño y un procedimiento de cambio.

| Documento / práctica | Pregunta que responde | Contenido |
|---|---|---|
| **Matriz VLAN** (*VLAN matrix*) | ¿Qué VLAN existen y para qué? | VLAN, nombre, subred, gateway, uso |
| **Tabla de puertos** (*port map*) | ¿Qué hay conectado a cada puerto y en qué modo? | Switch, puerto, modo, VLAN, uso |
| **Tabla de trunks** (*trunk table*) | ¿Qué VLAN atraviesan cada enlace? | Native, allowed, redundancia |
| **Plan de cambios** (*change plan*) | ¿Cómo aplico un cambio sin riesgo? | Pre-check → cambio → verificación → rollback |
| **Cambio mínimo** (*minimal change*) | ¿Cómo sé qué modificación arregló o rompió algo? | Estado previo → cambio concreto → estado posterior |

La documentación **no** es un añadido final: forma parte del despliegue.

## 12.1. Diseñar un sistema mantenible

Un despliegue VLAN profesional debería poder entenderse a partir de su documentación.

No basta con que «funcione ahora».

Debe quedar claro:

- qué VLAN existen;
- para qué sirve cada una;
- qué subred utiliza;
- cuál es su gateway;
- qué puertos son access;
- qué enlaces son trunk;
- qué VLAN atraviesan cada trunk;
- qué native VLAN se utiliza;
- dónde se realiza el routing;
- qué mecanismos de redundancia existen.

## 12.2. Matriz VLAN

Ejemplo:

| VLAN | Nombre | Subred | Gateway | Uso |
|---:|---|---|---|---|
| 10 | ADMIN | `10.10.10.0/24` | `10.10.10.1` | Administración |
| 20 | USERS | `10.10.20.0/24` | `10.10.20.1` | Usuarios |
| 30 | SERVERS | `10.10.30.0/24` | `10.10.30.1` | Servidores |
| 40 | VOICE | `10.10.40.0/24` | `10.10.40.1` | Telefonía |
| 99 | MGMT | `10.10.99.0/24` | `10.10.99.1` | Gestión |
| 666 | PARKING | — | — | Puertos no utilizados |
| 999 | NATIVE | — | — | Native VLAN de los trunks (sin usuarios) |

## 12.3. Tabla de puertos

| Switch | Puerto | Modo | VLAN/Allowed | Uso |
|---|---|---|---|---|
| SW1 | Gi0/1 | access | 10 | PC Admin |
| SW1 | Gi0/2 | access + voice | data 20 / voice 40 | Teléfono + PC |
| SW1 | Gi0/15–22 | access, `shutdown` | 666 | Puertos libres |
| SW1 | Gi0/23 | trunk | 10,20,40,99 | SW2 |
| SW1 | Po1 | trunk | 10,20,30,40,99 | SW3 |

## 12.4. Tabla de trunks

| Enlace | Native | Allowed | Redundancia | Observación |
|---|---:|---|---|---|
| SW1–SW2 | 999 | 10,20,40,99 | STP | VLAN30 no necesaria |
| SW1–SW3 | 999 | 10,20,30,40,99 | Po1/LACP | Port-channel |

Los valores son ejemplos de diseño, no normas universales. La native 999 es una VLAN sin usuarios; no hace falta incluirla en la lista `allowed` porque no debe transportar tráfico de usuarios.

## 12.5. Plan de cambios

Una secuencia profesional simple es:

```text
pre-check
→ cambio
→ verificación
→ rollback si es necesario
```

### Pre-check

Antes de modificar:

- leer configuración actual;
- comprobar VLAN;
- comprobar trunks;
- comprobar STP/EtherChannel;
- comprobar gateway;
- disponer de copia o forma de revertir (por ejemplo, `copy running-config startup-config` antes de empezar y guardar la salida de los `show`).

### Cambio

Aplicar únicamente lo planificado.

### Verificación

Comprobar:

- VLAN;
- puertos;
- MAC;
- trunks;
- allowed/native;
- STP/EtherChannel;
- gateway;
- intra-VLAN;
- inter-VLAN.

### Rollback

Debe existir una idea clara de qué revertir si la validación falla (por ejemplo, el comando inverso de cada cambio: `switchport trunk allowed vlan remove 30` para deshacer un `add 30`).

## 12.6. Cambio mínimo y trazable

Evitar:

> «Reconfigurar todo hasta que funcione».

Preferir:

```text
estado previo
→ cambio concreto
→ estado posterior
```

### Idea clave

> Una red mantenible es una red cuyo diseño puede explicarse, verificarse y modificarse sin depender de memoria informal.

# 13. Diagnóstico integrado de VLAN

Cuando algo falla en una red con VLAN, el número de posibles causas es grande: puerto, VLAN, trunk, native, STP, bundle, gateway, routing… Este apartado propone un método para **no probar comandos al azar**: primero delimitar el alcance del fallo, después elegir la prueba que más hipótesis descarta, y solo entonces cambiar lo mínimo y verificar.

| Paso | Pregunta que responde | Ejemplo |
|---|---|---|
| **Alcance** (*scope*) | ¿Falla un host, una VLAN, un enlace o solo entre VLAN? | Solo VLAN 20 falla |
| **Hipótesis** (*hypothesis*) | ¿Qué capa de decisión puede explicarlo? | VLAN 20 no permitida en el trunk |
| **Prueba** (*test*) | ¿Qué comando aporta la evidencia? | `show interfaces trunk` |
| **Hecho frente a hipótesis** (*fact vs. hypothesis*) | ¿Qué he visto y qué estoy suponiendo? | «No aparece 20» es un hecho |
| **Cambio mínimo** (*minimal change*) | ¿Qué es lo menos que debo cambiar? | `allowed vlan add 20` |
| **Verificación** (*verification*) | ¿Funciona lo que fallaba y sigue funcionando lo demás? | Ping intra e inter-VLAN |
| **Documentación** (*incident report*) | ¿Cómo dejo constancia? | Plantilla de incidencia |

Comparar **qué funciona** con **qué falla** es la herramienta más rápida para descartar hipótesis.

## 13.1. No empezar por comandos al azar

El objetivo del troubleshooting no es ejecutar toda la lista de comandos disponible.

Debemos localizar el **dominio probable del fallo**.

Una secuencia orientativa es:

```text
síntoma
→ alcance
→ endpoint/puerto
→ VLAN
→ MAC
→ trunk
→ allowed/active
→ native
→ STP/EtherChannel
→ VTP si aplica
→ IP/gateway
→ inter-VLAN routing
```

No siempre necesitamos recorrer todos los pasos.

## 13.2. Determinar el alcance

| Alcance | Hipótesis probables |
|---|---|
| Falla un único host | Puerto access incorrecto, endpoint, IP, Port Security, cableado |
| Falla una VLAN completa | VLAN inexistente, trunk/allowed list, STP para esa VLAN, gateway, VTP si se utiliza |
| Fallan todas las VLAN entre dos switches | Enlace, trunk (modo/DTP), Port-channel, STP, configuración común |
| Funciona dentro de la VLAN pero no entre VLAN | Gateway, trunk hacia router, subinterfaz, SVI, `ip routing` |

### Falla un único host

Hipótesis probables:

- puerto access incorrecto;
- endpoint;
- dirección IP;
- Port Security;
- cableado.

### Falla una VLAN completa

Hipótesis probables:

- VLAN inexistente;
- trunk/allowed list;
- STP para esa VLAN;
- gateway;
- VTP si se utiliza.

### Fallan todas las VLAN entre dos switches

Hipótesis probables:

- enlace;
- trunk (por ejemplo, ambos extremos en `dynamic auto`, apartado 6.3);
- Port-channel;
- STP;
- configuración común.

### Funciona dentro de la VLAN pero no entre VLAN

Hipótesis probables:

- gateway;
- trunk hacia router;
- subinterface;
- SVI;
- routing (por ejemplo, falta `ip routing` en el switch multicapa).

## 13.3. Caso: puerto en VLAN incorrecta

Esperado:

```text
Gi0/8 → VLAN20
```

Observado:

```text
Gi0/8 → VLAN10
```

Aunque el host tenga una dirección de la subred de VLAN20, su tráfico entra en el dominio L2 incorrecto.

Evidencia: `show vlan brief` o `show interfaces Gi0/8 switchport` (`Access Mode VLAN: 10`).

## 13.4. Caso: allowed list incompleta

Síntoma:

```text
VLAN10 funciona
VLAN20 falla
```

Mismo enlace entre switches.

Una buena prueba es:

```text
show interfaces trunk
```

Si VLAN20 no está permitida, tenemos evidencia concreta.

## 13.5. Caso: VLAN permitida pero no activa

Puede aparecer en la allowed list y faltar en la base local (por ejemplo, en un switch intermedio donde nadie la creó).

Comprobar también:

```text
show vlan brief
```

## 13.6. Caso: native VLAN mismatch

Comprobar **ambos extremos** del trunk (`show interfaces trunk` en cada uno, mensajes CDP en consola).

No cambiar uno al azar.

## 13.7. Caso: Port-channel

Si el diseño usa `Po1`:

```text
show etherchannel summary
```

es una prueba prioritaria antes de analizar miembros individuales de forma aislada.

## 13.8. Caso: inter-VLAN

Observación:

```text
host VLAN20 ↔ host VLAN20 = funciona
host VLAN20 ↔ host VLAN10 = falla
```

Esto demuestra que una parte importante del switching L2 de VLAN20 funciona.

La investigación puede pasar a:

```text
gateway
→ trunk al dispositivo L3
→ subinterface/SVI
→ routing
```

Pruebas útiles: ping desde el host a **su** gateway; ping al gateway de **la otra** VLAN; `show ip interface brief` y `show ip route` en el router o switch multicapa.

## 13.9. Hecho frente a hipótesis

### Hecho

> `show interfaces trunk` no muestra VLAN20 dentro de las VLAN permitidas de Gi0/24.

### Hipótesis

> VLAN20 falla porque no está permitida en el trunk.

La hipótesis se apoya en un hecho observable, pero debe verificarse tras el cambio.

## 13.10. Cambio mínimo

Si la evidencia identifica una allowed list incorrecta, no necesitamos reconstruir toda la configuración.

Debemos corregir únicamente la discrepancia necesaria y después volver a probar:

```text
interface GigabitEthernet0/24
 switchport trunk allowed vlan add 20
```

(Y no `switchport trunk allowed vlan 20`, que reemplazaría la lista: apartado 5.6.)

## 13.11. Verificación

Una corrección no está terminada hasta comprobar:

- el estado corregido;
- la conectividad esperada;
- que no se ha roto tráfico que antes funcionaba.

## 13.12. Documentación de una incidencia

Formato útil:

```text
Síntoma:
Alcance:
Estado esperado:
Hechos observados:
Hipótesis:
Prueba seleccionada:
Evidencia:
Cambio realizado:
Verificación:
Conclusión:
```

### Idea clave

> Comparar qué funciona con qué falla suele reducir hipótesis más rápido que ejecutar comandos sin una pregunta concreta.

# 14. Comandos de observación esenciales

Este apartado reúne en un solo sitio los comandos de verificación de la unidad. No es una receta que haya que ejecutar entera: cada comando responde a **una pregunta concreta**, y lo profesional es elegir el que aporta la evidencia que necesitamos.

| Comando | Pregunta que responde | Dónde se ejecuta |
|---|---|---|
| `show vlan brief` | ¿Qué VLAN existen y qué puertos access tienen? | Switch |
| `show interfaces <int> switchport` | ¿Qué modo (administrativo y operativo), VLAN de acceso, voz y native tiene un puerto? | Switch |
| `show mac address-table [vlan N]` | ¿Dónde se ha aprendido cada MAC y en qué VLAN? | Switch |
| `show interfaces trunk` | ¿Qué puertos son trunk, con qué native y qué VLAN permiten/activas? | Switch |
| `show spanning-tree vlan N` | ¿Quién es root y qué puertos reenvían para esa VLAN? | Switch |
| `show etherchannel summary` | ¿El Port-channel está formado y con qué miembros? | Switch |
| `show vtp status` | ¿Qué dominio, modo y revisión VTP tiene el switch? | Switch |
| `show ip interface brief` | ¿Qué subinterfaces o SVI tienen IP y están `up/up`? | Router / switch |
| `show ip route` | ¿Tiene el dispositivo L3 una ruta conectada por VLAN? | Router / switch multicapa |
| `show vlans` | ¿Qué VLAN atiende cada subinterfaz? | Router (ROAS) |

## VLAN y access

```text
show vlan brief
show interfaces switchport
show interfaces GigabitEthernet0/8 switchport
show mac address-table
```

## Trunks

```text
show interfaces trunk
```

## STP y EtherChannel

```text

show etherchannel summary
```

## VTP

```text

```

## Routing inter-VLAN

```text
show ip interface brief
```

La pregunta correcta es siempre:

# 15. Errores frecuentes

Los errores de este apartado no son de sintaxis, sino de **razonamiento**: conclusiones que parecen lógicas pero no lo son. Reconocerlos ahorra mucho tiempo de diagnóstico.

| Error | Idea correcta |
|---|---|
| «VLAN y subred son lo mismo» | Se asocian, pero son capa 2 y capa 3 |
| «Crear la VLAN ya coloca los puertos dentro» | Crear y asignar son pasos distintos |
| «El trunk está `up`, así que todas las VLAN funcionan» | Hay que comprobar allowed, active y native |
| «Si DTP negocia, el diseño es correcto» | Negociar no valida el diseño |
| «Dos VLAN se comunican porque están en el mismo switch» | Hace falta routing de capa 3 |
| «Una SVI siempre hace routing» | En un switch L2 solo sirve para gestión |
| «VTP configura todo el sistema VLAN» | Solo distribuye la lista de VLAN |
| «`allowed vlan 30` añade la VLAN 30» | Reemplaza la lista; se usa `add` |
| Cambiar varias cosas a la vez | Un cambio mínimo cada vez, y verificar |

## Error 1. «VLAN y subred son lo mismo»

No. Se suelen asociar, pero pertenecen a capas diferentes.

## Error 2. «Crear la VLAN ya coloca los puertos dentro»

No. Debemos comprobar la asignación de cada access port.

## Error 3. «El trunk está `up`, así que todas las VLAN funcionan»

Falso. Debemos comprobar allowed, active, native y el estado específico de cada VLAN.

## Error 4. «Si DTP negocia, el diseño es correcto»

No. Una negociación exitosa no demuestra que ese trunk deba existir ni que transporte las VLAN correctas.

## Error 5. «Dos VLAN pueden comunicarse porque están en el mismo switch»

No si representan subredes distintas y no existe routing entre ellas.

## Error 6. «Una SVI siempre hace routing»

No. Puede existir únicamente para gestión en un switch de capa 2. Incluso en un switch multicapa, sin `ip routing` no enruta.

## Error 7. «VTP configura todo el sistema VLAN»

No. No sustituye access ports, trunks, gateways ni routing.

## Error 8. «`switchport trunk allowed vlan 30` añade la VLAN 30»

No. Reemplaza toda la lista por «30». Para añadir se usa `switchport trunk allowed vlan add 30`.

## Error 9. Cambiar varias cosas a la vez

Dificulta saber qué modificación resolvió o empeoró el problema.

# 16. Síntesis de la unidad

Este apartado resume la unidad en una secuencia y doce ideas. Sirve para repasar antes del examen o para comprobar, al final del estudio, que las piezas encajan.

| Bloque | Pregunta clave | Evidencia típica |
|---|---|---|
| Segmentar (1–3) | ¿Cada equipo está en la VLAN de su diseño? | `show vlan brief` |
| Transportar (4–8) | ¿Cada enlace lleva las VLAN correctas con la native correcta? | `show interfaces trunk` |
| Comunicar (9–11) | ¿Cada VLAN tiene gateway y hay routing entre ellas? | `show ip interface brief`, `show ip route` |
| Operar (12–13) | ¿Está documentado y se diagnostica con evidencia? | Matriz VLAN, informe de incidencia |

Una VLAN permite construir varios dominios lógicos de capa 2 sobre una infraestructura física compartida.

El proceso completo puede representarse así:

```text
necesidad organizativa
→ diseño VLAN
→ access ports
→ 802.1Q
→ trunks
→ allowed/native
→ integración con STP/EtherChannel
→ gateway por VLAN
→ routing inter-VLAN
→ documentación
→ diagnóstico
```

Las ideas que debes conservar son:

1. **VLAN, subred y política de seguridad son conceptos diferentes.**
2. **La configuración debe partir de un diseño.**
3. **Un access port clasifica un endpoint dentro de una VLAN.**
4. **802.1Q permite transportar identidad VLAN por enlaces compartidos.**
5. **Un trunk operativo no demuestra que todas las VLAN funcionen.**
6. **Allowed y native deben ser coherentes en el diseño.**
7. **DTP y VTP son tecnologías Cisco útiles de reconocer, pero no sustituyen decisiones de arquitectura.**
8. **STP y EtherChannel de U06 siguen siendo relevantes cuando transportamos VLAN.**
9. **Las VLAN no se comunican entre sí sin routing de capa 3 cuando usan subredes diferentes.**
10. **ROAS y multilayer switching son dos formas de proporcionar inter-VLAN routing.**
11. **La documentación forma parte del despliegue.**
12. **El troubleshooting debe basarse en preguntas, pruebas y evidencia.**

# 17. Glosario esencial

Muchos términos de esta unidad se usan en inglés en la documentación, en los comandos y en el trabajo profesional. El glosario reúne el término en español (cuando se usa) y el término en inglés que encontrarás en la CLI y en los manuales.

| Término | Significado |
|---|---|
| **VLAN** (*Virtual LAN*) | red local virtual; dominio lógico de capa 2 |
| **Identificador de VLAN** (*VLAN ID, VID*) | número de 12 bits que identifica la VLAN (1–4094) |
| **Dominio de difusión** (*broadcast domain*) | conjunto de dispositivos que reciben un broadcast dentro del mismo dominio L2 |
| **VLAN por defecto** (*default VLAN*) | VLAN 1 en Cisco; no se puede borrar |
| **Puerto de acceso** (*access port*) | puerto asociado normalmente a una VLAN de datos |
| **VLAN de voz** (*voice VLAN*) | VLAN utilizada para tráfico de voz en el escenario estudiado |
| **Con etiqueta** (*tagged*) | trama que incluye información de VLAN 802.1Q |
| **Sin etiqueta** (*untagged*) | trama sin tag 802.1Q en el punto observado |
| **IEEE 802.1Q** | estándar de etiquetado VLAN |
| **TPID** (*Tag Protocol Identifier*) | identificador del protocolo de etiquetado (`0x8100`) |
| **Enlace troncal** (*trunk*) | enlace que transporta varias VLAN |
| **VLAN permitida** (*allowed VLAN*) | VLAN autorizada a atravesar un trunk |
| **VLAN nativa** (*native VLAN*) | VLAN a la que se asigna el tráfico sin etiqueta de un trunk 802.1Q |
| **DTP** (*Dynamic Trunking Protocol*) | protocolo Cisco de negociación de trunk |
| **Salto de VLAN** (*VLAN hopping*) | ataque para enviar tráfico a una VLAN a la que no se pertenece |
| **Port-channel** | interfaz lógica creada por EtherChannel |
| **VTP** (*VLAN Trunking Protocol*) | protocolo Cisco de distribución de información VLAN |
| **Número de revisión** (*configuration revision*) | indicador de versión/cambio en VTP clásico |
| **Routing entre VLAN** (*inter-VLAN routing*) | routing entre redes asociadas a VLAN diferentes |
| **Router-on-a-stick** (*ROAS*) | routing mediante subinterfaces sobre un trunk |
| **Subinterfaz** (*subinterface*) | interfaz lógica derivada de una interfaz física |
| **SVI** (*Switch Virtual Interface*) | interfaz virtual asociada a una VLAN |
| **Switch multicapa** (*multilayer switch*, *Layer 3 switch*) | switch capaz de realizar funciones de capa 3 |
| **Puerto enrutado** (*routed port*) | puerto de un switch multicapa que funciona como interfaz de router (`no switchport`) |
| **VLAN de gestión** (*management VLAN*) | VLAN utilizada para administración de infraestructura |

# 18. Mapa final de diagnóstico

Este mapa resume el apartado 13 en forma de preguntas encadenadas. Cada pregunta tiene un comando que la responde; no hace falta recorrerlas todas, sino elegir en cada momento la que más información aporta.

| Pregunta | Comando que aporta la evidencia |
|---|---|
| ¿El puerto está en la VLAN correcta? | `show interfaces <int> switchport`, `show vlan brief` |
| ¿La VLAN existe? | `show vlan brief` |
| ¿La MAC aparece donde espero? | `show mac address-table vlan N` |
| ¿El trunk transporta la VLAN (allowed/active)? | `show interfaces trunk` |
| ¿Native es coherente en ambos extremos? | `show interfaces trunk` en los dos switches |
| ¿STP/EtherChannel permiten el camino? | `show spanning-tree vlan N`, `show etherchannel summary` |
| ¿VTP interviene? | `show vtp status` |
| ¿ROAS/SVI están operativos? | `show ip interface brief`, `show vlans` |
| ¿El routing funciona? | `show ip route`, ping entre gateways |

Cuando aparezca un problema VLAN, una secuencia mental útil es:

```text
¿qué debería funcionar?
→ ¿qué funciona realmente?
→ ¿cuál es el alcance?
→ ¿el puerto está en la VLAN correcta?
→ ¿la VLAN existe?
→ ¿la MAC aparece donde espero?
→ ¿el trunk transporta la VLAN?
→ ¿allowed y active coinciden?
→ ¿native es coherente?
→ ¿STP/EtherChannel permiten el camino?
→ ¿VTP interviene en este diseño?
→ ¿IP y gateway son correctos?
→ ¿ROAS/SVI están operativos?
→ ¿el routing funciona?
→ ¿qué evidencia demuestra la causa?
```

No necesitas ejecutar todos los pasos siempre.

El objetivo profesional es seleccionar **la siguiente prueba que aporte más información**.
