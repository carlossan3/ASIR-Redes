---
title: "U03 — Infraestructura y conectividad"
---

> **Pregunta guía:** ¿Qué condiciones físicas y de acceso debe cumplir una red para que los dispositivos puedan conectarse de forma estable, verificable y con las prestaciones esperadas?

En U01 construimos un primer mapa de una red. En U02 formalizamos capas, encapsulación y análisis de tráfico. En esta unidad descendemos hasta la infraestructura que hace posible que los bits puedan circular realmente: interfaces, cobre, fibra, radio, terminaciones, negociación, alimentación, medidas, documentación y evidencias de estado.

La pregunta principal de U03 no es todavía si una subred IPv4 está bien calculada. Esa cuestión se estudiará en U04. Aquí aprenderemos primero a responder otra pregunta: **¿existe una conectividad física o radioeléctrica correcta y podemos demostrarlo mediante evidencias?**

El hilo conductor será profesional y verificable:

```text
síntoma → pregunta → hipótesis → prueba → evidencia → conclusión
```

Cuando exista una avería real, añadiremos dos pasos más:

```text
→ cambio mínimo → verificación
```

No se trata de memorizar catálogos de cables o conectores. Se trata de comprender qué función cumple cada elemento, qué limitaciones introduce y qué evidencia permite decidir si está funcionando correctamente.

# 1. Del dispositivo al enlace físico

Antes de configurar cualquier protocolo, debe existir un camino físico o radioeléctrico capaz de transportar señales.

## Conceptos básicos

| Concepto | Significado |
|---|---|
| **Adaptador de red** | Hardware que permite al equipo utilizar una tecnología de red |
| **Interfaz** | Punto físico o lógico mediante el que un dispositivo participa en una red |
| **Medio** | Entorno por el que se propaga la señal |
| **Señal** | Representación física de la información |
| **Enlace** | Conexión de comunicaciones entre dos interfaces |
| **Canal** | Recorrido completo del sistema de cableado entre extremos |
| **Transceptor** | Componente que adapta la señal a una interfaz/medio |

Ejemplos de medio y señal:

| Medio | Señal |
|---|---|
| Cobre | Eléctrica |
| Fibra óptica | Óptica |
| Aire | Radioeléctrica |

## Adaptadores de red

Un equipo puede utilizar:

- Ethernet integrado;
- tarjeta PCIe;
- adaptador USB–Ethernet;
- Wi‑Fi;
- interfaz virtual;
- interfaz de una máquina virtual.

Un switch o router puede incorporar:

- puertos de cobre;
- interfaces ópticas;
- módulos;
- transceptores;
- interfaces lógicas.

En U03 nos interesa principalmente el **estado físico/de acceso**.

## Interfaz

Una interfaz puede aportar información como:

```text
estado
velocidad
dúplex
dirección física
estadísticas
configuración
```

Ejemplos:

```text
Ethernet
Wi-Fi
Gi1/0/18
SFP interface
vNIC
```

No confundas:

```text
dispositivo
≠
adaptador
≠
interfaz
≠
medio
```

## Recorrido físico

Una conexión real puede ser:

```text
PC
→ interfaz Ethernet
→ latiguillo
→ roseta
→ cable horizontal
→ patch panel
→ latiguillo de rack
→ puerto del switch
```

Cada elemento puede ser una dependencia.

Por eso el síntoma:

> “El PC no tiene red”

no demuestra cuál de esos componentes falla.

## LED como evidencia inicial

Los LED varían según fabricante/modelo, pero pueden indicar:

- alimentación;
- estado del sistema;
- presencia de enlace;
- actividad;
- velocidad;
- PoE.

Ejemplo:

```text
LED de link apagado
→ evidencia inicial
→ revisar enlace físico
```

Pero:

```text
LED encendido
≠
comunicación IP demostrada
```

Un LED no demuestra:

- direccionamiento correcto;
- VLAN correcta;
- routing correcto;
- DNS;
- funcionamiento de la aplicación.

## Link up y link down

```text
link down
→ no existe enlace físico operativo

link up
→ existe una forma de enlace detectada
```

Pero:

```text
link up
+
configuración lógica incorrecta
=
sin comunicación útil
```

Por tanto:

> **`link up` demuestra algo, pero no lo demuestra todo.**

# 2. Prestaciones y degradación del medio

Una interfaz puede estar activa y funcionar muy por debajo de lo esperado.

## Capacidad nominal y throughput

La **capacidad nominal** expresa una tasa máxima prevista bajo determinadas condiciones.

Ejemplos:

```text
100 Mb/s
1 Gb/s
10 Gb/s
```

El **throughput** es la cantidad real de datos útiles transferidos.

Por tanto:

```text
capacidad nominal
≠
throughput real
```

El rendimiento puede verse afectado por:

- overhead;
- errores;
- retransmisiones;
- congestión;
- capacidad de los extremos;
- limitaciones de software;
- interferencia;
- características del medio;
- aplicación.

## Velocidad negociada

La velocidad de enlace observada puede ser:

```text
100 Mb/s
1 Gb/s
2.5 Gb/s
10 Gb/s
```

No es lo mismo que throughput.

Ejemplo:

```text
velocidad negociada = 1 Gb/s
throughput medido = 420 Mb/s
```

puede ser perfectamente posible.

## Atenuación

La **atenuación** es la reducción de intensidad de la señal al propagarse.

Puede aumentar por:

- distancia;
- conectores;
- empalmes;
- daños;
- curvaturas;
- instalación deficiente.

No necesitamos fórmulas avanzadas.

Debemos relacionar fenómeno y síntoma.

## Ruido e interferencia

El ruido añade energía no deseada.

Posibles fuentes:

- motores;
- alimentación eléctrica;
- cables próximos;
- transmisiones radio;
- otros equipos.

Puede provocar:

- errores;
- retransmisiones;
- reducción de throughput;
- renegociaciones;
- pérdida de enlace.

## Diafonía

La **diafonía** (*crosstalk*) es interferencia entre conductores o pares cercanos.

El trenzado de los pares ayuda a reducirla.

Por eso:

```text
continuidad correcta
+
demasiado destrenzado
→
puede existir degradación
```

## Síntoma no equivale a causa

| Observación | Hipótesis compatibles |
|---|---|
| Enlace a 100 Mb/s cuando se esperaba 1 Gb/s | Pares, terminación, cable, negociación, adaptador |
| CRC/FCS aumentando | Medio, conectores, interferencia, interfaz |
| Link flaps | Cable, conector, alimentación, transceptor, interfaz |
| Wi‑Fi inestable | Cobertura, interferencia, ocupación, cliente |

Esta tabla no diagnostica.

Genera hipótesis.

La secuencia correcta es:

```text
síntoma
→ hipótesis
→ prueba
→ evidencia
```

---

## Caso

Se observa:

```text
esperado: 1 Gb/s
observado: 100 Mb/s
```

Escribe al menos cuatro hipótesis.

Después selecciona la **primera prueba de mayor valor**.

# 3. Cobre y cableado estructurado

## Par trenzado

El cable Ethernet habitual de cobre contiene cuatro pares trenzados.

El trenzado contribuye a:

- reducir interferencia;
- reducir diafonía;
- mantener equilibrio eléctrico.

Debe conservarse hasta lo más cerca posible de la terminación.

## Categorías que interesa reconocer

| Categoría | Uso orientativo |
|---|---|
| **Cat 5e** | Gigabit Ethernet en instalaciones adecuadas |
| **Cat 6** | Gigabit y mayores prestaciones según tecnología/distancia |
| **Cat 6A** | 10GBASE-T en canal adecuado |

No es necesario memorizar todas las categorías existentes.

## Cable y canal no son lo mismo

Idea profesional:

```text
categoría del cable
≠
prestación garantizada del canal
```

El canal puede contener:

```text
latiguillo
+
roseta/keystone
+
cable horizontal
+
patch panel
+
latiguillo
+
terminaciones
```

Un único componente deficiente puede limitar el conjunto.

Ejemplo:

```text
cable horizontal Cat 6A
+
keystone Cat 5e
+
latiguillos Cat 6A
→
no permite afirmar que el canal completo sea Cat 6A
```

## Apantallamiento

Designaciones frecuentes:

| Designación | Significado inicial |
|---|---|
| U/UTP | Sin pantalla |
| F/UTP | Pantalla general |
| U/FTP | Pantalla sobre pares |
| S/FTP | Pantalla general y sobre pares |

No se trata de memorizar todas las combinaciones.

El apantallamiento debe formar parte de un sistema de instalación coherente.

## Calidad del material

Una especificación comercial no sustituye una instalación adecuada.

Material o terminaciones deficientes pueden producir:

- resistencia excesiva;
- calentamiento;
- peor funcionamiento PoE;
- menor margen de señal;
- menor fiabilidad;
- peor comportamiento a frecuencias altas.

---

## Cableado estructurado

El cableado estructurado organiza la infraestructura para que sea:

- mantenible;
- ampliable;
- trazable;
- verificable;
- documentable.

Elementos habituales:

- roseta;
- keystone;
- cable horizontal;
- patch panel;
- latiguillo;
- rack;
- organizadores;
- etiquetado.

## Enlace permanente

Parte fija:

```text
roseta
→ cable horizontal
→ patch panel
```

## Canal

Recorrido completo:

```text
equipo
→ latiguillo
→ enlace permanente
→ latiguillo
→ switch
```

## 8P8C y “RJ45”

El conector modular habitual se denomina técnicamente **8P8C**.

En el uso cotidiano se utiliza ampliamente el nombre “RJ45”.

Conviene reconocer ambos términos.

## T568A y T568B

| Pin | T568A | T568B |
|---:|---|---|
| 1 | blanco/verde | blanco/naranja |
| 2 | verde | naranja |
| 3 | blanco/naranja | blanco/verde |
| 4 | azul | azul |
| 5 | blanco/azul | blanco/azul |
| 6 | naranja | verde |
| 7 | blanco/marrón | blanco/marrón |
| 8 | marrón | marrón |

Ambos esquemas son válidos.

Lo importante es aplicar de forma coherente el esquema previsto.

## Cable directo y cruzado

Directo:

```text
A ↔ A
B ↔ B
```

Cruzado:

```text
A ↔ B
```

Históricamente se elegía según el tipo de dispositivos.

Hoy muchos equipos incorporan **Auto MDI-X**.

Por tanto:

> “PC-switch siempre directo y switch-switch siempre cruzado”

no debe aprenderse como una regla universal actual.

## Auto MDI-X

Auto MDI-X puede adaptar automáticamente pares de transmisión/recepción.

No repara:

- conductores abiertos;
- cortos;
- split pairs;
- terminaciones defectuosas.

```text
Auto MDI-X
≠
auto-reparación del cable
```

## Cable de consola

El **cable de consola** no transporta tráfico de red: conecta el puerto de administración (*console*) de un switch o router con el puerto serie o USB de un ordenador, para configurar el equipo con un emulador de terminal (PuTTY, Tera Term, `screen`).

| Tipo | Conectores | Observaciones |
|---|---|---|
| Rollover (clásico) | RJ-45 ↔ DB-9 o RJ-45 ↔ RJ-45 + adaptador | Los hilos están invertidos de extremo a extremo (1↔8, 2↔7…) |
| USB | USB ↔ mini-USB/USB-C del equipo | Habitual en equipos actuales; requiere controlador |
| Adaptador USB–serie | USB ↔ DB-9 | Para portátiles sin puerto serie |

Parámetros habituales del terminal: **9600 baudios, 8 bits de datos, sin paridad, 1 bit de parada, sin control de flujo (9600 8N1)**.

Un cable de consola no se comprueba con un tester Ethernet de wiremap convencional como un latiguillo: su esquema de hilos es distinto a propósito.

## Ethernet sobre cobre

Tecnologías de referencia:

| Tecnología | Velocidad | Pares utilizados |
|---|---:|---:|
| 100BASE-TX | 100 Mb/s | 2 |
| 1000BASE-T | 1 Gb/s | 4 |
| 10GBASE-T | 10 Gb/s | 4 |

También existen 2.5GBASE-T y 5GBASE-T.

Un defecto en determinados pares puede permitir que exista enlace pero impedir la velocidad esperada.

# 4. Autonegociación, dúplex y PoE

## Autonegociación

Los extremos pueden acordar automáticamente:

- velocidad;
- dúplex;
- determinadas capacidades.

La velocidad negociada es una **observación**, no una causa.

Ejemplo:

```text
NIC Gigabit
+
switch Gigabit
+
speed observada = 100 Mb/s
```

Hipótesis compatibles:

- pares no disponibles;
- terminación;
- cable;
- capacidad real;
- configuración;
- adaptador.

## Full-duplex

En **full-duplex** se puede transmitir y recibir simultáneamente.

```text
PC ⇄ switch
```

Es el comportamiento habitual esperado en Ethernet conmutada moderna.

## Dúplex como evidencia

Un valor de dúplex inesperado puede indicar una incidencia de negociación/configuración.

Pero el valor debe interpretarse junto a:

- velocidad;
- errores;
- configuración;
- tipo de enlace.

## PoE

**Power over Ethernet (PoE)** permite transportar energía y datos por el cableado Ethernet.

Usos frecuentes:

- access point;
- cámara IP;
- teléfono IP.

Antes de afirmar “PoE no funciona”, comprobar:

- compatibilidad del dispositivo alimentado;
- capacidad de la fuente/switch;
- potencia requerida;
- potencia disponible;
- calidad del canal.

En U03 PoE se estudia a nivel funcional.

No se requiere diseñar presupuestos complejos.

## Datos y alimentación comparten dependencia

Un fallo de cableado puede afectar:

```text
datos
+
alimentación
```

Ejemplo:

```text
AP con reinicios
+
link flaps
+
PoE
```

puede justificar revisar canal y alimentación antes de culpar al software.

# 5. Comprobación del cableado

Una herramienta es útil solo si comprendemos **qué mide** y **qué no demuestra**.

## Inspección visual

Antes del tester:

- revisar conectores;
- buscar daños;
- observar pestañas;
- detectar aplastamientos;
- revisar orden;
- observar exceso de destrenzado;
- comprobar etiquetado.

La inspección no sustituye a la medición.

Pero puede evitar pruebas innecesarias.

## Wiremap

Un tester básico puede mostrar la relación entre conductores.

| Resultado | Interpretación inicial |
|---|---|
| **Open** | Falta continuidad |
| **Short** | Conductores unidos indebidamente |
| **Reversed / miswired** | Orden incorrecto |
| **Crossed** | Correspondencia cruzada |
| **Split pair** | Pines con continuidad pero pares eléctricos incorrectos |

## Split pair

Es un fallo especialmente importante.

Puede ocurrir:

```text
continuidad pin a pin correcta
+
pares mal formados
=
wiremap que parece parcialmente válido
pero mal comportamiento eléctrico
```

## Longitud y distancia al fallo

Algunos testers pueden estimar:

- longitud;
- distancia al defecto.

No todos ofrecen estas funciones.

## Límites de un tester básico

Puede aportar evidencia de:

- continuidad;
- orden;
- determinados defectos;
- a veces longitud.

Pero no demuestra automáticamente:

- categoría real del canal;
- límites de diafonía;
- rendimiento real;
- aptitud para 10G;
- certificación normativa completa.

Por tanto:

```text
wiremap correcto
≠
canal certificado
```

## Medir una hipótesis

Ejemplo:

```text
Síntoma:
1 Gb/s esperado → 100 Mb/s observado

Hipótesis:
algún par no está disponible

Prueba:
wiremap

Resultado:
open pair
```

Interpretación prudente:

> El resultado es coherente con la hipótesis.

No necesitamos afirmar más de lo que la prueba demuestra.

# 6. Fabricación, reparación y verificación de latiguillos

Fabricar un cable es solo una parte de la competencia.

La secuencia completa es:

```text
fabricar
→ inspeccionar
→ medir
→ interpretar
→ reparar
→ volver a medir
→ documentar
```

## Seguridad y organización

- mantener mesa ordenada;
- utilizar adecuadamente crimpadora y herramientas de corte;
- recoger restos de conductor;
- no manipular energía innecesariamente;
- identificar cada cable.

## Procedimiento de fabricación

1. seleccionar T568A o T568B;
2. retirar cubierta sin dañar conductores;
3. conservar el trenzado lo máximo posible;
4. ordenar pares;
5. comprobar colores;
6. cortar uniformemente;
7. insertar en 8P8C;
8. verificar visualmente;
9. crimpar;
10. repetir el otro extremo.

## La práctica no termina con el crimpado

Después:

```text
inspección
→ wiremap
→ interpretación
```

No basta:

```text
“se enciende el LED”
→ práctica terminada
```

## Diagnóstico con fallos preparados

Puede recibirse un cable con fallo desconocido:

- open;
- conductores intercambiados;
- split pair;
- terminación deficiente.

Procedimiento:

```text
resultado
→ inspección
→ wiremap
→ hipótesis
→ localización
→ reparación
→ nuevo test
```

## Registro

| Cable | Esquema | Resultado inicial | Diagnóstico | Acción | Resultado final |
|---|---|---|---|---|---|

La práctica termina cuando puede demostrarse:

- qué se construyó;
- qué se midió;
- qué resultado apareció;
- qué cambio se realizó;
- qué resultado final se obtuvo.

# 7. Fibra óptica y transceptores

La fibra transporta información mediante luz.

## Ventajas

Puede ofrecer:

- alta capacidad;
- grandes distancias;
- inmunidad electromagnética;
- aislamiento eléctrico.

No debemos memorizar:

```text
fibra = siempre mejor
```

La selección depende de:

- distancia;
- tecnología;
- coste;
- entorno;
- equipos;
- mantenimiento.

## Monomodo y multimodo

| Característica | Monomodo | Multimodo |
|---|---|---|
| Uso típico | mayores distancias / backbone | distancias cortas/medias |
| Designación de referencia | OS2 | OM3 / OM4 |
| Núcleo | menor | mayor |

No existe una única regla como:

```text
multimodo = X metros
monomodo = Y kilómetros
```

El alcance depende de:

```text
tecnología Ethernet
+
transceptor
+
fibra
+
condiciones del enlace
```

## Conectores

Conviene reconocer especialmente:

- LC;
- SC.

No se requiere memorizar un catálogo completo.

## Polaridad

En una fibra dúplex:

```text
TX A → RX B
RX A ← TX B
```

Si se conectan transmisores entre sí, no se forma el enlace esperado.

## Transceptores

Un transceptor debe ser compatible con:

- velocidad;
- tipo de fibra;
- longitud de onda;
- alcance;
- conector;
- plataforma/equipo.

Idea importante:

```text
encaja físicamente
≠
es técnicamente compatible
```

## Seguridad

- no mirar directamente al extremo;
- no asumir que una fibra está inactiva;
- proteger conectores;
- no tocar superficies ópticas;
- respetar radios de curvatura;
- seguir normas del laboratorio.

# 8. Wi‑Fi como medio compartido

Wi‑Fi utiliza radio.

Varios dispositivos comparten el medio.

```text
cliente Wi-Fi
      ↕
      AP
      ↕
red cableada
```

## Compartir el medio

A diferencia de un enlace Ethernet full-duplex dedicado host-switch, varios clientes inalámbricos pueden competir por tiempo de transmisión.

Por tanto:

```text
tasa física
≠
throughput
```

## Cobertura y obstáculos

La señal puede degradarse por:

- distancia;
- paredes;
- materiales;
- geometría;
- ubicación;
- interferencia.

No se estudia propagación RF avanzada.

## Bandas

### 2,4 GHz

- mayor alcance relativo;
- menos espectro;
- mayor probabilidad de interferencia.

### 5 GHz

- más espectro/canales;
- buenas prestaciones;
- menor alcance relativo.

### 6 GHz

- espectro adicional;
- requiere dispositivos compatibles;
- depende de plataforma/regulación.

No se necesita memorizar tablas completas de canales.

## Métricas iniciales

| Métrica | Qué aporta |
|---|---|
| RSSI | Potencia recibida |
| SNR | Relación señal/ruido |
| Channel utilisation | Ocupación del medio |
| PHY rate | Tasa física negociada |
| Retries | Reintentos |
| Throughput | Rendimiento útil |

No existe:

```text
RSSI alto
=
throughput alto
```

como regla universal.

## Fases de acceso

De forma simplificada:

```text
detectar WLAN
→ seleccionar SSID
→ autenticarse / cumplir seguridad
→ asociarse
→ obtener configuración
→ comprobar conectividad
→ comprobar servicio
```

Estas fases son diferentes.

Ejemplo:

```text
SSID visible
≠
autenticación correcta
≠
configuración IP correcta
≠
Internet accesible
```

## Seguridad básica

Debemos reconocer:

- red abierta;
- WPA2;
- WPA3.

No es objetivo de U03 dominar:

- 802.1X;
- EAP;
- WLC;
- CAPWAP;
- arquitectura WLAN empresarial.

## Diagnóstico por etapas

Preguntas:

```text
¿aparece el SSID?
→ ¿hay señal suficiente?
→ ¿se autentica?
→ ¿se asocia?
→ ¿obtiene configuración?
→ ¿hay conectividad?
→ ¿el rendimiento es adecuado?
```

Esto separa:

```text
radio
≠
acceso Wi-Fi
≠
configuración IP
≠
servicio
```

# 9. Documentación, mapas y trazabilidad

Administrar una red significa poder responder:

> **¿A qué puerto está conectado realmente este equipo?**

## Rack

Un rack puede contener:

- patch panels;
- switches;
- routers;
- organizadores;
- fibra;
- PDU;
- UPS.

El objetivo no es diseñar un centro de datos completo.

Es comprender organización y trazabilidad.

## Etiquetado

Una conexión debería poder reconstruirse:

```text
toma
→ patch panel
→ puerto de switch
```

Ejemplo:

```text
A1-023
→ PP03-18
→ SW02-Gi1/0/18
```

Una convención debe ser:

- única;
- coherente;
- documentada;
- mantenible.

## Registro mínimo

| Toma | Patch panel | Puerto switch | Medio | Estado |
|---|---|---|---|---|
| A1-023 | PP03-18 | SW02-Gi1/0/18 | Cat 6A | Operativo |

## Mapa físico

Representa:

- dispositivo;
- ubicación;
- interfaz;
- medio;
- toma;
- panel;
- puerto.

Ejemplo:

```text
PC-07
→ toma A1-023
→ PP03-18
→ SW02 Gi1/0/18
```

## Mapa lógico básico

Representa relaciones funcionales:

- nombres de dispositivos;
- roles;
- enlaces;
- segmentos;
- servicios.

No necesita reflejar toda la ubicación física.

Mapa físico y lógico responden a preguntas diferentes.

## Contrastar documentación

La documentación es un estado **esperado**.

La red real es el estado **observado**.

```text
documentación
→ verificar
→ comparar
→ actualizar
```

No se debe cambiar primero y documentar después de memoria.

## CDP y LLDP como evidencia

En un entorno gestionable, una salida preparada puede mostrar:

```text
Local interface: Gi0/1
Neighbor: SW2
Remote port: Gi0/2
```

Puede utilizarse para contrastar el mapa.

En U03 no se configura CDP/LLDP.

Solo se interpreta.

# 10. Estado de interfaces, contadores y SNMP

La última competencia de U03 consiste en pasar de:

```text
“no funciona”
```

a:

```text
síntoma
→ alcance
→ recorrido físico
→ estado
→ contador
→ prueba
→ hipótesis
→ cambio mínimo
→ nueva medición
→ verificación
→ documentación
```

## Estado de interfaz

Información útil:

- up/down;
- speed;
- duplex;
- autonegotiation;
- errores;
- descartes;
- link flaps;
- PoE;
- transceptor.

### Windows

```powershell
Get-NetAdapter
Get-NetAdapterStatistics
```

### Linux

```bash
ip link
ethtool <interfaz>
```

### Cisco IOS

A nivel de interpretación:

```text
show interfaces
show interfaces status
show interfaces counters errors
```

No se exige todavía administrar el switch mediante CLI.

## Contadores

Un contador es acumulado.

Ejemplo:

```text
CRC = 245
```

por sí solo no demuestra que haya un fallo activo ahora.

Debemos medir evolución.

### Caso A

```text
CRC inicial = 245
CRC final   = 245
```

No se observan errores nuevos durante el intervalo.

### Caso B

```text
CRC inicial = 245
CRC final   = 390
```

El contador ha aumentado.

Procedimiento:

```text
registrar
→ reproducir tráfico/problema
→ volver a medir
→ comparar
```

## Estado, contador y tasa

- **estado**: condición actual;
- **contador**: acumulación histórica;
- **tasa**: evolución durante un intervalo;
- **línea base**: valor habitual con el que comparar.

## Un contador no explica automáticamente la causa

CRC crecientes pueden ser compatibles con:

- cable;
- conector;
- ruido;
- interfaz;
- transceptor;
- otros problemas físicos.

Hay que relacionar:

```text
contador
+
síntoma
+
prueba física
+
cambio controlado
```

## SNMP como herramienta de observación

SNMP permite a un sistema de gestión obtener información de dispositivos.

Modelo básico:

```text
NMS / manager
      ↕
    agent
      ↕
información gestionada
```

### NMS / manager

Sistema que consulta o recibe información.

### Agent

Componente del dispositivo que expone información gestionable.

### MIB

Estructura que organiza información gestionada.

### OID

Identificador de un dato concreto.

Ejemplos de información:

- estado de interfaz;
- octetos;
- errores;
- CPU;
- temperatura.

## Polling y notificación

Dos ideas:

```text
NMS
→ consulta periódica
→ polling
```

y:

```text
dispositivo
→ informa de evento
→ notification / trap
```

No se configura SNMPv3 ni comunidades en esta unidad.

El objetivo es comprender que la monitorización aporta evidencia incluso sin estar físicamente delante del equipo.

> Un puesto que normalmente enlaza a 1 Gb/s negocia a 100 Mb/s y sufre desconexiones.

## Paso 3 — Wiremap

Supongamos:

```text

```

Después:

# 14. Qué queda para U04 y U05

U03 termina cuando puedes responder:

> **¿Existe una infraestructura física o radioeléctrica correcta y qué evidencia lo demuestra?**

U04 responderá:

> **¿Está el equipo correctamente integrado en IPv4?**

Y U05:

> **¿Está correctamente integrado en IPv6?**

La secuencia queda:

```text
U03
medio / enlace / acceso
        ↓
U04
IPv4 / subnetting / DHCP
        ↓
U05
IPv6 / autoconfiguración
```

La regla profesional que se mantiene es:

```text
estado esperado
≠
estado observado
≠
causa demostrada
```

y:

```text
observar
→ medir
→ interpretar
→ cambiar una variable
→ volver a medir
→ verificar
→ documentar
```
