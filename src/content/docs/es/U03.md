> **Pregunta guía:** ¿Qué condiciones físicas y de acceso debe cumplir una red para que los dispositivos puedan conectarse de forma estable, verificable y con las prestaciones esperadas?

En U01 construimos un primer mapa de una red. En U02 formalizamos capas, encapsulación y análisis de tráfico. En esta unidad descendemos hasta la infraestructura que hace posible que los bits puedan circular realmente: interfaces, cobre, fibra, radio, terminaciones, negociación, alimentación, medidas, documentación y evidencias de estado.

La pregunta principal de U03 no es todavía si una subred IPv4 está bien calculada. Esa cuestión se estudiará en U04. Aquí aprenderemos primero a responder otra pregunta: **¿existe una conectividad física o radioeléctrica correcta y podemos demostrarlo mediante evidencias?**

El hilo conductor será profesional y verificable:

```text
síntoma → pregunta → hipótesis → prueba → evidencia → conclusión
```

Cuando exista una avería real, añadiremos dos pasos más:

```text
→ cambio mínimo → verificación
```

No se trata de memorizar catálogos de cables o conectores. Se trata de comprender qué función cumple cada elemento, qué limitaciones introduce y qué evidencia permite decidir si está funcionando correctamente.

# 1. Del dispositivo al enlace físico

Antes de configurar cualquier protocolo, debe existir un camino físico o radioeléctrico capaz de transportar señales. Este apartado sirve para poner nombre a cada pieza de ese camino: el hardware del equipo, el punto por el que se conecta, el medio por el que viaja la señal y la conexión que se forma entre dos extremos.

Cuando un usuario dice «no tengo red», el problema puede estar en cualquiera de esas piezas. Si sabemos distinguirlas y conocemos qué evidencia aporta cada una (un LED, un estado `up`/`down`), podremos empezar a buscar en el sitio correcto en lugar de probar cosas al azar.

| Concepto | Qué es | Pregunta que responde | Ejemplo |
|---|---|---|---|
| **Adaptador de red** (*network adapter, NIC*) | Hardware que permite al equipo usar una tecnología de red | ¿Con qué hardware se conecta el equipo? | Tarjeta Ethernet integrada, adaptador USB Wi‑Fi |
| **Interfaz** (*interface*) | Punto físico o lógico mediante el que un dispositivo participa en una red | ¿Por qué punto entra o sale la comunicación? | `Ethernet`, `Wi-Fi`, `Gi1/0/18` |
| **Medio** (*medium*) | Entorno por el que se propaga la señal | ¿Por dónde viaja la señal? | Cobre, fibra, aire |
| **Señal** (*signal*) | Representación física de la información | ¿Qué forma física toma la información? | Eléctrica, óptica, radio |
| **Enlace** (*link*) | Conexión de comunicaciones entre dos interfaces | ¿Hay conexión entre estos dos extremos? | PC ↔ puerto del switch |
| **Canal** (*channel*) | Recorrido completo del sistema de cableado entre extremos | ¿Qué elementos atraviesa la conexión? | Latiguillo + toma + cable + panel + latiguillo |
| **Transceptor** (*transceiver*) | Componente que adapta la señal a una interfaz/medio | ¿Qué adapta la interfaz al medio concreto? | Módulo SFP de fibra |

No debemos confundir el equipo con su adaptador, ni el adaptador con la interfaz, ni la interfaz con el medio: son niveles distintos y cada uno puede fallar por separado.

## 1.1. Medio y señal

| Medio | Señal |
|---|---|
| Cobre | Eléctrica |
| Fibra óptica | Óptica |
| Aire | Radioeléctrica |

## 1.2. Adaptadores de red

Un equipo puede utilizar:

- Ethernet integrado;
- tarjeta PCIe;
- adaptador USB–Ethernet;
- Wi‑Fi;
- interfaz virtual;
- interfaz de una máquina virtual.

Un switch o router puede incorporar:

- puertos de cobre;
- interfaces ópticas;
- módulos;
- transceptores;
- interfaces lógicas.

En U03 nos interesa principalmente el **estado físico/de acceso**.

## 1.3. Adaptadores cableados e inalámbricos en distintos sistemas operativos

Integrar un equipo en la red empieza por comprobar que el sistema operativo **reconoce el adaptador**, que tiene **controlador** (*driver*) y que la interfaz está **habilitada**. Solo después tiene sentido mirar el enlace, la asociación Wi‑Fi y, ya en U04, la configuración IP.

| Sistema | Dónde verlo (interfaz gráfica) | Comandos de consulta |
|---|---|---|
| **Windows** | Configuración → Red e Internet; Administrador de dispositivos (controlador) | `Get-NetAdapter`, `ipconfig /all`, `netsh wlan show interfaces` (Wi‑Fi: SSID, señal, velocidad) |
| **Linux** | NetworkManager (applet o `nmtui`) | `ip link`, `nmcli device status`, `ethtool <interfaz>` (cable), `iw dev <interfaz> link` (Wi‑Fi), `lspci` / `lsusb` (hardware) |
| **macOS** | Ajustes del Sistema → Red | `networksetup -listallhardwareports`, `ifconfig` |

Secuencia de comprobación de un adaptador:

```text
¿el SO detecta el hardware?
→ ¿tiene controlador correcto?
→ ¿la interfaz está habilitada?
→ ¿hay enlace (cable) o asociación (Wi-Fi)?
→ [U04] ¿tiene configuración IP coherente?
```

Los nombres de interfaz cambian según el sistema (`Ethernet`, `Wi-Fi`, `eth0`, `enp3s0`, `wlan0`, `wlp2s0`, `en0`). Lo importante es identificar **qué interfaz corresponde a qué adaptador y a qué medio**.

## 1.4. Interfaz

Una interfaz puede aportar información como:

```text
estado
velocidad
dúplex
dirección física
estadísticas
configuración
```

Ejemplos:

```text
Ethernet
Wi-Fi
Gi1/0/18
SFP interface
vNIC
```

No confundas:

```text
dispositivo
≠
adaptador
≠
interfaz
≠
medio
```

## 1.5. Recorrido físico

Una conexión real puede ser:

```text
PC
→ interfaz Ethernet
→ latiguillo
→ roseta
→ cable horizontal
→ patch panel
→ latiguillo de rack
→ puerto del switch
```

Cada elemento puede ser una dependencia.

Por eso el síntoma:

> “El PC no tiene red”

no demuestra cuál de esos componentes falla.

## 1.6. LED como evidencia inicial

Los LED varían según fabricante/modelo, pero pueden indicar:

- alimentación;
- estado del sistema;
- presencia de enlace;
- actividad;
- velocidad;
- PoE.

Ejemplo:

```text
LED de link apagado
→ evidencia inicial
→ revisar enlace físico
```

Pero:

```text
LED encendido
≠
comunicación IP demostrada
```

Un LED no demuestra:

- direccionamiento correcto;
- VLAN correcta;
- routing correcto;
- DNS;
- funcionamiento de la aplicación.

(El significado detallado de los LED de un switch Cisco se estudia en U06.)

## 1.7. Link up y link down

```text
link down
→ no existe enlace físico operativo

link up
→ existe una forma de enlace detectada
```

Pero:

```text
link up
+
configuración lógica incorrecta
=
sin comunicación útil
```

Por tanto:

> **`link up` demuestra algo, pero no lo demuestra todo.**

# 2. Prestaciones y degradación del medio

Una interfaz puede estar activa y funcionar muy por debajo de lo esperado. Este apartado sirve para separar tres ideas que se suelen mezclar: la velocidad que «pone» el equipo, la velocidad que realmente se consigue y los fenómenos físicos que degradan la señal por el camino.

Así podremos explicar situaciones habituales, como una descarga lenta con el enlace a 1 Gb/s, y relacionar cada fenómeno (atenuación, ruido, diafonía) con los síntomas que produce, sin necesidad de fórmulas.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Capacidad nominal** (*nominal capacity*) | ¿Cuál es la tasa máxima prevista de la tecnología? | 1 Gb/s en 1000BASE-T |
| **Velocidad negociada** (*negotiated speed / link speed*) | ¿A qué velocidad han acordado trabajar los dos extremos? | `speed = 100 Mb/s` en la interfaz |
| **Rendimiento real** (*throughput*) | ¿Cuántos datos útiles se transfieren realmente? | 420 Mb/s medidos en una copia |
| **Atenuación** (*attenuation*) | ¿Cuánta intensidad pierde la señal al propagarse? | Enlace muy largo o con muchos conectores |
| **Ruido e interferencia** (*noise, interference*) | ¿Qué energía no deseada se suma a la señal? | Cable junto a un motor o a la línea eléctrica |
| **Diafonía** (*crosstalk*) | ¿Se interfieren los pares vecinos entre sí? | Pares destrenzados en la terminación |

La trampa típica es tratar como sinónimos capacidad, velocidad negociada y throughput: son tres medidas distintas y pueden tener valores muy diferentes a la vez.

## 2.1. Capacidad nominal y throughput

La **capacidad nominal** expresa una tasa máxima prevista bajo determinadas condiciones.

Ejemplos:

```text
100 Mb/s
1 Gb/s
10 Gb/s
```

El **throughput** es la cantidad real de datos útiles transferidos.

Por tanto:

```text
capacidad nominal
≠
throughput real
```

El rendimiento puede verse afectado por:

- overhead;
- errores;
- retransmisiones;
- congestión;
- capacidad de los extremos;
- limitaciones de software;
- interferencia;
- características del medio;
- aplicación.

## 2.2. Velocidad negociada

La velocidad de enlace observada puede ser:

```text
100 Mb/s
1 Gb/s
2.5 Gb/s
10 Gb/s
```

No es lo mismo que throughput.

Ejemplo:

```text
velocidad negociada = 1 Gb/s
throughput medido = 420 Mb/s
```

puede ser perfectamente posible.

## 2.3. Atenuación

La **atenuación** es la reducción de intensidad de la señal al propagarse.

Puede aumentar por:

- distancia;
- conectores;
- empalmes;
- daños;
- curvaturas;
- instalación deficiente.

No necesitamos fórmulas avanzadas.

Debemos relacionar fenómeno y síntoma.

## 2.4. Ruido e interferencia

El ruido añade energía no deseada.

Posibles fuentes:

- motores;
- alimentación eléctrica;
- cables próximos;
- transmisiones radio;
- otros equipos.

Puede provocar:

- errores;
- retransmisiones;
- reducción de throughput;
- renegociaciones;
- pérdida de enlace.

## 2.5. Diafonía

La **diafonía** (*crosstalk*) es interferencia entre conductores o pares cercanos.

El trenzado de los pares ayuda a reducirla.

Por eso:

```text
continuidad correcta
+
demasiado destrenzado
→
puede existir degradación
```

## 2.6. Síntoma no equivale a causa

| Observación | Hipótesis compatibles |
|---|---|
| Enlace a 100 Mb/s cuando se esperaba 1 Gb/s | Pares, terminación, cable, negociación, adaptador |
| CRC/FCS aumentando | Medio, conectores, interferencia, interfaz |
| Link flaps | Cable, conector, alimentación, transceptor, interfaz |
| Wi‑Fi inestable | Cobertura, interferencia, ocupación, cliente |

Esta tabla no diagnostica.

Genera hipótesis.

La secuencia correcta es:

```text
síntoma
→ hipótesis
→ prueba
→ evidencia
```

## 2.7. Caso

Se observa:

```text
esperado: 1 Gb/s
observado: 100 Mb/s
```

Escribe al menos cuatro hipótesis.

Después selecciona la **primera prueba de mayor valor**.

# 3. Cobre y cableado estructurado

El cobre de par trenzado sigue siendo el medio más habitual para conectar puestos de trabajo, teléfonos IP, cámaras y puntos de acceso. Este apartado estudia el cable en sí, pero sobre todo el **canal completo** en el que se instala: la toma de la pared, el cable que va por el techo, el panel del rack y los latiguillos de cada extremo.

La idea central es que un canal rinde lo que rinde su elemento más débil, y que la instalación está regida por **normas** (qué categorías, qué longitudes, qué esquemas de colores). Al final veremos los tipos de cable que se fabrican con esos conectores: directo, cruzado y el **cable de consola**, que no transporta datos de red pero es imprescindible para administrar switches y routers.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Par trenzado** (*twisted pair*) | ¿Cómo está construido el cable y por qué se trenza? | 4 pares U/UTP |
| **Categoría** (*category*) | ¿Qué prestaciones admite el componente? | Cat 5e, Cat 6, Cat 6A |
| **Apantallamiento** (*shielding*) | ¿Lleva pantalla contra interferencias? | U/UTP, F/UTP, S/FTP |
| **Cableado estructurado** (*structured cabling*) | ¿Cómo se organiza una instalación mantenible? | Tomas, paneles, rack, etiquetas |
| **Enlace permanente y canal** (*permanent link, channel*) | ¿Qué parte es fija y qué parte es el recorrido completo? | Toma → panel (fijo); equipo → switch (canal) |
| **Normas de cableado** (*cabling standards*) | ¿Quién define categorías, longitudes y esquemas? | TIA-568, ISO/IEC 11801, IEEE 802.3 |
| **Conector 8P8C / «RJ45»** (*modular connector*) | ¿Qué conector termina el cable? | Conector de latiguillo |
| **T568A / T568B** (*wiring schemes*) | ¿En qué orden van los colores en cada pin? | T568B en ambos extremos |
| **Cable directo / cruzado** (*straight-through / crossover*) | ¿Se mantienen o se cruzan los pares de extremo a extremo? | PC–switch (directo) |
| **Auto MDI-X** | ¿Puede el puerto adaptarse al tipo de cable? | Switch actual con cualquier latiguillo |
| **Cable de consola** (*console cable, rollover*) | ¿Cómo conecto un PC al puerto de administración de un equipo de red? | RJ-45 ↔ DB-9 o USB |
| **Ethernet sobre cobre** (*BASE-T*) | ¿Qué tecnología Ethernet usa el cable y cuántos pares? | 1000BASE-T usa 4 pares |

No debemos mezclar la **categoría** (lo que admite un componente) con la **prestación del canal** (lo que admite el conjunto instalado), ni el **esquema de colores** (T568A/B) con el **tipo de cable** (directo, cruzado o consola).

## 3.1. Par trenzado

El cable Ethernet habitual de cobre contiene cuatro pares trenzados.

El trenzado contribuye a:

- reducir interferencia;
- reducir diafonía;
- mantener equilibrio eléctrico.

Debe conservarse hasta lo más cerca posible de la terminación.

## 3.2. Categorías que interesa reconocer

| Categoría | Uso orientativo |
|---|---|
| **Cat 5e** | Gigabit Ethernet en instalaciones adecuadas |
| **Cat 6** | Gigabit y mayores prestaciones según tecnología/distancia (10GBASE-T solo en canales cortos, del orden de 55 m) |
| **Cat 6A** | 10GBASE-T en canal adecuado (hasta 100 m) |

No es necesario memorizar todas las categorías existentes.

## 3.3. Cable y canal no son lo mismo

Idea profesional:

```text
categoría del cable
≠
prestación garantizada del canal
```

El canal puede contener:

```text
latiguillo
+
roseta/keystone
+
cable horizontal
+
patch panel
+
latiguillo
+
terminaciones
```

Un único componente deficiente puede limitar el conjunto.

Ejemplo:

```text
cable horizontal Cat 6A
+
keystone Cat 5e
+
latiguillos Cat 6A
→
no permite afirmar que el canal completo sea Cat 6A
```

## 3.4. Apantallamiento

Designaciones frecuentes:

| Designación | Significado inicial |
|---|---|
| U/UTP | Sin pantalla |
| F/UTP | Pantalla general |
| U/FTP | Pantalla sobre pares |
| S/FTP | Pantalla general y sobre pares |

No se trata de memorizar todas las combinaciones.

El apantallamiento debe formar parte de un sistema de instalación coherente.

## 3.5. Calidad del material

Una especificación comercial no sustituye una instalación adecuada.

Material o terminaciones deficientes pueden producir:

- resistencia excesiva;
- calentamiento;
- peor funcionamiento PoE;
- menor margen de señal;
- menor fiabilidad;
- peor comportamiento a frecuencias altas.

## 3.6. Cableado estructurado

El cableado estructurado organiza la infraestructura para que sea:

- mantenible;
- ampliable;
- trazable;
- verificable;
- documentable.

En lugar de tender un cable desde cada PC hasta el switch, se instala una parte **fija** (tomas, cable por techos o canaletas, paneles) y se conectan los equipos con latiguillos **intercambiables**. Así, mover un puesto o cambiar de puerto no obliga a tocar la obra.

| Elemento | Función | Dónde está |
|---|---|---|
| **Roseta / toma** (*network outlet*) | Punto de conexión del usuario | Pared o suelo del puesto |
| **Keystone** | Módulo de conexión que se inserta en la roseta o en el panel | Dentro de la toma o del panel |
| **Cable horizontal** (*horizontal cable*) | Tramo fijo entre la toma y el armario | Techo, suelo técnico, canaleta |
| **Patch panel** (*panel de parcheo*) | Termina los cables horizontales en el armario | Rack |
| **Latiguillo** (*patch cord*) | Cable corto y flexible que une equipo y toma, o panel y switch | Puesto y rack |
| **Rack** | Armario que aloja paneles y equipos | Cuarto de comunicaciones |
| **Organizadores** (*cable managers*) | Ordenan los latiguillos | Rack |
| **Etiquetado** (*labeling*) | Identifica cada toma, puerto y cable | Todos los elementos |

### Enlace permanente

Parte fija:

```text
roseta
→ cable horizontal
→ patch panel
```

### Canal

Recorrido completo:

```text
equipo
→ latiguillo
→ enlace permanente
→ latiguillo
→ switch
```

### Longitud máxima del canal de cobre

Las normas limitan el canal de par trenzado a **100 m** en total:

```text
enlace permanente ≤ 90 m
+
latiguillos (ambos extremos) ≤ 10 m
=
canal ≤ 100 m
```

Superar esa longitud aumenta la atenuación y puede provocar errores, negociación a menor velocidad o ausencia de enlace. Para distancias mayores (entre plantas o edificios) se suele usar **fibra**.

### Subsistemas

| Subsistema | Qué une | Medio habitual |
|---|---|---|
| **Horizontal** | Tomas de usuario ↔ armario de planta | Par trenzado |
| **Troncal / vertical** (*backbone*) | Armarios de planta ↔ sala de equipos | Fibra (o cobre en distancias cortas) |
| **Campus** | Edificios entre sí | Fibra |

## 3.7. Normas de referencia

No hace falta memorizar el texto de las normas, pero sí saber **qué regula cada una**, porque aparecen en presupuestos, fichas técnicas e informes de certificación.

| Norma | Qué regula |
|---|---|
| **ANSI/TIA-568** | Cableado estructurado (EE. UU.): categorías, longitudes, esquemas T568A/T568B |
| **ISO/IEC 11801** (y **EN 50173** en Europa) | Cableado estructurado a nivel internacional/europeo: clases de canal (p. ej., Clase EA ≈ Cat 6A) |
| **IEEE 802.3** | Tecnologías Ethernet: 100BASE-TX, 1000BASE-T, 10GBASE-T, fibra, PoE |
| **IEEE 802.11** | Redes inalámbricas Wi‑Fi (apartado 8) |

## 3.8. Conectores, esquemas y tipos de cable

Con los mismos conectores se fabrican cables con funciones distintas. Lo que los diferencia es **qué pin de un extremo se une con qué pin del otro**.

| Tipo de cable | Extremos | Uso |
|---|---|---|
| **Directo** (*straight-through*) | Mismo esquema en ambos extremos (T568B–T568B) | Conexión habitual equipo ↔ switch |
| **Cruzado** (*crossover*) | Un extremo T568A y el otro T568B | Conexión histórica entre equipos del mismo tipo (switch–switch, PC–PC) |
| **Consola** (*rollover*) | Orden de hilos invertido de extremo a extremo | Administración local de switches y routers |

### 8P8C y “RJ45”

El conector modular habitual se denomina técnicamente **8P8C**.

En el uso cotidiano se utiliza ampliamente el nombre “RJ45”.

Conviene reconocer ambos términos.

### T568A y T568B

| Pin | T568A | T568B |
|---:|---|---|
| 1 | blanco/verde | blanco/naranja |
| 2 | verde | naranja |
| 3 | blanco/naranja | blanco/verde |
| 4 | azul | azul |
| 5 | blanco/azul | blanco/azul |
| 6 | naranja | verde |
| 7 | blanco/marrón | blanco/marrón |
| 8 | marrón | marrón |

Ambos esquemas son válidos.

Lo importante es aplicar de forma coherente el esquema previsto.

### Cable directo y cruzado

Directo:

```text
A ↔ A
B ↔ B
```

Cruzado:

```text
A ↔ B
```

En un cruzado, los pares naranja y verde intercambian su posición: los pines **1-2** de un extremo llegan a los **3-6** del otro, y viceversa. Así, lo que transmite un equipo llega a los pines de recepción del otro.

Históricamente se elegía según el tipo de dispositivos.

Hoy muchos equipos incorporan **Auto MDI-X**.

Por tanto:

> “PC-switch siempre directo y switch-switch siempre cruzado”

no debe aprenderse como una regla universal actual.

### Auto MDI-X

Auto MDI-X puede adaptar automáticamente pares de transmisión/recepción.

No repara:

- conductores abiertos;
- cortos;
- split pairs;
- terminaciones defectuosas.

```text
Auto MDI-X
≠
auto-reparación del cable
```

### Cable de consola

El **cable de consola** no transporta tráfico de red: conecta el puerto de administración (*console*) de un switch o router con el puerto serie o USB de un ordenador, para configurar el equipo con un emulador de terminal (PuTTY, Tera Term, `screen`).

Es el método de acceso que funciona **aunque el equipo no tenga todavía ninguna configuración de red**, por eso es el primero que se usa con un equipo nuevo o cuando se pierde el acceso remoto.

| Tipo | Conectores | Observaciones |
|---|---|---|
| Rollover (clásico) | RJ-45 ↔ DB-9 o RJ-45 ↔ RJ-45 + adaptador | Los hilos están invertidos de extremo a extremo (1↔8, 2↔7…) |
| USB | USB ↔ mini-USB/USB-C del equipo | Habitual en equipos actuales; requiere controlador |
| Adaptador USB–serie | USB ↔ DB-9 | Para portátiles sin puerto serie |

Parámetros habituales del terminal: **9600 baudios, 8 bits de datos, sin paridad, 1 bit de parada, sin control de flujo (9600 8N1)**.

En el PC, el puerto aparece como `COM3`, `COM4`… (Windows, en el Administrador de dispositivos) o como `/dev/ttyUSB0`, `/dev/ttyACM0` (Linux). Hay que seleccionar ese puerto en el emulador de terminal.

Un cable de consola no se comprueba con un tester Ethernet de wiremap convencional como un latiguillo: su esquema de hilos es distinto a propósito.

(El uso de la consola para administrar el switch se desarrolla en U06, y el acceso remoto seguro por SSH en U08.)

## 3.9. Ethernet sobre cobre

Tecnologías de referencia (IEEE 802.3):

| Tecnología | Velocidad | Pares utilizados |
|---|---:|---:|
| 100BASE-TX | 100 Mb/s | 2 |
| 1000BASE-T | 1 Gb/s | 4 |
| 10GBASE-T | 10 Gb/s | 4 |

También existen 2.5GBASE-T y 5GBASE-T.

Un defecto en determinados pares puede permitir que exista enlace pero impedir la velocidad esperada. Por ejemplo, si falla uno de los pares que solo usa 1000BASE-T, muchos adaptadores **bajan a 100 Mb/s** (que solo necesita dos pares) en lugar de quedarse sin enlace.

# 4. Autonegociación, dúplex y PoE

Cuando conectamos un cable, los dos extremos no empiezan a transmitir sin más: primero **acuerdan** cómo van a hacerlo (velocidad y dúplex). Además, en muchos puertos el mismo cable lleva también la **alimentación eléctrica** del dispositivo. Este apartado explica esos dos mecanismos y cómo leer sus valores como evidencia.

La consecuencia práctica es importante: un fallo de cableado puede verse como «va lento», como «funciona en half-duplex» o como «el punto de acceso se reinicia», y en los tres casos la causa puede ser la misma.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Autonegociación** (*autonegotiation*) | ¿Qué velocidad y dúplex han acordado los extremos? | `a-1000`, `a-full` |
| **Full-duplex** | ¿Pueden transmitir y recibir a la vez? | PC ⇄ switch actual |
| **Half-duplex** | ¿Tienen que turnarse para transmitir? | Hub antiguo; negociación fallida |
| **Desajuste de dúplex** (*duplex mismatch*) | ¿Trabaja cada extremo en un dúplex distinto? | Un extremo fijo en full, el otro cae a half |
| **PoE** (*Power over Ethernet*) | ¿El cable lleva también la alimentación? | AP, cámara IP, teléfono IP |
| **PSE / PD** (*power sourcing equipment / powered device*) | ¿Quién da la energía y quién la recibe? | Switch PoE (PSE) → AP (PD) |

La velocidad y el dúplex negociados son **observaciones**, no causas: nos dicen qué ha pasado, pero no por qué.

## 4.1. Autonegociación

Los extremos pueden acordar automáticamente:

- velocidad;
- dúplex;
- determinadas capacidades.

La velocidad negociada es una **observación**, no una causa.

Ejemplo:

```text
NIC Gigabit
+
switch Gigabit
+
speed observada = 100 Mb/s
```

Hipótesis compatibles:

- pares no disponibles;
- terminación;
- cable;
- capacidad real;
- configuración;
- adaptador.

## 4.2. Full-duplex y half-duplex

En **full-duplex** se puede transmitir y recibir simultáneamente.

```text
PC ⇄ switch
```

Es el comportamiento habitual esperado en Ethernet conmutada moderna.

En **half-duplex** el extremo transmite **o** recibe, pero no ambas cosas a la vez. Era lo normal en los antiguos hubs y medios compartidos; hoy, verlo en un enlace host–switch suele ser síntoma de un problema de negociación.

## 4.3. Dúplex como evidencia

Un valor de dúplex inesperado puede indicar una incidencia de negociación/configuración.

Pero el valor debe interpretarse junto a:

- velocidad;
- errores;
- configuración;
- tipo de enlace.

Caso típico de **desajuste de dúplex** (*duplex mismatch*):

```text
extremo A: velocidad y dúplex fijados a mano (full), autonegociación desactivada
extremo B: autonegociación activada
→ B no recibe negociación y, por norma, asume half-duplex
→ A en full, B en half
```

Síntomas habituales: el enlace está `up`, pero el rendimiento es muy bajo y aparecen colisiones tardías (*late collisions*) en el lado half y errores CRC en el lado full.

Recomendación: **autonegociación en ambos extremos**, o configuración fija idéntica en ambos.

## 4.4. PoE

**Power over Ethernet (PoE)** permite transportar energía y datos por el cableado Ethernet.

Usos frecuentes:

- access point;
- cámara IP;
- teléfono IP.

El equipo que suministra energía (switch o inyector) es el **PSE**; el que la recibe es el **PD**. Estándares de referencia (IEEE 802.3):

| Estándar | Nombre habitual | Potencia máx. en el PSE | Potencia aprox. disponible en el PD |
|---|---|---:|---:|
| 802.3af | PoE | 15,4 W | 12,95 W |
| 802.3at | PoE+ | 30 W | 25,5 W |
| 802.3bt (Tipo 3) | PoE++ | 60 W | 51 W |
| 802.3bt (Tipo 4) | PoE++ | 90 W | 71,3 W |

La diferencia entre lo que entrega el PSE y lo que llega al PD se pierde en el cable.

Antes de afirmar “PoE no funciona”, comprobar:

- compatibilidad del dispositivo alimentado;
- capacidad de la fuente/switch;
- potencia requerida;
- potencia disponible;
- calidad del canal.

En U03 PoE se estudia a nivel funcional.

No se requiere diseñar presupuestos complejos.

## 4.5. Datos y alimentación comparten dependencia

Un fallo de cableado puede afectar:

```text
datos
+
alimentación
```

Ejemplo:

```text
AP con reinicios
+
link flaps
+
PoE
```

puede justificar revisar canal y alimentación antes de culpar al software.

# 5. Comprobación del cableado

Una herramienta es útil solo si comprendemos **qué mide** y **qué no demuestra**. Este apartado presenta las formas de comprobar un cable, desde mirarlo con atención hasta usar un tester, y enseña a leer sus resultados sin atribuirles más de lo que prueban.

Las comprobaciones van de menos a más: primero la inspección visual, después el mapa de hilos y, si hace falta, pruebas de longitud o de prestaciones con equipos más avanzados. Cada paso se elige para **probar una hipótesis concreta**, no por rutina.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Inspección visual** (*visual inspection*) | ¿Hay un defecto que se vea a simple vista? | Pestaña rota, pares destrenzados |
| **Mapa de hilos** (*wiremap*) | ¿Cada conductor llega al pin correcto del otro extremo? | Resultado `open` en el par 7-8 |
| **Longitud / distancia al fallo** (*length, distance to fault*) | ¿Cuánto mide el cable y dónde está el defecto? | Corte a 23 m |
| **Tipos de comprobador** (*verifier, qualifier, certifier*) | ¿Qué nivel de evidencia necesito? | Verificador en el aula; certificador para entregar una obra |
| **Split pair** | ¿Hay continuidad correcta pero pares mal formados? | Wiremap aparentemente válido con errores |

La confusión típica es creer que «el tester da OK» equivale a «el canal cumple la categoría»: un tester básico no mide prestaciones.

## 5.1. Inspección visual

Antes del tester:

- revisar conectores;
- buscar daños;
- observar pestañas;
- detectar aplastamientos;
- revisar orden;
- observar exceso de destrenzado;
- comprobar etiquetado.

La inspección no sustituye a la medición.

Pero puede evitar pruebas innecesarias.

## 5.2. Tipos de comprobadores

| Tipo | Qué comprueba | Pregunta que responde |
|---|---|---|
| **Verificador** (*verifier / wiremap tester*) | Continuidad y mapa de hilos; algunos, longitud | ¿Está bien conectado? |
| **Cualificador** (*qualifier*) | Si el enlace puede soportar una tecnología concreta | ¿Funcionará a 1 Gb/s? |
| **Certificador** (*certifier*) | Parámetros eléctricos (atenuación, diafonía…) frente a una norma y categoría | ¿Cumple el canal Cat 6A según la norma? |

En fibra se usan otras herramientas: el **medidor de potencia óptica** (mide la pérdida del enlace) y el **localizador visual de fallos** (*VFL*, luz roja que deja ver roturas y curvaturas).

## 5.3. Wiremap

Un tester básico puede mostrar la relación entre conductores.

| Resultado | Interpretación inicial |
|---|---|
| **Open** | Falta continuidad |
| **Short** | Conductores unidos indebidamente |
| **Reversed / miswired** | Orden incorrecto |
| **Crossed** | Correspondencia cruzada |
| **Split pair** | Pines con continuidad pero pares eléctricos incorrectos |

## 5.4. Split pair

Es un fallo especialmente importante.

Puede ocurrir:

```text
continuidad pin a pin correcta
+
pares mal formados
=
wiremap que parece parcialmente válido
pero mal comportamiento eléctrico
```

## 5.5. Longitud y distancia al fallo

Algunos testers pueden estimar:

- longitud;
- distancia al defecto.

No todos ofrecen estas funciones. Los que lo hacen suelen usar la técnica **TDR** (*time domain reflectometry*): envían un impulso y miden cuánto tarda en volver el reflejo del defecto.

## 5.6. Límites de un tester básico

Puede aportar evidencia de:

- continuidad;
- orden;
- determinados defectos;
- a veces longitud.

Pero no demuestra automáticamente:

- categoría real del canal;
- límites de diafonía;
- rendimiento real;
- aptitud para 10G;
- certificación normativa completa.

Por tanto:

```text
wiremap correcto
≠
canal certificado
```

## 5.7. Medir una hipótesis

Ejemplo:

```text
Síntoma:
1 Gb/s esperado → 100 Mb/s observado

Hipótesis:
algún par no está disponible

Prueba:
wiremap

Resultado:
open pair
```

Interpretación prudente:

> El resultado es coherente con la hipótesis.

No necesitamos afirmar más de lo que la prueba demuestra.

# 6. Fabricación, reparación y verificación de latiguillos

Fabricar un cable es solo una parte de la competencia. En un entorno profesional lo que se valora es poder **demostrar** que el cable funciona, o localizar y reparar el fallo de uno que no funciona, y dejar constancia de ello.

Este apartado describe el ciclo completo de trabajo, desde la preparación de la mesa hasta el registro final, y cómo abordar un cable con un fallo desconocido.

| Fase | Pregunta que responde | Evidencia que deja |
|---|---|---|
| **Fabricar** (*build / terminate*) | ¿He terminado el cable según el esquema elegido? | Esquema aplicado (T568A/B) |
| **Inspeccionar** (*inspect*) | ¿Se ve algún defecto antes de medir? | Observaciones visuales |
| **Medir** (*test*) | ¿Qué dice el tester? | Resultado del wiremap |
| **Interpretar** (*interpret*) | ¿Qué significa ese resultado? | Hipótesis sobre el fallo |
| **Reparar** (*repair*) | ¿Qué cambio mínimo corrige el fallo? | Acción realizada |
| **Volver a medir** (*retest*) | ¿El cambio lo ha resuelto? | Resultado final |
| **Documentar** (*document*) | ¿Puede otra persona comprobar lo que hice? | Registro del cable |

La práctica no termina cuando «se enciende el LED»: termina cuando el resultado está medido y registrado.

La secuencia completa es:

```text
fabricar
→ inspeccionar
→ medir
→ interpretar
→ reparar
→ volver a medir
→ documentar
```

## 6.1. Seguridad y organización

- mantener mesa ordenada;
- utilizar adecuadamente crimpadora y herramientas de corte;
- recoger restos de conductor;
- no manipular energía innecesariamente;
- identificar cada cable.

## 6.2. Procedimiento de fabricación

1. seleccionar T568A o T568B;
2. retirar cubierta sin dañar conductores;
3. conservar el trenzado lo máximo posible;
4. ordenar pares;
5. comprobar colores;
6. cortar uniformemente;
7. insertar en 8P8C;
8. verificar visualmente;
9. crimpar;
10. repetir el otro extremo.

Para un **cruzado**, el segundo extremo se termina con el otro esquema (T568A en un extremo y T568B en el otro). Un **cable de consola rollover** se fabrica con el mismo procedimiento, pero con el orden de colores **invertido** en el segundo extremo (el pin 1 de un lado llega al pin 8 del otro); en la práctica suele usarse el cable del fabricante o uno USB.

## 6.3. La práctica no termina con el crimpado

Después:

```text
inspección
→ wiremap
→ interpretación
```

No basta:

```text
“se enciende el LED”
→ práctica terminada
```

## 6.4. Diagnóstico con fallos preparados

Puede recibirse un cable con fallo desconocido:

- open;
- conductores intercambiados;
- split pair;
- terminación deficiente.

Procedimiento:

```text
resultado
→ inspección
→ wiremap
→ hipótesis
→ localización
→ reparación
→ nuevo test
```

## 6.5. Registro

| Cable | Esquema | Resultado inicial | Diagnóstico | Acción | Resultado final |
|---|---|---|---|---|---|

La práctica termina cuando puede demostrarse:

- qué se construyó;
- qué se midió;
- qué resultado apareció;
- qué cambio se realizó;
- qué resultado final se obtuvo.

# 7. Fibra óptica y transceptores

La fibra transporta información mediante luz. Se utiliza cuando el cobre no llega (más de 100 m), cuando hay mucha interferencia eléctrica o cuando se necesita mucha capacidad, por ejemplo entre armarios, plantas o edificios.

Para elegir y conectar un enlace de fibra hay que decidir el **tipo de fibra**, reconocer los **conectores**, respetar la **polaridad** (qué extremo transmite y cuál recibe) y escoger un **transceptor** compatible con todo lo anterior.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Fibra monomodo** (*single-mode, SM*) | ¿Necesito grandes distancias? | OS2 en un enlace entre edificios |
| **Fibra multimodo** (*multimode, MM*) | ¿Es una distancia corta o media dentro del edificio? | OM3/OM4 entre armarios |
| **Conector** (*connector*) | ¿Qué terminación tiene el cable? | LC, SC |
| **Polaridad** (*polarity*) | ¿Llega el TX de un extremo al RX del otro? | TX A → RX B |
| **Transceptor** (*transceiver*) | ¿Qué módulo convierte la señal eléctrica en luz para esa fibra? | SFP 1000BASE-LX |
| **Seguridad óptica** (*optical safety*) | ¿Cómo evito daños a personas y a conectores? | No mirar al extremo de la fibra |

La confusión típica es pensar que un transceptor que «encaja» en el puerto sirve: además debe coincidir en velocidad, tipo de fibra, longitud de onda y alcance.

## 7.1. Ventajas

Puede ofrecer:

- alta capacidad;
- grandes distancias;
- inmunidad electromagnética;
- aislamiento eléctrico.

No debemos memorizar:

```text
fibra = siempre mejor
```

La selección depende de:

- distancia;
- tecnología;
- coste;
- entorno;
- equipos;
- mantenimiento.

## 7.2. Monomodo y multimodo

| Característica | Monomodo | Multimodo |
|---|---|---|
| Uso típico | mayores distancias / backbone | distancias cortas/medias |
| Designación de referencia | OS2 | OM3 / OM4 |
| Núcleo | menor (≈ 9 µm) | mayor (50 µm; 62,5 µm en la antigua OM1) |
| Longitud de onda habitual | 1310 / 1550 nm | 850 nm |

No existe una única regla como:

```text
multimodo = X metros
monomodo = Y kilómetros
```

El alcance depende de:

```text
tecnología Ethernet
+
transceptor
+
fibra
+
condiciones del enlace
```

## 7.3. Conectores

Conviene reconocer especialmente:

- LC;
- SC.

No se requiere memorizar un catálogo completo.

## 7.4. Polaridad

En una fibra dúplex:

```text
TX A → RX B
RX A ← TX B
```

Si se conectan transmisores entre sí, no se forma el enlace esperado.

## 7.5. Transceptores

Un transceptor debe ser compatible con:

- velocidad;
- tipo de fibra;
- longitud de onda;
- alcance;
- conector;
- plataforma/equipo.

Ejemplos de tecnologías Ethernet sobre fibra (IEEE 802.3) que aparecen en las fichas de los módulos:

| Tecnología | Velocidad | Fibra | Módulo habitual |
|---|---:|---|---|
| 1000BASE-SX | 1 Gb/s | Multimodo, 850 nm | SFP |
| 1000BASE-LX | 1 Gb/s | Monomodo, 1310 nm | SFP |
| 10GBASE-SR | 10 Gb/s | Multimodo, 850 nm | SFP+ |
| 10GBASE-LR | 10 Gb/s | Monomodo, 1310 nm | SFP+ |

Regla para leer el nombre: **S** (*short*) suele indicar multimodo y corto alcance; **L** (*long*), monomodo y mayor alcance.

Idea importante:

```text
encaja físicamente
≠
es técnicamente compatible
```

## 7.6. Seguridad

- no mirar directamente al extremo;
- no asumir que una fibra está inactiva;
- proteger conectores;
- no tocar superficies ópticas;
- respetar radios de curvatura;
- seguir normas del laboratorio.

# 8. Wi‑Fi como medio compartido

Wi‑Fi utiliza radio y varios dispositivos comparten el mismo medio. Eso cambia muchas de las reglas que hemos visto para el cable: la señal se debilita con la distancia y los obstáculos, otros equipos pueden interferir y todos los clientes de un punto de acceso se reparten el tiempo de transmisión.

Este apartado explica cómo se conecta un cliente a una red inalámbrica, qué estándares y bandas existen, qué métricas permiten valorar la calidad del enlace y cómo diagnosticar un problema **por etapas**, separando la radio, el acceso y la configuración.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Medio compartido** (*shared medium*) | ¿Compiten los clientes por el tiempo de emisión? | 30 portátiles en un mismo AP |
| **Estándar Wi‑Fi** (*IEEE 802.11 / Wi‑Fi generation*) | ¿Qué tecnología usan el AP y el cliente? | 802.11ax = Wi‑Fi 6 |
| **Banda** (*band*) | ¿En qué frecuencias se transmite? | 2,4 / 5 / 6 GHz |
| **Cobertura** (*coverage*) | ¿Llega suficiente señal al cliente? | Aula al final del pasillo |
| **Métricas** (*RSSI, SNR, retries…*) | ¿Qué calidad tiene el enlace radio? | RSSI −70 dBm, muchos reintentos |
| **Fases de acceso** (*association, authentication*) | ¿En qué paso se queda el cliente? | Ve el SSID pero no se conecta |
| **Seguridad básica** (*WPA2 / WPA3*) | ¿Cómo se protege el acceso? | WPA3-Personal con contraseña |

No debemos mezclar **radio** (hay señal), **acceso Wi‑Fi** (me he asociado y autenticado) y **configuración IP** (tengo dirección y salida): son etapas distintas con evidencias distintas.

```text
cliente Wi-Fi
      ↕
      AP
      ↕
red cableada
```

## 8.1. Compartir el medio

A diferencia de un enlace Ethernet full-duplex dedicado host-switch, varios clientes inalámbricos pueden competir por tiempo de transmisión.

Por tanto:

```text
tasa física
≠
throughput
```

## 8.2. Estándares IEEE 802.11

Los estándares Wi‑Fi los define el **IEEE 802.11**; la **Wi‑Fi Alliance** certifica los equipos y les da nombres comerciales más sencillos.

| Estándar IEEE | Nombre comercial | Bandas |
|---|---|---|
| 802.11b / a / g | (heredados, sin nombre de generación) | 2,4 GHz (b, g) · 5 GHz (a) |
| 802.11n | Wi‑Fi 4 | 2,4 y 5 GHz |
| 802.11ac | Wi‑Fi 5 | 5 GHz |
| 802.11ax | Wi‑Fi 6 / Wi‑Fi 6E | 2,4 y 5 GHz; 6E añade 6 GHz |
| 802.11be | Wi‑Fi 7 | 2,4, 5 y 6 GHz |

Las velocidades que anuncian los fabricantes son **máximos teóricos**; el cliente y el AP trabajan con el estándar común más alto que soporten ambos.

## 8.3. Cobertura y obstáculos

La señal puede degradarse por:

- distancia;
- paredes;
- materiales;
- geometría;
- ubicación;
- interferencia.

No se estudia propagación RF avanzada.

## 8.4. Bandas

### 2,4 GHz

- mayor alcance relativo;
- menos espectro;
- mayor probabilidad de interferencia.

### 5 GHz

- más espectro/canales;
- buenas prestaciones;
- menor alcance relativo.

### 6 GHz

- espectro adicional;
- requiere dispositivos compatibles;
- depende de plataforma/regulación.

No se necesita memorizar tablas completas de canales.

## 8.5. Métricas iniciales

| Métrica | Qué aporta |
|---|---|
| RSSI | Potencia recibida |
| SNR | Relación señal/ruido |
| Channel utilization | Ocupación del medio |
| PHY rate | Tasa física negociada |
| Retries | Reintentos |
| Throughput | Rendimiento útil |

El RSSI se expresa en dBm con valores negativos: **cuanto más cerca de 0, más señal** (−50 dBm es mejor que −75 dBm).

No existe:

```text
RSSI alto
=
throughput alto
```

como regla universal.

En el cliente, estas métricas pueden consultarse con `netsh wlan show interfaces` (Windows) o `iw dev <interfaz> link` / `nmcli device wifi list` (Linux).

## 8.6. Fases de acceso

De forma simplificada:

```text
detectar WLAN
→ seleccionar SSID
→ autenticación 802.11 y asociación con el AP
→ superar la seguridad de la red (WPA2/WPA3: clave o credenciales)
→ obtener configuración
→ comprobar conectividad
→ comprobar servicio
```

En las redes WPA2/WPA3, la comprobación de la clave (o de las credenciales de usuario) se realiza **después** de la asociación; la «autenticación 802.11» previa es solo un intercambio inicial con el AP.

Estas fases son diferentes.

Ejemplo:

```text
SSID visible
≠
autenticación correcta
≠
configuración IP correcta
≠
Internet accesible
```

## 8.7. Seguridad básica

Debemos reconocer:

- red abierta;
- WPA2;
- WPA3.

Tanto WPA2 como WPA3 tienen modo **Personal** (una clave compartida) y modo **Enterprise** (credenciales por usuario contra un servidor). WPA3 es la opción recomendada cuando todos los equipos la admiten, y es obligatoria en la banda de 6 GHz.

No es objetivo de U03 dominar:

- 802.1X;
- EAP;
- WLC;
- CAPWAP;
- arquitectura WLAN empresarial.

## 8.8. Diagnóstico por etapas

Preguntas:

```text
¿aparece el SSID?
→ ¿hay señal suficiente?
→ ¿se asocia?
→ ¿supera la autenticación (clave/credenciales)?
→ ¿obtiene configuración?
→ ¿hay conectividad?
→ ¿el rendimiento es adecuado?
```

Esto separa:

```text
radio
≠
acceso Wi-Fi
≠
configuración IP
≠
servicio
```

# 9. Documentación, mapas y trazabilidad

Administrar una red significa poder responder:

> **¿A qué puerto está conectado realmente este equipo?**

Sin documentación, cada avería empieza por seguir cables a mano. Este apartado explica cómo se organiza físicamente un armario, cómo se etiqueta cada conexión para poder reconstruirla y qué diferencia hay entre un mapa **físico** (dónde está y por dónde va cada cosa) y un mapa **lógico** (qué papel tiene cada equipo y cómo se relacionan).

También veremos que la documentación describe lo **esperado**, y que hay que contrastarla con lo **observado**, por ejemplo con la información de vecinos que dan CDP o LLDP.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Rack** | ¿Dónde y cómo se alojan paneles y equipos? | Rack con 2 patch panels y 2 switches |
| **Etiquetado** (*labeling*) | ¿Cómo identifico cada toma, panel y puerto? | `A1-023 → PP03-18 → SW02-Gi1/0/18` |
| **Registro** (*cabling record*) | ¿Dónde consta cada conexión y su estado? | Tabla toma–panel–puerto |
| **Mapa físico** (*physical map*) | ¿Dónde está cada equipo y por dónde va cada cable? | Plano con tomas y armario |
| **Mapa lógico** (*logical map*) | ¿Qué función tiene cada equipo y cómo se relacionan? | Esquema PC–switch–router–servidor |
| **CDP / LLDP** (*neighbor discovery*) | ¿Qué equipo hay realmente al otro lado de este puerto? | Vecino `SW2`, puerto `Gi0/2` |

La confusión típica es tratar la documentación como verdad: es un estado esperado que hay que verificar y mantener actualizado.

## 9.1. Rack

Un rack puede contener:

- patch panels;
- switches;
- routers;
- organizadores;
- fibra;
- PDU;
- UPS.

El objetivo no es diseñar un centro de datos completo.

Es comprender organización y trazabilidad.

## 9.2. Etiquetado

Una conexión debería poder reconstruirse:

```text
toma
→ patch panel
→ puerto de switch
```

Ejemplo:

```text
A1-023
→ PP03-18
→ SW02-Gi1/0/18
```

Una convención debe ser:

- única;
- coherente;
- documentada;
- mantenible.

## 9.3. Registro mínimo

| Toma | Patch panel | Puerto switch | Medio | Estado |
|---|---|---|---|---|
| A1-023 | PP03-18 | SW02-Gi1/0/18 | Cat 6A | Operativo |

## 9.4. Mapa físico

Representa:

- dispositivo;
- ubicación;
- interfaz;
- medio;
- toma;
- panel;
- puerto.

Ejemplo:

```text
PC-07
→ toma A1-023
→ PP03-18
→ SW02 Gi1/0/18
```

## 9.5. Mapa lógico básico

Representa relaciones funcionales:

- nombres de dispositivos;
- roles;
- enlaces;
- segmentos;
- servicios.

No necesita reflejar toda la ubicación física.

Mapa físico y lógico responden a preguntas diferentes.

## 9.6. Contrastar documentación

La documentación es un estado **esperado**.

La red real es el estado **observado**.

```text
documentación
→ verificar
→ comparar
→ actualizar
```

No se debe cambiar primero y documentar después de memoria.

## 9.7. CDP y LLDP como evidencia

**CDP** (*Cisco Discovery Protocol*) es propietario de Cisco; **LLDP** (*Link Layer Discovery Protocol*, IEEE 802.1AB) es el estándar equivalente multifabricante. Ambos hacen que cada equipo anuncie a su vecino directo su nombre y el puerto por el que está conectado.

En un entorno gestionable, una salida preparada puede mostrar:

```text
Local interface: Gi0/1
Neighbor: SW2
Remote port: Gi0/2
```

Puede utilizarse para contrastar el mapa.

En U03 no se configura CDP/LLDP.

Solo se interpreta.

# 10. Estado de interfaces, contadores y SNMP

La última competencia de U03 consiste en pasar de:

```text
“no funciona”
```

a:

```text
síntoma
→ alcance
→ recorrido físico
→ estado
→ contador
→ prueba
→ hipótesis
→ cambio mínimo
→ nueva medición
→ verificación
→ documentación
```

Para eso necesitamos **datos** del propio equipo: su estado actual y los contadores de errores que acumula. Este apartado enseña a consultarlos en Windows, Linux y Cisco IOS, a interpretar un contador **comparando dos medidas en el tiempo** y a entender cómo SNMP permite recoger esos mismos datos de forma remota y continua.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Estado de interfaz** (*interface status*) | ¿Cómo está la interfaz ahora mismo? | `up`, 1 Gb/s, full-duplex |
| **Contador** (*counter*) | ¿Cuántos eventos se han acumulado desde el último reinicio o borrado? | `CRC = 245` |
| **Tasa** (*rate*) | ¿Cuánto ha cambiado el contador en un intervalo? | +145 CRC en 5 minutos |
| **Línea base** (*baseline*) | ¿Qué valor es normal en esta red? | 0 errores/día en ese puerto |
| **SNMP** (*Simple Network Management Protocol*) | ¿Cómo obtengo esos datos de forma remota y periódica? | Un NMS consulta el switch cada 5 min |

La confusión típica es leer un contador alto como avería actual: un contador es historia acumulada, y solo su **evolución** indica si el problema sigue ocurriendo.

## 10.1. Estado de interfaz

Información útil:

- up/down;
- speed;
- duplex;
- autonegotiation;
- errores;
- descartes;
- link flaps;
- PoE;
- transceptor.

### Windows

```powershell
Get-NetAdapter
Get-NetAdapterStatistics
```

### Linux

```bash
ip link
ethtool <interfaz>
```

### Cisco IOS

A nivel de interpretación:

```text
show interfaces
show interfaces status
show interfaces counters errors
```

No se exige todavía administrar el switch mediante CLI.

## 10.2. Contadores

Un contador es acumulado.

Ejemplo:

```text
CRC = 245
```

por sí solo no demuestra que haya un fallo activo ahora.

Debemos medir evolución.

### Caso A

```text
CRC inicial = 245
CRC final   = 245
```

No se observan errores nuevos durante el intervalo.

### Caso B

```text
CRC inicial = 245
CRC final   = 390
```

El contador ha aumentado.

Procedimiento:

```text
registrar
→ reproducir tráfico/problema
→ volver a medir
→ comparar
```

## 10.3. Estado, contador y tasa

- **estado**: condición actual;
- **contador**: acumulación histórica;
- **tasa**: evolución durante un intervalo;
- **línea base**: valor habitual con el que comparar.

## 10.4. Un contador no explica automáticamente la causa

CRC crecientes pueden ser compatibles con:

- cable;
- conector;
- ruido;
- interfaz;
- transceptor;
- otros problemas físicos.

Hay que relacionar:

```text
contador
+
síntoma
+
prueba física
+
cambio controlado
```

## 10.5. SNMP como herramienta de observación

SNMP permite a un sistema de gestión obtener información de dispositivos.

| Componente | Función | Ejemplo |
|---|---|---|
| **NMS / gestor** (*manager*) | Consulta o recibe información | Zabbix, LibreNMS, PRTG |
| **Agente** (*agent*) | Expone la información del dispositivo | Servicio SNMP del switch |
| **MIB** (*Management Information Base*) | Organiza la información gestionada en un árbol | MIB de interfaces (IF-MIB) |
| **OID** (*Object Identifier*) | Identifica un dato concreto | Estado operativo de una interfaz |

Modelo básico:

```text
NMS / manager
      ↕
    agent
      ↕
información gestionada
```

### NMS / manager

Sistema que consulta o recibe información.

### Agent

Componente del dispositivo que expone información gestionable.

### MIB

Estructura que organiza información gestionada.

### OID

Identificador de un dato concreto.

Ejemplos de información:

- estado de interfaz;
- octetos;
- errores;
- CPU;
- temperatura.

## 10.6. Polling y notificación

Dos ideas:

```text
NMS
→ consulta periódica
→ polling
```

y:

```text
dispositivo
→ informa de evento
→ notification / trap
```

Las consultas llegan al agente por **UDP 161**; las notificaciones (*traps*) se envían al NMS por **UDP 162**.

## 10.7. Versiones de SNMP

| Versión | Seguridad | Uso |
|---|---|---|
| **SNMPv1** | Cadena de comunidad en texto claro | Obsoleta |
| **SNMPv2c** | Cadena de comunidad en texto claro; mejores contadores y operaciones | Muy extendida, solo en redes de gestión controladas |
| **SNMPv3** | Usuarios con autenticación y cifrado | Recomendada |

No se configura SNMPv3 ni comunidades en esta unidad.

El objetivo es comprender que la monitorización aporta evidencia incluso sin estar físicamente delante del equipo.

# 11. Caso integrado de diagnóstico físico

Este apartado reúne en un solo caso todo lo anterior: recorrido físico, estado de la interfaz, contadores, tester, cambio controlado y documentación. Sirve de modelo para resolver incidencias reales de forma ordenada, sin cambiar varias cosas a la vez ni sacar conclusiones antes de tener evidencia.

| Paso | Pregunta que responde | Evidencia |
|---|---|---|
| **1. Contador en el tiempo** (*counter trend*) | ¿El problema está ocurriendo ahora? | CRC inicial y final |
| **2. Recorrido** (*physical path*) | ¿Qué elementos atraviesa la conexión? | Camino PC → switch |
| **3. Prueba física** (*wiremap*) | ¿Hay un defecto medible en el cobre? | Resultado del tester |
| **4. Cambio mínimo** (*minimum change*) | ¿Qué único elemento cambio? | Componente sustituido |
| **5. Verificación** (*verification*) | ¿Ha mejorado de forma medible? | Velocidad, CRC, flaps |
| **6. Documentación** (*documentation*) | ¿Queda constancia para otros? | Informe de incidencia |

Escenario:

> Un puesto que normalmente enlaza a 1 Gb/s negocia a 100 Mb/s y sufre desconexiones.

Evidencias iniciales:

```text
link up
speed = 100 Mb/s
full-duplex
autonegotiation = on
CRC = 245
```

## 11.1. Paso 1 — No interpretar el contador demasiado pronto

Pregunta:

> ¿Los CRC están aumentando ahora?

Registrar.

Reproducir tráfico.

Volver a medir.

## 11.2. Paso 2 — Seguir el recorrido

```text
PC
→ latiguillo
→ toma
→ horizontal
→ patch panel
→ latiguillo
→ switch
```

## 11.3. Paso 3 — Wiremap

Supongamos:

```text
open pair
```

La hipótesis de canal de cobre gana fuerza.

## 11.4. Paso 4 — Cambio mínimo

En vez de cambiar simultáneamente:

- NIC;
- switch;
- configuración;
- cableado;

se cambia solo un componente controlado, por ejemplo:

```text
latiguillo
```

## 11.5. Paso 5 — Verificación

Después:

```text
speed = 1 Gb/s
CRC estable
sin nuevos link flaps
```

Ahora existe evidencia de mejora.

## 11.6. Paso 6 — Documentación

```text

Estado:
```

# 12. Síntesis de la unidad

Este apartado resume lo que debes saber hacer al terminar U03. Úsalo como lista de comprobación antes del examen: cada punto remite a un apartado de los apuntes.

# 14. Qué queda para U04 y U05

U03 termina cuando puedes responder:

> **¿Existe una infraestructura física o radioeléctrica correcta y qué evidencia lo demuestra?**

Una vez demostrado que el camino físico funciona, la siguiente pregunta es si el equipo está bien **integrado lógicamente** en la red. Esa pregunta la responden las dos unidades siguientes, que completan el RA2.

| Unidad | Pregunta que responde | Contenidos |
|---|---|---|
| **U03** | ¿Existe infraestructura física o radioeléctrica correcta? | Medio, enlace, acceso, comprobación, SNMP |
| **U04** | ¿Está el equipo correctamente integrado en IPv4? | IPv4, subnetting, VLSM, CIDR, DHCP |
| **U05** | ¿Está correctamente integrado en IPv6? | IPv6, SLAAC, DHCPv6, dual stack |

Más adelante, **U06** retomará el switch desde dentro (LED, consola, tabla MAC, STP, seguridad L2) y **U08** el acceso remoto seguro por SSH.

U04 responderá:

> **¿Está el equipo correctamente integrado en IPv4?**

Y U05:

> **¿Está correctamente integrado en IPv6?**

La secuencia queda:

```text
U03
medio / enlace / acceso
        ↓
U04
IPv4 / subnetting / DHCP
        ↓
U05
IPv6 / autoconfiguración
```

La regla profesional que se mantiene es:

```text
estado esperado
≠
estado observado
≠
causa demostrada
```

y:

```text
observar
→ medir
→ interpretar
→ cambiar una variable
→ volver a medir
→ verificar
→ documentar
```
