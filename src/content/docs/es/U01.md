# 1. De una comunicación cotidiana a una red

Todos usamos redes a diario sin pensar en ellas: enviamos mensajes, vemos vídeos, imprimimos o consultamos una plataforma educativa. Para un técnico, cada una de esas acciones es una **comunicación** que depende de muchos elementos que el usuario no ve.

Este apartado parte de lo cotidiano para llegar a tres ideas básicas:

| Idea | Pregunta que responde |
|---|---|
| **Comunicación** (*communication*) | ¿Qué elementos intervienen para que la información llegue? |
| **Red de datos** (*data network*) | ¿Qué sistema organizado hace posible esas comunicaciones? |
| **Internet** | ¿Qué ocurre cuando necesitamos comunicarnos con otras redes? |

Al final del apartado verás que una aplicación sencilla depende de una **cadena de elementos**, y que conocer esa cadena es el primer paso para diagnosticar problemas.

## 1.1. Comunicar información

Imagina que envías una fotografía desde tu teléfono a otra persona. Desde el punto de vista del usuario parece una acción sencilla, pero técnicamente intervienen varios elementos.

| Elemento | Función | Ejemplo |
|---|---|---|
| **Emisor** | Origina la información | Tu teléfono |
| **Receptor** | Recibe la información | Teléfono de destino |
| **Mensaje** | Información intercambiada | Fotografía |
| **Medio** | Transporta la señal | Radio, cobre o fibra |
| **Codificación** | Representa la información | Señal eléctrica, óptica o radioeléctrica |
| **Protocolo** | Define reglas de comunicación | Ethernet, IP, TCP, HTTPS |

Un **protocolo** es un conjunto de reglas que permite que dos o más sistemas intercambien información de forma compatible. No existe un único protocolo que resuelva toda la comunicación. En una conexión real actúan varios protocolos, cada uno encargado de una parte del problema.

## 1.2. Qué es una red de datos

Una **red de datos** es un sistema organizado de dispositivos, interfaces, medios, protocolos y servicios que permite intercambiar información entre aplicaciones y sistemas.

Una red profesional puede incluir:

- ordenadores, portátiles y teléfonos;
- servidores físicos o virtuales;
- impresoras, cámaras y sensores;
- switches, routers, puntos de acceso y firewalls;
- interfaces físicas y virtuales;
- enlaces de cobre, fibra o radio;
- servicios como DNS o DHCP;
- recursos locales, remotos o alojados en cloud.

Por tanto:

```text
red ≠ conjunto de ordenadores conectados por cables
```

Una red también tiene que poder administrarse, ampliarse, protegerse, supervisarse y recuperarse de determinados fallos.

## 1.3. Red e Internet no son lo mismo

Una red puede funcionar perfectamente sin acceso a Internet.

```text
PC ── switch ── servidor local
```

Internet es una **interconexión mundial de redes** administradas por organizaciones distintas.

```text
PC
 │
switch
 │
router
 │
proveedor
 │
Internet
```

La diferencia es importante porque un problema de Internet no significa necesariamente que la red local esté averiada.

## 1.4. Dependencias

Una aplicación aparentemente sencilla puede depender de muchos elementos:

```text
cliente
 → red local
 → gateway
 → proveedor
 → DNS
 → servidor
 → aplicación
```

Cuantas más dependencias existen, más importante es aprender a separar:

- qué sabemos;
- qué suponemos;
- qué necesitamos comprobar.

Esta forma de pensar será esencial para diagnosticar redes.

### Ideas clave

- Toda comunicación necesita emisor, receptor, mensaje, medio, codificación y **protocolos**; ningún protocolo resuelve él solo toda la comunicación.
- Una red no es solo un conjunto de equipos con cables: incluye servicios, configuraciones y la necesidad de administrarla.
- Una red local puede funcionar perfectamente sin Internet.
- Una aplicación sencilla depende de una **cadena de elementos**: separa lo que sabes, lo que supones y lo que debes comprobar.

### Comprueba que lo has entendido

1. Un usuario dice «no hay red» porque no carga una web externa, pero imprime sin problemas en la impresora del aula. ¿Qué le responderías?
2. Cita tres elementos de una red que **no** sean dispositivos.
3. Abres por nombre la intranet del centro, cuyo servidor y cuyo DNS están dentro de la red del centro. De la cadena `cliente → red local → gateway → proveedor → DNS → servidor`, ¿qué elementos no intervienen?

# 2. Componentes de una red

Una red está formada por elementos muy distintos: equipos de usuario, equipos de red, cables, ondas de radio y servicios que funcionan «por detrás». Para analizar una red es útil clasificar sus elementos según la **función** que desempeñan.

| Grupo | Pregunta útil |
|---|---|
| **Dispositivo final** (*end device / host*) | ¿Dónde se origina o consume la información? |
| **Dispositivo intermediario** (*intermediary device*) | ¿Qué equipo conecta, reenvía, filtra o protege? |
| **Interfaz** (*interface*) | ¿Por qué punto entra o sale la comunicación? |
| **Medio** (*medium*) | ¿Por dónde se propaga la señal? |
| **Servicio** (*service*) | ¿Qué función de infraestructura se utiliza? |

Un mismo equipo puede aparecer en varias categorías según lo que analicemos: un router doméstico, por ejemplo, integra funciones de router, switch, punto de acceso y firewall en una sola caja.

## 2.1. Dispositivos finales

Los **dispositivos finales** son los sistemas donde se originan o terminan las comunicaciones de usuario o de aplicación.

Ejemplos:

- PC;
- portátil;
- smartphone;
- servidor;
- impresora de red;
- teléfono IP;
- cámara;
- sensor.

Un servidor también es un dispositivo final desde el punto de vista de la red: recibe y envía tráfico, aunque normalmente proporcione servicios a otros equipos.

## 2.2. Dispositivos intermediarios

Los **dispositivos intermediarios** ayudan a transportar, dirigir, filtrar o controlar el tráfico. No suelen ser el origen ni el destino de la información del usuario, pero sin ellos la información no llegaría.

| Dispositivo | Función principal | Dónde suele estar |
|---|---|---|
| **Switch** | Conectar equipos dentro de una misma red local | Armario de comunicaciones, rack, bajo la mesa |
| **Router** (*enrutador*) | Conectar redes distintas y elegir por dónde enviar el tráfico | Salida de la red hacia otras redes o hacia el proveedor |
| **Punto de acceso** (*access point, AP*) | Dar acceso inalámbrico a la red cableada | Techo o pared de aulas y oficinas |
| **Firewall** (*cortafuegos*) | Permitir o bloquear tráfico según reglas | Frontera entre redes; también como software en los equipos |

### Switch

Un switch conecta dispositivos dentro de una red local y toma decisiones de reenvío en función de información de nivel de enlace. Más adelante estudiarás cómo aprende direcciones MAC y cómo decide por qué puerto enviar una trama.

### Router

Un router conecta redes diferentes y decide por dónde reenviar tráfico IP. En esta unidad basta con conservar una idea:

```text
misma red → puede existir comunicación directa
red diferente → normalmente interviene un router
```

### Punto de acceso

Un **access point** conecta dispositivos inalámbricos con la red. Proporciona acceso Wi-Fi, pero no debe confundirse automáticamente con un router.

### Firewall

Un firewall aplica políticas de seguridad al tráfico. Puede estar integrado en otro equipo o ser un dispositivo independiente.

## 2.3. Interfaces

Una **interfaz de red** es el punto por el que un dispositivo se conecta a una red.

Puede ser:

- Ethernet;
- Wi-Fi;
- fibra;
- virtual;
- lógica.

Un mismo equipo puede tener varias interfaces y, por tanto, participar en más de una comunicación o red.

## 2.4. Medios

La información puede desplazarse mediante distintos medios físicos o inalámbricos:

- cobre;
- fibra óptica;
- radio.

En U03 estudiarás estos medios con mayor detalle: conectores, categorías, alcance, pérdidas, interferencias, cableado estructurado y verificación.

## 2.5. Servicios de infraestructura

Una red no depende solo de hardware. También necesita servicios.

Dos ejemplos que aparecerán muchas veces son:

- **DNS**: relaciona nombres de dominio con direcciones IP;
- **DHCP**: permite obtener automáticamente parámetros de red.

En esta unidad solo necesitamos reconocer su función. El análisis detallado llegará después.

### Ideas clave

- Clasificamos los elementos de una red por su **función**: dispositivo final, dispositivo intermediario, interfaz, medio y servicio.
- El switch conecta equipos dentro de una red local; el router conecta redes distintas; el punto de acceso da acceso inalámbrico (no es automáticamente un router); el firewall aplica políticas.
- Un equipo puede tener varias interfaces, y una sola caja puede integrar varias funciones (el «router» doméstico).
- DNS y DHCP son **servicios de infraestructura**: la red depende de ellos aunque el usuario no los vea.

### Comprueba que lo has entendido

1. Clasifica: smartphone, punto de acceso, cable de fibra, servidor DHCP, tarjeta Wi-Fi de un portátil.
2. ¿Por qué un servidor es un dispositivo **final** si da servicio a otros equipos?
3. ¿Qué funciones integra normalmente el «router» que el operador instala en una vivienda?

# 3. Representar una red

Un técnico no puede ver una red entera de un vistazo: los cables van por falsos techos, los equipos están en armarios y la información es invisible. Por eso trabaja con **representaciones**: diagramas que muestran lo importante y ocultan el resto. En este módulo, además, muchas redes las construirás y probarás en un simulador, **Cisco Packet Tracer**, que es en sí mismo un diagrama «vivo».

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Topología física** (*physical topology*) | ¿Dónde están los equipos y por dónde va cada cable? | Plano del aula con el rack y las rosetas |
| **Topología lógica** (*logical topology*) | ¿Cómo se organiza la comunicación: qué redes hay y cómo se conectan? | Esquema con dos redes unidas por un router |
| **Enlace** (*link*) | ¿Qué une a dos dispositivos y por qué interfaces? | `SW-20 G0/1 ↔ R-20 G0/0/0` |
| **Nombre de interfaz** (*interface name*) | ¿Qué puerto concreto es? | `Fa0/2`, `G0/0/1` |
| **Luz de enlace** (*link light*) | ¿Hay enlace en ese puerto? | Verde, ámbar, rojo |
| **Simulador** (*network simulator*) | ¿Cómo construyo y pruebo una red sin equipos reales? | Packet Tracer |

Una buena representación es la base de la documentación y de cualquier diagnóstico posterior. Pero ten presente desde el principio una idea que repetiremos: **un dibujo muestra cómo debería ser la red; solo una prueba demuestra cómo se comporta**.

## 3.1. Por qué representamos

Una red real contiene demasiados detalles para analizarlos todos a la vez. Por eso utilizamos **diagramas y topologías**.

Una representación útil debe permitir responder preguntas como:

- ¿qué dispositivos existen?;
- ¿cómo están conectados?;
- ¿qué enlaces son críticos?;
- ¿qué equipos dependen de otros?;
- ¿qué camino puede seguir una comunicación?

## 3.2. Topología física y lógica

La **topología física** describe cómo están conectados físicamente los equipos: dónde está cada uno, qué cable sale de cada puerto y a qué armario llega.

La **topología lógica** describe cómo se organiza la comunicación desde el punto de vista funcional: qué redes existen, qué equipos pertenecen a cada una y por dónde pasa el tráfico entre ellas.

No siempre coinciden. Dos ejemplos:

| Situación | Vista física | Vista lógica |
|---|---|---|
| Un aula con 20 PC cableados y 10 portátiles por Wi-Fi | PC unidos por cable a un switch del rack; portátiles conectados por radio a un punto de acceso del techo | Una sola red: PC y portátiles se comunican como si estuvieran en el mismo «sitio» |
| Un centro con administración y alumnado en la misma planta | Todos los equipos conectados al mismo switch | Dos redes separadas que solo se comunican a través de un router y sus reglas (lo construirás en U07) |

Históricamente, los antiguos *hubs* daban otro ejemplo clásico: físicamente formaban una estrella, pero lógicamente funcionaban como un **bus**, porque todo lo que entraba por un puerto se repetía por todos los demás.

Para un técnico, las dos vistas son necesarias: la física para **encontrar** un cable o un puerto; la lógica para **entender** por qué dos equipos pueden o no comunicarse.

## 3.3. Leer un diagrama: dispositivos, interfaces y enlaces

Un diagrama de red se lee siempre con los mismos elementos:

| Elemento | Cómo aparece | Qué debes leer |
|---|---|---|
| **Dispositivo** | Icono con un nombre (`PC-07`, `SW-20`, `R-20`) | Qué tipo de equipo es y cómo se llama |
| **Interfaz** | Etiqueta junto al extremo del cable (`Fa0/2`, `G0/1`) | Por qué puerto concreto entra o sale la comunicación |
| **Enlace** | Línea entre dos interfaces | Qué dos interfaces une y con qué tipo de medio |
| **Nube** | Icono de nube (Internet, proveedor) | Una parte que **no** detallamos: todo diagrama simplifica |

Un enlace se lee de un extremo al otro: **dispositivo + interfaz ↔ interfaz + dispositivo**. Por ejemplo:

```text
SW-20 G0/1  ↔  G0/0/0 R-20
```

Se lee: «la interfaz GigabitEthernet 0/1 del switch SW-20 está conectada a la interfaz GigabitEthernet 0/0/0 del router R-20».

### Nombres de interfaz

Los equipos de red nombran cada puerto con su **tipo** y su **posición**:

| Nombre (abreviado) | Nombre completo | Velocidad máxima | Cómo se lee la posición |
|---|---|---|---|
| `Fa0/2` | FastEthernet0/2 | 100 Mb/s | módulo 0, puerto 2 |
| `G0/1` o `Gi0/1` | GigabitEthernet0/1 | 1 Gb/s | módulo 0, puerto 1 |
| `G0/0/1` | GigabitEthernet0/0/1 | 1 Gb/s | ranura 0, módulo 0, puerto 1 (routers modulares) |
| `Fa0` / `G0` | FastEthernet0 / GigabitEthernet0 | — | única interfaz de un PC o impresora |

No hace falta memorizar la numeración de cada modelo: basta con saber leerla y copiarla exactamente en la documentación. Un error de una cifra en un diagrama envía al siguiente técnico al puerto equivocado.

## 3.4. Leer una red en Packet Tracer

**Cisco Packet Tracer** es un simulador de redes gratuito que utilizarás durante todo el módulo. Permite construir una topología, configurar los equipos y **probar** la comunicación sin disponer de los dispositivos reales. En esta unidad lo usamos sobre todo para **representar y observar**.

### Elementos de la ventana

| Elemento | Para qué sirve |
|---|---|
| **Espacio de trabajo lógico** (*Logical*) | Vista habitual: dispositivos, enlaces y etiquetas. Es la topología lógica dibujada |
| **Espacio de trabajo físico** (*Physical*) | Edificios, armarios y racks: la ubicación física de los equipos |
| **Paneles de dispositivos y conexiones** (parte inferior) | Elegir dispositivos (*Network Devices*, *End Devices*…) y cables (*Connections*) |
| **Modo *Realtime* / *Simulation*** (esquina inferior derecha) | Tiempo real, o paso a paso para ver cada mensaje (lo usarás en U02) |
| **Fast Forward Time** | Adelanta el reloj de la simulación para no esperar a que los puertos se activen |

### La ventana de un dispositivo

Al hacer clic en un dispositivo se abre su ventana con varias pestañas:

| Pestaña | Qué contiene | Equipos |
|---|---|---|
| **Physical** | El aspecto del equipo: módulos, puertos, botón de encendido | Todos |
| **Config** | Ajustes con formularios: *Display Name*, interfaces, IP | Todos |
| **Desktop** | Utilidades del usuario: *IP Configuration*, *Command Prompt*, navegador | PC, portátiles, servidores |
| **CLI** | Línea de comandos del sistema del equipo (Cisco IOS) | Switches y routers |

Ojo con una confusión frecuente: el **Display Name** (pestaña *Config*) es el nombre que ves en el diagrama; el *hostname* que se configura por CLI es el nombre interno del equipo. En el diagrama de esta unidad documentamos con el *Display Name*.

### Luces de enlace

En cada extremo de un enlace aparece un indicador de color. Es tu primera evidencia del estado físico:

| Color | Qué significa | Qué hacer |
|---|---|---|
| **Verde** | Hay enlace: la interfaz puede enviar y recibir | Nada: pero recuerda que verde no demuestra que los equipos se comuniquen |
| **Ámbar** | El puerto de un switch se está preparando antes de reenviar tráfico (unos segundos; el motivo se estudia en U06) | Esperar o usar *Fast Forward Time*; no cambiar el cable |
| **Rojo** | No hay enlace: cable en un puerto incorrecto, otro extremo apagado o **interfaz desactivada** | Comprobar la configuración de las dos interfaces antes de cambiar el cable |

En los routers, las interfaces vienen **desactivadas** por defecto: un enlace rojo entre dos routers recién conectados es lo esperable, no un cable defectuoso.

### Cables

Packet Tracer ofrece varios tipos de conexión: automática (icono del rayo: el programa elige el cable), cobre directo, cobre cruzado, consola, fibra y serie. En esta unidad basta con elegir el cable automático o el **directo** (*Copper Straight-Through*) entre un PC y un switch. Por qué existen los demás se estudia en U03.

### Probar la comunicación: *Add Simple PDU*

La herramienta **Add Simple PDU** (icono del sobre cerrado) envía una prueba de comunicación entre dos equipos: se hace clic **primero en el origen** y después en el destino. El resultado aparece en la lista inferior derecha como **Successful** o **Failed**. Si un resultado te sorprende justo después de conectar un cable, pulsa *Fast Forward Time* y repite la prueba.

### Documentar dentro del archivo

- **Etiquetas de puerto:** *Options → Preferences → Interface → Always Show Port Labels in Logical Workspace* (en algunas versiones, en otra pestaña de *Preferences*). Si no las activas, pasar el ratón por un enlace también muestra los puertos.
- **Notas** (*Place Note*): texto libre en el diagrama para explicar una decisión o un estado.
- **Guardar:** los archivos de Packet Tracer tienen extensión `.pkt`. Guarda con un nombre que indique qué contiene.

## 3.5. Un diagrama no demuestra la comunicación

Un diagrama, incluso uno con todas las luces en verde, **no garantiza** que dos equipos puedan comunicarse. Puede faltar una dirección, una interfaz puede estar desactivada en el otro extremo, o los equipos pueden estar en redes distintas sin un router configurado.

```text
dibujado        ≠  conectado
conectado (luz verde)  ≠  comunicando
comunicando     →  solo lo demuestra una prueba
```

Por eso, en cualquier red que construyas o recibas, la secuencia será siempre: **observar → predecir → probar**.

### Ideas clave

- La topología **física** dice dónde están los equipos y los cables; la **lógica**, cómo se organiza la comunicación. No siempre coinciden.
- Un enlace se lee de extremo a extremo: **dispositivo + interfaz ↔ interfaz + dispositivo** (`SW-20 G0/1 ↔ G0/0/0 R-20`).
- En Packet Tracer: verde = enlace; ámbar = puerto preparándose; rojo = sin enlace o interfaz desactivada.
- Un diagrama, aunque esté todo en verde, no demuestra la comunicación: hace falta una **prueba**.

### Comprueba que lo has entendido

1. Lee este enlace y nombra cada parte: `AP-03 G0 ↔ G0/12 SW-03`.
2. Abres un archivo de Packet Tracer y el enlace entre dos routers aparece en rojo en ambos extremos. Tu compañero propone cambiar el cable. ¿Qué le respondes?
3. Pon un ejemplo en el que la topología física y la lógica no coincidan.

# 4. Tipos de red y arquitecturas de servicio

Una misma red puede clasificarse desde varios puntos de vista: por su **alcance**, por **quién la administra y quién puede usarla**, o por cómo se **organizan los servicios** entre los equipos. No debemos mezclar esos criterios: una red puede ser a la vez LAN, privada y cliente-servidor.

| Criterio | Pregunta | Ejemplos |
|---|---|---|
| **Alcance** (*scope*) | ¿Qué extensión geográfica cubre? | PAN, LAN, WLAN, MAN, WAN |
| **Administración y acceso** | ¿Quién la gestiona y quién puede conectarse? | Red privada, red pública |
| **Arquitectura de servicios** | ¿Cómo se reparten los papeles entre los equipos? | Cliente-servidor, P2P |

Al final del apartado verás también por qué las redes **no dejan de cambiar**, y dónde estudiarás esos cambios a lo largo del módulo.

## 4.1. Clasificar por alcance

Las siglas de tipos de red son útiles si entendemos el criterio.

| Tipo | Idea general |
|---|---|
| **PAN** | entorno personal de corto alcance |
| **LAN** | red local, normalmente de una vivienda, aula, oficina o edificio |
| **WLAN** | LAN que utiliza acceso inalámbrico |
| **MAN** | red de alcance metropolitano: une sedes de una misma ciudad (p. ej., fibra municipal) |
| **WAN** | conecta ubicaciones o redes separadas geográficamente |

Estas categorías no describen por sí solas todos los aspectos de una red.

Una misma red puede ser a la vez:

- LAN;
- privada;
- Ethernet;
- cliente-servidor.

Son criterios diferentes.

## 4.2. Red pública y red privada

Según **quién la administra y quién puede usarla**:

| Tipo | Idea | Ejemplos |
|---|---|---|
| **Red privada** | La administra una organización y solo pueden usarla sus usuarios autorizados | Red del centro, red de una empresa, red de tu casa |
| **Red pública** | Se ofrece acceso al público en general, normalmente con condiciones | Wi-Fi de una biblioteca o de un aeropuerto, red de un operador de telecomunicaciones |

«Pública» no significa «todo está abierto». Una biblioteca puede ofrecer Wi-Fi al público, pero:

- la infraestructura sigue administrada;
- los usuarios no tienen acceso a todos los recursos;
- pueden existir filtros y políticas;
- poder conectarse no concede control sobre la red.

**No confundas tres usos de las mismas palabras:**

| Expresión | Se refiere a… | Dónde se estudia |
|---|---|---|
| Red pública / privada | Quién administra la red y quién puede conectarse | Este apartado |
| Dirección IP pública / privada | Si una dirección puede usarse directamente en Internet (`203.0.113.80`) o solo dentro de una organización (`192.168.10.25`) | U04 y U10 |
| Perfil de red «público» / «privado» de Windows | Lo restrictivo que es el firewall del equipo en esa conexión (en una cafetería conviene «público») | Seguridad del sistema operativo |

Por ejemplo, la Wi-Fi **pública** de una biblioteca suele entregar a los usuarios direcciones IP **privadas**, y el router de la biblioteca sale a Internet con una dirección **pública**.

## 4.3. Cliente y servidor son roles

Un **cliente** solicita un servicio.

Un **servidor** proporciona un servicio.

Estos términos describen roles en una comunicación, no necesariamente tipos fijos de dispositivo.

Un mismo equipo puede actuar como cliente en una comunicación y como servidor en otra.

Ejemplo:

```text
PC → servidor DNS
PC = cliente
DNS = servidor
```

pero un servidor de aplicaciones puede ser cliente de una base de datos.

## 4.4. Arquitectura cliente-servidor

En una arquitectura cliente-servidor, determinados sistemas proporcionan servicios a otros.

Ventajas habituales:

- administración centralizada;
- control de acceso;
- copias de seguridad más organizadas;
- datos compartidos;
- políticas comunes.

Riesgos:

- dependencia de determinados servicios;
- necesidad de redundancia;
- mayor impacto si falla un componente central sin alternativa.

## 4.5. Arquitectura P2P

En un modelo **peer-to-peer (P2P)** los equipos comparten recursos **entre iguales**: cada equipo puede pedir y ofrecer a la vez, sin un servidor central que lo organice todo.

Ejemplos:

- dos portátiles que comparten una carpeta directamente en una red doméstica;
- el envío directo de archivos entre teléfonos cercanos;
- aplicaciones de intercambio de archivos (por ejemplo, BitTorrent), en las que cada equipo descarga partes de otros y a la vez las ofrece.

| | Cliente-servidor | P2P |
|---|---|---|
| Quién ofrece el servicio | Equipos dedicados (servidores) | Cualquier equipo participante |
| Administración y copias | Centralizadas | Repartidas entre los equipos |
| Si falla un equipo | Puede caer el servicio si era el servidor | El resto puede seguir |
| Escala | Requiere dimensionar los servidores | Crece con los participantes, pero es difícil de controlar |

P2P no significa «sin red» ni «sin reglas»: cambia cómo se reparten los roles y los recursos. En una organización suele limitarse, porque dificulta el control de accesos y las copias de seguridad.

## 4.6. Factores que impulsan la evolución de las redes

Las redes no dejan de crecer ni de cambiar. Conocer los motivos ayuda a entender por qué aparecen nuevas tecnologías y por qué otras se abandonan.

| Factor | Qué exige a la red | Ejemplo |
|---|---|---|
| Movilidad | Acceso desde cualquier lugar y dispositivo | Wi-Fi en todo el edificio, 4G/5G |
| Servicios en la nube | Conexión a Internet fiable y con capacidad | Correo, ofimática y almacenamiento en la nube |
| Vídeo y colaboración | Mucho ancho de banda y baja latencia | Videollamadas, streaming, formación en línea |
| Internet de las cosas (IoT) | Enormes cantidades de dispositivos con dirección | Sensores, cámaras, climatización |
| Virtualización | Redes que también existen dentro de los servidores | Máquinas virtuales, contenedores |
| Teletrabajo | Acceso seguro desde fuera de la organización | VPN, servicios publicados |
| Seguridad | Segmentación, control de acceso, registro | VLAN, ACL, cifrado |
| Agotamiento de IPv4 | Nuevo direccionamiento | IPv6, NAT |
| Automatización | Configuración de muchos equipos a la vez | Plantillas, APIs, herramientas de gestión |

Muchos de estos factores reaparecerán a lo largo del módulo: IPv6 en U05, VLAN en U07, ACL en U08, NAT en U10.

### Ideas clave

- Una red se clasifica con **criterios distintos** que no hay que mezclar: alcance (PAN, LAN, WLAN, MAN, WAN), administración y acceso (pública/privada) y arquitectura de servicios (cliente-servidor, P2P).
- Red pública/privada (quién la usa) **no es lo mismo** que dirección IP pública/privada (dónde es válida una dirección).
- Cliente y servidor son **roles** en una comunicación, no tipos fijos de equipo.
- Las redes evolucionan impulsadas por la movilidad, la nube, el vídeo, el IoT, la virtualización, el teletrabajo, la seguridad, el agotamiento de IPv4 y la automatización.

# 5. Topologías, dependencias y redundancia

Una vez que sabes leer un diagrama, la pregunta siguiente es práctica: **¿qué ocurre si falla un elemento?** La respuesta depende de la forma de la red, es decir, de su topología, y de qué servicio queramos mantener.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Topología** (*topology*) | ¿Qué forma tienen las conexiones? | Estrella, jerárquica, malla |
| **Dependencia** (*dependency*) | ¿De qué elementos depende un servicio? | Navegar depende del switch, del router y del proveedor |
| **Redundancia** (*redundancy*) | ¿Hay caminos o componentes alternativos? | Dos enlaces entre switches |
| **Punto único de fallo** (*SPOF*) | ¿Qué elemento deja el servicio sin alternativa si falla? | El único router de salida |

## 5.1. Visión de conjunto

| Topología | Idea | Uso actual |
|---|---|---|
| **Estrella** (*star*) | Todos los equipos se conectan a un punto central | LAN Ethernet y Wi-Fi |
| **Jerárquica** (*hierarchical / extended star*) | Varias estrellas unidas por niveles | Redes de empresa y de centros educativos |
| **Malla** (*mesh*) | Varios caminos entre dispositivos | Núcleo de redes, enlaces entre sedes |
| **Bus** | Un medio compartido por todos | Histórica (Ethernet coaxial) |
| **Anillo** (*ring*) | Cada nodo pasa la información al siguiente | Histórica y algunos anillos de fibra |

## 5.2. Estrella

En una topología en estrella, varios equipos se conectan a un punto central.

```text
 PC1
  |
PC2 ─ switch ─ PC3
  |
 PC4
```

Ventajas:

- sencilla de ampliar;
- un fallo de un enlace de acceso suele afectar a un único dispositivo;
- facilita localizar determinadas incidencias.

Riesgo:

- si el dispositivo central no tiene redundancia, puede convertirse en un punto único de fallo.

## 5.3. Estructura jerárquica

Las redes de empresas y centros educativos se organizan en **niveles**, cada uno con una función. Así pueden crecer por bloques, administrarse con orden y añadir redundancia donde más importa.

```text
NÚCLEO           SW-N1 ═══════ SW-N2
                   │  ╲       ╱  │
                   │    ╲   ╱    │
                   │      ╳      │
                   │    ╱   ╲    │
DISTRIBUCIÓN     SW-D1         SW-D2
                 ╱    ╲       ╱    ╲
ACCESO        SW-A1  SW-A2  SW-A3  SW-A4
                │      │      │      │
               PC     PC     AP   impresoras
```

| Nivel | Función | Qué se conecta |
|---|---|---|
| **Acceso** (*access*) | Dar conexión a los usuarios y dispositivos finales | PC, puntos de acceso, impresoras, teléfonos IP |
| **Distribución** (*distribution*) | Agrupar los switches de acceso de una zona y aplicar políticas entre redes | Switches de acceso de una planta o edificio |
| **Núcleo** (*core*) | Transportar tráfico muy rápido entre bloques y hacia la salida | Switches de distribución, servidores, routers de salida |

En redes pequeñas y medianas, como un instituto, distribución y núcleo suelen unirse en un único nivel: es el diseño de **núcleo colapsado** (*collapsed core*), con dos niveles en lugar de tres.

No necesitas memorizar un diseño de campus completo. Lo importante es reconocer que una red grande se organiza en **bloques con funciones distintas** y que los niveles superiores son los que más equipos afectan si fallan; por eso suelen duplicarse.

## 5.4. Malla

En una topología de **malla** existen varios caminos posibles entre determinados puntos.

```text
Malla completa (4 nodos)        Malla parcial (4 nodos)
   A ───── B                       A ───── B
   │ ╲   ╱ │                       │     ╱ │
   │   ╳   │                       │   ╱   │
   │ ╱   ╲ │                       │ ╱     │
   C ───── D                       C       D
```

- En una **malla completa** cada nodo se une con todos los demás. El número de enlaces crece muy deprisa: con *n* nodos hacen falta *n·(n−1)/2* enlaces (4 nodos → 6 enlaces; 10 nodos → 45).
- En una **malla parcial** solo se duplican los caminos más importantes. Es lo habitual en la práctica.

La malla mejora la **resiliencia**, pero también aumenta el coste, la complejidad y la necesidad de mecanismos de control que eviten que el tráfico circule en bucle (STP en U06, protocolos de routing en U09).

## 5.5. Bus y anillo

```text
Bus                                   Anillo
PC1   PC2   PC3   PC4                 PC1 ──── PC2
 │     │     │     │                   │        │
═╧═════╧═════╧═════╧═  (cable común)   PC4 ──── PC3
```

- En un **bus** todos los equipos comparten un único cable. Lo que envía uno lo reciben todos, solo puede transmitir uno a la vez y una rotura del cable afecta a toda la red. Fue la base de las primeras redes Ethernet con cable coaxial.
- En un **anillo** cada equipo recibe del anterior y entrega al siguiente. Se usó en redes de área local antiguas y sigue utilizándose en algunos **anillos de fibra** de operadores y redes metropolitanas, con mecanismos para recuperarse si se corta un tramo.

Hoy no se diseñan LAN Ethernet en bus ni en anillo, pero conocerlas ayuda a entender por qué la estrella se impuso y por qué aparecen en documentación antigua.

## 5.6. Redundancia y SPOF

La **redundancia** introduce caminos o componentes alternativos para reducir el impacto de fallos.

Un **SPOF** (*Single Point of Failure*) es un elemento cuyo fallo puede interrumpir por completo una función o servicio.

Ejemplo:

```text
PCs ─ switch único ─ router único ─ Internet
```

El switch o el router pueden ser SPOF dependiendo del servicio que analicemos.

La pregunta correcta no es solo:

> “¿Hay redundancia?”

sino:

> “¿Qué servicio intentamos mantener y qué elemento puede dejarlo sin alternativa?”

## 5.7. Analizar el impacto de un fallo

Para analizar una topología no basta con «buscar el elemento central». Conviene seguir siempre los mismos pasos:

1. elegir el **servicio** que se quiere mantener;
2. trazar la **cadena de dependencias** de ese servicio en el diagrama;
3. marcar los elementos sin alternativa: son sus **SPOF**;
4. proponer una mejora y valorar su **coste**.

**Ejemplo resuelto.** Una clínica dental tiene tres PC en recepción, un punto de acceso para las tabletas de los gabinetes y la agenda de citas en un servicio en la nube.

```text
PC-R1 ─┐
PC-R2 ─┼── SW-CL ── R-CL ── proveedor ── Internet ── agenda en la nube
PC-R3 ─┤
AP-CL ─┘
```

| Servicio | Cadena de dependencias | SPOF | Mejora posible | Inconveniente |
|---|---|---|---|---|
| Consultar la agenda desde recepción | PC → SW-CL → R-CL → proveedor → Internet → nube | SW-CL, R-CL y el proveedor | Segunda línea de otro operador (por ejemplo, 5G) en el router | Coste mensual; el router sigue siendo SPOF |
| Que PC-R1 y PC-R2 compartan una carpeta | PC → SW-CL → PC | SW-CL | Switch de repuesto configurado en el armario | Requiere que alguien lo cambie |
| Consultar la agenda desde las tabletas | Tableta → AP-CL → SW-CL → R-CL → … | AP-CL además de los anteriores | Segundo punto de acceso | Coste y planificación de canales (U03) |

Observa que **el SPOF depende del servicio**: el proveedor es un SPOF para la agenda, pero no para compartir una carpeta. Y que añadir redundancia en un punto (dos operadores) no elimina los demás SPOF (el router y el switch siguen siendo únicos).

### Ideas clave

- La estrella es la topología dominante en las LAN; su punto central puede ser un **SPOF**.
- Las redes grandes se organizan en niveles (acceso, distribución, núcleo); en redes medianas, con **núcleo colapsado**.
- La malla ofrece caminos alternativos a cambio de coste y complejidad; en la práctica se usa la malla **parcial**.
- El SPOF depende del **servicio** que analizas, y añadir redundancia en un punto no elimina todos los SPOF.

# 6. Arquitectura por capas: primer mapa TCP/IP

Cuando algo falla en una red, la lista de posibles causas es enorme: un cable, una configuración, un servicio, la propia aplicación… Para no perderse, los técnicos usan **modelos por capas** (*layered models*): dividen la comunicación en niveles y cada nivel resuelve un problema concreto.

En este apartado construirás un primer mapa con el **modelo TCP/IP de cinco capas** y conocerás el **modelo OSI** como referencia. El objetivo no es memorizar listas, sino tener una pregunta para cada capa:

| Capa | Pregunta |
|---|---|
| Aplicación | ¿Qué servicio necesita la aplicación? |
| Transporte | ¿Qué proceso debe recibir los datos? |
| Red | ¿A qué red y equipo debe llegar? |
| Enlace de datos | ¿Cómo se entrega en el enlace local? |
| Física | ¿Cómo se transmite la señal? |

En U02 estudiarás con detalle cómo trabajan juntas estas capas (encapsulación, cabeceras y análisis de tráfico).

## 6.1. Por qué necesitamos capas

Una comunicación de red resuelve problemas diferentes al mismo tiempo:

- transmitir bits;
- entregar información dentro de un enlace local;
- llegar a otra red;
- comunicar procesos;
- ofrecer servicios de aplicación.

Intentar explicar todo como un único mecanismo sería demasiado complejo.

Por eso utilizamos **capas**: agrupamos funciones relacionadas y estudiamos cada problema con un nivel de detalle adecuado.

## 6.2. Modelo TCP/IP de cinco capas

En este módulo utilizaremos como mapa inicial un modelo TCP/IP de cinco capas:

| Capa | Pregunta funcional inicial | Ejemplos |
|---|---|---|
| **Aplicación** | ¿Qué servicio usa la aplicación? | HTTP, DNS, DHCP, SSH |
| **Transporte** | ¿Qué proceso o servicio debe recibir los datos? | TCP, UDP, puertos |
| **Red** | ¿A qué red/equipo IP debe llegar la información? | IPv4, IPv6, routing |
| **Enlace de datos** | ¿Cómo se entrega en el enlace local? | Ethernet, MAC |
| **Física** | ¿Cómo se transmite la señal? | cobre, fibra, radio |

Este modelo no significa que “un problema pertenece siempre a una sola capa”. Sirve para organizar funciones y preguntas.

## 6.3. OSI como referencia

El modelo OSI divide la comunicación en siete capas. Sigue siendo útil como referencia conceptual y terminológica.

No necesitas memorizar ahora cada detalle. En U02 relacionaremos ambos modelos con mayor precisión.

## 6.4. Primer uso diagnóstico

Supón que un usuario dice:

> “No puedo abrir una web.”

Todavía no sabemos si el problema está en:

- la conexión física;
- la red local;
- el direccionamiento IP;
- la ruta;
- DNS;
- el servidor;
- la aplicación.

Las capas ayudan a evitar conclusiones prematuras y a formular mejores preguntas.

### Ideas clave

- Las capas separan una comunicación en problemas más pequeños; cada capa tiene **su pregunta**.
- El modelo TCP/IP de cinco capas es el mapa del módulo; OSI se usa como referencia y vocabulario.
- Un problema no siempre pertenece a una sola capa: las capas organizan preguntas, no reparten culpas.
- Pensar por capas evita conclusiones prematuras ante un síntoma vago.

2. ¿Qué pregunta responde la capa de red?

# 7. Identificadores: nombre, puerto, IP, MAC y gateway

Para que una comunicación llegue a su destino hay que identificar **qué** queremos, **dónde** está y **por dónde** salir. En redes aparecen distintos identificadores porque responden a preguntas diferentes, y cada uno pertenece a una capa distinta del modelo del apartado anterior.

| Identificador | Capa | Ejemplo | Lo ve el usuario |
|---|---|---|---|
| **Nombre** (*name*) | Aplicación | `www.example.com` | Sí |
| **Puerto** (*port*) | Transporte | `443` | A veces (en la URL) |
| **Dirección IP** (*IP address*) | Red | `192.168.10.25` | Casi nunca |
| **Dirección MAC** (*MAC address*) | Enlace de datos | `00:1A:2B:3C:4D:5E` | No |
| **Puerta de enlace** (*default gateway*) | Red | `192.168.10.1` | No |

Entender qué hace cada uno te permitirá, más adelante, saber qué comprobar cuando algo falla: un error de nombre no se arregla cambiando una MAC.

## 7.1. Mapa funcional

| Elemento | Pregunta que ayuda a responder |
|---|---|
| **Nombre** | ¿Qué recurso o sistema quiero utilizar? |
| **Puerto** | ¿Qué servicio o proceso quiero alcanzar? |
| **Dirección IP** | ¿Qué interfaz IP es el destino? |
| **Dirección MAC** | ¿Qué interfaz participa en el enlace local? |
| **Default gateway** | ¿A qué router entrego tráfico destinado fuera de mi red local? |

No son equivalentes ni intercambiables.

## 7.2. Nombre

Los nombres son más fáciles de recordar que las direcciones.

Ejemplo:

```text
www.example.com
```

Para comunicarse mediante IP, ese nombre normalmente debe relacionarse con una dirección. DNS participa en ese proceso.

## 7.3. Puerto

Un host puede ejecutar varias aplicaciones de red al mismo tiempo. Los **puertos** ayudan a identificar procesos o servicios de transporte.

Ejemplos habituales:

- HTTP: 80/TCP;
- HTTPS: 443/TCP;
- DNS: 53/UDP y 53/TCP según el caso;
- SSH: 22/TCP.

En U02 estudiarás transporte con más detalle.

## 7.4. Dirección IP

Una dirección IP identifica una interfaz dentro del contexto de una red IP.

Ejemplo IPv4:

```text
192.168.10.25
```

La dirección no se interpreta de forma aislada: también necesitamos información como el prefijo o máscara.

Los cálculos de red, broadcast, subnetting y VLSM pertenecen a U04.

## 7.5. Dirección MAC

Una dirección MAC se utiliza en tecnologías de enlace como Ethernet para identificar interfaces dentro del enlace local.

Ejemplo:

```text
00:1A:2B:3C:4D:5E
```

En U02 observarás cómo aparecen las direcciones MAC en las tramas. En U06 estudiarás cómo las utilizan los switches.

## 7.6. Default gateway

El **default gateway** es la dirección (normalmente la del router) a la que un host entrega tráfico destinado a redes que no considera locales.

Una forma útil de pensar es:

```text
destino local
→ comunicación dentro de la red local

destino remoto
→ necesito un camino hacia otras redes
→ normalmente utilizo el default gateway
```

La decisión exacta sobre qué es “local” y qué es “remoto” se estudiará con IPv4 e IPv6.

## 7.7. Cómo se escriben los identificadores: decimal, binario y hexadecimal

Los equipos trabajan con **bits** (0 y 1). Las personas escribimos esos bits de una forma más cómoda: las direcciones IPv4 en **decimal** y las MAC en **hexadecimal**.

| Identificador | Tamaño | Cómo se escribe | Ejemplo |
|---|---|---|---|
| IPv4 | 32 bits = 4 octetos | 4 números decimales (0–255) separados por puntos | `192.168.10.25` |
| MAC | 48 bits = 6 octetos | 12 dígitos hexadecimales | `00:1A:2B:3C:4D:5E` |

### Del octeto al decimal

Un **octeto** son 8 bits. Cada posición tiene un peso:

```text
peso:   128  64  32  16   8   4   2   1
bits:     1   1   0   0   0   0   0   0   →  128 + 64 = 192
```

Ejemplos:

```text
192 = 128 + 64             → 1100 0000 → C0
168 = 128 + 32 + 8         → 1010 1000 → A8
255 = todos los bits a 1   → 1111 1111 → FF
```

### Del binario al hexadecimal

Cada dígito hexadecimal (0–9 y A–F, donde A = 10 … F = 15) representa **4 bits**; por eso un octeto se escribe con **dos** dígitos hexadecimales: `1010 1000` → `A` `8` → `A8`.

### La misma MAC escrita de tres formas

| Sistema | Formato | Ejemplo |
|---|---|---|
| Linux, Wireshark | Pares separados por dos puntos | `00:1a:2b:3c:4d:5e` |
| Windows | Pares separados por guiones | `00-1A-2B-3C-4D-5E` |
| Cisco IOS y Packet Tracer | Grupos de cuatro separados por puntos | `001a.2b3c.4d5e` |

Las tres representan **la misma dirección**; mayúsculas y minúsculas no cambian el valor. Por eso en Packet Tracer verás MAC como `00E0.A357.B5AB` y en Windows como `00-E0-A3-57-B5-AB`.

La conversión se practicará a fondo en U04 (subnetting) y U05 (IPv6).

### Ideas clave

- Nombre, puerto, IP, MAC y gateway responden **preguntas distintas** y no son intercambiables.
- Una dirección IP se interpreta junto a su máscara o prefijo; la MAC solo tiene sentido en el **enlace local**.
- El **default gateway** es la salida hacia los destinos que el host no considera locales.
- IPv4: 32 bits escritos en decimal; MAC: 48 bits escritos en hexadecimal, con tres formatos según el sistema.

2. Convierte 172 a binario y a hexadecimal.

# 8. Estado de un host y primeras herramientas

Ante una incidencia, lo primero no es cambiar nada, sino **observar el estado** del equipo afectado y hacer pruebas sencillas. Todos los sistemas operativos incluyen herramientas para ello. En este apartado aprenderás a leer sus salidas y, sobre todo, **qué pregunta responde cada una y qué no demuestra**.

| Herramienta | Pregunta que responde |
|---|---|
| `ipconfig /all` (Windows) · `ip addr`, `ip route`, `resolvectl status` (Linux) | ¿Qué configuración de red tiene el equipo? |
| `ping` | ¿Hay comunicación IP con un destino concreto? |
| `nslookup` · `Resolve-DnsName` · `dig` | ¿Se traduce correctamente un nombre a una dirección? |
| `tracert` / `traceroute` | ¿Por qué routers pasa el tráfico hacia un destino? |
| `Test-NetConnection -Port` · `nc -zv` | ¿Responde un **servicio** concreto (un puerto) en el destino? |

Antes de las herramientas, conviene distinguir tres ideas que a menudo se confunden: **conectividad**, **rendimiento** y **disponibilidad**.

## 8.1. Conectividad, rendimiento y disponibilidad

| Concepto | Pregunta | Se expresa en |
|---|---|---|
| **Conectividad** (*connectivity*) | ¿Puede haber comunicación entre dos puntos? | Sí / no, para una prueba concreta |
| **Rendimiento** (*performance*) | ¿Cómo de bien funciona esa comunicación? | Mb/s, ms, % |
| **Disponibilidad** (*availability*) | ¿Durante cuánto tiempo está operativo y accesible el servicio? | % del tiempo |

### Rendimiento

| Medida | Qué es | Unidad habitual | Ejemplo |
|---|---|---|---|
| **Ancho de banda** (*bandwidth*) | Capacidad máxima del enlace o del contrato | Mb/s, Gb/s | Fibra de 600 Mb/s |
| **Throughput** | Datos que realmente se transfieren | Mb/s | Una descarga real a 480 Mb/s |
| **Latencia** (*latency*) | Tiempo que tarda la información en ir (y volver) | ms | `ping`: tiempo = 12 ms |
| **Variación del retardo** (*jitter*) | Cuánto cambia la latencia de un paquete a otro | ms | Clave en voz y vídeo |
| **Pérdida** (*packet loss*) | Porcentaje de paquetes que no llegan | % | `ping`: 25 % perdidos |

**Bits y bytes.** Las velocidades de red se expresan en **bits** por segundo (b/s); los navegadores y gestores de descargas suelen mostrar **bytes** por segundo (B/s). Un byte son 8 bits: una conexión de 100 Mb/s descarga, como máximo, unos 12,5 MB/s.

### Disponibilidad

Se expresa como porcentaje del tiempo en que el servicio funciona:

| Disponibilidad | Tiempo máximo de caída al año |
|---|---|
| 99 % | ≈ 3,65 días |
| 99,9 % | ≈ 8,8 horas |
| 99,99 % | ≈ 53 minutos |

Un servicio puede tener conectividad pero ofrecer un rendimiento inaceptable (una videollamada que se congela), o funcionar bien cuando lo pruebas pero tener baja disponibilidad (se cae cada tarde).

## 8.2. Leer la configuración antes de cambiarla

Antes de modificar nada conviene observar el estado. El objetivo no es memorizar la salida, sino **saber dónde buscar** cada dato.

**Windows** (`ipconfig /all`, salida resumida de un equipo en español):

```text
Adaptador de Ethernet Ethernet:

   Descripción . . . . . . . . . . . . . . : Intel(R) Ethernet Connection I219-V
   Dirección física. . . . . . . . . . . . : 3C-52-82-1A-7B-04
   DHCP habilitado . . . . . . . . . . . . : sí
   Vínculo: dirección IPv6 local. . . : fe80::8d4c:2e1a:93b0:5f12%12(Preferido)
   Dirección IPv4. . . . . . . . . . . . . : 192.168.10.25(Preferido)
   Máscara de subred . . . . . . . . . . . : 255.255.255.0
   Puerta de enlace predeterminada . . . . : 192.168.10.1
   Servidor DHCP . . . . . . . . . . . . . : 192.168.10.1
   Servidores DNS. . . . . . . . . . . . . : 192.168.30.53
```

| Línea | Qué te dice |
|---|---|
| Dirección física | La **MAC** de la interfaz (formato Windows, con guiones) |
| DHCP habilitado: sí | La configuración se ha obtenido automáticamente |
| Dirección IPv4 + Máscara de subred | La dirección del equipo y la información para saber qué es local (U04) |
| Puerta de enlace predeterminada | A qué router entrega el tráfico hacia otras redes |
| Servidores DNS | A quién pregunta para traducir nombres; puede estar en otra red, como aquí |
| Vínculo: dirección IPv6 local (`fe80::…`) | Una dirección IPv6 que el equipo crea por sí mismo (U05). **No** es «la IP» que buscas |

En PowerShell, `Get-NetIPConfiguration` muestra los mismos datos de forma más compacta. En Packet Tracer, el equivalente está en **Desktop → Command Prompt** (`ipconfig /all`) o en **Desktop → IP Configuration**.

**Linux** (salida resumida):

```text
$ ip -br addr
lo        UNKNOWN   127.0.0.1/8 ::1/128
enp0s3    UP        192.168.10.40/24 fe80::a00:27ff:fe4e:66a1/64

$ ip route
default via 192.168.10.1 dev enp0s3 proto dhcp metric 100
192.168.10.0/24 dev enp0s3 proto kernel scope link src 192.168.10.40

$ resolvectl status enp0s3
Link 2 (enp0s3)
Current DNS Server: 192.168.30.53
```

| Salida | Qué te dice |
|---|---|
| `enp0s3 UP 192.168.10.40/24` | Interfaz activa, su dirección y su prefijo (`/24` equivale a la máscara 255.255.255.0) |
| `default via 192.168.10.1` | El **default gateway** |
| `Current DNS Server` | El servidor DNS que se está usando |
| `lo 127.0.0.1` | La interfaz *loopback*: el propio equipo. No sirve para comunicarse con otros |

## 8.3. Una dirección que delata un problema: 169.254.x.x

Si un equipo Windows está configurado para obtener la dirección por DHCP y **nadie le responde**, se asigna a sí mismo una dirección del rango **169.254.0.0/16**. Es el mecanismo **APIPA** (*Automatic Private IP Addressing*).

```text
   Dirección IPv4 de configuración automática: 169.254.112.47(Preferido)
   Máscara de subred . . . . . . . . . . . . : 255.255.0.0
   Puerta de enlace predeterminada . . . . . :
```

| Puedes afirmar | No puedes afirmar todavía |
|---|---|
| El equipo pidió configuración automática y no la recibió | Que el servidor DHCP esté apagado |
| No tiene gateway: no podrá salir a otras redes | Que el cable esté bien (si no hay enlace tampoco llega la respuesta) |

Las siguientes preguntas serían: ¿hay enlace (luz, `Estado de los medios`)? ¿Otros equipos de la misma red reciben dirección? DHCP se observa en U02 y se configura en U04. En Linux no se suele asignar una 169.254 automáticamente: la interfaz simplemente queda sin dirección IPv4.

## 8.4. `ping`

`ping` envía mensajes ICMP de eco y espera la respuesta. Aporta evidencia de alcance IP **para esa prueba**.

**Respuesta correcta:**

```text
C:\> ping 192.168.10.1

Haciendo ping a 192.168.10.1 con 32 bytes de datos:
Respuesta desde 192.168.10.1: bytes=32 tiempo<1m TTL=255
Respuesta desde 192.168.10.1: bytes=32 tiempo<1m TTL=255
Respuesta desde 192.168.10.1: bytes=32 tiempo=1ms TTL=255
Respuesta desde 192.168.10.1: bytes=32 tiempo<1m TTL=255

Estadísticas de ping para 192.168.10.1:
    Paquetes: enviados = 4, recibidos = 4, perdidos = 0
    (0% perdidos),
```

`tiempo` es la latencia de ida y vuelta; el `TTL` lo estudiarás en U02.

**Tres fallos que no significan lo mismo:**

| Salida | Qué indica | Lo que todavía no sabes |
|---|---|---|
| `Tiempo de espera agotado para esta solicitud.` | Se envió la petición y no llegó respuesta a tiempo | Si el destino existe, si está apagado, si un firewall bloquea ICMP o si falla el camino de vuelta |
| `Respuesta desde 192.168.10.25: Host de destino inaccesible.` | El **propio equipo** (o un router intermedio, si la IP es otra) informa de que no sabe entregar el paquete | Por qué: en la red local, normalmente porque el destino no contesta en el enlace (U02) |
| `La solicitud de ping no pudo encontrar el host www.example.cm.` | Ni siquiera se envió el ping: el **nombre** no se pudo traducir | Si es un error de escritura o un problema de DNS |

**Trampa frecuente:** en el caso «Host de destino inaccesible», Windows cuenta las respuestas como **recibidas** y muestra `0% perdidos`. Lee siempre las líneas, no solo el resumen.

Y la regla general: un `ping` fallido **no demuestra por sí solo** la causa. Podría haber un problema de enlace, una dirección incorrecta, una ruta ausente, un filtrado, un host apagado o una política que bloquee ICMP.

```text
resultado de una prueba ≠ diagnóstico completo
```

## 8.5. Consulta DNS

Si una dirección IP funciona pero un nombre no, conviene comprobar la resolución directamente.

```text
C:\> nslookup www.example.com
Servidor:  UnKnown
Address:  192.168.30.53

Respuesta no autoritativa:
Nombre:  www.example.com
Address:  203.0.113.80
```

- Las dos primeras líneas dicen **qué servidor DNS respondió**: compruébalo siempre. `UnKnown` solo indica que el servidor no tiene un nombre registrado; no es un error.
- «Respuesta no autoritativa» es lo normal: el servidor DNS de la organización responde con información que ha obtenido de otro servidor.

| Resultado (texto aproximado) | Qué indica |
|---|---|
| Devuelve una dirección | La resolución funciona **desde este equipo y con este servidor** |
| `DNS request timed out` / tiempo de espera agotado | El servidor DNS configurado **no responde**: no llega la consulta, no hay servicio DNS en esa dirección o no vuelve la respuesta |
| `*** UnKnown no encuentra www.exmple.com: Non-existent domain` | El servidor **sí responde**, pero ese nombre no existe (a menudo, un error de escritura) |

En PowerShell, `Resolve-DnsName www.example.com` hace la misma consulta; en Linux, `dig www.example.com` o `resolvectl query www.example.com`. El texto exacto de las salidas cambia según el sistema y el idioma: aprende a reconocer la **idea**.

## 8.6. `traceroute` / `tracert`

Estas herramientas muestran los routers que **responden** a lo largo del camino hacia un destino.

```text
C:\> tracert www.example.com

Traza a la dirección www.example.com [203.0.113.80]
sobre un máximo de 30 saltos:

  1    <1 ms    <1 ms    <1 ms  192.168.10.1
  2     3 ms     2 ms     3 ms  198.51.100.1
  3     *        *        *     Tiempo de espera agotado para esta solicitud.
  4    12 ms    11 ms    12 ms  203.0.113.80

Traza completa.
```

- Cada línea es un **salto** (un router); las tres columnas son tres medidas de latencia.
- El salto 1 suele ser tu **default gateway**.
- `* * *` en un salto intermedio, con el destino respondiendo después, significa que ese router **no contesta a las sondas**, no que esté averiado.

Su salida no es una representación perfecta de Internet: algunos equipos no responden y el camino de vuelta puede ser distinto del de ida.

## 8.7. Probar un servicio, no solo un equipo

`ping` dice si un equipo responde a ICMP, no si ofrece el servicio que necesita el usuario. Para comprobar un **puerto** concreto:

```text
PS C:\> Test-NetConnection www.example.com -Port 443

ComputerName     : www.example.com
RemoteAddress    : 203.0.113.80
RemotePort       : 443
SourceAddress    : 192.168.10.25
TcpTestSucceeded : True
```

`TcpTestSucceeded : True` demuestra que el servicio escucha en el puerto 443 y que se puede abrir una conexión con él desde este equipo. En Linux, `nc -zv www.example.com 443` hace una comprobación equivalente.

Esta prueba es especialmente útil cuando ICMP está filtrado: un servidor web puede **no** responder a `ping` y, aun así, servir páginas sin problemas.

## 8.8. Qué demuestra cada prueba

| Prueba | Si sale bien, demuestra… | Si sale mal… |
|---|---|---|
| `ipconfig /all` / `ip addr` | Qué configuración tiene el equipo ahora | — (es una observación, no una prueba) |
| `ping` al gateway | Comunicación IP con el router local | No demuestra la causa |
| `ping` a una IP externa | Comunicación IP hasta ese destino y vuelta | No demuestra la causa |
| `nslookup nombre` | Que ese servidor DNS traduce ese nombre | Distingue «no responde» de «no existe» |
| `tracert` | Qué saltos responden en el camino | `*` no demuestra una avería |
| `Test-NetConnection -Port` | Que el servicio escucha en ese puerto | No demuestra si es un filtro o un servicio parado |

### Ideas clave

- Antes de cambiar nada, **observa**: IP, máscara, gateway, DNS y MAC.
- Conectividad, rendimiento y disponibilidad son cosas distintas; las velocidades van en **bits** por segundo (100 Mb/s ≈ 12,5 MB/s).
- Una dirección **169.254.x.x** indica que el equipo no recibió configuración automática.
- Cada prueba responde **una** pregunta; un fallo no demuestra la causa.
- Responder a `ping` no es ofrecer un servicio: para eso se prueba el **puerto**.

### Comprueba que lo has entendido

1. Un portátil muestra la dirección 169.254.30.7 y ninguna puerta de enlace; otro portátil de la misma aula funciona. ¿Qué sabes y qué comprobarías primero?
2. `ping` al servidor web responde, pero el navegador no carga la página. ¿Qué prueba harías y qué demostraría?
3. Una descarga va a 12 MB/s en una conexión de 100 Mb/s. ¿Es un mal rendimiento?
4. `ping 192.168.10.77` muestra cuatro veces «Host de destino inaccesible» y el resumen dice «0% perdidos». ¿Ha funcionado?

# 9. Primera observación con Wireshark

Las herramientas del apartado anterior muestran **resultados** (responde / no responde). Un **analizador de tráfico** (*packet analyzer*) como Wireshark va un paso más allá: permite ver los mensajes que realmente circulan por la red.

Wireshark es una herramienta libre y de uso profesional muy extendido. En U01 lo utilizamos únicamente para aprender una idea:

> una afirmación técnica mejora cuando puede relacionarse con una evidencia observable.

| En U01 | En U02 y siguientes |
|---|---|
| Abrir una captura, filtrar (`dns`, `icmp`), contar y leer la columna *Info* | Cabeceras, campos, puertos, filtros de captura y análisis de protocolos |

## 9.1. Capturar de forma responsable

Capturar tráfico puede revelar información sensible. Utiliza Wireshark únicamente:

- en equipos y redes autorizados;
- con fines formativos o profesionales legítimos;
- evitando recoger datos personales innecesarios;
- siguiendo las normas del centro y de la organización.

## 9.2. Qué observar inicialmente

En una captura sencilla puedes reconocer:

- tiempo;
- origen;
- destino;
- protocolo identificado;
- longitud;
- resumen del paquete.

Todavía no necesitas interpretar todos los campos.

La pregunta inicial es más sencilla:

> “¿Qué comunicación estoy observando y qué evidencia me aporta?”

## 9.3. El punto de captura importa

Una captura solo muestra el tráfico que puede observarse desde el punto donde se realiza.

Por eso una ausencia de paquetes no siempre significa que “el tráfico no existe”. También puede significar que estás observando desde un lugar que no lo ve.

Esta idea será esencial en U02.

### Ideas clave

- Wireshark muestra los **mensajes** que circulan, no solo un resultado.
- Solo se captura en redes y equipos **autorizados**.
- En U01 basta con abrir una captura, aplicar un filtro (`dns`, `icmp`), contar y leer la columna *Info*.
- No ver algo en una captura no demuestra que no exista: depende del **punto de captura**.

2. ¿Puedes capturar el tráfico de la Wi-Fi de una cafetería para practicar? ¿Por qué?

# 10. Diagnóstico basado en evidencias

Un buen técnico no es quien sabe más comandos, sino quien **razona** mejor con los datos que obtiene. Diagnosticar no significa ejecutar comandos al azar hasta que algo funcione: significa formular preguntas, probarlas y sacar conclusiones que la evidencia pueda sostener.

Un marco útil es:

```text
síntoma
→ pregunta
→ hipótesis
→ prueba
→ evidencia
→ conclusión
```

Cuando además se corrige una incidencia:

```text
conclusión
→ cambio mínimo
→ verificación
```

| Término | Significado | Ejemplo |
|---|---|---|
| **Síntoma** (*symptom*) | Lo que se observa o se comunica | «No abre ninguna web» |
| **Hecho** (*fact*) | Algo comprobado | `ping 8.8.8.8` responde |
| **Hipótesis** (*hypothesis*) | Una explicación posible | «El DNS configurado no responde» |
| **Prueba** (*test*) | Una acción que responde a una pregunta | `nslookup www.example.com` |
| **Evidencia** (*evidence*) | El resultado observable de la prueba | «DNS request timed out» |

No es una receta rígida. Es una forma de evitar cambios sin fundamento.

## 10.1. Síntoma

El síntoma describe qué observa el usuario o el técnico.

Malo:

> “Internet está roto.”

Mejor:

> “El equipo abre recursos locales, pero no puede resolver nombres externos.”

Cuanto más preciso es el síntoma, mejores preguntas podemos formular.

## 10.2. Hecho

Un **hecho** es algo observado o comprobado.

Ejemplos:

- la interfaz aparece activa;
- el host tiene una dirección IP;
- `ping` al gateway responde;
- `nslookup` devuelve un error.

## 10.3. Hipótesis

Una **hipótesis** es una explicación posible.

Ejemplo:

> “El servicio DNS configurado podría no responder.”

No debe presentarse como conclusión hasta obtener evidencia.

## 10.4. Prueba

Una prueba debe responder una pregunta concreta.

Ejemplo:

> “Si quiero saber si el problema está limitado a resolución de nombres, compararé una prueba por IP con una consulta DNS.”

## 10.5. Evidencia

La evidencia es el resultado observable de la prueba.

Debe permitir:

- apoyar una hipótesis;
- debilitarla;
- descartar una posibilidad;
- decidir qué comprobar después.

## 10.6. Caso guiado: por IP funciona, por nombre no

Síntoma:

> Un equipo puede alcanzar `203.0.113.80`, pero no puede abrir `www.example.com` en el navegador.

Hechos iniciales:

- hay conectividad IP hacia un destino externo;
- la comunicación por nombre falla.

Hipótesis razonable:

- puede existir un problema relacionado con la resolución de nombres.

Prueba siguiente:

```bash
nslookup www.example.com
```

La prueba es buena porque **distingue entre hipótesis**. Lo que hagas después depende del resultado:

| Resultado de `nslookup` | Qué indica | Siguiente paso razonable |
|---|---|---|
| Devuelve la dirección esperada | La resolución funciona: la hipótesis DNS se debilita | Probar el servicio (`Test-NetConnection www.example.com -Port 443`) y revisar el navegador |
| Tiempo de espera agotado | El DNS configurado no responde | `ping` a la dirección del DNS; revisar qué DNS tiene configurado y compararlo con un equipo que funcione |
| `Non-existent domain` | El DNS responde, pero no conoce ese nombre | Comprobar cómo está escrito el nombre |

Conclusión incorrecta, sea cual sea el resultado:

> «La red funciona perfectamente.»

La conectividad hacia una dirección concreta no demuestra que todos los servicios de la red funcionen.

Si finalmente cambias algo (por ejemplo, el servidor DNS configurado), cambia **solo eso** y verifica repitiendo **la misma prueba** que fallaba.

### Ideas clave

- El diagnóstico sigue un marco: **síntoma → pregunta → hipótesis → prueba → evidencia → conclusión**; si se corrige, **cambio mínimo → verificación**.
- Un **hecho** está comprobado; una **hipótesis** es una explicación posible que aún no lo está.
- Un síntoma preciso («abre recursos locales pero no resuelve nombres externos») produce mejores preguntas que uno vago («Internet está roto»).
- La conclusión no debe decir más de lo que la evidencia permite.

### Comprueba que lo has entendido

1. Clasifica como síntoma, hecho o hipótesis: «la web va lenta»; «`ping` al gateway: 0 % perdidos»; «puede que el switch esté saturado».
2. ¿Qué es un cambio mínimo y por qué se verifica con la misma prueba que fallaba?

# 11. Leer una situación completa

En la práctica, las incidencias no llegan ordenadas: llegan como una frase del usuario («no me funciona») y un conjunto de datos incompletos. Este apartado propone una forma de **ordenar la información** antes de actuar, integrando todo lo visto en la unidad.

Ante una incidencia sencilla, intenta separar estas preguntas:

| Pregunta | Qué obtienes |
|---|---|
| ¿Qué intenta hacer el usuario? | El servicio afectado |
| ¿Qué componentes participan? | La cadena de dependencias |
| ¿Qué información tengo? | Los hechos |
| ¿Qué información falta? | Lo que no debes suponer |
| ¿Qué prueba aporta más información? | El siguiente paso |

## 11.1. Qué intenta hacer el usuario

Ejemplo:

> acceder a una aplicación web por nombre.

## 11.2. Qué componentes participan

Por ejemplo:

```text
PC
→ interfaz
→ switch
→ router
→ DNS
→ servidor
```

## 11.3. Qué información tengo

- dirección IP;
- gateway;
- DNS;
- estado de interfaz;
- resultado de una prueba.

## 11.4. Qué información falta

No debemos rellenar los huecos con suposiciones.

Podemos necesitar saber:

- si alcanza el gateway;
- si el nombre se resuelve;
- si otros equipos tienen el mismo problema;
- si el servidor está disponible.

## 11.5. Qué prueba aporta más información

Una buena prueba no es simplemente la que “podemos ejecutar”. Es la que ayuda a distinguir entre hipótesis.

### Ideas clave

- Antes de actuar, ordena la información: qué intenta el usuario, qué componentes participan, qué sabes, qué falta y qué prueba aporta más.
- La mejor prueba no es la que puedes ejecutar, sino la que **distingue entre hipótesis**.

### Comprueba que lo has entendido

1. Una usuaria no puede imprimir, pero sus compañeros de la misma oficina sí. ¿Qué información te falta antes de actuar y qué te indica que los compañeros puedan imprimir?

# 12. Uso responsable de asistentes de IA

Los asistentes de inteligencia artificial se han convertido en una herramienta habitual para consultar dudas técnicas. Pueden ahorrar tiempo, pero **no ven tu red**: responden a partir de lo que les cuentas y de patrones generales, y pueden equivocarse con mucha seguridad.

Una respuesta generada por IA puede contener:

- una explicación correcta;
- una simplificación excesiva;
- una suposición no justificada;
- un comando innecesario;
- una conclusión que no se deriva de la evidencia.

Por tanto, utiliza la IA como apoyo, no como sustituto del razonamiento.

Un buen procedimiento es:

1. identificar qué afirma;
2. separar hechos de hipótesis;
3. comprobar qué evidencia utiliza;
4. verificar los comandos o conceptos;
5. contrastar con documentación y resultados reales;
6. corregir la respuesta si es necesario.

Nunca cambies una configuración crítica solo porque una IA lo sugiera.

### Ideas clave

- Un asistente de IA **no ve tu red**: responde con patrones generales y puede equivocarse con mucha seguridad.
- Contrasta cada afirmación con evidencias y documentación antes de aplicarla.
- Nunca cambies una configuración crítica solo porque lo sugiera una IA.

### Comprueba que lo has entendido

1. Ante «por IP funciona, por nombre no», una IA responde: «Tu servidor DNS está caído; reinstala el controlador de la tarjeta de red y reinicia el router». Señala dos problemas de esa respuesta.

3. El gateway, el proveedor e Internet: el servidor y el DNS están en la red del centro.

2. Porque desde el punto de vista de la red es origen o destino de la información; dar servicio a otros es un **rol**, no lo convierte en intermediario.
