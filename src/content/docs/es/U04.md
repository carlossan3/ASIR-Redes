> **Pregunta guía:** ¿Cómo diseñamos y verificamos un plan IPv4 que permita a los equipos decidir correctamente qué destinos son locales, cuáles requieren un gateway y cómo deben configurarse sus parámetros de red?

En U03 estudiamos la infraestructura que permite que exista un enlace. Ahora añadimos la **organización lógica IPv4**.

El objetivo de esta unidad no es memorizar trucos para calcular subredes. Debes aprender un procedimiento que puedas **explicar, comprobar, documentar y utilizar para diagnosticar errores**.

La progresión será:

```text
leer una configuración
→ interpretar dirección y prefijo
→ calcular límites
→ decidir pertenencia
→ decidir local/remoto
→ dividir el espacio
→ elegir tamaños
→ diseñar con VLSM
→ resumir cuando proceda con CIDR
→ documentar
→ configurar
→ verificar
→ diagnosticar
```

# 1. Leer una configuración IPv4

Antes de calcular una red debemos saber qué información tenemos delante.

Ejemplo:

```text
IPv4:    192.168.10.25
Prefijo: /24
Gateway: 192.168.10.1
DNS:     192.168.10.53
```

Estos cuatro datos responden a preguntas distintas.

## 1.1. Dirección IPv4

Una dirección IPv4 identifica lógicamente una interfaz dentro del espacio de direccionamiento IPv4.

IPv4 utiliza **32 bits**, representados habitualmente mediante cuatro octetos decimales:

```text
192.168.10.25
```

Una dirección no debe interpretarse aislada. Para saber a qué red pertenece necesitamos también su prefijo:

```text
192.168.10.25/24
```

## 1.2. Prefijo y máscara

El **prefijo** indica cuántos bits pertenecen a la parte de red.

```text
/24
→ 24 bits describen el prefijo de red
→ quedan 8 bits para posiciones dentro del bloque
```

La misma información puede representarse mediante una **subnet mask**:

```text
/24
=
255.255.255.0
```

No debes deducir la máscara observando únicamente el primer octeto de la dirección.

## 1.3. Default gateway

El **default gateway** es el siguiente salto que un host utiliza para enviar tráfico destinado a redes que no considera locales.

```text
gateway
≠
Internet
```

El gateway es normalmente una interfaz de router directamente alcanzable desde la red local del host.

## 1.4. DNS

El servidor DNS permite resolver nombres como:

```text
www.example.com
```

en direcciones IP.

No confundas:

```text
DNS
≠
gateway
```

El DNS resuelve nombres. El gateway participa en el envío hacia otras redes.

## 1.5. Herramientas de consulta

### Windows

```text
ipconfig /all
Get-NetIPConfiguration
route print
arp -a
```

### Linux

```text
ip address
ip route
ip neigh
```

La finalidad no es memorizar cada opción, sino saber **qué evidencia puede aportar cada herramienta**.

## 1.6. Leer no significa validar

Considera:

```text
IPv4:    192.168.20.37
Prefijo: /27
Gateway: 192.168.20.1
DNS:     192.168.50.53
```

Podemos leer esos valores, pero todavía no sabemos si todos son coherentes.

Necesitaremos responder preguntas como:

- ¿qué red contiene `192.168.20.37/27`?;
- ¿pertenece el gateway a esa red?;
- ¿puede el DNS estar en otra red?;
- si está en otra red, ¿existe una ruta para alcanzarlo?

> **Idea clave:** una salida de configuración contiene hechos observables. La conclusión sobre si está bien configurada exige interpretar esos hechos.

# 2. Binario útil, máscara y prefijo

IPv4 utiliza 32 bits. Cada octeto utiliza 8.

## 2.1. Pesos binarios

Los pesos de un octeto son:

```text
128 64 32 16 8 4 2 1
```

Ejemplo:

```text
192 = 128 + 64
    = 11000000
```

```text
25 = 16 + 8 + 1
   = 00011001
```

El binario es una **herramienta para comprender** cómo funciona la máscara. No es necesario convertir continuamente los 32 bits completos.

## 2.2. Máscaras frecuentes

| Prefijo | Máscara | Bits de host |
|---:|---|---:|
| /24 | 255.255.255.0 | 8 |
| /25 | 255.255.255.128 | 7 |
| /26 | 255.255.255.192 | 6 |
| /27 | 255.255.255.224 | 5 |
| /28 | 255.255.255.240 | 4 |
| /29 | 255.255.255.248 | 3 |
| /30 | 255.255.255.252 | 2 |

`/31` y `/32` existen y tienen usos reales, pero no son el centro de los primeros cálculos de esta unidad.

## 2.3. El prefijo no tiene por qué coincidir con los puntos

Ejemplo:

```text
192.168.10.25/26
```

`/26` significa:

```text
24 bits completos de los tres primeros octetos
+
2 bits del cuarto octeto
```

La frontera red/host puede encontrarse dentro de un octeto.

## 2.4. AND lógico

La dirección de red puede obtenerse mediante:

```text
IP
AND
máscara
=
dirección de red
```

Ejemplo simplificado en el cuarto octeto:

```text
IP:       70 = 01000110
Máscara: 192 = 11000000
AND:      64 = 01000000
```

Por tanto, para `192.168.10.70/26`:

```text
red = 192.168.10.64
```

Comprender el AND explica el fundamento. Para trabajar con rapidez utilizaremos también el **método de bloques**.

## 2.5. No utilizar clases históricas como procedimiento

No es correcto razonar:

```text
192.x.x.x
→ siempre /24
```

En redes actuales utilizamos:

```text
dirección + prefijo explícito
```

Ejemplo:

```text
192.168.10.25/26
```

es una red `/26`, aunque la dirección comience por `192`.

# 3. Dirección de red, broadcast, rango y capacidad

Una subred IPv4 convencional tiene límites que debemos identificar.

## 3.1. Dirección de red

La **network address** representa el bloque.

Ejemplo:

```text
192.168.10.64/26
```

La dirección `192.168.10.64` identifica esa red.

## 3.2. Broadcast

En una subred IPv4 convencional, la última dirección del bloque es el **broadcast address**.

Para:

```text
192.168.10.64/26
```

el broadcast es:

```text
192.168.10.127
```

## 3.3. Rango de hosts

En los casos convencionales trabajados inicialmente:

```text
primer host = red + 1
último host = broadcast - 1
```

Ejemplo:

```text
Red:       192.168.10.64/26
1.er host: 192.168.10.65
Último:    192.168.10.126
Broadcast: 192.168.10.127
```

## 3.4. Capacidad

Si quedan `h` bits para host:

```text
direcciones totales = 2^h
```

En las subredes convencionales de esta unidad:

```text
hosts utilizables = 2^h - 2
```

Ejemplo `/26`:

```text
h = 6
2^6 = 64 direcciones
64 - 2 = 62 hosts utilizables
```

## 3.5. Ejemplo completo

Calcular `172.16.5.140/27`.

Máscara:

```text
/27 = 255.255.255.224
```

Tamaño de bloque:

```text
256 - 224 = 32
```

Límites del cuarto octeto:

```text
0, 32, 64, 96, 128, 160, 192, 224
```

`140` se encuentra entre `128` y `159`.

Resultado:

```text
Red:        172.16.5.128/27
Broadcast:  172.16.5.159
Primer host:172.16.5.129
Último host:172.16.5.158
Capacidad:  30 hosts
```

> **Idea clave:** calcular una subred no consiste únicamente en encontrar la máscara. Debemos identificar sus límites y su capacidad.

# 4. Método de bloques y pertenencia

El método de bloques permite localizar rápidamente una dirección dentro de su subred.

## 4.1. Tamaño de bloque

Para `/26`:

```text
máscara del octeto variable = 192
bloque = 256 - 192 = 64
```

Los límites son:

```text
0
64
128
192
```

## 4.2. Localizar una dirección

Para:

```text
192.168.10.70/26
```

`70` cae en el intervalo:

```text
64–127
```

Por tanto:

```text
Red:       192.168.10.64/26
Broadcast: 192.168.10.127
Hosts:     192.168.10.65–126
```

## 4.3. Procedimiento estable

```text
prefijo
→ máscara
→ octeto variable
→ tamaño de bloque
→ intervalo
→ red
→ broadcast
→ rango
```

## 4.4. Pertenencia

Considera:

```text
192.168.10.20/26
192.168.10.50/26
```

Ambas pertenecen a:

```text
192.168.10.0/26
```

En cambio:

```text
192.168.10.70/26
```

pertenece a:

```text
192.168.10.64/26
```

Dos direcciones pueden parecer próximas y pertenecer a redes distintas.

## 4.5. Error frecuente: «los tres primeros octetos coinciden»

```text
192.168.10.20/26
192.168.10.70/26
```

comparten `192.168.10`, pero **no** pertenecen a la misma subred.

La pertenencia depende de:

```text
IP + prefijo
```

no de la apariencia decimal.

# 5. Destino local, destino remoto y default gateway

El subnetting no es únicamente cálculo. Permite a un host responder una pregunta esencial:

```text
¿el destino pertenece a mi red?
```

## 5.1. Destino local

Si el destino pertenece a la misma subred:

```text
host origen
→ enlace local
→ host destino
```

No necesita enviar el paquete al default gateway para alcanzar ese destino.

## 5.2. Destino remoto

Si el destino pertenece a otra red:

```text
host origen
→ default gateway
→ otras redes
```

El host mantiene como **IP destino** la dirección del destino final, pero en la primera trama Ethernet puede utilizar como **MAC destino** la del gateway.

Esto recupera conceptos de U02:

```text
IP destino
→ destino final

MAC destino de la primera trama
→ siguiente salto local
```

## 5.3. El gateway debe ser localmente alcanzable

Ejemplo coherente:

```text
Host:    192.168.50.20/26
Gateway: 192.168.50.1
```

Ambos pertenecen a:

```text
192.168.50.0/26
```

Ejemplo incoherente:

```text
Host:    192.168.50.20/26
Gateway: 192.168.50.129
```

El supuesto gateway pertenece a otro bloque `/26`.

## 5.4. Tabla de rutas del host

A nivel inicial interesa reconocer:

- red local;
- ruta por defecto;
- interfaz;
- gateway.

Windows:

```text
route print
```

Linux:

```text
ip route
```

Ejemplo simplificado:

```text
192.168.50.0/26 dev eth0
 default via 192.168.50.1
```

Significa que la red local se alcanza directamente y que otros destinos pueden enviarse al gateway.

## 5.5. ARP como evidencia local

Para enviar una trama al gateway en IPv4, el host puede necesitar conocer su MAC.

```text
arp -a
ip neigh
```

Una entrada ARP para el gateway es evidencia de descubrimiento/comunicación local reciente, pero **no demuestra por sí sola** que exista conectividad con Internet o con cualquier destino remoto.

## 5.6. Ejemplo de decisión

```text
Host: 10.20.30.70/27
GW:   10.20.30.65
Dest: 10.20.30.94
```

Para `/27`, el bloque es `32`.

`70` pertenece a:

```text
10.20.30.64–95
```

Por tanto:

```text
Red:       10.20.30.64/27
Broadcast: 10.20.30.95
```

El gateway `10.20.30.65` es local.

El destino `10.20.30.94` también es local.

Conclusión:

```text
el host no necesita entregar este paquete al default gateway
```

# 6. Subnetting con FLSM

**Subnetting** consiste en dividir un bloque en otros bloques más pequeños.

## 6.1. ¿Por qué dividir una red?

Puede ser útil para:

- separar departamentos;
- reducir dominios de broadcast;
- aplicar políticas;
- organizar direccionamiento;
- facilitar troubleshooting;
- reservar capacidad para crecimiento;
- preparar VLAN y routing.

## 6.2. FLSM

En **Fixed Length Subnet Masking (FLSM)** todas las subredes utilizan el mismo prefijo.

Ejemplo:

```text
Bloque inicial: 192.168.10.0/24
Necesidad:       4 subredes iguales
```

Necesitamos 2 bits para identificar 4 subredes:

```text
2^2 = 4
```

El prefijo pasa de `/24` a `/26`.

Resultado:

```text
192.168.10.0/26
192.168.10.64/26
192.168.10.128/26
192.168.10.192/26
```

Cada subred tiene:

```text
64 direcciones
62 hosts utilizables en el caso convencional
```

## 6.3. Procedimiento FLSM

```text
1. identificar el bloque padre
2. determinar cuántas subredes necesitamos
3. calcular cuántos bits hay que tomar
4. obtener el nuevo prefijo
5. calcular el tamaño de bloque
6. enumerar redes
7. comprobar que todas quedan dentro del bloque padre
```

## 6.4. Número de subredes

Si tomamos `s` bits:

```text
subredes = 2^s
```

No aplicaremos reglas históricas que restaban dos subredes.

## 6.5. Comprobación inversa

Cuando dividimos por completo un bloque de forma uniforme:

```text
número de subredes
×
tamaño de cada subred
=
tamaño del bloque padre
```

Ejemplo:

```text
4 × 64 = 256
```

que coincide con el tamaño de un `/24`.

# 7. Elegir un prefijo a partir del número de hosts

En un diseño real no siempre nos dicen «usa `/27`». Es habitual recibir un requisito:

> necesitamos una red para 25 equipos.

Debemos convertir una **necesidad** en un **prefijo**.

## 7.1. Procedimiento

Buscamos el menor número de bits de host que proporcione capacidad suficiente.

Ejemplo: 25 hosts.

Probamos:

```text
2^4 - 2 = 14
→ insuficiente

2^5 - 2 = 30
→ suficiente
```

Necesitamos 5 bits para host.

```text
32 - 5 = /27
```

Por tanto:

```text
25 hosts
→ /27
```

## 7.2. Tabla práctica

| Prefijo | Direcciones | Hosts convencionales |
|---:|---:|---:|
| /24 | 256 | 254 |
| /25 | 128 | 126 |
| /26 | 64 | 62 |
| /27 | 32 | 30 |
| /28 | 16 | 14 |
| /29 | 8 | 6 |
| /30 | 4 | 2 |

## 7.3. No elegir siempre la red más grande

Si necesitamos 20 hosts, un `/24` funcionaría, pero desperdicia mucho espacio.

El objetivo habitual es:

```text
capacidad suficiente
+
margen razonable
+
uso coherente del espacio
```

## 7.4. Crecimiento

El prefijo mínimo matemático no siempre es la mejor decisión profesional.

Si una red tiene 28 dispositivos y está creciendo:

```text
/27 → 30 hosts utilizables
```

puede dejar un margen demasiado pequeño.

El diseño debe considerar requisitos previsibles, no solo la fotografía actual.

# 8. VLSM: subredes de distinto tamaño

FLSM es sencillo, pero no siempre aprovecha bien el espacio.

Supongamos estas necesidades:

```text
USERS   100 hosts
SERVERS 30 hosts
VOICE   20 hosts
MGMT    10 hosts
```

Asignar el mismo tamaño a todas las redes puede desperdiciar muchas direcciones.

**Variable Length Subnet Masking (VLSM)** permite utilizar prefijos distintos dentro de un mismo plan.

## 8.1. Procedimiento estable

```text
1. ordenar necesidades de mayor a menor
2. calcular el prefijo mínimo adecuado para cada necesidad
3. asignar primero el bloque mayor
4. continuar desde el siguiente límite válido
5. comprobar que ningún bloque se solapa
6. comprobar que todo queda dentro del bloque padre
7. documentar
```

## 8.2. Ejemplo

Bloque disponible:

```text
192.168.100.0/24
```

Necesidades:

```text
A: 100 hosts
B: 50 hosts
C: 20 hosts
D: 10 hosts
```

Prefijos:

```text
100 hosts → /25 → 126 hosts
50 hosts  → /26 → 62 hosts
20 hosts  → /27 → 30 hosts
10 hosts  → /28 → 14 hosts
```

Asignación:

```text
A → 192.168.100.0/25
B → 192.168.100.128/26
C → 192.168.100.192/27
D → 192.168.100.224/28
```

Espacio restante:

```text
192.168.100.240/28
```

## 8.3. Tabla de documentación

| Red | Necesidad | Prefijo | Network address | Host range | Broadcast |
|---|---:|---:|---|---|---|
| A | 100 | /25 | 192.168.100.0 | .1–.126 | .127 |
| B | 50 | /26 | 192.168.100.128 | .129–.190 | .191 |
| C | 20 | /27 | 192.168.100.192 | .193–.222 | .223 |
| D | 10 | /28 | 192.168.100.224 | .225–.238 | .239 |

## 8.4. Límites válidos

No podemos colocar una red de cualquier tamaño en cualquier dirección.

Una `/26` utiliza bloques de 64:

```text
0, 64, 128, 192
```

Por tanto:

```text
192.168.100.96/26
```

no representa un límite válido de `/26`.

## 8.5. Por qué se empieza por la red mayor

Si asignamos primero bloques pequeños de forma desordenada podemos fragmentar el espacio e impedir después colocar una red grande contigua.

Ordenar de mayor a menor reduce ese riesgo.

## 8.6. Comprobar solapamientos

Dos subredes se solapan si comparten alguna dirección.

Cada asignación debe verificarse mediante sus límites:

```text
inicio del bloque
→ final del bloque
→ siguiente bloque comienza después
```

## 8.7. Diseño y crecimiento

VLSM no significa utilizar siempre el prefijo mínimo sin margen.

El diseño debe equilibrar:

- requisitos actuales;
- crecimiento;
- simplicidad;
- documentación;
- disponibilidad del bloque padre.

# 9. CIDR y agregación sencilla

**Classless Inter-Domain Routing (CIDR)** utiliza prefijos explícitos y permite representar bloques sin depender de clases históricas.

## 9.1. Una dirección sin prefijo está incompleta para muchos cálculos

```text
10.20.30.40
```

no indica por sí sola si pertenece a un `/8`, `/16`, `/24`, `/27` u otro bloque.

Necesitamos:

```text
10.20.30.40/27
```

para interpretar la frontera.

## 9.2. Agregación

La **agregación** o **summary** representa varios bloques mediante un prefijo común cuando sus límites lo permiten.

Ejemplo:

```text
192.168.0.0/24
192.168.1.0/24
```

pueden resumirse como:

```text
192.168.0.0/23
```

porque `/23` cubre:

```text
192.168.0.0
hasta
192.168.1.255
```

## 9.3. No basta con que las redes sean consecutivas

Un resumen debe:

- comenzar en un límite válido;
- cubrir exactamente el intervalo deseado o entender qué bloques adicionales incluye;
- tener bits comunes suficientes.

Por ejemplo:

```text
192.168.1.0/24
192.168.2.0/24
```

no se resumen limpiamente como un único `/23` que contenga solo esas dos redes, porque los límites `/23` comienzan en pares adecuados de tercer octeto (`0`, `2`, `4`, ...).

## 9.4. Utilidad posterior

En U09 reutilizaremos agregación y prefijos cuando estudiemos routing dinámico. En U04 interesa comprender la lógica de los bloques y ser capaz de verificar un resumen sencillo.

# 10. Plan de direccionamiento e IPAM básico

Un cálculo correcto puede producir un diseño difícil de operar si no existe documentación.

## 10.1. Qué debe tener un buen plan

Debe ser:

- coherente;
- legible;
- documentado;
- verificable;
- ampliable;
- mantenible.

## 10.2. Ejemplo de requisitos

```text
USERS    → 100 hosts
SERVERS  → 30 hosts
VOICE    → 20 hosts
MGMT     → 10 hosts
```

El trabajo no termina al seleccionar los prefijos. También hay que decidir:

- redes;
- gateways;
- rangos dinámicos;
- direcciones reservadas;
- espacio libre;
- convenciones de nombres/documentación.

## 10.3. IPAM

**IP Address Management (IPAM)** es la gestión organizada del espacio de direcciones.

En esta unidad puede bastar una tabla bien mantenida:

| Nombre | Red/prefijo | Gateway | Rango de hosts | Broadcast | Asignación | Observaciones |
|---|---|---|---|---|---|---|

No es necesario utilizar una plataforma empresarial para aplicar los principios de IPAM.

## 10.4. Convención de gateway

Una organización puede decidir, por ejemplo:

```text
gateway = primer host
```

u otra convención coherente.

No existe una única regla universal. Lo importante es:

```text
criterio conocido
+
aplicación consistente
+
documentación
```

## 10.5. Direcciones estáticas y dinámicas

Un criterio posible:

```text
infraestructura → estática
servidores       → estática o reserva
clientes         → DHCP
```

La decisión depende de necesidades operativas.

## 10.6. Validación cruzada

Antes de aplicar un plan, comprobar:

- no existen solapamientos;
- cada gateway pertenece a su subred;
- los pools no invaden direcciones excluidas o estáticas;
- todas las redes tienen capacidad suficiente;
- el espacio libre queda identificado;
- las convenciones son consistentes.

# 11. Configuración IPv4 estática y verificación

Una vez diseñado el plan debemos aplicarlo y demostrar que funciona.

## 11.1. Parámetros habituales

Un host suele necesitar:

```text
IPv4 address
subnet mask / prefix
 default gateway
DNS server
```

## 11.2. Verificación progresiva

Un orden útil es:

```text
1. interfaz
2. dirección y prefijo
3. red calculada
4. vecino/local
5. gateway
6. destino remoto por IP
7. DNS
8. servicio
```

No significa que siempre debamos ejecutar ocho pruebas. Significa que debemos escoger la siguiente prueba que reduzca mejor la incertidumbre.

## 11.3. Configurar no equivale a verificar

Introducir valores en una interfaz solo demuestra que hemos cambiado la configuración.

Para demostrar conectividad debemos obtener evidencia.

Ejemplos:

```text
ipconfig /all
ip address
ip route
ping
arp -a
ip neigh
nslookup
```

Cada prueba responde a una pregunta diferente.

## 11.4. Cambiar una sola variable

Ante un fallo, evita cambiar simultáneamente:

- IP;
- máscara;
- gateway;
- DNS.

Si cambiamos todo a la vez y después funciona, sabemos que algo estaba mal, pero no hemos demostrado qué.

## 11.5. Caso

```text
PC1
IP: 192.168.40.34/27
GW: 192.168.40.33

PC2
IP: 192.168.40.62/27
GW: 192.168.40.33
```

Para `/27`, los bloques son de 32.

Ambas direcciones están dentro de:

```text
192.168.40.32–63
```

Por tanto:

```text
Red:       192.168.40.32/27
Hosts:     192.168.40.33–62
Broadcast: 192.168.40.63
```

El gateway `192.168.40.33` es válido y local.

Un ping correcto entre PC1 y PC2 demuestra conectividad IP entre esos hosts en ese momento, pero no demuestra por sí solo:

- que DNS funcione;
- que exista routing a Internet;
- que cualquier aplicación responda.

# 12. DHCP: asignación dinámica de parámetros IPv4

Cuando ya entendemos qué parámetros necesita un host, podemos automatizar su entrega.

**Dynamic Host Configuration Protocol (DHCP)** permite proporcionar configuración de red a clientes.

## 12.1. Parámetros que puede entregar

Entre otros:

- dirección IPv4;
- máscara/prefijo;
- default gateway;
- servidor DNS;
- tiempo de concesión.

DHCP automatiza la entrega. No cambia el significado de esos parámetros.

> **Dónde se configura en este módulo.** En esta unidad el servidor DHCP es un equipo servidor (el servicio *DHCP* de un servidor en Packet Tracer, o un servidor Windows/Linux). Configurar un **router Cisco** como servidor DHCP (`ip dhcp pool`) y como relay (`ip helper-address`) se trabaja en U08, cuando ya se administran routers.

## 12.2. DORA

El intercambio inicial simplificado se representa como:

```text
Discover
→ Offer
→ Request
→ Acknowledgment
```

En U02 observamos este intercambio como tráfico. Aquí lo relacionamos con el **plan de direccionamiento**.

## 12.3. DHCP pool

Un **pool** es el conjunto de direcciones que el servidor puede entregar dinámicamente para una red determinada.

Debe ser coherente con:

- red;
- prefijo;
- gateway;
- exclusiones;
- otras opciones.

## 12.4. Exclusiones

Una dirección excluida no debe asignarse dinámicamente.

Ejemplos habituales:

- gateway;
- interfaces de infraestructura;
- determinados servidores;
- impresoras con configuración fija.

## 12.5. Reserva

Una **reservation** permite que un cliente concreto reciba una dirección prevista mediante el mecanismo del servidor DHCP.

No es lo mismo que configurar manualmente esa dirección en el cliente.

## 12.6. Lease

La asignación dinámica es una **concesión temporal**.

Conviene poder interpretar:

- dirección obtenida;
- máscara/prefijo;
- gateway;
- DNS;
- servidor DHCP;
- duración de la concesión.

## 12.7. Verificación en el cliente

No basta con afirmar:

> «Ha obtenido una IP, luego DHCP funciona correctamente».

Debemos comprobar que los parámetros recibidos son los esperados.

Ejemplo:

```text
IP correcta
máscara correcta
gateway incorrecto
```

El cliente ha recibido una concesión, pero la configuración no es funcional para destinos remotos.

## 12.8. Cuatro fallos típicos

### Sin dirección válida

Posibles ámbitos de investigación:

- servicio DHCP no disponible;
- cliente sin acceso al servicio;
- pool agotado;
- configuración incorrecta;
- problema de enlace o acceso.

No debemos elegir una causa sin evidencia.

### Dirección correcta, gateway incorrecto

Síntoma posible:

```text
comunicación local → sí
comunicación remota → no
```

### DNS incorrecto

Posible patrón:

```text
IP correcta
gateway correcto
ping a destino remoto por IP funciona
resolución de nombres falla
```

### Pool invade una dirección estática

Puede producir conflictos o asignaciones incoherentes.

## 12.9. DHCP relay

Cuando cliente y servidor DHCP se encuentran en redes distintas puede ser necesario un mecanismo de **relay**.

En U04 basta con reconocer la necesidad. Su funcionamiento se entiende mejor cuando ya se domina routing entre redes, por lo que se retomará más adelante.

# 13. Diagnóstico IPv4 basado en evidencias

Un mensaje como:

> «No tengo red»

es un **síntoma**, no una causa.

Un marco útil es:

```text
síntoma
→ pregunta
→ hipótesis
→ prueba
→ evidencia
→ conclusión
```

Si existe una corrección:

```text
→ cambio mínimo
→ verificación
```

## 13.1. Cadena de dependencias

Ante un problema IPv4 podemos considerar:

```text
interfaz
→ IP
→ prefijo
→ red
→ pertenencia
→ gateway
→ ruta
→ ARP/neighbor
→ destino remoto por IP
→ DNS
→ servicio
```

No debemos ejecutar mecánicamente todos los comandos. La pregunta es:

> **¿qué prueba aporta ahora la información que necesito para distinguir mis hipótesis?**

## 13.2. Hecho, hipótesis y conclusión

Ejemplo:

```text
Hecho:
ipconfig muestra 192.168.50.70/27
```

```text
Hipótesis:
el gateway podría estar fuera de la subred
```

```text
Prueba:
calcular la red del host y comparar el gateway
```

```text
Evidencia:
la red es 192.168.50.64/27 y el gateway configurado es 192.168.50.1
```

```text
Conclusión:
el gateway configurado no pertenece a la subred local del host
```

La conclusión está vinculada a una evidencia observable.

## 13.3. No modificar antes de comprender

Cambiar parámetros sin saber qué se intenta demostrar puede ocultar el problema original.

Un procedimiento profesional busca:

```text
una hipótesis concreta
→ una prueba adecuada
→ una corrección mínima
→ una verificación posterior
```

# 14. Procedimientos de referencia

## 14.1. Calcular una subred a partir de IP/prefijo

```text
IP/prefijo
→ máscara
→ octeto variable
→ tamaño de bloque
→ localizar intervalo
→ network address
→ broadcast
→ host range
→ capacidad
```

## 14.2. Elegir prefijo a partir de hosts

```text
hosts necesarios
→ buscar 2^h - 2 suficiente
→ calcular h
→ prefijo = 32 - h
→ comprobar margen
```

## 14.3. Diseñar con VLSM

```text
requisitos
→ ordenar de mayor a menor
→ prefijo para cada requisito
→ asignar sobre límites válidos
→ comprobar solapamiento
→ comprobar espacio restante
→ documentar
```

## 14.4. Verificar una configuración

```text
leer configuración
→ calcular red
→ comprobar gateway
→ decidir local/remoto
→ seleccionar prueba
→ interpretar evidencia
→ corregir si procede
→ volver a verificar
```

# 16. Errores frecuentes que debes evitar

## Deducir la máscara por la antigua clase

Incorrecto:

```text
192.x.x.x → /24
```

Correcto:

```text
usar el prefijo explícito
```

## Confundir direcciones próximas con misma subred

```text
192.168.1.30
192.168.1.70
```

pueden pertenecer o no a la misma red dependiendo del prefijo.

## Elegir un gateway fuera de la red local

El host debe poder alcanzar directamente el gateway configurado.

## Memorizar resultados sin comprobar límites

Un prefijo implica un tamaño de bloque y unos límites válidos.

## Empezar VLSM por las redes pequeñas

Puede fragmentar el espacio e impedir ubicar redes grandes.

## Confundir reserva DHCP con IP estática manual

Ambas pueden producir una dirección estable, pero se gestionan de forma distinta.

## Dar por bueno DHCP porque existe una dirección

También deben comprobarse máscara, gateway, DNS y coherencia del plan.

## Cambiar varios parámetros a la vez

Dificulta demostrar cuál era la causa.

U04 proporciona herramientas que volverán a utilizarse durante todo el curso.

IPv6 reutiliza ideas como:

- prefijo;

- local/remoto;
- gateway/next hop;

Pero introduce mecanismos propios, por lo que no debe tratarse como «IPv4 con más bits».

Cada VLAN que deba operar como red IP necesitará un plan de direccionamiento coherente.

## U08 — Routing estático y ACL

El router necesita conocer redes y prefijos. El alumnado necesitará decidir qué destinos son locales, remotos y por qué ruta deben enviarse.

## U09 — Routing dinámico

VLSM y CIDR reaparecerán cuando los routers intercambien información de redes y prefijos.

## U10 — NAT

NAT y acceso a Internet dependen de que el direccionamiento interno y el routing previo sean correctos.

# 18. Síntesis final

Al terminar esta unidad debes conservar estas ideas:

1. Una IPv4 se interpreta junto con su **prefijo**.
2. El prefijo define qué bits describen la red y qué espacio queda dentro del bloque.
3. Una subred tiene **network address, broadcast, rango y capacidad**.
4. La pertenencia se calcula; no se decide por la apariencia decimal.
5. Un host utiliza el **default gateway** cuando el destino no es local.
6. FLSM divide un bloque en subredes iguales; VLSM permite tamaños distintos.
7. Elegir un prefijo es una decisión de **capacidad y diseño**, no solo una operación matemática.
8. CIDR permite trabajar con prefijos explícitos y realizar agregaciones cuando los límites son correctos.
9. Un plan profesional debe quedar **documentado** mediante IPAM u otra representación mantenible.
10. DHCP automatiza parámetros que primero debemos comprender.
11. Configurar no equivale a verificar.
12. El diagnóstico debe relacionar **hipótesis con pruebas y conclusiones con evidencias**.

El objetivo profesional no es responder rápidamente «qué máscara tiene esta IP», sino poder defender afirmaciones como:

> «Este host pertenece a esta subred, este gateway es localmente alcanzable, este bloque satisface la necesidad prevista y estas pruebas demuestran dónde se encuentra el fallo.»
