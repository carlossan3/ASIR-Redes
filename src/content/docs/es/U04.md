>
> **Versión:** V7.1 (sept. 2026): introducción de contexto y tabla-resumen por apartado.

En U03 estudiamos la infraestructura que permite que exista un enlace. Ahora añadimos la **organización lógica IPv4**.

El objetivo de esta unidad no es memorizar trucos para calcular subredes. Debes aprender un procedimiento que puedas **explicar, comprobar, documentar y utilizar para diagnosticar errores**.

La progresión será:

```text
leer una configuración
→ interpretar dirección y prefijo
→ calcular límites
→ decidir pertenencia
→ decidir local/remoto
→ dividir el espacio
→ elegir tamaños
→ diseñar con VLSM
→ resumir cuando proceda con CIDR
→ documentar
→ configurar
→ verificar
→ diagnosticar
```

# 1. Leer una configuración IPv4

Antes de calcular una red debemos saber qué información tenemos delante. Cuando ejecutamos `ipconfig /all` en Windows o `ip address` en Linux, el sistema nos muestra varios datos. Cada uno tiene una función distinta y conviene no mezclarlos: la **dirección** y el **prefijo** definen juntos a qué red pertenece el equipo; el **gateway** es la «puerta» hacia las demás redes y tiene que estar dentro de esa red; el **DNS** traduce nombres y puede estar en cualquier red a la que se llegue.

Este apartado sirve para aprender a **leer** esos datos, reconocer algunos tipos de dirección especiales y saber qué herramienta muestra cada cosa. Comprobar si son coherentes vendrá después.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Dirección IPv4** (*IPv4 address*) | ¿Qué identificador lógico tiene esta interfaz? | `192.168.10.25` |
| **Prefijo / máscara** (*prefix length / subnet mask*) | ¿Qué parte de la dirección indica la red? ¿Qué destinos son locales? | `/24` = `255.255.255.0` |
| **Puerta de enlace predeterminada** (*default gateway*) | ¿A quién entrego lo que no es local? | `192.168.10.1` |
| **Servidor DNS** (*DNS server*) | ¿Quién traduce nombres en direcciones IP? | `192.168.10.53` |
| **Herramientas de consulta** (*inspection tools*) | ¿Dónde veo esos datos en cada sistema? | `ipconfig /all`, `ip address` |
| **Rangos especiales** (*special-purpose addresses*) | ¿Esta dirección es privada, de loopback, autoasignada…? | `127.0.0.1`, `169.254.x.x` |

> No debemos confundir **leer** con **validar**: ver unos valores en pantalla no demuestra que sean correctos.

Ejemplo:

```text
IPv4:    192.168.10.25
Prefijo: /24
Gateway: 192.168.10.1
DNS:     192.168.10.53
```

Estos cuatro datos responden a preguntas distintas.

## 1.1. Dirección IPv4

Una dirección IPv4 identifica lógicamente una interfaz dentro del espacio de direccionamiento IPv4.

IPv4 utiliza **32 bits**, representados habitualmente mediante cuatro octetos decimales:

```text
192.168.10.25
```

Una dirección no debe interpretarse aislada. Para saber a qué red pertenece necesitamos también su prefijo:

```text
192.168.10.25/24
```

## 1.2. Prefijo y máscara

El **prefijo** indica cuántos bits pertenecen a la parte de red.

```text
/24
→ 24 bits describen el prefijo de red
→ quedan 8 bits para posiciones dentro del bloque
```

La misma información puede representarse mediante una **subnet mask**:

```text
/24
=
255.255.255.0
```

No debes deducir la máscara observando únicamente el primer octeto de la dirección.

## 1.3. Default gateway

El **default gateway** es el siguiente salto que un host utiliza para enviar tráfico destinado a redes que no considera locales.

```text
gateway
≠
Internet
```

El gateway es normalmente una interfaz de router directamente alcanzable desde la red local del host.

## 1.4. DNS

El servidor DNS permite resolver nombres como:

```text
www.example.com
```

en direcciones IP.

No confundas:

```text
DNS
≠
gateway
```

El DNS resuelve nombres. El gateway participa en el envío hacia otras redes.

## 1.5. Herramientas de consulta

Cada herramienta aporta una evidencia distinta. Antes de ejecutar un comando conviene saber qué pregunta responde:

| Herramienta | Sistema | Qué evidencia aporta |
|---|---|---|
| `ipconfig /all` | Windows | IP, máscara, gateway, DNS, MAC, si hay DHCP y datos de la concesión |
| `Get-NetIPConfiguration` | Windows (PowerShell) | Resumen por interfaz: IP, gateway y DNS |
| `route print` | Windows | Tabla de rutas del host (red local, ruta por defecto) |
| `arp -a` | Windows / Linux | Caché ARP: qué IP locales tienen ya MAC conocida |
| `ip address` | Linux | Direcciones y prefijos de cada interfaz |
| `ip route` | Linux | Rutas del host y ruta por defecto (`default via …`) |
| `ip neigh` | Linux | Vecinos IPv4 conocidos (equivalente a la caché ARP) |
| `resolvectl status` o `/etc/resolv.conf` | Linux | Servidores DNS que usa el sistema |

### Windows

```text
ipconfig /all
Get-NetIPConfiguration
route print
arp -a
```

### Linux

```text
ip address
ip route
ip neigh
resolvectl status
```

La finalidad no es memorizar cada opción, sino saber **qué evidencia puede aportar cada herramienta**.

## 1.6. Leer no significa validar

Considera:

```text
IPv4:    192.168.20.37
Prefijo: /27
Gateway: 192.168.20.1
DNS:     192.168.50.53
```

Podemos leer esos valores, pero todavía no sabemos si todos son coherentes.

Necesitaremos responder preguntas como:

- ¿qué red contiene `192.168.20.37/27`?;
- ¿pertenece el gateway a esa red?;
- ¿puede el DNS estar en otra red?;
- si está en otra red, ¿existe una ruta para alcanzarlo?

Resolveremos este caso en el apartado 5.7, cuando ya sepamos calcular la red.

> **Idea clave:** una salida de configuración contiene hechos observables. La conclusión sobre si está bien configurada exige interpretar esos hechos.

## 1.7. Rangos de direcciones que debes reconocer

Al leer una configuración conviene reconocer a simple vista algunos rangos reservados. Saber que una dirección es privada, de loopback o autoasignada ya es información para el diagnóstico.

| Rango | Nombre | Qué significa al verlo |
|---|---|---|
| `10.0.0.0/8` | Privada (RFC 1918) | Red interna; no se enruta en Internet sin NAT (U10) |
| `172.16.0.0/12` (de `172.16.0.0` a `172.31.255.255`) | Privada (RFC 1918) | Red interna |
| `192.168.0.0/16` | Privada (RFC 1918) | Red interna (habitual en hogares y laboratorios) |
| `127.0.0.0/8` | Loopback | El propio equipo (`127.0.0.1`); no sale a la red |
| `169.254.0.0/16` | Enlace local / APIPA (*link-local*) | El equipo pidió DHCP y **no obtuvo respuesta**; se autoasignó una dirección |
| `0.0.0.0` | Dirección no especificada | «Aún no tengo dirección» (p. ej., cliente DHCP al empezar) o, como `0.0.0.0/0`, «cualquier destino» (ruta por defecto) |
| `255.255.255.255` | Broadcast limitado | A todos los equipos del enlace local |
| `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24` | Documentación (RFC 5737) | Direcciones «públicas» de ejemplo para manuales y laboratorios |

Un equipo con `169.254.x.x` no está «sin red» necesariamente: tiene enlace, pero no ha recibido configuración del servidor DHCP (apartado 12.8).

# 2. Binario útil, máscara y prefijo

La máscara y el prefijo son, en el fondo, un **patrón de bits**: unos que marcan la parte de red y ceros que marcan la parte de host. Para entender por qué `192.168.10.70/26` pertenece a la red `192.168.10.64` necesitamos mirar ese patrón, al menos en el octeto donde cambia.

Este apartado no pretende que conviertas continuamente direcciones completas a binario. El binario explica **el fundamento** (el AND lógico); después usaremos el método de bloques, más rápido, que da el mismo resultado.

| Concepto | Función | Ejemplo |
|---|---|---|
| **Octeto** (*octet*) | Grupo de 8 bits; vale de 0 a 255 | `192` |
| **Pesos binarios** (*binary place values*) | Valor de cada bit de un octeto | `128 64 32 16 8 4 2 1` |
| **Máscara de subred** (*subnet mask*) | Unos contiguos para la red, ceros para el host | `255.255.255.192` |
| **Longitud de prefijo** (*prefix length*) | Número de unos de la máscara | `/26` |
| **AND lógico** (*bitwise AND*) | Operación IP AND máscara que da la dirección de red | `70 AND 192 = 64` |
| **Direccionamiento con clases** (*classful addressing*) | Sistema histórico que deducía la máscara por el primer octeto | **No usar** para calcular |

> No confundas el **prefijo** (dato explícito que acompaña a la dirección) con la antigua **clase** (una regla histórica que ya no se aplica).

## 2.1. Pesos binarios

Los pesos de un octeto son:

```text
128 64 32 16 8 4 2 1
```

Ejemplo:

```text
192 = 128 + 64
    = 11000000
```

```text
25 = 16 + 8 + 1
   = 00011001
```

El binario es una **herramienta para comprender** cómo funciona la máscara. No es necesario convertir continuamente los 32 bits completos.

## 2.2. Máscaras frecuentes

| Prefijo | Máscara | Bits de host |
|---:|---|---:|
| /24 | 255.255.255.0 | 8 |
| /25 | 255.255.255.128 | 7 |
| /26 | 255.255.255.192 | 6 |
| /27 | 255.255.255.224 | 5 |
| /28 | 255.255.255.240 | 4 |
| /29 | 255.255.255.248 | 3 |
| /30 | 255.255.255.252 | 2 |

`/31` y `/32` existen y tienen usos reales, pero no son el centro de los primeros cálculos de esta unidad.

Como la máscara son unos **seguidos** de ceros, un octeto de máscara solo puede valer:

```text
0, 128, 192, 224, 240, 248, 252, 254, 255
```

Una «máscara» como `255.255.255.200` no es válida.

## 2.3. El prefijo no tiene por qué coincidir con los puntos

Ejemplo:

```text
192.168.10.25/26
```

`/26` significa:

```text
24 bits completos de los tres primeros octetos
+
2 bits del cuarto octeto
```

La frontera red/host puede encontrarse dentro de un octeto.

## 2.4. AND lógico

La dirección de red puede obtenerse mediante:

```text
IP
AND
máscara
=
dirección de red
```

Ejemplo simplificado en el cuarto octeto:

```text
IP:       70 = 01000110
Máscara: 192 = 11000000
AND:      64 = 01000000
```

Por tanto, para `192.168.10.70/26`:

```text
red = 192.168.10.64
```

Comprender el AND explica el fundamento. Para trabajar con rapidez utilizaremos también el **método de bloques**.

## 2.5. No utilizar clases históricas como procedimiento

No es correcto razonar:

```text
192.x.x.x
→ siempre /24
```

En redes actuales utilizamos:

```text
dirección + prefijo explícito
```

Ejemplo:

```text
192.168.10.25/26
```

es una red `/26`, aunque la dirección comience por `192`.

# 3. Dirección de red, broadcast, rango y capacidad

Una subred IPv4 es un **bloque de direcciones consecutivas**. Para trabajar con ella no basta con saber su máscara: necesitamos conocer dónde empieza, dónde termina, qué direcciones podemos dar a los equipos y cuántos caben. Esos cuatro datos son los que aparecerán en cualquier plan de direccionamiento, en la configuración de un servidor DHCP o en una ruta.

Las cuatro piezas están relacionadas: la primera dirección identifica la red, la última es el broadcast, lo que queda en medio son los hosts, y la capacidad depende de los bits de host.

| Concepto | Qué es | Ejemplo para `192.168.10.64/26` |
|---|---|---|
| **Dirección de red** (*network address*) | Primera dirección del bloque; identifica la red | `192.168.10.64` |
| **Dirección de broadcast** (*broadcast address*) | Última dirección del bloque; llega a todos los hosts de la subred | `192.168.10.127` |
| **Rango de hosts** (*host range*) | Direcciones asignables a interfaces | `192.168.10.65`–`192.168.10.126` |
| **Capacidad** (*capacity / usable hosts*) | Cuántos hosts caben: `2^h − 2` | 62 |

> Error típico: asignar a un equipo la dirección de red o la de broadcast. En una subred convencional ninguna de las dos es válida para un host.

## 3.1. Dirección de red

La **network address** representa el bloque.

Ejemplo:

```text
192.168.10.64/26
```

La dirección `192.168.10.64` identifica esa red.

## 3.2. Broadcast

En una subred IPv4 convencional, la última dirección del bloque es el **broadcast address**.

Para:

```text
192.168.10.64/26
```

el broadcast es:

```text
192.168.10.127
```

## 3.3. Rango de hosts

En los casos convencionales trabajados inicialmente:

```text
primer host = red + 1
último host = broadcast - 1
```

Ejemplo:

```text
Red:       192.168.10.64/26
1.er host: 192.168.10.65
Último:    192.168.10.126
Broadcast: 192.168.10.127
```

## 3.4. Capacidad

Si quedan `h` bits para host:

```text
direcciones totales = 2^h
```

En las subredes convencionales de esta unidad:

```text
hosts utilizables = 2^h - 2
```

Ejemplo `/26`:

```text
h = 6
2^6 = 64 direcciones
64 - 2 = 62 hosts utilizables
```

## 3.5. Ejemplo completo

Calcular `172.16.5.140/27`.

Máscara:

```text
/27 = 255.255.255.224
```

Tamaño de bloque:

```text
256 - 224 = 32
```

Límites del cuarto octeto:

```text
0, 32, 64, 96, 128, 160, 192, 224
```

`140` se encuentra entre `128` y `159`.

Resultado:

```text
Red:         172.16.5.128/27
Broadcast:   172.16.5.159
Primer host: 172.16.5.129
Último host: 172.16.5.158
Capacidad:   30 hosts
```

> **Idea clave:** calcular una subred no consiste únicamente en encontrar la máscara. Debemos identificar sus límites y su capacidad.

# 4. Método de bloques y pertenencia

El AND lógico funciona siempre, pero es lento para el trabajo diario. El **método de bloques** aprovecha una propiedad sencilla: con un prefijo dado, todas las subredes tienen el mismo tamaño y empiezan en múltiplos de ese tamaño. Si conocemos el tamaño del bloque, basta con buscar entre qué dos múltiplos cae la dirección.

Con este método respondemos también a la pregunta de **pertenencia**: dos direcciones están en la misma subred si caen dentro del mismo bloque.

| Concepto | Pregunta que responde | Ejemplo con `/26` |
|---|---|---|
| **Octeto variable** (*interesting octet*) | ¿En qué octeto está la frontera red/host? | El cuarto (máscara `192`) |
| **Tamaño de bloque** (*block size*) | ¿Cada cuántas direcciones empieza una subred? | `256 − 192 = 64` |
| **Límites válidos** (*subnet boundaries*) | ¿Dónde puede empezar una subred de este tamaño? | `0, 64, 128, 192` |
| **Pertenencia** (*subnet membership*) | ¿Dos direcciones están en el mismo bloque? | `.20` y `.50` sí; `.20` y `.70` no |

> La pertenencia depende de **IP + prefijo**, no de que las direcciones «se parezcan».

## 4.1. Tamaño de bloque

Para `/26`:

```text
máscara del octeto variable = 192
bloque = 256 - 192 = 64
```

Los límites son:

```text
0
64
128
192
```

## 4.2. Localizar una dirección

Para:

```text
192.168.10.70/26
```

`70` cae en el intervalo:

```text
64–127
```

Por tanto:

```text
Red:       192.168.10.64/26
Broadcast: 192.168.10.127
Hosts:     192.168.10.65–126
```

## 4.3. Procedimiento estable

```text
prefijo
→ máscara
→ octeto variable
→ tamaño de bloque
→ intervalo
→ red
→ broadcast
→ rango
```

## 4.4. Pertenencia

Considera:

```text
192.168.10.20/26
192.168.10.50/26
```

Ambas pertenecen a:

```text
192.168.10.0/26
```

En cambio:

```text
192.168.10.70/26
```

pertenece a:

```text
192.168.10.64/26
```

Dos direcciones pueden parecer próximas y pertenecer a redes distintas.

## 4.5. Error frecuente: «los tres primeros octetos coinciden»

```text
192.168.10.20/26
192.168.10.70/26
```

comparten `192.168.10`, pero **no** pertenecen a la misma subred.

La pertenencia depende de:

```text
IP + prefijo
```

no de la apariencia decimal.

## 4.6. Cuando el octeto variable no es el cuarto

El método es el mismo aunque la frontera caiga en otro octeto. Solo cambia **dónde** aplicamos el bloque.

Calcular `172.16.45.200/20`:

```text
/20 = 255.255.240.0
octeto variable = el tercero (máscara 240)
bloque = 256 - 240 = 16
límites del tercer octeto: 0, 16, 32, 48, 64, ...
45 cae entre 32 y 47
```

Resultado:

```text
Red:         172.16.32.0/20
Broadcast:   172.16.47.255
Primer host: 172.16.32.1
Último host: 172.16.47.254
Capacidad:   2^12 - 2 = 4094 hosts
```

Fíjate en que, a la derecha del octeto variable, la red lleva todo a `0` y el broadcast todo a `255`.

# 5. Destino local, destino remoto y default gateway

El subnetting no es únicamente cálculo. Cada vez que un host envía un paquete tiene que tomar una decisión: si el destino está en su propia red, se lo entrega directamente; si no, se lo entrega al gateway. Esa decisión depende de la dirección y del prefijo del host, y es la razón práctica de todo lo calculado hasta ahora.

Este apartado relaciona el cálculo con lo que ocurre en la red: la tabla de rutas del host, el gateway y ARP (visto en U02).

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Destino local** (*local destination*) | ¿El destino está en mi subred? → entrega directa | `10.20.30.70/27` → `10.20.30.94` |
| **Destino remoto** (*remote destination*) | ¿Está en otra red? → entrega al gateway | `192.168.50.20/26` → `8.8.8.8` |
| **Default gateway** | ¿Quién es mi primer salto hacia otras redes? | `192.168.50.1` |
| **Tabla de rutas del host** (*host routing table*) | ¿Qué rutas conoce el equipo? | red local + `default via …` |
| **Coincidencia del prefijo más largo** (*longest prefix match*) | Si varias rutas encajan, ¿cuál gana? | la más específica |
| **ARP** (*Address Resolution Protocol*) | ¿Qué MAC tiene la IP local a la que entrego la trama? | `arp -a`, `ip neigh` |

> Aunque el paquete vaya al gateway, la **IP destino** sigue siendo la del destino final; lo que cambia es la **MAC destino** de la trama.

El host se pregunta:

```text
¿el destino pertenece a mi red?
```

## 5.1. Destino local

Si el destino pertenece a la misma subred:

```text
host origen
→ enlace local
→ host destino
```

No necesita enviar el paquete al default gateway para alcanzar ese destino.

## 5.2. Destino remoto

Si el destino pertenece a otra red:

```text
host origen
→ default gateway
→ otras redes
```

El host mantiene como **IP destino** la dirección del destino final, pero en la primera trama Ethernet puede utilizar como **MAC destino** la del gateway.

Esto recupera conceptos de U02:

```text
IP destino
→ destino final

MAC destino de la primera trama
→ siguiente salto local
```

## 5.3. El gateway debe ser localmente alcanzable

Ejemplo coherente:

```text
Host:    192.168.50.20/26
Gateway: 192.168.50.1
```

Ambos pertenecen a:

```text
192.168.50.0/26
```

Ejemplo incoherente:

```text
Host:    192.168.50.20/26
Gateway: 192.168.50.129
```

El supuesto gateway pertenece a otro bloque `/26` (`192.168.50.128/26`).

## 5.4. Tabla de rutas del host

A nivel inicial interesa reconocer:

- red local;
- ruta por defecto;
- interfaz;
- gateway.

Windows:

```text
route print
```

Linux:

```text
ip route
```

Ejemplo simplificado:

```text
192.168.50.0/26 dev eth0
default via 192.168.50.1
```

Significa que la red local se alcanza directamente y que otros destinos pueden enviarse al gateway.

En Windows, la ruta por defecto aparece en `route print` como destino `0.0.0.0` con máscara `0.0.0.0` y la IP del gateway como «Puerta de enlace».

### Qué ruta se elige: el prefijo más largo

La ruta por defecto equivale a `0.0.0.0/0`: encaja con **cualquier** destino. La ruta de la red local (`/26`) solo encaja con los destinos de esa red. Cuando varias rutas encajan con un destino, el host elige la **más específica**, es decir, la de **prefijo más largo** (*longest prefix match*):

```text
Destino 192.168.50.30  → encaja con /26 y con /0 → gana /26 → entrega directa
Destino 8.8.8.8        → solo encaja con /0      → gateway 192.168.50.1
```

Los routers aplican la misma regla; la estudiarás a fondo en U08.

## 5.5. ARP como evidencia local

Para enviar una trama al gateway en IPv4, el host puede necesitar conocer su MAC.

```text
arp -a
ip neigh
```

Una entrada ARP para el gateway es evidencia de descubrimiento/comunicación local reciente, pero **no demuestra por sí sola** que exista conectividad con Internet o con cualquier destino remoto.

## 5.6. Ejemplo de decisión

```text
Host: 10.20.30.70/27
GW:   10.20.30.65
Dest: 10.20.30.94
```

Para `/27`, el bloque es `32`.

`70` pertenece a:

```text
10.20.30.64–95
```

Por tanto:

```text
Red:       10.20.30.64/27
Broadcast: 10.20.30.95
```

El gateway `10.20.30.65` es local.

El destino `10.20.30.94` también es local.

Conclusión:

```text
el host no necesita entregar este paquete al default gateway
```

## 5.7. Resolución del caso del apartado 1.6

```text
IPv4:    192.168.20.37/27
Gateway: 192.168.20.1
DNS:     192.168.50.53
```

Para `/27`, el bloque es `32`. `37` cae entre `32` y `63`:

```text
Red:       192.168.20.32/27
Hosts:     192.168.20.33–62
Broadcast: 192.168.20.63
```

- El gateway `192.168.20.1` está en otro bloque (`192.168.20.0/27`, de `.0` a `.31`): **no es localmente alcanzable**. La configuración es incoherente.
- El DNS `192.168.50.53` está en otra red. Eso sí es admisible: muchos servidores DNS están en otra subred. Pero para llegar a él el host necesita un gateway válido; con este error, la resolución de nombres también fallará.

Corrección mínima: usar un gateway dentro de `192.168.20.33–62` (por ejemplo, `192.168.20.33` si esa es la convención de la organización y existe allí una interfaz de router), o revisar si el prefijo documentado era otro.

# 6. Subnetting con FLSM

Una organización rara vez usa un bloque grande como una única red: lo divide para separar departamentos, limitar el broadcast o aplicar políticas distintas. **Subnetting** consiste en dividir un bloque en otros bloques más pequeños. La forma más sencilla de hacerlo es la división en partes **iguales** (FLSM), que sirve para aprender un procedimiento estable antes de pasar a tamaños distintos (VLSM, apartado 8).

La idea central es un intercambio: cada bit que «tomamos prestado» de la parte de host para la parte de red **duplica** el número de subredes y **divide por dos** su tamaño.

| Concepto | Qué significa | Ejemplo |
|---|---|---|
| **Subnetting** | Dividir un bloque en bloques menores | `/24` → cuatro `/26` |
| **Bloque padre** (*parent block*) | Espacio de partida que se divide | `192.168.10.0/24` |
| **Bits prestados** (*borrowed bits*) | Bits de host que pasan a identificar subred | `s = 2` |
| **FLSM** (*Fixed Length Subnet Masking*) | Todas las subredes con el mismo prefijo | cuatro `/26` de 64 direcciones |
| **Comprobación inversa** (*reverse check*) | Nº de subredes × tamaño = tamaño del padre | `4 × 64 = 256` |

> No mezcles **número de subredes** (`2^s`, depende de los bits prestados) con **hosts por subred** (`2^h − 2`, depende de los bits que quedan).

## 6.1. ¿Por qué dividir una red?

Puede ser útil para:

- separar departamentos;
- reducir dominios de broadcast;
- aplicar políticas;
- organizar direccionamiento;
- facilitar troubleshooting;
- reservar capacidad para crecimiento;
- preparar VLAN y routing.

## 6.2. FLSM

En **Fixed Length Subnet Masking (FLSM)** todas las subredes utilizan el mismo prefijo.

Ejemplo:

```text
Bloque inicial: 192.168.10.0/24
Necesidad:       4 subredes iguales
```

Necesitamos 2 bits para identificar 4 subredes:

```text
2^2 = 4
```

El prefijo pasa de `/24` a `/26`.

Resultado:

```text
192.168.10.0/26
192.168.10.64/26
192.168.10.128/26
192.168.10.192/26
```

Cada subred tiene:

```text
64 direcciones
62 hosts utilizables en el caso convencional
```

## 6.3. Procedimiento FLSM

```text
1. identificar el bloque padre
2. determinar cuántas subredes necesitamos
3. calcular cuántos bits hay que tomar
4. obtener el nuevo prefijo
5. calcular el tamaño de bloque
6. enumerar redes
7. comprobar que todas quedan dentro del bloque padre
```

## 6.4. Número de subredes

Si tomamos `s` bits:

```text
subredes = 2^s
```

No aplicaremos reglas históricas que restaban dos subredes.

Si el número de subredes necesarias no es una potencia de 2, tomamos el menor `s` tal que `2^s` sea **mayor o igual** que la necesidad:

```text
Bloque: 192.168.10.0/24
Necesidad: 5 subredes
2^2 = 4 → insuficiente
2^3 = 8 → suficiente → s = 3 → /27

Subredes /27 (bloque 32, 30 hosts cada una):
.0  .32  .64  .96  .128  .160  .192  .224
```

Usamos cinco y quedan tres libres para crecimiento.

## 6.5. Comprobación inversa

Cuando dividimos por completo un bloque de forma uniforme:

```text
número de subredes
×
tamaño de cada subred
=
tamaño del bloque padre
```

Ejemplo:

```text
4 × 64 = 256
```

que coincide con el tamaño de un `/24`.

# 7. Elegir un prefijo a partir del número de hosts

En un diseño real no siempre nos dicen «usa `/27`». Es habitual recibir un requisito:

> necesitamos una red para 25 equipos.

Debemos convertir una **necesidad** en un **prefijo**. Es el paso inverso al del apartado 3: allí partíamos del prefijo y calculábamos la capacidad; aquí partimos de la capacidad necesaria y buscamos el prefijo. Además, la respuesta no es solo matemática: hay que decidir cuánto margen dejar.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Requisito de hosts** (*host requirement*) | ¿Cuántas interfaces necesitan IP en esa red? | 25 equipos |
| **Bits de host** (*host bits*, `h`) | ¿Cuántos bits necesito para que quepan? | `2^5 − 2 = 30 ≥ 25` → `h = 5` |
| **Prefijo mínimo** (*minimum prefix*) | ¿Qué prefijo resulta? | `32 − 5 = /27` |
| **Margen de crecimiento** (*growth margin*) | ¿Cuánto espacio queda para el futuro? | 30 − 25 = 5 libres |

> El prefijo **mínimo** no siempre es el **adecuado**: si la red crece, un diseño sin margen obliga a renumerar.

## 7.1. Procedimiento

Buscamos el menor número de bits de host que proporcione capacidad suficiente.

Ejemplo: 25 hosts.

Probamos:

```text
2^4 - 2 = 14
→ insuficiente

2^5 - 2 = 30
→ suficiente
```

Necesitamos 5 bits para host.

```text
32 - 5 = /27
```

Por tanto:

```text
25 hosts
→ /27
```

Al contar hosts, incluye **todas las interfaces que necesitan IP** en esa red: equipos, impresoras, servidores y también la interfaz del router que hará de gateway, salvo que el enunciado indique otra cosa.

## 7.2. Tabla práctica

| Prefijo | Direcciones | Hosts convencionales |
|---:|---:|---:|
| /24 | 256 | 254 |
| /25 | 128 | 126 |
| /26 | 64 | 62 |
| /27 | 32 | 30 |
| /28 | 16 | 14 |
| /29 | 8 | 6 |
| /30 | 4 | 2 |

Un `/30` (2 hosts) es el tamaño clásico de un enlace punto a punto entre dos routers; lo usarás en U08.

## 7.3. No elegir siempre la red más grande

Si necesitamos 20 hosts, un `/24` funcionaría, pero desperdicia mucho espacio.

El objetivo habitual es:

```text
capacidad suficiente
+
margen razonable
+
uso coherente del espacio
```

## 7.4. Crecimiento

El prefijo mínimo matemático no siempre es la mejor decisión profesional.

Si una red tiene 28 dispositivos y está creciendo:

```text
/27 → 30 hosts utilizables
```

puede dejar un margen demasiado pequeño.

El diseño debe considerar requisitos previsibles, no solo la fotografía actual.

# 8. VLSM: subredes de distinto tamaño

FLSM es sencillo, pero no siempre aprovecha bien el espacio: si todas las subredes deben ser iguales, la más grande impone el tamaño de todas. **Variable Length Subnet Masking (VLSM)** permite utilizar prefijos distintos dentro de un mismo plan, de forma que cada red reciba el tamaño que necesita.

A cambio, hay que ser más cuidadoso: los bloques tienen tamaños distintos y deben colocarse en **límites válidos**, sin **solaparse** y sin salirse del bloque padre. Por eso VLSM se hace con un procedimiento ordenado y termina siempre con una comprobación y una documentación.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **VLSM** (*Variable Length Subnet Masking*) | ¿Puedo dar a cada red el tamaño que necesita? | `/25`, `/26`, `/27`, `/28` en un mismo `/24` |
| **Orden de mayor a menor** (*largest first*) | ¿Por dónde empiezo a asignar? | Primero la red de 100 hosts |
| **Límite válido** (*valid boundary / alignment*) | ¿Dónde puede empezar un bloque de este tamaño? | un `/26` solo en `.0`, `.64`, `.128`, `.192` |
| **Solapamiento** (*overlap*) | ¿Dos bloques comparten direcciones? | `.128/26` y `.160/27` se solapan |
| **Espacio libre** (*free space*) | ¿Qué queda disponible para crecer? | `192.168.100.240/28` |

> Un error de VLSM no siempre se nota al configurar: dos redes solapadas pueden funcionar «a ratos» y fallar cuando se añaden rutas o equipos.

Supongamos estas necesidades:

```text
USERS   100 hosts
SERVERS 30 hosts
VOICE   20 hosts
MGMT    10 hosts
```

Asignar el mismo tamaño a todas las redes puede desperdiciar muchas direcciones. Con FLSM, la red de 100 hosts obliga a usar `/25` (128 direcciones) para las cuatro: 4 × 128 = 512 direcciones, que **ni siquiera caben** en un `/24`. Con VLSM basta con `/25` + `/27` + `/27` + `/28` = 128 + 32 + 32 + 16 = 208 direcciones.

## 8.1. Procedimiento estable

```text
1. ordenar necesidades de mayor a menor
2. calcular el prefijo mínimo adecuado para cada necesidad
3. asignar primero el bloque mayor
4. continuar desde el siguiente límite válido
5. comprobar que ningún bloque se solapa
6. comprobar que todo queda dentro del bloque padre
7. documentar
```

## 8.2. Ejemplo

Bloque disponible:

```text
192.168.100.0/24
```

Necesidades:

```text
A: 100 hosts
B: 50 hosts
C: 20 hosts
D: 10 hosts
```

Prefijos:

```text
100 hosts → /25 → 126 hosts
50 hosts  → /26 → 62 hosts
20 hosts  → /27 → 30 hosts
10 hosts  → /28 → 14 hosts
```

Asignación:

```text
A → 192.168.100.0/25
B → 192.168.100.128/26
C → 192.168.100.192/27
D → 192.168.100.224/28
```

Espacio restante:

```text
192.168.100.240/28
```

## 8.3. Tabla de documentación

| Red | Necesidad | Prefijo | Network address | Host range | Broadcast |
|---|---:|---:|---|---|---|
| A | 100 | /25 | 192.168.100.0 | .1–.126 | .127 |
| B | 50 | /26 | 192.168.100.128 | .129–.190 | .191 |
| C | 20 | /27 | 192.168.100.192 | .193–.222 | .223 |
| D | 10 | /28 | 192.168.100.224 | .225–.238 | .239 |
| Libre | — | /28 | 192.168.100.240 | .241–.254 | .255 |

## 8.4. Límites válidos

No podemos colocar una red de cualquier tamaño en cualquier dirección.

Una `/26` utiliza bloques de 64:

```text
0, 64, 128, 192
```

Por tanto:

```text
192.168.100.96/26
```

no representa un límite válido de `/26`. `96` es un límite válido de `/27` (múltiplo de 32), pero no de `/26` (no es múltiplo de 64): con máscara `/26`, `192.168.100.96` sería un host de la red `192.168.100.64/26`.

## 8.5. Por qué se empieza por la red mayor

Si asignamos primero bloques pequeños de forma desordenada podemos fragmentar el espacio e impedir después colocar una red grande contigua.

Ordenar de mayor a menor reduce ese riesgo.

## 8.6. Comprobar solapamientos

Dos subredes se solapan si comparten alguna dirección.

Cada asignación debe verificarse mediante sus límites:

```text
inicio del bloque
→ final del bloque
→ siguiente bloque comienza después
```

Ejemplo de solapamiento:

```text
B: 192.168.100.128/26 → .128–.191
X: 192.168.100.160/27 → .160–.191
```

`X` está completamente dentro de `B`: comparten 32 direcciones. Es un error de diseño aunque cada red, por separado, esté bien calculada.

## 8.7. Diseño y crecimiento

VLSM no significa utilizar siempre el prefijo mínimo sin margen.

El diseño debe equilibrar:

- requisitos actuales;
- crecimiento;
- simplicidad;
- documentación;
- disponibilidad del bloque padre.

# 9. CIDR y agregación sencilla

**Classless Inter-Domain Routing (CIDR)** utiliza prefijos explícitos y permite representar bloques sin depender de clases históricas. Es la forma en que se escriben y se reparten hoy todas las direcciones IPv4, desde un aula hasta un proveedor de Internet.

CIDR tiene dos caras que usaremos en esta unidad: la **notación** (`dirección/prefijo`), que ya vienes usando, y la **agregación**: representar varias redes contiguas con un único prefijo más corto. La agregación permite que un router anuncie «todas mis redes» con una sola línea; aquí solo aprenderemos a comprobar si un resumen sencillo es correcto.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **CIDR** (*Classless Inter-Domain Routing*) | ¿Cómo expreso un bloque sin depender de clases? | `10.20.30.32/27` |
| **Notación de prefijo** (*prefix notation / slash notation*) | ¿Dónde está la frontera red/host? | `/27` |
| **Agregación o resumen** (*aggregation / summarization*) | ¿Puedo representar varias redes con un solo prefijo? | `192.168.0.0/24` + `192.168.1.0/24` = `192.168.0.0/23` |
| **Límite de resumen** (*summary boundary*) | ¿El resumen empieza donde debe y cubre solo lo que quiero? | un `/23` empieza en tercer octeto par |

> Que dos redes sean **consecutivas** no significa que se puedan resumir **exactamente** en un solo prefijo.

## 9.1. Una dirección sin prefijo está incompleta para muchos cálculos

```text
10.20.30.40
```

no indica por sí sola si pertenece a un `/8`, `/16`, `/24`, `/27` u otro bloque.

Necesitamos:

```text
10.20.30.40/27
```

para interpretar la frontera.

## 9.2. Agregación

La **agregación** o **summary** representa varios bloques mediante un prefijo común cuando sus límites lo permiten.

Ejemplo:

```text
192.168.0.0/24
192.168.1.0/24
```

pueden resumirse como:

```text
192.168.0.0/23
```

porque `/23` cubre:

```text
192.168.0.0
hasta
192.168.1.255
```

## 9.3. No basta con que las redes sean consecutivas

Un resumen debe:

- comenzar en un límite válido;
- cubrir exactamente el intervalo deseado o entender qué bloques adicionales incluye;
- tener bits comunes suficientes.

Por ejemplo:

```text
192.168.1.0/24
192.168.2.0/24
```

no se resumen limpiamente como un único `/23` que contenga solo esas dos redes, porque los límites `/23` comienzan en pares adecuados de tercer octeto (`0`, `2`, `4`, ...).

El menor prefijo único que contiene ambas es `192.168.0.0/22` (de `192.168.0.0` a `192.168.3.255`), que incluye además `192.168.0.0/24` y `192.168.3.0/24`. Puede ser aceptable si esas redes no existen en otro sitio, pero hay que saberlo y documentarlo.

## 9.4. Comprobar un resumen con binario

Queremos resumir cuatro redes:

```text
172.16.4.0/24
172.16.5.0/24
172.16.6.0/24
172.16.7.0/24
```

Solo cambia el tercer octeto. Lo pasamos a binario:

```text
4 = 000001 00
5 = 000001 01
6 = 000001 10
7 = 000001 11
```

Los 6 primeros bits del tercer octeto son comunes. Prefijo del resumen: `16 + 6 = /22`.

```text
Resumen: 172.16.4.0/22  (máscara 255.255.252.0)
Cubre:   172.16.4.0 – 172.16.7.255
```

Comprobaciones: `4` es múltiplo de 4 (límite válido de `/22` en el tercer octeto) y el `/22` contiene exactamente las cuatro redes, ni una más.

## 9.5. Utilidad posterior

En U09 reutilizaremos agregación y prefijos cuando estudiemos routing dinámico. En U04 interesa comprender la lógica de los bloques y ser capaz de verificar un resumen sencillo.

# 10. Plan de direccionamiento e IPAM básico

Un cálculo correcto puede producir un diseño difícil de operar si no existe documentación. Un plan de direccionamiento responde a preguntas que el cálculo no resuelve: qué dirección tiene el gateway, qué direcciones reparte el DHCP, cuáles son fijas, qué espacio queda libre. Si esas decisiones no están escritas, cada técnico las toma a su manera y aparecen conflictos.

La gestión organizada de ese plan se llama **IPAM**. En esta unidad no necesitas una herramienta profesional: una tabla bien mantenida y revisada es suficiente para aplicar sus principios.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Plan de direccionamiento** (*addressing plan*) | ¿Qué red, gateway y uso tiene cada segmento? | USERS → `172.16.10.0/25`, gw `.1` |
| **IPAM** (*IP Address Management*) | ¿Dónde se documenta y mantiene el uso del espacio? | Tabla de redes, rangos y asignaciones |
| **Convención de gateway** (*gateway convention*) | ¿Qué dirección lleva siempre el gateway? | primer host de cada subred |
| **Estático, dinámico, reserva** (*static / dynamic / reservation*) | ¿Cómo recibe su IP cada tipo de equipo? | servidores fijos, clientes por DHCP |
| **Validación cruzada** (*cross-check*) | ¿El plan es coherente antes de aplicarlo? | sin solapes, pools fuera de las fijas |

> Un plan **correcto** (los cálculos cuadran) no es lo mismo que un plan **mantenible** (otro técnico puede entenderlo, ampliarlo y auditarlo).

## 10.1. Qué debe tener un buen plan

Debe ser:

- coherente;
- legible;
- documentado;
- verificable;
- ampliable;
- mantenible.

## 10.2. Ejemplo de requisitos

```text
USERS    → 100 hosts
SERVERS  → 30 hosts
VOICE    → 20 hosts
MGMT     → 10 hosts
```

El trabajo no termina al seleccionar los prefijos. También hay que decidir:

- redes;
- gateways;
- rangos dinámicos;
- direcciones reservadas;
- espacio libre;
- convenciones de nombres/documentación.

El apartado 10.7 muestra un plan completo para estos requisitos.

## 10.3. IPAM

**IP Address Management (IPAM)** es la gestión organizada del espacio de direcciones.

En esta unidad puede bastar una tabla bien mantenida:

| Nombre | Red/prefijo | Gateway | Rango de hosts | Broadcast | Asignación | Observaciones |
|---|---|---|---|---|---|---|

No es necesario utilizar una plataforma empresarial para aplicar los principios de IPAM.

## 10.4. Convención de gateway

Una organización puede decidir, por ejemplo:

```text
gateway = primer host
```

u otra convención coherente.

No existe una única regla universal. Lo importante es:

```text
criterio conocido
+
aplicación consistente
+
documentación
```

## 10.5. Direcciones estáticas y dinámicas

Un criterio posible:

```text
infraestructura → estática
servidores       → estática o reserva
clientes         → DHCP
```

La decisión depende de necesidades operativas.

## 10.6. Validación cruzada

Antes de aplicar un plan, comprobar:

- no existen solapamientos;
- cada gateway pertenece a su subred;
- los pools no invaden direcciones excluidas o estáticas;
- todas las redes tienen capacidad suficiente;
- el espacio libre queda identificado;
- las convenciones son consistentes.

## 10.7. Ejemplo completo de plan IPAM

Bloque padre: `172.16.10.0/24`. Requisitos del apartado 10.2. Convenciones: gateway = primer host; en las redes con DHCP, las primeras direcciones se reservan para infraestructura.

Decisión de prefijos (de mayor a menor):

```text
USERS   100 → /25 (126 hosts)
SERVERS  30 → /27 daría 30 hosts: margen 0 → se elige /26 (62 hosts) por crecimiento
VOICE    20 → /27 (30 hosts)
MGMT     10 → /28 (14 hosts)
Total: 128 + 64 + 32 + 16 = 240 direcciones de 256 → cabe; quedan 16 libres
```

| Nombre | Red/prefijo | Gateway | Rango de hosts | Broadcast | Asignación | Observaciones |
|---|---|---|---|---|---|---|
| USERS | 172.16.10.0/25 | .1 | .1–.126 | .127 | DHCP: pool .11–.126 | .2–.10 excluidas (infraestructura); pool de 116 direcciones |
| SERVERS | 172.16.10.128/26 | .129 | .129–.190 | .191 | Estática o reserva | DNS interno en .130 |
| VOICE | 172.16.10.192/27 | .193 | .193–.222 | .223 | DHCP: pool .201–.222 | .194–.200 excluidas; pool de 22 direcciones |
| MGMT | 172.16.10.224/28 | .225 | .225–.238 | .239 | Estática | Gestión de switches y AP |
| Libre | 172.16.10.240/28 | — | .241–.254 | .255 | Sin asignar | Reserva para crecimiento |

Validación cruzada: los bloques terminan en `.127`, `.191`, `.223`, `.239` y el siguiente empieza justo después (sin solapes); cada gateway está dentro de su red; los pools no incluyen el gateway ni las direcciones excluidas; todas las redes cubren su necesidad.

# 11. Configuración IPv4 estática y verificación

Una vez diseñado el plan debemos aplicarlo y demostrar que funciona. Son dos tareas distintas: **configurar** es introducir valores; **verificar** es obtener evidencias de que esos valores producen la comunicación esperada. Un técnico profesional no da por terminado un cambio hasta haberlo verificado.

Este apartado recoge qué parámetros necesita un host, dónde se introducen en cada sistema, en qué orden conviene comprobarlos y cómo actuar si algo falla.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Parámetros del host** (*host parameters*) | ¿Qué necesita un equipo para comunicarse? | IP, prefijo, gateway, DNS |
| **Configuración estática** (*static configuration*) | ¿Cómo los introduzco a mano? | Panel de red, `New-NetIPAddress`, `nmcli` |
| **Verificación progresiva** (*progressive verification*) | ¿En qué orden compruebo? | interfaz → IP → gateway → remoto → DNS |
| **Evidencia** (*evidence*) | ¿Qué demuestra cada prueba? | `ping` al gateway ≠ acceso a Internet |
| **Cambio de una sola variable** (*one change at a time*) | ¿Cómo sé qué arregló el problema? | corregir solo el gateway y volver a probar |

> **Configurar no equivale a verificar.**

## 11.1. Parámetros habituales

Un host suele necesitar:

```text
IPv4 address
subnet mask / prefix
default gateway
DNS server
```

## 11.2. Verificación progresiva

Un orden útil es:

```text
1. interfaz
2. dirección y prefijo
3. red calculada
4. vecino/local
5. gateway
6. destino remoto por IP
7. DNS
8. servicio
```

No significa que siempre debamos ejecutar ocho pruebas. Significa que debemos escoger la siguiente prueba que reduzca mejor la incertidumbre.

## 11.3. Configurar no equivale a verificar

Introducir valores en una interfaz solo demuestra que hemos cambiado la configuración.

Para demostrar conectividad debemos obtener evidencia.

Ejemplos:

```text
ipconfig /all
ip address
ip route
ping
arp -a
ip neigh
nslookup
```

Cada prueba responde a una pregunta diferente.

## 11.4. Cambiar una sola variable

Ante un fallo, evita cambiar simultáneamente:

- IP;
- máscara;
- gateway;
- DNS.

Si cambiamos todo a la vez y después funciona, sabemos que algo estaba mal, pero no hemos demostrado qué.

## 11.5. Caso

```text
PC1
IP: 192.168.40.34/27
GW: 192.168.40.33

PC2
IP: 192.168.40.62/27
GW: 192.168.40.33
```

Para `/27`, los bloques son de 32.

Ambas direcciones están dentro de:

```text
192.168.40.32–63
```

Por tanto:

```text
Red:       192.168.40.32/27
Hosts:     192.168.40.33–62
Broadcast: 192.168.40.63
```

El gateway `192.168.40.33` es válido y local.

Un ping correcto entre PC1 y PC2 demuestra conectividad IP entre esos hosts en ese momento, pero no demuestra por sí solo:

- que DNS funcione;
- que exista routing a Internet;
- que cualquier aplicación responda.

## 11.6. Dónde se introduce la configuración

Los parámetros son los mismos en todos los sistemas; cambia la herramienta. Ejemplo con PC1 del caso anterior (DNS supuesto: `192.168.40.53`):

**Packet Tracer (PC):** *Desktop → IP Configuration → Static*: IPv4 Address, Subnet Mask, Default Gateway y DNS Server.

**Windows (interfaz gráfica):** *Configuración de red → Cambiar opciones del adaptador* (`ncpa.cpl`) → propiedades del adaptador → *Protocolo de Internet versión 4 (TCP/IPv4)*.

**Windows (PowerShell, como administrador):**

```text
New-NetIPAddress -InterfaceAlias "Ethernet" -IPAddress 192.168.40.34 -PrefixLength 27 -DefaultGateway 192.168.40.33
Set-DnsClientServerAddress -InterfaceAlias "Ethernet" -ServerAddresses 192.168.40.53
```

**Linux con NetworkManager (persistente):**

```text
nmcli connection modify "Wired connection 1" ipv4.method manual ipv4.addresses 192.168.40.34/27 ipv4.gateway 192.168.40.33 ipv4.dns 192.168.40.53
nmcli connection up "Wired connection 1"
```

**Linux con `ip` (temporal, se pierde al reiniciar):**

```text
sudo ip address add 192.168.40.34/27 dev eth0
sudo ip route add default via 192.168.40.33
```

El nombre de la interfaz o de la conexión (`Ethernet`, `eth0`, `Wired connection 1`…) varía según el equipo: compruébalo antes con `Get-NetAdapter`, `ip address` o `nmcli connection show`. Otras distribuciones usan otros sistemas persistentes (por ejemplo, *netplan* en Ubuntu Server); los parámetros siguen siendo los mismos.

# 12. DHCP: asignación dinámica de parámetros IPv4

Cuando ya entendemos qué parámetros necesita un host, podemos automatizar su entrega. Configurar a mano cientos de equipos es lento y provoca errores (direcciones duplicadas, gateways equivocados). **Dynamic Host Configuration Protocol (DHCP)** permite que un servidor proporcione la configuración de red a los clientes a partir de lo que hemos definido en el plan de direccionamiento.

DHCP no sustituye al diseño: el servidor entrega exactamente lo que le hemos configurado, correcto o no. Por eso relacionamos cada pieza de DHCP con el plan IPAM y con la verificación en el cliente.

| Concepto | Pregunta que responde | Ejemplo |
|---|---|---|
| **DHCP** (*Dynamic Host Configuration Protocol*) | ¿Cómo recibe un equipo su configuración automáticamente? | cliente en modo «DHCP» |
| **DORA** (*Discover, Offer, Request, Acknowledgment*) | ¿Qué mensajes se intercambian? | 4 mensajes UDP 67/68 |
| **Ámbito o pool** (*scope / address pool*) | ¿Qué direcciones puede repartir el servidor en una red? | `172.16.10.11`–`172.16.10.126` |
| **Exclusión** (*exclusion*) | ¿Qué direcciones no debe repartir nunca? | gateway, servidores, impresoras |
| **Reserva** (*reservation*) | ¿Cómo doy siempre la misma IP a un equipo concreto por DHCP? | MAC de la impresora → `.9` |
| **Concesión** (*lease*) | ¿Durante cuánto tiempo puede usar el cliente la dirección? | 1 día, 8 días |
| **Agente de retransmisión** (*DHCP relay agent*) | ¿Cómo llega el cliente a un servidor de otra red? | se configura en U08 |

> **Dónde se configura en este módulo.** En esta unidad el servidor DHCP es un equipo servidor (el servicio *DHCP* de un servidor en Packet Tracer, o un servidor Windows/Linux). Configurar un **router Cisco** como servidor DHCP (`ip dhcp pool`) y como relay (`ip helper-address`) se trabaja en U08, cuando ya se administran routers.

## 12.1. Parámetros que puede entregar

Entre otros:

- dirección IPv4;
- máscara/prefijo;
- default gateway;
- servidor DNS;
- tiempo de concesión.

DHCP automatiza la entrega. No cambia el significado de esos parámetros.

## 12.2. DORA

El intercambio inicial simplificado se representa como:

```text
Discover
→ Offer
→ Request
→ Acknowledgment
```

En U02 observamos este intercambio como tráfico. Aquí lo relacionamos con el **plan de direccionamiento**.

| Mensaje | Quién lo envía | Para qué | Direcciones típicas |
|---|---|---|---|
| **Discover** | Cliente | «¿Hay algún servidor DHCP?» | `0.0.0.0` → `255.255.255.255` (broadcast) |
| **Offer** | Servidor | «Te ofrezco esta IP y estos parámetros» | servidor → cliente |
| **Request** | Cliente | «Acepto la oferta de este servidor» | `0.0.0.0` → `255.255.255.255` (así se enteran todos los servidores) |
| **Acknowledgment (ACK)** | Servidor | «Confirmado: la concesión es tuya» | servidor → cliente |

DHCP usa **UDP**: el servidor escucha en el puerto **67** y el cliente en el **68**. Como el cliente todavía no tiene dirección, empieza con origen `0.0.0.0` y destino broadcast; por eso, sin ayuda de un relay, los mensajes no salen de la red local.

## 12.3. DHCP pool

Un **pool** es el conjunto de direcciones que el servidor puede entregar dinámicamente para una red determinada.

Debe ser coherente con:

- red;
- prefijo;
- gateway;
- exclusiones;
- otras opciones.

## 12.4. Exclusiones

Una dirección excluida no debe asignarse dinámicamente.

Ejemplos habituales:

- gateway;
- interfaces de infraestructura;
- determinados servidores;
- impresoras con configuración fija.

## 12.5. Reserva

Una **reservation** permite que un cliente concreto reciba una dirección prevista mediante el mecanismo del servidor DHCP.

No es lo mismo que configurar manualmente esa dirección en el cliente.

Normalmente la reserva se asocia a la **dirección MAC** del cliente: el equipo sigue configurado en modo DHCP, pero el servidor le entrega siempre la misma IP. La ventaja es que la dirección queda gestionada y documentada en un único lugar.

## 12.6. Lease

La asignación dinámica es una **concesión temporal**.

Conviene poder interpretar:

- dirección obtenida;
- máscara/prefijo;
- gateway;
- DNS;
- servidor DHCP;
- duración de la concesión.

El cliente no espera a que la concesión caduque: a mitad del tiempo (50 %, llamado T1) intenta **renovarla** con el mismo servidor; si no lo consigue, vuelve a intentarlo con cualquier servidor hacia el 87,5 % (T2). Si la concesión caduca sin renovarse, el cliente deja de usar la dirección.

Comandos útiles en el cliente:

```text
Windows:  ipconfig /all        (servidor DHCP, concesión obtenida y fecha de caducidad)
          ipconfig /release    (libera la concesión)
          ipconfig /renew      (pide una nueva)
Linux:    ip address           (dirección y tiempo de validez restante, valid_lft)
          sudo dhclient -r eth0 ; sudo dhclient eth0   (liberar y pedir, si se usa dhclient)
          nmcli connection up "<conexión>"             (con NetworkManager)
```

## 12.7. Verificación en el cliente

No basta con afirmar:

> «Ha obtenido una IP, luego DHCP funciona correctamente».

Debemos comprobar que los parámetros recibidos son los esperados.

Ejemplo:

```text
IP correcta
máscara correcta
gateway incorrecto
```

El cliente ha recibido una concesión, pero la configuración no es funcional para destinos remotos.

## 12.8. Cuatro fallos típicos

Cada fallo de DHCP deja un patrón de síntomas distinto. Reconocer el patrón ayuda a elegir la primera prueba, pero no sustituye a la evidencia.

| Fallo | Síntoma típico en el cliente | Primera comprobación útil |
|---|---|---|
| Sin dirección válida | Sin IP o con `169.254.x.x` (APIPA) | ¿Hay enlace? ¿El servidor está activo, en la misma red (o con relay) y con direcciones libres? |
| Gateway incorrecto | Local sí, remoto no | Comparar el gateway recibido con el plan y con la red calculada |
| DNS incorrecto | `ping` por IP sí, por nombre no | `nslookup` y DNS recibido en `ipconfig /all` |
| Pool invade una estática | Conflictos de IP intermitentes | Comparar el pool con las exclusiones y la tabla IPAM |

### Sin dirección válida

Posibles ámbitos de investigación:

- servicio DHCP no disponible;
- cliente sin acceso al servicio;
- pool agotado;
- configuración incorrecta;
- problema de enlace o acceso.

No debemos elegir una causa sin evidencia.

Si el cliente muestra `169.254.x.x/16`, sabemos algo concreto: el equipo pidió configuración por DHCP y **no recibió respuesta**, así que se autoasignó una dirección de enlace local (APIPA). Con ella solo podría hablar con otros equipos en la misma situación; no tiene gateway.

### Dirección correcta, gateway incorrecto

Síntoma posible:

```text
comunicación local → sí
comunicación remota → no
```

### DNS incorrecto

Posible patrón:

```text
IP correcta
gateway correcto
ping a destino remoto por IP funciona
resolución de nombres falla
```

### Pool invade una dirección estática

Puede producir conflictos o asignaciones incoherentes.

## 12.9. DHCP relay

Cuando cliente y servidor DHCP se encuentran en redes distintas puede ser necesario un mecanismo de **relay**.

En U04 basta con reconocer la necesidad: el Discover es un broadcast y los routers no reenvían broadcasts. Un **agente de retransmisión** (*relay agent*), normalmente el router de la red del cliente, recoge ese broadcast y lo reenvía como unicast al servidor. Lo configurarás en U08 (`ip helper-address`), cuando ya domines el routing entre redes.

## 12.10. Cómo se ve en un servidor DHCP

Los conceptos son los mismos en todos los servidores; cambian los nombres de las opciones.

| Concepto | Servidor de Packet Tracer (*Services → DHCP*) | Windows Server (rol DHCP) | Linux (isc-dhcp-server / Kea) |
|---|---|---|---|
| Red y máscara | *Subnet Mask* (la red la marca *Start IP Address*) | Ámbito (*scope*) con máscara o longitud | `subnet … netmask …` / `"subnet"` |
| Rango repartible | *Start IP Address* + *Maximum Number of Users* | Intervalo inicial y final del ámbito | `range` / `"pools"` |
| Exclusiones | Implícitas: lo que queda fuera del rango | Intervalo de exclusión | Lo que queda fuera de `range` |
| Gateway | *Default Gateway* | Opción 003 *Enrutador* | `option routers` |
| DNS | *DNS Server* | Opción 006 *Servidores DNS* | `option domain-name-servers` |
| Reserva | No disponible | Reservas (por MAC) | `host { hardware ethernet …; fixed-address …; }` / `"reservations"` |
| Concesión | No configurable | Duración de la concesión (8 días por defecto) | `default-lease-time` / `"valid-lifetime"` |

Ejemplo en Packet Tracer para la red USERS del plan 10.7 (el servidor tiene IP estática dentro de la red, p. ej. `172.16.10.10/25`, en la zona excluida):

```text
Service:                 On
Pool Name:               USERS
Default Gateway:         172.16.10.1
DNS Server:              172.16.10.130
Start IP Address:        172.16.10.11
Subnet Mask:             255.255.255.128
Maximum Number of Users: 116        (de .11 a .126: 126 - 11 + 1 = 116)
```

Comprobación: el pool termina en `.126`, último host de `172.16.10.0/25`; no incluye el gateway (`.1`), ni el servidor (`.10`), ni el broadcast (`.127`).

# 13. Diagnóstico IPv4 basado en evidencias

Un mensaje como:

> «No tengo red»

es un **síntoma**, no una causa. Este apartado reúne todo lo anterior en un método de trabajo: en lugar de probar comandos al azar o cambiar parámetros «a ver si funciona», formulamos una hipótesis, elegimos la prueba que la confirma o la descarta y basamos la conclusión en la evidencia. Es el mismo método que usaste en U01–U03, ahora aplicado a la configuración IPv4.

| Paso | Pregunta que responde | Ejemplo |
|---|---|---|
| **Síntoma** (*symptom*) | ¿Qué observa el usuario? | «No abre ninguna web» |
| **Hipótesis** (*hypothesis*) | ¿Qué podría explicarlo? | gateway fuera de la subred |
| **Prueba** (*test*) | ¿Qué comprobación distingue mis hipótesis? | calcular la red y compararla con el gateway |
| **Evidencia** (*evidence*) | ¿Qué resultado he obtenido? | red `.64/27`, gateway `.1` |
| **Conclusión** (*conclusion*) | ¿Qué afirmo, basado en la evidencia? | el gateway no es local |
| **Cambio mínimo y verificación** (*minimal change / verification*) | ¿Qué corrijo y cómo demuestro que ya funciona? | cambiar solo el gateway y repetir la prueba |

> No confundas un **hecho** («ipconfig muestra…») con una **hipótesis** («podría ser el gateway») ni con una **conclusión** («el gateway es incorrecto porque…»).

Un marco útil es:

```text
síntoma
→ pregunta
→ hipótesis
→ prueba
→ evidencia
→ conclusión
```

Si existe una corrección:

```text
→ cambio mínimo
→ verificación
```

## 13.1. Cadena de dependencias

Ante un problema IPv4 podemos considerar:

```text
interfaz
→ IP
→ prefijo
→ red
→ pertenencia
→ gateway
→ ruta
→ ARP/neighbor
→ destino remoto por IP
→ DNS
→ servicio
```

No debemos ejecutar mecánicamente todos los comandos. La pregunta es:

> **¿qué prueba aporta ahora la información que necesito para distinguir mis hipótesis?**

## 13.2. Hecho, hipótesis y conclusión

Ejemplo:

```text
Hecho:
ipconfig muestra 192.168.50.70/27
```

```text
Hipótesis:
el gateway podría estar fuera de la subred
```

```text
Prueba:
calcular la red del host y comparar el gateway
```

```text
Evidencia:
la red es 192.168.50.64/27 (hosts .65–.94) y el gateway configurado es 192.168.50.1
```

```text
Conclusión:
el gateway configurado no pertenece a la subred local del host
```

La conclusión está vinculada a una evidencia observable.

## 13.3. No modificar antes de comprender

Cambiar parámetros sin saber qué se intenta demostrar puede ocultar el problema original.

Un procedimiento profesional busca:

```text
una hipótesis concreta
→ una prueba adecuada
→ una corrección mínima
→ una verificación posterior
```

# 16. Errores frecuentes que debes evitar

Casi todos los errores de esta unidad tienen el mismo origen: sustituir el cálculo o la evidencia por una impresión («se parecen», «tiene IP, luego funciona»). La tabla resume cada error y la forma correcta de razonar; después se explica cada uno.

| Error | Por qué es un error | Qué hacer |
|---|---|---|
| Deducir la máscara por la clase (*classful assumption*) | Las clases ya no se usan | Usar el prefijo explícito |
| Direcciones próximas = misma subred | La pertenencia depende del prefijo | Calcular el bloque |
| Gateway fuera de la red local | El host no puede alcanzarlo directamente | Comprobar que está en el rango de hosts |
| Memorizar sin comprobar límites | Un bloque solo empieza en múltiplos de su tamaño | Verificar el límite válido |
| Empezar VLSM por las redes pequeñas | Fragmenta el espacio | Ordenar de mayor a menor |
| Reserva DHCP = IP estática manual | Se gestionan en sitios distintos | Distinguir servidor y cliente |
| «Tiene IP, luego DHCP va bien» | Puede haber recibido parámetros erróneos | Comprobar máscara, gateway y DNS |
| Cambiar varios parámetros a la vez | No se demuestra la causa | Un cambio, una verificación |

## Deducir la máscara por la antigua clase

Incorrecto:

```text
192.x.x.x → /24
```

Correcto:

```text
usar el prefijo explícito
```

## Confundir direcciones próximas con misma subred

```text
192.168.1.30
192.168.1.70
```

pueden pertenecer o no a la misma red dependiendo del prefijo. Con `/24` están en la misma red; con `/26` no (`.30` está en `192.168.1.0/26` y `.70` en `192.168.1.64/26`).

## Elegir un gateway fuera de la red local

El host debe poder alcanzar directamente el gateway configurado.

## Memorizar resultados sin comprobar límites

Un prefijo implica un tamaño de bloque y unos límites válidos.

## Empezar VLSM por las redes pequeñas

Puede fragmentar el espacio e impedir ubicar redes grandes.

## Confundir reserva DHCP con IP estática manual

Ambas pueden producir una dirección estable, pero se gestionan de forma distinta.

## Dar por bueno DHCP porque existe una dirección

También deben comprobarse máscara, gateway, DNS y coherencia del plan.

## Cambiar varios parámetros a la vez

Dificulta demostrar cuál era la causa.

# 18. Síntesis final

Al terminar esta unidad debes conservar estas ideas. Están agrupadas en cuatro bloques que siguen el recorrido de la unidad: calcular, decidir, diseñar y operar.

| Bloque | Ideas | Qué debes saber demostrar |
|---|---|---|
| **Calcular** (*calculate*) | 1–4 | Red, broadcast, rango, capacidad y pertenencia de cualquier IP/prefijo |
| **Decidir** (*decide*) | 5 | Si un destino es local o remoto y si el gateway es válido |
| **Diseñar** (*design*) | 6–9 | Un plan FLSM/VLSM sin solapes, con margen, resumible y documentado |
| **Operar** (*operate*) | 10–12 | Configurar (estático o DHCP), verificar y diagnosticar con evidencias |

1. Una IPv4 se interpreta junto con su **prefijo**.
2. El prefijo define qué bits describen la red y qué espacio queda dentro del bloque.
3. Una subred tiene **network address, broadcast, rango y capacidad**.
4. La pertenencia se calcula; no se decide por la apariencia decimal.
5. Un host utiliza el **default gateway** cuando el destino no es local.
6. FLSM divide un bloque en subredes iguales; VLSM permite tamaños distintos.
7. Elegir un prefijo es una decisión de **capacidad y diseño**, no solo una operación matemática.
8. CIDR permite trabajar con prefijos explícitos y realizar agregaciones cuando los límites son correctos.
9. Un plan profesional debe quedar **documentado** mediante IPAM u otra representación mantenible.
10. DHCP automatiza parámetros que primero debemos comprender.
11. Configurar no equivale a verificar.
12. El diagnóstico debe relacionar **hipótesis con pruebas y conclusiones con evidencias**.

El objetivo profesional no es responder rápidamente «qué máscara tiene esta IP», sino poder defender afirmaciones como:

> «Este host pertenece a esta subred, este gateway es localmente alcanzable, este bloque satisface la necesidad prevista y estas pruebas demuestran dónde se encuentra el fallo.»
